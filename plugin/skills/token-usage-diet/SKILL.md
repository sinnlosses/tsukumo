# tsukumo の消費を減らす提案を作る

tsukumo は使用量を2種類の記録に残している。**ターンごと**（`token-usage/<YYYY-MM-DD>.jsonl`、
1行 = 1ターン）と、**セッションごとのコンテキストの内訳**（`context-usage/<YYYY-MM-DD>.jsonl`、
1行 = 1セッション）。置き場は `$TSUKUMO_HOME`（既定 `~/.tsukumo`）。

このスキルの仕事は、**その数から「何を・どれだけ減らせそうか・根拠は何件か」を3点セットで言う**こと。
数を並べるだけでは利用者は動けないし、根拠なしの提案は削ってはいけないものを削らせる。

**返し方は呼ばれた場で変わる。** ツール一覧に `mcp__tsukumo__usage_review_stage` /
`mcp__tsukumo__usage_review_result` があれば（tsukumo の仕事の会話でこのスキルが呼ばれたとき）
**7章の手順**でこの2つのツールに結果を渡す。無ければ（tsukumo の雑談モードなど）、
**3章の形で本文のレポートに書く**。

## 1. まず集計を走らせる

記録は1日で数百行・数百KBになる。**JSONL を `cat` や Read で開かない**——文脈が埋まるうえ、
手で足し合わせると数を間違える。同梱のスクリプトが読み、畳んだ表（90行ほど）だけを返す。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/summarize_usage.py"          # 直近7日（既定）
python3 "${CLAUDE_SKILL_DIR}/scripts/summarize_usage.py" --days 30
python3 "${CLAUDE_SKILL_DIR}/scripts/summarize_usage.py" --since 2026-09-01 --until 2026-09-07
python3 "${CLAUDE_SKILL_DIR}/scripts/summarize_usage.py" --top 20  # 各一覧を厚く見る
```

`python3` が無くて走らないときは、集計できないと断って止める（JSONL を自分で読んで代わりに数えない）。

**期間の既定は直近7日**（今日を終端にした7日間）。利用者が期間を言ったらそれに合わせ、
「最近」「このごろ」程度なら既定のままでよい。長く取るほど1度も呼ばれていないツールの判定は
信頼できるが、古い設定のままの日も混ざる——**30日を超えるときは、その日数を提案に明記する**。

置き場は `--home` でも渡せるが、**既定は `$TSUKUMO_HOME` を尊重する**（分けたホームで動かして
いる利用者がいる）。`--json` で同じ集計を機械向けに出せる（自分でさらに計算したいときと、
提案を構造で渡すときに見積もりの節 `estimates` を読むとき）。

## 2. 表の読み方（ここを取り違えると提案が嘘になる）

- **物差しは費用ではなくトークンの消費量。** 利用者の契約はサブスクリプション（Claude Max）で、
  減らしたいのは利用枠を食うトークンの量。スクリプトの「トークンの消費量」は**入力・キャッシュ読み・
  キャッシュ作成・出力を重みなしで足した数**で、思考は出力に含まれるので足さない。
  **利用枠が種類ごとにどう数えられるか（キャッシュ読みを軽く数えるか等）は公開されておらず、
  確かめていない。** だから重みを推測で置かず、割合は「消費量（重みなし）の約 P%」と言い、
  「利用枠の P%」とは言わない。表の1章の「種類の内訳」は数の比で、利用枠に占める比ではない
- **費用（`costUsd`）は API の単価で換算した参考の額。** サブスクリプションでは払っていない額なので
  提案の物差しにしない。利用者が「いくら使った」と聞いたときだけ、換算の目安だと断って答える
- **「1歩あたり」は1ステップで読み直す文脈の平均。** 1歩ごとに文脈を丸ごとキャッシュ読みするので、
  歩を1つ増やす・減らす重さはこの数。歩の数を論じるときの根拠に使う（表の2章の持ち場の行）
- **ターンの合計は `models` が正典。** 持ち場（main / subagent）の `tokens` は割り振りを見る
  ための下限で、とくに `outputTokens` は確定値でないので合計より小さく出る。**どちらの持ち場が
  文脈を食ったかは入力とキャッシュ読みで見る**（スクリプトはその2つを足した「読み込み」で
  比率を出している）
- **古い版の行（`v=1`）は内訳を持たない。** スクリプトは合計だけ使える行として扱い、
  「内訳の取れた行 N/M」を出す。**その母数を提案にも書く**
- **`deferred` は窓の外。** 使用量には足さない（分類の判定は `kind` で行い、名前では行わない）。
  ただし「定義が重い」という話では材料になる——呼び出せば窓に入ってくる
- **スキルは「使っていない」と言えない。** 呼び出しの記録に残るのは `Skill` という名前だけで、
  どのスキルを開いたかは残らない。だから**重さの一覧までにして、要否は利用者に判断してもらう**。
  合計が `Skills` 分類の何割かは数で言ってよい
- **MCP ツールだけは突き合わせができる。** `mcp__<サーバ>__<ツール>` の名前がそのまま呼び出しの
  記録に出るため。ただし `speak` と `report` は仕組み上ツールの呼び出しとして数えられないので、
  スクリプトが突き合わせから外して別に出す。**その2つを未使用と言わない**

**定義の重さは1セッションぶんの数**として出る。「削ったらどれだけ減るか」は**自分で掛け算せず**、
表の「6. 見積もり」（`--json` なら `estimates` 節）の数を使う。**見積もりだと分かる書き方にし、
測った数のように書かない。**

## 3. 提案の書き方

**ここは本文のレポートで返すとき（ツールが無いとき）の形。** tsukumo の中でツールを呼ぶときは
同じ中身をツールの引数に写す（対応は7.2）。

効きの大きい順に**3〜5件**。多く挙げるほど利用者は選べなくなる。1件はこの形で書く。

```
### <何を削るかが分かる見出し>
- 何を: 具体的にどのファイル・どの定義・どの使い方を変えるか
- どれだけ減らせそうか: 見積もりの節の数（「約 N トークン、期間の消費量（重みなし）の約 P%（見積もり）」）
- 失うもの: 削ると何が無くなるか（無ければ「なし」。4章「無料の削り方とトレードオフ」）
- 根拠: どの数から言っているか（N ターン / M セッション ぶんの記録）と、見積もりの仮定
```

**ドルで言わない。** 「約 $X」は書かない（費用は2章のとおり参考の額）。

**「どれだけ」と効きめは見積もりの節から写す。** 同じ `kind` と `target` の件があれば、その
`estimatedTokens`・`sharePct` を「見積もり」と断って書き、効きめはその件の
`impact`（`large` / `medium` / `small` = 大 / 中 / 小）をそのまま使う。仮定の値（`assumptions`）が
入っている件は「結果を半分に絞れたら」のように仮定ごと書く。`bound` が `upper` の件は
「全部外した場合の上限」と書く。`confidence` が `low` の件は、確かさが低いと添える。

- **見積もりの節に無い提案**（`notEstimated` の種類や、節から落ちた件）も出してよいが、
  「どれだけ」は測った数（表の1〜5章）だけで言い、**割合を作らない**。効きめは多くて「小」にする
- **「全体で約 X%」は `upperBoundSharePct` を足した数として言わない。** 提案どうしが同じ
  キャッシュ読みを削り合うので重なりを除いていない。言うなら「重なりを除かない上限で約 X%」と
  断るか、一番大きい1件の割合（「いちばん効くもので約 P%」）で言う。`status` が
  `unavailable` なら割合は言わない
- **見送った候補を最後に1行ずつ添える**（どの候補を・なぜ出さなかったか。根拠が薄い・失うものが
  大きい・利用者が前に見送った など）。利用者が「見ていない」と誤解しないため

根拠に書くのは**数と、その数を支えている記録の量**。「Bash の結果が大きい」ではなく
「Bash が N 回で合計 X MB、1回あたり Y バイト（内訳の取れた N ターンぶん）」と書く。
**根拠が1〜2件しかない数からは提案を出さない**——外れ値を恒常的な浪費と取り違える。
削ると何が失われるかが明らかなもの（よく呼ぶツール、日々読むメモリ）は、**効きが大きくても
「削らないほうがよい」と添える**。セッションを区切る提案は、区切ると会話の文脈が消える
ことも添える。

### 見積もりの節（`estimates`）の形

`--json` の `estimates` は**固定の形**で、tsukumo の画面やツールに渡す提案へそのまま写せるように
してある。形を変えたら `version` を上げる（読む側はこの数で形の変わり目に気づく。いまは `2`。
`1` は費用を分母にし、各件に `estimatedCostUsd`、節に `unitPrices` を持っていた）。

| キー                 | 中身                                                                                                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`            | 形の版（整数）                                                                                                                                                                |
| `measured`           | いつも `false`（測った数ではない印）                                                                                                                                          |
| `status`             | `ok` か `unavailable`。`unavailable` のときは `items` が空で、`reasons` に理由                                                                                                |
| `reasons`            | 出せなかった理由・一部の種類を出せなかった理由（文字列の配列）                                                                                                                |
| `caveats`            | 見積もり全体の断り書き（main だけを数えた・期間全体へ伸ばした など）                                                                                                          |
| `denominator`        | 割合の分母。`kind` は `consumedTokens`（期間のトークンの消費量。入力・キャッシュ読み・キャッシュ作成・出力の重みなしの和）、`value`、種類ごとの数 `byType`、`cacheReadTokens` |
| `mainReadSharePct`   | 式に入った main の読みが、キャッシュ読みの合計に占める割合                                                                                                                    |
| `thresholds`         | 効きめの境目（`largePct` / `mediumPct`）                                                                                                                                      |
| `assumptions`        | この回に使った仮定の値（`resultTrim` / `memoryTrim` / `sessionThreshold`）                                                                                                    |
| `upperBoundSharePct` | `items` の `sharePct` を足した数。**重なりを除かない上限**                                                                                                                    |
| `items`              | 見積もりの1件ずつ（`sharePct` の大きい順。種類ごとに上位3件まで）                                                                                                             |
| `notEstimated`       | 見積もりを出していない種類と理由（`kind` / `reason`）                                                                                                                         |

`items` の1件の持ち物:

| キー              | 中身                                                                                                                                                                                                                                                                                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`            | 提案の種類。tsukumo の `USAGE_PROPOSAL_KINDS` と同じ語（`unused-mcp` / `memory-file` / `skill-definition` / `tool-result` / `session-length`）                                                                                                                                                                       |
| `target`          | 対象。種類ごとの決まりは tsukumo の `USAGE_PROPOSAL_KIND_TARGETS` と同じ（MCP はサーバ名、メモリはパス、ツールは名前、全体なら空）。作業ツリーごとの `CLAUDE.md`（`Project`）はファイル名で束ねる                                                                                                                    |
| `key`             | 提案の識別子（`kind:target`。tsukumo の `usageProposalKey` と同じ作り方）                                                                                                                                                                                                                                            |
| `estimatedTokens` | 期間中に減っていたトークンの消費量の見積もり（重みなし。`session-length` は増えるキャッシュ作成を差し引いた数）                                                                                                                                                                                                      |
| `sharePct`        | 分母に占める割合（%）                                                                                                                                                                                                                                                                                                |
| `impact`          | 効きめ（`large` / `medium` / `small`）。`sharePct` が 3% 以上で大、0.5% 以上で中。境目の数は費用の割合だった v1 のまま据え置いた（利用枠に照らした較正の材料が無く、変えるのも推測になる）。分母がトークンになって同じ提案の割合は v1 より大きく出る（キャッシュ読みが費用では約2/3、トークンでは約98%を占めるため） |
| `confidence`      | 確かさ（`high` / `medium` / `low`）。定義を外す見積もりは、内訳のあるステップが半分未満だと1段下げる                                                                                                                                                                                                                 |
| `bound`           | `estimate` か `upper`（全部外した場合の上限）                                                                                                                                                                                                                                                                        |
| `basis`           | 根拠の母数（`turns` / `sessions`。種類によって `steps` / `scaledToSteps` / `calls` / `restarts`）                                                                                                                                                                                                                    |
| `assumptions`     | その件が使った仮定の値                                                                                                                                                                                                                                                                                               |
| `note`            | 式の一言                                                                                                                                                                                                                                                                                                             |

見積もりの式（どれも **main の読みだけ**を数える）:

- `unused-mcp`: 期間中1度も呼ばれていないツールの定義（サーバごと）× main のステップ数。
  deferred のぶんは窓の外なので、セッションごとの MCP の分類の used の比で按分して除く
- `memory-file`: ファイルの大きさ × main のステップ数 × 削れる割合（`--memory-trim`、既定 0.3）
- `skill-definition`: スキルの定義の合計 × main のステップ数（上限。どれを外すかは利用者が決める）
- `tool-result`: 結果のトークン（4バイト/トークン）× そのあとに続く main のステップ数
  （そのターンの残りは半分とみなす）× 絞れる割合（`--result-trim`、既定 0.5）。自動圧縮の時点は
  記録に無いので、1ステップあたりの読みが前のターンの半分を下回ったところで打ち切る。それでも大きめに出る
- `session-length`: main のコンテキストがしきい値（`--session-threshold`、既定 200,000）を
  超えた時点で区切り、土台（定義ぶん）から作り直したとして減る読み − 区切りで増えるキャッシュ作成

**「1ステップあたりのキャッシュ読み ≒ コンテキストの大きさ」は main でだけ確かめてある**
（セッションの内訳の使用量と2分以内のターンで中央値 0.99 倍）。subagent はコンテキストの記録が
無く確かめられないので、ステップに掛ける式には使わない（見積もりは小さめに出る）。
`model-choice` は見積もらない。モデルの単価の違いはトークンの数を変えず、持ち場ごとのモデルの
内訳も記録に無く「移せるターンの割合」が推測にしかならないため（4章の終わり）。`subagent-share` と `cache-reuse` は比率の診断で、減る量の式が無い。

## 4. 何を候補にするか

表から**必ず検討する**もの。全部を提案に載せる必要はなく、数が小さいもの・根拠が薄いものは
落としてよい（落としたことは一言添えると、利用者が「見ていない」と誤解しない）。

1. **定義は重いが1度も呼ばれていない MCP ツール** — 突き合わせで出せる唯一の「確かな無駄」。
   毎回必ず検討する。サーバ単位で未使用がまとまっているなら、**そのサーバごと外す**提案にする
   （ツール単位より現実的に手が打てる）
2. **メモリファイルの大きさ** — `CLAUDE.md` 系が使用量の何割を占めているか。同じ内容の
   `CLAUDE.md` が作業ツリーの数だけ並ぶ形なら、重複ではなく「1セッションに載るのは1つ」なので
   **合算しない**（1件あたりの大きさで言う）
3. **スキルの定義の重さ** — 合計と重い順。呼び出し実績とは突き合わせられないと断る
4. **サブエージェントの持ち場の比率** — 読み込みの何割がサブエージェント側か。比率が高いなら、
   渡す文脈の量・起こす数・使うモデルが論点になる
5. **結果のバイト数が大きいツール** — 1回あたりが大きいものは、絞り込み（`head`・行数制限・
   範囲指定の読み）で効く。回数が多いものは使い方そのものが論点
6. **キャッシュ作成とキャッシュ読みの比** — 読み/作成の倍率が低いなら、文脈を作り直している
   （セッションを切りすぎ・前置きを変えすぎ）。高いなら定義を減らす効きがそのぶん大きい

### 無料の削り方とトレードオフ

提案ごとに**失うもの**を書く（3章の「失うもの」）。種類ごとの目安:

| `kind`                                            | 失うもの                                                                               |
| ------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `unused-mcp`                                      | 期間中に呼ばれていないなら、なし（無料）。まれに使うツールなら、使うときに足し直す手間 |
| `memory-file`                                     | 削った指示。守られなくなる決まりが出る                                                 |
| `skill-definition`                                | 外したスキルが自動で呼ばれなくなる                                                     |
| `tool-result`                                     | 絞った結果の情報。読み直しで歩が増えると逆効果                                         |
| `session-length`                                  | 区切った時点までの会話の文脈                                                           |
| `subagent-share` / `cache-reuse` / `model-choice` | 何を変えるか次第（提案の中で書く）                                                     |

### cost-optimize 由来の分析の取捨（2026-09-25）

`/claude-api cost-optimize`（API のアプリ向けの費用削減）が出した分析のうち、トークンの物差しで
意味を持つものだけを取り入れた:

- **種類別の内訳 — 取り入れた（表の1章「種類の内訳」、`totals.overall.typeSharePct`）。** ただし
  重みなしのトークンの比で、ドルで割った比ではない。どの種類が数を占めるか（いまはキャッシュ読みが
  ほぼ全部）を見て、どの提案が効くか（文脈を小さくする・歩を減らす）の見当に使う
- **モデルと effort — 取り入れない。** モデルの単価の違い（Opus 5 → 5.5 でキャッシュ読みが安い等）は
  トークンの数を変えないので、この物差しでは効きが消える。effort は出力と思考の量を変えうるが、
  記録に effort が無く、出力（思考を含む）は消費量の1%に満たないので効きを測れない
- **歩数 — 一部だけ取り入れた（表の2章「1歩あたり」、`scopes.rows.*.readPerStep`）。** 1歩ごとに
  文脈を丸ごと読み直すのはトークンでもそのまま効く。ただし `speak` だけの歩の数は記録に無い
  （`speak` は `tools[]` に残らない）ので、減らせる歩の数を置くと推測になる。見積もりは出さず、
  1歩の重さを測った数として根拠に使うまでにする
- **無料とトレードオフの区別と見送りの一覧 — 取り入れた（上の表と3章）。** トークンでも「失うもの
  なしで減る」か「何かと引き換えか」は利用者の判断に要る。画面の提案の型は変えず、失うものは `basis` の文面に
  書く（7.2）。見送りの一覧は本文のレポートで返すとき（3章）だけ添え、ツールで返すときは渡す欄が
  無いので省く

## 5. 記録が少ない・内訳が無いとき

**黙って0を出さない。** スクリプトは「何日ぶんあるか」「内訳の取れた行はいくつか」を先頭に出す。
それをそのまま断り書きにする。

- 記録が1件も無い: 提案を作らない。期間か置き場（`$TSUKUMO_HOME`）を確かめる案内に留める
- ターンの記録はあるが**セッションの内訳が無い日がある**: メモリ・スキル・MCP 定義の重さと
  「呼ばれていないツール」は出せない。**出せないと言ってから**、出せるほう（合計・持ち場・
  ツール別・キャッシュ比）で提案する
- 要求した日数より記録が短い: 「7日を見たが記録は2日ぶん」と書いてから提案する。
  短い期間で「1度も呼ばれていない」と言うときは、**その日数を根拠に添える**

## 6. 記録の扱い

この記録には会話の文面は入っていないが、**同じ扱いをする**。

- **外部へ送らない。別の場所へ複製しない。** 集計結果を別のファイルに書き出すのは、利用者が
  頼んだときだけにする（スクリプトはどこにも書かない）
- メモリファイルのパス・スキル名・MCP ツール名は内訳に出る。**提案に必要な範囲でだけ**使い、
  一覧を丸ごと貼らない
- `~/.claude/settings.json` は読むだけでよく、このスキルからは書き換えない。設定を変える
  提案は、変更そのものではなく**変更案として**利用者に出す

## 7. tsukumo の中で見直しの2つのツールを呼ぶ

ツール一覧に `mcp__tsukumo__usage_review_stage` と `mcp__tsukumo__usage_review_result` が
あるとき（冒頭で確かめた場合分けのとおり）は、本文のレポートではなくこの2つの
ツールで結果を返す。**tsukumo が結果を札に描く**ので、本文を長く書かない（7.3）。

### 7.1 段ごとに `usage_review_stage` を呼ぶ

段に入る**前**に必ず呼ぶ（`days` は1章の集計と同じ期間）。節とツールの `stage` の対応（呼ぶ順も
このまま）:

| 対応する分析                                                                   | `stage`                                      |
| ------------------------------------------------------------------------------ | -------------------------------------------- |
| 1章の集計を走らせた直後、表の「モデル別」を見るとき                            | `model`（モデルの使い分けを見る）            |
| 「6. 見積もり」のキャッシュ作成/読みの比、4章6を見るとき                       | `cache`（キャッシュの効き方を見る）          |
| 4章1（未使用 MCP）・4章5（結果の大きいツール）を見るとき                       | `tool`（ツールの呼び方と結果の大きさを見る） |
| 4章2（メモリ）・4章3（スキル定義）・4章4（サブエージェントの持ち場）を見るとき | `context`（コンテキストの中身を見る）        |
| 3章の形に沿って提案をまとめ、`usage_review_result` を呼ぶ直前                  | `proposal`（見直し案をまとめる）             |

戻り値が `"ok"` だけならそのまま次へ進む。`"ok"` のあとに「利用者が見送った提案（種類:対象）」の
一覧が付いていたら、その `kind:target` の組は候補に挙がっても `usage_review_result` の
`proposals` に入れない。「タスク運用なし」の行が付いていたら、`followUp` に `task` を使わない（7.2）。

### 7.2 提案を `usage_review_result` の引数に写す

3章で決めた1件（見出し・何を・どれだけ減らせそうか・根拠）を、次の対応でツールの引数に写す。
専用の欄が無い要素は隣の欄にまとめて書く:

| 3章の要素                              | 引数                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------- |
| 見出し                                 | `title`                                                                     |
| 何を                                   | `action`                                                                    |
| どれだけ減らせそうか + 失うもの + 根拠 | `basis`（見積もりの数値はトークンで。ドルは書かない。失うものも一言添える） |
| 効きめ                                 | `impact`（2章「見積もりの節から写す」の基準のまま）                         |

`kind` / `target` は4章の候補番号との対応で決める:

| 4章の候補                                                       | `kind`             | `target`                         |
| --------------------------------------------------------------- | ------------------ | -------------------------------- |
| 1. 未使用 MCP ツール                                            | `unused-mcp`       | サーバ名                         |
| 2. メモリファイルの大きさ                                       | `memory-file`      | ファイルのパス                   |
| 3. スキルの定義の重さ                                           | `skill-definition` | スキル名（定義全体なら空）       |
| 4. サブエージェントの持ち場の比率                               | `subagent-share`   | 空                               |
| 5. 結果のバイト数が大きいツール                                 | `tool-result`      | ツール名                         |
| 6. キャッシュ作成/読みの比                                      | `cache-reuse`      | 空                               |
| 見積もりの `session-length`（4章に無いが「6. 見積もり」に出る） | `session-length`   | 空                               |
| モデルを移す提案（見積もらない。出すなら測った数だけで言う）    | `model-choice`     | 移す先のモデル（決めないなら空） |

`followUp` は、**この会話の中でそのまま tsukumo に頼めば完結する**もの（設定ファイルを1行削る・
メモリの行を削る、など）なら `delegate`、**調査や実装が要る・その場では決め切れない**もの
（しきい値を決める・コードを変える・モデルを移す判断そのもの）なら `task` にする。迷ったら
`task`（生煮えの依頼を `delegate` で送らない）。**ただし `usage_review_stage` の戻り値に
「タスク運用なし」と出たら `task` を使わず、すべて `delegate` にする**（タスクにする置き場が無い）。

`headline` は1〜2文、キャラクターの口調で「見てきたぞ！効きそうなのは○つ。」に続ける。「○つ」は
`impact` が `large` か `medium` の提案の件数。そのあとの「約X%」は2章「見積もりの節から写す」の
割合のルールに従う（`upperBoundSharePct` をそのまま足さない。言うなら重なりを除かない上限か
いちばん効く1件の割合と断り、`estimates.status` が `unavailable` なら言わない）。

`usage_review_result` が受け付けられないと、`isError` 付きの理由（件数超過・空欄・重複・
見送り済みの混入・タスク運用なしでの `task` のどれか）が返る。理由に従って直し、`usage_review_stage` は
やり直さずに `usage_review_result` だけ呼び直す。

### 7.3 report ゲートとの折り合い

仕事の会話は**ターンの最後に必ず `report` ツールを呼ぶ決まり**（`Stop` の関所）。この決まりは
`usage_review_result` を呼んでも免除されない——関所が数えるのは `report` の呼び出しの有無だけで、
見直しの2つのツールは対象外。

だから、`usage_review_result` が受け付けられたら**そのあとに `report` を1回呼ぶ**。
`conclusion` は「見直し完了。提案◯件を渡した。」程度の1〜2文でよい。提案の中身は札に描かれるので
`sections` で繰り返さない（`favor` も無ければ省く）。締めの一言は `report` の `closing` に入れる。
