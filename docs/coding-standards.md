# コーディング規約の詳細

`CLAUDE.md`「コーディング規約・レビュー方針」にルールの一覧がある。**ここにはその理由と例外**
だけを書く（ルール本体はCLAUDE.md側が正典で、二重に書かない）。`/code-review` のStandards軸は
この2つを合わせて評価軸にする。

実装スタックは **Bun + TypeScript**。チェックコマンドは `bun run check`
（`tsc --noEmit` → `oxlint` → `oxfmt --check` → `bun test`）。

## 関数の並び順

ファイル内で「外から使うもの → その内部で使うもの」の順に並べ、`export` された関数を上に、
そこからしか呼ばれない非公開関数を下に置く。非公開関数同士は呼ばれる順に並べる。

読む人がファイルを開いて最初に目にするのが、そのファイルの公開インターフェースになるように
するため。目次を別に置かなくてもファイルの先頭が目次として働く。

### テストのためだけに公開しない

非公開関数は、`export` された関数の振る舞いを通して検証する。テストのために `export` すると、
「このファイルの公開インターフェース」がテストの都合で膨らみ、上の並び順の意味も崩れる。

テストのその他の規約（置き場所・モック・カバレッジ・消す/足すの判断）は下の「テスト」節。

## 変数は基本イミュータブル

再代入が必要に見える場合はまず、値を返す関数に切り出せないかを検討する。ループカウンタや、
例外処理で外側のスコープに結果を持ち出す必要があるなど、可変が自然な場合はその限りではない。

変数は基本 `const`。不変性はローカル変数だけでなくコレクションにも適用する
（`readonly` フィールド・`readonly T[]`・`ReadonlyMap`）。**引数として渡した入れ物が
呼び出し先で書き変わる契約にしない。** サイドカーは「読む → 決める → 描く」を繰り返す
ループなので、途中の入れ物が書き変わると「今フレームの入力」がどこにも残らなくなる
（`docs/architecture.md` 原則2）。

## 型を迂回するキャストを使わない

次を書かない: `as` キャスト、`any`、非nullアサーション `!`、`@ts-expect-error` /
`@ts-ignore`。必要になったのは、**その値の型が実際の中身と合っていない**という合図なので、
迂回ではなく型のほうを直す。`any` は oxlint の `typescript/no-explicit-any` で error にしてある。

**唯一の逃げ道は「境界で検証してから内側の型に変換する」こと。** `unknown` で受けて検証関数を
通し、通った値だけを内側の型として返す。この変換関数の中でだけ、検証済みであることを根拠に
型を確定させてよい。

外部由来の値（transcript の1行、キャラクター定義ファイル、環境変数）は**構造が信用できない**
ので、境界で検証してから内側の型に変換する。検証を通っていない値が内側に入らないよう、
変換は1箇所の関数に封じ込める。

## 型注釈より `satisfies`

定数・テーブル・設定オブジェクトの定義は、型注釈（`const x: T = …`）ではなく `satisfies` で
形を検査する。

```diff
-const PORTRAITS: Record<Expression, string | undefined> = { … }
+const PORTRAITS = { … } satisfies Record<Expression, string | undefined>
```

型注釈は値の型を `T` に**広げる**ので、どのキーが実際にあるか・どの文字列リテラルだったかが
その場で失われる。`satisfies` は `T` を満たすかどうかだけを検査し、値の型はリテラルのまま残す。
`Object.keys` で取り出したキーが `string` に潰れない、使っていないキーが型から見える、といった
差になって効く。

`as` の代替としても使う。「この形になっているはず」と言いたいだけなら `satisfies` で
**検査させる**（`as` は検査せずに黙らせる。上の「型を迂回するキャストを使わない」）。

例外は、値より先に型が必要なとき — 再帰的な型、関数の引数・戻り値、`useState<T>` のような
型引数。ここは注釈でよい。

## エラーハンドリング

**サイドカーは常駐プロセスであり、描画1回の失敗で落ちてはいけない**
（`docs/requirements.md`「5. 実行環境・非機能要件」）。エラーは2チャネルに分ける:

| 種類                                                                                      | 扱い                                                     |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 起動時に前提が満たされていない（transcript のパスが分からない、定義ファイルが壊れている） | 例外を投げて**即時終了**。理由を1行で表示する            |
| 動作中の一時的な失敗（JSONLの行が途中まで、画像が読めない、端末が狭い）                   | **その回の描画だけ諦めて次へ進む**。落ちない             |
| 画像プロトコルが使えない                                                                  | エラーではない。テキストのみのフォールバックへ切り替える |

**描画ループの中に `try`/`catch` を散らさない。** 1回分の描画をまるごと包む場所を1つ決め、
そこで受け止める。散らすと「どこまで描けたのか」が分からなくなり、部分的に壊れた画面が残る。

## 外部の入力を読む場所を1つにする

環境変数・ホームディレクトリ・transcript のパス・キャラクター定義のパスといった
**外の世界に依存する値は、読み取りを1つのモジュールに集約する**。モジュールのトップレベルで
環境変数に触らない（読み取りの順序に依存し、テストから差し替えられなくなる）。

集約すると、テストで環境を差し替える手段が1つで済み、「この値はどこで決まったのか」を
探す場所も1つになる。

## コメント

**コードから読み取れないことだけ**を書く。型名・フィールド名・関数名の言い換えは書かない。

残すかどうかは**長さではなく種類**で決める。行数の目安は置かない（数字を置くと、種類の基準の
代わりにその数字が基準として使われるため）。

| 種類                                                                      | 扱い                                       |
| ------------------------------------------------------------------------- | ------------------------------------------ |
| 今の挙動の制約・前提（この順序でなければならない理由など）                | コードに残す。必要なだけ長くてよい         |
| 外部との対応関係（transcript のどの `type` 由来か、端末プロトコルの挙動） | コードに残す。必要なだけ長くてよい         |
| 昔はこうだった（過去の実装・過去の設計の経緯）                            | 長短にかかわらず正典へ移し、コードから消す |

正典の対応:

| 書きたいこと   | 置き場所               |
| -------------- | ---------------------- |
| 設計判断・経緯 | `docs/architecture.md` |
| ドメイン用語   | `docs/glossary.md`     |
| 要件           | `docs/requirements.md` |

経緯をコードから消すときは、**先に正典の該当箇所を確認する**。既に書かれていれば消すだけ、
無ければ正典に書いてから消す。

レビューでは各段落に次を1問だけ問う: **「この段落はコードの今の挙動を説明しているか、昔の話か」。**
昔の話なら正典へ移す。この判定は機械化しない（日本語の過去形は外部挙動の記録にも使われ、
語での検出は誤検知が多すぎる）。

## 「無いかもしれない」値

「無いかもしれない」プロパティは `readonly x: T | undefined` で書き、`?:` のオプショナル
プロパティ記法は使わない。`?:` は「キー自体が無い」場合まで許してしまい、渡し忘れが型で
見えなくなる。`readonly x: T | undefined` なら値の受け渡しのたびに `undefined` を明示させられる。

例外は、それ自体を丸ごと省略できるオプション引数の中身（既定値を持つ調整用のつまみ）。
「値が無い」を表しているわけではなく、`| undefined` にすると呼び出し側が使わないつまみまで
毎回書くことになる。

`tsconfig.json` の `noUncheckedIndexedAccess` を有効にしてあるので、配列・レコードの
インデックスアクセスは自動的に `| undefined` になる。**これを `!` で潰さない**（上の
「型を迂回するキャストを使わない」）。

**「無い」を型から消すことを目的にしない。** なぜ「無い」が生まれるのかを先に問い、
値の持ち主や取得のタイミングが正しくないなら**そちらを直す**。構造が正しければ残る「無い」は
本物の情報なので消さない。

- **許容する**: 外の世界の「無い」をそのまま写しているもの。transcript にまだ assistant の行が
  1つも無い、状態ファイルがまだ書かれていない、キャラクター定義に該当する表情が無い、
  環境変数の未設定。要件を変えても消えない情報なので、正直に表す
- **避ける**: プログラムの都合で生まれたもの。具体的には次の3パターン
  - 実行時には到達しないのに型に残っている「無い」
  - 1つの「無い」に複数の意味が乗っているもの（「まだ読んでいない」と「本当に無い」の両方）
  - 既定値が確定しているのに層をまたいで運ばれているもの

### 複数の「無い」が1つの状態

2つ以上の `| undefined` が**同じ1つのこと**を表しているなら、フィールドを並べず判別可能な
合併型（タグ付き合併）にする。

```ts
// 避ける: 8通り書けるのに、実在するのは3つ
readonly turnInProgress: boolean
readonly turnStartedAt: number | undefined
readonly turnFinishedAt: number | undefined

// こうする
readonly turn:
  | { readonly kind: "idle" }
  | { readonly kind: "running"; readonly startedAt: number }
  | { readonly kind: "finished"; readonly startedAt: number; readonly finishedAt: number }
```

並べると、**型としては書けるのに起きない組み合わせ**（終わっているのに始まっていない、など）が
残る。読む側はそれを毎回 `=== undefined` の組み合わせで解き直すことになり、同じ解読が使う場所の
数だけ複製される。合併型なら分岐は `turn.kind` の1つで済み、各状態に**その状態でだけ意味を持つ
値**を持たせられる。

判断の目安は「**片方だけが `undefined` になる状態が実在するか**」。しないなら1つの状態なので
合併型にする。

### 「無い」を層をまたいで運ばない

「無い」が本物なのは、外の世界と接する**入口だけ**。そこで畳んでから内側へ渡し、内側の関数は
「必ず値がある」型で受ける。畳み方は2つ — 既定値に置き換える（`??`）か、呼び出し側で分岐して
「ある」場合にだけ内側を呼ぶ。

`T | undefined` を受ける関数が数珠つなぎになると、**どの層で「無い」が確定するのか**が
分からなくなり、同じ `undefined` チェックが各層に散る。内側の関数は自分の仕事に集中できず、
「値が無いときにここは何を返すべきか」をその都度決めることになる。

### null は自前の型に出さない

`null` を書いてよいのは次の3つだけ:

- React の作法 — `useRef<T>(null)` の初期値、「何も描かない」を表す `return null`
- 外来 API の戻り値をそのまま受ける場所 — `localStorage.getItem`、`child_process` の `error`、
  SDK の `parent_tool_use_id`
- `typeof value === "object" && value !== null` の型ガード

自分で定義する型・関数の戻り値・`shared` の型には出さない。外来の `null` は**受け取った境界で
`undefined` に畳む**。「無い」の表し方が2つあると、チェックが `== null` か `=== undefined` かで
揺れ、どちらが起きうるのかを呼び出し側が毎回確かめることになる。この判断を境界の1箇所に寄せる。

## 会話内容の扱い

**このリポジトリ固有の規約で、優先度が最も高い。** transcript には利用者と Claude の
生の会話が入っている。**SDK のイベント（ターンの本文・ツールの入力と結果・`speak` の引数）も
transcript と同じ扱いにする。**

- **外部に送らない。** 解析サービス・テレメトリ・クラッシュレポートを含め、ネットワークに
  出す経路を作らない
- **別の場所に複製しない。** キャッシュ・一時ファイル・バックアップとして transcript の
  内容を書き出さない。**禁じているのは「書き出す」ほうで、正典（claude 自身が
  `~/.claude/projects/` に書く transcript）を読んでメモリ上のビューを組み直すのは複製に
  あたらない**（セッションの復元。`docs/requirements.md` 4.8）。読んだものはプロセスの
  メモリに留め、`127.0.0.1` のビュー以外へ出さない
- **ログに全文を出さない。** デバッグ時も、出すのは長さ・行数・`type` のような**中身を
  含まない情報**にとどめる。文面そのものを出す必要があるときは、その場限りにして
  コミットしない
- **テストのフィクスチャに実物を使わない。** SDK のイベントや JSONL のフィクスチャは、
  手で書いた架空の会話にする

**会話は tsukumo のプロセスの外へ出さない。** SDK は claude を子プロセスとして起こすだけ、
`speak` はプロセス内の MCP ツール（戻り値は `"ok"` だけ）、ビューは `127.0.0.1` にだけ配る。
ここに外へ出る経路を足さない。

**ブラウザ側で会話の状態を持つこと（移行後の `SessionState`）は、外へ出すことにあたらない。**
同じマシンの同じオリジン（`127.0.0.1`）のタブのメモリに閉じるためで、いまも DOM として同じものを
持っている。**`localStorage` などブラウザ側の永続化に会話を置かない**（置いてよいのは領域の比率の
ような画面の都合だけ。`docs/design.md` 9章）。

## 層と依存の向き

**2026-09-13 の移行後、`src/` は層をディレクトリで表す**（設計は `docs/design.md` 2章）。
**2026-09-16 にサーバ側を `core`（判断）と `adapter`（境界）に割り、2026-09-20 に層の名前を
実行環境に合わせて `shared`（サーバとブラウザ）/ `browser`（ブラウザ）へ改名し、サーバ側の
2つを `src/server/` の下へ入れ子にした。**
**新しいファイルは、まずどの層かを決めてから置く。**

**4つの層（`shared` / `server/core` / `server/adapter` / `browser`）が何を置き、どこへ import して
よいかの表は
二重に書かず `docs/design.md` 2章「層と依存の向き」を正典とする**（`src/browser/` の箱の表と
同じ扱い）。ここには、その表だけでは読み取れない決まりを書く。

`src/cli.ts` は配線なので全部を import してよい。**`core` と `browser` は互いを import しない。**
**`core → adapter` も禁止**で、`core` は `node:` / `@anthropic-ai/*` / `ws` を import しない
（外の世界へ出る道が無い）。両者を結ぶのは `cli.ts` だけ。`adapter` は**1ファイル = 1つの境界**で、
インターフェースは切らない（実装が2つあるもの — 駆動とホスト — だけ契約の型を `core` に置く）。
`shared` は `node:` にも `document` にも触らない（両方の実行場所で動くため）。**許した辺以外は
`test/architecture.test.ts` が落とす**ので、向きを変えたくなったら先にこのテストと `docs/design.md`
2章を直す。

**`browser` 層の中も、箱（`main.tsx` / `features/` / `components/` / `lib/` / `stores/`）ごとに
import してよい先が決まっている**（表は二重に書かず `docs/design.md` 2章「`src/browser/` の箱と、
置く基準」を正典とする）。この縦の辺も `test/architecture.test.ts` が落とす。

**ファイルは単数形にする。** 複数は「複数返す」関数名の側で表す（`task-summary.ts` の
`readTaskSummaries`）。理由は、ファイル名が**概念**を指すため（原則5）。概念は1つで、いくつ返すかは
関数の都合。

**ディレクトリも単数形。ただし `src/browser/` の置き場所のディレクトリだけ例外**（2026-09-16）。
`features/` `components/` `lib/` `stores/` `styles/` は bullet-proof-react の名前をそのまま使う
（名前が広く知られていることのほうが、単数形で揃うことより読み手の助けになる、というユーザーの
選択）。**例外はこの5つだけ**で、`src/shared/` `src/server/core/` `src/server/adapter/` と、機能の中の
ディレクトリ・ファイル名は単数形のまま（`features/main-view/markdown/` のように**概念の名前**を
付ける）。**`utils/` `helpers/` `common/` は引き続き作らない**（bullet-proof-react にある
`utils/` も採らない。理由と、`src/browser/` の箱ごとの置く基準は `docs/design.md` 2章）。

**barrel file を作らない。** ディレクトリに `index.ts` を置いて中身をまとめて re-export しない
（import は実ファイルを直接指す）。理由は2つ: (1) 束ねるときの tree-shaking が効かなくなる
（`browser` は `bun build` で1本に束ねる。`docs/design.md` 11章）。(2) `index.ts` という名前自体が
「置き場所を名前にしたファイル」になり、原則5に反する（ディレクトリ名がすでに概念や置き場所を
表すのに、その中の `index.ts` は何も指さない。**ディレクトリ名の例外を足した後も、ファイル名は
概念のまま**）。2026-09-13、`src/browser/` を切った段（`docs/design.md`
12章 段3）で bulletproof-react の実例と突き合わせて決めた。

## React

React 19。関数コンポーネントと Hooks だけを使う（クラスコンポーネントは書かない。`forwardRef` も
使わない — 19 では `ref` がそのまま props で渡る）。

### useEffect は4類型だけ

`useEffect` は **React の外にある世界と同期するためのもの**。書いてよいのは次の4つで、
当てはまらないものは書かない。

| 類型                             | 例                                                                          |
| -------------------------------- | --------------------------------------------------------------------------- |
| 外部システムの購読               | WebSocket の接続（`browser/stores/session.tsx`）                            |
| React の外にある状態への書き込み | `document.title`・CSS カスタムプロパティ・`dialog.showModal()`・`scrollTop` |
| タイマー                         | 経過時間の1秒刻み（`browser/features/dispatch/turn-status.tsx`）            |
| 外部からの読み込み               | `fetch`・vendor script の読み込み                                           |

4類型から外れるものをどうしても書くときは、**なぜ下の代替では書けないのか**をコメントに残す
（「コメント」節の「今の挙動の制約・前提」にあたる）。

### useEffect の代わりに使うもの

`useEffect` を書きたくなったら、先にこの表を見る。

| やりたいこと                      | 使うもの                                         |
| --------------------------------- | ------------------------------------------------ |
| props / state から計算できる値    | レンダー中に計算する（state にしない）           |
| props が変わったら state を捨てる | `key` で部品ごと作り直す                         |
| 利用者の操作で起きること          | イベントハンドラ                                 |
| effect から最新の値を読みたいだけ | `useEffectEvent`（React 19.3 にある）            |
| 外部ストアの購読                  | `useSyncExternalStore`                           |
| DOM ノードの取り付け・取り外し    | ref コールバック（React 19 は cleanup を返せる） |

いちばん多い誤りは、**props や state から計算できる値を state に入れて effect で更新する**もの。
レンダーのたびに計算すればよく、effect を挟むと「計算し終わる前の1フレーム」が画面に出るうえ、
更新の連鎖が起きる。

### 依存配列を手で間引かない

`react-hooks(exhaustive-deps)` が要求する依存を、コメントで理由を書いて外す形にしない。
外したくなるのは、たいてい「その値は**読むだけ**で、変わっても effect を張り直したくない」
ケースで、それは `useEffectEvent` に包めば依存から正しく消える。

### レンダー中に ref を読み書きしない

`ref.current` に触ってよいのはイベントハンドラと effect の中だけ。レンダー中に書くと、React が
レンダーをやり直したり捨てたりしたときに値がずれる。「最新の値をクロージャから読みたい」だけなら
`useEffectEvent`。

## テスト

### 置き場所とモック

- 実装コードの前に失敗するテストを書く（`/tdd` スキル参照）
- テストは `test/` 以下に、テスト対象と同じディレクトリ構成で置く
  （`src/<相対パス>.ts` → `test/<相対パス>.test.ts`）
- テストランナーは `bun test`。`describe` / `it` / `expect` は `bun:test` から import する
- **モックするのはシステム境界だけ**: ファイルシステム、時刻、端末の能力判定（画像プロトコルが
  使えるか）。`bun:test` の `mock` / `spyOn` を使う。自分たちのモジュール同士はモックしない
  （`/tdd` の `mocking.md` が正典）
- 非公開関数は、`export` された関数の振る舞いを通して検証する。テストのためだけに `export`
  しない（上の「関数の並び順」節と同じ規約）

### カバレッジに閾値を設けない

カバレッジは**穴の在り処を見る道具としてだけ**使い、達成すべき数値は決めない。閾値を置くと
「数字を満たすためのテスト」が増え、それは下で消そうとしている冗長テストと同じものになるため。

### 消すかどうか

| 観点                                                               | 扱い                                                   |
| ------------------------------------------------------------------ | ------------------------------------------------------ |
| 同じ入力分岐を別のテストが既に通している                           | 消す候補                                               |
| 型が既に保証している性質を実行時に確認している                     | 消す候補                                               |
| 実装の内部構造をなぞるだけで、外から見た入出力を固定していない     | 消す候補                                               |
| 同じモックの準備が複数ファイルに重複している                       | テストは消さず、準備を共通のフィクスチャに寄せる       |
| 出力の書式を固定している（吹き出しの折り返し・枠線の組み立てなど） | 残す。書式は他に守る手段が無い                         |
| 過去のバグの再発防止として書かれた回帰テスト                       | 残す                                                   |
| そのテストを外してもカバレッジの到達行・分岐が減らない             | **それだけでは消す理由にしない**（積極的な理由が要る） |

消したときは、**その振る舞いを上位で守っているテストがどれか**を書き残す。「カバレッジが
減らないから消した」だけの記録は、次に同じ調査をする人の役に立たない。

### 足すかどうか

未到達の行を全部は埋めない。埋めるのは次の2つに当たるものだけ。

- エラー方針の分岐（起動時の即時終了か、その回だけ諦めるか、フォールバックか）
- `docs/requirements.md` が明示している振る舞い（フォールバック、未知の `type` を無視する、
  状態ファイルが無いときの既定の表情など）

到達不能な防御的コードと、エラーメッセージの文面だけが変わる分岐は埋めない。
**埋めないと決めた穴は、理由を添えてこの節に書き残す**（次にカバレッジを見た人が同じ調査を
繰り返さずに済むように）。

### 描画は自動テストで守らない

端末に実際に絵と枠が出ているかは、テストでは捉えられない。テストで守るのは
「読む」（transcript・状態ファイルの解釈）と「決める」（何をどんな表情で出すか）までとし、
**「描く」は目視で確認する**（`docs/architecture.md`「手で確かめること」）。

この線引きがあるので、原則2の「読む・決める・描く」の分離は**テスト可能性の要請**でもある。
決める部分に端末依存の処理が混ざると、テストできる範囲がそのぶん減る。

## Bun固有APIに寄せない

ファイル・パス・プロセス・子プロセスは、`Bun.file()` や `Bun.spawn()` ではなく
`node:fs` / `node:path` / `node:process` / `node:child_process` の標準APIを使う。

理由は退避先を残すため。Bun を選んだのは「TypeScript をそのまま実行でき、テストランナーも
内蔵していて、依存が最小で済む」からであって、Bun でなければ書けない処理があるからではない。
標準APIに寄せておけば、Bun に不都合が出たとき Node へ移すのがランタイムの入れ替えだけで済む。

**ただし退避先は完全ではない。** `src/server/adapter/bundle.ts` は `execFile("bun", ["build", ...])` で
**`bun` コマンドそのものに実行時依存している**ので（`Bun.*` の API は使っていない）、Node へ移す
ときは束ねる仕組みの差し替えが別に要る。この規約が守っているのは、その一点を除いた残り全部。

**唯一の例外は `bun:test`**（テストランナーそのものなので、移すときは差し替えるしかない）。
性能上どうしても `Bun.*` が必要になったら、その理由をコメントに残したうえで使う。

## 整形の対象外

`oxfmt` は `.prettierignore` に従い、**`.claude/` と `docs/history/` を整形しない**。

`.claude/skills/` の大半は [mattpocock/skills](https://github.com/mattpocock/skills) 由来で、
上流から取り直すことがある。こちらの整形（セミコロン除去・強調記法の統一）をかけてしまうと、
取り直したときの差分が実質的な変更と見分けられなくなる。

`docs/history/` は**過去の記録**で、書いた時点の文言がそのまま残っていることに意味がある。
加えて oxfmt の折り返しは、強調（`**`）の範囲をずらしたりコード中の `*` を `_` に変えたりして
**中身を壊す**（2026-09-20、`docs/history/direction.md` で19行が壊れた）。

`docs/history/` 以外の `docs/` は整形の対象に含める。表の桁揃えが全角文字幅を考慮して揃うので、
手で書くより正確になる。

## タスク番号を書かない

コード・ドキュメントにタスク番号（`develop/tasks.json` の `id`。`T-` + 3桁の連番）を書かない。
変更の経緯は `develop/tasks.json` と `docs/history/` 側に持たせ、コードやドキュメントには
「現在どうなっているか」と「なぜそうなっているか」だけを書く。

タスク番号はアーカイブされると意味を失う一方、コード側の記述は残り続けるため、参照先が消えた
死んだ識別子になる。この規約は `grep -rE "T-[0-9]{3}"` が `develop/` / `docs/history/` 以外で
0件になることで機械的に確認できる。

**例外は `docs/requirements.md`「7. 未決事項」の対応タスク列だけ。** 未決事項は「どのタスクで
決まるのか」が分からないと宙に浮くため、ここだけIDを許す（決まった時点で本文へ移り、IDごと
消える）。上のgrepは `develop/` / `docs/history/` に加えて、この表だけを除外して読む。

**コミットメッセージは対象外**（上の確認はワーキングツリーしか見ない）。件名の先頭にIDを置く
運用は `~/.claude/skills/task-workflow/WORKFLOW.md`「コミットメッセージ」が正典。
