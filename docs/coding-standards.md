# コーディング規約の詳細

`CLAUDE.md`「コーディング規約・レビュー方針」にルールの一覧がある。**ここにはその理由と例外**
だけを書く（ルール本体はCLAUDE.md側が正典で、二重に書かない。ただし lint やテストが検査する
ルール——`Date` を使わない・層と依存の向き——は CLAUDE.md に一覧の行を置かず、ここだけに書く）。`/code-review` のStandards軸は
この2つを合わせて評価軸にする。

配置・分割の規約は `docs/architecture.md` が正典。

実装スタックは **Bun + TypeScript**。チェックコマンドは `bun run check`
（`tsc --noEmit` → `oxlint` → `oxfmt --check` → 単体テスト → E2E。E2E の段は `docs/design.md`
10章「E2E の走らせ方」）。

## このファイルの読み方

現時点では小さいので通読してよい。**30KBを超えたら**、下の索引で節を1つ特定して、
その節だけを次の形で読む運用に切り替える:

```bash
# `##` の節を丸ごと（配下の `###` も含めて）読む
sed -n '/^## テスト/,/^## /p' docs/coding-standards.md

# `###` の小節だけを読む
sed -n '/^### 消すかどうか/,/^#\{2,4\} /p' docs/coding-standards.md
```

## 関数の並び順

ファイル内で「外から使うもの → その内部で使うもの」の順に並べ、`export` された関数を上に、
そこからしか呼ばれない非公開関数を下に置く。非公開関数同士は呼ばれる順に並べる。

読む人がファイルを開いて最初に目にするのが、そのファイルの公開インターフェースになるように
するため。目次を別に置かなくてもファイルの先頭が目次として働く。

### テストのためだけに公開しない

非公開関数は、`export` された関数の振る舞いを通して検証する。テストのために `export` すると、
「このファイルの公開インターフェース」がテストの都合で膨らみ、上の並び順の意味も崩れる。

テストのその他の規約（置き場所・モック・カバレッジ・消す/足すの判断）は下の「テスト」節。

## 変数は基本イミュータブル

再代入が必要に見える場合はまず、値を返す関数に切り出せないかを検討する。ループカウンタや、
例外処理で外側のスコープに結果を持ち出す必要があるなど、可変が自然な場合はその限りではない。

変数は基本 `const`。不変性はローカル変数だけでなくコレクションにも適用する
（`readonly` フィールド・`readonly T[]`・`ReadonlyMap`）。**引数として渡した入れ物が
呼び出し先で書き変わる契約にしない。** サイドカーは「読む → 決める → 描く」を繰り返す
ループなので、途中の入れ物が書き変わると「今フレームの入力」がどこにも残らなくなる
（`docs/architecture.md` 原則2）。

**状態を持つ入れ物（キャッシュなど）を配線から渡すときも同じ**——中の `Map` などを型に出して
呼び出し先に `.set` させず、作る側の閉包に閉じ込めて、覚える・引く口だけを渡す。
`src/server/achievement/adapter/main-history.ts` の `createAchievementCommitCache()` が例（型は
`dailyCountOf` / `rememberDailyCount` の関数2つだけを持ち、`Map` は閉包の中）。

## 型を迂回するキャストを使わない

次を書かない: `as` キャスト、`any`、非nullアサーション `!`、`@ts-expect-error` /
`@ts-ignore`。必要になったのは、**その値の型が実際の中身と合っていない**という合図なので、
迂回ではなく型のほうを直す。`any` は oxlint の `typescript/no-explicit-any` で error にしてある。

**唯一の逃げ道は「境界で検証してから内側の型に変換する」こと。** `unknown` で受けて検証関数を
通し、通った値だけを内側の型として返す。この変換関数の中でだけ、検証済みであることを根拠に
型を確定させてよい。

外部由来の値（transcript の1行、キャラクター定義ファイル、環境変数）は**構造が信用できない**
ので、境界で検証してから内側の型に変換する。検証を通っていない値が内側に入らないよう、
変換は1箇所の関数に封じ込める。

**「素のオブジェクトか」の判定は remeda の `isPlainObject` を使う**（2026-09-22。それまでは
8ファイルがそれぞれ `isRecord` を書き写していた）。**`isPlainObject` は prototype が
`Object.prototype` か `null` のものだけを通す**ので、`JSON.parse` の結果・SDK のメッセージ・
transcript の1行のような**外から来た素のデータ**に使う。捕まえた例外（`Error` の実体）のように
prototype を持つものを見るときだけ `isObjectType` で、`code` のようなフィールドは `in` で
確かめてから読む。

## 可読性が良くなる場合は remeda を優先する

手書きの `reduce` での合計・グループ分け・比較関数などは、remeda に同じ関数があれば
**可読性が良くなる場合**にそちらへ寄せる。基準は「案を選ぶときの指標」と同じで、
**行数の削減それ自体は理由にしない**。remeda は依存にある（`package.json`。2026-09-22 に
型ガードなどの一般的な小物として承認）。

**寄せないもの**（線引き）:

- **標準の慣用句で差が無いもの**: `[...new Set(xs)]`、`Array.from({ length })`、名前付きの
  関数に包んだ clamp など。remeda に置き換えても読みやすさが変わらないものは寄せない
- **戻り値の型が変わって呼び出し側まで直すことになるもの**: `Map` を返す集計を `Record` を
  返す `groupBy`・`countBy` に置き換える、など。呼び出し側の型まで連鎖して直す羽目になる
  置き換えは、「置き換えのための置き換え」になっていないかを疑う

**`utils/` を作る前に remeda にあるかを見る**という**置き場所**の判断は、`docs/design.md`
「`lib/` と `utils/` に置く基準」が正典（ここでは重複させない）。この節が扱うのは、
`utils/` に切り出すかどうかに関係なく、その場で書く `reduce`・比較関数などのインラインの
書き方の基準。

## class 名は clsx で組む

2つ以上の class 名をつないで `className` に渡すときは、配列の `.filter(...).join(" ")` や
テンプレート文字列で手で組まず、`clsx(...)` に渡す。clsx は依存にある（`package.json`。
2026-09-26 に承認）。

CSS Modules の `styles["..."]` は `string | undefined` と型付けされるので、手で組むと
`?? ""` や `value !== undefined` の型ガードが混ざり、区切りの空白をどちらが持つかも呼び出し側が
気にすることになる。clsx は `undefined`・`false`・空文字を捨てて空白でつなぐので、渡す側は
並べるだけで済む。

- 条件付きの class は `cond && styles["x"]` の形で渡す。オブジェクト記法
  （`{ [styles["x"]]: cond }`）は、キーが `undefined` になりうるので使わない
- class 名が1つだけのとき（`className={styles["x"]}`）は包まない

## 型注釈より `satisfies`

定数・テーブル・設定オブジェクトの定義は、型注釈（`const x: T = …`）ではなく `satisfies` で
形を検査する。

```diff
-const PORTRAITS: Record<Expression, string | undefined> = { … }
+const PORTRAITS = { … } satisfies Record<Expression, string | undefined>
```

型注釈は値の型を `T` に**広げる**ので、どのキーが実際にあるか・どの文字列リテラルだったかが
その場で失われる。`satisfies` は `T` を満たすかどうかだけを検査し、値の型はリテラルのまま残す。
`Object.keys` で取り出したキーが `string` に潰れない、使っていないキーが型から見える、といった
差になって効く。

`as` の代替としても使う。「この形になっているはず」と言いたいだけなら `satisfies` で
**検査させる**（`as` は検査せずに黙らせる。上の「型を迂回するキャストを使わない」）。

例外は、値より先に型が必要なとき — 再帰的な型、関数の引数・戻り値、`useState<T>` のような
型引数。ここは注釈でよい。

## エラーハンドリング

**サイドカーは常駐プロセスであり、描画1回の失敗で落ちてはいけない**
（`docs/requirements.md`「5. 実行環境・非機能要件」）。エラーは2チャネルに分ける:

| 種類                                                                                      | 扱い                                                     |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 起動時に前提が満たされていない（transcript のパスが分からない、定義ファイルが壊れている） | 例外を投げて**即時終了**。理由を1行で表示する            |
| 動作中の一時的な失敗（JSONLの行が途中まで、画像が読めない、端末が狭い）                   | **その回の描画だけ諦めて次へ進む**。落ちない             |
| 画像プロトコルが使えない                                                                  | エラーではない。テキストのみのフォールバックへ切り替える |

**描画ループの中に `try`/`catch` を散らさない。** 1回分の描画をまるごと包む場所を1つ決め、
そこで受け止める。散らすと「どこまで描けたのか」が分からなくなり、部分的に壊れた画面が残る。

**入口で済ませた判定（ターン中なら断る、など）は `await` をまたいで保たれない。** `await` の
あとで同じ判定を取り直す。駆動へは「前提を渡す口」を「依頼を送る口」より先に呼ぶ——待つあいだに
別の依頼でターンが始まると、判定を取り直さない限り二重に送ってしまう。

## 外部の入力を読む場所を1つにする

環境変数・ホームディレクトリ・transcript のパス・キャラクター定義のパスといった
**外の世界に依存する値は、読み取りを1つのモジュールに集約する**。モジュールのトップレベルで
環境変数に触らない（読み取りの順序に依存し、テストから差し替えられなくなる）。

集約すると、テストで環境を差し替える手段が1つで済み、「この値はどこで決まったのか」を
探す場所も1つになる。

## コメント

**コードから読み取れないことだけ**を書く。型名・フィールド名・関数名の言い換えは書かない。

残すかどうかは**長さではなく種類**で決める。行数の目安は置かない（数字を置くと、種類の基準の
代わりにその数字が基準として使われるため）。

| 種類                                                                       | 扱い                                                                                                                                                                                                                                        |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 今の挙動の制約・前提（この順序でなければならない理由など）                 | コードに残す。必要なだけ長くてよい                                                                                                                                                                                                          |
| 外部との対応関係（transcript のどの `type` 由来か、端末プロトコルの挙動）  | コードに残す。必要なだけ長くてよい                                                                                                                                                                                                          |
| 昔はこうだった（過去の実装・過去の設計の経緯）                             | 長短にかかわらず正典へ移し、コードから消す                                                                                                                                                                                                  |
| 採らなかった案の比較（どの案をなぜ捨てたか）                               | 正典（`docs/architecture.md`）へ移し、コードから消す。素直に書き直すと壊れることを防ぐ一言（Why not）だけは残す                                                                                                                             |
| ほかの箇所との照らし合わせ（「〜と同じ割り切り」「〜と同じ考え方」）       | 書かない。この箇所の制約はこの箇所の言葉で書く。揃えておく義務があるときだけ `{@link}` か1行の参照で指す                                                                                                                                    |
| 正典に書いてあることの要約                                                 | 書かない。節への参照（`docs/…` と節の句）だけを残す                                                                                                                                                                                         |
| いつ決まったか・誰が言ったか（特定の日付・「〜の指摘」「ユーザーの決定」） | 書かない（禁止）。理由（Why / Why not）は残す。日付つきの記録は `docs/architecture.md` と `docs/history/` が持つ。**`src` `test` `scripts` は `test/architecture.test.ts`「コメント中の日付」が機械で検査する**（`bun run check` から走る） |

**同じ制約・前提を、呼び出しの経路上の複数の関数に書き写さない。** それを決めている関数
（絞り込むならその絞り込みをしている関数）に1回だけ書き、経路上の他の関数からは `{@link}` か
1行の参照で指す。書き写すと、仕様が変わったときに直す場所が増え、直し忘れが起きる。

正典の対応:

| 書きたいこと   | 置き場所               |
| -------------- | ---------------------- |
| 設計判断・経緯 | `docs/architecture.md` |
| ドメイン用語   | `docs/glossary.md`     |
| 要件           | `docs/requirements.md` |

経緯をコードから消すときは、**先に正典の該当箇所を確認する**。既に書かれていれば消すだけ、
無ければ正典に書いてから消す。

レビューでは各段落に次を1問だけ問う: **「この段落はコードの今の挙動を説明しているか、昔の話か」。**
昔の話なら正典へ移す。この判定は機械化しない（日本語の過去形は外部挙動の記録にも使われ、
語での検出は誤検知が多すぎる）。

## 「無いかもしれない」値

`| undefined` は**次の5つの場所でだけ書いてよい**。どれにも当てはまらないなら型に「無い」を
残さず、判別可能な合併型にするか（下の「複数の「無い」が1つの状態」）、入口で畳む
（下の「「無い」を層をまたいで運ばない」）。

| #   | 書いてよい場所                           | 判定（コードを見れば決まる）                                                                                                                             |
| --- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **外の世界の値を写した直後**             | その `\| undefined` を書いている関数が `src/server/adapter/` にある、または `unknown` / 定義ファイルの中身 / 環境変数 / SDK のイベントを引数に取っている |
| 2   | **TypeScript が生む `undefined`**        | 型注釈を書いていない（`noUncheckedIndexedAccess` の添字・`Map.get`・`Array.at` / `find` / `findLast` の戻り値）                                          |
| 3   | **React が型で要求するもの**             | `useState` / `useRef` / `createContext` の型引数、`CSSProperties` の拡張                                                                                 |
| 4   | **React の外の資源を持つ可変の入れ物**   | `let` 宣言で、初期値が `undefined`、あとから代入がある（タイマー・ソケット・キャッシュ・畳み込みの途中）                                                 |
| 5   | **丸ごと省略できるオプション引数の中身** | 引数オブジェクトごと省略でき、既定値がある                                                                                                               |

例外1は外の世界の「無い」をそのまま写したもの。transcript にまだ assistant の行が1つも無い、
状態ファイルがまだ書かれていない、キャラクター定義に該当する表情が無い、環境変数の未設定。
要件を変えても消えない情報なので、正直に表す。

例外2は `tsconfig.json` の `noUncheckedIndexedAccess` を有効にしてあるために自動で付くもの。
**これを `!` で潰さない**（上の「型を迂回するキャストを使わない」）。消したいなら、添字ではなく
「必ずある」ことを型で表せる形（合併型・全域の対応表）に変える。

例外5は「値が無い」を表しているわけではなく、既定値を持つ調整用のつまみ。`| undefined` に
すると呼び出し側が使わないつまみまで毎回書くことになる。

書き方は `readonly x: T | undefined` で、`?:` のオプショナルプロパティ記法は使わない。
`?:` は「キー自体が無い」場合まで許してしまい、渡し忘れが型で見えなくなる。
`readonly x: T | undefined` なら値の受け渡しのたびに `undefined` を明示させられる。
`?:` で書いてよいのは例外5だけで、丸ごと省略できる引数の中身なので渡し忘れる相手がいない。

**例外1に当てはまらないのに `| undefined` を書くとき**は、書く前に次の3つを確かめる
（例外2〜5は書くかどうかを選べないので対象外）:

- **片方だけが `undefined` になる状態が実在するか。** しないなら1つの状態なので合併型にする
  （下の「複数の「無い」が1つの状態」）
- **その `undefined` が持つ意味が1つか。** 「まだ来ていない」と「読めない」が同じ `undefined` に
  乗っているなら割る
- **入口より内側へ運んでいないか。** 層をまたぐなら入口で畳む
  （下の「「無い」を層をまたいで運ばない」）

**「無い」を型から消すことを目的にしない。** 消す手は判別可能な合併型にするか入口で全域に
畳むかの2つだけで、**この2つで消えないものは本物の「無い」**なので消さない。手が無いのに
消そうとすると `!` や `as` に化ける（上の「型を迂回するキャストを使わない」）。なぜ「無い」が
生まれるのかを先に問い、値の持ち主や取得のタイミングが正しくないなら**そちらを直す**。

### 複数の「無い」が1つの状態

2つ以上の `| undefined` が**同じ1つのこと**を表しているなら、フィールドを並べず判別可能な
合併型（タグ付き合併）にする。

```ts
// 避ける: 8通り書けるのに、実在するのは3つ
readonly turnInProgress: boolean
readonly turnStartedAt: number | undefined
readonly turnFinishedAt: number | undefined

// こうする
readonly turn:
  | { readonly kind: "idle" }
  | { readonly kind: "running"; readonly startedAt: number }
  | { readonly kind: "finished"; readonly startedAt: number; readonly finishedAt: number }
```

並べると、**型としては書けるのに起きない組み合わせ**（終わっているのに始まっていない、など）が
残る。読む側はそれを毎回 `=== undefined` の組み合わせで解き直すことになり、同じ解読が使う場所の
数だけ複製される。合併型なら分岐は `turn.kind` の1つで済み、各状態に**その状態でだけ意味を持つ
値**を持たせられる。

判断の目安は「**片方だけが `undefined` になる状態が実在するか**」。しないなら1つの状態なので
合併型にする。

### 「無い」を層をまたいで運ばない

「無い」が本物なのは、外の世界と接する**入口だけ**。そこで畳んでから内側へ渡し、内側の関数は
「必ず値がある」型で受ける。畳み方は2つ — 既定値に置き換える（`??`）か、呼び出し側で分岐して
「ある」場合にだけ内側を呼ぶ。

`T | undefined` を受ける関数が数珠つなぎになると、**どの層で「無い」が確定するのか**が
分からなくなり、同じ `undefined` チェックが各層に散る。内側の関数は自分の仕事に集中できず、
「値が無いときにここは何を返すべきか」をその都度決めることになる。

### null は自前の型に出さない

`null` を書いてよいのは次の3つだけ:

- React の作法 — `useRef<T>(null)` の初期値、「何も描かない」を表す `return null`
- 外来 API の戻り値をそのまま受ける場所 — `localStorage.getItem`、`child_process` の `error`、
  SDK の `parent_tool_use_id`
- `typeof value === "object" && value !== null` の型ガード

自分で定義する型・関数の戻り値・`shared` の型には出さない。外来の `null` は**受け取った境界で
`undefined` に畳む**。「無い」の表し方が2つあると、チェックが `== null` か `=== undefined` かで
揺れ、どちらが起きうるのかを呼び出し側が毎回確かめることになる。この判断を境界の1箇所に寄せる。

## 会話内容の扱い

**このリポジトリ固有の規約で、優先度が最も高い。** transcript には利用者と Claude の
生の会話が入っている。**SDK のイベント（ターンの本文・ツールの入力と結果・`speak` の引数）も
transcript と同じ扱いにする。**

- **外部に送らない。** 解析サービス・テレメトリ・クラッシュレポートを含め、ネットワークに
  出す経路を作らない
- **別の場所に複製しない。** キャッシュ・一時ファイル・バックアップとして transcript の
  内容を書き出さない。**禁じているのは「書き出す」ほうで、正典（claude 自身が
  `~/.claude/projects/` に書く transcript）を読んでメモリ上のビューを組み直すのは複製に
  あたらない**（セッションの復元。`docs/requirements.md` 4.8）。読んだものはプロセスの
  メモリに留め、`127.0.0.1` のビュー以外へ出さない。**例外は下の2つの表だけ** —
  **書き出してよいもの**が3つ、**会話を claude へ渡してよいもの**が3つ。

- **ログに全文を出さない。** デバッグ時も、出すのは長さ・行数・`type` のような**中身を
  含まない情報**にとどめる。文面そのものを出す必要があるときは、その場限りにして
  コミットしない
- **テストのフィクスチャに実物を使わない。** SDK のイベントや JSONL のフィクスチャは、
  手で書いた架空の会話にする

- **transcript を読んで書き出さない。** 残すのは tsukumo が画面のために受け取ったものだけで、

  出してよいのは長さ・件数まで）、テストのフィクスチャに実物を使わない（アーカイブのフィクスチャも

- **キャラクターパックへ書く1行はこの表に数えない**（`persona.md` の「覚えたこと」）。あれは
  会話ではなく**キャラクター自身の属性**で、複製にあたらないという整理のまま

**会話は tsukumo のプロセスの外へ出さない。** SDK は claude を子プロセスとして起こすだけ、
`speak` はプロセス内の MCP ツール（戻り値は `"ok"` だけ）、ビューは `127.0.0.1` にだけ配る。
ここに外へ出る経路を足さない。**読み戻した逐語を `systemPrompt` に載せることも、定着の
使い捨て `query()` に渡すことも、この線の内側**——渡す相手は同じプロセスが起こした子プロセスで、
tsukumo から外へは出ない。

**ブラウザ側で会話の状態を持つこと（移行後の `SessionState`）は、外へ出すことにあたらない。**
同じマシンの同じオリジン（`127.0.0.1`）のタブのメモリに閉じるためで、いまも DOM として同じものを
持っている。**`localStorage` などブラウザ側の永続化に会話を置かない**（置いてよいのは領域の比率の
ような画面の都合だけ。`docs/design.md` 9章）。

## 層と依存の向き

**2026-09-13 の移行後、`src/` は層をディレクトリで表す**（設計は `docs/design.md` 2章）。
**2026-09-16 にサーバ側を `core`（判断）と `adapter`（境界）に割り、2026-09-20 に層の名前を
実行環境に合わせて `shared`（サーバとブラウザ）/ `browser`（ブラウザ）へ改名し、サーバ側の
2つを `src/server/` の下へ入れ子にした。** **2026-09-25 に、サーバ側の `core` と `adapter` を
機能の中へ入れると決めた**（`src/server/<機能>/{core,adapter}/`。機能の一覧・機能どうしの辺・
共有の箱は `docs/design.md` 2章「サーバの機能と、機能どうしの辺」が正典）。
**新しいファイルは、まずどの層かを決めてから置く**（サーバ側は、どの機能かも決める）。

**4つの層（`shared` / `server/core` / `server/adapter` / `browser`）が何を置き、どこへ import して
よいかの表は
二重に書かず `docs/design.md` 2章「層と依存の向き」を正典とする**（`src/browser/` の箱の表と
同じ扱い）。ここには、その表だけでは読み取れない決まりを書く。

`src/` 直下（`cli.ts` / `main.ts` と起動の段取り）は配線なので全部を import してよい。**`core` と `browser` は互いを import しない。**
**`core → adapter` も禁止**で、`core` は `node:` / `@anthropic-ai/*` / `ws` を import しない
（外の世界へ出る道が無い）。両者を結ぶのは `src/` 直下だけ。`adapter` は**1ファイル = 1つの境界**で、
インターフェースは切らない（実装が2つあるもの — 駆動とホスト — だけ契約の型を `core` に置く）。
`shared` は `node:` にも `document` にも触らない（両方の実行場所で動くため）。**許した辺以外は
`test/architecture.test.ts` が落とす**ので、向きを変えたくなったら先にこのテストと `docs/design.md`
2章を直す。

**`browser` 層の中も、箱（`main.tsx` / `features/` / `components/` / `lib/` / `stores/`）ごとに
import してよい先が決まっている**（表は二重に書かず `docs/design.md` 2章「`src/browser/` の箱と、
置く基準」を正典とする）。この縦の辺も `test/architecture.test.ts` が落とす。

**ファイルは単数形にする。** 複数は「複数返す」関数名の側で表す（`task-summary.ts` の
`unfinishedTaskIds`）。理由は、ファイル名が**概念**を指すため（原則5）。概念は1つで、いくつ返すかは
関数の都合。

**ディレクトリも単数形。ただし `src/browser/` の置き場所のディレクトリだけ例外**（2026-09-16）。
`features/` `components/` `lib/` `stores/` `styles/` は bullet-proof-react の名前をそのまま使う
（名前が広く知られていることのほうが、単数形で揃うことより読み手の助けになる、というユーザーの
選択）。**例外はこの5つだけ**で、`src/shared/` `src/server/core/` `src/server/adapter/` と、機能の中の
ディレクトリ・ファイル名は単数形のまま（`components/page/conversation/components/main-view/markdown/` のように**概念の名前**を
付ける）。**置き場所を名前にしたディレクトリのうち、`lib/` と `utils/` はどの層の中にも作ってよく、
`helpers/` と `common/` は作らない**（2026-09-21 決定。どちらの箱に置くかの判定手順・`utils/` を
受け皿にしないための歯止め・層ごとの読み方は二重に書かず `docs/design.md` 2章
「`lib/` と `utils/` に置く基準」を正典とする）。**ファイル名としての `utils.ts` / `helpers.ts` /
`common.ts` は引き続き作らない**（許したのはディレクトリの名前だけで、ファイル名は概念のまま）。

**barrel file を作らない。** ディレクトリに `index.ts` を置いて中身をまとめて re-export しない
（import は実ファイルを直接指す）。理由は2つ: (1) 束ねるときの tree-shaking が効かなくなる
（`browser` は `bun build` で1本に束ねる。`docs/design.md` 11章）。(2) `index.ts` という名前自体が
「置き場所を名前にしたファイル」になり、原則5に反する（ディレクトリ名がすでに概念や置き場所を
表すのに、その中の `index.ts` は何も指さない。**ディレクトリ名の例外を足した後も、ファイル名は
概念のまま**）。2026-09-13、`src/browser/` を切った段（`docs/history/decision.md`
「design.md 12. 移行の段階」の段3）で bulletproof-react の実例と突き合わせて決めた。

**`components/ui/` の部品は `ui/<部品>/<部品>.tsx` に置き、`index.tsx` は作らない。検査が
落とす。** 部品ごとのディレクトリに分けるのは `docs/design.md` 2章の「1部品1フォルダは
真似しない」の例外で、barrel file を作らない理由はここと二重に書かない。

## React

React 19。関数コンポーネントと Hooks だけを使う（クラスコンポーネントは書かない。`forwardRef` も
使わない — 19 では `ref` がそのまま props で渡る）。

### useEffect は4類型だけ

`useEffect` は **React の外にある世界と同期するためのもの**。書いてよいのは次の4つで、
当てはまらないものは書かない。

| 類型                             | 例                                                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 外部システムの購読               | WebSocket の接続（`browser/stores/session.tsx`）                                                         |
| React の外にある状態への書き込み | `document.title`・CSS カスタムプロパティ・`dialog.showModal()`・`scrollTop`                              |
| タイマー                         | 経過時間の1秒刻み（`browser/components/page/conversation/components/dispatch/hooks/use-turn-status.ts`） |
| 外部からの読み込み               | `fetch`・vendor script の読み込み                                                                        |

4類型から外れるものをどうしても書くときは、**なぜ下の代替では書けないのか**をコメントに残す
（「コメント」節の「今の挙動の制約・前提」にあたる）。

### useEffect の代わりに使うもの

`useEffect` を書きたくなったら、先にこの表を見る。

| やりたいこと                      | 使うもの                                         |
| --------------------------------- | ------------------------------------------------ |
| props / state から計算できる値    | レンダー中に計算する（state にしない）           |
| props が変わったら state を捨てる | `key` で部品ごと作り直す                         |
| 利用者の操作で起きること          | イベントハンドラ                                 |
| effect から最新の値を読みたいだけ | `useEffectEvent`（React 19.3 にある）            |
| 外部ストアの購読                  | `useSyncExternalStore`                           |
| DOM ノードの取り付け・取り外し    | ref コールバック（React 19 は cleanup を返せる） |

`useEffectEvent` で包んだ関数は**レンダー中には呼べない**（React が投げる）。呼んでよいのは
effect の中と、イベントハンドラ・そこで登録した寿命の長いリスナの中
（`browser/components/domain/layout/layout-resizer.tsx` の、ドラッグの間だけ生きる `pointermove`）。

**画面を離れるとアンマウントされる部品（`main.tsx` の `OVERLAY_SCREEN`）では、一回限りの合図や
「もう見せた」の印を部品の state に持たない。** React の外（モジュールの store）に持つ——
アンマウントで消える state に印を仕込むと、再訪のたびに初期値へ戻って演出が勝手にやり直しになる。

いちばん多い誤りは、**props や state から計算できる値を state に入れて effect で更新する**もの。
レンダーのたびに計算すればよく、effect を挟むと「計算し終わる前の1フレーム」が画面に出るうえ、
更新の連鎖が起きる。

### 依存配列を手で間引かない

`react-hooks(exhaustive-deps)` が要求する依存を、コメントで理由を書いて外す形にしない。
外したくなるのは、たいてい「その値は**読むだけ**で、変わっても effect を張り直したくない」
ケースで、それは `useEffectEvent` に包めば依存から正しく消える。

### レンダー中に ref を読み書きしない

`ref.current` に触ってよいのはイベントハンドラと effect の中だけ。レンダー中に書くと、React が
レンダーをやり直したり捨てたりしたときに値がずれる。「最新の値をクロージャから読みたい」だけなら
`useEffectEvent`。

### 部品は `function` で書く

`ReactElement` を返す関数は**関数宣言**（`function Name(props: Props): ReactElement`）で書く。
`const Name = (props) => ...` の形にしない。定義の形が2つあると、**並び順の規約
（「外から使うもの → その内部で使うもの」）が守れなくなる**ことがある——巻き上げがあるから
「使う側より下に置く」が書けるのであって、`const` は宣言より前で使えない。

**例外は `memo` で包むときだけ。** `const <部品名> = memo(<部品名>View)` と書き、中身は
`function <部品名>View(...)` の関数宣言のまま下に置く（`components/page/conversation/components/main-view/components/report/report.tsx` の
`Report` と `features/task-board/components/task-table.tsx` の `TaskTable`）。
**`memo(function X() { ... })` の形にしない** — 定義が `const` の右辺に入ると、その部品だけ
本体が上に来て並び順が逆になる。

この規約は**部品（`ReactElement` を返す関数）とフック**にかかる。JSX を値として持つだけの定数
（`task-table.tsx` の `TASK_TABLE_HEAD` のような静的な見出し行）は関数ではないので `const` のまま。

### 部品の中で部品を定義しない

部品（`ReactElement` を返す関数）の内側で別の部品を定義しない。定義は必ず親の外
（モジュールのトップレベル）に置き、変わるデータは props で渡す。内側で定義すると、
親がレンダーされるたびに内側の部品の型が新しく作られる。React はそれを「別の部品」だと
見なして、その下の DOM と state を作り直す（入力欄のフォーカスが飛ぶ・演出がやり直しに
なるといった不具合になる）。

`react/no-unstable-nested-components`（`.oxlintrc.json` で `"error"`）がこれを機械的に落とす
（「仕組みをヒューリスティックより優先する」）。例外は設けない。

## テスト

### 置き場所とモック

- 実装コードの前に失敗するテストを書く（`/tdd` スキル参照）
- テストは `test/` 以下に、テスト対象と同じディレクトリ構成で置く
  （`src/<相対パス>.ts` → `test/<相対パス>.test.ts`）。**E2E だけは `test/e2e/<シナリオ>.test.ts`**
  （1つのファイルの振る舞いではないため。形は `docs/design.md` 10章「E2E の走らせ方」）
- テストランナーは `bun test`。`describe` / `it` / `expect` は `bun:test` から import する
- **モックするのはシステム境界だけ**: ファイルシステム、時刻、端末の能力判定（画像プロトコルが
  使えるか）。`bun:test` の `mock` / `spyOn` を使う。自分たちのモジュール同士はモックしない
  （`/tdd` の `mocking.md` が正典）
- **`bun test` はプロセスのタイムゾーンを UTC にして走る**（`process.env.TZ` は未設定のまま、
  `Temporal.Now.timeZoneId()` が `"UTC"` を返す。ホストが JST でも変わらない。2026-09-25 に
  実測）。日付の境目を見るテストは、オフセットを `+09:00` のように固定せず、
  `Temporal.Now.timeZoneId()` を基準に時刻を組む。固定すると `bun test` が見る日の境界と
  ずれ、境界に近い時刻のコミット・イベントが意図と違う日に数えられる
  （`test/server/adapter/main-history.test.ts` の `isoDateAt`）
- 非公開関数は、`export` された関数の振る舞いを通して検証する。テストのためだけに `export`
  しない（上の「関数の並び順」節と同じ規約）
- **語彙（表情・衣装など全域を列挙する定数）の長さに依存する期待値は、その定数から導く**
  （`EXPRESSIONS.length` のように）。個数を直書きすると、列挙が1つ伸びたときに `tsc` の型検査
  では検知できず、`bun test` を走らせて初めて落ちる。「typecheck が通った」を作業の完了の合図に
  しないための書き方
- **CLI やサーバを起こすテストは、マシンの負荷が高いと時間切れで落ちることがある**（1件に
  457秒かかったことがある）。`bun run check` は他の重い処理と同時に走らせず、時間切れで落ちたら
  まず打ち直して、同じテストが続けて落ちるかを見る
- **テストの中で子プロセスを同期で待たない**（`execFileSync` / `execSync` / `spawnSync`。
  `.oxlintrc.json` が `test/` で止める）。`test/fixture/subprocess.ts` の `runSubprocess` /
  `runSubprocessOrThrow` を使う。bun の `spawnSync` には、macOS arm64 で子の終了を取りこぼし、
  待ちが 100% CPU で空回りする不具合が報告されている（oven-sh/bun #34069、修正 PR #40078。
  2026-09-26 時点でどちらも open）。空回り中は `spawnSync` の `timeout` も効かないので、1回の
  固まりが `bun run check` 全体を止めうる。非同期で待てば、取りこぼしてもその1件がテストの
  時間切れで落ちて次へ進む。**`bun test --isolate` が 100% CPU のまま返らなかったのはこれだと
  断定できていない**（手元の数百回の繰り返しでは再現しなかった）
- **`bun test --isolate` が返らなくなったら、止める前にどのファイルかを取る。** `--isolate` は
  子プロセスを起こさず1つのプロセスの中でファイルを順に流し、非 TTY の出力は最後の要約しか
  出さないので、ログからもプロセスの引数からも分からない。次の preload を一時ディレクトリに置いて
  `--preload <パス>` で渡して流し直すと、いま走っているファイル（`Bun.main`）とテストの前後が
  時刻つきで残る（preload はファイルごとに評価し直される）。止まったら、最後の行のファイルと、
  `B`（テストの中）で終わっているか `E`（テストの外）で終わっているかを見る。あわせて
  `ps -o pid,ppid,stat,command -ax` で、そのプロセスの子に終わったまま（`Z`）のものが無いかを
  見る（上の不具合なら残っている）

  ```ts
  import { appendFileSync } from "node:fs"
  import { afterEach, beforeEach } from "bun:test"
  const log = "<書き出す先>"
  beforeEach(() => appendFileSync(log, `${performance.now().toFixed(0)} B ${Bun.main}\n`))
  afterEach(() => appendFileSync(log, `${performance.now().toFixed(0)} E ${Bun.main}\n`))
  ```

### カバレッジに閾値を設けない

カバレッジは**穴の在り処を見る道具としてだけ**使い、達成すべき数値は決めない。閾値を置くと
「数字を満たすためのテスト」が増え、それは下で消そうとしている冗長テストと同じものになるため。

### 消すかどうか

| 観点                                                               | 扱い                                                   |
| ------------------------------------------------------------------ | ------------------------------------------------------ |
| 同じ入力分岐を別のテストが既に通している                           | 消す候補                                               |
| E2E の台本が通している振る舞い                                     | 消す候補（**どのシナリオが守るかを書く**）             |
| 型が既に保証している性質を実行時に確認している                     | 消す候補                                               |
| 実装の内部構造をなぞるだけで、外から見た入出力を固定していない     | 消す候補                                               |
| 同じモックの準備が複数ファイルに重複している                       | テストは消さず、準備を共通のフィクスチャに寄せる       |
| 出力の書式を固定している（吹き出しの折り返し・枠線の組み立てなど） | 残す。書式は他に守る手段が無い                         |
| 過去のバグの再発防止として書かれた回帰テスト                       | 残す                                                   |
| そのテストを外してもカバレッジの到達行・分岐が減らない             | **それだけでは消す理由にしない**（積極的な理由が要る） |

消したときは、**その振る舞いを上位で守っているテストがどれか**を書き残す。「カバレッジが
減らないから消した」だけの記録は、次に同じ調査をする人の役に立たない。

**E2E の台本が通している、とは**: 疑似セッション（`test/fixture/fake-session.json`）に同じ
並びの場面があり、シナリオがそれを流して結果を DOM の構造かメッセージの列の期待値で固定している
こと。**台本に無い並び・未知の `type` / `kind`・SDK のメッセージからの写し・時刻に依る計算は
E2E を通らない**ので、この行には当たらない（範囲は `docs/design.md` 10章「E2E に任せず
単体テストに残すもの」）。「残す」の2行（書式の固定・回帰テスト）は E2E が通していても残す。

### 足すかどうか

未到達の行を全部は埋めない。埋めるのは次の2つに当たるものだけ。

- エラー方針の分岐（起動時の即時終了か、その回だけ諦めるか、フォールバックか）
- `docs/requirements.md` が明示している振る舞い（フォールバック、未知の `type` を無視する、
  状態ファイルが無いときの既定の表情など）

到達不能な防御的コードと、エラーメッセージの文面だけが変わる分岐は埋めない。
**埋めないと決めた穴は、理由を添えてこの節に書き残す**（次にカバレッジを見た人が同じ調査を
繰り返さずに済むように）。

**埋めないと決めた穴（2026-09-20 の棚卸し。`docs/research/test-coverage.md`「埋めないと決めた穴」
節に、この時点のファイルと行番号の内訳がある）:**

- **外の世界の境界**（原則3。1ファイル = 1つの境界）: 到達させるには本物の外部
  （Agent SDK・WebSocket・orca・`fs.watch`・ブラウザの入口）を実際に動かすことになり、
  境界を偽装したら確かめているのは偽物のほうになる。例: SDK を起こす駆動、WebSocket
  クライアントの再接続、ホスト（orca）への操作、開発時だけの UI 再構築、`main.tsx` の
  DOM への1回きりの配線
- **ホームやパスを組み立てるだけの関数**: テストが常に置き場所を注入しているとき、残った
  既定の1行を通しても `join(homedir(), ...)` という実装をなぞるだけになる
  （上の「消すかどうか」表の「実装の内部構造をなぞるだけ」と同じ判断）
- **描画**（「DOM の構造と画面の流れは E2E、見た目は目視」節）: ライブラリの初期化・テーマ設定、
  `window.location.reload()`、複数の部品を並べるだけの組み立てなど
- **到達不能な防御的コード**: コード自身に「配線の誤りのときだけ」等の断り書きがある分岐、
  同梱物が読めない（`bun install` 済みが起動時の前提）、`listen` 後のアドレスが想定の形でない、
  `localStorage` が**例外を投げる**側（値が無い・読めない側は「足すかどうか」の対象。
  書き込みの失敗はプライベートウィンドウ限定）
- **同じ方針を別の入口で既に守っている分岐**: 同じガードを別の経路（鍵盤とマウス、複数ある
  仕切りのうち別の1本など）で既に通しているとき、二重に固定しない
- **要件に無い振る舞い**: `docs/design.md` やコードのコメントにはあっても
  `docs/requirements.md` に無い取り決めは、足すなら先に要件側へ書くのが順序
- **自分たちのモジュールをモックしないと届かない分岐**: 「モックするのはシステム境界だけ」
  （「置き場所とモック」節）に反するので、畳み込み自体を直に使うテストで守る

### DOM の構造と画面の流れは E2E、見た目は目視

画面は3つに分けて守る。

| 守るもの                                                   | 手段                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 受け取る・決める（イベントの畳み込み、何をどう出すか）     | 単体テスト（`shared` と部品）                                                            |
| **DOM の構造と画面の流れ**（何が出て、押すと何が流れるか） | **E2E**（fake driver で起こし、DOM の構造と WebSocket の流れを期待値と比べる）           |
| **見た目**（色・崩れ・間合い・書体）                       | **目視**（`docs/architecture.md`「手で確かめること」。E2E のスクリーンショットは添え物） |

E2E が見るのは `data-*`・`aria-*`・文字と要素の入れ子までで、`class` と `style` は見ない
（形は `docs/design.md` 10章「E2E の成果物と再現」）。**画面の状態を E2E で確かめたいのに
`class` にしか出ていないなら、`data-*` か `aria-*` に出す**——見た目の直しで E2E が割れず、
状態の意味が変わったときだけ割れるようにするため。

この線引きがあるので、原則2の層の分離は**テスト可能性の要請**でもある。決める部分に
ブラウザ依存の処理が混ざると、単体テストで守れる範囲がそのぶん減る。

## Bun固有APIに寄せない

ファイル・パス・プロセス・子プロセスは、`Bun.file()` や `Bun.spawn()` ではなく
`node:fs` / `node:path` / `node:process` / `node:child_process` の標準APIを使う。

理由は退避先を残すため。Bun を選んだのは「TypeScript をそのまま実行でき、テストランナーも
内蔵していて、依存が最小で済む」からであって、Bun でなければ書けない処理があるからではない。
標準APIに寄せておけば、Bun に不都合が出たとき Node へ移すのがランタイムの入れ替えだけで済む。

**ただし退避先は完全ではない。** `src/server/view-server/adapter/bundle.ts` は `execFile("bun", ["build", ...])` で
**`bun` コマンドそのものに依存している**ので（`Bun.*` の API は使っていない）、Node へ移す
ときは束ねる仕組みの差し替えが別に要る。この規約が守っているのは、その一点を除いた残り全部。
**2026-09-21 に事前組み立てへ変えた**ので、`bun build` が要るのは `bun run build`（と
`bun run dev` の見張り）のときだけで、**起動の経路には残っていない**。**同日のうちに
`bun run dev` の前置きとして `bun run build` を足したが、これは `package.json` の `&&` が
外から呼ぶだけで、`src/main.ts` の起動処理（`run()`）自体は変わらず組み立てない。**

**唯一の例外は `bun:test`**（テストランナーそのものなので、移すときは差し替えるしかない）。
性能上どうしても `Bun.*` が必要になったら、その理由をコメントに残したうえで使う。

## `Date` を使わない

時刻は `Date` ではなく `Temporal`（`Temporal.Now` / `Temporal.Instant` /
`Temporal.ZonedDateTime` / `Temporal.PlainDate` など）で扱う。`.oxlintrc.json` の
`no-restricted-globals` で `Date` を `error` にして検査する（`src` / `test` / `scripts` すべてが
対象）。

理由は `Date` のメソッドの多くがミュータブル（`setFullYear` などが自分自身を書き換える）で、
月が0始まりだったり、うるう年・タイムゾーンの計算を呼び出し側に押し付けたりする点。`Temporal`
はイミュータブルで、日付の計算・タイムゾーン付きの時刻・ISO 8601 の文字列化を1つの体系で
扱える。**時刻の数（`shared` を通る値）はこれまでどおりエポックミリ秒の数のまま持つ**
（`Temporal.Instant` そのものを `shared` に出さない）。数を作る場所はサーバが
`src/session-start.ts` の `now`、ブラウザが `src/browser/utils/clock.ts` の
`nowEpochMilliseconds()`。数を読み書き可能な日時に戻すときは
`Temporal.Instant.fromEpochMilliseconds(...)` を使う（`src/server/adapter/local-time.ts`）。

**例外は無い。** テストで固定の時刻を作るときも `Temporal.ZonedDateTime.from({ ..., timeZone })`
や `Temporal.PlainDate` を使い、偽の時計は `spyOn(Temporal.Now, "instant")` で差し替える
（`test/browser/components/page/conversation/components/character-view/character-view.test.tsx` /
`test/browser/components/page/conversation/components/dispatch/turn-status.test.tsx`）。ファイルの mtime のように「エポック秒の
数をそのまま受け取れる」API（`node:fs` の `utimesSync` など）は `Date` を経由せず数を直接渡す。

## 整形の対象外

`oxfmt` は `.prettierignore` に従い、**`.claude/` と `docs/history/` と `test/e2e/expected/` を
整形しない**。

`.claude/skills/` の大半は [mattpocock/skills](https://github.com/mattpocock/skills) 由来で、
上流から取り直すことがある。こちらの整形（セミコロン除去・強調記法の統一）をかけてしまうと、
取り直したときの差分が実質的な変更と見分けられなくなる。

`docs/history/` は**過去の記録**で、書いた時点の文言がそのまま残っていることに意味がある。
加えて oxfmt の折り返しは、強調（`**`）の範囲をずらしたりコード中の `*` を `_` に変えたりして
**中身を壊す**（2026-09-20、`docs/history/direction.md` で19行が壊れた）。

`test/e2e/expected/` は E2E の足場が書く期待値で、`bun run test:e2e:update` のたびに書き直す。
整形をかけると書き直すたびに `format:check` が落ち、走らせた結果（`/tmp/tsukumo-e2e/`）とも
そのまま diff できなくなる。

`docs/history/` 以外の `docs/` は整形の対象に含める。表の桁揃えが全角文字幅を考慮して揃うので、
手で書くより正確になる。

## タスク番号を書かない

コード・ドキュメントにタスク番号（`develop/task/T-xxx.md` の `id`。`T-` + 3桁の連番）を書かない。
変更の経緯は `develop/task/` と `docs/history/` 側に持たせ、コードやドキュメントには
「現在どうなっているか」と「なぜそうなっているか」だけを書く。

タスク番号はアーカイブされると意味を失う一方、コード側の記述は残り続けるため、参照先が消えた
死んだ識別子になる。この規約は `grep -rE "T-[0-9]{3}"` が `develop/` / `docs/history/` 以外で
0件になることで機械的に確認できる。

**例外は `docs/requirements.md`「7. 未決事項」の対応タスク列だけ。** 未決事項は「どのタスクで
決まるのか」が分からないと宙に浮くため、ここだけIDを許す（決まった時点で本文へ移り、IDごと
消える）。上のgrepは `develop/` / `docs/history/` に加えて、この表だけを除外して読む。

**コミットメッセージは対象外**（上の確認はワーキングツリーしか見ない）。件名の先頭にIDを置く
運用は `~/.claude/skills/task-workflow/WORKFLOW.md`「コミットメッセージ」が正典。

## 案を選ぶときの指標（コードの把握のしやすさ）

案が2つ以上あるときは、書いたあとのコードを**読む人が把握しやすいほう**を選ぶ。物差しは次の3つ。

- **1. 開くファイルの数。** その変更を理解するのに何ファイル開く必要があるか。1ファイルで
  完結する案を、2ファイル以上に散る案より上に置く
- **2. 呼ぶ側が知らずに済むか。** 呼ぶ側が、自分のファイルの外の事情（親の DOM の構造・
  別ファイルの CSS・他の層の都合）を知らないと正しく書けない案は下げる。
  `layout.module.css` の「部品は自分の subtree の外の DOM を直接いじらない」と同じ考え方
- **3. 黙って効かなくならないか。** 暗黙の前提（画面幅・件数・並び順）に乗っていて、前提が
  変わると**エラーも出さずに何もしなくなる**案は採らない。読んだ人の理解が裏切られるため

**同点のときだけ**、既存の書き方との一貫性・実行の速さで決める。**工数と行数は指標にしない**
（コードを書く時間は一度きりだが、読む回数はそれより多い）。

**提案で案を並べるときは、この3つでの優劣と理由を必ず添える**（並べただけで終わらせない）。

**例: メインビューのスクロール位置を親へ戻す3案では、`scrollIntoView` を使う案が勝った。**
呼ぶ側が「どの祖先の要素が実際に転がっているか」を知らずに済み、開くファイルも1つで済み、
画面幅が変わって祖先の構造が変わっても黙って効かなくなることがなかったため。

## 仕組みをヒューリスティックより優先する

解決策を提案・選択するときは、**機械的に判定・強制できる仕組み**（検査・テスト・型・hook・lint・
ツールの戻り値での差し戻し）を、**ヒューリスティック**（文面の条・モデルへの指示・覚え書き・
閾値の当て推量）より優先する。仕組みは前提が変わっても自動で効き続けるが、文面の条は読まれない・
忘れられる・モデルが解釈を誤る形で黙って効かなくなる。

**優先の順**: 機械的な仕組み ＞ 仕組みで塞げない部分だけを文面の条で補う。このリポジトリにある
「仕組み」の実例:

- `test/architecture.test.ts`: 層をまたぐ `import` を正規表現で検査し、許した辺以外を落とす
- `src/server/report/core/report-review.ts`: 規約違反のある `report` 呼び出しを handler が差し戻す
- `src/server/report/core/report-tool.ts` の `Stop` フックの関所: ターンの最後に `report` を
  通さない本文で止まろうとしたら差し戻す
- `.oxlintrc.json` の `no-restricted-globals`: `Date` の使用を lint で落とす
- `test/section-reference.test.ts`: 正典の節への参照が切れていないかを検査する

**ヒューリスティックを採るしかないとき**は、その理由（機械で判定できない点）を提案に1行添える。

**案を並べるとき**は、各案が「仕組み」か「ヒューリスティック」かを明示する（「案を選ぶときの
指標」の3つの物差しとは別の軸で、両方を併記してよい）。
