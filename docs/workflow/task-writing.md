# タスク運用: タスクを書く・受け入れる

入口は `docs/workflow.md`（このリポジトリでのタスク運用の上乗せ）。

責務: `plan-tasks` と `next-task` が共通版の手順に加えて守る、このリポジトリ固有の書き方・受け入れ方と、`summary` の長さを持つ。
読む時: タスクを書く・受け入れる・委譲するとき。
直す時: タスクの書き方・受け入れの確かめ方・`summary` の長さを変えたとき。

## タスクを書くとき・受け入れるとき

**`plan-tasks` と `next-task` は、共通版の手順に加えて次を守る。**

- **目視でしか確かめられないものは、何をどう見れば合格なのかまで書く。** 「適切に」
  「きれいに」のような読み手で結論が変わる語を使わない。**`loopable` を `"N"` にするかどうかは
  `docs/workflow/loopable.md`「`loopable` の判定」で決める**（描画の確認そのものは自動でできるので、
  それだけを理由に `"N"` にしない）
- **目視で確かめる完了条件の項目は、頭に印 `[目視]` を付ける。** 印があるときだけ `tw done` が
  `## 結果` の `- 目視:` を求める（正典は task-model の `WORKFLOW.md`「段の中身の書き方」の描画を変えるタスクの項）
- **値の見本（画・HTML）がある描画タスクは、計画の段に、見本の該当する CSS の規則と形（罫・形・高さ・色）を
  写し、実装のどこに当てるかを書く。** 見本の言葉の説明だけを写すと細部が落ち、受け入れの差し戻しで
  初めて出る。実装の方式が見本の DOM と違うとき（表の外の `div` など）は、見本との差が出る細部を先に
  挙げる。例: 見本の `tr.rest` が最後のデータ行の下に罫を残すのに、実装は表の外の `div` にして罫が
  消えた。見本の入口・出口は筒形なのに、角の丸い四角になり凡例と合わなかった
- **`~/.claude/settings.json` を触るタスクには、既存の hooks / statusLine を壊さないことを
  必ず書く**（orca が専有している。`AGENTS.md`「承認が要ること」）
- **環境側の前提はその場で確かめる。** ターミナルの画像プロトコル対応、外部コマンドの有無、
  常駐プロセスの生死は時間とともに変わる。docs やタスク本文に書かれた実測を鵜呑みにしない
- **E2E 全件を何度も流す測定のタスクは、計画の段に E2E 全件を流す回数の割り振りを段ごとに書く。**
  割り振りは `scripts/shared/e2e-run-ledger.ts` の `RUN_LIMIT`（着手中の1件ごとに E2E 全件を
  流してよい回数の上限）の内に収め、最後の段で `tw verify` を通す分の1回を残す。過去の測定では、
  方式ごとに `check --full` を流して上限を使い切り、混ぜ方の測定が終わらず、最後の `tw verify` が
  E2E の段で拒まれて、受け入れで流し直したことがあった。
- **描画を変えるタスクは、DOM に足す class・属性が、記法の語彙の検査と E2E の DOM の期待値にどう響くかを
  計画の段で先に確かめ、期待値の更新（`pnpm run test:e2e:update`）を1回にまとめる。**
  語彙の検査は `test/server/report/core/report-notation.test.ts`、期待値は `test/e2e/expected/`。
  DOM に残る class は CSS Modules のハッシュ名で選べず、class の置き換えは `div`・`span`・`ol`・`li`
  にだけ掛かって svg の要素の class はハッシュ名にならない。印は2つに分ける。
  選ぶためだけの印（CSS の規則を持たない印）は、語彙（`REPORT_NOTATION_NAMES`）に足すと
  「`.report-<名前>` の CSS まで届くか」の検査に落ち、足さなければハッシュ名にならない素の class
  として DOM に残るので、属性にする（`data-reveal-caption` と同じ）。見た目を付ける印は、語彙と
  `.report-<名前>` の CSS を一緒に足す。属性を足すと期待値のファイルが動き、更新と `tw verify` の
  打ち直しが E2E 全件の上限（`RUN_LIMIT`）に響く。
- **`report` の説明文または塊（型の定義）を足す計画は、字数を測るテストを全部挙げ、今の字数と上限の差を数えて段に書く。**
  測るのは3か所で、`test/server/report/core/report-notation.test.ts` が `REPORT_NOTATION_PROMPT` を
  4600字以下に、`test/server/report/core/report-tool.test.ts` が `REPORT_TOOL_DESCRIPTION` を
  2048字未満（MCP ツールの説明文の既定の上限）に、`test/server/session-driver/adapter/sdk-report-tool.test.ts` の
  `REPORT_INPUT_SCHEMA_MAX_CHARS`（21300字）が引数 schema の JSON 全体
  （`REPORT_TASK_DESCRIPTION` などの説明文を含む）を抑える。
  塊を足す計画は、前提の裏取りの行に `REPORT_INPUT_SCHEMA_MAX_CHARS` と実物の字数の差（余白）と、足す塊の
  型の定義のおおよその字数（`claims` で約620字、`region` で約220字）を書き、余白より
  大きければ上限を上げる段を入れる。欄の既定値・空でない文字列・
  正の数は `report-block-field.ts` の `omittable`・`nonEmpty`・`positiveNumber` で書く
  （`.default()`・文字列の `.min(1)`・`.positive()`・`.int()`・数の `.min()` は schema に出て、同じテストファイルの検査に落ちる）。挙げ漏れは
  `grep -rn 'REPORT_INPUT_SCHEMA_MAX_CHARS\|REPORT_NOTATION_PROMPT\|REPORT_TOOL_DESCRIPTION' test` で拾う。
  一部の字数だけ数えると、実装の途中で別のファイルの上限に当たる。
- **記録（使用量の1行）の欄を足す計画は、記録1行を作る場所と丸ごと比べるテストを grep で洗い、
  名指すファイルに入れる。** 洗うには直近に足した欄の名前と版の定数で引く
  （`grep -rln 'shortTable\|hasHowToVerify\|REPORT_USAGE_FORMAT_VERSION' test src scripts`）。
  `test/server/session/core/session-manager-record.test.ts` は1行を欄の値ごと丸ごと比べ、
  `test/server/report/core/report-usage.test.ts` と `report-usage-hint.test.ts` は欄ごとの導出と
  1行の既定値を比べるので、欄が増えたら全部直す。`test/server/report/adapter/report-usage-log.test.ts` は欄名の一覧を比べ、版は
  `REPORT_USAGE_FORMAT_VERSION` の参照なので、欄が増えたら一覧を直し、版だけ上げるなら無修正で通る。
  版を上げるときは `scripts/runtime/report-block-usage.ts` の版別の枝（定数・`recordSchema` の union・
  `rejectionSchema` の版の上限の3か所）も足す。
- **描き分けの条件を足し、既存の描き方に届かなくなる場合ができる変更の計画は、段に「届かなくなった描き方を
  書いた正典の文・コメント・テスト名・分岐・印と CSS を grep で洗って直す」を置く。** 洗うには、届かなく
  なった描き方の語（表示名・関数名・印の名前・CSS の class）で `docs/` `src/` `test/` を引く。例は帯に
  waterfall の分岐を足した変更で、帯の斜線の箇条・2つの図・`src/shared/report/report-phase-time.ts` の
  `bandSegmentMarkdown` の不明の枝が古くなり、段が無かったので最後の受け入れの差し戻しで初めて出た。
- **spec の出典**は `docs/requirements.md` と各タスクの本文（`tw show GH-<n>`。GitHub の Issue は
  その写しで、正は Beads）。2026-09-27 より前に閉じたタスクの本文は、git の履歴の `develop/task/` と
  `docs/history/tasks.md` にある。**standards の出典**は `AGENTS.md` ＋
  `docs/coding-standards.md` ＋ `docs/architecture.md` の3つ。`code-review` スキルが
  「リポジトリ内から探す」と言うのはこれらのこと
- **ブランチは自分で切らない。** コミット先はいま居るブランチで、作業ツリーを分けるのは
  orca の仕事（`AGENTS.md`「Git運用」）
- **会話の内容をログ・`evidence`・テストのフィクスチャに写さない**
  （`docs/coding-standards.md`「会話内容の扱い」。他のどの規約よりも優先する）
- **確認手順が触る資源は「触らない」ではなく「確認後に元の値へ戻す」と書く。** 「触らない」と
  禁止だけを書くと、完了条件を確かめる手順そのものがその資源を書き換える場合に矛盾する
  （例: パック切り替えの目視確認は `~/.tsukumo/state.json` を書き換える）
- **層で割った一括置換のタスクを書くときは、どの層にも属さないディレクトリ（`scripts/` など）を
  本文に名指しする。** `shared` / `server` / `browser` のような層の一覧だけを挙げると、
  どの層にも属さない置き場が誰の担当にもならず、対象から漏れたまま残る
- **対象の場所は行番号ではなくシンボル名（関数名・型名・ファイル名）で書き、件数を挙げるときは
  着手時に一覧を取り直す grep のコマンドを添える。** 行番号と件数は、並行する作業ツリーの
  分割・移動で着手までにずれる
- **正典の大掃除（本文を `docs/history/` などへ移して消す）を委譲するときは、「先に移送先へ
  書いてから元を消す」順で進めさせる。** 途中で落ちても「移り終わったところまで」が残る。
  逆の順だと、利用上限で止まったときに消した本文がどこにも無い状態で残る（実際に
  `docs/requirements.md` から151行が消え、移送先がまだ作られていないまま止まったことがある）
- **AGENTS.md や docs の節を削る・縮めるタスクは、消した規則ごとの行き先（移した節・捨てた理由）の表を
  完了条件に書かせ、受け入れでその表と差分を突き合わせる。** 常設の指示のファイルを 413行から347行に
  縮めたとき、「新しい作業ツリーの立ち上げは人がやる」という規則がどこにも移されずに消え、
  受け入れで見つけて戻したことがある
- **サブエージェントの途中経過は `TaskOutput` で読まない。** 出力ファイルは会話まるごとの
  JSONL で、読むとメインのコンテキストが溢れる。途中経過は委譲した側から
  `SendMessage({ to: "main" })` で押し込ませる（背景で動いているときだけ使える）
- **SDK のイベントを足す・扱いを変えるタスクは、そのイベントを起こす経路を本文に列挙し、
  1回のやり取りで何回起きうるかを書く。** 委譲中の進み具合の合図（`SendMessage`）を「委譲1回に
  つき1回」と見て吹き出しを空にする仕様を書いたところ、実際は合図が委譲1回で複数回届き、
  吹き出しが「（まだ発話がありません）」に戻り続けた（経緯は `docs/architecture/screen-design.md` 13.9
  「バックグラウンドタスク」）
- **わざと壊して落ちるか確かめるときは、このタスクで編集していないファイルか一時ファイルに
  壊しを入れる。** 退避したコピーから戻す——`git checkout --` で戻すと、同じファイルへの
  先行の編集ごと消える
- **ランタイム・束ね・タイマーを変えるタスクは、`tw status` の件名に「ときどき落ちる」とある
  未完了のタスクを `dependencies` に入れて登録する。** 実行環境やタイミングが変わると、ときどきだった
  揺れが毎回落ちるようになり、移行の差分ごと戻すことになる
- **新しい部品・フック・`domain/` を足すタスクの計画では、置き場を `docs/architecture/directory.md`「ページの形」の
  表と深さの上限で確かめてから `## やること` に書く。** 子部品を部品の `components/` の下に置く
  計画は、実装の途中で `test/architecture/browser-depth.test.ts` の深さの検査に落ち、置き場を作り直すことになる
- **`components/page/` へ移すタスクは、移し先をページの形で書く。** 「6ファイルを
  `conversation-layout/` へ」のように置き場所だけ書くと、直下に置くか `components/` や
  `hooks/`・`domain/` の下に置くかが不明で、`test/architecture/browser-box.test.ts`「components/page/ の形」の検査に
  落ちる。対象ファイルを `components/<部品>/`・`domain/`・`hooks/` の層ごとに分けて書き、タスク本文で
  各層の対応を明示する（ページの形は `docs/architecture/directory.md`「ページの形」）。置き場所だけの指示では
  直下に置かれ、この検査に落とされて同じファイルを何度も直すことになった
- **実装・受け入れで、文字列・正規表現・行の形（1行目・先頭語の照合を含む）・モデルの自己申告で
  判定している箇所を見つけたら、構造化した値・台帳・型で置き換えられるかを指摘する。** キャラクターの
  セリフ・振る舞いは除く（`docs/coding-standards.md`「仕組みをヒューリスティックより優先する」）。
  外の形式が文字列しか渡さないときは、その旨を1行添える
- **タスクを積むとき（`plan-tasks`・振り返りのドラフト）は、それが判定の仕組みかを見る。**
  ヒューリスティックの判定を後から仕組みにし直す話になっていないかを確かめる
- **用語の追随（旧称を新しい呼び名へ揃える作業）では、旧称の grep の出力を切らずに全件出し、
  ディレクトリ単位で別の意味と決めず、1件ずつ文脈で分類する。** 出力を `cut` で削ると長い表の行の
  後半にある旧称を見落とし、縮めた語を一括で別の意味と分類すると、その中の1行を落とす
  （どちらも受け入れで全件を読み直して拾ったことがある）。旧称は行末で折り返されることがあり、
  1行の grep では拾えないので、改行と行頭の記号（`//`・`*`・`>`）を詰めて探す走査も打つ。
  `と`・`・` でつないだ並列形や近い綴り（「雑談の要約・アーカイブ」など）は、旧称を文字どおり
  引く grep に当たらないので、語を分けても洗う。最後に、旧称の grep の残りが
  `docs/glossary.md`「避ける言い方」の説明の行と分類済みの別の意味の行だけであることを、
  `ファイル:行 | 分類` の一覧で報告に示す。旧称が「避ける言い方」に無ければ、旧称と新しい呼び名を
  報告の冒頭に書く。折り返しの走査を `scripts/document/` の検査にしないのは、旧称がその作業ごとに
  変わり、検査に載せる固定の語が無く、`rg -U` に折り返しの正規表現を渡せば足りるため
- **手順書に「この条件では撮れない・失敗する」と書くときは、書いた最新のコマンドをその条件で
  そのまま走らせて確かめた事実だけを書く。** 古い手順のときの観察を新しいコマンドの隣に残すと、
  新しい手順の話に読める。手順書を直すタスクの計画の「確かめ方」には、書いた
  失敗の仕方を別の条件（別の幅など）で走らせる確認を入れる
- **`test/e2e/` にファイルを足す計画は、名指すファイルに `scripts/shared/e2e-watch.ts` と
  `docs/architecture/testing.md` を入れ、段に「見張りの表に足す」「一覧に行を足す」を書く。**
  `E2E_WATCHED_REGIONS` にそのファイルが見ている領域（`E2E_REGION_ROOTS` の名前の配列、ページ全体を
  見るなら `"every"`）を足し、`docs/architecture/testing.md`「E2E のシナリオの一覧」の表に行を足す。
  どちらも足し忘れると、
  `test/scripts/shared/e2e-selection.test.ts` の「見張りの表」と
  `test/architecture/e2e-scenario-list.test.ts` が `tw verify` の長い E2E の段のあとで落ち、足して
  打ち直すことになる。計画を書く前に
  `grep -n 'test/e2e/<近い既存のファイル>' scripts/shared/e2e-watch.ts docs/architecture/testing.md` で、
  近い既存ファイルの行を見本にする
- **名指すファイルは `pnpm run token-count <パス…>` で測る。** `over`・`near` が付いたものは、足す先を
  別ファイルにする段か切り出す段を計画に置く
- **差分が1か所・数行に収まる文書のタスク（追記・言い換え）の `## やること` は、段を分けず1段にまとめる。**
  数行の追記を複数の段に割ると、実装役が頼まれた段を越えて全段を済ませて返し、往復が空になる。1段にしたときは、満たす完了条件の欄にすべての行を
  引き、検証（`pnpm run check`。打つのは `tw verify`）もその段に含める。段の分け方の一般の基準は
  `~/.claude/skills/task-model/WORKFLOW.md`「段の形」を見る
- **大きいファイルを割るタスクの計画には、呼ぶ側の数え方と関数の並べ替えを書く。** 呼ぶ側を数える
  `grep` の範囲は `src test scripts docs` にする。群をまたぐ private を `export` にした段は、
  `test/architecture/function-order.test.ts`（export する関数は export しない関数より前）が落ちるので、
  宣言の並べ替えを同じ段に含める
- **テストを割るタスクの計画には、書き出し直した前後の `\u` エスケープの数の確かめを書く。**
  `grep -oE '\\u[0-9A-Fa-f]{4}' <ファイル> | wc -l` の合計を、移す前の元のファイルと移したあとの
  全ファイルで比べる（`-c` は当たった行の数で、`-E` が無いと `{4}` が効かず常に 0）。
  Write・Edit で書き出し直すと、元の `\u` に4桁を続けたエスケープ（ゼロ幅スペースなど）が
  見えない文字そのものに置き換わり、型検査・テスト・format のどれでも落ちない。合わなければ、`\` と `u200B` を別々に組み立てて直す

## `summary` の長さ

共通版は「1行に収める」とだけ言う。**このリポジトリでは全角40文字以内**を目安にする
（サイドバーのタスク一覧が2列の行で出すため。`src/browser/features/task-board/task-list.tsx` の `TaskItem`）。
