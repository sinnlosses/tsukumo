## 作業ツリーを並行させるとき

作業ツリーが分かれていれば、2つのタスクを並行して進めてよい（触る層が重なっていても選んでよい。
相手の足元のファイルは動かない。取り合いを防ぐのは Beads の着手の印——`tw claim` が本体の
作業ツリーの `.beads` に `bd update --claim` を打つ）。**検証コマンドは並行して打ってよい**（自分の作業ツリーで走る
ので、相手の作業中の変更を拾わない）が、次の2点は tsukumo 固有の落とし穴:

- **ポートは作業ツリーで分かれない。** `pnpm run check` に含まれる `test/cli.test.ts`
  「既定ポートから上限まで全部塞がっていると…終了コード1で終わる」はポート範囲を専有して
  確かめるテストなので、並行して打つと時間切れになることがある（テスト側をポートの取り合いに
  左右されなくする直しは別のタスクで扱う。それまでは時間切れになったら打ち直す）
- **tsukumo を起こす目視確認が要るタスクを並行させるなら、`TSUKUMO_VIEW_PORT` と
  `TSUKUMO_HOME` を2つとも分ける。** ポートだけ分けてもホーム（`~/.tsukumo/` の
  `state.json`・あらすじと会話のアーカイブ・トークンの記録）は共有されたままで、とくにあらすじは
  全上書きなので後に書いたほうが相手のものを丸ごと消す。分けたホームに覚えたキャラクターは
  本体のホームへは戻らない
- 自分の着手の印が無く未コミットの変更がある作業ツリーでの `git restore`・`checkout --`・`clean`・`stash` は、
  hook `deny-foreign-restore`（`scripts/hook/lib/foreign-restore.ts`）が log-only で記録する（拒まない。手順は `docs/coding-standards/hook-rollout.md`）

## タスクに紐付かない作業を main へ送る

**`main` へ入れるまでが開発のひと区切り。** 会話で頼まれた雑多な変更も、検証（`pnpm run check`、
描画に関わるなら目視も）が済んだら自分の枝にコミットして `main` へ送る。**送ってよいか聞いて
止まらない**——未コミットのまま待つと、作業ツリーを後から使うセッションが `git restore` で
捨てうる（2026-09-23 に実際に9ファイルぶんが痕跡なく消えた）。

`node scripts/dev/ship.ts`（`pnpm run ship`）を打つ。作業ツリーが clean か → `main` を出している
作業ツリーが clean か → `git rebase main` → `pnpm run check --full` → `git -C <本体> merge --ff-only`
の順に動き、`--ff-only` が `main` の先回りで落ちたら取り込み（`rebase`）と検証をやり直す
（上限2回。超えたら止まる）。この作業ツリーに `tw claim` 済みの着手中のタスクがあると、`ship` は
検証より前に拒む（着手中のタスクは `tw finish` で送る。`tw status` が読めないときは拒まず進む）。
落ちた段によって次を行う。

- 自分の作業ツリーが clean でない: コミットしてから打ち直す
- `main` を出している作業ツリーが clean でない: そちらを片付けてから打ち直す
- `git rebase main` が衝突した（`rebase --abort` 済み）: 衝突を手で解消し、コミットしてから打ち直す
- `pnpm run check --full` が落ちた: 直してから打ち直す
- やり直しの上限を超えた: `main` が速く進みすぎている。少し待つか、送る相手に相談する

## コミット前のファイルの大きさの検査

1 ファイルが大きいと、読むたびにコンテキストを食い、編集の突き合わせも壊れやすくなる。
そこで git の `pre-commit` が、ステージした内容（インデックスの blob）の大きさを測り、
上限（5,000 トークン = 20,000 バイト。`docs/` 配下の `.md` だけ 12,000 トークン = 48,000 バイト。
1 トークン = 4 バイト）を超えるファイルの**追加**と、
すでに超えているファイルを HEAD より**大きくする**変更を止める（終了コード 1）。
上限ちょうどは通る。縮める・同じ大きさは通る。名前変更は元のパスの HEAD と比べる。
Claude Code の hook は `tw finish` や `tw ship` が子プロセスで打つ `git commit` を見られないので、検査は git 側に置く。

- 止まったら、stderr の分割の手順（拡張子ごと）に従って分け、`git add` し直してもう一度コミットする。
  `--no-verify` は使わない
- 増やす場合は、同じコミットで同じファイルの別の部分を減らす・別のファイルへ移して、純増にならないようにする
- 検査から外すのは、ロックファイル・生成物・取り込んだ履歴・submodule・疑似セッションの台本・バイナリ。
  外すパターンは `scripts/shared/token-limit.ts` の `EXEMPT_PATH_PATTERNS` 1 か所にある。
  分けられない生成物は、ここへ足すことを人に相談する
- git が失敗して判定できないときは、コミットを巻き込まずに通す
- 検査は `mise run setup`（または `node scripts/dev/install-git-hook.ts`）が共有の `.git/hooks/pre-commit` に置く。
  別の中身の `pre-commit` が既にあれば上書きしない。共有の `.git/hooks` はリポジトリの外にあるので、
  置くのは各自が本体の作業ツリーで 1 回打つ

## 実機の Claude Code を動かす計測のとき

エージェントの Bash から同梱 CLI（`claude -p`・SDK の `query`）を起こす計測は、本番の計測の前に
**数秒の上限を付けた1回の呼び出しで、CLI が応答するか**を確かめる。macOS には `timeout` コマンドが
無いので、上限は perl の alarm（外側）か node の `AbortController`（内側）で付ける。2026-10-17 に実機で通った形:

```bash
perl -e 'alarm 15; exec @ARGV' claude -p "1と答えて"   # 7秒で応答、exit=0
```

SDK の `query` は `maxTurns: 1` と `AbortController`（20秒）を付けて同じ形で打ち、3.6秒で応答した。

過去の計測では、CLI がキーチェーンの読み出し待ちで無音のまま止まり、原因の特定に5回打ち、止まった
9本のプロセスが残った。2026-10-17 の再確認では止まらなかったので、**止まる条件は特定できていない**
（条件つきで起きるのだろう）。

- 見分け方: 応答が上限を超えたら、止まったプロセスに `sample <pid>` を打ち、`SecItemCopyMatching`
  （キーチェーンの読み出し待ち）が出るかを見る。これは止まったときの観測で、2026-10-17 は止まらず、
  この見分けは実機で確かめていない
- 止め方: 残った子のプロセスの kill は auto mode に拒まれる。エージェントは止めずに、止まった事実と
  pid を報告に書いてメインに預ける
