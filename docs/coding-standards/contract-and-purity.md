# コーディング規約: 契約による設計と純粋関数

ステータス: **正典**。入口は `docs/coding-standards.md`（規約の理由と例外の入口と、子のファイルの一覧）。

責務: 事前条件・事後条件・不変条件で関数の責務を分ける考え方と、検査を型・境界・テストのどこに置くかの判断、副作用を端に押し出して判断を純粋関数に保つ決まりの、理由と例外を持つ。
読む時: 関数の引数の条件や返り値の保証をどこで守るか決めるとき、判断と副作用（時計・乱数・DOM・ファイル・通信）が同じ関数に混ざったとき。
直す時: 検査を置く場所の判断・純粋にする範囲・例外を変えたとき。調査の根拠は `docs/research/design-by-contract.md`。

## 契約の三つの条件

関数（や型）の責務を、呼ぶ側と呼ばれる側の約束として分けて考える。

| 条件     | 誰が守るか                 | tsukumo での表し方                                                                                 |
| -------- | -------------------------- | -------------------------------------------------------------------------------------------------- |
| 事前条件 | 呼ぶ側（顧客）             | 型で表す。表せない外の値は境界で parse してから内側へ渡す                                          |
| 事後条件 | 呼ばれる側（供給者）       | 返り値の型で表す。型で表せない性質（並びが保たれる・合計が一致する）は純粋な関数の単体テストで守る |
| 不変条件 | 型の作り手（作り方を絞る） | 判別可能な合併型・branded な型・作り手を1つにした関数で、不正な状態を書けなくする                  |

呼ばれる側は、事前条件が成り立つと仮定してよい。**内側の関数が、境界で畳んだ値をもう一度確かめ直さない**
（防御的な重複検査は契約が退けたもの。確かめ直すほど、どこが責任を持つのか分からなくなる）。

## 検査をどこに置くか

| 区分                                                | 扱い                                                                                       |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 外の世界から入る値（ファイル・環境変数・SDK・通信） | **境界で1回、実行時に parse する**（`unknown` で受けて zod で畳む）。`as` で型だけ付けない |
| 境界の内側の、型で表せる条件                        | **型に任せる**（判別可能な合併型・branded な型）。実行時に検査しない                       |
| 内側の関数の事前条件のうち、型で表せないもの        | **検査しない**。doc コメントに条件を書き、呼ぶ側のテストで確かめる                         |
| 内側の「ここで起きたらバグ」の確認                  | 少数だけ `asserts` 関数で表す。`!`・`as` で黙らせない                                      |
| 純粋な関数の事後条件                                | **テストで確かめる**。実行時の検査にしない                                                 |

型の契約が嘘になる形を作らない: 境界で `as` や型注釈だけで内側の型を主張し、実行時には何も確かめない。

### 不変条件を型で守る

- 2つ以上のフィールドが組み合わせの制約を持つ（片方が `true` のときだけもう片方に意味がある、2つの欄が同時に有る無しになる）なら、**判別可能な合併型**にする。`boolean` や `""` で「種類」を表さない
- 検査済みの値は **branded な型**で運び、作れるのは検査する関数（`parse…`）だけにする。同じ形の `string` の ID（種類の違うもの）や、検査済みと未検査が同じ型で流れる形を避ける。branded な型が既にあるのに、その型を使う関数が素の `string` で受けているのは不変条件の取りこぼし
- 日付・ID・パスのように「形が決まっている `string`」は、境界で畳んだ型（`DateKey` など）で内側へ渡す。内側で `Temporal.PlainDate.from(string)` のように例外を投げうる変換を呼ばない

### 失敗の載せ先

契約の違反（バグ）を例外で表すとき、常駐プロセスを落とさない規約（`docs/coding-standards/error-input-and-absent-value.md`「エラーハンドリング」）に従う。起動時の前提不足だけが即時終了で、動作中は描画の境界（`ScreenBoundary` など）が受け止める。内側の関数に `try`/`catch` を散らして表明を握りつぶさない。

## 副作用を隔離し、純粋関数を保つ

tsukumo は「読む → 決める → 描く」を繰り返す（`docs/architecture.md` 原則2）。**「決める」を純粋な関数にし、「読む」と「描く」（副作用）を端に置く。** 純粋な関数は同じ入力で同じ出力を返し、テストに時計も偽の読み元も要らず、事後条件をテストで守れる。

純粋にする範囲は `src/shared/`・`src/server/**/core/`・`src/browser/domain/`・`src/browser/utils/`・`src/browser/lib/` の関数。ここでは次をしない:

- **引数の入れ物を書き換えない**（`push`・`splice`・`sort`・`delete`・プロパティへの代入。関数の中で作ったローカルの入れ物は良い）
- **隠れた入力を内側で読まない**: 時計（`Date.now`・`Temporal.Now`・`performance.now`）・乱数（`crypto.randomUUID`・`Math.random`）・`process`・`window`・`document`・`localStorage`・`fetch`・`node:fs`。必要なら引数（値、または `now: () => number` のような関数）で受け、配線の側で渡す
- **モジュールのトップレベルに、変わる状態（キャッシュ・カウンタ）を持たない**。状態を持つ資源は作る側の閉包に閉じ込める（`typescript-writing.md`「変数は基本イミュータブル」）

`adapter`・`wiring`・React の部品とフックは副作用を持ってよい層だが、**純粋に切り出せる判断（分岐・変換・整形・「通知するか」の判定）を IO と同じ関数に埋めない**。判断を `core`（または `domain`）の純粋な関数に出し、`adapter` は「読む・書く・呼ぶ」だけにする。

### 例外

- 常駐の資源（接続・タイマー・購読）の可変状態は、閉包の中なら良い
- DOM を読み書きすること自体が目的の関数（スクロール・計測・描画の演出）は、`src/browser/domain/` の中でも DOM を直接触ってよい。ただし判断（いつ・どれだけ）は別の純粋関数に出す
- 常駐でないキャッシュを持つときは、持つ理由を doc コメントに1行で書く
