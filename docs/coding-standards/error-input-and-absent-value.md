# コーディング規約: エラー・外部の入力・「無い」値

ステータス: **正典**。入口は `docs/coding-standards.md`（規約の理由と例外の入口と、子のファイルの一覧）。

責務: エラーハンドリング・失敗を返す戻り値の kind の語・外部の入力を読む場所・型に「無い」を残してよい場所と `null` の書いてよい場所・「無い」の書き方の、理由と例外を持つ。
読む時: 失敗の扱い・環境変数やパスの読み取り・「無いかもしれない」値の型を決めるとき。
直す時: エラーの2チャネル・入力の集約・`| undefined` / `null` の例外を変えたとき、プロパティと引数の `| undefined` の検査を変えたとき。

## エラーハンドリング

**tsukumo は常駐プロセスであり、描画1回の失敗で落ちてはいけない**
（`docs/requirements.md`「5. 実行環境・非機能要件」）。エラーは2チャネルに分ける:

| 種類                                                                                      | 扱い                                                     |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 起動時に前提が満たされていない（transcript のパスが分からない、定義ファイルが壊れている） | 例外を投げて**即時終了**。理由を1行で表示する            |
| 動作中の一時的な失敗（JSONLの行が途中まで、画像が読めない、端末が狭い）                   | **その回の描画だけ諦めて次へ進む**。落ちない             |
| 画像プロトコルが使えない                                                                  | エラーではない。テキストのみのフォールバックへ切り替える |

**描画ループの中に `try`/`catch` を散らさない。** 1回分の描画をまるごと包む場所を1つ決め、
そこで受け止める。散らすと「どこまで描けたのか」が分からなくなり、部分的に壊れた画面が残る。
ブラウザ側の包む場所は `components/app/layout.tsx` の画面ごとの `ScreenBoundary`（画面のナビの帯は外に残す）。

**入口で済ませた判定（ターン中なら断る、など）は `await` をまたいで保たれない。** `await` の
あとで同じ判定を取り直す。駆動へは「前提を渡すメソッド」を「依頼を送るメソッド」より先に呼ぶ——待つあいだに
別の依頼でターンが始まると、判定を取り直さない限り二重に送ってしまう。

## 失敗を返す戻り値

例外にしない失敗（動作中の一時的な失敗・読めなかった・断った）を戻り値で返すときは、**`kind` の判別可能な合併型**にし、`kind` の語は次の表から選ぶ。`ok: boolean` と `reason: string` の対にしない。理由を足すなら、その kind の枝に `reason`（列挙した語の合併型）などの欄を持たせる。`undefined` や `[]` を「失敗」の代わりに返さない。

| 語            | 意味                                                           | 使う場面                                                                 | 旧い語・形からの対応                                  |
| ------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------- |
| `failed`      | 外の世界の呼び出し・書き込みを試みて失敗した                   | ファイル書き込み・子プロセス・ネットワーク・SDK の呼び出しの失敗         | 残す。`ok: false` の「実行の失敗」はここへ寄せる      |
| `unavailable` | 読み取りの結果が得られない（読み元が応じない・読めない）       | 読み取りの結果型。読めない原因は `reason` の欄で分ける                   | 残す。`unreadable` はここへ寄せる                     |
| `invalid`     | 受け取った入力・読めた中身が形・範囲・前提に合わない（拒否も） | 環境変数・利用者の入力・読めたが形の違うデータ・前提を満たさず断った操作 | 残す。`broken` はここへ寄せる                         |
| `missing`     | 無い（失敗ではない）                                           | 置き場にまだ無い・見つからない                                           | 残す。`ok: false, reason: "not-found"` はここへ寄せる |

- 6語の行き先: `failed`・`unavailable`・`invalid`・`missing` は残す。`unreadable` は `unavailable`、`broken` は `invalid` へ寄せる。表に無い意味が出たら、まず表の語に当てられないか考え、足すなら表に1行足す。
- 「無い」と「失敗」は別の kind で表す。`missing` は失敗ではなく、呼ぶ側が既定で埋めてよい。`unavailable`・`failed` は埋めずに利用者へ見せる（「無いかもしれない」値の節と同じ向き）。
- **core の段取り関数は、port（外へ出る口）の失敗を1か所で kind に畳む。** `try`/`catch` は port を呼ぶ最も外側の1か所に置き、そこで `failed` / `unavailable` に変える。そこより内側に `catch` を散らさず、空の `catch` や `.catch(() => undefined)` で失敗を握りつぶさない。呼ぶ側は kind の分岐で扱う。
- 例外は契約違反（バグ）を表すときだけに残す。上の「エラーハンドリング」の2チャネルは変えない。

## 外部の入力を読む場所を1つにする

環境変数・ホームディレクトリ・transcript のパス・キャラクターパックのパスといった
**外の世界に依存する値は、読み取りを1つのモジュールに集約する**。モジュールのトップレベルで
環境変数に触らない（読み取りの順序に依存し、テストから差し替えられなくなる）。
tsukumo を起こしたディレクトリ（`process.cwd()`）も同じで、読むのは入口の `src/cli.ts` だけ。
以降は引数で受け取る。`process.env`・`process.cwd`・`node:os` を読めるファイルは
`.oxlintrc.json` の `overrides` が決め、ほかのファイルで読むと lint が落とす。
`process` を別名で import した下の読み取りは lint が拾えないので、`test/architecture/outside-world.test.ts` が
別名の import を落とす。`require()` で読む形は見ない（`src` は ESM で使い手が無い）。

集約すると、テストで環境を差し替える手段が1つで済み、「この値はどこで決まったのか」を
探す場所も1つになる。

**同じ形を型と schema で二重に書かない。** 外から読む値の型は、schema から `z.infer` で導く。

### 同じコードベースの送り手を信頼する

サーバからブラウザへ押すフレーム（`ServerFrame`）は外の世界ではなく、同じビルドのサーバが型の付いた値から組み立てる。
そこで受け取る側（`parseServerFrame`）は**封筒だけを実行時に確かめ、中身は送り手を信頼する**。

| 確かめるもの（封筒）                                                         | 信頼するもの（中身）                                                   |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `type`・`protocolVersion`・`target`、`events[]` の `at` と `event.kind`      | `hello` の `state` が `SessionState` の形であること                    |
| `state`・`event` がオブジェクトであること、`kind` が知っている種類であること | `event` の `kind` 以外の欄が、その種類の `SessionEvent` の形であること |

信頼の事前条件は「送り手が同じビルドである」こと。版の違う組（古いタブと新しいプロセス）は `hello` の `protocolVersion` で見分けて読み込み直しを出すので、
形を変えたら `PROTOCOL_VERSION` を上げることが、この事前条件を守る手段になる。
中身まで schema にすると `SessionEvent` と `SessionState` の全種類を zod で持ち直すことになり、上の「二重に書かない」と両立しない。

壊れたフレームの扱い:

- 封筒が読めないフレームは1つ丸ごと捨て、次を待つ。`events` の束から知らない `kind` の要素だけを落とし、残りは畳む
- 封筒が読めて中身の欄が壊れたフレームは、境界では見分けない。送り手の不具合で、畳み込みか描画で投げたら「その回の描画だけ諦める」（上の「エラーハンドリング」）に任せる

疑似セッションの定義ファイル（`fixture/fake-session/`）も同じリポジトリで手で書くものなので、同じ封筒の schema（`sessionEventSchema`）で読む。

## 「無いかもしれない」値

型に「無い」を残してよいのは**次の4つの場所**。どれにも当てはまらないなら型に「無い」を
残さず、判別可能な合併型にするか（下の「複数の「無い」が1つの状態」）、入口で畳む
（下の「「無い」を層をまたいで運ばない」）。

| #   | 型に「無い」を残してよい場所           | 判定（コードを見れば決まる）                                                                                                                     |
| --- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **外の世界の値を写した直後**           | その「無い」を書いている関数が `src/server/adapter/` にある、または `unknown` / 定義ファイルの中身 / 環境変数 / SDK のイベントを引数に取っている |
| 2   | **TypeScript が生む `undefined`**      | 型注釈を書いていない（`noUncheckedIndexedAccess` の添字・`Map.get`・`Array.at` / `find` / `findLast` の戻り値）                                  |
| 3   | **React が型で要求するもの**           | `useState` / `useRef` / `createContext` / zustand の `create` の型引数、`CSSProperties` の拡張                                                   |
| 4   | **React の外の資源を持つ可変の入れ物** | `let` 宣言で、初期値が `undefined`、あとから代入がある（タイマー・ソケット・キャッシュ・畳み込みの途中）                                         |

例外1は外の世界の「無い」をそのまま写したもの。transcript にまだ assistant の行が1つも無い、
状態ファイルがまだ書かれていない、キャラクターパックに該当する表情が無い、環境変数の未設定。
要件を変えても消えない情報なので、正直に表す。

例外2は `tsconfig.json` の `noUncheckedIndexedAccess` を有効にしてあるために自動で付くもの。
**これを `!` で潰さない**（上の「型を迂回するキャストを使わない」）。消したいなら、添字ではなく
「必ずある」ことを型で表せる形（合併型・全域の対応表）に変える。

**プロパティと引数の「無い」は `?:` で書き、`T | undefined` を書かない。** 書き方は
`readonly x?: T`（プロパティ）と `x?: T`（引数）。`x?: T | undefined` とも重ねない。
`tsconfig.json` は `exactOptionalPropertyTypes` を有効にしていないので、`x?: T` を読む側の型は
`T | undefined` のままで、`x: undefined` と書いて渡すこともできる。
既定値を持つ調整用のつまみ（引数オブジェクトごと省略できる中身）や、省略が普通の DOM 属性
（ui の部品の `aria*`・`title` など）も同じ `?:` で書き、別扱いにしない。
引数の後ろに必須の引数が続くときだけは `?:` にできない（TypeScript が TS1016 で拒む）ので、
`x: T | undefined` と書く。
戻り値・変数・型引数・入れ子の型（`Record<string, T | undefined>` など）の `undefined` は、
表記の決まりの対象外（上の表の例外2〜4に当たるか、合併型の値そのもの）。
`test/architecture/type-shape.test.ts` が、`src`・`test`・`scripts` のプロパティと引数の型の
最上位の合併に `undefined` を書くと落とす（後ろに必須の引数が続く引数は通す）。

**例外1に当てはまらないのに型に「無い」を残すとき**は、書く前に次の3つを確かめる
（例外2〜4は残すかどうかを選べないので対象外）:

- **片方だけが `undefined` になる状態が実在するか。** しないなら1つの状態なので合併型にする
  （下の「複数の「無い」が1つの状態」）
- **その `undefined` が持つ意味が1つか。** 「まだ来ていない」と「読めない」が同じ `undefined` に
  乗っているなら割る
- **入口より内側へ運んでいないか。** 層をまたぐなら入口で畳む
  （下の「「無い」を層をまたいで運ばない」）

**「無い」を型から消すことを目的にしない。** 消す手は判別可能な合併型にするか入口で全域に
畳むかの2つだけで、**この2つで消えないものは本物の「無い」** なので消さない。手が無いのに
消そうとすると `!` や `as` に化ける（上の「型を迂回するキャストを使わない」）。なぜ「無い」が
生まれるのかを先に問い、値の持ち主や取得のタイミングが正しくないなら**そちらを直す**。

### 複数の「無い」が1つの状態

2つ以上の「無い」（`?:` の欄）が**同じ1つのこと**を表しているなら、フィールドを並べず判別可能な
合併型（タグ付き合併）にする。

```ts
// 避ける: 8通り書けるのに、実在するのは3つ
readonly turnInProgress: boolean
readonly turnStartedAt?: number
readonly turnFinishedAt?: number

// こうする
readonly turn:
  | { readonly kind: "idle" }
  | { readonly kind: "running"; readonly startedAt: number }
  | { readonly kind: "finished"; readonly startedAt: number; readonly finishedAt: number }
```

並べると、**型としては書けるのに起きない組み合わせ**（終わっているのに始まっていない、など）が
残る。読む側はそれを毎回 `=== undefined` の組み合わせで解き直すことになり、同じ解読が使う場所の
数だけ複製される。合併型なら分岐は `turn.kind` の1つで済み、各状態に**その状態でだけ意味を持つ
値**を持たせられる。

判断の目安は「**片方だけが `undefined` になる状態が実在するか**」。しないなら1つの状態なので
合併型にする。

### 「無い」を層をまたいで運ばない

「無い」が本物なのは、外の世界と接する**入口だけ**。そこで畳んでから内側へ渡し、内側の関数は
「必ず値がある」型で受ける。畳み方は2つ — 既定値に置き換える（`??`）か、呼び出し側で分岐して
「ある」場合にだけ内側を呼ぶ。

「無い」を受ける関数（`x?: T` の引数）が数珠つなぎになると、**どの層で「無い」が確定するのか**が
分からなくなり、同じ `undefined` チェックが各層に散る。内側の関数は自分の仕事に集中できず、
「値が無いときにここは何を返すべきか」をその都度決めることになる。

### null は自前の型に出さない

`null` を書いてよいのは次の3つだけ:

- React の型が要求する `null` — `useRef<T>(null)` の初期値、`ref=` へ渡す値、`RefCallback` が受ける引数
- 外来 API の戻り値・SDK の型が要求するものをそのまま受ける場所 — `localStorage.getItem`、
  `child_process` の `error`、SDK の `parent_tool_use_id`
- `typeof value === "object" && value !== null` の型ガード

「何も描かない」は `return undefined` で、コンポーネントの戻り値の型は `ReactElement | undefined`。
リテラルの `null` は `.oxlintrc.json` の `unicorn/no-null` が `src/`・`scripts/`・`test/` で見る（SDK の型が要求する
2 ファイルと、SDK・外来の生データや DOM API の `null` を扱う `test/fixture/`・`test/browser/`・`test/e2e/`・
`test/server/` の `session-driver`・`diary`・`repository`・`usage`・`workflow-setting` は外す。ref の初期値と `=== null` の比較は見ない）。

自分で定義する型・関数の戻り値・`shared` の型には出さない。外来の `null` は**受け取った境界で
`undefined` に畳む**。「無い」の表し方が2つあると、チェックが `== null` か `=== undefined` かで
揺れ、どちらが起きうるのかを呼び出し側が毎回確かめることになる。この判断を境界の1箇所に寄せる。

`scripts/`・`src/shared/`・`src/server/` の `core`・`src/browser/` の `domain` と `utils` の型位置の `null`（型・インターフェース・関数の引数と戻り値・
変数の型注釈・クラスのメンバの型）は、`.oxlintrc.json` の `typescript/no-restricted-types` が機械で見る。
外の型が null を要求する口（React の `RefObject<X | null>`、lezer の `SyntaxNode | null`）だけは、そのファイルを除外する。除外は5件までにする。
