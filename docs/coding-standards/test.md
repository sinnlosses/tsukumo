# コーディング規約: テスト

ステータス: **正典**。入口は `docs/coding-standards.md`（規約の理由と例外の入口と、子のファイルの一覧）。

責務: テストの置き場所とモック、カバレッジ、消す/足すの判断、流れ・出し分け・見た目の守り分け、E2E の差分をレビューするとき見ることの理由と例外を持つ。
読む時: テストを書く・消す・足す・レビューするとき。
直す時: テストの規約・守り分けの線・レビューで見ることを変えたとき（方法と E2E の足場は `docs/architecture/testing.md`）。

## テスト

### 置き場所とモック

- 実装コードの前に失敗するテストを書く（`/tdd` スキル参照）
- テストは `test/` 以下に、テスト対象と同じディレクトリ構成で置く
  （`src/<相対パス>.ts` → `test/<相対パス>.test.ts`）。**E2E だけは `test/e2e/<シナリオ>.test.ts`**
  （1つのファイルの振る舞いではないため。形は `docs/architecture/testing.md`「E2E の走らせ方」）。
  同名の対象が別の場所にあるのに鏡の場所に無いテストは、`test/architecture/test-location.test.ts` の
  許す一覧（既存の違反）を除いて落とす。一覧に無いずれが増えたとき、一覧の項目が直ったときに落ちる
- テストランナーは Vitest。`describe` / `it` / `expect` は `vitest` から import する
- **モックするのはシステム境界だけ**: ファイルシステム、時刻、端末の能力判定（画像プロトコルが
  使えるか）。Vitest の `vi.fn` / `vi.spyOn` を使う。自分たちのモジュール同士はモックしない
  （`/tdd` の `mocking.md` が正典）
- **単体の `node` project は `isolate: false` なので、同じ worker で先に走ったテストが読んだモジュールがキャッシュに残る**。
  そのためファイルの頭の `vi.mock` による差し替えが効かないことがあり（または別のテストの差し替えが残り）、
  呼び出し回数の数えが実行順で通ったり落ちたりする。`node:fs` などを差し替えるテストは、
  `vi.resetModules()` のあとに `vi.doMock` で差し替え、動的 `import` で読み込み直す。後始末は `vi.doUnmock` と
  `vi.resetModules()`（見本は `test/server/adapter/lib/jsonl.test.ts` の `loadCountingAppender`）。
  ファイル全体を隔離するなら `vitest.config.ts` の `ISOLATED_FILES` に挙げる
- **単体テストのプロセスのタイムゾーンは UTC に固定してある**（単体テストの設定の `test.env.TZ`。
  ホストが JST でも `Temporal.Now.timeZoneId()` は `"UTC"` を返す）。日付の境目を見るテストは、
  オフセットを `+09:00` のように固定せず、`Temporal.Now.timeZoneId()` を基準に時刻を組む。
  固定すると単体テストが見る日の境界とずれ、境界に近い時刻の課題・イベントが意図と違う日に
  数えられる（`test/server/achievement/adapter/closed-issue.test.ts` の `isoDateAt`）
- 非公開関数は、`export` された関数の振る舞いを通して検証する。テストのためだけに `export`
  しない（上の「関数の並び順」節と同じ規約）
- **語彙（表情など全域を列挙する定数）の長さに依存する期待値は、その定数から導く**
  （`EXPRESSIONS.length` のように）。個数を直書きすると、列挙が1つ伸びたときに `tsc` の型検査
  では検知できず、単体テストを走らせて初めて落ちる。「typecheck が通った」を作業の完了の合図に
  しないための書き方
- **CLI やサーバを起こすテストは、マシンの負荷が高いと時間切れで落ちることがある**（1件に
  457秒かかったことがある）。`pnpm run check` は他の重い処理と同時に走らせず、時間切れで落ちたら
  まず打ち直して、同じテストが続けて落ちるかを見る
- **テストの中で子プロセスを同期で待たない**（`execFileSync` / `execSync` / `spawnSync`。
  `.oxlintrc.json` が `test/` で止める）。`test/fixture/subprocess.ts` の `runSubprocess` /
  `runSubprocessOrThrow` を使う。同期で待つと、詰まったときにテストの時間切れが効かず、
  1件の詰まりが `pnpm run check` 全体を止めうる。非同期で待てば、詰まってもその1件が
  時間切れで落ちて次へ進む

### カバレッジに閾値を設けない

カバレッジは**穴の在り処を見る道具としてだけ**使い、達成すべき数値は決めない。閾値を置くと
「数字を満たすためのテスト」が増え、それは下で消そうとしている冗長テストと同じものになるため。

### 消すかどうか

| 観点                                                                                                                                                                 | 扱い                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 同じ入力分岐を別のテストが既に通している                                                                                                                             | 消す候補                                                                                                                                  |
| 型が既に保証している性質を実行時に確認している。`@ts-expect-error` だけで実行時の値に意味の無い it、`satisfies` で網羅が保証される一覧を実行時に確かめる it が当たる | 消す候補。型の検査は src 側の `satisfies` に置く                                                                                          |
| 実装の内部構造をなぞるだけで、外から見た入出力を固定していない                                                                                                       | 消す候補                                                                                                                                  |
| 契約ではないプロンプトの文面（モデルに渡す地の文）を `toContain` で語句ごとに写している                                                                              | 消す。文面の並びは append 全体の完全一致1本に任せる。回帰の注記があるもの・名乗った要素が層をまたいで届くかの突き合わせ・字数の上限は残す |
| 見た目の class 名の対応表、受け取った `className` を素通しするだけの部品の写し                                                                                       | 消す。見た目は目視の担当（「流れは E2E、出し分けは単体、見た目は目視」節）                                                                |
| 持ち主の層と同じ入力分岐を、呼ぶ側の層（例: 判定を渡すだけの配線の層）で同じ場面としてくり返している                                                                 | 持ち主の層だけ残し、呼ぶ側は配線を1本だけ見る                                                                                             |
| 本番（src・scripts）に呼び手のいない export とそのテスト                                                                                                             | 関数ごと消す。持ち主が別の関数なら、テストを持ち主へ移す                                                                                  |
| 同じモックの準備が複数ファイルに重複している                                                                                                                         | テストは消さず、準備を共通のフィクスチャに寄せる                                                                                          |
| 出力の書式を固定している（吹き出しの折り返し・枠線の組み立てなど）                                                                                                   | 残す。書式は他に守る手段が無い                                                                                                            |
| 過去のバグの再発防止として書かれた回帰テスト                                                                                                                         | 残す                                                                                                                                      |
| そのテストを外してもカバレッジの到達行・分岐が減らない                                                                                                               | **それだけでは消す理由にしない**（積極的な理由が要る）                                                                                    |

消したときは、**その振る舞いを上位で守っているテストがどれか**を書き残す。「カバレッジが
減らないから消した」だけの記録は、次に同じ調査をする人の役に立たない。

**E2E が通していることは、単体を消す理由にしない**: 出し分けと DOM の細部は部品・フックの単体が
持ち、E2E の場面で組み直さない（範囲は `docs/architecture/testing.md`「E2E に任せず単体テストに
残すもの」）。消す根拠にできるのは、上の表の同じ入力分岐・型の保証・内部構造のなぞりだけ。

### 足すかどうか

未到達の行を全部は埋めない。埋めるのは次の2つに当たるものだけ。

- エラー方針の分岐（起動時の即時終了か、その回だけ諦めるか、フォールバックか）
- `docs/requirements.md` が明示している振る舞い（フォールバック、未知の `type` を無視する、
  状態ファイルが無いときの既定の表情など）

到達不能な防御的コードと、エラーメッセージの文面だけが変わる分岐は埋めない。
**埋めないと決めた穴は、理由を添えてこの節に書き残す**（次にカバレッジを見た人が同じ調査を
繰り返さずに済むように）。

**埋めないと決めた穴（2026-09-20 の棚卸し。`docs/research/test-coverage.md`「埋めないと決めた穴」
節に、この時点のファイルと行番号の内訳がある）:**

- **外の世界の境界**（原則3。1ファイル = 1つの境界）: 到達させるには本物の外部
  （Agent SDK・WebSocket・orca・`fs.watch`・ブラウザの入口）を実際に動かすことになり、
  境界を偽装したら確かめているのは偽物のほうになる。例: SDK を起こす駆動、WebSocket
  クライアントの再接続、ホスト（orca）への操作、開発時だけの UI 再構築、`main.tsx` の
  DOM への1回きりの配線
- **ホームやパスを組み立てるだけの関数**: テストが常に置き場所を注入しているとき、残った
  既定の1行を通しても `join(homedir(), ...)` という実装をなぞるだけになる
  （上の「消すかどうか」表の「実装の内部構造をなぞるだけ」と同じ判断）
- **描画**（「流れは E2E、出し分けは単体、見た目は目視」節）: ライブラリの初期化・テーマ設定、
  `window.location.reload()`、複数の部品を並べるだけの組み立てなど
- **到達不能な防御的コード**: コード自身に「配線の誤りのときだけ」等の断り書きがある分岐、
  同梱物が読めない（`pnpm install` 済みが起動時の前提）、`listen` 後のアドレスが想定の形でない、
  `localStorage` が**例外を投げる**側（値が無い・読めない側は「足すかどうか」の対象。
  書き込みの失敗はプライベートウィンドウ限定）
- **同じ方針を別の入口で既に守っている分岐**: 同じガードを別の経路（鍵盤とマウス、複数ある
  仕切りのうち別の1本など）で既に通しているとき、二重に固定しない
- **要件に無い振る舞い**: `docs/architecture.md` やコードのコメントにはあっても
  `docs/requirements.md` に無い取り決めは、足すなら先に要件側へ書くのが順序
- **自分たちのモジュールをモックしないと届かない分岐**: 「モックするのはシステム境界だけ」
  （「置き場所とモック」節）に反するので、畳み込み自体を直に使うテストで守る

### 流れは E2E、出し分けは単体、見た目は目視

画面は3つに分けて守る。

| 守るもの                                                                                                               | 手段                                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 受け取る・決める（イベントの畳み込み、何をどう出すか）と、出し分け・DOM の細部（どの場合に何が出て、押すと何を送るか） | 単体テスト（`shared` と部品・フック）                                                                                                      |
| **利用者に見える流れ**を1本ずつと、**実ブラウザでしか確かめられないもの**（寸法・入力・サーバとの往復）                | **E2E**（fake driver で起こし、DOM の構造と WebSocket の流れを期待値と比べる。2本目を置く条件は `docs/architecture/testing.md`「テスト」） |
| **見た目**（色・崩れ・間合い・書体）                                                                                   | **目視**（`docs/architecture/testing.md`「手で確かめること」。E2E のスクリーンショットは添え物）                                           |

E2E が見るのは `data-*`・`aria-*`・文字と要素の入れ子までで、`class` と `style` は見ない
（形は `docs/architecture/testing.md`「E2E の成果物と再現」）。**画面の状態を E2E で確かめたいのに
`class` にしか出ていないなら、`data-*` か `aria-*` に出す**——見た目の直しで E2E が割れず、
状態の意味が変わったときだけ割れるようにするため。

この線引きがあるので、原則2の層の分離は**テスト可能性の要請**でもある。決める部分に
ブラウザ依存の処理が混ざると、単体テストで守れる範囲がそのぶん減る。

### E2E の差分をレビューするとき

条とその理由は `docs/architecture/testing.md`「E2E の揺れを生まない書き方」が正典。`/code-review` の
Standards 軸はこの節から入るので、レビューで見ることをここに置く。

- 待ち方を直した・足した差分で、**操作が場面のタイマーで届く手の途切れた区切りで行われて
  いるか**（`open` の直後か、疑似セッションに作った区切りの手まで待ったあとか）
- 新しく撮る場面の差分で、**「撮る前に、非同期の取得が済んだことを DOM の印で待つ」**に
  なっているか
- 期待値を撮り直した差分は、`git diff test/e2e/expected/` を開いて**途中の状態が入って
  いないか**を見る
- 揺れの報告には、**打ち直す前に控えた it の名前と成果物**が添えられているか
- シナリオを足した・待ち方を直した差分には、**続けて回して確かめた回数**が `## 結果` に
  書かれているか
- 待ちを足した差分が、**時間ではなく条件を待っているか**（`page.waitForTimeout`・`setTimeout` で
  待っていないか。例外は `settledDom` の読み直しの間隔だけ）
- `vitest.e2e.config.ts` や `it` に **`retry` が足されていないか**
- 足場や新しいシナリオが、**固定のパス・固定のポート・リポジトリの中のファイル**を使っていないか
