# コーディング規約: コメント（指し方と書き方）・タスク番号

ステータス: **正典**。入口は `docs/coding-standards.md`（規約の理由と例外の入口と、子のファイルの一覧）。

責務: コメントの後半。同じ前提を経路上に書き写さない基準、別の場所を指すときの指し方、書き方の3つ、正典の対応表を持つ（前半は `docs/coding-standards/comment.md`）。加えて、タスク番号を書かない理由と例外を持つ。
読む時: コメントから別の場所を指すとき、コメントの書き方を確かめるとき、タスク番号を書いてよいかを確かめるとき。
直す時: 指し方・書き方・それを検査する規則を変えたとき、タスク番号の例外を変えたとき。

## コメント

**同じ制約・前提を、呼び出しの経路上の複数の関数に書き写さない。** それを決めている関数
（絞り込むならその絞り込みをしている関数）に1回だけ書く。経路上の他の関数には書かず、そこで素直に
書き直すと壊れるときだけ、決めている関数をシンボルの名前で指す。書き写すと、仕様が変わったときに
直す場所が増え、直し忘れが起きる。

**別の場所を指すときは、名前・置き場所が変わっても書き直さずに済むもので指す。**
コードの修正・ファイル名の変更・移設のたびに、関係の薄いコメントを直して回らないための規則。
指すかどうかは上の表で先に決める。ここで決めるのは、残すと決めたコメントの中での指し方だけ。

| 指す先                                                                                  | 指し方                                                                                                                                                     |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| このリポジトリのコード（関数・型・定数・部品）                                          | シンボルの名前。JSDoc（`/** */`）の中で、そのファイルから見えるシンボルは `{@link 名前}`。それ以外はバッククォートで囲んだ名前。ファイル名・パスは書かない |
| 機能・置き場所のまとまり                                                                | 機能の名前（`docs/glossary.md` の語）。ディレクトリのパスは書かない                                                                                        |
| 正典の節                                                                                | `docs/<ファイル>.md「句」`。節番号（`4.2`・`7章`・`原則2`）は書かない。番号だけで指す形（`（13.9）`）も書かない                                            |
| シンボルを持たないもの（外部パッケージの型定義・設定ファイル・CSS・素材・打つコマンド） | ファイル名・コマンドをそのまま書く。扱うデータの形を示す例のパスは、名前を `foo` / `bar` / `baz` にする                                                    |
| このファイルを呼ぶ側・使う側                                                            | 書かない。呼ぶ側に求める条件は「何が満たされているか」で書く。制約の理由が特定の使い手にあるときだけ、理由としてその名前を1つ書く                          |

- ファイル名・パスは移設と改名のたびに古くなり、古くなっても何も落ちない（実在しないファイル名が
  コメントに残っていたことがある）。シンボルの名前は移設では変わらず、`{@link}` は改名にも追随する
- `{@link}` をエディタが解決するのは JSDoc の中だけ。`//` の中に書くと、追随するように見えて追随しない
- 自分のファイルは名前で呼ばず「ここ」「このファイル」と書く
- 節番号は節を足すと繰り上がる。節の参照の検査（`test/scripts/document/section-reference-repository.test.ts`）は句しか照らさない
  ので、番号は黙って古くなる。句は検査が守るので、節を改名したときに直す箇所は
  `node scripts/document/find-stray-reference.ts` が一覧で出す
- 節への参照を置くのは、上の表の「規約の例外」と、残すと決めたコメント（制約・外部との対応）の理由が長くて正典にあり、
  それを読まないと直してよいかを決められないときだけ。コメントは制約そのものを自分の言葉で書き、
  参照は理由の置き場として添える。参照だけで制約を言っていないコメントは書かない。
  規約・方針への参照、関連を示すだけの参照、用語の出典は置かない
- 呼ぶ側・使う側の一覧は、使い手が増減するたびに古くなる。今の使い手はエディタの参照検索が
  常に正しく出す。この一覧を持つ正典も作らない（置き場所の設計は `docs/architecture.md` が持つ）

```ts
// 避ける: パスで指し、節を番号で指し、使い手を並べ、行コメントに {@link} を書いている
// 環境変数の解釈は src/server/core/config.ts（docs/architecture.md「起動」）。
// `scripts/capture/open-room-grid.ts` と {@link startSession} が使う。

// こうする
/** 環境変数の解釈は {@link readConfig} だけが持つ。ここで `process.env` を読まない。 */
```

`src` `test` `scripts` のコメントのうち、ソースファイル名（`.ts` / `.tsx`。型定義・コマンド・「」の中・
`foo` などの例は除く）・節番号つきの参照・`//` の中の `{@link}` の3つは、`test/architecture/comment.test.ts`「コメント中の指し方」
が機械で検査する（`pnpm run check` から走る）。移行待ちの一覧は無く、違反は1件でも落ちる。
次の3つは検査しない。

- ディレクトリのパス。置き場所そのものを検査するテストのように、パスが検査の中身である箇所と見分けられない
- 呼ぶ側・使う側への言及。日本語の述語（「〜が呼ぶ」）で拾うと誤検知が多すぎる。
  ただし括弧の中にバッククォートの名前の並びと「が呼ぶ」「が使う」だけを置く形（``（`Foo` が使う）``）は、
  `test/architecture/comment.test.ts`「コメント中の呼ぶ側」が機械で検査する（`pnpm run check` から走る）。
  「から読む」のような述語は、外部の素材の読み元や、制約の理由として名前を1つ挙げる行にも当たるので入れない
- 番号だけの節の参照と、`{@link}` が解決できるか。前者は `0.66` や `WCAG 2.1` のような数値と
  見分けられず、後者は `tsc` が検査せず、見るには型検査器を別に起こすことになる

**書き方は3つ守る。**

- **Markdown の記法を使わない。** 強調の `**…**`・見出しの `#`・表はコメントに書かない。
  コメントはエディタで生の文字として読まれるので、記法は飾りにならず読む邪魔になる。
  コードの名前を囲むバッククォートと、JSDoc の `{@link}` は使ってよい
- **意味の切れ目で行を改める。** 1行に置くのは1文か、意味のまとまり1つ。
  決まった幅で折り返して文の途中で行を割らない。「——」で文をつながず、文を分けて次の行へ送る
- **複数行の JSDoc は `/**` だけの行で書き出す。** 1行に収まるなら `/** … */`。
  `/** 本文` から次の行へ続く形は、書き出しの行だけ本文の位置がずれて読みにくい

強調の `**` は、`src` `test` `scripts` について `test/architecture/comment.test.ts`「コメント中の強調」が機械で検査する（`pnpm run check` から走る）。
JSDoc の書き出しは、同じ範囲を `test/architecture/comment.test.ts`「複数行の JSDoc の書き出し」が機械で検査する。
既存のコメントの改行は、そのファイルを触るときに直す（機械では検査できないため）。

```ts
// 避ける: 強調の記法を使い、決まった幅で折り返して文の途中で行を割っている
// 保存済みの画面の色を `documentElement` へ反映する1回。**最初の描画より前に差す**必要が
// あるので、色を持つ部品（帯の歯車。13.9）の初期化には任せない——任せると、保存した色が
// 一瞬だけ既定で描かれてから入れ替わる。

// こうする
// 保存済みの画面の色を `documentElement` へ反映する1回。
// 最初の描画より前に差す必要があるので、色を持つ部品（帯の歯車）の初期化には任せない。
// 任せると、保存した色が一瞬だけ既定で描かれてから入れ替わる。
```

正典の対応:

| 書きたいこと   | 置き場所               |
| -------------- | ---------------------- |
| 設計判断・経緯 | `docs/architecture.md` |
| ドメイン用語   | `docs/glossary.md`     |
| 要件           | `docs/requirements.md` |

経緯をコードから消すときは、**先に正典の該当箇所を確認する**。既に書かれていれば消すだけ、
無ければ正典に書いてから消す。

レビューでは各段落に、冒頭の1問（消したときに壊す・誤って使う場面を挙げられるか）を問う。
挙げられない段落は消し、昔の話なら正典へ移す。この判定は機械化しない（不都合があるかは語で決まらず、
日本語の過去形も外部挙動の記録に使われるので、語での検出は誤検知が多すぎる）。

## タスク番号を書かない

コード・ドキュメントにタスク番号（Beads のタスクの `GH-<n>`（GitHub の Issue 番号）と、それより前の
`T-` + 3桁の連番）を書かない。
変更の経緯は Beads のタスクと `docs/history/` 側に持たせ、コードやドキュメントには
「現在どうなっているか」と「なぜそうなっているか」だけを書く。

タスク番号はアーカイブされると意味を失う一方、コード側の記述は残り続けるため、参照先が消えた
死んだ識別子になる。この規約は `scripts/document/task-mention.ts` が `.tw/` / `docs/history/` 以外で
0件になることを機械的に確かめる。

**例外は `docs/requirements.md`「7. 未決事項」の対応タスク列だけ。** 未決事項は「どのタスクで
決まるのか」が分からないと宙に浮くため、ここだけIDを許す（決まった時点で本文へ移り、IDごと
消える）。上の検査は `.tw/` / `docs/history/` に加えて、この表だけを除外して読む。

**コミットメッセージは対象外**（上の確認はワーキングツリーしか見ない）。件名の先頭にIDを置く
運用は `~/.claude/skills/task-model/WORKFLOW.md`「コミットメッセージ」が正典。

## 正典に日付を書かない

`docs/`（`docs/architecture/adr/`・`docs/history/`・`docs/research/` を除く）の本文に `20\d\d-\d\d-\d\d` の日付を書かない。経緯は ADR へ置く。日付入りのファイル名と「…」で引いた節名は対象外。既存の該当は `test/scripts/document/date-mention.test.ts` が範囲ごとの行数で凍結し、増やすと落ちる。
