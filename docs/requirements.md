## 1. 概要・目的

**tsukumo は、キャラクターと一緒に楽しく仕事をするためのターミナル環境である。**

立ち絵・吹き出し・セリフと詳細の分離・詳細ビュー・画面レイアウトは、**すべてこの目的のための
手段**であって目的ではない。**機能を足すかどうかは「この目的に沿うか」で決める**（手段の側から
「立ち絵ツールだからこれも要る」と発想しない）。

目的は2つの成分に分かれ、**どちらか一方だけでは足りない**:

- **キャラクターと一緒にいる感じがすること。** 応答が無機質なテキストの塊ではなく、
  キャラクターのセリフとして届く
- **仕事が捗ること。** 楽しさのために効率を落とさない。技術的な詳細は、セリフとは別の場所に
  人間が読みやすい形で出す

### 合格シーン（v1）

**プロジェクトのディレクトリで `tsukumo` と打つと1つの画面が開く。そこで依頼を打つと、左下の
キャラが話し、左上にレポートが出て、キャラが質問したら画面上のボタンで答えられる。Claude Code
の TUI は一度も見ない**（2026-09-11 のユーザーの言葉）。

これが v1 の合格ラインである。**機能を足すかどうかは、このシーンに近づくかで決める。**

### 「ターミナル環境」とは何を指すか

**道具立てはターミナルが中心**である。作業の中心はターミナル（Orca）の中にあり、tsukumo は
そこで1コマンドで起動する。ただしこれは**すべてをターミナルの文字で描く**という意味ではない。
**入力も表示も HTML** で、**Orca 自身のブラウザタブ**に出す（4.2 / 4.7）。**Claude Code の TUI は
使わない**ので、利用者が見るのは tsukumo の画面だけになる（2026-09-11 の方針転換。3章）。

境界はここに引く: **Orca のウィンドウの中で完結し、外部ブラウザ（Chrome など）へ飛ばないこと。**
一体感が壊れるのは「ターミナルの文字でないこと」ではなく「別のアプリケーションへ視線と操作が
移ること」だと確認済み（`docs/history/direction.md` 2026-09-09「詳細ペインの実体」）。

**Orca は「ページを表示する箱」**であって、中身は箱を差し替えても動く Web アプリとして作る
（`docs/architecture.md`「箱（Orca のタブ）と中身（Web アプリ）を分ける」）。

### 実現の手段

**tsukumo が Claude Code を動かす。** Agent SDK（`@anthropic-ai/claude-agent-sdk`）で claude を
子プロセスとして起こし、会話・ツール実行・許可プロンプト・質問を構造化イベントで受け取って、
入力欄・レポート・吹き出し・ボタンを tsukumo が描く。**Claude Code の TUI は使わない。**
この形を採る理由は「3. 技術制約」、**2026-09-11 に TUI を使う形から転換した経緯**と採らなかった案は
`docs/architecture.md`「Claude Code の TUI を捨て、SDK で動かす」が正典。

名前は付喪神から。長く使った道具に魂が宿るように、ターミナルという道具に姿と声を与える。

## 2. スコープ

### 2.1 対象とすること

- **Agent SDK で Claude Code を動かす**（4.1）。セッションは tsukumo 1プロセスに1つで、
  起こし直したら前の続きから始める（4.8）
- 画面の入力欄から依頼を送り、実行中は中断する。`/` でスラッシュコマンドを補完する
- セリフを MCP ツール `speak(text, expression)` で受け取り、吹き出しに出す（4.2）
- **ターンの本文**をレポートとして HTML に整形し、メインビューに**リアルタイムで**出す
- 許可プロンプトとキャラクターからの質問を、右下の入力欄の上のボタンで答えられるようにする（4.7）
- 作業の進行（実行中のツールと、その依頼での手順）を画面の最上部の帯に、タスク一覧・
  セッション情報をサイドバーに出す
- メインビュー・キャラビュー・サイドバー・入力欄を1枚のページに組み立てる（4.7）
- `speak` の引数とツールの実行状況から表情を、モデルから衣装を切り替える（4.3）
- キャラクターの素材と、表情・衣装の対応を差し替え可能にする
- ページを「どの箱でも動く Web アプリ」として保ち、箱（いまは Orca のタブ）に依存する操作を
  1箇所に閉じる
- **どのプロジェクトのディレクトリでも `tsukumo` で起動でき、そのプロジェクト（cwd）を
  作業対象にする**（`claude` を打つのと同じ感覚。ユーザーの言葉「絶対条件」）

### 2.2 対象外とすること（スコープ外）

- **Claude Code 本体のTUIへの描画割り込み**。割り込む経路が無く（「3. 技術制約」）、
  そもそも**TUI を使わない**
- Claude Code 本体のフォーク・パッチ適用
- **端末（PTY）を自前で持つこと**（2026-09-11）。画面の中でシェルや TUI を動かすことはやらない。
  **設計上の余地も残さない**（2026-09-13。tsukumo 自身が Orca のタブの中にいて隣にターミナルが
  あるので、画面の中に端末を持つ用途が無いことを確認した。実験の経緯は
  `docs/architecture.md`「Claude Code の TUI を捨て、SDK で動かす」）
- **セッションを選ばせる画面**（2026-09-13）。復元は**常に自動で続きから**なので、起動のたびに
  どれを続けるかを選ばせる画面も、過去のセッションの一覧・切り替えも作らない（4.8）
- **ファイルの貼り付け**（2026-09-11。2026-09-21 に**画像だけを覆した**）。入力欄が
  ファイルの中身を受け取ることはしない — **`@` のファイル補完がパスを渡す道を既に持っている**
  （4.2 (5)）。パスのほうが素直に強く、大きさの上限が要らず、どんな種類でも通り、Claude Code が
  自分の `Read` で必要なだけ読む。**画像だけが例外**で、**クリップボードの画像にはパスが無い** —
  `@` で埋められない穴はそこ1つしかないので、貼り付けとドロップで受け取る（4.10）
- **箱を Orca 以外に用意すること。** いまの箱は Orca のブラウザタブで、開くのに
  `orca tab create --url` を使う。他の箱（VS Code・Electron・素のブラウザ）へ載せ替えるときは
  **ホストのポートの `showView` を差し替えるだけ**で済む形に保つが、**いま2つ目の実装は作らない**
  （`docs/architecture.md`「ホスト依存の操作は1つのポートにまとめる」）
- `orca` コマンドが無い環境では、**ビューを開くことを諦めて動作を続ける**（起動失敗にしない。
  URL は表示するので、手で開けば同じページが見える）
- **レポートの中身の要約・再構成。** 読みづらさの主因は見た目だと確認済みなので
  （`docs/history/direction.md` 2026-09-09 Q2）、整形は**見た目の範囲**に留める。
  中身を削る・並べ替える・言い換えることはしない
- **音声・口パク**（2026-09-13。2026-09-21 に**当面やらない**へ緩めた）。
  **いまの立ち絵は動くが話さない**。VOICEVOX の口パク同期は後回しで、MVP には含めない（4.2）
- 会話内容の外部送信・クラウドへの保存（「5. 実行環境・非機能要件」の会話内容の扱い）。
  **同じマシンのディスクに残すことはこれに当たらない** — 2026-09-21 に、雑談の会話だけを
  `~/.tsukumo/` の下へ残すと決めた（4.9「雑談の会話のアーカイブ」）。**外へ出さないことは
  変わらない。**
  **分離や整形のために会話を外部のモデルへ送ることも含めて対象外**（2026-09-21 補足:
  **いま動いている claude 自身に `/compact` で要約させるのはこれに当たらない** — 会話はもともと
  その文脈にあり、要約も同じプロセスの中で作られる。4.9「記憶の圧縮と忘却」）
- キャラクター素材そのものの同梱・配布。**素材は利用者が自分で用意する**。権利の扱いを
  このリポジトリに持ち込まないため。**`persona.md` に書く人格の記述もここに数える**
  （2026-09-14。画像でなくても、既存の作品のキャラクターを書けば同じ問題になる）
- **複数セッション・常駐（client–daemon）へ広げること**（2026-09-21 に未決から落とした）。
  1つの画面で相手にするセッションは1つ。`SessionManager` が `sessionId` を鍵に持つのは
  起こし直しの一瞬のためで、複数化の布石ではない（`docs/design.md` 8章）
- **Electron などのスタンドアロンのアプリに包むこと**（2026-09-21 に未決から落とした）。
  箱は Orca のタブのままにする。ただし**載せ替えられる形は保つ** — ホスト依存の操作は
  `showView` 1つに閉じてあり、包みたくなったらそこを差し替える（`docs/architecture.md`
  「ホスト依存の操作は1つのポートにまとめる」。候補は `docs/research/app-shell.md`）
- **statusline 側にも小さいマスコットを出すこと**（案B。2026-09-21 に節ごと落とした。
  経緯は `docs/history/decision.md`）
- Windows / Linux での動作保証。動けばよいが、確認するのは macOS のみ

### 2.3 想定利用者

個人利用（作者本人）。**macOS の Orca を第一級の環境とする**。

Orca は「ページを表示する箱」として第一級であり、VS Code 統合ターミナルは第一級ではない。
ただし**Orca に頼む仕事はページを箱の中に開くこと1つだけ**になったので、箱の差し替えは
現実的な選択肢として残っているが、**包むのは当面やらない**（2026-09-21 に 2.2 へ移した）。

## 3. 技術制約

**事実**: Claude Code のTUIは自分で全画面を描画する。ここから次が決まる。

- `claude | cowsay` のようにパイプを噛ませる方式は**不可**
- hook の stdout はエスケープされてテキスト扱いになるため、そこから ANSI エスケープや
  画像プロトコルを流し込む方式も**不可**
- **TUI の中にキャラクターを出す方法は無い**

**だから TUI を使わない。** Agent SDK（`@anthropic-ai/claude-agent-sdk`）で Claude Code を動かし、
会話・ツール実行・許可・質問を構造化イベントとして受け取る。描くべきものは全部こちらに届くので、
**割り込む必要がそもそも無くなる**（TUI をそのまま使っていた頃の形と、そこから転換した経緯は
`docs/architecture.md`「Claude Code の TUI を捨て、SDK で動かす」）。

**SDK で使えることは一次情報で確認済み**（2026-09-11、code.claude.com/docs の agent-sdk 各ページ）:
構造化イベント、`canUseTool`（許可と `AskUserQuestion` の両方が届く）、ストリーミング入力モードでの
追加入力と中断、スキルと `.claude/commands`、hook、MCP、Bun サポート。**スラッシュコマンドは
`/<name>` を入力文字列に書けば送れ**、使えるものは `system` の `init` イベントの `slash_commands` に
並ぶ（対話端末が要る `/theme` `/terminal-setup` などは使えない）。

**headless CLI（`claude -p --input-format stream-json`）は採らない。** 中断ができず、
`--permission-prompt-tool` が手元の版（v2.1.x）に無い。**採るなら SDK 一択**。

採用アーキテクチャと、採らなかった案（PTY で TUI を包む・headless CLI）は
`docs/architecture.md` が正典。

## 4. 機能要件

### 4.1 Claude Code の駆動

**Agent SDK の `query` を、ストリーミング入力モードで1つ動かす**
（`@anthropic-ai/claude-agent-sdk`）。**セッションは tsukumo 1プロセスにつき1つ**（起こし直した
ときは前の続きから始める。4.8）。入力欄から送られたテキストは同じ `query` への追加入力として流し込み、
実行中の中断も SDK の経路で行う。

受け取るイベントと、その行き先:

| イベント                   | 行き先                                                           |
| -------------------------- | ---------------------------------------------------------------- |
| `assistant` のテキスト     | **ターンの本文**。レポートとしてメインビューへ（4.2）            |
| `speak` ツールの呼び出し   | **セリフ**と**表情**。キャラビューの吹き出しへ（4.2 / 4.3）      |
| `tool_use` / `tool_result` | 作業の進行。帯の「いまの作業」へ（4.2）                          |
| `canUseTool`               | 許可プロンプトと、キャラクターからの質問。答え待ちにする（4.2）  |
| `system` の `init`         | 使えるスラッシュコマンド（`slash_commands`）・モデル・許可モード |

- **モデルと許可モードは SDK のオプションで渡す**（`/model` を入力文字列として送らない）。
  どちらも画面から切り替えられるようにする。**既定の許可モードは `auto`**（SDK の
  `permissionMode` に `auto` がある。2026-09-11 スパイクで実測。`default` にすると Bash の
  書き込みなどが `canUseTool` に届き、`ls` のような読み取り専用は Claude Code 側が自動で通す）
- **既定のモデルは Opus、既定の effort は high**（ユーザーの指示、2026-09-12）。`effort` は
  `query()` に渡すだけで、画面には出さない。**effort は外から観測できない**（`init` の
  システムメッセージに `effort` は無く、`setModel` はモデル名しか取らない。2026-09-12 実測）。
  そのため画面の切り替えで effort が保たれるかは分からない。**分からないことを前提に、
  effort を画面の要素にしない**
- **`thinking` は表示しない。** モデルの内部の思考なので、出すと事故になる
- **未知のイベント種別が来ても落ちないこと。** 種別は本体の更新で増える（旧方針で
  transcript の `type` が実際に増えたのを観測している）
- **出力スタイル（`~/.claude/output-styles/asuna.md`）は SDK でもそのまま効く**（2026-09-11
  スパイクで実測。`settingSources` 省略時に `init` の `output_style` が `"Asuna"` で、応答も規約
  どおりだった）。`init` はプロンプトを送るたびに届くので、「新しいセッション」の合図にしない
- **中断は SDK の `interrupt()` で効く。** 中断されたターンの `result` は `error_during_execution`
  で終わり、同じセッションに続けて入力を送れる（中断前の文脈を保っている）
- **SDK も transcript（JSONL）を書くが、tsukumo はそれを読まない**

### 4.2 表示

#### 出力の分離（セリフと詳細）

**1つのターンを「セリフ」と「詳細（レポート）」に分け、別々の領域に出す。** 同じ内容が2箇所に
出ると、キャラクターとのやり取りがノイズに埋もれる（`docs/history/direction.md` 2026-09-09）。

**セリフは MCP ツール `speak(text, expression)` で受け取る**（2026-09-11 決定）。

- tsukumo がプロセス内の MCP サーバとして `speak` を提供し、モデルが呼んだらその `text` を
  吹き出しに出す。`expression` はキャラクター定義にある表情名から選ぶ（4.3）
- **戻り値は `"ok"` だけ**にする。ツールの結果はモデルの文脈に戻るので、ここに情報を載せると
  tsukumo からモデルへの逆流路ができる。**例外は雑談の `recall` の1つだけ**で、あれが返すのは
  tsukumo の状態ではなく**その会話自身の過去**（4.9「古い雑談は索引を引いて思い出す」）。
  **2つ目を足すにはユーザーの決定が要る**
- **呼ぶ頻度・契機・セリフに入れる中身は tsukumo 側が持つ**（2026-09-16 決定。書く場所は
  `src/server/core/speech-cadence.ts` の `SPEECH_CADENCE_PROMPT`）。**目安は1ターンに5〜10回**で、
  ツールを走らせる前に1回、その結果で分かったことがあればもう1回。セリフの中身は
  **「いま何をしていて、そこでどう感じているか」**が分かるものにする（ユーザーへの問いかけを
  増やすのではない）。**どのパックでも吹き出しが長く止まらない**ことは tsukumo 全体の体験なので、
  パックの `persona.md` には書かない（パックが決めるのは口調・言い回しだけ）。それまでは
  各 `persona.md` の「`speak` の呼び方」だけが規約で、**回数の目安が無く1ターン3〜5回に
  落ち着いていた**。tsukumo は呼ばれたら出すだけで、判定に推測が要らない
- **サブエージェントへの委譲は背景で行い**（2026-09-16 決定）、進み具合をサブエージェントからの
  合図（`状況 | n/N | …` の1行）で受け取ってメインが `speak` で言い直す。フォアグラウンドの委譲は
  ツール呼び出しの中でメインを止め、吹き出しが数分単位で止まるため
- **ターンの本文（`assistant` のテキスト）はすべて詳細**として扱い、レポートにする

**行頭のマーカーの経路は撤去した**（2026-09-21 決定）。補助として残っていた（2026-09-11 に
格下げ）行頭でマーカーに完全一致する行を拾い、`speak` を呼んだターンでも本文にマーカー行が
あれば吹き出しへ回す経路を消した。撤去した根拠は、**同梱のどの `persona.md` もマーカーを
使えと書いていない**こと — セリフは `speak` で言う規約に一本化されていて、この経路は実際には
発火していなかった。

**出力スタイル側の規約（2026-09-12 改訂。正典は `~/.claude/output-styles/asuna.md`
「セリフと詳細の書き分け」）**: セリフは `speak` で言い、本文にセリフを書かない。`text` は1〜2文、
`expression` はツールの説明にある表情名から。呼ぶのは着手の一言・ステップごとに1〜2回・許可や質問を
出す直前・完了報告。本文の冒頭・締め・途中でユーザーに語りかける一文を書かない。

**分離を文章の規約で表す案は採らない**（経緯は `docs/architecture.md`「セリフはテキストの規約
ではなく、ツール呼び出しで受け取る」）。

**そのほかの決まりごと**:

- **セリフに入れるのは役割で決める**（掛け声・呼びかけ・リアクション・感想・完了報告）。
  レポートに入るのは事実・根拠・手順・コード・表・判断とその理由
- **文体は役割で分ける。** セリフはキャラクターの口調、**レポートの本文は中立の技術文**
  （2026-09-14 決定。**2026-09-10 の「レポート側も口調を落とさない」を覆している**）。
  規約を書く場所は `src/server/core/report-notation.ts` で、`persona.md` には書かない
  （下の「読む時間を減らすために足すのは、規約の側」）
- **tsukumo 側のヒューリスティック分類（コードブロックは詳細、地の文はセリフ等）は採らない。**
  判定が壊れやすい。**小さいモデルに分離・整形させる案も採らない**（コスト・遅延に加えて、
  会話内容を外部に送らない規約と衝突する）
- **セリフが1つも来なかったターンの扱い**: **新しいターンが始まった時点（`request`）で
  吹き出しを空にする**（プレースホルダー「（まだ発話がありません）」に切り替わる。送信した
  直後に前のターンの一言が残っていると、次のターンに移ったことが画面から分からないため。
  2026-09-16 決定。ユーザーの指摘「(まだ発話がありません)のように定型句でもかまわないから
  次のタスクに移ったことがわかるようにしてほしい」）。
  そのターンで最初の `speak` が呼ばれるまでは、このプレースホルダーが出続ける
- **`/clear` は例外で、吹き出しに加えて記録（`records`）も空にする**（2026-09-15 決定。
  ユーザーの報告「clear コマンドを実行するとレポートは消えるがキャラのセリフはリセットされない」）。
  普通の `request` は過去のターンを遡れるように記録を残すが、`/clear` は会話そのものを消す操作
  なので記録も落とす。**空にしても
  キャラクターは消えない**（起動直後と同じ「（まだ発話がありません）」の吹き出しが出て、
  立ち絵はそのまま）。残すのはキャラクター定義・セッション情報（モデル・許可モード）・
  答え待ちの列で、**消すのは吹き出しとメインビューが読む値だけ**。
  **合図は SDK の `conversation_reset` メッセージ**（2026-09-15 実測。`new_conversation_id` が
  付き、直後に新しい `session_id` の `system`/`init` が届く）。tsukumo は依頼の文面が
  `/clear` かどうかを見ない。**`/compact` では届かない**ので、要約では何もリセットされない
  （同じ実測で `system`/`status` と同じ `session_id` の `init` だけだった）
- **レポートの構造は出力スタイル側の規約で決める**（2026-09-12。正典は同ファイル「レポートの
  組み立て方」）。内容の種類ごとに使う構造（表・番号付き・箇条書き1段・mermaid・chart・
  コードブロック・`note` / `badge` / `cols` / `card` の HTML）を表で示し、冒頭は結論、1ターンの
  レポートは最後に1つ、とした。**図とグラフは同梱した mermaid / Chart.js で描く**（2026-09-10 の
  決定どおり。tsukumo 側で構造を推測・整形しない）。**引用 `> ` は Markdown のまま描ける**
  （2026-09-13、描く層を unified に置き換えた移行の段6で対応。以前はレンダラが描けず
  `<blockquote>` を HTML で書く迂回を規約に書いていたが、その迂回は不要になった）
- **利用者への「お願い」だけは本文に置く**（2026-09-16 決定。ユーザーの指摘「レポートの中で
  判断を求められても、地の文に紛れて見落とす」）。利用者にしか決められない・できないことが
  実際にあるときだけ、**レポートのいちばん最後**に `<div class="note note-favor">` の塊を1つ置き、
  `speak` では「お願いがある」ことだけを言う（中身は本文が正典）。**無いターンでは置かない**。
  「語りかけはセリフ」の原則に開ける穴はここだけで、雑談・感想・完了の報告・「次はどうする？」の
  誘いは今までどおりセリフ（呼び名は `docs/glossary.md`「お願い」）

#### レポートの記法は、TUI と tsukumo で出し分ける

**出力スタイル（`~/.claude/output-styles/asuna.md`）は `~/.claude/settings.json` の
`outputStyle` で全プロジェクトに同じものが当たる**ため、そこに HTML の記法を書くと、tsukumo 以外の
素の TUI でもタグが文字のまま見える（2026-09-12 のユーザーの報告）。逆に「引用 `> `・ネストした
リスト・水平線 `---` は描けない」という制約は tsukumo のレンダラの都合で、TUI では成り立たない
（**2026-09-13、移行の段6で tsukumo 側もこれらを描けるようになり、この制約自体が無くなった**。
下の決定自体は HTML の記法の出し分けとして変わらず残る）。

**tsukumo が `systemPrompt` の append で差分を足す形にする**（2026-09-12 決定）。

- グローバルの `asuna.md` は **TUI 向け**に保つ。人格・`speak` の分岐・セリフと詳細の書き分けは
  残し、**HTML の記法（`note` / `badge` / `cols` / `card` / `details` / `blockquote` / `hr`）と
  mermaid / chart のフェンスを外す**。代わりに、レンダラの都合で禁じていた引用 `> `・ネストした
  リスト・水平線 `---` の禁止を**解く**
- **レポートの文体は tsukumo が決める**（2026-09-14 決定）。**本文は中立の技術文**にし、
  キャラクターの口調を担うのは `speak` のセリフのほうにする。どのパックに切り替えても
  本文の読みやすさが変わらないようにするため（**長く読み続ける面**なので、読みやすさを
  キャラクター性より優先する）。書く場所は `src/server/core/report-notation.ts` で、
  **`persona.md` の側には書かない**
- **レポートは必ず日本語で書かせる**（2026-09-23 決定）。`CLAUDE.md` の「対話は日本語」だけでは
  本文が英語で出たことがあるため、同じ `report-notation.ts` の文面で縛り、送る前の検算にも入れる。
  英語のまま残してよいのは識別子・パス・コマンド・コード・エラー文・原文の引用だけ
- **HTML・mermaid・chart の規約は tsukumo が持つ。** `query()` の
  `systemPrompt: { type: "preset", preset: "claude_code", append }` で足す。正典がリポジトリ内に
  来るので、**描ける記法の一覧が `src/browser/features/main-view/markdown/sanitize-schema.ts` と同じコミットで動く**
  （レンダラを直したのに規約が古いまま、が起きない）
- **`~/.claude/settings.json` には触らない**（`outputStyle` も、orca が専有する hooks /
  statusLine も無傷のまま）。書き換えるのは `asuna.md` 1ファイルだけ

**この2つの案は採らない**（理由は `docs/history/decision.md`「requirements.md 4.2 表示 /
レポートの記法は、TUI と tsukumo で出し分ける」）: 出力スタイルを2ファイルに分けて選ぶ案と、
1ファイルのまま条件分岐で書く案。

**文面は `src/server/core/report-notation.ts` の `REPORT_NOTATION_PROMPT` にあり、
`startSession`（`src/server/adapter/sdk-driver.ts`）が `query()` の `systemPrompt` へ渡す。**

#### 読む時間を減らすために足すのは、規約の側（2026-09-13 決定）

**読む時間を減らすために直すのは、3層（レンダラ / 通す HTML と CSS / 組み立ての規約）のうち
規約の側。** 表現の語彙はすでに足りていて、足りないのは「どの内容をどう描くか」の指示のほう
（ユーザーの言葉: 「多少の問題はあれどそれなりの表現力はすでにある」「重要なのは output styles の
ほうなのかもしれない」）。**書く場所は `src/server/core/report-notation.ts`** で、グローバルの
`~/.claude/output-styles/asuna.md` は TUI 向けのまま触らない。

- **見せ方と再構成の線引き**: **本文の文字列を変えないものが見せ方**（CSS・要素の付け替え・
  折りたたみ・列揃え）で、これは足してよい。**レンダラが本文から目次・要約・段組みを起こすのは
  再構成**（2.2 のスコープ外）なので採らない。**書き手（モデル）が最初からその構造で書くのは
  執筆であって再構成ではない**ので、規約で促してよい。この線引きは同じ議論が再燃したときの基準
- **足さないもの**: **画像 `img`**（会話の載るページに外部を読みに行く経路を作らない）/
  **レンダラによる自動の段組み・目次・先頭の要約の生成**（上の線引きで再構成の側）/
  **`.note` の種類を増やす**（ok / warn / ng の3つで区別がつく。増やすと選ぶ手が止まる）

**`class` の語彙を増やすときは、同じコミットで規約の文面・`sanitize-schema.ts` の許可リスト・
CSS の3つを揃える**（レンダラを直したのに規約が古いまま、が起きない）。**記法の表の行を削ることは
許可リストを同じコミットで削ることを意味する。**

**効くのは書く前だけ。** 規約は `systemPrompt` の append なので、**本文が書かれたあとに tsukumo が
削る経路は無い**うえ、**規約の変更が効くのは次にプロセスを起こしたときから**（定数なので、
動いているセッションには当たらない）。**量の上限は数で書かない**（行数や項目数で縛ると、長い調査の
報告まで同じ長さに押し込められる。ユーザーの選択）。

改訂の経緯（5回ぶん）は `docs/history/decision.md`「requirements.md 4.2 表示 / 読む時間を減らす
ために足すのは、規約の側」、短縮の案と実測は `docs/research/report-notation-shortening.md`。

#### 各表示物

**表示はすべて HTML である**（2026-09-09 決定。`docs/architecture.md`「表示はターミナル描画を
やめて、すべて HTML にした」）。ターミナルに文字と絵を描く経路は持たない。4つの領域は
**1枚のページ**として tsukumo のローカル HTTP サーバから配られ、**Orca 内のブラウザタブ**に出る
（4.7）。

- **立ち絵**: HTML の `<img>` で表示する。ドット絵ではなく本物の立ち絵を出せることを狙う。
  ターミナルの画像プロトコル（Sixel / iTerm inline images）は使わない
- **吹き出し**: `speak` で受け取った**セリフだけ**を、キャラビューの中に立ち絵と同居させて
  表示する。**セリフ1件につき吹き出し1つ**とし、今のターンの分を縦に積んで**最新を一番下**に
  見せる（並びは自前でスクロールする。2026-09-12 決定。DOM は新しい順で `column-reverse` を
  使うため、視覚上は最新が並びの一番下に来る）。**主役は立ち絵**で、**立ち絵は領域の
  左下・吹き出しの並びは右上**に置き、最新の吹き出しの左辺から立ち絵へ向けて尻尾を伸ばす
  （下の尻尾の段落）。
  **「どれが最新か」は位置と見た目の強弱の両方で示す**（最新だけ濃く大きく、過去は小さく薄く）。
  吹き出しの幅は中身なり。**ターンの
  本文は出さない**（本文はメインビューに回る）。**折り返し・全角文字の幅・禁則処理はブラウザに
  任せる**。**最新の吹き出しの下端の位置は固定し、過去のセリフが上へスライドする**形にする
  （2026-09-13 決定。**下端揃え＋固定の下余白**〔`--balloon-bottom-gap`〕で、並びの最大の高さも
  その余白ぶん差し引く。これで最新の Y 座標はセリフの件数によらず一定になり、入りきらない分だけ
  内側でスクロールする。立ち絵の高さは `--portrait-height` = 78%）。位置と幅が往復した経緯は
  `docs/history/decision.md`
- **吹き出しに出るのは `speak` で来たセリフだけ**（2026-09-17 決定）。**ツールを実行している
  間だけ「作業中の一言」を重ねる案は採らない**（表情の自動の上書きと一緒に撤去した。4.3）
- **尻尾の向き**: 立ち絵は左にいるので、**尻尾は吹き出しの左辺から真横（左）へ出し、先端を左に
  向ける**（2026-09-13 決定）
- **許可と質問**: **キャラが聞く**（2026-09-11 決定）。吹き出しに「これ実行していい？」と出て、
  その**下にボタン**を並べる。`AskUserQuestion` の選択肢も同じ見た目にする。押すと答えが
  `canUseTool` の戻り値として SDK へ返り、ボタンは消える。**許可モード**（毎回聞く／編集は
  自動／全部許す／プラン）も画面から切り替えられる。**質問には選択肢とは
  別に自由入力欄を常に1つ出す**（TUI の `AskUserQuestion` の "Other" 相当。モデルが選択肢に
  自由入力を含めてこなかったときの受け皿。2026-09-12 決定）。**質問が複数あるときは1問ずつ出す**
  （2026-09-15 決定。単一選択は選んだ瞬間に次へ進み、最後の1問を答えた時点でまとめて返す。
  送る前なら「戻る」で選び直せる）。**選択肢の説明はラベルと同じ行に置き、幅が足りなければ
  折り返して全文を出す**（2026-09-16 決定。折り返しても選択肢そのものは縦にも横にも広げず、
  箱に入りきらないぶんは `.question-card` の中だけでスクロールする）。**選択肢は送られた順では
  なく、ラベルの辞書順（`localeCompare`）に並べ替えて出す**（2026-09-21 決定。ユーザーの指摘
  「質問の並びがアルファベット順ではないときがある」。**自由入力（「その他」）だけは並べ替えに
  混ぜず末尾に固定する**。並べ替えはブラウザ側で行う（`/` コマンド補完と同じ立場）。質問そのものの
  並び（1問ずつ出す側）はこの並べ替えの対象外）。**選択肢に `preview`（Markdown）が付いていたら、選択肢ごとの比較をメインビューに出す**
  （2026-09-21 決定。ユーザーの指摘「各選択肢を図やメリデメなどをテーブルにしたものにすること
  ってできたりする?」——箱はラベルと一文しか置けず、文章だけでは比べられない。`AskUserQuestion` は
  選択肢ごとに `preview` を持てるのに、`src/shared/question.ts` が読み取りの時点で捨てていた）。
  **描くのはレポートと同じ経路**（表・mermaid・chart のフェンス・記法の class・同じサニタイズが
  そのまま効く）で、`preview` を持つ選択肢が1つも無ければ何も描かない（常設の枠にしない）。
  **箱は押す場所に徹し、触れた選択肢の札がメインビューで光る**（何問目・どの選択肢に目を置いて
  いるかは `src/browser/stores/question-focus.tsx` が両方へ配る。選ぶ操作を2箇所に分けると、
  複数選択と自由入力の扱いが両側に散る）。**答えた質問は、
  そのやり取りのメインビューに「何を聞いて、どう答えたか」の記録として残す**（2026-09-16 決定。
  答えが確定した時点で1回だけ積み、あとから書き換えない。答えずに終わった質問は残さない）。**複数選択は選んだぶんすべてに印が付き、

  悪くはならない。**中間レポートは1ターンに何件でも積む**（最後の1件に絞ると、構造を持つ本文でも

  積まれるので、ターンが長いほど画面が伸びる」）。**まだ追い越されていない最後の中間レポートは

  見返すときは最後のレポートがあるので、中間レポートは全部畳まれる。

  （中間レポートにもしない）。

  （帯のいまの作業へも回さない。落ちるのは実況だけ、という前提に立つ）。**規約の条項は残す**
  （素の TUI では tsukumo 側の判定が効かないため。二重になるが害は無い）。

  ターンが終わった瞬間に整形し直す。**ただしターンが進行中のあいだは、いちばん新しいターンの
  最後のステップの本文を、そのステップにツールが1つでも付くまで出さない**（2026-09-21 決定。
  往復した経緯と実測は `docs/history/decision.md`）。**確定するまで出さない理由**: 書きかけは
  最後のステップへ積まれるので、締めの本文はまだ伸びる途中かもしれず、出してから形が変わる。
  形の変わるものを出してから消すと前の中間レポートの畳み（`superseded`）が反転し、`<details>` が
  閉じてからまた開く。確定するまで出さなければ**一度出した本文は二度と消えない**。
  **次の本文が始まって「最後のステップ」でなくなっても、ツールの付いていない本文は出さない**
  （2026-09-22 追加。それまでは資料だけが漏れていた）。漏れると、締めの本文が実況で終わって
  資料が最終レポートへ繰り上がったとき、**本文の箱はすでに「中間レポート」として組み立て
  られている**ので、マウントした時点でしか始まらない書き上げる演出（4.3）が二度と掛からない
  （実測: 資料が中間レポートとして出た 2.2 秒後に締めへ変わり、筆は一度も走らなかった）。
  **代わりに、資料はツールが付くかターンが終わるまで出ない**（早く読み始められるぶんを演出と
  引き換えにした）。判定は `main-view.ts` の `selectShownReports`。
  **代わりに失うもの**: **進行中の本文はどれも流れて見えない**（資料はツールが始まった時点で
  中間レポートとして出て、締めの本文はターンが終わった時点で出る）。流れて見える感じは**書き上げる演出**（4.3）が受け持ち、演出は
  確定した本文の全体に掛かる。ツールが始まって出るほうは**同時に中間レポートと判定される**ので、
  **囲いは最初から破線**で、あとから反転しない。
  **1ターン＝1枚**で、過去は**直近5件**（`MAX_MAIN_VIEW_TURNS`）までタブで選ぶ。新しいターンが
  始まったら先頭へ戻すが、利用者が過去のタブを見ている間は動かさない。**タブの名前は
  依頼の1行目**（短く切り、切る前の1行と「3つ前」のような位置は `title` で読める）で、
  やり取りが進んでも前からあるタブの名前は変わらない。**外部ブラウザには
  出さない**（1章）

  合図は**行頭または空白の直後の `@`**で、そこからキャレットまでに空白が入ったら終わり
  （`@` は文中にも出るので、(3) の「先頭かつ空白なし」は使えない）。
  絞り方は (3) に合わせて**前方一致を先に、続けて部分一致**（各グループの中は辞書順、合計最大
  10件）で、**そこだけ大文字小文字を区別しない**（打った綴りのまま `README.md` に当てられる）。
  キー操作も (3) と同じで、確定すると**キャレットの直前の `@<打ちかけ>` が `@<リポジトリ相対パス> `
  に置き換わる**（前後に書いた文は触らない。すぐ後ろがすでに空白なら末尾の空白は足さない）。
  **(3) と (5) の候補は同時に出ない。**
  一覧は**サーバへの GET 1本**（`/repository-file`。起動トークンが要る）で1回取り、
  **絞り込みはブラウザ側**で行う（打鍵のたびに `git ls-files` を起こさない）。
  **入力履歴と繰り返しの仕組みは次**（v1 に含めない）。ファイルの貼り付けはしない（2.2）が、
  **画像は貼り付け・ドロップで受け取る**（4.10）
- **配り方**: HTML は**ファイルに書き出さず**、`127.0.0.1` にだけバインドしたローカルの HTTP
  サーバからメモリのまま配る。更新は Server-Sent Events でブラウザへ押し、入力・回答・中断は
  同じサーバへの POST で受ける（`docs/architecture.md`「HTML はローカルの HTTP サーバから
  配る」「ビューの更新は Server-Sent Events で押す」）。**会話の内容をディスクに書く経路を
  作らない**。**移行後（2026-09-13 決定）は、サーバはイベントと状態を WebSocket 1本で押し、
  ブラウザ側の部品が描く**（`docs/design.md` 4章。ページの URL に起動トークンが付く）
- **フォールバック**: 表示できないものがあっても**残りを表示して動作を続ける**。
  立ち絵の素材が無い環境では**セリフだけを表示する**、`orca` コマンドが無い環境では
  **タブを開かずに配信だけ続ける**。表示物が1つ欠けたことを理由に起動失敗にしない
- **VOICEVOX の口パク同期は後回しでよい**（MVP に含めない。2026-09-21 に、2.2 の
  「検討しない」より**こちらを正典にする**と決めた）。**タイプライター表示は既に別の形で
  入っている** — 本文を塊ごとに出す「書き上げる演出」（4.3）がそれに当たるので、同じ機能を
  もう一度提案しない

### 4.3 状態連動

- **表情差分**: **`speak` の `expression` 引数を主にする**（2026-09-11 決定）。キャラクター
  定義にある表情名から選ばせる
- **表情は9つ**（2026-09-22 決定。`bored` を足した。2026-09-21 に `sad` と `excited` を
  足したのに続く。2026-09-20 に `serious` と `curious` を足したのに続く）。**`default` が先頭**で、
  足すものは**末尾に積む**（既存の並びを動かさず、パック作者から見える順を変えないため）:

  | 識別子      | ラベル（`characters/tsukumo`） | 出す場面                                                                                                                               |
  | ----------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
  | `default`   | にっと                         | 下のどれにも当たらないとき。**表情の指定が無いときの落とし先**でもある                                                                 |
  | `thinking`  | ふむ                           | 調べる前・結果を突き合わせるとき・判断に迷うとき                                                                                       |
  | `proud`     | えへん                         | うまくいったとき・完了を報告するとき                                                                                                   |
  | `flustered` | あわわ                         | 外したとき・失敗したとき                                                                                                               |
  | `serious`   | きりっ                         | **危険な操作を確認するとき**（はしゃぐのをやめて止める）                                                                               |
  | `curious`   | きょとん                       | **予想外のものに出くわして目を丸くするとき**                                                                                           |
  | `sad`       | しょんぼり                     | **思ったように行かず凹むとき・断られたとき・自分の見立てが外れたと認めるとき**（`flustered` は外した瞬間、`sad` はそのあと凹んでいる） |
  | `excited`   | わくわく                       | **面白そうなものを見つけたとき・これから始めるとき**                                                                                   |
  | `bored`     | たいくつ                       | **長いテストやビルドを待っているあいだ**（眠っている顔ではない。つくもは眠らない）。**話しかけられているあいだは出さない**             |
  - `curious` は**質問を出すときに必ず出すものではない**（2026-09-20 のユーザーの判断:
    「きょとんとするかは質問の内容による」）。他の表情と同じく、**キャラクター自身が場面に
    合わせて `speak` の引数で選ぶ**
  - 語の系統が違う同梱パック（`characters/tsukumo-spirit` / `characters/local`。
    通常 / 思案 / どや顔 / あわあわ）のラベルは**真顔** / **きょとん**
  - **選択肢に出るのは、立ち絵かラベルのどちらかが定義にある表情**（`src/shared/expression-choice.ts` の
    `expressionChoices`。ここから `speak` の enum を作るのは `src/server/adapter/sdk-driver.ts` の
    `speakExpressionEnum`）。**`default` は定義に無くても必ず出る**（未知の表情の落とし先なので、
    これが無いと受け付けられる名前が1つも無くなる）
  - つまり**ラベルだけ足したパックでも、その表情を選べる**（立ち絵は `default` に落ちる。
    `characters/README.md`）。**絵が揃っていないパックでも壊れない**のはこのため。
    選択肢から外れるのは、立ち絵もラベルも定義に無い表情だけ
  - **`persona.md` にも 4.3 にも場面が書かれていないものは足さない**（見送った例は
    `docs/history/decision.md`）

- **表情の源は `speak` の1つだけ**（2026-09-17 決定）。**ツールを実行している間に自動で
  「作業中」へ上書きする経路は持たない**（同じ案をまた出さないための理由と実測は
  `docs/history/decision.md`「requirements.md 4.3 状態連動」）。**原則は「表情と吹き出しは
  リンクしていること」**で、自動の上書きはこの原則を壊す唯一の経路だった
- **モデル別の衣装**: `haiku` = 軽装 / `sonnet` = 通常装備 / `opus` = 戦闘配置 / `fable` = 戦闘配置
  （`opus` と同じ。2026-09-17 決定。衣装は「装備の重さ」の3段のままにし、`OUTFITS` を増やさない）。
  Asuna output style の「出撃時の掛け声」のモデル分岐と対応させる。モデルは**SDK に渡した値と
  `system` の `init` から分かる**ので、**hook の状態ファイルは要らなくなった**（2026-09-11）。値の形式
  （短い別名か解決済みの完全なモデルIDか）は場合によるので、衣装の判定は部分一致で行う
- 表情・衣装の対応は、キャラクター定義ファイルの形式が決まるまで `src/shared/expression.ts` に置く
  （決まったら定義ファイル側へ移す。**移行の段8で `character.json` の `expressions` へ移す**。
  `docs/design.md` 7章）
- **立ち絵は動くが話さない**（2026-09-13）。演出はブラウザ側の `Portrait` 部品の中に閉じる
  （`docs/design.md` 6.5）
- **立ち絵は「1枚の矩形」として扱う**（2026-09-13 決定）。tsukumo が動かすのは**位置・大きさ・
  傾き・上下・不透明度**だけで、**素材の中身（目・口・腕）には触らない**。理由は 2.2 の
  「素材は利用者が自分で用意する」で、**素材がどう作られているかを当てにできない**から
  （既定の `characters/tsukumo-spirit/` の SVG も `id="body"` しか持たず、目に名前が無い）。
  この割り切りにより、**SVG でも PNG でも GIF でも同じだけ動く**（パック作者に何も要求しない）
- **まばたきと表情のクロスフェードは作らない**（同上の帰結。素材の構造に依存するため）。
  表情は引き続き立ち絵そのものの差し替えで表す
- **`<Portrait>` が動ける範囲はキャラビューの領域の中だけ**（読書を妨げないため）。
  **ただし「レポートの上に被らせない」の線は、ミニ立ち絵に限って見直した**（2026-09-20 決定。
  それまでは例外なく禁じていた）。元の指示は「レポートを書くときに、キャラクターが書いている
  ようにカーソルに合わせてミニキャラになった立ち絵が動くと楽しいよねきっと」（2026-09-14）。
  **認めるのは、いま書かれている本文の筆先に添う1体だけ**で、次を条件にする:
  - **書き上げる様子は演出で作る。** レポートは確定するまで出ない（4.2 の
    `selectShownReports`）ので、**流れている本文に添える筆先はどこにも無い**——
    出た時点で本文は全部そろっている。演出は**出そろった本文を「書き上げていくように見せる」**
    ものとし、ミニ立ち絵はその筆先に添う（2026-09-21 に「中間レポートが流れている間だけ筆先が
    実在する」という書き方を直した。当時の実装では書きかけが資料と判定されると先に出ていたが、
    その本文は演出が始まったあとも伸び続けるので、**筆は伸びた分を追えていなかった**）
  - **文字を足していく実装にしない。** Markdown のソースを1文字ずつ増やして変換し直すと、表・
    mermaid・Chart.js が未完成のソースで作り直され、非同期に描く mermaid は途中の形で失敗する
    （塊ごとの `memo` も全部無効になる）。**DOM は完成品を一度に作り、見せる範囲だけを進める**。
    **文字を持たない図・グラフの塊は塊ごと出し**、ミニ立ち絵はその脇に立つ
  - **筆は1行ずつ追わず、塊1つをZ字で書く**（2026-09-20 の方針変更。それまでは `Range` で
    1文字ずつ位置を取り、行の途中で止めていた）。塊の行を上下2つの帯に割り、帯ごとに左から右へ
    なぞって、あいだを斜めに戻る——Z字の3画。**帯の切れ目は実際の行の box に合わせる**ので
    文字が上下に切れず、1行しかない塊は1画で書く
  - **なぞる右端は帯ごとに、その帯にある行のいちばん右**（2026-09-21 決定。それまでは塊を囲む
    枠＝いちばん広い要素の幅だった）。枠でなぞると、箇条書きのように短い行しかない帯では
    **横画の1〜3割しか文字の上を通らず**、残りは何も書かれていない地の上を滑って、筆先に付く
    ミニ立ち絵が本文の右の空白に立つ。
    **左端はどの帯も塊の左端で揃える**（行頭は揃っているので帯ごとに変えない）。
    **横画の時間は帯の幅で按分する**——右端が帯ごとに変わるのに時間を等分したままだと、
    筆の速さが同じ塊の中で 2.2倍まで変わる
  - **塊は「トピック」**（同日のユーザーの判断。**段落や表の1つ1つではない**）。見出しと
    水平線を境に、そこから次の境目までの要素をひとまとめにする。**帯は要素をまたいで1本に
    伸びる**ので、見出しと段落と表が同じ画で書かれ、図・グラフは筆が通り過ぎた割合が
    そのまま `opacity` になる。細かく割ると筆が何度も折り返して目で追えなくなる
  - **速さは塊ごとに決め、レポート全体には上限を掛けない**（2026-09-20 決定。それまでは
    「全体で1.5〜2秒を上限に出し切る」としていた）。**塊の大きさ（中の文字数の合計）で按分し、
    1つあたり 2.4〜8秒**——文字1つあたり 40ms で、下限 2400ms・上限 8000ms に収める
    （図・グラフは文字数を持たないので、段落1つぶん＝100文字に相当させる）。
    **下限が大きいのは、1回のZ字をゆっくり書くため**。2画を書き切るので、
    短い塊を文字数に素直に比例させると筆が飛んで見える。**塊の数で全体が伸びるのは受け入れる**
    （2026-09-20 のユーザーの判断）。
    **全体に予算を置いて按分する案は採らない** — 長いレポートほど1文字が
    速くなり、目で追えるという狙いがレポートの長さで崩れる（値を決めた実測は
    `docs/history/decision.md`）。読み始めが遅れるぶんは、クリック・キー入力の
    どちらかで**即座に全部出す**ことで引き受ける。**ホイールと指では打ち切らない**
    （2026-09-22 のユーザーの判断。先を読もうとして転がすのは「もう要らない」ではなく
    「見ていたい」の側で、打ち切ると筆を追うたびに筆が消える）。**過去のタブを見返すときは
    演出しない**（確定済みの本文は一度も「書かれない」）
  - **塊の中は出だしと締めをゆっくり、真ん中を速く**（2026-09-22 のユーザーの判断。3次の
    イーズインアウトで、真ん中の速さは等速の3倍。
    `src/browser/features/main-view/reveal-plan.ts` の `blockProgress`）。ミニ立ち絵が「そこで
    書いている」ように見えるのは筆が遅いところだけなので、**見せたい両端に時間を寄せて、読み手が
    待つだけの真ん中を速く抜ける**。**塊の持ち時間そのものは変えない**ので、レポート全体の
    長さは前と同じ
  - **書いているあいだは画面が筆先に付いていく**（2026-09-20 のユーザーの判断。
    `src/browser/features/main-view/brush-scroll.ts`）。**追うのは帯ぜんたいではなく
    ミニ立ち絵の立つ位置**（帯の下端から立ち絵の高さぶん上まで。2026-09-23。帯ぜんたいを
    器へ収めようとすると、行の多いトピックでは帯の背が器の見える高さに迫り、送っては戻す
    往復になる）。そこが器の上下の縁から 96px 以内に入ったら、その差だけ器を送る。
    **器がその範囲と上下の余白を両方とも収められないほど狭いときは、下端を優先する**。
    **器は根から上へたどって見つける**——転がる祖先は画面幅で入れ替わる（広い画面は
    `section[data-region="main"]`、狭い画面はページ自身）ため。
    **利用者が手で転がしたら、その演出のあいだ自動送りは降りる**（2026-09-22。ホイールと指は
    演出を打ち切らなくなったので、送り続けると読もうとした位置から引き戻してしまう。読む位置を
    選んだのは利用者のほうなので、筆が譲る）
  - **素材は「あれば使う」。** `character.json` に任意の `mini` を置き、**無いパックは
    `portraits.default` の縮小に落ちる**（4.4「あるものだけでよい」に例外を作らない）。
    ミニ用の画像はリポジトリに同梱しない（2.2）
  - **2体見えることは「分身」として受け入れる**（2026-09-20 のユーザーの判断）。キャラビューの
    立ち絵は消さず、ミニ立ち絵を明確に小さくして式神として見せる（**不透明**。2026-09-21 の
    ユーザーの判断で半透明から変えた）。**書いている間だけキャラビューを空ける案は採らない**
    （吹き出しの持ち主が居なくなる）
  - **書き上げたあとも消えず、本文の末尾に残る**（2026-09-21 のユーザーの判断。
    「ミニキャラは書き終わったあとにも消えずに残るようにしよう」）。残った立ち絵は**本文に
    貼り付いて一緒に転がる**（筆先の座標をビューポートではなく本文の入れ物の原点で持つ。
    画面に固定する案と、隅の定位置へ寄せる案は採らない）。**消えるのは次に書き始めたときだけ**
    で、過去のタブへ切り替えたときにも依頼を送った時点でも消さない。**演出を途中で飛ばしたとき
    も、筆が止まった場所ではなく同じ末尾に置く**——飛ばすと本文は全部出るので、途中に残ると
    まだ書いている途中に見える
  - `prefers-reduced-motion: reduce` では**演出ごと無効**にし、ミニ立ち絵も出さない
    （**演出が走らない場面で新たに出すことはしない**——過去のタブも同じ）
- **動くのは利用者の注意が空いているときだけ。** 判定の材料は `SessionState` に既にある
  （`turn` / `runningTools`）。作るのは次の4つ:
  **呼吸**（常時のごく小さい上下。「居る」の最小単位）/ **待っている間の移動**（ターン進行中に
  領域の中をゆっくり歩く）/ **完了の反応**（ターンが終わると小さく跳ねる。完了の合図も兼ねる）/
  **失敗でびくっ**（ツールが失敗すると一瞬のけぞる）。
  **長いアイドルのふるまい（座る・うとうと）は作らない**（席を外している時間で誰も見ていない）
- `prefers-reduced-motion: reduce` を尊重する（規則は `src/browser/styles/theme.css` にある）

### 4.4 キャラクター定義

素材（立ち絵の画像）と、表情・衣装の対応は**宣言的な定義ファイル**で差し替え可能にする。
ハードコードしない（`docs/architecture.md` 原則4）。

**置き場所**（`characters/README.md` が使い方の正典）:

| 場所                            | 中身                                                       |
| ------------------------------- | ---------------------------------------------------------- |
| `characters/tsukumo/`           | 既定のキャラクター。**このリポジトリのために自作**したもの |
| `characters/tsukumo-spirit/`    | もう1体。同じく**このリポジトリのために自作**したもの      |
| `characters/local/`             | 利用者が自分で用意した素材。**`.gitignore` 済み**          |
| `~/.tsukumo/characters/<name>/` | **画面から作ったパック**（2026-09-15 決定）                |

**画面から作ったパックはリポジトリの外（`~/.tsukumo/`）に書く**（2026-09-15 決定）。
探索先の優先順位・画像の受け取り方（data URL を WebSocket のコマンドに載せる）・大きさの上限は
`docs/design.md` 7.1 が正典。**cwd には依存させない**ので、どのプロジェクトから起こしても同じ
パックが選べる。**作る口も、立ち絵・差し色を変える口も、会話の画面とは別のキャラクター画面にある**
（2026-09-17 決定。4.7、`docs/design.md` 13.6）。

**このリポジトリは公開されている。** 権利のある画像（公式絵・ファンアート等）を
コミットしないため、利用者の素材は `characters/local/` に置く
（`docs/architecture.md`「キャラクター素材はリポジトリに同梱しない」）。

**定義ファイル**（`character.json`）は次を持つ:

- `portraits`: 表情（4.3 の8つ）→ 画像ファイル。
  **「あるものだけ」でよく、見つからない表情は `default` に落ちる。** 1枚から始められる
- `outfitAccents`: 衣装（`default` / `light` / `normal` / `heavy`）→ 差し色。
  表情×衣装の全組み合わせぶんの画像を要求しないための仕組み

**移行後（2026-09-13 決定）は「パック」になる**: `character.json` に `expressions`（表情名 → ラベル）と
`speechMarker` が加わり、同じディレクトリの `persona.md`（tsukumo 向けの人格）と素材を1単位として
読む。切り替えは別のパックでセッションを起こし直し、**そのパックのセッションの続きから始まる**
（`docs/design.md` 7章・4.8）。

**同梱するパックは自作のものだけ**（2026-09-14 決定）。素材（画像）と同じ理由で、
**`persona.md` に書く人格の記述も「素材」に数える**。既存の作品のキャラクターを演じさせたい
ときは、`characters/local/` に自分で置く（`.gitignore` 済み）。同梱するのは
`tsukumo`（`assets/logo.png` にいる狐の付喪神。このプロジェクトの顔）と `tsukumo-spirit`
（つくもの精霊）の2体で、どちらもこのリポジトリのために自作したもの。

**人格の二重適用は `applyFlagSettings({ outputStyle: "default" })` で避ける**（2026-09-14 に
スパイクで実測）。`~/.claude/settings.json` の `outputStyle` は全プロジェクトに効くので、
そのまま `persona.md` を足すと人格が2つ重なる。**セッションを起こしたあと
`applyFlagSettings({ outputStyle: "default" })` を呼ぶと `init` の `output_style` が `default` に
なり、グローバルの人格が消えて `persona.md` だけが残る**。**これはセッション限りの層にしか
触らず、設定ファイルを書き換えない**（実測は `docs/history/decision.md`）。
`settingSources` からユーザー設定を外す案は、**orca の hooks まで外れる**ので採らない。

**差し色が効くのはインラインで埋め込んだ SVG だけ**（実測）。`<img>` で読み込んだ画像は
独立した文書として扱われ、ページ側の CSS 変数が届かない。ラスタ画像（PNG / GIF）を使う場合、
衣装の出し分けは表情と同じくファイルを分けることになる。

### 4.6 起動と設定

- **プロジェクトのディレクトリで `tsukumo` と打つ**（開発中はリポジトリ直下の `bun run start`
  でも同じ）。tsukumo はローカルの HTTP サーバを立て、Agent SDK で Claude Code を起こし、
  ページのタブを箱（Orca）の中に開く。**利用者が並べる手間はゼロ**（1枚のページで完結する。4.7）
- **ビューを配るポートは既定 7327**（`TSUKUMO_VIEW_PORT` で変更可）。**既定のまま塞がっていたら**
  EADDRINUSE のあいだ +1 して20個先（7346）まで順に試し、空いた番号で待つ（複数のプロジェクトで
  同時に起こしても2つ目以降が起動できるように。2026-09-12 決定）。**`TSUKUMO_VIEW_PORT` を
  明示的に渡したとき（`0` を含む）はずらさず、そのポートで一度だけ試してそのまま失敗する**
  （指定したポートで待てないことに気づけなくなるため）。EADDRINUSE 以外の失敗（`EACCES` など）も
  ずらさない。20個全部塞がっていたら、試した範囲（7327〜7346）を伝えて終了コード1で終わる
  （黙って0番＝空きポート自動割り当てへは逃げない。どのポートで待っているか分からない状態を
  作らないため）。実際に待っているポートは起動時に stdout へ出る URL（`layoutUrl`）で分かる
- **グローバルへの導入は `bun link`**（2026-09-12 決定・実施）。リポジトリの直下で
  `bun link` を1回打つと `~/.bun/bin/tsukumo` ができ、どのディレクトリからでも打てるようになる。
  **実体はリポジトリの `bin/tsukumo` へのシンボリックリンク**なので、開発中の変更がそのまま
  次の起動に反映される。**消すときはリポジトリの直下で `bun unlink`**。
  リポジトリの外に置かれるのは `~/.bun/bin/tsukumo` と `~/.bun/install/global/`（bun が管理する
  登録簿）の2つだけで、**シェルの設定ファイルは書き換えない**（`~/.bun/bin` が `PATH` に
  入っていることが前提。入っていなければ利用者自身が追記する）
- **cwd に依存してよいのは起動先プロジェクトのもの**（作業ディレクトリ・`develop/tasks.json`・
  相対指定の素材）**だけ**で、**自分で持ち歩くもの（既定の立ち絵・`node_modules` の外部
  ライブラリ）は自分の場所から読む**（`tsukumo` 自身が置かれている場所からの相対。
  どのディレクトリで起こしても立ち絵が出る）
- **`orca` が無ければタブを開くのを諦め、URL を表示して動作を続ける**（起動失敗にしない）
- **`~/.claude/settings.json` に tsukumo のエントリを残さない。** 旧方針で足した hook は外す。
  ただし**このファイルの hooks と statusLine は orca（`~/.orca/agent-hooks/`）が専有している**
  ので、触るときは既存エントリを壊さないこと。上書きすると orca 側が黙って動かなくなる
- **入力は画面の入力欄から SDK へ直接渡す。** Orca 経由でターミナルへ文字やキーを送る経路は
  使わない（**Orca はエージェント端末への合成入力を弾く**。実測は `docs/architecture.md`
  「既知の制約・注意点」）

### 4.7 画面レイアウト

biim システムをリスペクトした4領域にする。**領域ごとに役割を1つだけ持たせ、同じ情報が
2箇所に出ないようにする**ことが狙い。

```
┌────────────────────────────────────────┬────────┐
│ メインビュー                            │サイドバー│
│  レポート（広い）                        │ （狭い） │  全部で1枚のHTML
├─────────────────────┬──────────────────┴────────┤  ＝ブラウザタブ1つ
│ キャラビュー（半分）   │ 入力欄（半分）              │
│  立ち絵＋セリフ        │  答え待ちの箱・複数行入力   │
│                        │  ・送信・中断／のコマンド補完│
└─────────────────────┴───────────────────────────┘
```

| 位置         | 中身                                    | 対応する biim の要素 |
| ------------ | --------------------------------------- | -------------------- |
| 左上（広い） | メインビュー。レポート                  | ゲーム画面           |
| 右上（狭い） | サイドバー。タスク一覧・セッション情報  | タイム表・チャート   |
| 左下（半分） | キャラビュー。立ち絵＋セリフ            | 立ち絵・テロップ     |
| 右下（半分） | 入力欄。答え待ちの箱（許可/質問）＋入力 | 実況者の手元         |

**許可と質問の答え待ちの箱は、右下の入力欄の上に出す**（答えるのは入力の動作なので、
入力欄の側に置く。2026-09-11 決定。以前はキャラビューの吹き出しの下に出していたが、「気づかない」
「入力欄と離れている」という理由で使いづらかった〔2026-09-11 の目視〕）。キャラは吹き出しで
「これいい？」と言うだけで、tsukumo は吹き出しの文言を作らない。

**質問が出ている間は、入力欄の領域をまるごと質問の箱に渡す**（2026-09-17 決定。テキスト入力欄と
送信の行はその間だけ畳む）。質問の箱は自由入力欄を自分で持つので、下のテキスト入力欄が無くても
答えられる。**畳んでいる間も打ちかけの文字は捨てず、答えると元どおり戻る。**
**許可の箱は畳まない**（ツール名と2つのボタンだけで狭く、入力欄を出したままでも収まる。
許可の箱には自由入力欄が無いので、畳むと打つ場所が無くなる）。

**4領域は1枚の HTML にまとめ、CSS で領域を分ける。** ブラウザタブは1つだけで、
**ターミナルのペインは1つも要らない**（Claude Code の TUI を開かないため）。

**同じページの中に、4領域の会話の画面と入れ替わる「キャラクター画面」が1つある**（2026-09-17 決定。
ユーザー「結構UI的に難しいし、オプションみたいなイメージを持つ」「SPA のようなものを想定していたよ」）。
立ち絵・差し色の差し替え、新しいパックを作る口、画面の色3つ（`ground` / `surface` / `ink`）は
ここに置き、右下の「見た目」の引き出しは無くした（右下に残るのは「領域の比率を既定に戻す」だけ）。
**切り替えは URL の `#character`（作る画面は `#character/new`）**で、リロードしても同じ画面に
戻り、ブラウザの「戻る」が効く。**入る口も戻る口も、全画面の最上部の帯**（2026-09-22 決定。
それまでは入る口がサイドバーの「整える」、戻る口が画面の左上だった）。会話の画面は隠すだけで
外さないので、キャラクター画面に居る間も会話は進み、入力欄の打ちかけも残る。**答え待ちが来たら
帯のいまの作業が「答え待ち」に変わる。** 中身の並びと採らなかった案は `docs/design.md` 13.6、帯は 13.9 が正典。

**領域そのものは縦にだけスクロールし、横には転がらない**（2026-09-15 決定。ユーザーの指摘
「横にスクロールできたのが気になった。スクロールできないのが使い勝手良さそうだよ」）。
`.layout-region` に `overflow-y: auto` だけを書くと、CSS では片方の軸が `visible` でなくなった
ときにもう片方の `visible` も `auto` に計算されるため、書いていない `overflow-x` が `auto` に
なって4領域すべてが横に転がっていた。**横に長いものは、中身の側が自前のスクロール容器を持つ**
（レポートの表は `.table-scroll` の中で転がり、コードは折り返し、図は領域の幅に収め、
長い語は途中で折り返す）。

**狭い画面（760px 以下＝スマホ）では、画面の高さに固定して上段をタブで切り替える**
（2026-09-20 決定。基準は 390x844）。
全体の高さは **`100dvh`** に固定する（`vh` だとソフトウェアキーボードが出たときにページごと
押し上がる）。**上段はメインビューとサイドバーをタブで1つずつ出し**（同時には出さない）、
**下段のキャラビューと入力欄は常に見えたまま**にする。スクロールするのは上段の中だけで、
**ページ全体はスクロールしない**。**タブは「どちらを見せるか」の切り替えであって、領域を
統合するものではない**（4領域はそのまま4つある）。**仕切りのドラッグと「比率を既定に戻す」は
狭い画面では出さない**（動かせる比率が無い）。切れ目は `@media (max-width: 760px)` の1つだけで、
規則は各機能の CSS に分かれている（`docs/design.md` 6.6）。

**タスク一覧の表（「一覧を見る」で開くモーダル）は、狭い画面では1タスク＝1枚のカードになる**
（2026-09-20 決定。ユーザーの指摘「タスク一覧だけは横スクロールになっちゃう」）。
カードは ID・status・難易度・loopable を1行目、**要約を2行目**、依存・着手を3行目に置く
（要約が主なので、機械が付けた名前を読んでから意味にたどり着く形にしない）。**列は1つも
落とさない。** 組み替えるのは CSS だけで、部品の側は表のまま書く。**レポートの中の表は
この対象ではない**（`docs/design.md` 13.3「領域の内幅に入りきらない表は、その表だけ横
スクロールさせる」。あちらは何列になるか分からない一般の表なので、横へ逃がすほうが安全）。

**右下は入力欄**で、比率は CSS だけで決まる（1枚にまとめた理由と、そこが空いていた頃の経緯は
`docs/history/decision.md`「requirements.md 4.7 画面レイアウト」）。

- **上段と下段で縦の仕切り位置が違う。** 上段はメインが広くサイドバーが狭い、下段は半々。
  これは CSS の grid で表す
- **代償**: 領域を別々のウィンドウ（別モニタなど）に分けることはできない。今の構想では不要

### 4.8 セッションの復元

**tsukumo を起こし直したら、前の続きから始める**（2026-09-13 決定。ユーザーの指示
「tsukumo を開き直したとき、セッションを復元するように変更しよう」）。

#### 何を戻し、何を戻さないか

| もの                                       | 戻す     | どうやって                                                |
| ------------------------------------------ | -------- | --------------------------------------------------------- |
| claude 側の会話（文脈）                    | 戻す     | `query({ options: { resume: sessionId } })`               |
| メインビューのやり取り（レポート・ツール） | 戻す     | `getSessionMessages(sessionId, { dir })` を読み直して組む |
| 吹き出しのセリフ                           | 戻す     | 同上（`speak` の呼び出しは transcript に残っている）      |
| 答え待ち（許可・質問）                     | 戻さない | 前のプロセスの `canUseTool` は既に解決されている          |
| 書きかけの本文（`partial-utterance`）      | 戻さない | 仮の表示なので、完成した本文だけを組み直せば足りる        |

#### tsukumo 側に会話を保存しない

**復元のために会話を保存しない。** claude 自身が `~/.claude/projects/` に transcript を
書いている（SDK の `Options.persistSession`。既定 `true`）ので、**そこを正典として読み直す**。
tsukumo 側のキャッシュ・スナップショットは作らない。

これは `docs/coding-standards.md`「会話内容の扱い」の**「別の場所に複製しない」を満たす**。
複製にあたるのは「transcript の内容を tsukumo が別の場所へ書き出すこと」であって、正典を
読んでメモリ上のビューを組み直すのは複製ではない（組み上がったビューは今までどおりプロセスの
メモリにしかなく、`127.0.0.1` にだけ配られる）。**規約を曲げる必要は無い。**

**2026-09-21 に足した雑談の会話のアーカイブ（4.9）は、ここを変えない。** あちらは**あとで
活用するため**に雑談だけを残すもので、**復元の材料にはしない** — 起こし直したときに画面を
組み直すのは今までどおり transcript からで、アーカイブを読み戻す経路は作らない。

#### 鍵（どれを「前のセッション」とみなすか）

**起動した作業ディレクトリ（`cwd`）＋ tsukumo が付けた印**の2つで絞る。**印はキャラクター
パックごとに違い**（`tsukumo:<パック名>`。2026-09-14 決定）、**雑談のときだけ後ろに `:chat` が
付く**（2026-09-20 決定。4.9）ので、実質は「ディレクトリ×キャラクター×モード」で1つの
セッションになる。

1. セッションIDが届いたら（`session-info`）覚えておき、**ターンが終わるたびに**
   `tagSession(sessionId, <そのパックの印>, { dir: cwd })` で印を付け直す。**受け取った直後に
   付けても残らない**（本体もターンの終わりにセッションの要約を書いていて、その書き込みに
   印が含まれないため上書きで消える。2026-09-13 実測。ターンが終わって数秒おいてから付けた
   印は、tsukumo を落としたあとまで残った）
2. **起動時と、キャラクターを切り替えるたびに** `listSessions({ dir: cwd })` を読み、
   **これから起こすパックの印を持つもの**のうち `lastModified` が最新のものを選ぶ

**`cwd` は「起こしたリポジトリ」の意味で読む**（2026-09-22）。同じリポジトリでも worktree が
分かれていれば起こすたびに違うディレクトリになり、ディレクトリの文字列だけで絞ると
**前の続きが一度も見つからず、起動のたびに新規になる**ので、`listSessions` には
`includeWorktrees: true` を渡して**同じリポジトリの worktree を全部見てから印で絞る**。
履歴を読み直す `getSessionMessages` はディレクトリで絞らない（セッションIDが一意なので、
絞らなくても別のものには当たらない）。**鍵の考え方（ディレクトリ×キャラクター×モード）は
変わっていない** — 「ディレクトリ」の粒度がリポジトリになっただけ。

`cwd` だけで絞らないのは、`tsukumo` が `bun link` でグローバルに入っていて**どのプロジェクト
からも起こせる**（4.6）ため。同じディレクトリで素の `claude` を使っていると、印が無ければ
そちらのセッションを拾ってしまう。**印は会話の内容ではない**ので、transcript に付けても
「会話内容の扱い」には触れない。

**パックごとに分けるのは、キャラクターごとに別の部屋を持たせるため**（`docs/design.md` 7章）。
切り替えて戻ってくると、そのキャラクターとの会話と口調が戻る（`resume` したセッションは
最初に起こしたときの人格を保つ。2026-09-14 スパイクで実測）。ただし**印はターンが終わって
3秒後に付く**ので、ターンを1つも終えずに離れたパックのセッションは次に来たときに見つからず、
下の「復元できなかったとき」と同じく新規から始まる。

**2026-09-22 実測: 同じ `sessionId` を2つの `query` から重ねて `resume` しても、別ファイルへは
fork しない。** 使い捨てスクリプトで種セッションを1つ起こし、生きたままの `query`（A）に加えて、
A が生きている間に別の `query`（B）で同じ `sessionId` を `resume` して依頼を送ったところ、
`~/.claude/projects/` の transcript は最後まで同じ1ファイルのままだった（4回分のやり取りが
同居し、`listSessions` が返す `sessionId` も終始1つだけ）。この1つに `tagSession` を呼ぶと、
当然そのファイルに印が付く（他に付け先が無い）。**A 側の `query` はエラーにも止まりもせず、
B の依頼のあとに送った3回目の依頼にも黙って正常に応答した。** つまり「動いている側の会話も
汚れる」の正体は fork ではなく、**同じ transcript への混線**だった。印を起動ごとに分ける設計
（次のタスク）では、印だけでは「使用中かどうか」は分からない前提に立つ必要がある。

**2026-09-22 決定: 印の末尾に「目印」を足し、同じディレクトリで何個 tsukumo を起こしても
セッションを取り合わないようにする**（`tsukumo:<パック名>@7327` /
`tsukumo:<パック名>:chat@7327`）。鍵は「ディレクトリ×キャラクター×モード×目印」の4つになる。
組み立ても読み取りも `src/server/core/config.ts`（`sessionTag` / `readSessionMark`）だけで、
文字列を他所で作らない。

- **区切りは `@`。** `:` を使わないのは、後置きの `chat` と読み違えないため。**目印は
  いちばん後ろの `@` から先**で、読み取りもそこだけを見る
- **目印はビューのポート番号そのもの**（同日決定。**セッションを指す ID は「キャラクターパック
  × ポート番号」**にする、という決めごとの後半がここに出る。2026-09-22 まではポートの並び順を
  `A` / `B` / … の1文字に畳んでいた）。ポートを使うのは、**「その目印がいま使われているか」を
  知っているものが他に無い**ため — 印は transcript に残るだけなので、落ちた tsukumo の印と
  動いている tsukumo の印は見分けられない（上の実測）。ポートは OS が握っていて、**既定なら
  塞がっているぶんだけずれ**（4.6）、**プロセスが落ちれば空く**ので、生きている tsukumo の
  起動順がそのまま出る
- **落ちた側を起こし直すと、空いたポートへ戻るので落ちた側の続きから始まる**（動いている側の
  印は目印が違うので拾わない）。起動のたびに自動で続きから始まるのは変えない（下の「いつ復元するか」）
- **畳まない。** 既定から遠い番号（`TSUKUMO_VIEW_PORT` で指したとき）も `0`（OS まかせ）も、
  そのまま名乗る。**ポート番号なら上限が無い**ので、1文字に畳んでいたときの「26個めからは
  `A` に戻る」という無理が消える
- **昔の印は読むときにポートへ戻す**（`readSessionMark` だけの仕事。transcript を書き換える
  手当てはしない）。**目印の無い印**（`tsukumo:<パック名>`）は既定の 7327、**1文字だった目印**
  （`@A` / `@B` …）は並び順から元のポート（`A` が 7327、+1 ごとに次の番号）。いま続いている
  仕事はそのまま見つかり、次にターンが終われば新しい形の印に置き換わる
- **印の一覧がそのままセッションの一覧**（`listMarkedSessions` が目印・`sessionId`・
  `lastModified` を新しい順に返す）。別の保存先は作らない
- **人が読む部屋の名前はまだ無い。** 画面にはこの目印（ポート番号）がそのまま出る（4.7 の
  サイドバー）。表示名は別に決める

#### いつ復元するか

**常に自動で続きから始める。** 起動のたびに選ばせる画面は作らない（手数が増えるうえ、
「1コマンドで起動」という 4.6 の狙いと衝突する）。**新しい会話を始めたいときの逃げ道**
（新規で起こす指定）は併せて用意する。

#### 復元できなかったときどうするか

**新しいセッションとして起動し、プロセスは落とさない。** セッションIDが古い・transcript が
消えている・`listSessions` が読めない、のいずれも「前提不足」ではなく「動作中の一時的な失敗」
として扱う（`docs/coding-standards.md`「エラーハンドリング」。起動時の即時終了は前提不足だけ）。
**画面の履歴の組み直しに失敗したときも同じ**で、会話（`resume`）だけ生きていれば続行する。

### 4.9 雑談モード

**入れる**（2026-09-20 決定。ユーザーの指示 2026-09-16「雑談モードを入れたい」）。レポートを
読むための画面とは別に、**キャラクターと短い往復をするだけの場**を持つ。「1. 概要・目的」の
2つの成分のうち**「キャラクターと一緒にいる感じがすること」の側だけを取り出した場**で、
仕事の側（レポート）は止める。

**モードとして分ける。** 人格と記法の側で吸収する案（モードを持たず、雑談のような依頼には
自然に短く返らせる）は採らなかった: 記法の10か条は `systemPrompt` に載っているので、モードが
無いと「今回は雑談かどうか」をモデルの推測に委ねることになり、**雑談のつもりが技術文で返る
揺れ**が残る。

#### 雑談モードで変わるもの

| 変わるもの                             | 仕事のとき                       | 雑談のとき                                      |
| -------------------------------------- | -------------------------------- | ----------------------------------------------- |
| レポートの記法（`report-notation.ts`） | `systemPrompt` に載る            | **載せない**                                    |
| ターンの本文                           | メインビューにレポートとして出る | **出さない**（答えはすべてセリフ）              |
| メインビュー                           | レポートを縦に積む               | **立ち絵と会話のログ**（`docs/design.md` 13.7） |
| キャラビュー                           | 立ち絵と吹き出し                 | **畳む**（立ち絵がメインへ移る）                |
| セリフの間合い（`speech-cadence.ts`）  | ツールの前後に1回                | **往復そのもの**になるので別の文面が要る        |

**「レポートは出さない」はユーザーの決定**（2026-09-20。「やり取りは LINE とか Discord のような
イメージ」）。**雑談中に調べ物を頼んだときも本文は出さず、セリフで返す。** 本文が出たターンだけ
立ち絵を退けてレポートを出す案も示したが、採らなかった — 画面がターンごとに入れ替わり、
モードに入っている意味が薄れるため。

**雑談のときだけ、キャラクターから話しかけてもらえる**（2026-09-21 決定。ユーザーの指示
「雑談モードで、キャラ側が話題を決めて話しかけるトリガー(ボタン)を実装したい」）。利用者が
ボタンを押すと tsukumo が合図を1つ送り、キャラクターが**自分で選んだ話題**で話し始める。

- **送った合図は画面のログにも記録にも、下の「雑談の会話のアーカイブ」にも残さない**
  （2026-09-21、ユーザーの選択）。利用者が打っていない一言をログに並べない、という点で下の
  「依頼として流す案は採らない」（直近の逐語の読み戻し）と同じ立場
- **話題そのものを tsukumo は持たない**（原則4「キャラクターの中身をコードに書かない」）。
  渡すのは「話題はあなたが選ぶ」という合図だけ
- **仕事のときは押す場所そのものが無い**（メインビューが雑談のログではないため）。
  ボタンの置き場所・見え方・ターン進行中の扱いは `docs/design.md` 13.7

#### 切り替え方

**セッションを起こし直す**（`switch-character` と同じ道）。`systemPrompt` はセッションを起こす
ときに固定されるので、載せる文面を変えるには起こし直すしかない。**切り替えるたびに画面が
初期化される**のはキャラクターの切り替えと同じ挙動で、そこは受け入れる
（2026-09-20、承知のうえでの選択）。

**雑談と仕事は、画面だけでなく claude 側の文脈ごと分ける**（2026-09-20 ユーザー指示
「ここは分離したほうが良さそう」）。**セッションの印をモードごとに分け**
（`tsukumo:<パック名>` と `tsukumo:<パック名>:chat`。4.8「鍵」）、起こし直すときは
**これから入る側の印を持つセッションを `resume` する**。雑談⇄仕事を往復しても、それぞれが
自分の側の続きに戻る。**両側で分ける** — 仕事へ戻したメインビューにも雑談は出ない。
**仕事の側の印の文字列は変えない**（変えると、いま続いている仕事のセッションが次の起動で
見つからなくなる）。

**この決定は、ここに書いてあった「会話は `resume` で続くので、雑談に入ってからも直前までの
やり取りを踏まえて話せる」を覆した。** 分けない形では雑談へ入った時点で仕事のセッションを
`resume` してしまい、**仕事中の依頼文とセリフがそのまま雑談のログに並ぶ**（雑談のログが拾うのは
依頼とセリフの2種類なので、レポートとツールの行は落ちるが会話は残る）。2026-09-20 に実際に
目撃した。**画面だけ分ける案**（ログの組み立てで仕切る）と**雑談に入った時刻より後だけ並べる案**は
採らなかった: どちらも claude 側の文脈は仕事のまま残るので、口調と話題がそちらへ引かれる。

**代わりに、そのパックで一度も雑談のターンを終えていないうちは、雑談のログが空から始まる。**
印が付くのはターンが終わって数秒あとなので（4.8「鍵」）、最初の雑談には続きにするものが無い。
**これは受け入れる**（4.8「復元できなかったときどうするか」の範囲）。印を早く付ける手は、
本体がターンの終わりに書く要約に上書きされて消えるので採れない。

**依頼の先頭に印を足す案**（起こし直さずに済み、画面も消えない）も示したが採らなかった。記法が
`systemPrompt` に残ったままになり、**毎ターン「今回は外してよい」と打ち消し続ける**形になる。

**切り替える口は画面の最上部の帯の「仕事｜雑談」のトグル**（2026-09-23 決定。それまではサイドバーの
「セッション情報」の `<select>`）。モードはセッション限りの**動き方**で、どの画面からでも変えられる
帯に置く（`docs/design.md` 13.6 の表）。

- **トグルを1回押すと起こし直す**（確かめの一言は挟まない）。失うのは画面の初期化だけで、それは
  上で受け入れてある。戻せばそれぞれの続きから始まる
- **ターン進行中は切り替えられない**（キャラクターの切り替えと同じ条件。画面は押せなくし、
  サーバも断る）。理由の文面はモードの語で言う（「ターン進行中は仕事と雑談を切り替えられない
  （中断すると切り替えられる）」）
- 形・押せないときの見せ方は `docs/design.md` 13.9「動き方の操作子」、雑談中の帯は 13.7

#### どこまで遡れるか

**雑談だけ記録の上限を上げる**（2026-09-20 決定）。`src/shared/session-state.ts` の
`MAX_SESSION_STATE_TURNS = 20` は仕事のときの値として据え置き、**雑談のときは 100 ターン**を
持つ。雑談の1ターンはセリフ1〜2件で軽く、20往復は会話としては短いため。

**「そのセッションの全部」は採らなかった。** 復元側（`readRestoredEvents`）に件数の上限が
無いので技術的には可能だが、**常駐プロセスが持つ記録を無限に増やさない**という
`trimToRecentTurns` の前提と正面から衝突する。上限を消すのではなく、モードごとに値を変える。

**「20 のまま」も採らなかった。** 2026-09-20 の実測では、そもそも遡れない主因は上限ではなく
ログの容器が上方向へスクロールできないことだった（`docs/design.md` 13.7）。その CSS を直せば
20ターンぶんは全部見えるようになるが、**雑談で「さっき話したこと」に届く幅としては短い**。

**仕事のメインビューとは揃えない。** 仕事は依頼の見出しで区切ってタブで遡り
（`MAX_MAIN_VIEW_TURNS`）、雑談は素直な時系列をスクロールで遡る。並びの規則が違うので、
遡り方も別のままにする（`docs/design.md` 13.7）。

#### 記憶の圧縮と忘却

**入れる**（2026-09-21 決定。ユーザーの指示「雑談モードにおいて、tsukumo の会話ログはその表情と
セットですべて残しつつも、定期的にその要約を作成し、一定期間ごとに要約+新たな会話から要約を
作ることで記憶の引き継ぎを行いつつも忘却を再現したい」）。雑談は起こし直すたびに前の雑談
セッションへ戻るので（上の「切り替え方」）、**放っておくと claude 側の文脈だけが際限なく伸びる**。

**記憶は2層で持つ**（2026-09-21 決定。ユーザーの指示「直近残す量を tsukumo が決めたうえで、
compact ではなくそのまま(テキストデータ)で読み込む方針だよ」）。**直近は要約せず逐語のまま
読み戻し、それより前だけを要約が受け持つ。**

| 層         | 何が渡るか                             | どこから来るか                               | 量を決めるのは |
| ---------- | -------------------------------------- | -------------------------------------------- | -------------- |
| 直近       | **会話の文面そのもの**（逐語）         | `~/.tsukumo/chat-archive/`（下のアーカイブ） | **tsukumo**    |
| それより前 | claude が自分の言葉で書き直した要約1つ | `~/.tsukumo/chat-summary/`（下の要約の写し） | claude         |

**2つは別の口で、渡す先だけが同じ**（雑談のセッションの `systemPrompt`）。直近の側の正典は下の
「直近の会話は逐語のまま読み戻す」。

**要約を作るのは claude 自身で、口は Claude Code 組み込みの `/compact`。** tsukumo がするのは
容量を数えて、閾値を超えたターンの終わりに `/compact` を依頼として1回投げることだけ。

- **これは 2.2 の「会話を外部のモデルへ送る」に当たらない。** 会話はもともとその claude の
  文脈にあり、要約も同じプロセスの中で作られる。**tsukumo が自前で API を叩いて要約する案は
  2.2 のまま対象外**
- `/compact` は**組み込みのスラッシュコマンド**（2026-09-21 実測: `supportedCommands()` に
  `builtin: true` で並び、説明は "Free up context by summarizing the conversation so far"、
  `argumentHint` は `<optional custom summarization instructions>`）。**引数に要約の指示を
  添えられる**ので、雑談では「覚えておくことだけを短く」に当たる一文を添える
- 入力欄の `/` 補完にも同じものが出ているので、**利用者が手で叩く道も最初からある**
- **送る文面は画面のログにも記録にも、下の「雑談の会話のアーカイブ」にも残さない**（2026-09-21
  決定。上の「話しかけてもらう」の合図を残さないのと同じ立場——利用者が打っていない一言を
  ログに並べない）。流れるのは `request` ではなく `turn-started` なので、圧縮が起きたこと自体は
  下の「忘却は画面に1本の区切りとして出す」の細い線が別に伝える

**閾値は容量（バイト）で持ち、件数では測らない。**

| 何         | 値                                                                      |
| ---------- | ----------------------------------------------------------------------- |
| 規定の容量 | **128 KiB**（131,072 バイト）                                           |
| 数えるもの | 雑談のログの文面（利用者の依頼とキャラクターのセリフ）の UTF-8 バイト数 |
| 数える範囲 | **前の圧縮点から先だけ**（それより前は claude 側にもう無い）            |
| 数える契機 | ターンの終わりに1回。**1ターンで2度は投げない**                         |

**128 KiB の根拠**（1ターンのバイト数は 2026-09-21 に測った。**実物の会話は使わず**、
`test/fixture/` の架空の疑似セッションで測っている）: 疑似セッションのセリフ12件は1件あたり
21.8 文字・65 バイト（日本語1文字 ≈ 2.98 バイト）。雑談の1ターンは依頼1つとセリフ1〜2件なので
130〜195 バイトになり、128 KiB は **672〜1,008 ターン**に当たる。画面が持つ上限（上の
「どこまで遡れるか」の 100 ターン）の7〜10倍で、**「画面からは消えたけれど、まだ覚えている」が
普通の状態**になる。

**この値を決めているのは逐語の窓（下の「直近の会話は逐語のまま読み戻す」の 64 KiB）で、閾値は
その2倍**（2026-09-21 にユーザーが逐語を 64 KiB に決め、閾値も一緒に上げることを選んだ）。
倍率に意味があり、絶対値のほうは倍率から出ている:

- **1倍（＝逐語の窓と同じ）では忘却が起きない。** 畳んだ範囲を次のセッションが丸ごと逐語で
  戻すことになり、**畳むそばから同じ量を戻す**。**2倍なら、畳んだ 128 KiB のうち逐語で戻るのは
  新しい半分（64 KiB）だけ**で、古い半分は要約しか持たない
- **3倍・4倍にはしない。** 最後の圧縮点から先はまだ要約になっていないので、新しいセッションへ
  渡るのは「要約（前の圧縮点まで）＋新しいほうから 64 KiB」になり、**その間に挟まってどちらにも
  入らない範囲**が最大で「閾値 − 64 KiB」できる。2倍ならそれは1窓ぶん（64 KiB・336〜504 ターン）
  で収まるが、4倍では3窓ぶん（192 KiB・1,000〜1,500 ターン）が**要約にも逐語にも無い**時間帯が
  できる

**圧縮の間隔が延びることは受け入れる。** 日に20往復なら閾値に届くのは 34〜50 日に1度で、
32 KiB のとき（8〜13 日に1度）より間遠になる。**忘却が起きる縁は2つあって、間隔が効くのは
片方だけ**だから釣り合う: 続きから始めるとき（`resume`）は圧縮点より前が要約だけになり、
新規に起こすときは**逐語の窓より前**が要約だけになる。後者は会話が伸びるたびに滑るので、
圧縮を待たない。**閾値が受け持つのは「claude 側の文脈を際限なく伸ばさない」というこの節の
最初の役**で、128 KiB は日本語で約 44,000 文字、下の実測の窓（1,000,000 トークン）から見れば
まだ十分に小さい。

**claude 自身の自動の圧縮には任せない。** 2026-09-21 の実測では窓は 1,000,000 トークン・自動の
閾値は 967,000 トークンで、雑談では永久に届かない。窓を小さくする設定（`autoCompactWindow`）を
セッション限りのフラグ層に載せる手も試したが、**受け付けはするのに閾値は動かなかった**ので
採れない。**忘却の距離は tsukumo が決め、claude 側の自動の圧縮は最後の受け皿として残る。**

**数え落としは許す。** 添えた画像とツールの入出力は数えない（雑談では稀で、正しく数えるには
毎ターン claude へ問い合わせる必要がある）。数え落ちて起きるのは「圧縮が少し遅れる」ことだけで、
その先は claude 側の自動の圧縮が受ける。

**「その時点より過去の記録は読み込まない」に、tsukumo 側の実装は要らない。** 圧縮は transcript に
区切りを1つ書き、**そこで親子の鎖が切れる**（2026-09-21 実測: 区切りの行は親を持たず、その直後に
要約の行が1つ入る）。`resume` も `getSessionMessages` も鎖をたどるので、**どちらも自動的に区切りから
先だけを見る**。範囲を指定する口（`resumeSessionAt` / `forkSession` の `upToMessageId`）はどれも
**「指定した点より前を残す」**方向で、欲しい向きの逆なので使わない。

**1回でどれだけ空くかも tsukumo は決めない。** 残す範囲を選ぶのは Claude Code 側で、実測では
29,998 → 3,844 トークン（約 1/8）まで落ちた。**圧縮の直後にまた閾値を超える心配が無い**ので、
「古い側の何割を要約の範囲にするか」という割合を tsukumo が持つ必要は無い。

ここで tsukumo が決めないのは**いま動いている claude の文脈に残る量**までで、**新しい
セッションへ渡す直近の量は tsukumo が決める**（下の「直近の会話は逐語のまま読み戻す」）。

**圧縮には時間がかかる**（実測 39〜65 秒）。だから**ターンが終わった直後に投げる** —
利用者が次の一言を打つ前に済ませる。

**画面のログは圧縮では消えない。** 記録（`SessionState`）は動いているプロセスが持つもので、
上限（雑談 100 ターン）はそのまま効く。**変わるのは起こし直したあと**で、transcript の鎖が切れて
いるので復元されるログも圧縮点から始まる。**画面に出るのはそこまで**で、それより前の会話は
下の「雑談の会話のアーカイブ」に残る。

**ただし「キャラクターが覚えている範囲」は画面とは別で、圧縮点より前にも届く**（2026-09-21
に足した）。下の逐語の読み戻しはアーカイブから読むので、**圧縮の区切りにも画面の上限にも
縛られない**。画面は「いま読むため」、記憶は claude の文脈、と持ち場が違う。

**100 ターンは画面の上限であって、残す量の上限ではない**（ユーザーが 2026-09-21 に
tsukumo 側のディスクへの複製を認めた。覆った記録は `docs/history/decision.md`）。
要約の写し（下の表）は記憶を渡すためのもので、会話そのものを残す役は持たない。

**忘却は画面に1本の区切りとして出す。** 雑談のログの圧縮点に当たる位置へ、**文言を添えない
細い線を1本だけ**入れる（2026-09-21 決定。ユーザーの言葉「これは頭の中で行われるもの、という
想定だから文言は出さないよ」）。「ここから前は要約になっている」に当たる説明文は画面に出さない。
**セリフでも知らせない** — セリフの文面を決めるのは
claude だけで、tsukumo がキャラクターの言葉を作らない。起こし直したあとはこの区切りがログの
いちばん上に来る。

**要約の写しを1つだけディスクに持つ**（2026-09-21 決定）。狙いは**「セッションをリセットしても
記憶を持つ」**こと——`/clear`・`TSUKUMO_NEW_SESSION=1`・印を見失ったとき・`cwd` が変わったときは
transcript が別になり、claude 側の要約ごと落ちるため。**ユーザーはそれを承知のうえで
「新しいセッションでも持つ」を選び、要約を `~/.tsukumo/` の下に置く例外を認めた**
（`docs/coding-standards.md`「会話内容の扱い」の「別の場所に複製しない」に対する、範囲を
限った例外）。

| セッションが別になる場面                                                    | claude 側の要約        | tsukumo の写しを載せるか                             |
| --------------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------- |
| 起こし直し（モード切替・キャラ切替・上げ直し）                              | `resume` が読む        | **載せない**（載せると2度載る）                      |
| `/clear`                                                                    | 落ちる見込み（未実測） | その場では載せない。**次に起こしたときに必ず載せる** |
| 新しいセッション（`TSUKUMO_NEW_SESSION=1`・印を見失った・`cwd` が変わった） | 落ちる                 | **載せる**                                           |

**載せる条件は2つあり、どちらかに当たれば載せる**（どちらでもなければ載せない）:

1. **続きから始めない**（新規に起こす）
2. **続きから始めるが、前に `/clear` を見ている**

- **「続きから始めたか」だけでは足りない。** 印はターンが終わるたびに**そのときのセッションID**へ
  付け直されるので（`src/server/adapter/sdk-driver.ts`。`/clear` の直後は新しい `session_id` に
  なる）、**`/clear` のあと1ターンでも回すと、空になったほうのセッションが印を持つ**。次の起動は
  それを `resume` するので、条件が1つだけだと**そのパックの記憶が二度と戻らない**
- **`/clear` を見た事実は写しのファイル自身に「未渡し」の1行の印として残す**（プロセスをまたぐ
  ため。`~/.tsukumo/state.json` には混ぜない。置き場と形は `docs/design.md` 7章）。**印が無い・
  読めないときは未渡し扱い** — 倒れる方向を「同じ要約が2度載る」側にして、**黙って記憶が消える
  ほうへ倒さない**
- **写しを載せたら印を「渡し済み」に戻す。** `resume` した文脈に要約が既にあるときに重ねない、
  という目的はそのまま保つ
- **雑談のときだけ**。仕事の側の文脈に写しを載せることはしない
- 置き場（`~/.tsukumo/chat-summary/<パック名>.md`）・捕まえ方・渡し方・上限は
  `docs/design.md` 7章

**写しに会話の文面がそのまま入らないよう、`/compact` の引数に指示を添える。** 引く線は
「プロフィールの書き戻し」の3条件と「書かないもの」をそのまま使う（**自分の言葉で書き直す・
発言を引用しない・利用者について知ったことは書かない**）。

**ただし、それだけでは守らせきれない。** 要約を書くのはモデルで、**tsukumo は写す中身を読んで
判定しない**（読んで判定する経路を作るほうが規約とぶつかる。`docs/design.md` 7.1
「tsukumo がターンの終わりに会話を見て判定する案は採らない」と同じ理由）。だから**中身に立ち入らない
縛り**を重ねて、写しが会話のログに育つ経路のほうを塞ぐ:

| 縛り                                              | 何を塞ぐか                                                         |
| ------------------------------------------------- | ------------------------------------------------------------------ |
| 写すのは claude が作った要約1つだけ               | 生のログ・transcript・ツールの入出力は今までどおり書かない         |
| 1パック1ファイルを上書きする                      | 履歴が積み上がらない（前の要約は残らない）                         |
| 8 KiB を上限にし、溢れたら古いほうの行を落とす    | 要約の形をした会話の写しが際限なく太らない                         |
| 画面にも `error` フレームにも stderr にも出さない | 写しが別の経路から外へ出ない                                       |
| 雑談のときだけ書き、仕事のときは触らない          | 作業の文脈（プロジェクトの事情・利用者の都合）が入る経路を作らない |

**「会話内容の扱い」の4つの条のうち、例外を使うのは「別の場所に複製しない」の1つだけ。** 残る3つは
そのまま満たす — **外部に送らない**（写しはローカルのファイルで、戻す先は同じマシンで動いている
claude の `systemPrompt` だけ）、**ログに全文を出さない**（出すのは長さまで）、**テストの
フィクスチャに実物を使わない**（要約のフィクスチャも手で書いた架空の文面）。ブラウザ側の永続化に
会話を置かないことも変わらない（写しはサーバ側のファイルで、`SessionState` にも `localStorage` にも
載らない）。

**元に戻す手はファイルを消すこと。** `~/.tsukumo/chat-summary/` を消せば、そのぶんを忘れる
（「覚えたこと」の節を消せば書き足す前に戻るのと同じ考え方）。

**写しは世代を重ねるほど薄くなる。** 新しいセッションへ写しを渡すのは `systemPrompt` で、そこは
会話ではないので、**次の圧縮が作る要約に写しの中身が全部は残らないことがある**。**これは受け入れる**
— 倒れる方向が忘却の側で、この機能が再現したいものと同じ向きだから。**薄くなるのは古い側だけ**
になった（2026-09-21）——直近は逐語のまま別の口で渡るので、世代を重ねて削れるのは要約が
受け持つ範囲だけになる。

**`/clear` の直後の文脈には記憶が無く、戻るのは次にセッションを起こしたとき**（モードの出入り・
キャラクターの切り替え・次の起動）。`persona.md` への書き戻しが**次に起こしてから効く**のと同じ粒度で、
**`conversation-cleared` を見てその場で起こし直す案は採らない** — 画面の初期化とセッションの
起こし直しという大きな動きを、利用者が打った組み込みコマンド1つの副作用にしないため。**その代わり、
「次に起こしたとき」では確実に戻す**（上の条件2）。`/clear` は利用者がいちばん素直に「セッションを
リセット」と呼ぶ操作なので、ここが抜けるとこの機能の狙いそのものを外す。

**`/clear` で要約が落ちるかは実測していない。** 落ちる前提で組んでいるが、もし残っていたとしても
起きるのは**同じ要約が2度載ること**だけで、記憶が消えることはない。**実測を決定の前提にしない。**

**直近の会話は逐語のまま読み戻す**（2026-09-21 決定。上の「記憶は2層で持つ」の直近の側）。
`systemPrompt` に載せるのは要約の写しだけ、という形をここで覆した。

**出どころは下の「雑談の会話のアーカイブ」だけ**（`~/.tsukumo/chat-archive/<パック名>/`）。
transcript を読む案は採らない — 下のアーカイブの節が2つの理由（鎖を無視して全部読む口が無い・
保持期間も形式も Claude Code の都合）で既に否定しているうえ、`docs/coding-standards.md`
「会話内容の扱い」の「広げていないこと」に**transcript を読んで書き出さない**が明記されている。
**別に持つ案も採らない** — 同じ会話を2箇所へ書くことになり、複製を1つ増やす。

**量は容量（バイト）で決め、件数では測らない**（上の閾値と同じ物差しを引き継ぐ）。

| 何         | 値                                                                            |
| ---------- | ----------------------------------------------------------------------------- |
| 規定の容量 | **64 KiB**（65,536 バイト）                                                   |
| 数えるもの | アーカイブの各行の**文面だけ**の UTF-8 バイト数（時刻・話者・表情は数えない） |
| 数える向き | **新しいほうから遡る**（新しい日のファイルから順に、届いたところで止める）    |
| 切り方     | **1件（1行）を単位にし、途中では切らない**。溢れる1件は載せない               |

**64 KiB はユーザーの指示**（2026-09-21「雑談モードの要約以外の記憶領域（直近の会話の逐次
文字列）を 16KB から 64KB にしたい」）。雑談の1ターンは 130〜195 バイト（上の「128 KiB の根拠」で
測った値）なので、64 KiB は **336〜504 ターン**に当たる。

**線を引く場所が画面から日数へ移った。** 16 KiB だったころは 84〜126 ターンで画面の上限（上の
「どこまで遡れるか」の 100 ターン）とほぼ重なり、「画面に出ている範囲＝逐語で覚えている範囲」が
1本の線として読めた。64 KiB は画面の **3.4〜5倍**あるので、その読み方はもう当たらない。
代わりに**3つが入れ子**になる:

| 範囲             | どこまで                  | 読み方                                       |
| ---------------- | ------------------------- | -------------------------------------------- |
| 画面のログ       | 100 ターン                | **いま読める**                               |
| 逐語で覚えている | 336〜504 ターン（64 KiB） | **画面から消えても、言葉のまま覚えている**   |
| 要約だけが持つ   | それより前                | **話の筋は残っているが、言葉は残っていない** |

**新しい物差しは日数。** 日に20往復なら 64 KiB は **17〜25 日**ぶんで、**「ここ3週間ほどの雑談は
そのまま覚えていて、それより前は要約になっている」**と読める。画面（100 ターン）は窓の 1/3 にも
満たないので**必ず内側に収まり**、「さっき画面で見た話を忘れている」は起きない——16 KiB のときに
線を画面へ合わせて守ろうとしていたものは、窓が広がったことでそのまま満たされる。

- **8 KiB（約 42〜63 ターン）も 16 KiB（84〜126 ターン）も、もう採らない。** 要約の写しの上限が
  8 KiB のままなのは「要約が会話の写しに育つのを止める」ためで、理由が違うので逐語の窓と
  連動させない（下の「要約の写しの上限（8 KiB）は動かさない」）
- **圧縮の閾値（128 KiB）と読み戻す量（64 KiB）は別の値で、閾値のほうが大きい。** 前者は
  「いつ畳むか」、後者は「新しいセッションへ逐語で何を渡すか」。**揃えると「畳むそばから同じ量を
  戻す」ことになり忘却が起きない**ので、閾値を窓の2倍に置いている（根拠は上の「128 KiB の根拠」）。
  **表が2つに割れているのはそのため**

**`systemPrompt` が毎ターン抱える量が4倍になることは受け入れる。** 64 KiB は日本語で約 22,000 文字
（1文字 ≈ 2.98 バイト）。**1文字＝1トークンと最も悪く見積もっても**、窓（上の「claude 自身の自動の
圧縮には任せない」で実測した 1,000,000 トークン）の 2.2% 程度で、自動の圧縮の閾値
（967,000 トークン）には桁が2つ足りない。加えて:

- **前置きは伸びない。** 会話は往復のたびに伸びるが、`systemPrompt` は起こすときに固定される。
  毎ターン抱えるのは同じ 22,000 文字で、**上限が決まっている側**に入る
- **載る機会が限られる。** 載せるのは「新規に起こしたとき」と「`/clear` のあと」だけで（下の
  「載せる口」）、`resume` で続く普通の往復では載らない
- **払っているものが、そのまま「覚えている距離」。** この機能が決めるのは忘却の距離なので、
  窓を4倍にした対価が文脈の数%なら目的と釣り合う

**要約の写しの上限（8 KiB）は動かさない。** あちらの 8 KiB は「要約が会話の写しに育つ経路を塞ぐ」
ための上限で、**逐語でどれだけ戻すか**とは目的が違う（上の「中身に立ち入らない縛り」の表、
`docs/design.md` 7章）。

**載せる口は `systemPrompt` の append で、載せる条件は要約の写しと同じ**（上の「載せる条件は2つ
あり、どちらかに当たれば載せる」）: (1) 続きから始めない、(2) 続きから始めるが写しの印が「未渡し」。
どちらでもなければ載せない——**`resume` した文脈には同じ会話が既にある**ので、載せると二重になる。

- **写しがまだ無いときも逐語は載せる。** 条件を決めるのは「続きから始めたか」と印だけで、
  要約の写しがあるかどうかではない（**印が無い・読めないときは未渡し扱い**、も同じ）
- **依頼として流す案は採らない**（写しと同じ理由。雑談のログに利用者が打っていない一言が並び、
  次の transcript にも依頼として残る）
- **画面には出さない。** 読み戻した逐語は claude の文脈に入るだけで、画面のログは今までどおり
  transcript からの復元で作る（4.8）。**新しいセッションでは画面が空でもキャラクターは直近を
  覚えている**——持ち場が違う（上の「画面のログは圧縮では消えない」）
- **要約と範囲が重なるのは許す。** アーカイブは圧縮に影響されないので、64 KiB の窓が最後の
  圧縮点より前まで届くことがあり、そのぶんは要約にも入っている。**倒れる方向を「忘れる」側に
  しない**
- **載せるのは文面と話者の別だけ。** 表情も画像の枚数も載せない（表情はそのときのセリフに付いて
  いた印で、次のセリフを縛る材料にしない）。いつごろの話かは**日付が変わるところに見出しを
  1つ挟む**ことで足りる（並べる順は `readRecent` が返したまま。日付で並べ替えたり落としたり
  しない。1日ぶんしか無いときの見出しは1つだけ）

**窓から溢れた1往復でも、旗が立っていれば落ちない**（下の「残すと決めた1往復は窓から落とさない」）。
**この 64 KiB の外側に、別の 8 KiB として足す**ので、上の見積もりの前提（窓の大きさ）は動かない。

**`/compact` はやめない。** 直近を逐語で渡すようになっても、**古い側の要約を作る口**として残る。
外すと claude 側の文脈が際限なく伸び、受けるのは claude 自身の自動の圧縮だけになる（上の
「claude 自身の自動の圧縮には任せない」で、雑談では永久に届かないと実測済み）。ユーザーの方針も
「それより前は要約のまま」で、要約をやめるとは言っていない。

**規約の例外を1つ広げた。** 生の会話をアーカイブから読み戻して claude の `systemPrompt` へ渡すのは、
**書き出す**ことしか認めていなかった `docs/coding-standards.md`「会話内容の扱い」の例外に収まらない。
**ユーザーが 2026-09-21 に認めた**ので、規約の側にも「読み戻してよいもの」の表を足した。
**逐語の会話が新しいセッションの transcript（`~/.claude/projects/`）へ毎回書かれることも、その
承認に含まれる。** 広げたのはここまでで、**仕事の側の文脈には載せない**（雑談のときだけ）。

#### 残すと決めた1往復は窓から落とさない

**入れる**（2026-09-21 決定。ユーザー承認済みのドラフト「逐語の読み戻しを増やすだけでは、大事な
一言と相槌が同じ重さで古い順に落ちる。雑談の1件に『残す』印を付けられるようにし、読み戻しの窓から
溢れても印の付いた件は落とさない」）。上の窓（64 KiB）は**古い順に落ちるだけ**で、重み付けが無い。

**旗を立てるのはキャラクター自身**（2026-09-21、ユーザーの選択）。`remember` / `forget` と同じく
**プロセス内の MCP ツールを1つ足す**（`keep`）。**利用者が画面から指す UI は作らない。**

| 論点              | 決め                                                                          |
| ----------------- | ----------------------------------------------------------------------------- |
| どの1件に立てるか | **そのターンの1往復**（依頼とセリフをまとめて）。ツールは**引数を取らない**   |
| いつ書くか        | **ターンの終わり**（旗はターンの途中のどこで呼んでも、その1往復ぜんぶに付く） |
| どう残すか        | **アーカイブの行を指す印だけ**を別に積む（**文面は複製しない**）              |
| 読み戻しでの扱い  | **窓の外に足す**（窓の中で優先しない）。**上限は別に 8 KiB**                  |
| 旗が増え続けたら  | 8 KiB に収まらないぶんは**古い旗から落ちる**（窓と同じ向き）                  |
| 消す口            | **作らない**（`forget` に当たるものは置かない）                               |

**ツールに引数を持たせない。** 「残したい文面」をモデルに渡させる案は採らない — 会話の文面が
ツールの引数を通って戻ってくる経路になり、**アーカイブの行と一致しない写し**が生まれる。指せるのが
そのターンだけなら、指し先は tsukumo 側で確定する。

**1件ではなく1往復に付ける。** 大事なのは「何を言われて、何と答えたか」なので、片側だけを残すと
読み戻したときに意味が立たない。

**窓の中で優先しない。** 旗の付いた件を 64 KiB の中で先に詰めると、旗が増えるほど直近が押し出され、
**「いまの話が通じなくなる」**ほうへ倒れる。外に足せば、読み戻し全体の上限は **64 KiB + 8 KiB** で
決まったままで、払う対価も上の見積もり（文脈の数%）の 1/8 だけ増える。

**8 KiB は要約の写しと同じ大きさ**（約 42〜63 ターン ＝ 21〜31 往復）。旗は「たまに立てるもの」で、
これで足りなければ立てすぎだと読む。

**窓に入っている件は旗のぶんに重ねない。** 旗を立てた直後のセッションでは、その1往復はまだ窓の中に
あるので、旗のぶんは空になる。**同じ会話が2度載らない。**

**形は「印だけ」。** 旗の付いた行の**文面は複製しない** — 積むのは行を指す時刻だけで、会話は
アーカイブの日付のファイルに1つあるまま。だから旗そのものは
`docs/coding-standards.md`「会話内容の扱い」の**書き出してよいものの表に数えずに済む**
（同じ表が3行になったのは下の「古い雑談は索引を引いて思い出す」の見出しの1行で、あちらは
文面を持つ）。**版（`v`）も上げない**（日付のファイルの行は1バイトも変わらない。追記のまま）。
置き場と形は `docs/design.md` 7章。

**時系列が飛ぶことは、節を分けて伝える。** 旗のぶんは直近より前で、間に残っていない会話がある。
`systemPrompt` には**別の見出しの節**として、要約と直近の間に置き、**続きとして読まないこと**を
前置きで断る（混ぜて1つの並びにすると、その断絶が読む側に見えない）。並べ方（話者の印・日付の
見出し）は直近と同じ。

**消す口は作らない。** `forget` に当たるものを置くと、**消したい行の文面をツールの引数で指す**ことに
なり、上の「引数を持たせない」と逆を向く。**消す手はファイルを消すこと**（アーカイブ・要約の写し・
「覚えたこと」と同じ考え方）——索引のファイルを消せば旗が全部落ち、会話そのものは残る。

#### 古い雑談は索引を引いて思い出す

**入れる**（2026-09-21 決定。ユーザー承認済みのドラフト「1日1行の索引ファイルを持ち、まず索引を
引いて当たった日のアーカイブだけを逐語で読む。`docs/` の『節の索引』と同じ作り。全文検索の
仕組みは要らない（1日20KB・1年7MB の規模なので足りる）」「足りないのは探す手段ではなく、
**探しに行く契機と、言葉のずれを吸収する索引**のほう」）。上の窓（64 KiB）と旗（8 KiB）は
**起こすときに渡しきり**なので、そこから溢れた話は要約にしか残らない。

| 論点                  | 決め                                                                           |
| --------------------- | ------------------------------------------------------------------------------ |
| 索引の1行を誰が書くか | **キャラクター自身**（`index` ツール。**文面の判断はモデル側**）               |
| いつ書くか            | **その日のうち**（付くのは書いた日で、前の日には付け直せない）                 |
| 何を書くか            | **その日の見出し1行**（120文字まで・**1ターンに1行**）。会話の写しではない     |
| 置き場                | `~/.tsukumo/chat-archive/<パック名>/index.jsonl`（**パックごと**。またがない） |
| 探しに行く契機        | **キャラクター自身が引く**（`recall` ツール。引く言葉を渡す）                  |
| 読む量                | **1回 8 KiB**・**1ターンに1回**（窓とも旗とも別に数える）                      |
| 引くのに何を使うか    | **`node:fs` で索引を読んで絞る**（`grep` などの外部コマンドを起こさない）      |

**`/compact` のときに書かせる案は採れない。** `/compact` は **Claude Code 本体が畳む流れ**で、
tsukumo が渡すのは要約の指示だけ（できた要約は `PostCompact` フックで受け取る。上の「記憶の圧縮と
忘却」）。その流れの中で tsukumo の MCP ツールが呼ばれる保証が無く、**畳む契機（128 KiB）と
日の境目もそろわない**。

**日が変わったことを tsukumo が見て起こす案も採らない。** 隠しの依頼を1つ送ることになり、雑談では
**セリフが返る**ので、利用者が打っていない一言に対する返事が画面に並ぶ（上の「話しかけてもらう」で
合図を記録にもログにも残さないと決めたのと、倒れる向きが逆）。**作法の条（`docs/design.md` 5章の
`chat-manner.ts`）とツールの説明で足りる** — 索引を書くのも引くのも、キャラクターが自分で決める。

**契機をセッションを起こすときに置く案も採らない。** 起こす時点では**引く言葉が無い**ので、
「当たった日だけ読む」が成り立たない（載せられるのは窓と同じ「新しいほうから」だけで、
いまある読み戻しと変わらない）。**利用者の依頼の文面で tsukumo が引く案も採らない** — tsukumo が
会話の中身を読んで判定する経路になり、上の「文面を読んで判定しない」と正面からぶつかる。

**`recall` は戻り値が `"ok"` だけではない唯一のツールになる**（4.2 の線をここで1つだけ広げる）。
**広げてよいと判断した理由は3つ:**

1. **返すのは tsukumo の状態ではなく、その会話自身の過去。** 4.2 が塞いでいるのは
   「tsukumo からモデルへの逆流路」（画面の事情・セッションの状態が文脈へ戻ること）で、
   アーカイブの逐語はそこに当たらない
2. **逐語を claude へ戻すこと自体は 2026-09-21 に認められている**（上の「直近の会話は逐語のまま
   読み戻す」）。ここで増えるのは**渡す扉**であって、渡すものではない
3. **扉を増やさないと「当たった日だけ」が成り立たない**（引く言葉を受け取れるのはツールだけ）

**広げるのはこの1つだけ。** `speak` / `remember` / `forget` / `keep` の戻り値は `"ok"` のままで、
**2つ目を足すにはユーザーの決定が要る**。

**見出しに書いてよいものの線は `remember` と同じ**（上の「プロフィールの書き戻し」の3条件のうち、
**自分の言葉で書く**・**会話の文面を写さない**・**利用者について知ったことは書かない**の3つ）。
**見出しは会話ではなく、その日の目次**で、当たったときに開く先がアーカイブの1つの行になる。

- **当たらなかったときは正直に言う**（作り話で埋めない）。tsukumo が返すのは短い一言だけで、
  **会話の文面は1バイトも入らない**
- **引いた逐語を読み上げない・引用しない**（踏まえてよい、は窓と同じ）
- **画面には出さない。** 引いた結果はモデルの文脈に入るだけで、雑談のログには並ばない
- **消す手はファイルを消すこと**（`index.jsonl` を消せば索引が全部落ち、**会話そのものは残る**。
  旗の索引と同じ）
- **規約の例外を2つ広げた**（`docs/coding-standards.md`「会話内容の扱い」の表に、**書き出して
  よいもの**の3つ目＝見出しの1行と、**読み戻して渡してよいもの**の2つ目＝当たった日の逐語を
  足した）。どちらも雑談のときだけ・`~/.tsukumo/` の下・渡す先は同じプロセスが起こした claude

置き場・形・誰がいつ書くか・どう引くかは `docs/design.md` 7章。

#### 雑談の会話のアーカイブ

**入れる**（2026-09-21 決定。ユーザーの指示「100ターン上限は画面上としての上限。会話そのものは
アーカイブとしては残して保存し、あとで活用できるようにあるいは設計変更に耐えられるように
したくて」）。**tsukumo が自分で、雑談の会話を受け取ったその場でディスクへ書く。**

**claude の transcript には任せない**（2026-09-21 に確かめた）。圧縮は transcript の行を消さない
（親子の鎖が切れるだけ）が、**鎖を無視して全部読む口が無い**（`getSessionMessages` のオプションは
`dir` / `limit` / `offset` / `includeSystemMessages` / `sessionStore` だけ）。そのうえ保持期間も
形式も Claude Code の都合で、`cleanupPeriodDays` の既定（30日）で古いものから消えていく。
**`cleanupPeriodDays` を延ばす案・両方やる案は採らなかった** — どちらも「設計変更に耐える」という
狙いと合わない（形式が他人の都合のままで、ユーザーのグローバル設定にも手が入る）。

**画面の上限とアーカイブは別物。** 混ぜない:

| 何               | 画面のログ                                   | アーカイブ                                                             |
| ---------------- | -------------------------------------------- | ---------------------------------------------------------------------- |
| 何のためにある   | **いま読むため**                             | **直近を逐語で読み戻すため・あとで活用するため・設計変更に耐えるため** |
| 持ち場           | 動いているプロセスのメモリ（`SessionState`） | `~/.tsukumo/` の下のファイル                                           |
| 上限             | 雑談 100 ターン（`trimToRecentTurns`）       | **持たない**                                                           |
| 圧縮・起こし直し | 圧縮点から先だけが復元される                 | **影響されない**（続きに書き足す）                                     |
| 消える契機       | プロセスが終わる・窓から溢れる               | **利用者がファイルを消したときだけ**                                   |

**残すのは雑談だけ**（仕事の会話は残さない）。この決定の文脈は雑談モードの記憶で、仕事の会話を
残す理由は出ていない。仕事の側は今までどおり**ディスクに書かない**。広げたくなったら、まず
`docs/coding-standards.md`「会話内容の扱い」の例外を1つ増やす判断からになる。

**残すのは雑談のログに乗る2種類（利用者の依頼とキャラクターのセリフ）と、セリフの表情だけ。**
指示の「その表情とセットで」をそのまま満たす（表情は同じ1件の中に持つ。`docs/design.md` 7章）。
**本文（レポート）・ツールの入力と結果・許可プロンプト・質問は書かない**（画面の雑談のログが
拾っていないものは、アーカイブにも入らない。`src/shared/chat-log.ts`）。**添えた画像そのものも
書かない** — 残すのは枚数だけで、原寸は記録にも無い（4.10）。

**書くのは届いたその場で1件ずつ。** ターンの終わりにまとめない（溜めている間にプロセスが
終わるとそのターンが丸ごと落ちる）。**`SessionState` の 100 ターンに影響されない経路で書く** —
届いたイベントから直接書き、切り詰めたあとの記録からは数えも拾いもしない
（`chatLogBytesSinceCompact` が `state.records` から数えないのと同じ理由）。
**復元で流し直されたぶんは書かない**（transcript から組み直した会話をもう一度書くと、
起こし直すたびに同じ行が積み上がる）。経路と層の切り方は `docs/design.md` 7章。

**保持期間も総量の上限も持たない。** tsukumo は自分で消さない — 「あとで活用できる」が狙いなので、
勝手に消すとその狙いを外す。歯止めは**日ごとにファイルを割ること**で、太り方が目で分かり、
消す単位も人に分かる。大きさの見積もりは、雑談の1ターンが 130〜195 バイト（「記憶の圧縮と忘却」で
測った値）に1件ぶんの枠を足して **1日20往復で 10 KiB 前後**、1年続けても数 MiB に届かない。

**消す手はファイルを消すこと**（要約の写し・「覚えたこと」と同じ考え方）。`~/.tsukumo/chat-archive/`
を消せば全部、`<パック名>/` を消せばそのキャラクターぶん、日付のファイルを消せばその日ぶんを
忘れる。**画面から消す口は作らない**（対象利用者は作者本人だけで、ファイルを直接開ける）。

**既に claude の transcript にあるぶんを遡って取り込むことはしない。** 取り込めるのは最後の
圧縮点から先だけ（鎖が切れていて、無視して読む口が無い）なので**「すべて残す」には最初から
届かない**うえ、取り込む経路は「transcript を読んでディスクへ書き出す」ことになり、**いま広げた
例外（受け取った雑談をその場で書く）より広い口**を常駐プロセスに残す。2026-10-09 ごろから古い
transcript が消え始めるが、そこで失われるのは**この機能が動き出す前の会話**だけで、以後は
取りこぼさない。

**規約との関係。** 使うのは `docs/coding-standards.md`「会話内容の扱い」の**「別の場所に複製
しない」の例外だけ**で、残る3条はそのまま満たす — **外部に送らない**（書く先は同じマシンの
ファイルで、渡す先も同じマシンで動いている claude の `systemPrompt` だけ）、**ログに全文を
出さない**（画面にも `error` フレームにも stderr にも出さない）、**テストのフィクスチャに実物を
使わない**。ブラウザ側の永続化に会話を置かないことも変わらない。

**アーカイブは直近を逐語で読み戻す唯一の出どころ**でもある（上の「直近の会話は逐語のまま
読み戻す」）。**読み戻してよいのは新しいほうから 64 KiB までで、渡す先は
雑談のセッションの `systemPrompt` だけ。** それ以外の読み戻しは今までどおり作らない。

#### プロフィールの書き戻し

**雑談でキャラクター自身の設定に関わることが決まったら、`persona.md` に1行だけ書き足す**
（2026-09-21 決定。ユーザーの指示「雑談モードで、プロフィールに関わることをやり取りしたら
persona.md を自動で更新する仕組みにしたい」）。**書き換えは自動で、事前の承認も事後の通知も
しない**（同日のユーザーの判断）。

**`docs/coding-standards.md`「会話内容の扱い」が最優先なので、書き戻してよい範囲を先に狭める。**
書いてよいのは、次の3つを**すべて**満たすものだけ:

1. **主語がキャラクター自身**（「ボクは〜」）。利用者・第三者・プロジェクト・コードの話ではない
2. **次のセッションでも同じく成り立つ属性**（好み・口調・呼び方・来歴）。その場の出来事・
   今日やったこと・進行中の作業ではない
3. **会話の文面を写していない。** キャラクターが自分の言葉で書き直した1行で、発言の引用でも
   その要約でもない

**書かないもの**（1つでも当たれば書かない）:

- **利用者について知ったこと**（名前・所属・家族・健康・予定・好み・感情・評価）。
  これは**会話から抜き出した内容をディスクに残す行為そのもの**で、規約と正面からぶつかる
- 会話の引用・要約・日時・出来事のログ
- ファイルのパス・コードの断片・プロジェクトの事情・認証情報

**この線引きなら規約と衝突しない**理由は2つ。(1) 書く先の `persona.md` は 2.2 が
**キャラクター素材**に数えた文書で、同梱パックにも「好きなもの」節が最初からある —
その欄に入る種類の情報は、もともと会話ではなく素材である。(2) 残るのは**キャラクターの属性
1行だけ**で、誰が何を言ったか・利用者が何を抱えているかは残らない。きっかけが雑談であることは
避けられないが、**会話そのものは複製されない**。

**裏返しとして、利用者のプロフィールは覚えない。** 利用者について書くことは規約の禁止の
中心にあるので、この仕組みでは扱わない。

**遅れて効くことは説明しない。** `persona.md` は `systemPrompt` の append なので、書き足した
内容が効くのは**次にセッションを起こしてから**（雑談モードへの出入り・キャラクターの切り替え）。
通知しないと決めた以上、遅れて効くことも画面には出ない。

**覚えた1行は、キャラクター自身が1行だけ忘れられる**（2026-09-21 決定。ユーザーの指示
「雑談モードで、キャラが覚えたことを自身で削除できるようにしたい。ただし、もともとのファイルに
記載してあったことは編集できず、自身で書いたことのみ対象とする」）。**消すのも自動で、事前の
承認も事後の通知もしない**（書き足すときと同じ）。**消す手がファイルを開くことしか無い**と、
取り違えて覚えた1行が「次に会うときも成り立つ属性」として残り続ける。

**消せるのは「覚えたこと」の節に自分で書き足した行だけ。** もともと `persona.md` にあった文面
（見出し・地の文・表）は消せない。**節の境目がそのまま「自分で書いたもの」の線**になるので、
どれを自分で書いたかを覚えておく仕掛けは要らない。

**消してよいのは、次のどれかに当たるときだけ:**

1. **もう成り立たなくなった**（好みが変わった・呼び方を変えた）
2. **取り違えて覚えた**（そもそも自分の属性ではなかった。上の3条件のどれかを満たしていなかった）
3. **利用者から消すよう言われた**

**消す口ができても、触れる範囲は広がらない。** 触るのは「覚えたこと」の節だけで、**会話を
読み直して判定する経路はここにも作らない** — どれを消すかを決めるのはキャラクター（モデル）で、
tsukumo 側は受け取った1行と一致する行を落とすだけ。**利用者のプロフィールを覚えない**のと同じく、
**消すために会話を保持することもしない**。

書き込み先・書き手・書き方・上限・消し方（指し方・一致しなかったとき・節が空になったとき）・
元に戻す手は `docs/design.md` 7.1。

### 4.10 画像の添付

**入れる**（2026-09-21 決定。ユーザーの指示 2026-09-20「Discordのように画像を添付できると良いね」）。
2.2 の「画像やファイルの貼り付け」（2026-09-11）のうち、**画像だけを覆した**。

#### 渡せることの裏取り

**Agent SDK には画像を渡す道がある**（2026-09-21 に型定義と公式ドキュメントで確認）。
`SDKUserMessage.message` は Messages API の `MessageParam` そのもので、`content` は文字列でも
**内容ブロックの配列**でもよい。配列に `image` ブロック（`source.type: "base64"`）を混ぜれば渡る。

**`Base64ImageSource`（`{ data, media_type, type: "base64" }`）で渡せ、形式は `image/jpeg` /
`image/png` / `image/gif` / `image/webp` の4つだけ。** **単発入力（Single Message Input）は画像を
受け付けない**ので、ストリーミング入力の側にいることが条件になる（出典の一覧は
`docs/history/decision.md`「requirements.md 4.10 画像の添付 / 渡せることの裏取り」）。

**tsukumo は最初からストリーミング入力の側にいる**（`createPromptStream` が `query` に「まだ
終わらない」非同期イテレータを渡している。4.1）。**渡し方を変えずに、`content` を文字列から
配列にするだけで済む。**

#### 受け取り方

**貼り付け（`paste`）とドロップ（`drop`）の2つだけ。ボタンは置かない**
（`docs/design.md` 13.1 原則2。枠も常設の操作子も増やさない）。どちらも**いまの `<textarea>` の
上の動作**なので、操作子が1つも増えない。**クリップボードの画像を貼るのが主な道**で、これは
`@` の補完では埋められない穴そのもの（下の「ファイルは覆さない理由」）。気づけるように、
**入力欄のプレースホルダの操作の並びに「画像は貼り付け」を足す**（置き場所は既にある1行で、
新しい説明の面は作らない）。

#### 上限

**`docs/design.md` 7.1（キャラクターパックの素材）の上限はそのままは使えない。** 向きが違い
（あちらは1つのパックが持てる総数、こちらは1件の依頼に添えられる数）、**受け付ける形式は
API 側で決まっている**。

| 何                        | 上限                                                                            |
| ------------------------- | ------------------------------------------------------------------------------- |
| 画像1枚（デコード後）     | 5 MiB（API の天井「base64 で1枚 10 MB」の内側で、スクリーンショットが収まる幅） |
| 1件の依頼に添えられる枚数 | 2 枚                                                                            |
| 控え1枚（デコード後）     | 128 KiB（長辺 320px の webp。下の「記録の大きさが有界になる」を数にしたもの）   |
| 形式                      | `.png` / `.jpg` / `.gif` / `.webp` の4つ                                        |
| WebSocket の `maxPayload` | 16 MiB（2 枚 × 5 MiB の base64 ≒ 13.33 MiB ＋ 控え2枚 ≒ 0.34 MiB ＋ 文面）      |

- **形式は tsukumo の都合ではなく API の天井。** `Base64ImageSource.media_type` が上の4つしか
  取らないので、**`.svg` は渡せない**（立ち絵は `.svg` を受け付けるが、あちらは画面に描くだけで
  モデルへは渡らない。同じ「画像の上限」に見えて別の制約）
- **枚数を 2 枚に絞ったのはリクエスト全体の天井のため。** 1枚あたりを 5 MiB まで緩めたので、
  枚数まで広いと base64 が API の 32 MB に届きうる（2 枚なら ≒ 13.3 MiB で当たらない）。
  「スクリーンショットを1〜2枚貼る」という主な使い方は 2 枚で足りる
- **`maxPayload` を上げても依頼の文面は緩まない**（`MAX_PROMPT_TEXT_LENGTH` の 20,000 文字が
  別に効いている。7.1 と同じ理屈）

#### 画面での見え方

**送る前は入力欄の中の小さな札、送ったあとは依頼に付く控え。**

- **送る前**: 添えた画像が `<textarea>` の上に**小さな札**（縮めた絵と外す `×`）で並ぶ。
  **1枚も無いときは何も出ない**ので、常設の枠にならない
- **送ったあと**: 依頼の記録（`request`）に**縮めた控え**が付き、仕事のときはメインビューの
  依頼の見出しの下に、雑談のときは利用者の発言の吹き出しの中に並ぶ（`docs/design.md` 13.7。
  LINE / Discord と同じ見え方になるのはここ）
- **札も控えも押せない。** 拡大して見る面は作らない（下のとおり原寸をもう持っていないので、
  作ろうとしても開くものが無い）

#### 会話内容の扱い（この機能の形そのもの）

**画像も会話の内容**（`docs/coding-standards.md`「会話内容の扱い」）。**この制約は注意書きではなく、
上の形の決め方そのものになっている。**

- **ディスクに書かない。** 原寸はブラウザのメモリ → WebSocket の1フレーム → サーバのメモリ →
  SDK の子プロセス、と流れるだけで、**どこにも書き出さない。一時ファイルに落とす案は採らない**
  （`src/server/adapter/` に新しい書き込み先が増え、「どこに置きいつ消すか」という問いが
  生まれる。`Base64ImageSource` で直接渡せるので、そもそも要らない）
- **原寸は送った時点で手放す。** 記録に残るのは控えだけで、tsukumo のどちらの側も原寸を
  持ち続けない。**上の「札も控えも押せない」はこの帰結**
- **控えだけを記録に残すので、記録の大きさが上限を持つ。** 原寸を `SessionState` に積むと
  雑談の 100 ターン（4.9）で数百 MiB に届きうるが、控えなら1枚あたり数十 KiB で収まる。
  **縮めるのはブラウザ側**で、サーバは受け取った控えをそのまま `request` に載せるだけ
  （**サーバは画像を加工しない**）
- **経路は既にあるものをそのまま使う。** 起動トークンと `Origin` の照合・zod の検証・定型文の
  `error` が効く WebSocket の `prompt` コマンドに足すだけで、新しい書き込み口（POST）を作らない
  （`docs/design.md` 7.1 と同じ判断）
- **Claude Code 本体が自分の transcript に何を書くかは変わらない**（`~/.claude/`。文面と同じ
  扱いで、4.8 の復元はそこを読む）。**tsukumo が新しく残す場所を作らない**、というのがここでの約束

#### ファイルは覆さない理由

**2.2 のうち覆したのは画像だけで、ファイルの貼り付けは対象外のまま。** `@` のファイル補完
（4.2 (5)）が**パスを渡す道を既に持っている**ためで、パスを渡すほうが中身を送るより素直に強い:
大きさの上限が要らず、どんな種類でも通り、Claude Code が自分の `Read` で必要なだけ読む。
**画像だけが例外なのは、クリップボードの画像にパスが無いから** — `@` で埋められない穴は
そこ1つしかない。

## 5. 実行環境・非機能要件

実装スタック: **Bun + TypeScript**（2026-09-11 に再確認。SDK は Bun を公式にサポートしており、
Electron などに載せ替えるときも Bun のプロセスを子として起こせば済む）。チェックコマンドは
`bun run check`。

実行時の依存は次のとおり:

- **`@anthropic-ai/claude-agent-sdk`**（npm パッケージ）— Claude Code を動かす。2026-09-11 に
  追加。これが唯一の本質的な実行時依存で、`claude` 本体は SDK が子プロセスとして起こす
- **`orca` コマンド**— 使うのは **`orca tab list` / `orca goto` / `orca tab create --url`（ページを箱の中に開く・開いているタブを貼り直す）だけ**。
  1つのアダプタに閉じ込め、**無ければその機能を諦めて動作を続ける**（`orca` に何ができるかの
  一覧は `docs/history/decision.md`「requirements.md 5. 実行環境・非機能要件 / Orca の使える機能」）
- **本体（立ち絵・吹き出し・レポートの整形）は外部コマンドに依存しない**
- **2026-09-13 の移行で足す npm の依存（React・`ws`・unified 一式）は承認済み**（一覧は
  `docs/design.md` 11章）。外部**コマンド**は増えない
- これ以外の実行時依存を増やすときは、ユーザーの承認を得る

開発する環境は **macOS + Orca**（第一級の環境は 2.3）。**バージョンや導入済みコマンドの一覧は
正典に持たない**（2026-09-21 決定。時間が経つと変わるので、前提にする前に**その場で確認する**。
2026-09-09 時点の実測は `docs/history/environment-2026-09-09.md`）。

**ただし「入っていないもの」は残す** — 外部コマンドを増やす提案を止める材料になるため。
2026-09-09 時点で**未導入**だったのは `tmux`, `chafa`, `viu`, `timg`, `img2sixel`, `cowsay`,
`deno`, `cargo`。これらに依存する案は、入れてよいかの承認から始まる。

非機能要件:

- **常駐プロセスは、描画1回の失敗で落ちない。** 未知のイベントが来ても、画像が読めなくても、
  `orca` コマンドが失敗しても、次の更新で復帰する。**SDK のセッションが終わったり落ちたりしても
  プロセスは生き、画面はその事実を出す**（黙って止まらない）
- **会話は tsukumo のプロセスの外へ出さない。** SDK のイベント（本文・ツールの入出力・`speak` の
  引数）にはユーザーの生の会話が入る。外部へ送らない、別の場所に複製しない、ログに丸ごと
  出さない（`docs/coding-standards.md`「会話内容の扱い」が正典）。**ビューの HTML は
  ファイルに書き出さない。** 本文はプロセスのメモリにだけ持ち、`127.0.0.1` にだけバインドした
  サーバから配る（4.2）
- 画面への反映は体感で気にならない程度（目安1秒以内）。厳密な数値目標は置かない
