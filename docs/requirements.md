## 1. 概要・目的

**tsukumo は、キャラクターと一緒に楽しく仕事をするためのターミナル環境である。**

立ち絵・吹き出し・セリフと詳細の分離・詳細ビュー・画面レイアウトは、**すべてこの目的のための
手段**であって目的ではない。**機能を足すかどうかは「この目的に沿うか」で決める**（手段の側から
「立ち絵ツールだからこれも要る」と発想しない）。

目的は2つの成分に分かれ、**どちらか一方だけでは足りない**:

- **キャラクターと一緒にいる感じがすること。** 応答が無機質なテキストの塊ではなく、
  キャラクターのセリフとして届く
- **仕事が捗ること。** 楽しさのために効率を落とさない。技術的な詳細は、セリフとは別の場所に
  人間が読みやすい形で出す

### 「ターミナル環境」とは何を指すか

**道具立てはターミナルが中心**である。作業の中心はターミナルのペインにあり、入力は Claude Code
の TUI で行う。ただしこれは**すべてをターミナルの文字で描く**という意味ではない。詳細の表示だけ
は HTML にして、**Orca 自身のブラウザタブ**に出す（4.2 / 4.7）。

境界はここに引く: **Orca のウィンドウの中で完結し、外部ブラウザ（Chrome など）へ飛ばないこと。**
一体感が壊れるのは「ターミナルの文字でないこと」ではなく「別のアプリケーションへ視線と操作が
移ること」だと確認済み（`docs/history/direction.md` 2026-09-09「詳細ペインの実体」）。

### 実現の手段

Claude Code 本体のTUIには**一切割り込まず**、別ペインで常駐するサイドカーがセッションの
transcript（JSONL）を追従して描画する。この形を採る理由は1つしかない（「3. 技術制約」）。

名前は付喪神から。長く使った道具に魂が宿るように、ターミナルという道具に姿と声を与える。
（検討時の作業名は `chara-terminal` だった。正式な名前は `tsukumo`）

## 2. スコープ

### 2.1 対象とすること

- Claude Code の transcript（JSONL）を追従し、最新の assistant 発話を取り出す
- 発話を**セリフ**と**詳細**に分離する。分離は**出力スタイル側の規約でモデルに書き分けさせ**、
  tsukumo はその規約に従って機械的に切り出す（規約の具体は「7. 未決事項」）
- 別ペインに常駐し、立ち絵＋**セリフ**を HTML のビューとして配るプロセスを提供する
- **詳細**を HTML に整形し、Orca 内のブラウザタブに出す
- 入力・セリフ・詳細・その他情報のペインを分ける画面レイアウトを組み立てる（4.7）
- hook が書き出す状態ファイルを読み、表情・衣装を切り替える
- キャラクターの素材と、表情・衣装の対応を差し替え可能にする
- 他のCLIエージェント（Codex / Gemini CLI 等）のログにも流用できる形に保つ
  （本体はただのログ tailer であり、**流用を妨げない**ことまでが対象。個別対応は対象外）

### 2.2 対象外とすること（スコープ外）

- **Claude Code 本体のTUIへの描画割り込み**。技術的に不可能（「3. 技術制約」）
- Claude Code 本体のフォーク・パッチ適用
- **Orca 以外のターミナルでの、画面レイアウトと詳細ビューの動作。** レイアウトの組み立ては
  `orca terminal split`、詳細ビューは `orca tab create --url` に依存する。他のターミナル
  （VS Code 統合ターミナル・tmux・iTerm2 など）に同等の経路を用意することはしない
- ただし**ホストに依存する操作は1つの抽象の裏に置く**。将来 VS Code など別のホストに載せ替える
  ことがあっても、差し替える場所が1箇所で済むようにする（`docs/architecture.md`
  「ホスト依存の操作は1つのポートにまとめる」）。**いま VS Code 用の実装は作らない**
- `orca` コマンドが無い環境では、**レイアウト組み立てとビューを開くことを諦めて動作を続ける**
  （起動失敗にしない。4.2 のフォールバックと同じ考え方）。引数で transcript を渡せば
  配信そのものは単体でも成立するが、**これは結果であって維持すべき要件ではない**
- **詳細の中身の要約・再構成。** 読みづらさの主因は見た目だと確認済みなので
  （`docs/history/direction.md` 2026-09-09 Q2）、整形は**見た目の範囲**に留める。
  中身を削る・並べ替える・言い換えることはしない
- 音声合成そのものの実装。VOICEVOX 連携は口パク同期の入力としてのみ検討し、後回しにする
- 会話内容の外部送信・クラウドへの保存（「5. 実行環境・非機能要件」の会話内容の扱い）。
  **分離や整形のために会話を外部のモデルへ送ることも含めて対象外**
- キャラクター素材そのものの同梱・配布。**素材は利用者が自分で用意する**。権利の扱いを
  このリポジトリに持ち込まないため
- Windows / Linux での動作保証。動けばよいが、確認するのは macOS のみ

### 2.3 想定利用者

個人利用（作者本人）。**macOS の Orca を第一級の環境とする**。

VS Code 統合ターミナルは第一級ではない。サイドカー単体は動くが、画面レイアウトと、
ビューをアプリケーションの中に開くことはそこでは成立しない（2.2）。

## 3. 技術制約

**Claude Code のTUIは自分で全画面を描画する。** ここから次が決まる:

- `claude | cowsay` のようにパイプを噛ませる方式は**不可**
- hook の stdout はエスケープされてテキスト扱いになるため、そこから ANSI エスケープや
  画像プロトコルを流し込む方式も**不可**

したがって tsukumo は**本体の描画に割り込まない**。サイドカー方式（別ペイン常駐）を採る
理由はこれ1つであり、他の方式に作り直そうとする前に必ずここを読む。採用アーキテクチャと
採らなかった案は `docs/architecture.md` が正典。

## 4. 機能要件

### 4.1 発話の取得

- transcript の場所は `~/.claude/projects/<cwd をスラッグ化したもの>/<session-id>.jsonl`
- 最新の assistant 発話は次で取り出せる（2026-09-08 に動作確認済み）:

  ```bash
  jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="text") | .text' \
    ~/.claude/projects/<slug>/<session-id>.jsonl | tail -1
  ```

- hook には `transcript_path` と `cwd` が渡る。SessionStart hook で既知の場所に書き出しておけば、
  サイドカーは**スラッグ化の規則を自前で再実装せずに**追従先を知れる。**書き出す場所は全セッション
  共通の1ファイル**なので、`cwd` も一緒に書いて「どのディレクトリのセッションか」を読む側が
  判定できるようにする
- 行の `type` 分布（2026-09-09 に907行で実測）: `attachment` / `assistant` / `user` /
  `permission-mode` / `mode` / `last-prompt` / `bridge-session` / `atis-latch` / `ai-title` /
  `system` / `file-history-snapshot` / `file-history-delta`。**assistant 以外は無視してよい**が、
  **未知の `type` が来ても落ちないこと**。後半の5つは 2026-09-08 の実測時には無かったもので、
  **この集合は増える**と実際に確かめられている
- **assistant 行の `content[]` にも複数の `type` がある**（同じ実測で `tool_use` 84 /
  `thinking` 58 / `text` 30）。**表示してよいのは `type: "text"` だけ。**
  `thinking` はモデルの内部の思考なので、表示すると事故になる
- 同じディレクトリには `<session-id>.jsonl` のほかに `<session-id>/` という**サブディレクトリ**が
  でき、その下にサブエージェントの transcript（`subagents/*.jsonl`）が入る。
  **`*.jsonl` を再帰的に拾うとサブエージェントの発話まで混ざる**ので、追従先は1ファイルに絞ること

### 4.2 表示

#### 出力の分離（セリフと詳細）

**1つの発話を「セリフ」と「詳細」に分け、別々のペインに出す。** 同じ内容が Claude Code の TUI と
tsukumo のペインに二重に出ると、入力するときに簡素なほうへ移らざるを得ず、キャラクターとの
やり取りがノイズに埋もれる（`docs/history/direction.md` 2026-09-09）。

- **分離はモデル側が行う。** 出力スタイル（`~/.claude/output-styles/asuna.md`）に規約を入れて、
  セリフと詳細を構造的に書き分けさせる。tsukumo はその規約に従って機械的に切り出すだけにする
- **tsukumo 側のヒューリスティック分類（コードブロックは詳細、地の文はセリフ等）は採らない。**
  判定が壊れやすい。**小さいモデルに分離・整形させる案も採らない**（コスト・遅延に加えて、
  会話内容を外部に送らない規約と衝突する）
  **規約（2026-09-10 改訂。正典は `~/.claude/output-styles/asuna.md`「セリフと詳細の書き分け」）**:

- **セリフは行頭のマーカー（既定は `アスナ: `）で始める。それ以外はすべて詳細。** tsukumo は
  行頭でマーカーに完全一致する行を拾うだけでよく、判定に推測が要らない。**マーカーは設定値**で、
  環境変数 `TSUKUMO_SPEECH_MARKER` で差し替えられる（キャラクターの名前を変えても追従できる）
- **引用（`> `）からマーカーに変えた**（2026-09-10）。引用は TUI で左に縦線が付いて描かれ、
  「誰かの発言を引いている」ように見えるため、キャラクターのセリフとレポート内の引用の
  区別が付かなくなった。**話者名のプレフィックスは見た目がそのままセリフの意味になる**ので、
  下の「見えていて意味が通る形を選ぶ」という判断はそのまま保てている
- **不可視のマーカーは使えない**（2026-09-09 実測）。HTMLコメント `<!-- -->`・独自タグ
  `<serif>`・引用のいずれも Claude Code の TUI にそのまま表示される。**隠すのは諦め、
  「見えていて意味が通る形」を選んだ**
- **セリフに入れるのは役割で決める**（掛け声・呼びかけ・リアクション・感想・完了報告）。
  詳細に入るのは事実・根拠・手順・コード・表・判断とその理由
- **文体はどちらもキャラクターのまま。** 詳細側も口調を落とさない。読みやすさは表示側
  （詳細ビューのレンダリングとレイアウト）で解く問題であって、人格を薄めて解かない
- **引用（`> `）はセリフではない。** レポートの中で普通の引用として自由に使える
- **コードブロック（``` で囲まれた範囲）の中のマーカー行は拾わない**
- 応答の冒頭に必ず1つセリフを置く

**規約に従っていない発話が来たときの扱い**: 吹き出しは**直前のセリフを出し続ける**。
空にするとキャラクターが消えたように見えるため。実装は「7. 未決事項」の対応タスク側。

#### 各表示物

**表示はすべて HTML である**（2026-09-09 決定。`docs/architecture.md`「表示はターミナル描画を
やめて、すべて HTML にした」）。ターミナルに文字と絵を描く経路は持たない。3つのビューは
サイドカーが持つローカルの HTTP サーバから配られ、**Orca 内のブラウザタブ**に出る。

- **立ち絵**: HTML の `<img>` で表示する。ドット絵ではなく本物の立ち絵を出せることを狙う。
  ターミナルの画像プロトコル（Sixel / iTerm inline images）は使わない
- **吹き出し**: 発話のうち**セリフ部分だけ**を、キャラビューの中に立ち絵と同居させて表示する。
  **発話の全文は出さない**（全文が2箇所に出ることが二重表示の原因だったため）。
  詳細はメインビュー側に回る。**折り返し・全角文字の幅・禁則処理はブラウザに任せる**
- **メインビュー**: 作業の進行と、発話の詳細部分を HTML に整形して出す。Markdown が素のまま
  流れることによる読みづらさ（表が桁揃えされない、コードに色が付かない、見出しが埋もれる）を、
  レンダリングで解く。**外部ブラウザには出さない**（1章）
  作業の進行として出す**ツールの実行は、利用者が見るべきものだけに絞る**（2026-09-10 決定。
  当初は引数も結果も全部出す形にしていたが、実際に使ったユーザーが「打ったBashコマンドは
  さすがにメイン画面に出さなくてよかった」と撤回した）。**出す**のはファイルを変えた操作
  （ツール名とパス）・サブエージェントの起動（タスク名）・失敗したツール（エラーの内容）の
  3種類だけで、**コマンドとその出力、読み取り・検索は出さない**。**未知のツール名は出さない側に
  倒す**（安全側）。利用者が見たいのは「何をしたか」であって「どう調べたか」ではなく、
  テストの件数やエラーといった重要な結果は発話の詳細（レポート）側に必ず書かれるので、
  ツールの実行として重複して出す必要が無い
- **配り方**: HTML は**ファイルに書き出さず**、`127.0.0.1` にだけバインドしたローカルの HTTP
  サーバからメモリのまま配る。更新は Server-Sent Events でブラウザへ押す
  （`docs/architecture.md`「HTML はローカルの HTTP サーバから配る」「ビューの更新は
  Server-Sent Events で押す」）。**会話の内容をディスクに書く経路を作らない**
- **フォールバック**: 表示できないものがあっても**残りを表示して動作を続ける**。
  立ち絵の素材が無い環境では**セリフだけを表示する**、`orca` コマンドが無い環境では
  **ビューを開かずに配信だけ続ける**。表示物が1つ欠けたことを理由に起動失敗にしない
- **タイプライター表示**と、VOICEVOX の口パク同期は後回しでよい（MVPに含めない）

### 4.3 状態連動

- **表情差分**: hook イベントで切り替える。対応の初期案は
  `PreToolUse` = 作業中 / `Stop` = どや顔 / エラー = あわあわ
- **モデル別の衣装**: `haiku` = 軽装 / `sonnet` = 通常装備 / `opus` = 戦闘配置。
  Asuna output style の「出撃時の掛け声」のモデル分岐と対応させる。
  **`model` は `SessionStart` の payload にしか載らない**（他のイベントのスキーマには無い。
  Claude Code v2.1.263 のバイナリに埋め込まれたスキーマ定義で確認）。したがって hook は
  SessionStart でだけ `model` を拾い、以降のイベントは状態ファイルの前回値を引き継ぐ。
  値の形式（短い別名か解決済みの完全なモデルIDか）は未確認なので、衣装の判定は部分一致で行う
- 表情・衣装の対応は、キャラクター定義ファイルの形式が決まるまで `src/expression.ts` に置く
  （決まったら定義ファイル側へ移す。「7. 未決事項」）
- **hook は状態ファイルを書くだけ**にし、描画はサイドカーが行う。hook の stdout からは
  何も描画できない（「3. 技術制約」）ので、状態の受け渡しはファイル経由になる

### 4.4 キャラクター定義

素材（立ち絵の画像）と、表情・衣装の対応は**宣言的な定義ファイル**で差し替え可能にする。
ハードコードしない（`docs/architecture.md` 原則4）。

**置き場所**（`characters/README.md` が使い方の正典）:

| 場所                         | 中身                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| `characters/tsukumo-spirit/` | 既定のキャラクター。**このリポジトリのために自作**したもの |
| `characters/local/`          | 利用者が自分で用意した素材。**`.gitignore` 済み**          |

**このリポジトリは公開されている。** 権利のある画像（公式絵・ファンアート等）を
コミットしないため、利用者の素材は `characters/local/` に置く
（`docs/architecture.md`「キャラクター素材はリポジトリに同梱しない」）。

**定義ファイル**（`character.json`）は次を持つ:

- `portraits`: 表情（`default` / `working` / `proud` / `flustered`）→ 画像ファイル。
  **「あるものだけ」でよく、見つからない表情は `default` に落ちる。** 1枚から始められる
- `outfitAccents`: 衣装（`default` / `light` / `normal` / `heavy`）→ 差し色。
  表情×衣装の全組み合わせぶんの画像を要求しないための仕組み

**差し色が効くのはインラインで埋め込んだ SVG だけ**（実測）。`<img>` で読み込んだ画像は
独立した文書として扱われ、ページ側の CSS 変数が届かない。ラスタ画像（PNG / GIF）を使う場合、
衣装の出し分けは表情と同じくファイルを分けることになる。

### 4.5 statusline 併走（案B・優先度低）

statusline 側にも小さいマスコットを出す。mascot-statusline をフォークし、
**hook が書く状態ファイルをサイドカーと共有**すれば二重実装にならない。

**やるかどうかの判断から始める。** 案Bは「入力ペインの中にキャラを出すことで二重表示を避ける」
ための案だったが、画面レイアウト（4.7）で**立ち絵＋セリフのペインとサイドバーが入力とは別に
確保される**ことになった。案Bが埋めようとしていた穴は、レイアウト側で既に塞がっている可能性が
ある。**入力ペインを見ているときにキャラの気配が足りないか**を実際に確かめてから決める。

いずれにせよサイドカーが動いたあとの追加機能であり、MVPには含めない。不要と判断した場合は
この節ごと落とす。

### 4.6 起動と設定

- 別ペインで常駐プロセスとして起動する。ペイン分割は **Orca の split terminal**
  （`orca terminal split`）で行い、tmux の導入は前提にしない
- 追従先の transcript は引数で渡せる。**引数だけで起動できる**ことは保つ
  （Orca が無い環境でもサイドカー単体が成立する条件。2.2）
- **引数を省略したときは、同じディレクトリで始まった新しいセッションへ自動で乗り換える。**
  Claude Code を再起動してもサイドカーを起動し直さずに済むため。**別のディレクトリのセッションには
  乗り換えない**（複数のリポジトリで claude を動かしても、見ているペインの相手を奪われない）。
  引数で渡したときは乗り換えず、その1本を追い続ける
- hook の登録先である `~/.claude/settings.json` は、**既存の hooks / statusLine 設定を
  壊さないよう追記する**（現状 orca が専有している。`develop/progress.md`「注意」参照）

### 4.7 画面レイアウト

biim システムをリスペクトした3領域にする。**領域ごとに役割を1つだけ持たせ、同じ情報が
2箇所に出ないようにする**ことが狙い。

```
┌────────────────────────────────────────┬────────┐
│ メインビュー                            │サイドバー│  ← ここまでが
│  作業の進行＋詳細（広い）                │ （狭い） │     1枚のHTML
├─────────────────────┬──────────────────┴────────┤     ＝ブラウザタブ1つ
│ キャラビュー（半分）   │                            │
│  立ち絵＋セリフ        │                            │
└─────────────────────┴───────────────────────────┘

              ＋ 入力（Claude Code の TUI）＝ターミナル
```

| 位置         | 中身                           | 対応する biim の要素 |
| ------------ | ------------------------------ | -------------------- |
| 左上（広い） | メインビュー。作業の進行＋詳細 | ゲーム画面           |
| 右上（狭い） | サイドバー。その他情報         | タイム表・チャート   |
| 左下（半分） | キャラビュー。立ち絵＋セリフ   | 立ち絵・テロップ     |
| 別ペイン     | 入力（Claude Code の TUI）     | 実況者の手元         |

**3つのビューは1枚の HTML にまとめ、CSS で領域を分ける。** ブラウザタブは1つだけになる。

**右下は空いている。** 元の構想ではそこが入力（Claude Code の TUI）だったが、ターミナルは
ページの中に入れられないので、グリッドだけが4分割の形で残っている。**この空きは、入力を
HTML 側から送り込めるようになった時点で埋まる**（4.8）。埋まれば1枚のページだけで完結し、
利用者が並べる手間はゼロになる。それまでは「ここに何か来る」と分かる形で空けておく
（畳んで広げてまた割ると、そのたびに見た目が変わるため）。

- **理由**: Orca の CLI には、**ブラウザタブをターミナルのペインのグリッドに配置する手段が
  無い**（2026-09-10、`orca agent-context --json` の全コマンドを確認。`tab` 系は
  `create` / `close` / `list` / `switch` / `show` / `profile` のみで、ペインへの配置は無い）。
  タブとペインは別の面なので、CLI から3領域を組み立てることはできない
- **1枚にまとめた利点**: 3領域の比率を**こちら側で完全に制御できる**（`orca terminal split` に
  比率フラグが無いという制約が、この3領域については関係なくなる）。利用者が手で並べるのも
  「ブラウザタブ1つ」と「claude のターミナル1つ」の2つだけで済む
- **上段と下段で縦の仕切り位置が違う。** 上段はメインが広くサイドバーが狭い、下段の左半分が
  キャラビュー。これは CSS の grid で表す
- **入力ペインとの並びは利用者が手で行う。** ここだけは自動化できない

## 5. 実行環境・非機能要件

実装スタック: **Bun + TypeScript**。チェックコマンドは `bun run check`。

外部コマンドへの依存は次の切り分けにする:

- **サイドカー本体（transcript の追従・立ち絵・吹き出し）は外部コマンドに依存しない**
  （`docs/architecture.md`「画像処理に外部コマンドを使わない（当面）」）
- **画面レイアウトの組み立てと詳細ビューは `orca` コマンドに依存する**（Orca 前提の決定による）。
  依存は1つのアダプタに閉じ込め、**`orca` が無ければその機能を諦めて動作を続ける**
- これ以外の実行時依存を増やすときは、ユーザーの承認を得る

環境の実測値（2026-09-09 時点。**時間が経つと変わるので、前提にする前にその場で確認する**）:

- macOS (Darwin 25.6.0), zsh
- ターミナル: **Orca** v1.4.194（`com.stablyai.orca`。`TERM_PROGRAM=Orca`,
  `TERM=xterm-256color`）。VS Code 統合ターミナルも手元にはあるが、第一級ではない（2.3）
- 導入済み: `bun` 1.3.8, `node` v22.13.1, `npm`, `pnpm`, `go` 1.26.5, `python3` 3.9.6,
  `jq`, ImageMagick（`magick`。**SIXEL の読み書きに対応**）, `ffmpeg`
- 未導入: `tmux`, `chafa`, `viu`, `timg`, `img2sixel`, `cowsay`, `deno`, `cargo`
- Claude Code v2.1.263 / outputStyle: `Asuna`

**2026-09-08 の記録からの差分**: `bun` は「未導入」だったが導入済みになった。ターミナルも
`TERM_PROGRAM=vscode` から `Orca` に変わっている。

### Orca の使える機能（2026-09-09 に `orca --help` で確認）

| コマンド                                      | できること                                               |
| --------------------------------------------- | -------------------------------------------------------- |
| `orca tab create --url`                       | **Orca 自身のブラウザタブ**を開く（Chrome に出ない）     |
| `orca tab list` / `goto` / `reload`           | 開いているタブの一覧・遷移・再読み込み                   |
| `orca terminal split`                         | ペインを分割する。`--command` で起動時のコマンドも渡せる |
| `orca terminal list --include-visual-layouts` | 現在のレイアウトを読む                                   |
| `orca terminal create` / `rename` / `switch`  | ターミナルの作成・タイトル設定・前面化                   |
| `orca file open`                              | Orca のエディタでファイルを開く                          |
| `orca agent-context`                          | エージェント向けの機械可読なコマンドスキーマを出す       |

**幅や比率を指定するフラグは存在しない**（`orca agent-context --json` の schema を全文検索して
確認済み）。レイアウトの比率調整をどこまで自動化するかは「7. 未決事項」。

非機能要件:

- **常駐プロセスは、描画1回の失敗で落ちない。** transcript の行が壊れていても、画像が
  読めなくても、`orca` コマンドが失敗しても、次の更新で復帰する
- **transcript にはユーザーの生の会話が入る。** 外部へ送らない、別の場所に複製しない、
  ログに丸ごと出さない（`docs/coding-standards.md`「会話内容の扱い」が正典）。
  **ビューの HTML はファイルに書き出さない。** 本文はサイドカーのメモリにだけ持ち、
  `127.0.0.1` にだけバインドしたサーバから配る（4.2）。置き場所と後始末の問題は、
  ディスクに書かないことで消えている
- 追従の遅延は体感で気にならない程度（目安1秒以内）。厳密な数値目標は置かない

## 6. 既存のものとの関係（なぜ作るのか）

2026-09-08 時点の調査結果。**同じものを作らないため**にここを残す。

- **`/buddy`** — Claude Code 本体の companion 機能。バイナリ v2.1.263 に `companion_intro`
  という内部リマインダ種別が実在するのを確認済み。入力欄の横に ASCII ペットが住み、
  10秒おきに吹き出しで喋る。18種、ユーザーIDから決定論的に生成される
- **claude-code-mascot-statusline**（TeXmeijin） — statusline に半角ブロックのピクセル絵
  マスコットを出す。11個の hook イベントで表情9状態、context 消費で毛色が赤くなる。
  **キャラパックが YAML/JSON で差し替え可能**。
  <https://github.com/TeXmeijin/claude-code-mascot-statusline>
- **VOICEVOX / ずんだもん hooks** — Stop hook で応答を読み上げる。音声のみで、絵は出ない

**空いている穴**: 「**キャラクターと一緒に仕事をする環境**」として、セリフと詳細を分けて
別々の場所に出すものは存在しない。上の3つはいずれも**本体の出力に絵か音を添える**もので、
出力そのものの見せ方を組み替えてはいない。tsukumo が埋めるのはここ。
