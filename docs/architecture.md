## 現在の実装状況

**transcript の追従と吹き出しの描画までが動いている。立ち絵はまだ無い。**
実装スタックは **Bun + TypeScript**、チェックコマンドは `bun run check`。
規約は `docs/coding-standards.md` が正典。

### 各ファイルの責務

原則2の「読む」「決める」「描く」が、そのままファイルの分かれ目になっている。

| ファイル            | 層       | 責務                                                                                  |
| ------------------- | -------- | ------------------------------------------------------------------------------------- |
| `src/transcript.ts` | 読む     | JSONL の全文から最新の assistant 発話を取り出す。壊れた行・未知の `type` は読み飛ばす |
| `src/balloon.ts`    | 決める   | 発話とペイン幅から、折り返し・切り詰め・枠付けをした行の配列を返す純粋関数            |
| `src/draw.ts`       | 描く     | `process.stdout` への書き込みとペイン幅の取得を閉じ込めるアダプタ                     |
| `src/index.ts`      | （配線） | 引数の受け取り、起動時の前提チェック、ポーリングループ、1回分の `try`/`catch`         |

- **`transcript.ts` はファイルI/Oを持たない。** 入力は文字列で、ファイルを読むのは `index.ts`。
  こうすると「読む」の中身をフィクスチャの文字列だけでテストできる
- **`balloon.ts` は `process` に触らない。** ペイン幅は引数で受け取る。ここが最も密にテスト
  されている層で、端末に依存させないことがその前提になっている
- **`draw.ts` は自動テストの対象外**（「描画は自動テストで守らない」）。テストしたくなったら、
  それは判断が「決める」側に漏れている合図

## 採用アーキテクチャ（サイドカー pane）

別ペインで常駐するプロセスが、セッションの JSONL を tail して立ち絵＋吹き出しを描く。
本体と描画が競合しないので、描画に関しては何でもできる。

```
┌─────────────────┬──────────────────┐
│ claude (本体TUI) │ tsukumo          │
│                 │  ┌────────────┐  │
│  通常の会話      │  │  立ち絵     │  │
│                 │  └────────────┘  │
│                 │  ╭────────────╮  │
│                 │  │ 最新の発話  │  │
│                 │  ╰────────────╯  │
└─────────────────┴──────────────────┘
       │                    ▲
       │ 書く                │ tail
       ▼                    │
  ~/.claude/projects/<slug>/<session-id>.jsonl
       ＋ hook が書く状態ファイル（表情・モデル）
```

データの流れは2系統ある。**どちらもファイル経由**で、tsukumo から Claude Code へ戻る経路は無い。

1. **発話**: Claude Code が transcript(JSONL) に追記する → tsukumo が tail して、最新の
   assistant 発話を吹き出しにする
2. **状態**: hook が状態ファイル（表情・モデル）を書く → tsukumo が読んで立ち絵を差し替える

追従先の transcript のパスは、SessionStart hook が既知の場所に書き出したものを読む
（下の「追従先は自前でスラッグ化せず、hookが書いたパスを読む」）。

## 新しいコードを置く場所

ディレクトリの割り当ては次のとおり。

| 置き場所      | 何を置くか                                                           |
| ------------- | -------------------------------------------------------------------- |
| `src/`        | サイドカー本体。`src/index.ts` が CLI の入口                         |
| `test/`       | テスト。`src/<相対パス>.ts` → `test/<相対パス>.test.ts` で対応させる |
| `hooks/`      | Claude Code の hook から呼ばれるスクリプト（状態ファイルを書く）     |
| `characters/` | キャラクター定義とサンプル素材                                       |

**`hooks/` は本体パイプラインから呼ばれない。** hook から実行される側なので `src/` には置かない
（`src/` に置くと「サイドカーが起動時に読むもの」と混ざる）。

置き場所の判断は次の原則で決める。**まだ存在しないディレクトリは、必要になったときに作る**
（空のディレクトリを先に切らない）。

- **原則1**: **本体の描画に割り込まない。** パイプ・hook の stdout・本体へのパッチを
  経路にしない。理由は `docs/requirements.md`「3. 技術制約」
- **原則2**: 「**読む**（transcript・状態ファイル）」「**決める**（何を、どんな表情で
  出すか）」「**描く**（端末に出力する）」を別のモジュールに分ける。「決める」は入力から
  出力への純粋な変換にでき、そこにテストを集中させられるため
- **原則3**: 端末・画像プロトコル・OSに依存するものは**1つのアダプタに閉じ込める**。
  Sixel / iTerm inline / テキストのみ、という差し替えがここだけで済むようにする
  （`docs/requirements.md` 4.2 のフォールバック要件がこの形を要求する）
- **原則4**: **キャラクターの中身をコードに書かない。** 立ち絵のパス、表情と hook イベントの
  対応、モデルと衣装の対応は定義ファイル側に置く。コードは定義を解釈するだけにする
- **原則5**: 1ファイルにまとめるか分けるかは、行数でも関数の数でもなく
  「**ファイル名が概念になっているか**」で決める。`helpers` / `utils` / `common` のような
  **置き場所を名前にしたファイルは作らない**

## 設計判断（なぜ今の形なのか）

#### パイプ・hook stdout ではなくサイドカーにした

Claude Code のTUIは自分で全画面を描画するため、`claude | cowsay` のようなパイプは成立せず、
hook の stdout もエスケープされてテキスト扱いになる。**本体の描画に割り込む経路が存在しない**
というのが出発点で、サイドカーはその制約から導かれた唯一の形である。

検討した案:

- **案A: 本体のTUIに描画を混ぜる** — 上記の理由で不可
- **案B: statusline にマスコットを出す** — 可能だが、statusline は1行しかないため
  「立ち絵＋吹き出し」にはならない。**併走機能として残す**（`docs/requirements.md` 4.5）
- **案C: サイドカー pane** — **採用**

副次的な利点として、本体のログを読んでいるだけなので Codex / Gemini CLI にも流用できる。

#### tmux ではなく VS Code の split terminal を前提にした

ペイン分割の手段として tmux が自然だが、実測環境に tmux は入っていない
（`docs/requirements.md`「5. 実行環境」）。VS Code の split terminal で代用でき、
そちらは既に手元にある。**tmux を要件にしない**ことで、導入の手間を最初の一歩から外した。

tmux を使いたくなったときも、tsukumo 側は「別ペインで起動される1プロセス」でしかないので
影響を受けない。ペイン分割の方法に依存する実装を入れないこと。

#### 追従先は自前でスラッグ化せず、hookが書いたパスを読む

transcript の場所は `~/.claude/projects/<cwd をスラッグ化>/<session-id>.jsonl` だが、
**スラッグ化の規則は Claude Code の内部仕様**であり、こちらが再実装すると本体の更新で壊れる。

hook には `transcript_path` がそのまま渡るので、SessionStart hook で既知の場所へ書き出し、
tsukumo はそれを読む。規則が変わっても壊れない。

#### hookは状態ファイルを書くだけにする

hook の stdout からは何も描画できない（技術制約）。したがって hook の仕事は
**状態をファイルに書くところまで**とし、描画の判断はすべてサイドカー側に置く。

この分担には副産物がある: statusline 併走（案B）を作るとき、**同じ状態ファイルを読めば
二重実装にならない**。hook を状態の単一の発生源にしておく理由がこれ。

#### 立ち絵が出ない環境ではテキストにフォールバックする

画像プロトコルが通るかどうかは、ターミナル・設定・接続方法（SSH越しなど）で変わる。
立ち絵が出ないことを起動失敗にすると、環境が変わるたびに使えなくなる。

**吹き出しだけでも成立する**ように作り、立ち絵は「出せたら出す」ものとして扱う。
原則3のアダプタが、この判定を1箇所に閉じ込める場所になる。

#### キャラクター素材はリポジトリに同梱しない

立ち絵の素材には権利が伴う。同梱するとリポジトリの公開可否がその権利に縛られ、
「AIまわりの実験リポジトリ」という位置づけと合わなくなる。

素材は利用者がローカルに置き、**定義ファイルからパスで参照する**（原則4）。
リポジトリにはサンプルとして、自作またはライセンスの明確なものだけを置く。

#### 画像処理に外部コマンドを使わない（当面）

立ち絵を出すのに画像デコードや量子化のライブラリは要らない、と調べて分かった:

- **iTerm2 inline images** は PNG をそのまま base64 して `ESC ]1337;File=inline=1:<base64>` で
  流すだけ。しかも `width` / `height` をセル単位で指定でき、**縮小は端末側がやる**ので
  自前のリサイズも不要
- **Sixel** に落とす必要が出た場合も、手元の ImageMagick（`magick foo.png sixel:-`）で足りる。
  専用ライブラリを入れる必要はない

そのうえで、**当面は外部コマンドに依存しない**（iTerm2 inline images の経路だけを持つ）。
ImageMagick を最初から任意依存として組み込むと、iTerm inline が通った場合に一度も実行されない
分岐がアダプタに残る。依存は「後から足す」ほうが「先に入れて剥がす」より安い。

Sixel が必要だと分かった時点で、原則3のアダプタに経路を1つ足す。フォールバックの階層は
そのとき「iTerm inline → Sixel → テキストのみ」の3段になる。

## 手で確かめること

**描画結果は自動チェックで捉えられない。** テストで守れるのは「読む」「決める」までで、
実際に端末に絵と枠が出ているかは目で見るしかない。表示に関わる変更をしたら、次を確認して
その結果を `evidence` に書く（`docs/workflow.md`「良いevidenceの書き方」）。

1. VS Code 統合ターミナルを split し、片方で `claude`、もう片方で tsukumo を起動する
2. Claude Code に何か話しかけ、**吹き出しが最新の発話に追従する**ことを見る
3. 立ち絵が表示されること。表示されない場合は、**エラーで落ちずに吹き出しだけが出ている**こと
4. ツール実行中・停止時に**表情が切り替わる**こと
5. ペイン幅を変えて、**折り返しが崩れない**こと

`evidence` には「どの環境で何を見たか」を1行で書く。

## 既知の制約・注意点

- **`~/.claude/settings.json` の hooks と statusLine は orca（`~/.orca/agent-hooks/`）が
  専有している。** 設定を足すときは既存エントリを壊さず追記する。上書きすると orca 側が
  黙って動かなくなる
- **transcript の JSONL は `type` が増えうる。** 2026-09-08 の実測では `assistant` / `user` /
  `attachment` / `mode` / `permission-mode` / `last-prompt` / `ai-title` があった。
  未知の `type` が来ても落ちないこと（知らないものは無視する）
- **transcript はユーザーの生の会話ログである。** 別の場所に複製しない、外部に送らない、
  ログに丸ごと出さない（`docs/coding-standards.md`「会話内容の扱い」）
- **画像プロトコルは、2026-09-09 時点でどちらも通っていない。** 赤い四角を iTerm2 inline
  images（`ESC ]1337;File=inline=1:<base64>`）と Sixel の両方で流すプローブを、VS Code 統合
  ターミナルと Orca で実行したが、**どちらの端末でも何も表示されなかった**。VS Code 側は
  `terminal.integrated.enableImages` が未設定（既定 `false`）だったことで説明が付くので、
  まず有効化して再確認する。Orca は素で非対応の可能性がある。詳細は
  `docs/requirements.md`「7. 未決事項」
