## 現在の実装状況

**2026-09-11 に方針を全面的に見直した**（`docs/requirements.md` 3章）。新方針（Agent SDK で
Claude Code を動かす）の核（セッション駆動・イベントの変換・`speak` ツール・答え待ちの列）は
入っていて、`bun run start` はセッションを起こし、`POST /api/prompt` で受けた依頼の結果を
3つのビューへ配る。**旧方針（transcript の追従・hook の状態ファイル・Orca 経由の入力送信）は
呼ばれなくなったが、撤去はまだ**である。画面側（入力欄の付け替え・許可と質問のボタン・
サイドバーの作り直し）も残っている。最初に着手すべきタスクは `develop/progress.md` が正典。

実装スタックは **Bun + TypeScript**、チェックコマンドは `bun run check`。
規約は `docs/coding-standards.md` が正典。

**拾うもの・捨てるもの・足すもの**（2026-09-11 の決定。「作り直し前提で始め、使えるものだけ拾う」）:

| 扱い       | もの                                                                                                                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **拾う**   | キャラクター定義（`src/character.ts`）・表情と衣装の対応（`src/expression.ts`）・レポートの HTML 化（`src/report-html.ts`）・レイアウトのページ（`src/view.ts`）・SSE 配信（`src/view-server.ts`） |
| **捨てる** | transcript の追従と乗り換え（`src/transcript.ts` / `src/transcript-target.ts`）・hook と状態ファイル（`hooks/state.sh` / `src/state.ts`）・Orca 経由の入力送信とキー送信                           |
| **足す**   | セッション駆動（SDK を起こし、イベントを内部の型に変える）・`speak` の MCP サーバ・入力と回答を受ける HTTP API                                                                                     |

### 各ファイルの責務

原則2の「受け取る」「決める」「描く」が、そのままファイルの分かれ目になっている。

| ファイル                | 層           | 責務                                                                                   |
| ----------------------- | ------------ | -------------------------------------------------------------------------------------- |
| `src/session-event.ts`  | 受け取る     | SDK のメッセージを内部イベント（判別可能な union）に変換する。知らない種別は無視する   |
| `src/pending-answer.ts` | 受け取る     | `canUseTool` に届いた許可要求・質問を積み、画面が答えるまで Promise を保留する         |
| `src/session-driver.ts` | （アダプタ） | SDK でセッションを起こし、入力・中断・許可の応答を渡す。**SDK を呼ぶのはここだけ**     |
| `src/session-view.ts`   | 決める       | 内部イベントを畳み込んで、いま画面に出す中身（セリフ・表情・記録・ツール名）を決める   |
| `src/transcript.ts`     | 読む         | JSONL の全文から最新の assistant 発話を取り出す。壊れた行・未知の `type` は読み飛ばす  |
| `src/state.ts`          | 読む         | hook が書いた状態ファイルの JSON を検証し、イベント種別とモデル名を取り出す            |
| `src/expression.ts`     | 決める       | モデル名 → 衣装を決める。未知・欠落は既定に落とす（イベント種別 → 表情は役目を終えた） |
| `src/view.ts`           | 決める       | ビューの識別子・URL の経路と、配る HTML を組み立てる純粋関数                           |
| `src/view-server.ts`    | 描く         | 127.0.0.1 の HTTP サーバ。本文をメモリに持ち、更新を Server-Sent Events で押す         |
| `src/host.ts`           | （ポート）   | ホストに頼む操作の型。ペインを開く／ビューを見せる。特定のホストの語彙を入れない       |
| `src/orca-host.ts`      | （アダプタ） | `src/host.ts` を Orca の CLI で実装する。**`orca` を呼ぶのはここだけ**                 |
| `src/index.ts`          | （配線）     | 環境変数の受け取り、起動時の前提チェック、今の姿を1つ持つこと、1回分の `try`/`catch`   |
| `hooks/state.sh`        | （hook）     | Claude Code の hook から呼ばれ、状態ファイルと transcript パスを書く                   |
| `scripts/open-views.ts` | （道具）     | 配信中のビューをホストの中に開く。tsukumo 本体からは呼ばれない                         |

- **`transcript.ts` はファイルI/Oを持たない。** 入力は文字列で、ファイルを読むのは `index.ts`。
  こうすると「読む」の中身をフィクスチャの文字列だけでテストできる
- **`view.ts` は `process` にも `node:http` にも触らない。** 折り返し・全角文字の幅・禁則処理は
  ブラウザがやるので、ここが決めるのは中身だけ。純粋関数なので密にテストできる
- **`hooks/state.sh` は Bun を起動しない。** `PreToolUse` は毎回のツール実行で発火するので、
  数十msの起動コストを毎回払わない。`sh` と `sed` だけで完結させ、実行時の外部コマンド
  依存も増やしていない
- **`view-server.ts` はテストする。** 「描く」層だが、配った結果を HTTP で外から観測できるので、
  バインド先・経路・push は自動で守れる。目視でしか確かめられないのは**ブラウザに出た絵**の側
- **`orca-host.ts` は自動テストの対象外。** 実際に Orca が動いていないと結果を確かめられない。
  ここに判断を書きたくなったら、それは「決める」側に置くべきものが漏れている合図

`transcript.ts` / `state.ts` / `hooks/state.sh` と、`orca-host.ts` の `openPane` /
`sendText` / `pressKey` は 2026-09-11 の方針転換で役目を終えた。**呼ばれなくなっただけで、
撤去はまだ**（後続タスク）。

- **`session-event.ts` は SDK の型を import しない。** 依存を `session-driver.ts` の1ファイルに
  閉じるため、届くメッセージは `unknown` で受けて検証する（外部由来の値なので、どのみち構造は
  信用しない）。おかげで変換のテストは SDK を起動しない
- **`session-view.ts` は純粋な畳み込み。** 状態（今の姿）を持つのは `index.ts` だけで、
  「イベント1件でどう変わるか」はすべてここのテストで守れる
- **`speak` のセリフは MCP の handler ではなく `assistant` メッセージの変換から取り出す。**
  handler は `"ok"` を返すだけにして、イベントの流れを1本に保つ

## 採用アーキテクチャ

tsukumo は**1つのプロセス**で、Agent SDK（`@anthropic-ai/claude-agent-sdk`）で Claude Code を
子プロセスとして起こし、受け取ったイベントを HTML のビューに変えて、箱（Orca のタブ）の中の
ブラウザへ配る。**Claude Code の TUI は開かない**ので、利用者が見るのは tsukumo の画面だけになる。

```
┌────────────────────────────────────────────────┐
│ ブラウザ（Orca のタブ）                        │
│   メインビュー：レポート                       │
│   キャラビュー：立ち絵＋セリフ                 │
│   サイドバー：進行・タスク一覧・セッション情報 │
│   入力欄：依頼・送信・中断・回答・答え待ちの箱 │
└────────────────────────────────────────────────┘
      ▲                       │
      │ SSE で押す            ▼ POST（依頼・回答・中断）
┌────────────────────────────────────────────────┐
│ tsukumo（Bun の1プロセス）                     │
│   ビューサーバ 127.0.0.1:7327                  │
│   セッション駆動（SDK の query）               │
│   speak ツール（プロセス内の MCP サーバ）      │
└────────────────────────────────────────────────┘
      │ 起動・追加入力・中断  ▲
      ▼                       │ イベント（本文 / ツール / canUseTool）
┌────────────────────────────────────────────────┐
│ Claude Code（SDK が起こす子プロセス）          │
└────────────────────────────────────────────────┘
```

データの流れは3本ある。

1. **入力欄 → `query`**: 入力欄に打った依頼を POST で受け、ストリーミング入力モードの `query` へ
   追加入力として流す。中断も同じ経路（SDK の中断を呼ぶ）
2. **イベント → 各ビュー**: `assistant` のテキストは**レポート**（メインビュー）、`speak` の
   引数は**セリフと表情**（キャラビュー）、`tool_use` / `tool_result` は**進行**（サイドバー）。
   更新は Server-Sent Events でブラウザへ押す（下の「ビューの更新は Server-Sent Events で押す」）
3. **`canUseTool` → 答え待ち → ボタン → 回答**: 許可プロンプトと `AskUserQuestion` はどちらも
   `canUseTool` に届く。tsukumo は答え待ちの状態にして**入力欄の上**にボタンを出し（2026-09-11
   決定。キャラは吹き出しで聞くだけ）、押された結果を `canUseTool` の戻り値として SDK へ返す

**外へ出る経路は作らない。** SDK は claude を子プロセスとして起こすだけ、`speak` は tsukumo の
プロセス内の MCP サーバ（戻り値は `"ok"` だけ）、ビューは `127.0.0.1` にだけバインドする。
**会話は tsukumo のプロセスの外へ出さない**というのが、旧方針の「tsukumo から Claude Code へ
戻る経路は無い」に代わる原則である（`docs/coding-standards.md`「会話内容の扱い」）。

**上の図は3者の関係だけを取り出したもの**で、実際の画面はメインビュー・キャラビュー・
サイドバー・入力欄の4領域が**1枚のページ**に入る（`docs/requirements.md` 4.7 が正典）。

## 新しいコードを置く場所

ディレクトリの割り当ては次のとおり。

| 置き場所      | 何を置くか                                                              |
| ------------- | ----------------------------------------------------------------------- |
| `src/`        | tsukumo 本体。`src/index.ts` が CLI の入口                              |
| `test/`       | テスト。`src/<相対パス>.ts` → `test/<相対パス>.test.ts` で対応させる    |
| `hooks/`      | Claude Code の hook から呼ばれるスクリプト（2026-09-11 に役目を終えた） |
| `characters/` | キャラクター定義とサンプル素材                                          |
| `scripts/`    | 開発・調査用のスクリプト。本体から呼ばれない                            |

**`scripts/` は本体から呼ばれない調査用の道具置き場**（端末の実測幅を測るプローブなど）。
`src/` に混ぜると「tsukumo が動くのに必要なもの」と区別がつかなくなる。

**`hooks/` は本体パイプラインから呼ばれない。** hook から実行される側なので `src/` には置かない
（`src/` に置くと「tsukumo が起動時に読むもの」と混ざる）。

置き場所の判断は次の原則で決める。**まだ存在しないディレクトリは、必要になったときに作る**
（空のディレクトリを先に切らない）。

- **原則1**: **Claude Code の TUI を使わない。** TUI には割り込めないので、パイプ・hook の
  stdout・本体へのパッチを経路にせず、SDK で動かす側に回る。理由は
  `docs/requirements.md`「3. 技術制約」
- **原則2**: 「**受け取る**（SDK のイベント）」「**決める**（何を、どんな表情で出すか）」
  「**描く**（HTML にしてブラウザへ配る）」を別のモジュールに分ける。「決める」は入力から
  出力への純粋な変換にでき、そこにテストを集中させられるため
- **原則3**: ホスト（ターミナル環境）・外部コマンド・OSに依存するものは
  **1つのアダプタに閉じ込める**。ホストが Orca から別のものに変わっても、差し替えが
  ここだけで済むようにする（下の「ホスト依存の操作は1つのポートにまとめる」）
- **原則4**: **キャラクターの中身をコードに書かない。** 立ち絵のパス、表情と hook イベントの
  対応、モデルと衣装の対応は定義ファイル側に置く。コードは定義を解釈するだけにする
- **原則5**: 1ファイルにまとめるか分けるかは、行数でも関数の数でもなく
  「**ファイル名が概念になっているか**」で決める。`helpers` / `utils` / `common` のような
  **置き場所を名前にしたファイルは作らない**

## 設計判断（なぜ今の形なのか）

#### Claude Code の TUI を捨て、SDK で動かす

**2026-09-11 の方針転換。** それまでは TUI をそのまま使い、別ペインの常駐プロセスが transcript を
追従して覗き見ていた。一式動くようにはなったが、**合格シーンに構造的に届かない**ことが分かった
（「1コマンドで起動すると1つの画面が開く。…**Claude Code の TUI は一度も見ない**」。
`docs/requirements.md` 1章）。TUI が画面に残る限り同じ内容が2箇所に出て、入力は簡素なほうへ移る。
加えて**Orca はエージェント端末への合成入力を弾く**（2026-09-11 実測。`orca terminal send` は
`agent_prompt_blocked`、`orca keypress` は前面のペインにしか届かず、前面にしても入らなかった）
ため、**画面から答えることすらできなかった**。

検討した案:

- **案A: PTY を自前で持ち、その中で TUI を動かして画面に埋め込む** — **採らない**。TUI の
  二重表示が残る（キャラの吹き出しと TUI が同じことを言う）うえ、キー入力を合成する壊れやすい
  層が増える。実験までは通したが、方針転換で不採用にした
- **案B: headless CLI（`claude -p --input-format stream-json`）** — **採らない**。**中断ができず**、
  `--permission-prompt-tool` が手元の版（v2.1.x）に無い
- **案C: Agent SDK（`@anthropic-ai/claude-agent-sdk`）で動かす** — **採用**。会話・ツール実行・
  許可・質問が構造化イベントで届き、ストリーミング入力モードで追加入力と中断ができる。
  スキル・`.claude/commands`・hook・MCP もそのまま使える（一次情報で確認済み。
  `docs/requirements.md` 3章）

**代償**: 「本体のログを読んでいるだけなので Codex / Gemini CLI にも流用できる」という副次的な
利点は消えた。汎用のログ tailer ではなく、Claude Code に固有の駆動役になる。目的は
「キャラクターと一緒に楽しく仕事をする」ことであって汎用性ではないので、これは払ってよい。

#### セリフはテキストの規約ではなく、ツール呼び出しで受け取る

セリフ（吹き出し）とレポート（メインビュー）の分離を、**出力スタイルの文章の規約**で表そうと
して**3回書き直した**:

1. 引用 `> `（2026-09-09）— TUI で左に縦線が付き、レポート内の普通の引用と区別が付かなくなった
2. 行頭マーカー `アスナ: `（2026-09-10）— 見た目がそのまま意味になるのは良かったが、
   「地の文の中でユーザーに語りかけている部分」が漏れた
3. 役割で決める条項の追加（同日）— **それでも揺れた**

不可視のマーカー（HTMLコメント・独自タグ）は TUI にそのまま表示されるので、そもそも使えない。
**規約は「守られたかどうか」がこちら側から分からない**のが根本で、条項を足しても揺れは減らない。

`speak(text, expression)` を tsukumo 側の MCP ツールとして提供すれば、**呼ばれた事実そのものが
分離**になる。引数に表情も入るので、状態ファイルを介さずに顔が決まる（`docs/requirements.md` 4.3）。

**戻り値は `"ok"` だけにする。** ツールの結果はモデルの文脈に戻るので、ここに情報を載せると
tsukumo からモデルへの逆流路ができてしまう。逆流させないことを戻り値の形で示す。

**行頭マーカーは補助として残す**（環境変数で差し替え可能）。`speak` が呼ばれなかったターンで
吹き出しが空になると、キャラクターが消えたように見えるため。

#### 箱（Orca のタブ）と中身（Web アプリ）を分ける

画面を出す入れ物を「箱」と呼ぶ。**いまの箱は Orca のブラウザタブ**で、開くのに
`orca tab create --url` を使う。ページそのものは**どの箱でも動く Web アプリ**として作り、
箱に依存する操作はホストのポート（`src/host.ts`）の裏に置く（下の「ホスト依存の操作は
1つのポートにまとめる」）。

TUI を捨てたことで、**Orca に頼む仕事は `showView`（ページを箱の中に開く）1つだけ**になった。
ペイン分割も、ターミナルへの文字送信・キー送信も要らない。**Orca 固有の機能への依存が最小に
なったので、箱の差し替えは現実的な選択肢**として残る。

**最終形は「使い勝手が上がるなら」Electron などのスタンドアロン**（2026-09-11 のユーザーの決定）。
判断は縦1本が動いて実際に使ってからで（`docs/requirements.md`「7. 未決事項」）、いまは Orca の
タブのまま進める。Bun を選び続けるのもこれに効く（Electron に移るときは Bun のプロセスを子として
起こせばよい）。

#### 外部ライブラリは CDN から読まず、同梱して自分で配る

レポートに図・グラフ・コードの色付けを入れるため、外部ライブラリ（highlight.js / mermaid /
Chart.js）を使うことにした（2026-09-10 のユーザーの決定。2026-09-11 の方針転換でも
**リッチな表示は残す**と決まっている）。ただし**CDN から読む形は採らない**。

このページは**会話の内容を持っている**（`docs/coding-standards.md`「会話内容の扱い」）。
外部スクリプトはそのページの中身を読めるうえ、表示のたびに外部へリクエストが飛ぶ。
`vendor/` に置いてローカルの HTTP サーバ（`127.0.0.1`）から配れば、**機能はそのまま・
表示時の外部通信はゼロ**にできる。配る名前は allowlist の対応表で、リクエストのパスから
ファイル名を組み立てない（`..` で外へ出る経路を作らない。`src/view-server.ts`）。

**大きいものは使うときだけ読む。** mermaid は 3.2MB あるので、レポートが実際に mermaid の
コードブロックを書いたときにだけ `<script>` を足す（Chart.js も同じ）。常に読むのは 118KB の
highlight.js だけ。

#### パイプ・hook stdout ではなくサイドカーにした

> **この判断は 2026-09-11 の方針転換で役目を終えた。** 経緯として残す（以下は当時の記述）。

Claude Code のTUIは自分で全画面を描画するため、`claude | cowsay` のようなパイプは成立せず、
hook の stdout もエスケープされてテキスト扱いになる。**本体の描画に割り込む経路が存在しない**
というのが出発点で、サイドカーはその制約から導かれた唯一の形である。

検討した案:

- **案A: 本体のTUIに描画を混ぜる** — 上記の理由で不可
- **案B: statusline にマスコットを出す** — 可能だが、statusline は1行しかないため
  「立ち絵＋吹き出し」にはならない。**併走機能として残す**（`docs/requirements.md` 4.5）
- **案C: サイドカー pane** — 当時は採用。2026-09-11 に案D（SDK で動かす）へ移った

副次的な利点として、本体のログを読んでいるだけなので Codex / Gemini CLI にも流用できる
（この利点は方針転換で失われた）。

#### ペイン分割は Orca を前提にした（VS Code の split terminal から乗り換えた）

> **この判断は 2026-09-11 の方針転換で役目を終えた。** 経緯として残す（以下は当時の記述）。

**当初の判断（2026-09-08）**: ペイン分割の手段として tmux が自然だが、実測環境に tmux は
入っていなかった。VS Code の split terminal で代用でき、そちらは既に手元にあったので、
**tmux を要件にしない**ことで、導入の手間を最初の一歩から外した。

**覆した理由（2026-09-09）**: 「詳細を人間に読みやすく出す」要求が入り、その手段が
**HTML のレンダリング**に決まった。ただし外部ブラウザ（Chrome）へ飛ぶと一体感が壊れるため、
**アプリケーションの外に出さずに HTML を出せること**が新たな条件になった。実測環境の
ターミナルは既に Orca に変わっており、Orca は `orca tab create --url` で**自身のブラウザタブ**
を開けるうえ、`orca terminal split` でペイン分割もできる。**詳細ビューとペイン分割を同じ道具で
賄えるのは Orca だけ**なので、第一級の環境を VS Code 統合ターミナルから Orca に移した
（`docs/requirements.md` 2.3 / 4.7、`docs/history/direction.md` 2026-09-09
「詳細ペインの実体」「Orca 依存と画面レイアウトの決定」）。

**当初の結論のうち「tmux を要件にしない」はそのまま残る。** 変わったのは代用先が
VS Code から Orca になったことだけで、tmux を導入する理由は今も無い。

**それでもサイドカー本体はペイン分割の方法に依存させない。** tsukumo は「別ペインで起動される
1プロセス」でしかなく、追従先を引数で受け取れる限り Orca が無くても単体で動く
（`docs/requirements.md` 2.2）。`orca` コマンドを呼ぶのは**レイアウト組み立てと詳細ビューの
アダプタだけ**に閉じ込める（原則3）。ペイン分割の手段がまた変わっても、影響はそこで止まる。

#### 追従先は自前でスラッグ化せず、hookが書いたパスを読む

> **この判断は 2026-09-11 の方針転換で役目を終えた。** 経緯として残す（以下は当時の記述）。

transcript の場所は `~/.claude/projects/<cwd をスラッグ化>/<session-id>.jsonl` だが、
**スラッグ化の規則は Claude Code の内部仕様**であり、こちらが再実装すると本体の更新で壊れる。

hook には `transcript_path` がそのまま渡るので、SessionStart hook で既知の場所へ書き出し、
tsukumo はそれを読む。規則が変わっても壊れない。

**追従先は起動時に固定せず、ポーリングのたびに読み直して乗り換える**（2026-09-10）。
Claude Code を再起動すると transcript は別のファイルになり、古いほうは更新が止まる。起動時に
決めたきりだと、ビューは**終わったセッションを映したまま黙って止まる**（サイドカーもビューも
正常に動いているので、失敗の兆候が出ない）。

乗り換えの条件は**セッションの cwd がサイドカーの cwd と同じか、その配下にあること**。
hook は `transcript_path` と一緒に `cwd` も書き（`hooks/state.sh`）、読む側が自分と無関係な
セッションを弾く（`src/transcript-target.ts`）。**引数でパスを渡して起動したときは乗り換えない**
（特定のセッションを見張り続けるための逃げ道）。

**追従先ファイルはセッションの cwd ごとに分ける**（`~/.tsukumo/targets/<cwd のスラッグ>`。
2026-09-11）。最初は全セッション共通の1ファイルにしていたが、**別のリポジトリで claude を
起動しただけで上書きされ、元のディレクトリではサイドカーが起動すらできなくなった**（実際に
踏んだ）。ファイルを分ければ互いに奪い合わない。読む側は `targets/` を全部読み、**自分の cwd に
属するもののうちいちばん新しいもの**を採る。**ファイル名は判定に使わない**（スラッグ化の規則を
読む側が信用しないため。判定は中身の `cwd`）。

#### hookは状態ファイルを書くだけにする

> **この判断は 2026-09-11 の方針転換で役目を終えた。** 経緯として残す（以下は当時の記述）。

hook の stdout からは何も描画できない（技術制約）。したがって hook の仕事は
**状態をファイルに書くところまで**とし、描画の判断はすべてサイドカー側に置く。

この分担には副産物がある: statusline 併走（案B）を作るとき、**同じ状態ファイルを読めば
二重実装にならない**。hook を状態の単一の発生源にしておく理由がこれ。

#### 表示物が1つ欠けても起動失敗にしない

立ち絵の素材が置かれていない、`orca` が入っていなくてビューを開けない、といったことは起こる。
**そのたびに起動失敗にすると、環境が変わるだけで使えなくなる。**

セリフだけでも成立するように作り、立ち絵・ホスト連携は「できたらやる」ものとして扱う
（`docs/requirements.md` 4.2「フォールバック」）。**ホストのポートが失敗を例外ではなく
戻り値で返すのは、この方針を型で示すため。**

#### キャラクター素材はリポジトリに同梱しない

立ち絵の素材には権利が伴う。同梱するとリポジトリの公開可否がその権利に縛られ、
「AIまわりの実験リポジトリ」という位置づけと合わなくなる。

素材は利用者がローカルに置き、**定義ファイルからパスで参照する**（原則4）。
リポジトリにはサンプルとして、自作またはライセンスの明確なものだけを置く。

#### ホスト依存の操作は1つのポートにまとめる

Orca に全面的に依存してよいが、**ホスト（ターミナル環境）に依存する操作は1つのポートの裏に
置く**。ポートは `src/host.ts`、アダプタは `src/orca-host.ts`。今あるのは次の2つ:

- **ペインを開く**（`openPane`）— 今のペインの横／下に、コマンドを起動した新しいペインを作る
- **ビューを見せる**（`showView`）— URL のビューが無ければ開き、あればその内容を最新にする

**「開く」と「更新する」を1つの操作にしてある。** 分けると呼び出し側が「今どちらの状態か」を
覚えることになり、その状態はホスト側の都合（タブが閉じられた等）でいつでも古くなる。
同じ URL で何度呼んでもビューが1つになる形にして、判断をアダプタの中に閉じた。

**2026-09-11 の方針転換で、残るのは `showView` だけになった。** TUI を開かなくなったので
`openPane` は要らない（ターミナルへの文字送信・キー送信も同じく消えた）。**ホストに頼む仕事が
1つしかないこと**が、箱を差し替えられるという主張の裏付けになっている
（上の「箱（Orca のタブ）と中身（Web アプリ）を分ける」）。

アダプタは**当面 Orca の1つだけ**を作る。VS Code 用の実装は**作らない**。

**これは `.claude/skills/codebase-design` の「アダプタが1つならそれは仮説上のシーム。
アダプタが2つなら本物のシーム」に反する。** 意図的に外している。理由は、**ユーザーが2つ目の
ホスト（VS Code）を実際に見込んでいる**と明言しているため。あの戒めが防ごうとしているのは
「誰も求めていない差し替えのために間接化を積むこと」であって、ここはその状況ではない。

ただし戒めの趣旨は守る。**ポートは「ホストに何をしてほしいか」だけを表し、Orca の語彙
（`terminal split` のフラグ名、タブの概念）をインターフェースに漏らさない。** 漏らすと、
2つ目のアダプタを書くときに結局インターフェースごと直すことになり、ポートを置いた意味が消える。

具体的には、ポートに現れるのは**ペイン・配置（横／下）・ビュー・URL**だけで、`tab` も
`--direction horizontal|vertical` も出てこない。`horizontal` が左右で `vertical` が上下、
という Orca 固有の対応はアダプタの中だけで解決する
（ポート側は `beside` / `below` という、見た目の位置そのものを言う語にした）。

**失敗を例外にしない**のもポートの形の一部。`orca` が入っていない環境ではその操作を諦めて
動作を続けるのが要件（`docs/requirements.md` 4.2）なので、成否を戻り値で返す。

**ポートを置く範囲を広げない。** transcript の読み取り・吹き出しの組み立て・立ち絵の描画は
ホストに依存しないので、ポートの外に置く。

#### 表示はターミナル描画をやめて、すべて HTML にした

**当初の判断（2026-09-08）**: 立ち絵は端末の画像プロトコル（iTerm2 inline images / Sixel）で、
吹き出しは端末に枠線を書いて描く。そのために折り返し・切り詰め・全角文字の幅・枠付けを
自前で持っていた（`src/balloon.ts` / `src/draw.ts`）。

**覆した理由（2026-09-09）**: 「ターミナルにこだわるより、キャラと一緒に仕事できる状況が重要」
というのがユーザーの判断（`docs/history/direction.md` 2026-09-09（3））。表示をすべて HTML に
一本化した。これで次が一度に解ける:

- **折り返し・全角文字の幅・禁則処理をブラウザがやる。** 自前の幅計算とその周りのバグが消える
- **立ち絵が `<img>` になる。** どの端末でも画像プロトコルが1つも通らないという詰まり
  （2026-09-09 の実測）が、そもそも関係なくなる
- **レイアウトを CSS で書ける。** 端末のセル単位の制約から出られる

**捨てたもの**: `src/balloon.ts`（折り返し・切り詰め・枠付け）と `src/draw.ts`（端末への
書き出しとペイン幅の取得）、およびそれらを実測するための `scripts/` のプローブ。
**残したもの**: `src/transcript.ts` / `src/state.ts` / `src/expression.ts`。これらは
表示方法に依存しない。

**画像プロトコルの調査結果はもう参照しない。** iTerm2 inline images も Sixel も、
ImageMagick を後から足すかどうかの検討も、`<img>` になった時点で判断そのものが不要になった。

#### HTML はローカルの HTTP サーバから配る（ファイルに書き出さない）

検討した案:

- **案A: HTML をファイルに書き出して `file://` で開く** — **採らない**
- **案B: 127.0.0.1 のローカル HTTP サーバから配る** — **採用**

決め手は**会話内容の扱い**（`docs/coding-standards.md`）。案Aはビューの中身、つまり発話の一部を
**平文でディスクに残す**ことになり、「別の場所に複製しない」と正面から衝突する。案Bなら本文は
プロセスのメモリにしか無く、プロセスが終われば消える。**発話を含む HTML をファイルに書き出す
経路をコードに作らない**のは、この判断がそのまま制約になっているため。

副次的な理由が2つある。後段で**入力を claude に送り込む**ことが決まっており、そのときサーバは
どのみち要る（`docs/history/direction.md` 2026-09-09 Q6）。**2026-09-11 にこれは前提になった**:
入力欄・許可の回答・中断がすべてこのサーバへの POST で届く。また `file://` のページは
Server-Sent Events の接続元として扱いが悪く、更新の押し込みが素直に書けない。

**サーバは `127.0.0.1` にだけバインドする。** 会話の一部を平文で配るので、同じマシンの外からは
届かないことが前提になっている。`0.0.0.0` に変えない。

ポートは既定を固定（7327）にした。ブラウザのタブは URL で開きっぱなしになるので、
tsukumo を起動し直すたびにポートが変わると、開いていたタブが全部死ぬ。空きを探して
番号がずれるより、**塞がっていたら起動時に失敗する**ほうが原因が分かりやすい
（起動時の前提不足なので即時終了してよい。`docs/coding-standards.md`「エラーハンドリング」）。
`TSUKUMO_VIEW_PORT` で変えられるようにしてあり、`0` を渡すと空きポートを使う。

#### ビューは1枚のページにまとめる

メインビュー・キャラビュー・サイドバー・入力欄を**1枚の HTML にまとめ、CSS の grid で領域を
分ける**。ブラウザタブは1つだけになる（**2026-09-11 の方針転換で入力欄が加わり、
ターミナルのペインは1つも要らなくなった**。`docs/requirements.md` 4.7）。

**当初は3つを別々のビューとして開き、`orca terminal split` でペインを組み立てるつもりだった。
これは成立しない。** 実際に組み立てを実行したところ、ビューは**ブラウザタブとして開くだけ**で、
ターミナルのペインのグリッドには入らなかった（2026-09-10、ユーザーの実機で確認）。

原因を Orca のコマンドスキーマ全件で確かめたところ、**ブラウザタブをペインのグリッドに配置する
コマンドが存在しない**。`tab` 系は `create` / `close` / `list` / `switch` / `show` / `profile` のみ。
`terminal split` はターミナル同士を割るもので、タブは対象外。**タブとペインは別の面**であり、
CLI から両者を1つのレイアウトに組むことはできない（UI 上で手で並べることはできる）。

1枚にまとめると、**3領域の比率をこちら側で完全に制御できる**。`orca terminal split` に比率を
指定するフラグが無いという制約は、この3領域については関係がなくなる。利用者が手で並べるのも
「ブラウザタブ1つ」と「claude のターミナル1つ」の2つだけになる。

**代償**: 領域を別々のウィンドウ（別モニタなど）に分けることはできなくなる。今の構想では不要と判断した。

#### ビューの更新は Server-Sent Events で押す

検討した案:

- **案A: ブラウザ側が一定間隔でポーリングして再読み込みする** — 採らない
- **案B: Server-Sent Events でサーバから押す** — **採用**
- **案C: WebSocket で双方向につなぐ** — 今は採らない

**押す側が既に情報を持っている**、というのが決め手。更新のきっかけは SDK から届くイベントで、
それを受け取るのは tsukumo 自身である（旧方針では transcript の変化だった）。ポーリングに
すると、間隔ぶんの遅延と、変化が無いときの無駄な再読み込みの**両方**を払うことになる。
反映の遅延目安は1秒以内（`docs/requirements.md` 5章）なので、間隔を詰めるほど無駄が増える側の
設計になる。

**ページ全体を再読み込みしない**ことも効く。レポートは書きかけの本文がリアルタイムに流れる
場所になり、入力欄には打ちかけのテキストが入っている。更新のたびに読み込み直すとスクロール
位置も入力中の文字も飛ぶ。SSE なら本文だけを差し替えられ、もっと細かい差分に変えたくなっても
経路はそのまま使える。

**WebSocket ではなく SSE**にしたのは、更新が**サーバ → ブラウザの片方向**しか無いため。
`EventSource` はブラウザ標準で再接続まで自前で持っており、サーバ側は `node:http` だけで
書けて依存が増えない。**上り方向（依頼・回答・中断）は普通の POST で足りる**ので、
2026-09-11 に入力を受け取るようになってもこの判断は変わらない。WebSocket が要るのは、
1つのリクエストの中で双方向にやり取りしたくなったときでよい。

## 手で確かめること

**ブラウザに出た絵は自動チェックで捉えられない。** テストで守れるのは「受け取る」「決める」と、
配信そのもの（バインド先・経路・push）まで。表示に関わる変更をしたら、次を確認して
その結果を `evidence` に書く（`docs/workflow.md`「良いevidenceの書き方」）。

**配信側が疑わしいときは、ブラウザを開く前に `curl` で切り分ける。** 起動時にビューの URL が
表示されるので、`curl <URL>` で HTML が返るか、`curl -N <URL>/events/...` に `event: update` が
流れてくるかを見る。ここまで出ていれば配信はシロで、原因はページの側かホストの側にある。

1. Orca のターミナルで `bun run start` を1つ起動する（Claude Code の TUI は開かない）
2. **tsukumo 自身がレイアウトページのタブを開く**ので、それが**Orca 内のブラウザタブ**に
   出ること（外部ブラウザに出ないこと）を見る。タブだけ閉じてしまったときは
   `bun run scripts/open-views.ts <URL>` で開き直せる
3. **画面の入力欄から依頼を打つ**。送信できること、実行中に中断できること
4. **再読み込みなしに**吹き出しにセリフが出て、メインビューにレポートが流れること
5. ツールを使う依頼で、**サイドバーに進行が出て、表情が「作業中」に切り替わる**こと
6. 許可の要る操作を頼み、**右下の入力欄の上にボタンが出て、枠の色とタブのタイトルが変わり、押すと
   作業が続く**こと
7. ウィンドウの幅を変えて、**折り返しがブラウザ側で追従する**こと
8. `orca` が使えない状況を作っても、プロセスが落ちずに配信を続けること

`evidence` には「どの環境で何を見たか」を1行で書く。

## 既知の制約・注意点

- **`~/.claude/settings.json` の hooks と statusLine は orca（`~/.orca/agent-hooks/`）が
  専有している。** 設定を足すときは既存エントリを壊さず追記する。上書きすると orca 側が
  黙って動かなくなる（tsukumo 自身は hook を使わなくなったが、**旧方針で足したエントリを外す
  ときにここを踏む**）
- **SDK のイベント種別は増えうる。** 旧方針で transcript の `type` が実際に増えたのを観測して
  いる（2026-09-08 → 2026-09-09 で5種類増えた）。**知らないものは無視して落ちないこと**
- **SDK のイベントはユーザーの生の会話である。** 本文・ツールの入出力・`speak` の引数を、
  別の場所に複製しない、外部に送らない、ログに丸ごと出さない
  （`docs/coding-standards.md`「会話内容の扱い」）
- **`thinking` は表示しない。** モデルの内部の思考なので、出すと事故になる
- **ビューは 127.0.0.1 に配られるので、同じマシンの他のプロセスからは読める。** 単一利用者の
  開発機を前提にした割り切りで、外からは届かないことだけを保証している。認証を足すより先に、
  この前提が変わっていないかを確認する
- **ビューの本文はメモリにしかない。** プロセスを落とすとブラウザのタブは繋ぎ先を失う
  （`EventSource` が再接続を試み続ける）。起動し直せば同じ URL でそのまま復帰するが、
  **セッションは毎回新規**なので会話は続かない（`docs/requirements.md` 2.2）
- **Orca はエージェント端末への合成入力を弾く**（2026-09-11 実測）。`orca terminal send` も
  `orca keypress` も claude の端末には届かない。**この経路に戻ろうとしないこと**
- **ホストのポートの `openPane` は、一度も実際に呼ばれないまま役目を終えた。** 消すときは
  `src/host.ts` と `src/orca-host.ts` の両方から外す
- **cwd に依存してよいのは起動先プロジェクトのものだけ。** 作業ディレクトリ・
  `develop/tasks.json`・相対指定で渡した素材（`TSUKUMO_CHARACTER_DIR` に相対パスを渡した場合）
  はそこに当たる。**同梱物（`vendor/`・既定の立ち絵）は tsukumo 自身の場所から読む**
  （`src/bundled-files.ts`）。`tsukumo` コマンドをどのプロジェクトのディレクトリで起こしても
  同梱物が見つかるようにするための区別
