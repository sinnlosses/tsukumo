# 流し読みする読み手に最も速く伝わるレポートの構造（2026-10-02）

**この文書は調査の記録であって正典ではない。** `docs/` の他ファイルにある「節の索引」はここには作らない。
正典は `docs/architecture/display.md`「読む時間を減らす物差しと線引き」と
`src/server/report/core/report-notation.ts` の10か条で、**採用が決まるまでコードは1行も変わらない**。

**主題**: 流し読みする読み手にとって最も理解の速いレポートの構造と情報設計。tsukumo の `report` は
`conclusion` → `checks` → `sections`（塊の列）→ `favor` の型で受け取り、アプリが描く。改善の余地は
「アプリがどう描くか」と「どんな塊・順序を用意するか」にある。

**出典の印**: 無印は一次情報（原典・公式サイト）に当たったもの。**【二次】**は二次情報しか見つからなかったもの。
**【換算】**は英語の字数・語数を日本語向けに置き換えた私の数で、原典には無い。

## 要点（10行以内）

1. **人は読まずに走り読みする**という結論は、NN/g の 1997 年（79% が走り読み）から 2019 年（500人超・750時間超の視線計測）まで変わっていない。平均で読まれるのは**語の 20〜28%**、見られる率は 1→4 段落目で **81%→32%**、閲覧時間の **57% は最初の1画面**に落ちる
2. 走り読みの型のうち最も効くのは**見出しだけを拾って要る節に降りる layer-cake**で、成立条件は「見出しが本文と視覚的に区別され、その節の中身を言っている」こと。F 型は見出しも印も無い文の壁で起きる最悪の型
3. 結論先行は分野を問わず同じ形に収斂している: 陸軍の BLUF（1回の速読で分かる・平均15語の文・10行までの段落・1ページ）、ポストモーテムの Summary 1文 → Impact 1文、構造化抄録のラベル付き節、ADR の 1〜2 ページ・完全な文
4. **表か箇条書きかは属性の数で決まる**: 1属性なら箇条書き、2属性（名前と説明）ならラベル付き箇条書き、3属性以上なら表（Google・MS が一致）。見比べる候補は **5つまで**（NN/g）
5. **畳んでよいのは「一部の読み手しか要らないもの」だけ**で、大半の読み手が要るものは畳まない（GOV.UK Design System・NN/g が一致）。畳む階層は **2 まで**、入れ子は禁止。畳みのラベルは中身を予告する語でなければ開かれない
6. **note（コールアウト）は 1 記事に 1〜2 個、隣接させない、見出しの直後に置かない、必須の情報を入れない**（MS Learn・Google・Apple が一致）。多いと視覚的な区別が消える
7. Tufte: 図は「キャプション付きの特別な出来事」ではなく**語と同じ大きさで文・表の中に埋める**（sparkline）。データを運ばないインクは消し、区別は**効く最小の差**で付ける。箇条書きは「原因を欠いた効果の列挙」になりやすく、因果は文で書く
8. Butterick: 行長 **45〜90 半角字**、行間 **120〜145%**、見出しは **3 階層まで（2 が良い）**、強調は太字か斜体のどちらかを最小限（全部を強調すれば何も強調されない）、罫線は **0.5〜1pt** で先に余白を試す
9. いまの規約と食い違うのは、箇条書きへ寄せる条8に属性の数の線引きが無いこと・畳む基準に「少数派だけが要る」と「入れ子禁止」が無いこと・note の数と置き場所を縛っていないこと。段落 3 文の上限はどの指針（5〜6文・5文・3〜7行）より厳しいので変えなくてよい

## 3. 知見: Tufte

- **sparkline**:「小さく、密で、単純な、**語の大きさ**の図」。「図はもはやキャプションと枠の付いた漫画的な特別の出来事ではなく、**語や数の置ける場所ならどこにでも**置ける――文の中、表、見出し、地図、表計算、図の中」。最新値は赤い点で示し、添える数字と色で結ぶ。正常域は灰色の帯。縦横比は Cleveland に倣い**傾きが平均 45 度**になる「こぶのある」形（尖らせず平たくもしない）。[Sparkline theory and practice](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/)
- **技術報告の形**: 33 枚のスライドは 11×17 インチを二つ折りにした **4 ページ**の報告に収まる。中身は「**文・段落・表・本文に統合された図**」。「箇条書きは原因を欠いた効果だけを見せる、地面を蹴るうなり声になりがち」。コロンビア事故調査委員会と帰還飛行タスクグループの結論は「PowerPoint は工学的な報告・文書に不適切で、**技術報告書のほうが優れる**」。[PowerPoint Does Rocket Science（2005）](https://www.edwardtufte.com/notebook/powerpoint-does-rocket-science-and-better-techniques-for-technical-reports/)
- **data-ink とチャートジャンク**（The Visual Display of Quantitative Information、第2版）: data-ink 比 = 図のインクのうち、データ情報の非冗長な表示に使われた割合（p.93）。5 原則「何よりもデータを見せる / data-ink 比を最大に / データでないインクを消す / 冗長なデータインクを消す / 見直して直す」（p.105）。チャートジャンクは情報を運ばない装飾（第5章）。small multiples は「本質的に比較的」で、**1つの区画の設計が分かれば残り全部のデータに即座に届く**（p.170）。「図の優秀さとは、最短の時間に・最少のインクで・最小の空間で、最大の数の考えを見る人に与えること」（p.51）。**本の本文は Web で照合できず、文言は二次情報で突き合わせた**【二次】: [guypursey の要約](https://guypursey.com/blog/202001041530-tufte-principles-visual-display-quantitative-information)。公式の書誌は [edwardtufte.com](https://www.edwardtufte.com/book/the-visual-display-of-quantitative-information/)
- **smallest effective difference**（Visual Explanations p.73）:「**あらゆる視覚的な区別を、はっきり効く範囲でできるだけ控えめに**する」。矢印・目盛・枠・凡例のような脇役を弱めると主役が立つ。「小さな差は、より多くの差を許す」【二次】: [要約記事](https://medium.com/@pj_/the-smallest-effective-difference-90fc94d5ab0d)
- **分析的デザインの原則**（Beautiful Evidence 第5章）: 比較を見せる / 因果と仕組みを見せる / 多変量を見せる / **語・数・画像・図を完全に統合する**（「語、数、絵、図、グラフ、表は一緒にあるべき」）/ 証拠を十分に記述する / 中身の質がすべてを決める【二次】: [要約記事](http://eppsnet.com/2010/02/fundamental-principles-of-analytical-design/)

## 6. tsukumo に効く示唆

数は上の出典の条件つきの値で、**【換算】**は 1 全角字 ≒ 2 半角字・日本語の 1 文 ≒ 英語 15 語 ≒ 全角 35 字として置き換えた私の数。
採るかどうかは `docs/architecture/display.md`「読む時間を減らす物差しと線引き」の物差しで決める。

### 6.1 結論と最初の1画面

- **`conclusion` の 1 文目は先頭の語で変化を言い、全角 50 字以内【換算】**（GOV.UK の要約 160 半角字・AR 25-50 の平均 15 語の文・NN/g「先頭 2 語で判断される」）。「〜について」「今回は」のような前置きの語を先頭に置かない。1 文目だけで伝わるかの検算は条の末尾にすでにあり、字数の目安だけが無い
- **`conclusion` と `checks` は最初の1画面に収める**（閲覧時間の 57% が1画面目、2画面目までで 74%）。`checks` は種類ごとに 1 行（型検査・lint・単体・E2E・目視）に畳み、件数は行の中に書く。長い `checks` は最初の1画面を食い、`sections` を2画面目以降へ押し出す
- **`favor` は最後尾なので、構造上いちばん見られない**（4 段落目を見る人は 32%）。本文を動かさずに済む手当ては、`favor` があることを `conclusion` の脇に印で示すこと（見せ方。文字列は変えない）。採るかはユーザーの決め
- `sessionSummary`・`closing` は走り読みの対象外なので、ここでは触れない

### 6.2 見出しと節

- **見出しは「取り外しても本文が成り立つ」「疑問文にしない」「全角 30 字以内【換算】」を足す**（GOV.UK の removable・not questions、NN/g 40〜60 半角字）。条10「その節の結論を言う語」は layer-cake の成立条件そのもので、変えない
- **見出しは 1 階層のまま**（MS「1〜2 ページなら 1 階層で十分」、Butterick「3 まで、2 が良い」）。`markdown` の塊に見出しを書かせない現状の差し戻しは、この条で裏が取れる
- **節の並びは「結論を支える順」にし、やった順にしない**（Minto の 4 つの順のうち、作業報告の既定は演繹。時系列は `list` の `flow` と `ordered` の中だけ）。ポストモーテムも時系列を最後に置く
- 節の数は数で縛らない（`display.md` の決定）が、**4 つ目以降は 3 人に 1 人しか見ない前提で並べる**。4 つ目以降に置けるのは、読み手の判断を変えないもの（条4 で落とすか畳むもの）だけ

### 6.3 表・箇条書き・ラベル付き箇条書き

- **属性の数で決める: 1 → `list`、2（名前と説明）→ `list` の `label`、3 以上 → `table`**（Google・MS）。条8「文字より視覚情報」にこの線引きを足すと、1 属性の表（MS が禁じる）と 3 属性の箇条書きが減る
- **`compare` / `options` の候補は 5 つまで**（NN/g）。6 つ以上なら、まず候補を絞った理由を `text` に 1 文で書き、残りを `fold`
- **表の列は 4〜5 列まで、セルの文は 1 行、空セルは「なし」と書く**（GOV.UK・MS。ダッシュで埋めない）。1 列目は識別子、列は重要度順（NN/g）。数の列の右揃えはすでにある
- **箇条書きは 3 項目以上・7 項目以内・1 項目 1 文**（NN/g・MS・GOV.UK）。2 項目なら `text` の 1 文に、8 項目以上なら種類で割って `label` 付きにするか表にする
- **因果（なぜそうなるか）は `text` の文で書き、箇条書きにしない**（Tufte「原因を欠いた効果の列挙」、Nygard「文の断片の言い訳にしない」）。条8 を「同じ種類の項目は印に、因果は文に」と読む。段落 3 文の上限は Google の 5〜6 文・GOV.UK の 5 文・MS の 3〜7 行より厳しいので、そのまま
- `card` を外した判断は NN/g の「同種の項目では一覧より走り読みしにくい」で裏が取れる。戻さない

### 6.4 畳む基準（`fold` / `<details>`）

- **畳んでよいのは「一部の読み手・一部の場面でしか要らないもの」だけ**: 再現手順・生の数値の全行・採らなかった案の細部。**読み手の判断を変えるもの・`unverified`・`warn` / `ng` は畳まない**（GOV.UK「大半が要るものを隠さない」、Google「必須の情報を note に入れない」の類推）
- **畳みは 1 階層。`fold` や `<details>` の入れ子は境界で差し戻す**（NN/g「3 階層以上は迷子」、GOV.UK「入れ子にしない」）。機械的に検査できる
- **畳みのラベルは中身と数を言う**（「採らなかった案 2 件: 性能と互換」）。「詳細」「補足」は information scent が無く開かれない。`fold` の `summary` が汎用語 1 語だけなら差し戻す案は機械的に書ける
- **落とすか畳むかの線**: 読んでも判断が変わらず、あとで確かめるときにも要らないなら落とす（条4）。あとで確かめるときに要るなら畳む。「畳めるから書く」はしない（100 語ごとに +4.4 秒。畳んでも開けば同じ）

### 6.5 `note` の数と置き場所

- **1 レポートに `note` は 2 つまで、隣接させない、節の先頭（見出しの直後）に置かない**（MS Learn 1〜2 個・隣接禁止、Apple 見出し直後禁止、Google 複数で区別が消える）。3 つ目・隣接は境界で差し戻せる
- 例外は「戻せない操作」の `warn` / `ng` 1 つで、これは節の先頭でもよい（いまの「上の条を曲げてよいとき」のまま）
- **`ok` は `checks` に吸収できる**（Google の Success は対話的な内容専用）。種類を増やさない決定（`display.md`）は正しく、減らす余地のほうがある。使われ方は `scripts/report-block-usage.ts` の数で見る

### 6.6 数・図・`stats`

- 数は数字と単位で書く（すでに条6）。NN/g の視線計測では、数字は読み飛ばされる文中でも目を止める
- **`stats` に短い系列を持たせて語の高さの sparkline を描く**案は Tufte の「語や数の置ける場所ならどこにでも」そのもので、`chart`（364 回で 1 回）より書く手間が軽い。最新値を強調色の点、`before` との差を色で結ぶ。縦横比は傾きが平均 45 度になる程度に抑える
- **複数の系列は 1 つの図に重ねず、同じ小さな設計を並べる**（small multiples）。`compare` と `chart` の描き方の既定にできる
- **区別は効く最小の差で**: 表の罫線は 0.5〜1 px か余白だけ、縞は 8 行以上の表だけ、図の格子線は消す、強調色（狐火色）は状態か最新値の 1 役に限る（Tufte・Butterick「3 色と 5 書体が要ると思ったら考え直す」）
- 図のキャプションは「図: 構成」でなく、その図が言う結論を 1 文で（Tufte「語と図を統合する」。条3「図で示したことを地の文で言い直さない」とは両立する）

### 6.7 文字組み（CSS。目視で確かめる対象）

- **本文の行長は全角 25〜45 字【換算】**（Butterick 45〜90 半角字、NN/g 50〜75 半角字）。レポートの `text` に `max-width` を置き、表・`code` だけ広げる。JLReq に日本語の推奨字数は無いので、上限は目視で決める
- 本文 15〜25 px、行間 120〜145%（Butterick。欧文の値。日本語の行間に一次情報は見つからなかった）、段落間は本文サイズの 50〜100%、字下げと余白を併用しない
- 見出しは上の余白を大きく下を小さく、太字、大きさの差は最小の増分（MS・Butterick）
- **太字は `label`・状態・UI 要素にだけ。`text` の中の強調に使わない**（GOV.UK は強調の太字を禁止、Butterick「全部を強調すれば何も強調されない」）。`text` の `**` を通常の太さで描く（見せ方。文字列は変えない）か、規約で止めるかは選べる
- 罫線より余白を先に試す。枠は 0.5〜1 px、点線・二重線にしない

### 6.8 いまの規約との差分と、確かめていないこと

| いまの規約                    | 差分                                                                              | 根拠                       |
| ----------------------------- | --------------------------------------------------------------------------------- | -------------------------- |
| 条8「文字より視覚情報」       | 属性の数（1 / 2 / 3 以上）と「因果は文」の線引きが無い                            | 5 章・3 章                 |
| 条4「落とすか `fold` で畳む」 | 「少数派だけが要る」「入れ子禁止」「ラベルは中身を言う」が無い                    | 1 章・2 章の Design System |
