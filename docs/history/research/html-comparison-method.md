# HTML 版とレポート版を同じ題材で見比べ、改善点を取り込む手順（2026-10-24）

**正典ではなく、手順の案と形の比較。** `src/` は変えない。HTML 版は参照用で、tsukumo のレポートには載せない（`docs/architecture/adr/0032-free-html-block.md`）。

## 見立て

- 手順は6段に分かれ、機械でできるのは「撮る・数える・並べる・雛形に流す」まで。題材・依頼文・色分けと読む順の判定・取り込みの採否は人の判断で残る（「HTML 版のほうが良い」の判定は人の目で付ける、が決定済み）
- 実績は手作業の2回だけ（0032 の測定 2026-10-23、`docs/history/research/html-comparison-trial.md` 2026-10-24）。頻度の根拠が薄く、仕組みにして浮くのは撮影と数の下書き（1回あたり数分）にとどまる
- 2回とも観点の表の形が違った（0032 は所要・量・画、`html-comparison-trial.md` は枠・題・色分け・読む順）。型が無いと次の回が表の形を思い出すところから始まる

## 手順

| #   | 段                  | 機械でできる                                                                                    | 人の判断が要る                                                       |
| --- | ------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | 題材を決める        | 候補の一覧(`node scripts/runtime/report-block-usage.ts` で塊の使われ方の数)                     | どの題材か。HTML 版が勝ちそうな読み物(流れ・見比べ・図)から選ぶ      |
| 2   | 同じ依頼で2版を作る | HTML 版: 固定の雛形の依頼文で書かせ `/tmp` に置く。レポート版: 本文を疑似セッションの複製に差す | 依頼文の言い回し、暗い面の指示の有無。レポート版の本文は書き手が書く |
| 3   | 同じ幅で撮る        | `capture-view.ts` で 390 と 1400 を基本に撮り、`--measure` で横のはみ出しを取る                 | 幅を足すか                                                           |
| 4   | 観点の表の下書き    | 画像のパス、はみ出し px、字数、レポート版の `--paper-metric`                                    | 枠・題・色分け・読む順は人の目で付ける。機械の数は補助               |

## 形の比較

| 観点           | (a) スキル                                                            | (b) `scripts/` のスクリプト                  | (c) 研究メモの型                 |
| -------------- | --------------------------------------------------------------------- | -------------------------------------------- | -------------------------------- |
| 使うときの手間 | 小さい。題材を渡せば回る                                              | 中。撮影と表の下書きは機械、残りは手         | 大きい。毎回手順を読んで打つ     |
| 作る手間       | 大きい。手順・依頼文の雛形・表の型を書き、題材ごとに検証する          | 中。糊のスクリプト1〜2本                     | 小さい。型を書くだけ             |
| 再現性         | 雛形で書き手のばらつきの一部を抑える。判断の段はモデル任せで揺れる    | 撮影・数は固定できる。書き手のばらつきは残る | 表の形は揃う。読み方は人で揺れる |
| 壊れやすさ     | `capture-view.ts` や疑似セッションの形が変わると崩れ、気づきにくい    | 同じ依存。テストで気づける                   | 壊れない。古くなる               |
| 置き場         | `~/.claude/skills` か `tsukumo-plugins`。グローバルへの導入は承認事項 | このリポジトリ(`scripts/capture/` の隣)      | `docs/research/`                 |

このリポジトリに `.claude/skills/` は無い。0032 の方針(HTML の口を足さない)には、どの形も当たらない。

## 推す形

**(c) の型を先に置き、(b) の撮影の糊は、3回目の見比べが要るときに足す。(a) のスキルは、(b) が回って頻度が確かめられてから見直す。**

1. 実績が2回だけで、頻度の根拠が薄い。「頻度にならないなら (c) だけ」の側に寄る
2. 機械にできる部分は `capture-view.ts` で足りていて、糊が薄い。3回目に同じ手作業を打つ時点で、自動化したいものが見える
3. (a) はグローバルのスキルになり、導入が承認事項。判断の段が多く、スキルにしても人の判断は減らない。ここでは推すだけで入れない
4. この文書自体が (c) の型。次の回は、上の手順と表の形をなぞる

(b) の着手の条件つきの課題は、条件つきの課題(ドラフト)として積んだ。着手の条件は、HTML 版との見比べが3回目に要るとき。

- 手作業の実績が2回の先で、見比べが本当に続く頻度か
