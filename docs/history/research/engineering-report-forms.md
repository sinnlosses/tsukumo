**主題**: 終わった仕事を人に渡す文書（コミット・PR・changelog・状態の報告・障害の報告・AI エージェントの最終報告）の

**【二次】**は二次情報しか見つからなかったもの。実物は見た件数を添える（少数の例であって統計ではない）。

## 要点（10行以内）

1. **型の間で一致する順序は「状態と変化 → なぜ・影響 → 証拠 → 限界と未確認 → 読者の行動 → 次」**。前の3つ（状態と変化・なぜ・証拠）は節として持つ型ではどれも同じ並びで、限界と読者の行動の位置は型によって揺れる。「どれだけかかったか」を本文の節に持つ型は1つも無く、どれも札（メタデータ）で見せる
2. **1行目の条はどの型でも同じ**: 単独で読める・読み手から見た変化を言う（Google の CL・Chromium・changelog の題・Anthropic の Opus 5 の指針・Devin の「diff を見ていない読者向け」）
3. **証拠の節の源流は Meta の Test Plan**。Phabricator は「知らない人が確かめられる、繰り返せる手順」、React は「打ったコマンドと出力・画面写真」を求め「空なら閉じる」。Claude Code の PR は「コマンド＋件数」を書くが、同じ箱の一覧に「確かめたこと」と「確かめてほしいこと」が混ざる
4. **Codex（cloud）は主張の種類で引用の置き場を分ける**: 変更の要約にはファイルの行、検証の節には端末出力の行を引く。CLI では `path:line` を1参照1パスで書き、範囲は書かない
5. **限界と未確認は、提案の型（RFC・PEP・KEP）では独立の節、PR の型では任意の欄**。エージェントは「できなかったことは確かめ方を添える」（Codex）、「終えられなかった理由を書く」（OpenHands）
6. **2026 年のエージェントは既定の本文を縮めている**: Devin は既定の雛形を4節から Summary 1節へ（2026-02 → 10）、Copilot の完成形は問題1〜2文＋太字ラベルの箇条2〜3、Codex CLI は既定10行以内・箇条4〜6
7. **育てる形の代表は Copilot**: 作業中は題に `[WIP]`、本文は計画のチェックリストで、終わると問題と変更の本文に**書き換える**（継ぎ足さない）。Google は「出す前に本文がまだ合っているか読み直す」を条にしている
8. **changelog の1項目は約40語・3文（何が変わった → どう使う → 誰が使える）**。Stripe は 新機能 → 影響 → 変更点（From → to の表）で、影響を読者の側の文で別の節にし、**影響しないもの**まで書く
9. **報告の種類で型が変わる**: 作業＝Summary と Test plan、判断＝RFC・PEP の Rationale と Rejected Ideas、調べもの＝What / So what / Now what、中断・失敗＝Azure の PIR（What happened → What went wrong and why → …）

| Augment                                  | Tasklist の項目ごとの状態と、項目ごとの差分（Tasks と Changes を切り替える）                                                                                      | 記述なし                                                                                      | 記述なし                                                                                                                                       | 記述なし                                                                                                                                                       | 終わったら手順を Jira・Linear のコメントに残せる                  |

Amp と Factory は、最終報告の本文の型を言う一次資料が見つからなかった。

**育てる形と一括の形**

| 形                             | 例                                                                                                                                                                                   | 読者への効き                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| 作業中は計画、終わると書き換え | Copilot: `[WIP]` の題と計画のチェックリスト（実物1件は4項目すべて `[ ]`）→ 完成形の本文。2025-07-30 から「フィードバックに応じて題と本文を最新に保ち、何が変わったかが一目で分かる」 | 進行中は「どこまで来たか」、終わったあとは「何が変わったか」に答える。継ぎ足さないので古い計画が残らない |
| 版の外に積む                   | Keep a Changelog の Unreleased                                                                                                                                                       | 出る前に何が入るかを見せ、出すときに版へ移す                                                             |
| 状態を時系列で比べる           | Shape Up の丘（過去の状態との比較）、Atlassian の週次の更新                                                                                                                          | 「どこにいるか」に加えて「どう動いているか」。動かない点が挙げた手になる                                 |
| 計画と項目ごとの差分           | Augment の Tasklist、Devin の plan（`docs/history/research/agent-report-ui-patterns.md`）                                                                                                    | 項目の単位で確かめられるが、全体の結論は別に要る                                                         |
| 一括                           | Claude Code の PR・Codex・Jules・OpenHands の finish                                                                                                                                 | 終わった状態から1回で書くので筋が通る。進行中は見えない                                                  |

## 5. 知見: 読者の問いの梯子

| 順  | 読者の問い                            | 裏付ける型の条                                                                                                                                                       | tsukumo の今の置き場                               |
| --- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 1   | 終わった?（状態）                     | Atlassian の状態と日付、Copilot の `[WIP]`、Jules の完了の定型、Azure の What happened?                                                                              | `task` の終わり方                                  |
| 2   | 何が変わった?（読み手から見て）       | Google の1行目、changelog の題、Stripe の新機能、Smart Brevity の 1 big thing、Opus 5 の「1文目で何が起きたか」                                                      | `conclusion` の1文目                               |
| 3   | それで何が良い?（なぜ・影響）         | Smart Brevity の Why it matters、Stripe の影響、React の Summary（動機）、GitHub Docs の「なぜ要るか」、So what                                                      | 決まった置き場なし（`conclusion` の2文目に任せる） |
| 4   | 本当か?（証拠）                       | Test Plan（Phabricator・React・RN）、Chromium の `Test:`、KEP の Test Plan、Codex のテストの節と引用、Cursor の動画                                                  | `checks`・`figure`                                 |
| 5   | 何が足りない?（限界・未確認・戻し方） | Google の「方法の欠点」、RFC の Drawbacks / Unresolved、PEP の Open Issues、KEP の Risks と Non-Goals、Revert Plan、Codex の確かめ方、Copilot の「変えていないもの」 | `checks` の `unverified` と本文の1行               |
| 6   | 私がすることは?                       | Atlassian の「はっきりしたお願い」、Kubernetes の `action required`、Azure の「顧客が影響を減らすには」、週次の雛形の WHAT WE NEED FROM YOU                          | `favor`（最後に1つ）                               |
| 7   | どこを見ればいい?                     | GitHub Docs の「最も重要なファイルを先に」、Kubernetes の Special notes for your reviewer、Codex の `path:line`                                                      | `files`・押すと開くパス                            |
| 8   | 次はどうなる?                         | Smart Brevity の What's next、feature-dev の Suggested next steps、kickoff、Now what、Codex の「自然な次があるときだけ」                                             | `sessionRemaining`（画面に描かない）               |
| 9   | どれだけかかった?                     | 本文の節に持つ型は無い。Jules の所要時間と行数、Copilot の session log、Shape Up の段ごとの時間は札・別画面                                                          | 描かない                                           |

- **1〜4 の順は、その問いを節として持つ型ではどれも同じ**。例外は Google Cloud の障害報告（影響の詳細が最後）だけ
- **5 と 6 の位置は型で揺れる**: 提案の型は 5 を後半の独立の節に、状態の報告は 5（BLOCKED）を 6（お願い）の直前に、Azure は 6 を終わりから2番目に置く。**6 を末尾に置く型は、上端から見つけられる印を別に持つ**（Kubernetes の `action required` の文字列、Atlassian の状態の色）
- **3 を独立に持つのは読者が外の人の型**（changelog・Smart Brevity・Stripe）。書き手と読み手が近い PR の型は Summary に溶かす

**報告の種類ごとの型**

| 種類                       | 源の型                                                                                     | 既定の節の並び                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 作業（やったこと）         | PR の雛形（Summary → Test plan → Revert Plan）、Chromium、Copilot の完成形                 | 変化 → 証拠 → 変更の要所（どこを見るか）→ 限界と変えていないもの → お願い           |
| 判断（決めたこと）         | ADR、RFC（Rationale and alternatives・Unresolved）、PEP（Rejected Ideas・Open Issues）     | 決めたこと → 理由と採らなかった案 → 結果（良いものも悪いものも）→ 未決              |
| 調べもの（分かったこと）   | What / So what / Now what、Smart Brevity、Codex の問い合わせの作業（ファイルの引用を主に） | 分かったこと → 根拠（出典・`path:line`）→ 何を意味するか → 確かめていないこと → 次  |
| 中断・失敗（止まったこと） | Azure の PIR、Google Cloud、Shape Up の挙げた手、OpenHands の「終えられなかった説明」      | どこで止まったか → 原因 → 何を残し何を戻したか → 再開に要るもの（読者の判断・情報） |

## 6. tsukumo に効く示唆

印は効く先: 〔規約〕書き手（モデル）への規約 / 〔塊〕`report` の欄や塊の schema / 〔描画〕CSS・部品 / 〔仕組み〕検査・計測・運用。
**正典の変更**は、いまの欄・規約（`display.md` の「量の上限は数で書かない」「レンダラは要約を起こさない」を含む）と食い違うもの。採否は利用者が決める。

### (a) report の欄と順序

- **`conclusion` の2文目を「それで何が良いか」か「変えていないもの」に充てる**〔規約〕: 梯子の 3 は今どこにも置き場が無い。Stripe の影響・Smart Brevity の Why it matters・Copilot の「the runtime defect is unchanged」が根拠。1文目の規約（読み手から見た変化）はそのまま
- **「変えていないもの・範囲外」を1行で書く条**〔規約〕: 読者が「直ったはず」と誤解しうるときだけ。KEP の Non-Goals、Stripe の「影響を受けることはありません」、Copilot の完成形。`note` を増やさず本文の1文で足りる
- **`favor` は末尾のまま、上端に「お願いがある」印を出す**〔描画〕: 型の多くはお願いを後半に置くが、見つける印を別に持つ（Kubernetes・Atlassian）。既存の調査（4段落目を見る人は 32%）と同じ結論。欄の位置を `conclusion` の直後へ移すなら**正典の変更**
- **「確かめていないこと」は欄を新設せず `checks` の `unverified` に寄せ、行に「確かめ方」を持たせる**〔塊〕**正典の変更**: Codex の「できなかったことは確かめ方を添える」、Chromium の `Test:`、Phabricator の「知らない人が繰り返せる手順」。Claude Code の PR で「確かめたこと」と「確かめてほしいこと」が箱の印だけで混ざる弱点を、状態の語（`unverified`）と手順の欄で避けられる
- **「次の一手」は `favor`（読者がすること）と分けて扱う**〔塊〕: 型は「読者の行動」（Atlassian の asks）と「この先の仕事」（What's next・kickoff）を別の欄にする。tsukumo の後者は `sessionRemaining` で画面に描かない。`stopped` と `awaiting-answer` のときだけ残りを1行で描くなら**正典の変更**。Codex の「自然な次が無ければ書かない」は `favor` を省ける今の形と合う
- **所要時間・行数はモデルに書かせず札で出す**〔描画〕〔仕組み〕: 本文の節に持つ型は1つも無い（梯子の 9）。既存の調査の「数の帯」の案と同じ方向

### (b) 報告の種類ごとの既定の節の型

- **`task` に報告の種類（作業 / 判断 / 調べもの）を持たせ、5章の表の並びを規約の既定にする**〔塊〕〔規約〕**正典の変更**: 終わり方（`finished` / `stopped` / `awaiting-answer`）はすでにあり、`stopped` は「中断・失敗」の型に当たる。種類は節の数を縛らないので「量の上限は数で書かない」とは食い違わない
- 種類ごとの必須の塊を差し戻しで検査する〔仕組み〕: 判断なら `options`（採る・採らない）が1つ、調べものなら出典か `path:line` が1つ、`stopped` なら「どこで止まったか」と `favor`。`display.md` の「まず使われ方の記録で数を見て、要るときだけ差し戻しへ」に従い、先に `scripts/runtime/report-block-usage.ts` で種類ごとの使われ方を数える
- **中断の報告は Azure の PIR の前半3問（何が起きた・なぜ・どう対処した）を既定の見出しにする**〔規約〕: Shape Up の「誰も分からないと言いたくない」への手当てで、止まったことを本文の先頭で言わせる

### (c) 検証と証拠の書き方

- **`checks` の行は「打ったコマンド＋件数＋結果」**〔規約〕: Claude Code の PR（「`bun test` — 664 tests pass, 0 failures」）・React（「打ったコマンドとその出力」）。今の欄（label・状態・数・コマンド）と合う
- **目視の行は「何を見て、何が見えたか」を繰り返せる形で**〔規約〕: Phabricator の「知らない人が確かめられる手順」、Cursor の動画・画面写真。CLAUDE.md の「描画に関わる変更は何をどう確かめたか」を `checks` の行の形に落とす
- **主張の種類で証拠の置き場を分ける**〔規約〕: 変更の主張は `files` と本文の `path:line`、検証の主張は `checks`（codex-1 の「要約にはファイルの引用、テストには端末出力の引用」）。生の出力は貼らない（今の規約と同じ）
- **本文の `path:line` を押すと、その行でエディタが開く**〔描画〕: Codex CLI の「1参照1パス・`:line`・範囲は書かない」の形。tsukumo はパスを押して開けるが、行まで飛ぶかは確かめていない
- **性能を主張するなら前後の数を必須にする**〔規約〕: Phabricator の「性能が動機の変更は測定を含める」。`stats` か `beforeAfter` で
- **直したと言うのに `checks` が空のレポートを差し戻す**〔仕組み〕: React の「検証の欄が空なら閉じる」。(b) と同じく、先に使われ方を数える

### (d) 進行中にレポートを育てる形を採るか

- **今の形（帯と中間レポートが積まれ、最後に最終レポート）は Copilot の「作業中は計画、終わると書き換え」と同じ型**で、変える根拠は見つからなかった。最終レポートを中間の継ぎ足しで育てる形は、Google が条にした「本文と中身のずれ」を招く
- **最終レポートは終わった状態から書き直し、中間レポートを継ぎ足さない**〔規約〕: Copilot の書き換え、Google の「出す前に読み直す」。中間の要約の並べ直しは読者の問いの順にならない
- **中間で `unverified` だった行が最終でどうなったかを検査する**〔仕組み〕: 中間の `checks` の label が最終に無ければ差し戻す案。レンダラが中間から最終へ行を写すのは「再構成」で採れないが、照らして差し戻すのは書き手に書かせる側なので線の内側
- **段ごとの所要時間を帯に残し、止まった段を目立たせる**〔描画〕〔仕組み〕: Shape Up の「過去と比べられることが要」「動かない点は挙げた手」。進み具合の帯がすでに段を持つので、時間の記録を足すだけで済むかは確かめていない

## 確かめていないこと

Lenny's Newsletter の状態報告の雛形の原典（検索で出た雛形だけ）/ Smart Brevity の本の4部の文言（本の要約で照合）/ What-So what-Now what の原典（Borton 1970・Rolfe ら 2001）/
Atlassian の状態の値（検索結果の要約だけ）/ Codex cloud の PR の本文の実物（GitHub の検索が回数制限で止まり、system message の条だけ）/
Claude Code が PR 本文の雛形を system prompt で与えているか（実物3件からの推測。公式ドキュメントに雛形の記述は無い）/
Copilot・Claude Code の実物は計7件で、人が後から直した本文かどうかは分からない / Amp・Factory の最終報告の型 /
tsukumo で `path:line` を押したときに行まで飛ぶか / Diátaxis は4類型（tutorial・how-to・reference・explanation）に報告や changelog の置き場を持たず、当てはめは見送った。
