## 層1: DOM の更新

| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |

### 「サーバが HTML を作る」系の一族（2026-09-12 にユーザーの問いで追加調査）

ユーザーの問い「サーバが HTML を作り直す構成ならもっと選択肢はありそう。Next.js とかも視野に入る?」に答えるために、層1の候補を一族として並べ直した。

**先に外れるもの**: この一族が主に解くのは (1) ページ遷移をサーバ主導で速くする、(2) フォーム送信の結果を部分的に差し込む、(3) 部分更新をサーバから押す、の3つ。**tsukumo が持っているのは (3) だけ**（1ページで遷移が無く、入力欄1つの POST は既に `fetch` で書いてあり、更新は既に SSE で押している）。枠組みが持ってくる機能の大半が使われないことが、この一族を評価するときの前提になる。

| 候補            | プロセス構成                                                  | 「決める」層（`buildMainBody` ほか）   | 押す粒度                                                                                                                      | 枠組みの大きさ                                         | 出典                                                                      |
| --------------- | ------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| Idiomorph のみ  | 変わらない                                                    | そのまま残る                           | 領域まるごとのまま                                                                                                            | ライブラリ1つ                                          | [Idiomorph README](https://github.com/bigskysoftware/idiomorph)           |
| htmx + SSE 拡張 | 変わらない                                                    | 残る                                   | **名前付きイベント + ターゲット単位**に分ける必要。サーバは「HTML の断片を `event:` / `data:` で送る」形                      | 属性ベースの枠組み一式。遷移・フォームの機能は使わない | [htmx SSE extension](https://htmx.org/extensions/sse/)                    |
| Datastar        | 変わらない                                                    | 残る                                   | **今のままでよい**。`content-type: text/html` で返した要素を「id を手がかりに morph」する                                     | フロント側の反応性（signals）まで入る                  | [Datastar Getting Started](https://data-star.dev/guide/getting_started)   |
| Turbo Streams   | 変わらない                                                    | 残るが `<turbo-stream>` で包む必要     | **action + target ID 単位**。9つのアクション（append / replace / update / **morph** ほか）から選ぶ。SSE・WebSocket でも配れる | Rails 由来の枠組み一式                                 | [Turbo Handbook: Streams](https://turbo.hotwired.dev/handbook/streams)    |
| Next.js         | **Next のサーバが増える**（tsukumo は SDK を抱えた1プロセス） | **作り直し**（サーバコンポーネントへ） | 状態ベースに変わる                                                                                                            | ルータ・ページ・ビルド・RSC の枠組み全部               | [Next.js Custom Server](https://nextjs.org/docs/app/guides/custom-server) |

**一族はどれも最後は morph に行き着く。** Datastar は「モーフィングにより DOM の変更された部分だけが更新され、状態が保たれる」と説明し、Turbo Streams のアクション一覧にも `morph` がある。Idiomorph はその部品を単体で取り出したもの（htmx と同じ bigskysoftware 製）。**tsukumo に足りないのは morph の部分だけ**なので、一族から部品だけを取ると Idiomorph 1つになる。

**Next.js について**（ユーザーの名指しの問い）。tsukumo が Next.js を使うなら、SDK のイベントループを同じプロセスで回し SSE を自分で配りたいので **custom server** の形になる。公式はこれについてこう書いている。

> Before deciding to use a custom server, keep in mind that it should only be used when the integrated router of Next.js can't meet your app requirements.

つまり**公式が推奨しない入り方**から始まることになる。加えて `next build` が要り、`server.js` は「Next.js のコンパイラやバンドル処理を通らない」。得られるのは React のコンポーネントモデルだが、ユーザーが挙げた不足3つはどれも Next.js でなくても解ける（層1は morph、層2は `bun build`、層4は CSS の分割）。

**React について**（ユーザーの指示で名指しの評価）。React を入れると、いまサーバ側の関数（`buildMainBody` / `buildCharacterBody` / `buildSidebarBody`）が持っている「決める」層の仕事がクライアントへ移る。このプロジェクトの制約に照らすと:

- **ビルド工程**: React は JSX の変換にビルドが要る。ユーザーは工程の追加を許容しているので、ここは足切りの理由にならない
- **外部通信ゼロ**: React 本体は `vendor/` に同梱できるので、ここも理由にならない
- **噛み合わなさ**: 現構成は「サーバが HTML を組み立て、SSE で押し、クライアントは差し替えるだけ」。React はクライアントが状態を持って描く前提なので、**SSE で押すのを HTML ではなく状態（JSON）にする**ところまで作り直すことになる。これは**会話の内容をブラウザ側の状態として持つ**形に近づくが、同じプロセス内の `127.0.0.1` に閉じる限り「外部に出さない」規約には触れない
- **効き目**: ユーザーが挙げた不足3つのうち、React でなければ解けないものは**1つも無い**（層1は morph、層2は `bun build`、層4は CSS の分割で解ける）
- **重さ**: 対象ユーザーは作者本人のみ（`docs/requirements.md` 1）。React 公式自身が、ゼロから組む場合はルーティング・データ取得・コード分割を自分で解くことになると警告している

## 4層をまたぐ観点

- **`vendor/` 同梱の前例に沿えるか**: 同梱するライブラリは「表示時の外部通信ゼロ」を守れること・ライセンスが明示されていることが条件（`vendor/README.md`）。Idiomorph は 0BSD で条件を満たす。取得元だけが cdnjs から外れる
- **原則3（ホスト・外部依存は1つのアダプタに閉じ込める）との関係**: ブラウザの中で動くライブラリはホスト依存ではないので、この原則の対象外。`vendor/` に置いて自分のサーバから配る限り、差し替え点は「どのファイルを `<script>` で読むか」の1箇所に留まる
- **ビルド工程を足したときに壊れうるもの**: `bun run start`（`src/index.ts` を直接実行）と `bin/tsukumo`（`bun link` でグローバルに入っている）。**ビルド成果物が無くても起動できる形にするか、起動時にビルドするかを決める必要がある**
