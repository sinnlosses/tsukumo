# tsukumo 要件定義: 画面レイアウト

ステータス: **ドラフト**。入口は `docs/requirements.md`（要件定義の全体）。

責務: 4.7 画面レイアウト（biim 風の4領域、1枚の HTML にまとめた形、狭い画面での見せ方）。
読む時: 4領域の役割・お伺いの置き場・キャラクター画面・狭い画面の並びに触るとき。
直す時: 画面レイアウトの要件を変えたとき。

## 4. 機能要件

### 4.7 画面レイアウト

biim システムをリスペクトした4領域にする。**領域ごとに役割を1つだけ持たせ、同じ情報が
2箇所に出ないようにする**ことが狙い。**狭い画面（760px 以下）では4領域を並べない**（下の「狭い画面」の段落）。

```
┌────────────────────────────────────────┬────────┐
│ メインビュー                            │サイドバー│
│  始め方の一覧／進み具合の帯／レポート（広い）│ （狭い） │  全部で1枚のHTML
├─────────────────────┬──────────────────┴────────┤  ＝ブラウザタブ1つ
│ キャラビュー（半分）   │ 入力欄（半分）              │
│  立ち絵＋セリフ        │  依頼・お伺いの自由入力     │
│                        │  ・送信・中断／のコマンド補完│
└─────────────────────┴───────────────────────────┘
```

| 位置         | 中身                                         | 対応する biim の要素 |
| ------------ | -------------------------------------------- | -------------------- |
| 左上（広い） | メインビュー。局面ごとの中身（お伺いを含む） | ゲーム画面           |
| 右上（狭い） | サイドバー。タスク一覧・セッション情報       | タイム表・チャート   |
| 左下（半分） | キャラビュー。立ち絵＋セリフ                 | 立ち絵・テロップ     |
| 右下（半分） | 入力欄。依頼とお伺いの自由入力               | 実況者の手元         |

**許可と質問は、同じ形の札「お伺い」にしてメインビューに出す**（進み具合の帯の下の本文。2026-10-02 決定。
形は `docs/architecture/screen-design.md` 13.13「お伺い」）。キャラは吹き出しで「これいい？」と言うだけで、
tsukumo は吹き出しの文言を作らない。**入力欄はそのまま出したままにし**、質問の間だけ**選択肢にない答えを
書く場所**になる（打ちかけの文字はそのまま残る）。許可の間は、ふつうの下書きのまま。
それまでの「許可は入力欄の上の箱、質問はメインビューの札」（2026-09-11・2026-09-23）と覆した理由は
`docs/history/decision.md`「requirements.md 4.7 画面レイアウト（答え待ちの箱。2026-10-02 に覆した記録）」。
**狭い画面（760px 以下）だけは、お伺いを本文に出さず、入力欄のすぐ上に固定した答え待ちの札に出す**（2026-10-09 ユーザー決定。
下の「狭い画面」の段落）。

**メインビューの中身は、ターンの局面（迎える・働く・尋ねる・渡す・つまずく）で入れ替わる**（2026-10-02 決定。
4領域の位置と比率は依頼のあいだ動かさない。`docs/architecture/screen-design.md` 13.13）。

**4領域は1枚の HTML にまとめ、CSS で領域を分ける。** ブラウザタブは1つだけで、
**ターミナルのペインは1つも要らない**（Claude Code の TUI を開かないため）。

**同じページの中に、4領域の会話の画面と入れ替わる「キャラクター画面」が1つある**
（2026-09-17 決定）。立ち絵・差し色の差し替え、新しいパックを作る口、画面の色3つ
（`ground` / `surface` / `ink`）はここに置く。
**切り替えは URL の `#character`（作る画面は `#character/new`）**で、リロードしても同じ画面に
戻り、ブラウザの「戻る」が効く。**入る口も戻る口も、全画面の最上部の帯**（2026-09-22 決定。狭い画面は引き出しの歯車の面と頭の「‹ 会話へ」）。
会話の画面は隠すだけで外さないので、キャラクター画面に居る間も会話は進み、入力欄の打ちかけも
残る。**答え待ちが来たら帯のいまの作業が「答え待ち」に変わる**（狭い画面は帯の代わりに頭の状態の語）。中身の並びと採らなかった案は
`docs/architecture/screen-design.md` 13.6、帯は 13.9 が正典。

**領域そのものは縦にだけスクロールし、横には転がらない**（2026-09-15 決定）。
`.layout-region` に `overflow-y: auto` だけを書くと、CSS では片方の軸が `visible` でなくなった
ときにもう片方の `visible` も `auto` に計算されるため、書いていない `overflow-x` が `auto` に
なって4領域すべてが横に転がっていた。**横に長いものは、中身の側が自前のスクロール容器を持つ**
（レポートの表は `.table-scroll` の中で転がり、コードは折り返し、図は領域の幅に収め、
長い語は途中で折り返す）。

**狭い画面（760px 以下＝スマホ）では、4領域を並べず、上から「頭・本文・顔と吹き出し・答え待ちの札・入力欄」の
縦の1列にする**（2026-10-09 ユーザー決定。基準は 390x844。見本は `docs/history/mockup/phone-layout-2026-10-09/PHONE-1.dc.html`
で、言葉と食い違ったら見本が勝つ）。スマホでやる「様子を見る」「聞かれたら答える」「止める」を親指の届く下半分に集めるのが狙い。

- **頭**: 顔・いまの作業の状態と経過・いまの段の題・右上の ≡ と、段の点・n/N・「手順 n」
- **本文**: 依頼の1行・中間レポートの1段1行の一覧（押すと下から上がる板で読む）・いまの段・渡したあとの最終レポート
- **顔と吹き出し**: キャラクターの舞台（立ち絵のキャラビュー）は出さず、入力欄の上に顔と**最新のセリフ1件**を出す。
  **作業中も常に出す**（答え待ちのときだけにしない）
- **答え待ちの札**: お伺い（許可と質問）は本文ではなく入力欄のすぐ上に固定し、答えを押しやすいボタンで選ぶ
- **入力欄**: 丸い1行の欄。左に ＋（画像・`/`・`@`）、右は作業中は止める ■（確かめてから止める）、待ちのときは送る ↑
- **引き出し**: 帯とサイドバーが持っていたもの（名乗り・動き方・タスク一覧・使用量・ほかの画面の口・設定）は、≡ から右に出る
  引き出しに入れる。メインビュー／サイドバーのタブとキャラビューは狭い画面には無い

全体の高さは **`100dvh`** に固定し（`vh` だとソフトウェアキーボードが出たときにページごと押し上がる）、
**転がるのは本文だけで、ページ全体はスクロールしない**。**仕切りのドラッグと「比率を既定に戻す」は狭い画面では出さない**
（動かせる比率が無い）。**広い画面の配置・入力欄・中間レポートの見せ方は変えない。** 切れ目は `@media (max-width: 760px)` の
1つだけで、規則は各機能の CSS に分かれている（`docs/architecture/browser.md`「CSS」）。寸法・色・部品の行き先・見本に無い場面は
`docs/architecture/screen-design.md` 13.9「狭い画面（760px 以下）」が正典。2026-09-20 からの「上段をタブで切り替え、下段のキャラビューと
入力欄を常に出す」形と覆した理由は `docs/history/decision.md`「requirements.md 4.7 / screen-design.md 13.9 狭い画面（タブ切り替え・
キャラビュー常設・「≡」の落ちてくる面。2026-10-09 に覆した記録）」。

**タスクのモーダル（「一覧を見る」で開く、左に一覧・右に詳細のモーダル）は、狭い画面では2列を
縦に積む**（2026-09-28 決定。2026-09-20 の「1タスク＝1枚のカード」は、表をやめたので置き換えた）。
一覧が上で高さを区切って内側で転がし、詳細が残りの高さで内側で転がし、下の操作の帯は箱の下端に
残す。組み替えるのは CSS だけで、部品の側は広い画面のまま書く（一覧と詳細を行き来する画面の
切り替えは持たない。切り替え画面〔`docs/architecture/screen-design.md` 13.9「切り替え画面」〕の積み方と同じ）。
値は `docs/architecture/screen-design.md` 13.12。**レポートの中の表はこの対象ではない**（`docs/architecture/screen-design.md`
13.3「領域の内幅に入りきらない表は、その表だけ横スクロールさせる」）。

**右下は入力欄**で、比率は CSS だけで決まる（1枚にまとめた理由と、そこが空いていた頃の経緯は
`docs/history/decision.md`「requirements.md 4.7 画面レイアウト」）。

- **上段と下段で縦の仕切り位置が違う。** 上段はメインが広くサイドバーが狭い、下段は半々。
  これは CSS の grid で表す
- **代償**: 領域を別々のウィンドウ（別モニタなど）に分けることはできない。今の構想では不要
