# tsukumo 要件定義: 画像の添付

ステータス: **ドラフト**。入口は `docs/requirements.md`（要件定義の全体）。

責務: 4.10 画像の添付（入力欄に画像を添える道。SDK 側の裏取り・受け取り方・上限・見え方・会話内容の扱い）。
読む時: 画像を貼る・送る・控えを見せる・原寸を持つ場所に触るとき。
直す時: 画像の添付の要件を変えたとき。

## 4. 機能要件

### 4.10 画像の添付

**入れる**（元の指示は `docs/history/decision.md`）。2.2 の「画像やファイルの
貼り付け」のうち、**画像だけを覆した**。

#### 渡せることの裏取り

**Agent SDK には画像を渡す道がある**（型定義と公式ドキュメントで確認。出典の一覧は
`docs/history/decision.md`「requirements.md 4.10 画像の添付 / 渡せることの裏取り」）。
`SDKUserMessage.message` の `content` に `image` ブロックを混ぜれば渡り、
**`Base64ImageSource`（`{ data, media_type, type: "base64" }`）で渡せ、形式は `image/jpeg` /
`image/png` / `image/gif` / `image/webp` の4つだけ。** **単発入力（Single Message Input）は画像を
受け付けない**ので、ストリーミング入力の側にいることが条件になる。

**tsukumo は最初からストリーミング入力の側にいる**（`createPromptStream` が `query` に「まだ
終わらない」非同期イテレータを渡している。4.1）。**渡し方を変えずに、`content` を文字列から
配列にするだけで済む。**

#### 受け取り方

**貼り付け（`paste`）・ドロップ（`drop`）・入力欄の下の画像のボタン（ファイルを選ぶ窓）の3つ。**
**クリップボードの画像を貼るのが主な道**で、これは `@` の補完では埋められない穴そのもの
（下の「ファイルは覆さない理由」）。操作の案内は入力欄の下の道具の行に1行で出す
（「画像は貼り付けかドロップでも」）。**ボタンもある**（ボタンを足す前の形は
`docs/history/decision.md`）。選ぶ窓で選べるのは受け付ける4種だけで、ほかの種類は貼り付けと
同じく黙って落ちる。

#### 上限

**`docs/architecture/character-pack.md`「画面から作るときの置き場と受け取り方」（キャラクターパックの素材）の上限はそのままは使えない。** 向きが違い
（あちらは1つのパックが持てる総数、こちらは1件の依頼に添えられる数）、**受け付ける形式は
API 側で決まっている**。

| 何                        | 上限                                                                            |
| ------------------------- | ------------------------------------------------------------------------------- |
| 画像1枚（デコード後）     | 5 MiB（API の天井「base64 で1枚 10 MB」の内側で、スクリーンショットが収まる幅） |
| 1件の依頼に添えられる枚数 | 2 枚                                                                            |
| 控え1枚（デコード後）     | 128 KiB（長辺 320px の webp。下の「記録の大きさが有界になる」を数にしたもの）   |
| 形式                      | `.png` / `.jpg` / `.gif` / `.webp` の4つ                                        |
| WebSocket の `maxPayload` | 16 MiB（2 枚 × 5 MiB の base64 ≒ 13.33 MiB ＋ 控え2枚 ≒ 0.34 MiB ＋ 文面）      |

- **形式は tsukumo の都合ではなく API の天井。** `Base64ImageSource.media_type` が上の4つしか
  取らないので、**`.svg` は渡せない**（立ち絵は `.svg` を受け付けるが、あちらは画面に描くだけで
  モデルへは渡らない。同じ「画像の上限」に見えて別の制約）
- **枚数を 2 枚に絞ったのはリクエスト全体の天井のため。** 1枚あたりを 5 MiB まで緩めたので、
  枚数まで広いと base64 が API の 32 MB に届きうる（2 枚なら ≒ 13.3 MiB で当たらない）。
  「スクリーンショットを1〜2枚貼る」という主な使い方は 2 枚で足りる
- **`maxPayload` を上げても依頼の文面は緩まない**（`MAX_PROMPT_TEXT_LENGTH` の 20,000 文字が
  別に効いている）

#### 画面での見え方

**送る前は入力欄の中の小さな札、送ったあとは依頼に付く控え。**

- **送る前**: 添えた画像が `<textarea>` の上に**小さな札**（縮めた絵と外す `×`）で並ぶ。
  **1枚も無いときは何も出ない**ので、常設の枠にならない
- **送ったあと**: 依頼の記録（`request`）に**縮めた控え**が付き、仕事のときはメインビューの
  依頼の見出しの下に、雑談のときは利用者の発言の吹き出しの中に並ぶ（`docs/architecture/screen-design.md` 13.7。
  LINE / Discord と同じ見え方になるのはここ）
- **札も控えも押すと原寸を拡大して見られる**（ホバー・フォーカスで虫眼鏡を
  重ね、押すと画面の内側に収めた拡大の面が開く。閉じ方は Esc・背景のクリック・閉じるボタンの
  3つ）。控えは押した瞬間に id で下の「棚」から原寸を取りに行き、**残っていれば原寸を、棚から
  落ちていれば控えを代わりに拡大して「原寸はもう手放したので、控えを拡大しています」と1行
  添える**

#### 会話内容の扱い（この機能の形そのもの）

**画像も会話の内容**（`docs/coding-standards.md`「会話内容の扱い」）。**この制約は注意書きではなく、
上の形の決め方そのものになっている。**

- **ディスクに書かない。** 原寸はブラウザのメモリ → WebSocket の1フレーム → サーバのメモリ →
  SDK の子プロセス、と流れるだけで、**どこにも書き出さない。一時ファイルに落とす案は採らない**
  （`src/server/adapter/` に新しい書き込み先が増え、「どこに置きいつ消すか」という問いが
  生まれる。`Base64ImageSource` で直接渡せるので、そもそも要らない）。**例外は雑談で貼った画像だけ**で、渡す道とは別に、会話のアーカイブの置き場へ原寸を7日だけ保存する。
  範囲は `docs/coding-standards.md`「会話内容の扱い」の表の4行目、形は `docs/architecture/chat-mode.md`
  4.9「会話のアーカイブ」。仕事の画像は今までどおり書かない
- **原寸はサーバのメモリの「棚」に直近ぶんだけ残る**（
  `src/server/session-driver/core/prompt-image-shelf.ts`）。記録（`SessionState`）と `hello` に載るのは
  控えと id の組だけで、原寸は棚にしか無い。**捨てる契機は2つ**——記録の窓（4.9のターン数。
  仕事20・雑談100）から依頼が落ちたときと、棚が持つ原寸の合計の大きさが
  `MAX_SHELVED_PROMPT_IMAGE_BYTES`（128 MiB。枚数の上限から変えた経緯は
  `docs/history/decision.md`）を超えたとき（古いほうから）。**どちらの契機でも、棚はディスクに
  書かない**（プロセスのメモリにだけ置く。上の1つめの約束のまま）。**上の「控えも押せる」は、
  棚に原寸が残っている間だけ効く**
- **控えだけを記録に残すので、記録の大きさが上限を持つ。** 原寸を `SessionState` に積むと
  雑談の 100 ターン（4.9）で数百 MiB に届きうるが、控えなら1枚あたり数十 KiB で収まる。
  **縮めるのはブラウザ側**で、サーバは受け取った控えをそのまま `request` に載せるだけ
  （**サーバは画像を加工しない**）
- **経路は既にあるものをそのまま使う。** 起動トークンと `Origin` の照合・zod の検証・定型文の
  `error` が効く WebSocket の `prompt` コマンドに足すだけで、新しい書き込み口（POST）を作らない
  （`docs/architecture/character-pack.md`「画面から作るときの置き場と受け取り方」と同じ判断）
- **Claude Code が自分の transcript に何を書くかは変わらない**（`~/.claude/`。文面と同じ
  扱いで、4.8 の復元はそこを読む）。**tsukumo が新しく残す場所を作らない**、というのがここでの約束（雑談の画像の7日の保存だけが例外。上の1つめ）

#### ファイルは覆さない理由

**2.2 のうち覆したのは画像だけで、ファイルの貼り付けは対象外のまま**（理由は 2.2 の
「ファイルの貼り付け」。**画像だけが例外なのは、クリップボードの画像にパスが無いから** —
`@` で埋められない穴はそこ1つしかない）。
