# 進捗管理とHandoffの詳細

`CLAUDE.md`の「進捗管理とHandoff」節にある5手順の詳細（`develop/tasks.json` /
`develop/progress.md` のフィールド定義、difficultyの基準と委譲の書き方、evidenceの粒度、
アーカイブのトリガーと手順）。**手順そのものはCLAUDE.md側が正典**で、ここには繰り返さない。

## tasks.json のフィールド

各タスクは以下のフィールドを持つオブジェクト:

| フィールド     | 内容                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| `id`           | `T-` に3桁の連番を付けた通し番号（例: `T-XXX`）                                |
| `task`         | タスクの内容（背景・理由が分かるように具体的に書く）                           |
| `status`       | `todo` / `doing` / `done`                                                      |
| `difficulty`   | `haiku` / `sonnet` / `opus`（実行に使うモデルの目安。下記）                    |
| `passes`       | 完了条件を満たしたか（`boolean`）                                              |
| `evidence`     | 完了の証拠（コミットハッシュ、テスト件数、生成物へのパス、目視確認の結果など） |
| `dependencies` | 先に完了している必要がある他タスクの `id` 配列                                 |

## difficulty（タスクの難易度）

タスクごとに必要な判断の重さを3段階で表す。**モデル名だが「どのモデルを使うか」ではなく
「どれだけの判断を要するか」を表すラベル**として扱い、タスクを登録した時点で付ける。
難易度に応じて実行モデルを切り替える運用で、**`difficulty` の値がそのまま委譲先サブ
エージェントのモデル指定になる**（下の「difficulty に応じたモデルの切り替え方」）。ラベルの
定義そのものは「判断の重さ」のままで、モデル指定を兼ねることで変わらない。

| 値       | 基準                                                                                                                                             | 例                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `haiku`  | 機械的な作業。判断がほぼ不要で正解が1つに定まる（ファイルの移動、名前の一括置換、ドキュメントへの追記）                                          | 例: 吹き出しの枠線文字を定数に切り出す                         |
| `sonnet` | 通常の実装。設計判断はあるが局所的で、既存の方針・前例に沿えば決まる。複数ファイルにまたがる分割やテスト追加を含む                               | 例: JSONLの追従処理を1ファイルに切り出す、hookスクリプトの追加 |
| `opus`   | 方針・設計そのものの判断が必要。既存の原則との衝突を解く、選択肢のトレードオフを比較する、並行性やエラー方針など間違えても気づきにくいものを扱う | 例: 実装スタックの選定、立ち絵の素材形式と描画方式の決定       |

運用ルール:

- 迷ったら1段上を選ぶ（判断を要するタスクを機械的に処理させるほうが、その逆より事故が大きい）
- 「作業量が多い」ことは難易度を上げる理由にならない。**判断の質**だけで決める
- 着手してみて想定より判断が必要だと分かったら、`difficulty` を上げてから再開する
- 完了済み（`done`）のタスクには遡って付けない。実行前の見積もりに使う値なので、
  完了後は `evidence` が実績を語る

## difficulty に応じたモデルの切り替え方

**タスクを実行するときは、`difficulty` に沿ったモデルを指定したサブエージェントに依頼する。**
`haiku` のタスクは `haiku` の、`sonnet` は `sonnet` の、`opus` は `opus` のサブエージェント。
**メインセッションがどのモデルで動いているかは判断材料にしない。** ユーザーは `/model` で
メインのモデルを普通に切り替えるので、メインを基準にすると `difficulty` が実行モデルを
表さなくなる（メインを基準にすると、`/model` で切り替えた瞬間に同じ `difficulty` のタスクが
別のモデルで実行されてしまう）。

セッションを実行しているモデル（Claude Code のメインループ）は**自分自身のモデルを途中で
変えられない**。切り替えの手段がサブエージェントへの委譲しかないのはこのため。

- メインのモデルと `difficulty` がたまたま一致するタスクでも委譲する。委譲するとコールド
  スタートのぶん損になるが、**`difficulty` と実行モデルが常に一致することを優先して
  受け入れる**
- **委譲しないケース**: ユーザーへの確認が必要なタスク（サブエージェントはユーザーに
  質問できない）と、会話中の文脈に依存するタスク。これは**モデル選択とは別の軸**で、
  「どのモデルで実行するか」ではなく「サブエージェントに投げられるか」を決める。方針決めは
  メインで済ませてから、決まった作業だけを委譲する。`opus` のタスクは方針決めそのものを
  含むことが多く、これに当たりやすい。該当する場合は `/loop` の自動進行に載せず、
  ユーザーがいるセッションで扱う。**このときだけメインセッションが実行し、実行モデルは
  `difficulty` と一致しない**
- サブエージェントは**まっさらな文脈で起動する**ため、`tasks.json` の `task` 本文だけで
  作業が完結するように書く（対象ファイル・完了条件・チェックコマンドを通すことを明記する）
- 委譲したタスクも、完了報告をそのまま信用せず、チェックコマンドの結果で受け入れを判定し、
  `evidence` はメイン側で書く。**表示まわりのように自動チェックで捉えられない変更**は、
  `docs/architecture.md`「手で確かめること」の手順で目視確認した結果を `evidence` に書く

## progress.md の構成

以下の4セクションで構成する:

- **完了したこと**: 何を、なぜ、どう検証したか（コミットハッシュ・テスト件数を添える）。
  **このセッション分のみ**を書き、過去セッション分はアーカイブへ移す（下記）。
  配下の小節は **`### YYYY-MM-DD 〜` の形**にし、見出しの先頭に日付を置く。
  「どこまでが今回のセッションか」をファイル自身から機械的に決めるため
  （`grep '^### ' develop/progress.md` で日付を拾い、**最新の日付以外は過去セッション分**）。
  日付の無い小節は境界が決められないので作らない
- **次にやること**: 未着手タスクの一覧（`tasks.json`の`id`を添える）
- **未解決**: 判断が必要で保留中の事項
- **注意**: 誤解しやすい前提・外部リソースの状態など、次回セッションで踏み外しやすい点

## 良いevidenceの書き方

「完了しました」という宣言だけでは合格にしない。次のような、後から検証可能な形で残す:

- コミットハッシュ（`commit e59c410` のように）
- チェックコマンドの通過件数（テスト件数が変わっていれば増減が分かる）
- 生成物や検証ログへの具体的な参照
- 目視でしか確かめられないもの（描画結果など）は、**どの環境で何を見たか**を1行で
  （例: `Orca / Sixelで立ち絵が表示され、吹き出しが最新のセリフに追従`）

**書かないこと**: 設計変更の物語、検討して撤回した案、手動検証の手順の詳細、
変更したファイルの列挙。これらは後から誰も参照しないわりに `tasks.json` を肥大化させ、
毎セッション冒頭に全件読む運用のコストを押し上げる。判断の経緯を残したい場合は、
要件に関わるものは `docs/requirements.md`、設計に関わるものは
`docs/architecture.md` か下記のアーカイブへ書く。目安として1タスクのevidenceは
**3行以内**に収める。

## コミットメッセージ

タスクに対応するコミットは、**件名の先頭にタスクIDを置く**（`T-110: コミットメッセージに
タスクIDを振る`）。`git log --oneline` にIDが出るので、後から `git log --grep='T-110'` で
そのタスクの変更だけを引ける。

- **1タスク＝1コミット**なので、IDは1件だけ書く。複数タスクにまたがる変更はコミットを分ける。
  分けられない場合に限り `T-105, T-108: 〜` とカンマ区切りで並べる
- **タスクIDを持たない作業にはIDを付けない**（運用の変更、typo修正、アーカイブなど）。
  無理に採番しない
- **過去のコミットは遡って書き換えない**。履歴の書き換えは破壊的操作で、得られるものより
  失うもののほうが大きい

`docs/coding-standards.md`「タスク番号を書かない」はコードとドキュメントについての規約で、
コミットメッセージは対象外。IDはアーカイブ後も `docs/history/tasks-archive.md` に
`## T-XXX` の節として残るため、参照先が消えた識別子にはならない。

## 指示メモ（`develop/direction.md`）

ユーザーからの指示は、チャットではなく `develop/direction.md` に書く。書式は課さない
（雑な箇条書きでよい）。**このファイルは「まだタスクになっていない指示」の置き場**で、
セッション開始時に中身があれば、他の作業より先にタスク化する（`/plan-tasks` スキル）。

- 判定は「見出し行以外に中身があるか」。`grep -v '^#' develop/direction.md | grep -v '^\s*$'`
  が空なら未対応の指示は無い
- 1項目＝1タスクとは限らない。分割も統合もしてよい。ただし**「各項目 → 生成したタスクID」の
  対応表を必ず報告する**（取りこぼしの検知点がここしかないため）
- **タスク化した時点で `develop/direction.md` を空にし、内容は `docs/history/direction.md` へ
  日付見出し付きで移す。** タスクが全部 `done` になるまで残す運用にはしない。残すと正典が
  `develop/tasks.json` と二重になり、片方だけ直したときに気づけないため。進捗の追跡は
  `develop/tasks.json` の `status` が担う
- 移すときは**当時の記述をそのまま**にし、後から書き換えない（アーカイブ全般と同じ扱い）。
  ユーザーの生の言い回しは、噛み砕いた後のタスク本文とは別の情報として残す価値がある
- 指示の前提が古い・既に対応済みだった場合は、勝手に消さずタスク化の報告に理由を書く

## 肥大化したときのアーカイブ

`develop/tasks.json` と `develop/progress.md` は毎セッション冒頭に読むファイルなので、増え続けさせない:

- `develop/tasks.json` の完了タスクの詳細な記録 → `docs/history/tasks-archive.md`
  （evidenceは「コミットハッシュ・テスト件数・アーカイブへの参照」に置き換える）
- `develop/progress.md` の過去セッションの「完了したこと」 → `docs/history/progress-archive.md`

アーカイブは当時の記述をそのまま移すだけにし、後から書き換えない（当時のファイル名・型名が
現在と違っていても履歴としてそのまま残す）。

### いつ移すか（トリガー）

判定する時点は2つある。**どちらも `develop/tasks.json` を読む／書く直後**で、増えたまま次の
セッションへ持ち越さないためにある。

- **セッション開始時**（`/next-task` の手順1）
- **タスクを登録した直後**（`/plan-tasks` の手順5）。登録がファイルを大きくした当事者なので、
  その場で判定する

**2つのファイルを同じ検査点でまとめて判定する。** 片方だけ該当したら、その片方だけを移す。

`develop/tasks.json` の基準:

- `status: done` が **10件以上**
- または `done` のタスクが占めるサイズが **30KB超**

**`todo` のタスクはこの判定の対象外**（サイズにも件数にも数えない）。`todo` はこれから
やる作業の待ち行列で、アーカイブする先が無い。ファイル全体のサイズで判定していた頃は、
`todo` だけで30KBを超えると「基準は超えているのに移せるものが1件も無い」状態になり、
毎回トリガーだけが鳴って何も起きなかった。判定するのは**減らせるものだけ**にする。

```bash
python3 -c "
import json,os
ts=json.load(open('develop/tasks.json'))
d=[t for t in ts if t['status']=='done']
print(len(d), len(json.dumps(d,ensure_ascii=False)))"
```

`develop/progress.md` の基準:

- 「完了したこと」配下に、**最新の日付以外の小節が1つでもある**（＝過去セッション分が残っている）

```bash
grep '^### ' develop/progress.md
```

`todo` と同じ理屈で、「次にやること」「未解決」「注意」の3節はサイズ判定に含めない
（アーカイブする先が無いため）。

**`tasks.json` の `done` を移すときは `progress.md` も同じ検査点で見る。** 片方だけ
メンテされて片方が伸び続けるのを防ぐため、判定を別々のタイミングに置かない。

### 何を移すか

- `done` のタスクは**全件**アーカイブする（直近セッションで完了した分も含む）。直近セッションの
  記録は `develop/progress.md` の「完了したこと」が担うため、`develop/tasks.json` 側に
  別途残す必要はない
- `develop/progress.md` の「完了したこと」は、**最新の日付の小節だけを残し**、それ以外を
  `docs/history/progress-archive.md` へ移す。「次にやること」「未解決」「注意」は移さない
  （未完了タスクの完了条件がこれらを参照していることがある）
- タスクIDの通し番号は再利用せず、常に続きから採番する

### `dependencies` の扱い

- アーカイブ済みタスクのIDを指す `dependencies` は**そのまま残す**（書き換えない）
- **`develop/tasks.json` に存在しないタスクIDは「アーカイブ済み＝完了」とみなす**。
  依存解決の際は
  `develop/tasks.json` の `id` 一覧に無い `dependencies` エントリを完了済みとして扱ってよい
