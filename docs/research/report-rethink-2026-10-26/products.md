# LLM が人に向けて構造化された出力を返すことの先例（2023〜2026）

調査日: 2026-10-26。一次情報源（公式ドキュメント・仕様・論文・公式ブログ）を WebFetch で読めたものだけを「事実」に書く。ページ本体が取れず検索結果の引用に頼ったものは **（検索引用）** と付け、確かめられなかった数字・日付は **未確認** と書く。
この文書は調査の記録であって正典ではない。提案の全体は同じ置き場の `index.html`。

比較対象（tsukumo の現状）: `report` ツールの JSON Schema 約 22,000 字・description 121 個・block 21 種・chart 7 種・形の札 14 種・`figure` 必須（置かない理由を enum）・機械検査 44 条・30 日で受け付け 4,652 件／差し戻し 805 件（1 文目の字数 354、スキーマ不一致 111）。

## 要点（7 つ）

1. **「名前付きの塊を n 種」の n は、先例では 13〜36 に収まる。** ProseMirror schema-basic 13（node 9 + mark 4）、A2UI 標準 18、Slack Block Kit 21、Adaptive Cards の要素・入力・アクションで約 26、Notion API の block type 32。tsukumo の 21 種は範囲内で、先例に無いのは「札 14 種 × 塊 21 種の対応表」と「図を置かない理由を言わせる欄」の層。（Slack: https://docs.slack.dev/reference/block-kit/blocks ／ Notion: https://developers.notion.com/reference/block ／ ProseMirror: https://prosemirror.net/docs/ref/#schema-basic ／ A2UI: https://developers.googleblog.com/en/introducing-a2ui-an-open-project-for-agent-driven-interfaces/）
2. **Anthropic は「ツール定義が 10 個以上、または 10k tokens 超なら文脈から外せ」「選択精度は 30〜50 個で落ちる」と明記し、JSON Schema は「構造は言えるが使い方は言えない」と述べている。** 121 個の description で使い分けを教える現状はこの警告の対象。（https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool ／ https://www.anthropic.com/engineering/advanced-tool-use）
3. **Structured Outputs（strict）はスキーマ不一致を消せるが、制約が強い。** 再帰スキーマ不可・数値の min/max 不可・文字列長不可・`minItems` は 0/1 のみ・strict ツールの optional パラメータは合計 24 個・union 型は 16 個まで。現状の 22,000 字のスキーマはこの枠に収まる可能性が低く、「1 文目の字数」のような意味の検査は原理的に対象外。（https://platform.claude.com/docs/en/build-with-claude/structured-outputs）
4. **「何を描くかを先に決め、形はあとで選ぶ」段分けは、2023 年の LIDA から 2025 年の Multimodal DeepResearcher まで一貫し、数字で効いている。** LIDA は goal（question + visualization + rationale）を先に出し、コード生成の error rate 3.5%。DeepResearcher は planning を抜くと 85% 負け（最大の悪化）。Claude Docs の chart ガイドも「WHAT TO DRAW, BEFORE HOW」を冒頭に置く。（https://ar5iv.labs.arxiv.org/html/2303.02927 ／ https://arxiv.org/abs/2506.02454）
5. **Generative UI の標準は「LLM は部品名 + props の JSON を書き、描く側がカタログで検証する」（A2UI・json-render）と「LLM は何も描かず、サーバが HTML を iframe で出す」（MCP Apps・OpenAI Apps SDK）の 2 系に収斂した。** どちらも「LLM に自由な HTML を書かせない」点は同じで、A2UI は「declarative data format, not executable code」、json-render は「AI can only use components in your catalog」。（https://a2ui.org/ ／ https://github.com/vercel-labs/json-render ／ https://modelcontextprotocol.io/extensions/apps/overview）
6. **出力トークンは記法で 30〜67% 減る。** TOON は JSON 比 72.2% vs 71.4% の精度で tokens 2,474 vs 4,308。OpenUI Lang（旧 Thesys C1）は json-render の JSON 比で 893 → 294 tokens（-67%）。いずれも「スキーマを文脈に載せる」費用ではなく「出力」の費用の話で、Markdown + フェンス方式はスキーマを載せない点で最も軽い。（https://github.com/toon-format/toon ／ https://cdn.jsdelivr.net/gh/thesysdev/openui@main/README.md）
7. **「文字で済むときは文字」の既定は、製品側では分類器と短いルールで実装されている。** ChatGPT Canvas は「開くか否か」の判定を 83%（文章）/94%（コード）に鍛え、ChatGPT のデータ分析は「構造化した表示が有益なときだけ表やグラフ」、OpenAI Apps の指針は「人が理解できる最小の表現を選べ」、Claude Docs は「表の全列を描いた図は表の繰り返し」。図の有無を enum で正当化させる先例は見当たらない（未確認）。（https://openai.com/index/introducing-canvas/（検索引用）／ https://developers.openai.com/apps-sdk/build/custom-ux）

### tsukumo への含意

- 業界は「LLM に部品名 + props を書かせてカタログで検証」か「LLM には描かせずサーバの HTML を iframe で出す」の 2 系で、tsukumo の `report` は前者。前者の先例（A2UI 18・shadcn 36）と比べて **21 種の塊そのものは多くない**。異質なのは、部品の上に「札 14 種 → 第一候補／代替／禁止」の対応表という 2 層目があることで、A2UI も json-render もこの層を持たず、どの部品を使うかは LLM の判断に委ねて検証はスキーマだけにしている。
- 検証の作法も違う。A2UI は「未知の部品は落とさず graceful fallback」、json-render は「カタログの外は出せない」ように生成側（system prompt）を作る。tsukumo の「44 条で差し戻す」は、どちらの系にもない事後の反復で、差し戻し 805 件（17%）はその費用。
- 「自由 HTML」系（Gemini dynamic view・Artifacts・MCP Apps）は表現の自由を最大にする代わりに「1 分以上かかることがある」「検証なし」。tsukumo は作業の最後に 1 回描く用途なので、この系は図 1 枚のためには重い。

## 2. チャットアシスタントの描き方

### 事実

- **ChatGPT データ分析**（2024-05-16、検索引用: openai.com は 403）: Python を書いて実行して描く。表は自動で対話的。カスタマイズできるグラフは bar / line / pie / scatter。ヘルプ記事は「create tables or charts **when the output benefits from a structured view**」とし、対話的なのは「only bar, pie, scatter, and line charts」、非対話で出せるのは histogram, box plot, heat map, area, radar, treemap, bubble, waterfall など（検索引用: https://help.openai.com/en/articles/9213685）。
- **ChatGPT Canvas**（2024-10-03、検索引用: openai.com は 403）: 文章とコードのための別窓。「いつ開くか」を学習させ、zero-shot GPT-4o の指示ベースラインに対して文章 83% / コード 94% の判定精度。「Help me cook a new recipe」のような Q&A で開かないことを明示的な目標にした。
- **Claude Artifacts**（support.claude.com）: 自動で作る条件は「significant and self-contained, typically over 15 lines」「likely to want to edit, iterate on, or reuse outside the conversation」「stands on its own」。種類は「documents, code snippets, single-page websites, images, diagrams and flowcharts, dashboards, and small interactive tools」。内部の型（HTML / React / SVG / Mermaid / Markdown / code）はリークした system prompt を根拠とする二次情報で、**公式では未確認**。
- **Claude Docs（claude.ai の文書製品）**: MCP の `guide` で得たガイド（2026-10-26 取得。公開 URL なし）。チャートは 2 通り—(a) 行データから手で `<svg>` を描く `<claude.Visualize>`、(b) 閉じた文法 `definition`（mark は bar / line / area / point / tile の 5 種 ≤8、annotation は rule / span、`Stat`、`Table`（cell ≤10）、small multiples）。「any other key is refused BY NAME with the fix」。図は手書き SVG（「既存の ```mermaid block → edit it in place, never convert it」）。冒頭に **「WHAT TO DRAW, BEFORE HOW → the one or two measures this doc's reader decides from, not every column its table offers: a table holds everything, a reader decides from one or two things, and a chart of all the table holds only repeats the table」**、「The chart carries its numbers ONCE」、「the finding in the title, with its number」、「GREY FIRST」。描いたあとは screenshot を読み直して「Adversarial review (correct is not enough)」を回す。
- **Gemini**: 1 節の通り。既定は Markdown で、「visual layout」「dynamic view」は Labs の実験として利用者が選ぶ。
- **Perplexity**: 2025-11-21 の changelog「Live price information for stocks, cryptocurrencies, and other financial assets now appears directly within answers on web」。Finance ページにチャート・ヒートマップ。天気ウィジェットの公式記述は**未確認**。
- **Notion AI**（help FAQ）: 生成するのは「outline, email draft, or table」と Notion のブロック、画像（「diagrams, flowcharts」）。チャートは Notion のデータベースビュー（bar / donut / line は Computerworld の二次情報、**公式では未確認**）。
- **Cursor Plan Mode**（2025-10-07）: 計画は「a Markdown file with file paths and code references」。計画内の Mermaid 描画は Cursor 2.2 のフォーラム告知による（二次、**未確認**）。
- **Claude Code**: CLI は Markdown を生のまま表示（GitHub issue #13600 の機能要望）、Desktop の Code タブは ```mermaid を描かない（issue #52517）。つまり出力の表現は Markdown の文と表のみ。**Codex は未確認。**

### tsukumo への含意

- 主要製品の既定は全部「文字（Markdown）」で、図や別窓は (a) 利用者が選ぶ（Gemini の Labs、Notion の /AI Block）、(b) 判定器が「開くべき場面」を当てる（Canvas 83/94%）、(c) データの性質から決まる（ChatGPT: 表データがあるときだけ表・グラフ）のどれか。「毎回のレポートで図の有無を宣言させる」形は見当たらない。
- 図の種類数は少ない。ChatGPT の対話的グラフは 4 種、Claude Docs の mark は 5 種 + Stat + Table。tsukumo の chart 7 種は多くはないが、Claude Docs は「種類」ではなく「mark × 軸 × split」の合成で表しており、種類を増やさず表現を増やす方針。
- Claude Docs の「what to draw, before how」と「表の全列の図は表の繰り返し」は、tsukumo の `figure` 必須欄の逆向き。先例は「置く理由」を問い、tsukumo は「置かない理由」を問う。「置く理由」を問う側に揃えると、図が要らない大多数の報告で欄が消える。

- 全系で「**意図（question / goal / plan）を先に文で書き、表現（mark・encoding）はあとで選ぶ**」が共通し、抜くと一番効く（DeepResearcher の planning 85%）。tsukumo の「形の札 14 種」は表現の分類で、意図ではない。「この節で読者が決めるものは何か」を 1 行書かせてから形を選ぶほうが先例に沿う。
- 表現の記法は grammar of graphics 系（mark + encoding）が主流（LIDA の Altair、FDV の mark/scale/layout、Claude Docs の mark 5 種）。「chart 7 種」の名前で持つより、mark（bar / line / point / area）× 軸 × split の合成にすると、種類を増やさずに「数直線」（point + 線形 x 軸 1 本）も「円グラフ」（arc）も表せる。
- ChartGPT の「1 段で 1 パラメータ」は精度を取る代わりに呼び出し回数を増やす。tsukumo は 1 回のツール呼び出しなので、段を増やすなら「意図 1 行 + 表現」の 2 段までが現実的。

**Structured Outputs（Anthropic）**

- 2025-11-14 に public beta（Sonnet 4.5・Opus 4.1）、2026-02-04 に GA。2 方式: `output_config.format`（JSON）と `strict: true`（ツール）。constrained decoding で「No more JSON.parse() errors」「No retries needed for schema violations」。
- 対応しないもの: 再帰スキーマ、enum 内の複合型、外部 `$ref`、**数値制約（minimum / maximum / multipleOf）**、**文字列制約（minLength / maxLength）**、`minItems` は 0 と 1 のみ、`additionalProperties` は false 固定。pattern は後方参照・lookaround・単語境界なし。

### tsukumo への含意

- 22,000 字のスキーマのトークン数は**未計測**だが、Anthropic の目安「定義が 10k tokens を超えたら文脈から外す」に近い可能性が高く、しかもこれは毎ターン載る（Tool Search の「3〜5 個だけ非 defer」の推奨から見ても、report は使用頻度が低い）。Agent SDK の MCP ツールなら `defer_loading` 相当（ToolSearch）で呼ぶときだけ読ませる手がある。
- Anthropic 自身が「スキーマは使い方を言えない」「brittle logic をプロンプトに書くな」「ambiguous decision points を作るな」と言っている。121 個の description と 14 × 21 の対応表は、まさに「使い方」をスキーマで言おうとしている形。`input_examples` 数個（各 100〜200 tokens）のほうが 72% → 90% の実績がある。
- strict / Structured Outputs は tool-error 111 件（2.4%）には効くが、スキーマがこの枠（optional 24・union 16・再帰なし・配列長なし）に入らないと使えない。21 種の block を oneOf で持つ現状はまず union の上限に当たる。1 文目の字数 354 件（7.6%）は意味の検査で、どの方式でも生成側の制約では消えない—検査するなら「字数」でなく「読み上げの 1 文目を別欄に短く書かせる」など構造で避けるほうが先例（OpenAI の「2 action まで」「3〜8 件」のような量の指針）に近い。
- 出力の記法では JSON が最も重く、TOON / OpenUI Lang が 30〜67% 軽い。Markdown + フェンスはさらに「スキーマを載せない」ので文脈側も軽い。ただしフェンスは「レンダラが拾わなければ生テキストが見える」（Claude Code がその状態）ので、描く側（tsukumo はブラウザ）がフェンス名を全部持つ前提になる。
