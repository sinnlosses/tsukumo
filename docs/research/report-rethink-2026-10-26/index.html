3. 筋の悪さの診断（6 点）

各点を「いまの形 → 先例・理論が言うこと → なぜ筋が悪いか」の順に書く。前回のレビュー（tsukumo-audit-2026-10-26.html の 4-1〜4-12）が個々の症状を挙げたのに対し、ここでは構造の原因だけを 6 つに束ねた。

3.1 判断の入力が「書き手の解釈（札）」で、データの形ではない

いま: 書き手は節ごとに形の札 14 種（cause・connection・position・state・time・order・quantity・choice・attribute・mapping・comparison・boundary・parallel・single）を選び、札ごとの表（第一候補・許す代替・許さない）に従う。

先例: APT（1986）から Draco（2019）・Draco 2（2023）まで、自動選択の入力はデータの型（名義・順序・量・時間）・基数・読者の課題で、出力は符号化（mark × チャネル）。Observable Plot の auto は「x/y があるか・順序か・単調か・集約か」の 10 行弱の条件分岐で mark を決める（github.com）。LLM は「型の決まった少数から 1 つ選ぶ」は 80〜86% 当てるが、「どの形が良いか」の好みは人の知覚実験の指針から大きく外れる（DracoGPT、idl.uw.edu）。

なぜ悪いか: 札は書き手の主観で揺れ、同じ材料に別の札が付く。機械は札の正しさを確かめられないので、検査は「札が許さない塊を使ったか」（56 節）という間接の形にしかならず、しかもそれは差し戻しの 7% の一部でしかない。判断の良し悪しを LLM の好みに任せる形は、理論からも実証からも支持されない。

3.2 表現を「名前付きの塊」で列挙し、増やすには塊を足すしかない

いま: 塊 21 種＋chart 7 種（bar・line・pie・arrow・slope・span・share）。「数直線」のような新しい形は塊か chartKind を足す。足すたびに describe・描画・検査の条・文書が増える。

先例: Vega-Lite は mark 原始 11＋合成 3 と encoding 41 チャネルの組で広い範囲を表す（vega.github.io）。Claude Docs の図の文法は mark 5 種（bar・line・area・point・tile）＋annotation（rule・span）＋Stat＋Table で、種類を増やさず「mark × 軸 × split」の合成で表現を増やす。名前付きの塊の数は先例でも 13〜36（ProseMirror 13・A2UI 18・Slack 21・Adaptive Cards 約 26・Notion 32）で、21 という数そのものは中央にある。

なぜ悪いか: 数が多いことではなく、合成がないことが問題。Draco は命令的コード 4,324 行の推薦器を hard 70・soft 110 の制約で再実装して同じ答えを返した（記述量 1/20、idl.cs.washington.edu）。名前の列挙は「列挙した分しか描けず、検証は塊ごとに別条が要る」ので、44 条が塊別に増えてきた構図はこの方式の必然。

3.3 「使い方」をスキーマの説明文 121 個と条 22 で教え、毎ステップ載せている

いま: 22,001 字のスキーマと 5,140 字の規約が、仕事のセッションの全ステップ（30 日で 59,688）の文脈に載る。report を呼ぶのは 1 ターンに 1 回で、ツールを何度も走らせる長いターンでは大半のステップが使わない。

先例: Anthropic は「ツール定義が 10 個以上、または 10k トークンを超えたら文脈から外す（Tool Search）」「JSON Schema は構造（型・必須・enum）は言えるが使い方は言えない」「input_examples 数個で複雑なパラメータの精度 72% → 90%」「brittle logic をプロンプトに書くな」と書いている（platform.claude.com、anthropic.com）。LLM の図生成の研究でも、効いたのは段階の分解と少数の例で、長い規則の列挙が効いた報告は見つからなかった（theory.md 5 節）。

なぜ悪いか: 常設の定義は「レポートを書かないステップ」にも載り、context rot（文脈が長いほど想起が落ちる）の側に効く。しかも 121 個の説明文は使い方を言おうとしているので、Anthropic の注意の対象そのもの。費用の本体は差し戻しの往復ではなく、この常設の重さにある（差し戻し 805 回 × 約 140k トークンの cache read ≒ 30 日の総量の 0.6% と小さい。常設は全 59,688 ステップに載る）。

3.4 figure を必須にして「置かない理由」を言わせる

いま: 欄 figure は必須で、図を置かないときは short-answer / no-shape / single-value / no-material の enum で理由を言う。理由と本文が食い違うと差し戻す（figure-contradiction 31 件）。

先例: 会話型 UI で「文だけ」を選ぶ人は 41%、個人内で 82〜89% 一貫し、推奨は「文脈つきの図を既定にし、個人設定で切れるようにする」（Hearst & Tory 2019、ischool.berkeley.edu）。APT の expressiveness は「余計な情報を表す図は誤りになり得る」と定義し、置かないほうが正しい場合を理論の側に置く。ChatGPT Canvas は「開くか否か」を分類器で判定（83%／94%）、Claude Docs は「表の全列を描いた図は表の繰り返し」と置く理由を問う。図の有無を enum で正当化させる先例は見当たらなかった。

なぜ悪いか: 理由の既定値化（no-shape 213・short-answer 174 がほぼ全部）と帳簿合わせの差し戻しを生み、書き手には毎回の正当化の字数を、器には矛盾検査の条を要求する。利用者は 1 人なので、「図派／文派」の既定を 1 つ持てば欄ごと要らない。

3.5 色・座標・一覧・要約など、器が決められる・知っていることを書かせている

いま: svg の塊は座標を書き手が書く。files は触ったファイルの一覧を書き手が書く（tsukumo は git の差分を知っている）。sessionSummary・sessionRemaining・waitingLine・title はセッションの帳簿で、毎回書き直させる（出力の 8%）。

先例: 座標を書かせる器（JSON Canvas・DiagrammerGPT）はどれも配置を直す往復が前提で、宣言型（Mermaid・D2・DOT・Vega-Lite）は座標を持たない（engines.md 要点 1）。自動修復の研究は「実行エラーはほぼ解けた。残るのは色・はみ出し・配置」と結び、色覚対応を満たす図は 33.3% にとどまる（arxiv.org）。Few の bullet graph の仕様は色を 1 色の濃淡に固定し、設計側の既定にしている。

なぜ悪いか: 書き手が苦手で器が得意なこと（座標・色）を書き手に、器が既に知っていること（差分・要約）を書き手に、どちらも書かせている。svg 67 件・dimension 212 件は、その代償を払って描いた図。

3.6 検査の重心が「表現の形」にあり、「データと符号化の整合」にない

いま: 44 条の大半は 1 文目 50 字・セル平均 35 字・見出しの有無・note の密度など、文章の体裁。本文の数と図の値の一致、集約の単位、軸の型（名義に折れ線）を見る条は無い。

先例: LLM の図生成の誤りは 73.8% がデータ側（絞り込み・軸の値）で、視覚側は 26.2%（arxiv.org）。Draco の hard 制約は「shape は量を表せない」のような expressiveness の違反を機械で落とす。Claude Docs は「違反は名前と直し方を返す」閉じた文法で、事後の条文を持たない。

なぜ悪いか: 71% の差し戻しが文章の体裁で起き、読み手の判断に効くデータ側の誤りは誰も見ていない。字数は読者の理解の代理にならず、一度も「読んで分かるまでの時間」を測っていない（前回レビュー 4-3）。

5. 提案: 理想の形 ——「問いと数を申告し、形は器が決める」

5.1 原則 5 つ

① 問いと数を先に、形はあとで図を置く箇所では、書き手は「読者がそれで決めること（問い）」1 行と、数（列の型・値・単位）と「関係」（比較・順位・割合・前後・傾向・区間・分布・相関の 8 語）だけを書く。形（棒・折れ線・数直線・円・帯）は器の決定表が決め、書き手は form: で上書きできる（上書きは数えるだけで差し戻さない）。
② 本文は Markdown、図は型つきフェンス 8 種塊 21 種を「本文（Markdown）＋フェンス 8 種（figure・graph・mermaid・table・code・callout・claims・image）」に畳む。表は Markdown の表（状態セルは ✓ 通過 のような印）、採否・見比べ・対応表は列の形で表に戻す。
③ 検査は文法と整合だけ、体裁は数えるか器が整える差し戻すのは、フェンスが解釈できない・expressiveness の違反（名義に折れ線、部分 6 以上の円）・本文の数と図の値の不一致・帳簿の欄の欠け、の約 10 条。1 文目の長さ・セルの長さ・見出しの有無は数えるだけにし、器が折り返し・畳みで整える。
④ 器が決められること・知っていることは書かせない色・座標・配置・値ラベルの位置は器。触ったファイルは git の差分から器が出す。セッションの要約・残り・待ちの一言は、report の外で器が別に作る（小さいモデルの脇の問い合わせ）。
⑤ 図の有無は利用者の既定利用者が「図派／文派」を 1 つ持つ。決定表の第一候補が「文」の行では図を出さず、「図」の行で利用者が文派なら、表か値つきの 1 文に落とす。書き手は置かない理由を書かない。

5.3 決定表（データの形 → 表現）

入力は書き手が申告する 列の型（N 名義・O 順序・T 時間・Q 量）・基数・関係（8 語）。出力は第一候補・代替・置かない形・必須の注記。tsukumo のレポートに出る材料（件数・前後・所要・依存・手順）に合わせて 12 行に絞った（理論メモの 15 行から、tsukumo で出ない行を落とした）。基数の境（3・5・7・20）は Few／APT の慣例に基づく目安で、実証された閾値ではない。

5.5 検査の作り直し

いまの条（44） 提案 理由
文の長さ・体裁 14 条（1 文目 50 字・結論の長さ・段落 3 文・文のセル・note の密度・矢印・見出し…） 数えるだけ 差し戻さない。1 文目が長ければ器が headline を 1 行に折り返し、長い段落は畳む 差し戻しの 71%。字数は理解の代理にならず、体裁は器のほうが確実に整えられる

5.7 文脈への載せ方

  • 常設にするのは原則 5 つと例 1 つ（約 1,500 字）だけ。 「レポートの記法」122 行は、原則と例に書き直す。条の番号で参照する形はやめる（Anthropic「適切な高度」）。
  • ツール定義は約 4,000 字（欄 6、フェンス名 8、関係の語 8）。塊ごとの describe は無くし、使い方は input_examples 相当の例 4 つ（作業・判断・調べもの・止めた）で示す。
  • 図の文法と決定表の全文（約 1,500 字）は、呼ぶ直前に 1 回だけ渡す。 実装の口は 2 つあり、(a) report ツールを ToolSearch の遅延読み込みにして定義を呼ぶときだけ載せる、(b) 最初の差し戻し（または work_plan の最後の段）で「文法カード」を返す。(a) は Agent SDK の MCP ツールで効くかを確かめる（9 節）。
