# UI をカタログで見る仕組み: 案の比較と推奨（2026-09-21）

**この文書は提案であって正典ではない。** `docs/` の他ファイルにある「節の索引」はここには作らない。
採用したら正典（`docs/architecture.md`「手で確かめること」・`CLAUDE.md`「テスト方針」）へ反映し、
この文書は経緯として `docs/research/` に残す。

**対象コミット**: `main` の `c2507e5`。**実測環境**: macOS（darwin 25.6.0 / arm64）、
手元の Google Chrome（`playwright-core` の `channel: "chrome"`）、`bun run` は Bun 1.3 系。
**きっかけ**: ユーザーの指示（2026-09-20）「そろそろ storybook など、UIの状況をカタログで
見ることができるものを作ってもいいかもね。」

**結論（3行）**

1. **足りていない。** ただし足りない理由は「部品の単位が無いこと」ではなく、**いまの道具が
   撮れていないもの**だった。`notation` の場面は 1358px のうち **855px（63%）が1枚に入らず**、
   「表・図・グラフを見るための場面」なのに**図もグラフも一度も撮れていない**（実測）
2. **推す案は 2（`capture-catalog.ts` に「撮る前の操作」を持たせ、疑似セッションの見本を厚くする）。**
   依存は1つも増えず、`bun build` に触らず、目視の手順の文面も変わらない。Playwright で
   スクロール・押す・打つ・`location.hash` の4つを実際に試し、**いま撮れていない状態が
   すべて撮れることを確認済み**
3. **Storybook は推さない。** 直接3つ（`storybook` / `@storybook/react-vite` / `vite`）、
   推移で**新規 126 パッケージ**（プラットフォーム別の optional 込みで 222）が増え、
   いまの 368 に対して +34%（+60%）になる。加えて `docs/design.md` 11章の明文の決定
   「**Vite は足していない**」を覆し、**Vite が組み立てた class 名は `bun build` が焼くものと
   別の綴りになる**ので、カタログで見た絵は tsukumo が実際に配る成果物ではなくなる

**結論（追記・2026-09-21）**: 案2 を採用し、`docs/architecture.md`「手で確かめること」へ反映した
（正典はそちら）。

## 1. いまの道具が撮れるもの・撮れないもの（実測）

すべて 2026-09-21 に実際に走らせて確かめた。推測は含まない。

### 1.1 走らせた結果

| 走らせたもの                                        | 結果                                                           |
| --------------------------------------------------- | -------------------------------------------------------------- |
| `bun run scripts/capture-catalog.ts`                | 12枚 / **22.5秒**（6場面 × 2サイズ。1場面あたり 3.74秒）       |
| `bun run scripts/capture-catalog.ts --only <1件>`   | 2枚 / **4.3秒**                                                |
| `bun run scripts/capture-view.ts <URL> --measure …` | 1枚 + 要素の位置と大きさ。横のはみ出し 0px                     |
| `bun build src/browser/main.tsx --target=browser`   | 577 modules / **41ms** / `main.js` 2.54MB + `main.css` 40.53KB |

**疑似セッションの場面は9件あるが、カタログに載っているのは6件。** `test/fixture/fake-session.json` の
`turns[].name` は `report` / `permission` / `question-multi` / `question-pair` / `question-long` /
`notation` / `narration` / `long-tool` / `interim-flicker` の9件で、`capture-catalog.ts` の
`CATALOG` に無い `narration` / `long-tool` / `interim-flicker` は撮られない。

### 1.2 撮れていないもの（4つ）

**(1) 領域の内側のスクロールの下 — これが一番大きい穴。**

`notation` の場面を 1400x900 で開いて DOM を測った値:

| 測ったもの                             | clientHeight | scrollHeight | 写らない量                            |
| -------------------------------------- | -----------: | -----------: | ------------------------------------- |
| `[data-region="main"]`（メインビュー） |          503 |         1358 | **855px（63%）**                      |
| サイドバーの塊のスクロール             |          107 |         1150 | 1043px（タスク24件中2件しか写らない） |
| キャラビューの中                       |          313 |          347 | 34px                                  |

**`fullPage` は効かない。** `document.documentElement.scrollHeight` は **900**（窓と同じ）で、
ページ自体はスクロールしない。スクロールしているのは領域（`layout-main`）の内側なので、
`capture-catalog.ts` の狭い側の `fullPage: true` も `capture-view.ts` の `--full` も何も足さない。

実際に切れているもの（`capture-view.ts --measure` の実測値。いずれも main の bottom 521 より下）:

| 要素                          | 位置と大きさ          | 中身              |
| ----------------------------- | --------------------- | ----------------- |
| `[data-region="main"] svg`    | top 567.86 / 高さ 278 | mermaid の図      |
| `[data-region="main"] canvas` | top 863.11 / 高さ 475 | chart.js のグラフ |
| `cols` / `card`               | 図の手前（画像の外）  | 横並びのカード    |

つまり **`notation` は「引用・ネスト・区切り線・表・図・グラフ」を見るために置いた場面なのに、
図とグラフは1枚も撮れたことがない。**

**(2) 手を動かさないと出ない状態。** いまの経路は「起こす → 待つ → 撮る」だけなので、
次は一度も撮られていない:

- タスク一覧のモーダル（サイドバーの「一覧を見る」）— `sidebar/task-board.tsx`
- `/` のコマンド補完 — `dispatch/command-suggestions.tsx`
- `@` のファイル補完 — `dispatch/file-suggestions.tsx`
- キャラクター画面（`#character`）と作る画面（`#character/new`）— `components/page/character/` の5ファイル

**(3) 部品の状態の網羅。** レポートの記法は `markdown/notation.tsx` の `NOTATION_CLASS_NAMES` が
**12の class**（`note` / `note-warn` / `note-ng` / `note-favor` / `badge` / `badge-ok` /
`badge-warn` / `badge-ng` / `cols` / `card` / `stats` / `stat`）を解決するのに、疑似セッションの `notation` が
書いているのは `note-warn` / `badge-ok` / `cols` / `card` の**4つだけ**。
**`note` / `note-ng` / `note-favor`（お願い）/ `badge-warn` / `badge-ng` / `stats` / `stat` の
7つは一度も描かれていない。**

**(4) class セレクタの probe は空振りする。** `capture-view.ts --measure '.report-note'` は
「無し」を返した。bun の CSS Modules は `report-note_nkMPPQ` の形に焼くため
（実測した `className`: `"report-note_nkMPPQ report-note-warn_nkMPPQ"`）、
**`[class*="report-note"]` なら当たる**。道具の使い方の話で、道具の欠陥ではない。

### 1.3 画像には本物のデータが写る

サイドバーのタスク一覧に出るのは `develop/tasks.json` の**実データ**（実在のタスクIDと要約）。
疑似セッションの会話は架空でも、**画像そのものは架空ではない**。`docs/architecture.md`「撮った画像は
リポジトリに置かない」は、会話だけでなくこの理由でも守る必要がある。

### 1.4 撮れなかった状態は、すべて Playwright で撮れた（実測）

`capture-catalog.ts` が使っているのと同じ `playwright-core` で、配信中のページに次の4つを
当てて撮ってみた。**4つとも成功した**:

| 当てた操作                           | 撮れたもの                                               |
| ------------------------------------ | -------------------------------------------------------- |
| `main.scrollTop = main.scrollHeight` | chart.js のグラフが1枚に収まった（それまで写らなかった） |
| 「一覧を見る」を `click()`           | タスク一覧のモーダル全体                                 |
| `textarea` に `/` を `type()`        | `/clear` `/compact` のコマンド補完                       |
| `location.hash = "#character"`       | キャラクター画面（立ち絵6枚・差し色4色・背景・画面の色） |

**疑似セッションにもサーバにも手を入れずに済んだ。** 足りないのは仕組みではなく、
`capture-catalog.ts` が撮る前に何もしないことだけだった。

## 2. 何を見たいのか

3つの問いに分けると、いまの穴の位置がはっきりする。

| 見たいもの         | 例                                               | いまの経路で見られるか                                     |
| ------------------ | ------------------------------------------------ | ---------------------------------------------------------- |
| **画面の状態違い** | 答え待ちの箱・許可プロンプト・狭い窓での積み替え | **見られる**（これがいまの `capture-catalog.ts`）          |
| **部品の状態違い** | `note` の4種・`badge` の3種・選択肢の長いラベル  | 半分。疑似セッションが出した分だけ、かつ画面に写った分だけ |
| **記法の見本**     | 表・図・グラフ・カード・数値の並び               | **見られない**（63%が写らない）                            |

**tsukumo で崩れるのは、部品そのものよりも「領域に入れたときの見え方」のほうが多い。**
実際に過去のタスクが追いかけたのは、選択肢のラベルと説明の重なり、吹き出しの折り返し、
立ち絵の往復、横のはみ出し、狭い窓での積み替え — どれも**部品単体を単独で並べても見えない**。
部品を1つずつ白い背景に並べる形（Storybook の既定の姿）は、この種の崩れに対しては効きが弱い。

一方で「`note-favor` が本当にお願いらしく見えるか」「`badge-ng` の赤が読めるか」は
部品の単位の問いで、**いまは疑似セッションに書かれていないから見られない**だけである。

## 3. 案

### 案1: 現状維持（比較の土台）

何もしない。穴（1.2 の4つ）はそのまま残る。

### 案2: `capture-catalog.ts` に「撮る前の操作」を持たせ、疑似セッションの見本を厚くする（**推奨**）

カタログの1件を `{ scene, label }` から `{ scene, label, prepare }` に広げ、撮る前に当てる操作を
名前で持つ。操作は 1.4 で成功した4種（領域の中をスクロール・要素を押す・入力欄に打つ・
`location.hash` を書く）だけで、それ以上は増やさない。あわせて疑似セッションの `notation` に、
描かれていない7つの class（`note` / `note-ng` / `note-favor` / `badge-warn` / `badge-ng` /
`stats` / `stat`）を書き足す。

- **触るファイル**: `scripts/capture-catalog.ts` と `test/fixture/fake-session.json` の2つ
- **増える依存**: 0（`playwright-core` は既に devDependency にある）
- **`bun build`**: 触らない。撮るのは配信中の本物のページなので、class 名も本番と同じ
- **効くところ**: 1.2 の (1)(2)(3) がすべて塞がる。(4) は道具の使い方をコメントに書けば済む
- **失うもの**: 部品を props で直接並べる見方は手に入らない。状態を1つ足すには
  疑似セッションに場面か文面を足す必要があり、1件あたり 3.74秒 の撮り直しがかかる

### 案3: `capture-catalog.ts` に部品を名指しして描く経路を足す

場面（疑似セッション）とは別に、**部品名と props の表**を `capture-catalog.ts` が持ち、
`page.evaluate` でページの中に描かせて撮る。

- **増える依存**: 0
- **`bun build`**: 描かせる部品は配信中の束の中にあるので、**部品を外から名指しするための
  口をブラウザ側に出す必要がある**（`window` に置くか、カタログ用の入口を作るか）。
  どちらも「製品のコードにカタログのための穴を開ける」ことになり、`CLAUDE.md`
  「テストのためだけに公開しない」に正面からぶつかる
- **効くところ**: 部品の状態違いは見られる
- **失うもの**: **領域に入れたときの見え方は見られない**（2章のとおり、tsukumo で崩れるのは
  そちらが多い）。また 37個の `.tsx` のうち **12個が session store を読む**
  （`useSessionSelector` / `useSessionDispatch`）ので、それらは偽の姿を用意しないと描けない

### 案4: 部品を並べる軽いページを自前で作る（`#catalog` の画面）

`stores/screen.tsx` の `Screen` に `catalog` を足し、`#catalog` で部品の一覧を出す画面を
`src/browser/features/` の下に作る。`createSessionStore()` と `SessionStoreContext` は
どちらも export 済みなので、偽の姿を `receive(frame)` で流し込んで本物の部品を描ける。
`/character/*` も `/vendor/*` も `/repository-file` も**同じサーバが既に配っている**ので、
立ち絵も mermaid も chart.js も追加の配線なしで出る。

- **増える依存**: 0
- **`bun build`**: 入口は `main.tsx` のままで、束ねは1本のまま。**ただしカタログの中身が
  製品の束（いま 2.54MB）に乗る。** 別エントリにすれば乗らないが、`bundle.ts` が2本目を
  扱う分岐を持つことになる（同じ `bun build` に2つ目のエントリを足しても CSS Modules の
  ハッシュは一致することは実測済み — `portrait_34ZLUQ` が両方の `.css` で同じ綴りだった）
- **効くところ**: 部品の一覧が1ページに出て、それを `capture-catalog.ts` の
  `location.hash` 操作（案2）でそのまま1枚に撮れる。画面が1つ増えるだけなので、
  目視の手順は「`#catalog` も見る」の1行で済む
- **失うもの**: `src/browser/` に「製品では使わない画面」が住む。4番目の画面になるので、
  `stores/screen.tsx` のコメント「画面は3つで、分岐は hook 1つで足りる」を書き換える

### 案5: Storybook を入れる

`.storybook/` を置き、`*.stories.tsx` を書く。

**増える devDependency（npm registry の実測、2026-09-21）**

| 段                    | 名前                                                                 |           数 |
| --------------------- | -------------------------------------------------------------------- | -----------: |
| 直接                  | `storybook@10.6.0` / `@storybook/react-vite@10.6.0` / `vite@8.3.0`   |        **3** |
| 推移（必須のみ）      | 上の3つから辿れる依存の閉包 241、うち既に入っているもの 19           | **新規 126** |
| 推移（optional 込み） | esbuild / rolldown / lightningcss のプラットフォーム別バイナリを含む | **新規 222** |

いまの `node_modules` は **368 パッケージ / 598MB**。+126 で **+34%**、+222 で **+60%**。
`@storybook/react-vite` の peer は `vite ^5–^8` と `typescript`、`storybook` の peer は
`vite-plus` と `@types/react` と `prettier`。

**`bun build` との関係**

- **組み立てがもう1系統になる。** `docs/design.md` 11章に「**Vite は足していない**」が
  明文の決定として書いてある（HMR を持たず、`refresh` フレームで作り直しを押す形を選んだときの
  決定）。Storybook を入れるとこれを覆す
- **class 名の綴りが変わる。** CSS Modules のハッシュを焼くのは組み立てた側なので、
  Vite が作る綴りは `bun build` が作る `report-note_nkMPPQ` とは別物になる。
  **カタログで見ている絵は tsukumo が実際に配る成果物ではない**。design.md 11章が
  「CSS だけを取り直す道は使わない」と決めた理由（片方だけ新しくすると綴りが食い違う）と
  同じ落とし穴を、系統ごと増やすことになる
- **配信の口を別に用意しないと部品が描けない。** 立ち絵（`useQuery` で `/character/<file>` を
  fetch してインライン化）・mermaid と chart.js（`vendor-script.ts` が `/vendor/*` を `<script>` で
  読む）・`@` の補完（`/repository-file`）は、どれも tsukumo のサーバが配っている。
  Storybook の dev サーバからは、proxy を書くか全部 mock するかのどちらかが要る
- **TanStack Query の Provider も decorator で用意する必要がある**（`main.tsx` にしかない）

**効くところ / 失うもの**: 部品の状態違いを props で切り替えて見る体験は一番良い。
代わりに、**目視の手順が2系統になる**（`bun run start` の本物と `storybook dev` の別プロセス・
別URL）。`CLAUDE.md`「ブラウザに出た絵は自動テストで守らない」の方針のもとでは、
「本物を見る」道が1本であることに価値がある。

## 5. 推奨

**案2 を採る。**

理由は3つ:

1. **いま痛んでいるのは部品の単位ではなく、撮れていない 63% のほう**だった（1.2）。
   案3・案4・案5 はどれも「部品の単位」を足す案で、**63% の穴は1つも塞がない**
2. **依存が増えず、`bun build` に触らず、目視の手順の文面も変わらない。**
   撮るのは配信中の本物のページなので、見えている絵は tsukumo が実際に配る成果物そのもの
3. **4つの操作が実際に効くことを確認済み**（1.4）。推測ではなく、やって撮れた

**次の段として案4 を残す**（いまは採らない）。案2 を当てたあとで「部品を1つずつ並べて見たい」が
実際に困りごととして出てきたら、そのときに `#catalog` の画面を足す。案4 は案2 と衝突せず、
案2 の `location.hash` 操作をそのまま再利用できる。

**案5（Storybook）は採らない。** 増える 126〜222 パッケージに見合う効きが、
このリポジトリの崩れ方（領域に入れたときの見え方が中心）に対して立たない。加えて、
Vite が焼く class 名が `bun build` のものと別になる以上、**カタログが「本物を見る」道ではなくなる**
ことが、`CLAUDE.md`「ブラウザに出た絵は自動テストで守らない／目視で確かめる」という方針と
噛み合わない。将来 `src/browser/components/` が（いまの2つから）十数個に増え、かつ
それらが領域から切り離して意味を持つようになったら、そのときに再検討する。

## 6. 案2 を当てるときの形（採用時の目安）

1. `CatalogEntry` に「撮る前に当てる操作」を足す。操作は判別可能な合併型で4種だけ持つ
   （領域の中をスクロール / 要素を押す / 入力欄に打つ / `location.hash` を書く）。
   `undefined` は許さず「何もしない」を明示の1種にする
2. `CATALOG` に、いま撮れていない状態を足す — メインビューを下まで送った `notation`、
   タスク一覧のモーダル、`/` の補完、`@` の補完、キャラクター画面、作る画面
3. `test/fixture/fake-session.json` の `notation` に、描かれていない7つの class を書き足す
4. `capture-view.ts` の冒頭コメントに、**class セレクタで測るときは `[class*="…"]`**（CSS Modules が
   `名前_ハッシュ` に焼くため）を1行で残す
