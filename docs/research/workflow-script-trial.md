## 設計に効くこと

- 関門はワークフロースクリプトの agent にも掛かる。ただし `lap-hook` は `agent_type` の末尾が `no-delegate`・`general-purpose` のときだけ `delegate` を書くので、ワークフロースクリプトの `agent()` が既定の型のままだと計測が書かれない。ワークフロースクリプトで `agentType` を指す必要がある。
- `isolation: 'worktree'` は未送信のコミットを持たない。送り出し前の枝の上で並列に直させる設計には使えず、`main`（`origin/main`）に載った内容を前提にする。
- ワークフロースクリプトはこのセッションの途中で足した保存済みのファイルを読まなかった。`/reload-skills` か次のセッションで読まれるかは未確認。
- ワークフロースクリプトの agent は tsukumo の MCP の道具を最初から持たず、`ToolSearch` で引いてから呼ぶ。ワークフロースクリプトの依頼文に「`ToolSearch` で引く」1行を入れる。
- ワークフロースクリプトの agent が `phase_result` を呼べるので、帯はワークフロースクリプトの完了を待たず段ごとに進む。ワークフロースクリプトが schema で返してメインが `work_plan` に写す形は要らない。
- ワークフロースクリプトの agent の `speak` は、メインや別の agent の直前の `speak` からあいだに新しい事実が無いと差し戻される。ワークフロースクリプトの中でセリフを言わせるなら、段ごとに事実（`phase_result` の戻りなど）を挟む。
- ワークフロースクリプトの完了通知は委譲ゲートを立てない。メインは通知を受けたあと、`work_plan` を呼ばずに作業の道具を使える。ただし帯はワークフロースクリプトの agent の `phase_result` で先に進んでいるので、メインの `work_plan` は進んだ位置のまま渡す。
- 計測の確かめには `tw metrics --stages` が使えない（送り出したタスクだけを数える）。`.git/task-workflow/flow/` の台帳を直接読んだ。

## ワークフロースクリプト版と今の流れの比べ方

調査メモ6章の項目4の比べ方。タスクの再試集は `claude -p` を1回起こすだけで、委譲・受け入れ・振り返りの流れそのものを再試できない（`docs/architecture/testing/harness-replay.md`「再試しないもの」）ので、今の流れは再試せず、送り出し済みの記録を基準線にする。

### 比べ方

- 比べる件は、再試集の凍結した10件のうち、今の流れで送り出した記録（台帳の段の時刻）と、タスクごとのトークンの記録（`token-usage` の `taskId`）が両方残っている 未知 kind の件（sonnet・bug）と 引用記号の件（sonnet・feature）の2件。同じタスクを両方の流れで比べるので、難しさと触る広さは揃う。
- 今の流れは再試しない。基準線は、その2件を送り出したときの記録。
- ワークフロースクリプト版は、再試集と同じ手順で起こした一時の作業ツリー（着手前のコミット、現在のハーネスを重ねたもの）で流す。流したあと `checkFiles` を置いて `command` を打ち、合否を見る。結果は main に送らず、作業ツリーと枝は消す。
- 流す回数は1件1回（k=1）。2件の数は傾向の確認であって、有意差の検定には足りない。

### 見る数と取り方

| 数             | 今の流れ（基準線）                                                                                                                           | ワークフロースクリプト版                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 合否           | 送り出し済み（`checkFiles` が通る）                                                                                                          | `checkFiles` を置いた `command` が通るか                                                                           |
| 所要           | 台帳の `claim` から `done` までの秒（`verify` の秒を含む）                                                                                   | ワークフロースクリプトの `Workflow` の `duration_ms`（ワークフロースクリプトの中は `Date.now()` が使えず測れない） |

### 「同等以上」の基準

次を全部満たしたら同等以上とする。

1. 2件とも合否が通る。
2. 所要とトークン（入力+出力+キャッシュ作成。キャッシュ読みは別に並べる）が、どちらも基準線の 1.25 倍以内。
3. 差し戻しの回数が基準線以下。

1.25 倍は、直近28日の `lead_median_seconds`（994 秒）が `long_delegation` などの外れ値で大きく振れること、基準線が1件ずつの1回きりの記録であることを見込んだ幅。基準線との差が幅の内側でも、ワークフロースクリプト版が一方的に重いときは「同等」と書かず、数をそのまま並べる。

### 試作のワークフロースクリプトの形

- agent は1件あたり最大7体（差し戻しが上限の2回まで続いたとき）: 実装（`difficulty` と同じ model）1、受け入れ（opus）最大3、直し（実装と同じ model。受け入れが差し戻したときだけ）最大2、振り返り（haiku）1。差し戻しが無ければ3体、1回なら5体。`Workflow` の規模の目安（10体未満）に収まる。
- 受け入れの輪の上限は2回（今の流れの `review-rounds.md` と同じ）。
- schema: 実装 `{summary, changedFiles}`、受け入れ `{verdict: accept|reject, findings[]}`、振り返り `{signal: none|some, note}`。
- ワークフロースクリプトは `Workflow` をメインから呼ぶ。`SKILL.md` と `tw` の既存の流れには手を入れない。

使い捨てのワークフロースクリプトの骨組み（`id` を `args` で受け、一時の作業ツリーの絶対パスを依頼文に渡す）:

```js
phase("Implement")
const impl = await agent(`${COMMON}\n依頼の本文を読み、完了条件を満たすよう実装する。`, {
  schema: IMPL,
  agentType: "tsukumo-workflow:no-delegate",
  model: "sonnet",
})
phase("Accept")
let rounds = 0,
  verdict = null
for (let i = 0; i < 3; i++) {
  verdict = await agent(`${COMMON}\n未コミットの差分が完了条件と規約を満たすか判定する。`, {
    schema: REVIEW,
    agentType: "tsukumo-workflow:acceptor",
  })
  if (verdict.verdict === "accept" || i === 2) break
  rounds += 1
  await agent(`${COMMON}\n指摘を直す: ${JSON.stringify(verdict.findings)}`, {
    schema: IMPL,
    agentType: "tsukumo-workflow:no-delegate",
    model: "sonnet",
  })
}
phase("Retro")
const retro = await agent(`${COMMON}\n環境の改善候補があったかだけを返す。`, {
  schema: RETRO,
  agentType: "tsukumo-workflow:no-delegate",
  model: "haiku",
})
return { impl, finalVerdict: verdict, rejectRounds: rounds, retro }
```

## ワークフロースクリプト版と今の流れの比べた結果

ワークフロースクリプト版を 未知 kind の件・引用記号の件 で1回ずつ流した（2026-11-01。一時の作業ツリーは消し、結果は main に送っていない）。ワークフロースクリプトは agent の transcript の `usage` を合計し、基準線は台帳と `token-usage` の `taskId` が一致する記録の合計。

| -------------- | ------------------------ | --------------------- | ------------------- | ------------------------------------ | -------------------------- | -------- | ----------------- |
| 未知 kind の件 | 今の流れ（記録）         | 送り出し済み          | 398（うち検証 131） | 189,469                              | 3,273,182                  | 0        | 記録なし          |
| 未知 kind の件 | ワークフロースクリプト版 | 通る（2ファイル39件） | 221                 | 167,561                              | 849,654                    | 1        | 1（`bash-guard`） |
| 引用記号の件   | 今の流れ（記録）         | 送り出し済み          | 543（うち検証 119） | 118,906                              | 2,810,734                  | 0        | 記録なし          |

- 差し戻しは、基準線が台帳で続く2つの `review` の `start` の間に `verify` かコミットが挟まる組の数、ワークフロースクリプト版が受け入れの輪の差し戻しの数。引用記号の件の基準線は `review` の `start` が3秒差で2回立っているが、間に `end` も `verify` も無い二重の記録で、差し戻しは0。
- 関門の拒否は、基準線をタスクごとに取る口が無い（`hook_tally` は期間の集計）。ワークフロースクリプト版は agent の transcript の `is_error` のうち hook の文言を含む数。

### 結論

- **合否・所要・トークンは基準線の 1.25 倍以内（実際は 0.27〜0.88 倍）。基準の1と2は満たした。** ワークフロースクリプト版の所要は 221・145 秒で、基準線の 398・543 秒（検証を除いても 267・424 秒）より短く、入力+出力+キャッシュ作成は 0.88・0.78 倍、キャッシュ読みは 0.26・0.21 倍だった。
- **基準の3（差し戻しの回数が基準線以下）は満たさなかった。** 未知 kind の件はワークフロースクリプト版が1回差し戻されて基準線の0を超え、引用記号の件は0対0。基準線が今の流れの1回きりの記録なので、1回の差は揺れの範囲かもしれないが、2件でこの基準を満たしたとは言えない。結論は「所要とトークンは同等以上、差し戻しはワークフロースクリプト版が1回多かった」。
- **この差は流れの優劣だけでは説明できない。** ワークフロースクリプト版は次を持たない: 着手の印・`tw verify`（`pnpm run check`）・`tw ship`・同期・申し送り・メインの会話の往復。基準線はこれらと、メインの毎ターンのキャッシュ読みを含む。ワークフロースクリプト版の agent は `pnpm run check` も E2E も走らせていない（引用記号の件 は E2E を足したのに未実行のまま受け入れが通った）。
- **合否は `checkFiles` の通りだけで、規約・全体検査・E2E の通りは見ていない。** 振り返りの agent は2件とも `some` を返し、検証の欠けと一時の作業ツリーの未コミット差分を挙げた。前者はワークフロースクリプトの形で拾う価値がある（下の「残すもの」）。

### ワークフロースクリプト版の形として残すもの

- agent の数・段ごとの model・輪の上限・schema は、上の「試作のワークフロースクリプトの形」のまま使える。未知 kind の件 は5体、引用記号の件 は3体で、`Workflow` の規模の目安（10体未満）に収まった。
- 実装の schema に、実行した検証コマンドとその結果（`pnpm run check` の通り、E2E を足したなら実行したか）の欄を足す。受け入れが「単体だけ通った」状態を通した。
- 着手の印・`tw verify`・`tw ship` はワークフロースクリプトの外（メイン）に残す。ワークフロースクリプトが置き換えたのは、委譲先の起こし方・受け入れの輪・振り返りの呼び出しだけ。
- ワークフロースクリプトの agent にも `bash-guard` は掛かる（未知 kind の件 の実装が1回拒まれた）。関門はワークフロースクリプトの外へ出さなくてよい。

### この比べ方の限界

- 1件1回・2件だけで、揺れ（同じワークフロースクリプトを流し直したときの差）を測っていない。
- 基準線は当時のハーネスで流した記録で、ワークフロースクリプト版は現在のハーネスを重ねた一時の作業ツリーで流した。
- トークンの合計の単位は、基準線（`token-usage`、メインの毎ターンの記録の合計）とワークフロースクリプト版（agent の `usage` の合計）で取り方が違い、キャッシュ読みの比は特に大きく出る。
