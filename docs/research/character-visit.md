# 待ち時間にほかのキャラクターが訪ねてくる仕組み（提案）

最終更新: 2026-09-25（ユーザーの判断を受けて論点2・3・6と「表情の源」を直した。起こしたのは 2026-09-24）
ステータス: **提案であって正典ではない。** 論点ごとに案を並べ、推す案と理由を書く。決まったら
正典（`docs/requirements.md`・`docs/design.md`・`docs/screen-design.md`）へ移し、この文書は
経緯として残す。`docs/` の他ファイルにある「節の索引」はここには作らない（`docs/research/` の慣習）。

発端は 2026-09-24 のユーザーの指示（`docs/history/direction.md` の同日の節）:
長いテストやビルドを待っているあいだに、帳ちゃんなどほかのキャラクターが画面に訪ねてきて、
つくもと話す時間があると楽しい。**決まっていること**は2つ——この段では考えるだけで作らない、
セッションは1つのまま画面に出るキャラクターが増えるだけ。

**2026-09-25 のユーザー判断**（下の各論点に反映済み）:

- 訪問の会話に仕事の会話を使ってよい（論点2）
- 2人目の出し方はデザインし直す。論点3の案は叩き台（論点3）
- claude の子プロセスが一時的に2つになること（複数セッション）は問題にしない（論点6）
- 訪問のあいだだけ表情の源に例外を設けたときの不都合を調べる（「表情の源」の節）
- 上の判断のうえで提案を承認。条件は「うまくいかず元に戻すかもしれないので、revert できるように入れる」（各タスクを1コミットにし、訪問のコードは専用のファイルに寄せる）

この文書では、いつものキャラクター（セッションを持ち `speak` で話すほう）を**あるじ**、
訪ねてくるほうを**客**と呼ぶ（用語集に載せるのは決まってから。識別子の案は `host` / `guest`）。

## 論点1: 訪問の契機

**待っている、と tsukumo が知れる信号は2つ**ある。

| 信号                            | 形                                                                                                      | あるじの様子                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| A. 背景のタスクだけが動いている | ターンが終わっていて（`finished`）、`backgroundTasks` が1件以上                                         | 手が空いている（claude は依頼を待っている）               |
| B. ツールが走りっぱなし         | ターンの中で、トップレベル（`parentToolUseId` が無い）の `tool-started` に `tool-finished` がまだ来ない | 手が塞がっている（ツールの戻りを待って `speak` できない） |

どちらも「長いテストやビルドを待っている」に当たる。答え待ち（許可・質問）は**待たせているのが
利用者**なので契機にしない。雑談モードもしない（往復そのものが会話で、キャラビューも畳まれている。
`docs/screen-design.md` 13.7）。

| 案                                                       | 良いところ                                                      | 悪いところ                                                                                     |
| -------------------------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **1a. サーバの core が状態と経過時間から決める**（推す） | 既にある信号だけで足りる。判断が純関数1つに閉じ、テストで守れる | タイマーを1つ持つ（adapter 側）                                                                |
| 1b. SDK の `tool_progress` の心拍で数える                | 経過秒を SDK が数えてくれる                                     | 信号 A（ターンの外）には届かない。心拍の間隔と、どのツールで届くかを実測していない             |
| 1c. あるじが `speak` で `bored` を選んだら来る           | 「たいくつそうだから来た」という筋が自然                        | 選ぶかどうかがモデル任せで、来るか来ないかが読めない。`bored` を選ばないパックでは永遠に来ない |
| 1d. ブラウザが決めてコマンドを送る                       | 画面の状態を見たまま決められる                                  | タブが2枚あると2回来る。会話を作るのはサーバなので、どのみち往復が1つ増える                    |

**推す: 1a。** しきい値の出発点は次のとおり（値は実物で遊んでから詰める）。

- 信号 A か B が**続けて 90 秒**続いたら来る（短いビルドでは来ない。`bun run check` 1回ぶん程度の
  待ちで来るくらいを狙う）
- **1回の待ちに1度だけ**。**前の訪問から 30 分**は来ない（仕事の邪魔をしない側に倒す）
- 信号 B は**ツールの種類を問わない**（Bash でもフォアグラウンドの委譲でも、あるじが話せない
  ことに変わりはない）
- 判断は `src/server/core/` の純関数（案: `visit-timing.ts`。状態・いまの時刻・前の訪問の時刻を
  受けて「来る／まだ／来ない」を返す）、時計を回すのは adapter。時刻は `Temporal`

## 論点2: 会話を誰が作るか

| 案                                                                       | トークン                                                                   | 会話の外部送信（2.2）                     | 待っている間に話せるか                                      |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------- |
| 2a. いま動いている claude に2人ぶん話させる（依頼を差し込む）            | **仕事の文脈ぶんを毎回読む**（数万〜十数万トークンのキャッシュ読み）       | 当たらない（同じ文脈の中）                | **信号 B では話せない**（ツールの戻りを待って止まっている） |
| **2b. 訪問1回ぶんの台本を、別の使い捨ての `query()` に書かせる**（推す） | 人格2つ（いまの `persona.md` で約 18 KB）＋数行。軽いモデルなら1回数円以下 | 当たらない（下。2026-09-25 ユーザー判断） | 話せる（あるじの手とは無関係に作れる）                      |
| 2c. パックに書いた台本から選ぶ                                           | 0                                                                          | 当たらない                                | 話せる                                                      |

**2a を採らない理由**: 信号 B（いちばんよくある長い待ち）で使えないうえに、差し込んだ依頼が
**仕事の会話に残る**（メインビューにやり取りが立ち、あとの判断の文脈に雑談が混ざる）。背景の
タスクが終わったときの続きのターン（`turn-resumed`）ともぶつかる。

**2c だけにしない理由**: 同じ掛け合いが繰り返されると数回で飽きる。進み具合の言い直しで
「tsukumo 側で定型句を組み立てる案」が「味気ない」と退けられた先例がある
（`src/server/core/speech-cadence.ts` の doc コメント）。

**推す: 2b を主にし、2c を落とし先にする。**

- 台本は**訪問1回ぶんをまとめて1回で作る**（3〜6往復。1行ごとに話し手・表情・セリフ）。
  `outputFormat` の JSON Schema で形を縛り、表情は**各パックの選択肢**（`expression-choice.ts`）
  の中から選ばせる。受け取った台本は境界で検証し、形が崩れていたら 2c へ落とす
- **渡すもの**: あるじと客の人格（`persona.md`）、**いまの仕事の抜き書き**（このターンの依頼の
  文面・直近の数件のセリフ・待っている相手の説明——背景のタスクの `description` か、走っている
  ツールの名前とコマンド）、経過時間、時間帯、**今日の成果**（コミット数と `done` のタスクの
  summary。`achievement.ts`）。仕事の会話を渡してよいことは 2026-09-25 にユーザーが決めた。
  抜き書きにするのは、掛け合いの話題に要るのは「いま何を待っているか」までで、長い文脈は
  トークンを食うだけだから
- 仕事の文脈を丸ごと持たせる手（`resume` + `forkSession: true` であるじのセッションを分けて
  起こす）も SDK にはある。話題はより具体的になるが、1回ごとに文脈ぶん（数万〜十数万トークンの
  キャッシュ読み）を払うので、抜き書きで足りなかったときの次の手に取っておく
- 起こし方: `tools: []`・MCP なし・`maxTurns: 1`・**`persistSession: false`**（transcript を書かない）・
  軽いモデル（haiku を出発点に）。台本はメモリにだけ持ち、ディスクにもログにも書かない
- SDK を呼ぶので置き場は `src/server/adapter/sdk-` で始まる1ファイル（案: `sdk-visit-script.ts`。
  原則3）。台本を組む指示文（何往復・どういう場面か）は core の定数（`speech-cadence.ts` と同じ
  切り分け）
- 作り損ねたとき（起動の失敗・時間切れ・形の崩れ）は、客のパックの `visit` に書いた短い台本
  （2c）から1本選ぶ。それも無ければ来ない。**常駐プロセスは落ちない**

**2.2 の「会話を外部のモデルへ送ること」との関係**: 送り先は仕事の claude と同じ Anthropic の
API で、同じマシンの claude の子プロセスが受ける。2026-09-25 にユーザーが「仕事の会話を渡して
よい」と決めたので、2.2 の「分離や整形のために会話を外部のモデルへ送ること」は**別の
事業者・別のサービスへ送ること**を指す、と読む（`/compact` をこれに当たらないとした 2026-09-21
の補足と同じ向き）。2.2 にこの補足を1行足すのはドラフトの1件目。

## 論点3: 2人目の立ち絵と吹き出しをどこに出すか

**デザインし直す**（2026-09-25 ユーザー判断）。下の 3a は叩き台で、決めた案ではない。
描き直すときも「表情の源」の節の3つの条件（あるじの表情を上書きする範囲）は効く。

| 案                                                                                 | 良いところ                                                                 | 悪いところ                                                             |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **3a. キャラビューの中、あるじの吹き出しの右に客の立ち絵と小さな吹き出し**（推す） | 「下は居る場所」（13.4）に収まる。枠も地も持たない原則のまま（13.1 原則2） | キャラビューが狭いと窮屈。狭い画面の扱いが要る                         |
| 3b. メインビューの上に重ねる                                                       | 広い                                                                       | 読む面にキャラクターを置かない原則（13.1 原則1）を破る。レポートを隠す |
| 3c. 帯の顔の隣に小さく出す                                                         | 場所を取らない                                                             | 小さすぎて「訪ねてきた」感じが出ない。帯は機械の場所                   |

**推す: 3a。**

```
   ◯      ╭──────────────────╮   ╭─────────╮
  あるじ   │ あるじの吹き出し   │   │ 客の吹き出し│
          ╰──────────────────╯   ╰─────────╯
                                      ◦  ← 客（背丈はあるじの半分ほど。帳ちゃんは膝丈）
```

- **入ってくるとき**は端から「ひょこっ」と覗く絵（下の論点7の `peek`）を出してから通常の立ち絵へ。
  **帰るとき**は同じ絵へ戻して引っ込む。動かすのは位置・不透明度だけ（`docs/requirements.md` 4.3
  「1枚の矩形」の範囲。`docs/design.md` 6.5 の `Portrait` 部品の中）
- **掛け合いは2つの吹き出しに交互に出す。** 間は 13.7「セリフは全文で現れ、吹き出しは2秒空ける」
  の2秒を出発点にする。あるじの吹き出しは訪問のあいだだけ訪問のセリフを出し、帰ったら**最後の
  `speak` のセリフに戻す**
- **訪問のセリフはどこにも残さない**（メインビューにも雑談のログにもセリフの記録にも積まない。
  その場限り）。残すと仕事の記録に作り話が混ざる
- 客の吹き出しの色は**客のパックの `accent`**（色はキャラクターの持ち物。13.1）
- 狭い画面（760px 以下。13.9「狭い画面」）では来ない

## 論点4: キャラクターパックを2つ同時に読む形

| 案                                                                                   | 良いところ                                                                  | 悪いところ                                                                                    |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 4a. `speak` に話し手（`speaker`）を足し、あるじの claude に客のセリフも言わせる      | 経路が1本                                                                   | 論点2で 2a を採らないので要らない。enum が2パックぶんに膨らみ、あるじの人格に客の口調が混ざる |
| **4b. `speak` は変えない。客は「セッションを持たないパック」として読むだけ**（推す） | 7章の「1つを選んで切り替える」がそのまま残る。客の姿は 7.2 の一覧に既にある | 訪問の形（台本・客の名前）を運ぶイベントが1つ要る                                             |
| 4c. 客のために2つ目の `SessionManager` を持つ                                        | 客も本物のセッションで話せる                                                | 2.2「複数セッション」そのもの。採らない                                                       |

**推す: 4b。**

- **使用中のパック（あるじ）は今までどおり1つ**で、切り替え・`speak` の enum・`systemPrompt` は
  何も変わらない。客は**立ち絵と人格を借りるだけ**で、セッションも `resume` も持たない
- 客の姿（`CharacterInfo`）と素材の URL は 7.2 で**全パックぶん既に配っている**ので、ブラウザは
  客のパック名だけ知れば描ける
- 運ぶのは新しい `SessionEvent` 2つを出発点に: `visit-started`（客のパック名・台本）と
  `visit-ended`（帰る理由）。畳み込みは `SessionState` に `visit`（来ていない／来ている＋台本）を
  判別可能な合併型で持つ。台本を1行ずつ流すか丸ごと渡すかは、ブラウザの間合い（2秒）を
  どちらが持つかで決まる——**丸ごと渡してブラウザが間合いを持つ**のを推す（再接続したタブが
  `hello` の snapshot で同じ訪問を途中から見られる）
- **誰が来るか**: 客になれるのは**`character.json` に `visit` を持つパックだけ**（論点7。
  持たないパックは来ない——知らないうちに誰でも来る形にしない）。あるじと同じパックは来ない。
  候補が複数なら毎回ひとり選ぶ。止めたい利用者のために設定の歯車（13.9「設定の歯車」）に
  「訪問」のオン・オフを1つ置く
- あるじと客の間柄（つくもは帳ちゃんの世話を焼く兄貴分）は**人格に書く**（原則4。コードに
  書かない）。いまはホームのパック（`~/.tsukumo/characters/tsukumo/persona.md`）の「覚えたこと」に
  1行あるだけで、同梱の `characters/tsukumo/persona.md` にも帳ちゃんの側にもまだ無い

## 論点5: 利用者が話しかけたら訪問をどう畳むか

**帰る合図**（どれか1つで帰る）:

- 利用者が依頼を送った（`request`。入力欄に打ち始めただけでは帰らない——メモ書きのこともある）
- 答え待ち（許可・質問）が積まれた
- あるじが本物の `speak` をした（信号 B のツールが戻った、背景のタスクが終わって続きのターンが
  始まった、など。あるじが仕事に戻った印）
- 待ちが終わった（信号 B のツールが `tool-finished` になった・背景のタスクが終わって
  `turn-resumed` が来た）。あるじが `speak` する前に次のツールへ進むことがあるので、
  `speak` だけを合図にしない
- 台本を言い終えた
- セッションが終わった・起こし直した・雑談モードへ切り替えた

| 案                                                                                         | 良いところ                               | 悪いところ                                 |
| ------------------------------------------------------------------------------------------ | ---------------------------------------- | ------------------------------------------ |
| 5a. その場で消す                                                                           | 速い                                     | ぷつっと切れて、居たことが嘘のように見える |
| **5b. 客が帰りの一言（生成しない定型）を言って引っ込む。あるじの吹き出しは即戻す**（推す） | 利用者の依頼は待たせずに、別れの間がある | 定型の一言がパックに要る                   |
| 5c. 台本を言い終えるまで待つ                                                               | 掛け合いが途切れない                     | 利用者の依頼より訪問を優先してしまう       |

**推す: 5b。** 依頼の送信はそのまま通し（訪問は依頼を遅らせない）、作りかけの台本は捨てる
（`query()` を中断する）。客の吹き出しに `visit.farewell` から1つ出して 1.5 秒ほどで `peek` の絵に
戻して引っ込む。**あるじの吹き出しはその瞬間に最後の `speak` へ戻す**——次に来る本物のセリフと
訪問のセリフを取り違えないため。

## 論点6: 2.2「複数セッション・常駐」に当たらないか

**問題にしない**（2026-09-25 ユーザー判断）。claude の子プロセスが一時的に2つになることは
構わない、と決まった。形は次のまま変えない。

- `SessionManager` は今までどおり**セッションを1つだけ持つ**（`docs/design.md` 8章）。
  利用者が相手にするのはあるじのセッションだけで、客に依頼を送る口は作らない
- 論点2の使い捨ての `query()` は**訪問1回ぶんの台本を返したら終わる**。transcript を書かない
  （`persistSession: false`）、利用者の入力を受けない。寿命は数秒〜十数秒で、tsukumo のプロセスの
  中で閉じる（常駐・client–daemon ではない）

## 論点7: 訪問のためにパックに要るもの

| 要るもの             | 案                                                                                                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客になれる印         | `character.json` に `visit` の節を足す（無ければ客にならない）                                                                                                  |
| 登場と退場の絵       | `visit.peek`（棚の陰から「ひょこっ」と覗く絵。帳ちゃんの設定画にある）。無ければ `default` を不透明度で出し入れする                                             |
| 帰りの一言           | `visit.farewell`（2〜3個の短いセリフ。論点5で生成せずに使う）                                                                                                   |
| 作り損ねたときの台本 | `visit.scripts`（任意。1本 3〜4 行の短い掛け合いをいくつか。論点2の 2c）                                                                                        |
| 表情                 | **新しい表情は足さない**。9つの enum の中で、パックが持つものを使う（帳ちゃんはパックを作るときの割り当て——ねむい→`bored`、にっこり→`proud` か `excited` など） |
| 人格                 | 客としての振る舞いは客の `persona.md` に「訪ねたとき」の節を足すか、台本を組む指示文に任せるか。**推すのは前者**（キャラクターの中身はパック側。原則4）         |

- `peek` を1枚足すと、画像の上限 `MAX_IMAGE_FILES_PER_PACK`（表情の数 + 2。
  `src/server/adapter/character-edit.ts`）に1枚ぶん当たる。**上限を +3 に広げる**のを推す
  （画面から作るパックでも `peek` を置けるように）
- 定義の型と検証は `src/shared/character-definition.ts`。`visit` は丸ごと省略できる任意の節
- 同梱の `characters/tsukumo/` にも `visit` を足せば、別のパックを使っているときにつくもが
  訪ねてくる形にもなる（帳ちゃんがあるじのとき）。最初は帳ちゃんだけでよい

## 表情の源（論点3・5に付随する、要件との関係）

論点3で、訪問のあいだ**あるじの吹き出しに訪問のセリフを出す**と、表情と吹き出しのリンク
（`docs/requirements.md` 4.3。原則は「表情と吹き出しはリンクしていること」）を保つには、
**あるじの表情も台本の表情に合わせる**必要がある。これは「表情の源は `speak` の1つだけ」の
**例外を1つ足す**ことになる。

| 案                                                                                      | 良いところ                                                 | 悪いところ                                          |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------- |
| **例外を足す: 訪問のあいだだけ台本の表情を出し、帰ったら最後の `speak` に戻す**（推す） | 表情と吹き出しのリンクが保たれる。戻し先がはっきりしている | 4.3 の決定に例外が1つ増える（ユーザーの承認が要る） |
| あるじは話さず、客だけが話す                                                            | 4.3 を触らない                                             | 「つくもと話す」にならない。指示の目的から外れる    |
| あるじの吹き出しには出すが表情は変えない                                                | 4.3 を触らない                                             | 表情と吹き出しがずれる（4.3 の原則を別の形で壊す）  |

**推す: 例外を足す。** 2026-09-17 に退けた「ツールを実行している間に自動で『作業中』へ上書きする
経路」とは違い、**セリフと表情が台本の1行で対になっている**ので、リンクの原則は破らない。
決定の文言を変えることなので、4.3 への追記はドラフトの1件目で行う。

### 例外を設けたときの不都合（2026-09-25 に調べた結果）

**致命的な不都合は見つからなかった。** ただし、次の3つを守らないと 2026-09-17 と同じ種類の
壊れ方をする。

**表情を読んでいる場所と、例外が効くかどうか**

| 読む場所                                        | 読むもの                                                                           | 例外の影響                                |
| ----------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------- |
| キャラビューの立ち絵（`use-character-view.ts`） | 今のターンは `state.speechExpression`、過去のターンは `records` から引き直した表情 | 例外が効く場所はここだけ                  |
| 雑談モードの顔（`use-chat-view.ts`）            | `speechExpression` と留めたセリフの表情                                            | 雑談モードでは来ないので影響しない        |
| ミニ立ち絵（`mini-portrait.tsx`）               | 固定の `MINI_EXPRESSION`                                                           | 影響しない                                |
| 過去のターンの吹き出し（`turn-speech.ts`）      | `records` の `speech`                                                              | 台本を `records` に積まなければ影響しない |

1. **`speechExpression` と `records` に書かない。** 台本の表情は `SessionState.visit` の側に持ち、
   キャラビューで「訪問中なら台本の行の表情、そうでなければ `speechExpression`」と選ぶ。
   `speechExpression` を書き換えると、帰ったあとに「最後の `speak` に戻す」ための値が消え、
   `records` に積むと過去のターンの表情と吹き出しに作り話が混ざる。この形なら「戻す」処理は
   要らない（訪問の状態が消えれば元の値が出る）
2. **過去のターンを見ているあいだは上書きしない。** 過去のターンの立ち絵は記録から引き直して
   いるので、訪問の表情を被せるとそのターンの吹き出しと表情がずれる。訪問は今のターンを
   見ているときだけ描く
3. **本物の `speak` と待ちの終わりで必ず帰る。** 例外が効いたまま本物の `speak` が届くと、
   吹き出しは新しいセリフなのに表情は台本のまま、になる（リンクの原則が壊れる）。論点5の
   帰る合図をサーバの状態遷移で1つの `visit-ended` にまとめ、ブラウザ側で別々に判定しない

2026-09-17 に退けた経路との違いは、切り替わる回数にもある。当時はツールの出入りのたびに
往復していた（`docs/history/decision.md`「requirements.md 4.3 状態連動」）が、
訪問は「1回の待ちに1度・30 分空ける」ので、1回の待ちで入りと帰りの2回しか切り替わらない。
