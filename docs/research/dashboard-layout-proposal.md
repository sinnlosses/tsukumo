## 4. tsukumo に足す候補（優先度つき）

どの候補も「読む時間を減らす物差し」で測る。書き手の判断負荷は「書き手が1レポートで新しく決めることの数」で言う。
スキーマの増え方は `report` の定義が約 1.27 万トークンで毎リクエスト載ること（`docs/research/report-schema-alternatives.md`）から、欄1つ・塊1つの重さとして添える。

### 4.1 見本を候補1〜3で書くと

見本の中身を `board` で書くと次の形になる（欄の名は案）。判決の頭（目録・結論）は今のまま上に出る。

```json
{
  "layout": "board",
  "conclusion": "毎朝の収集結果を、入力・公式ソース・下書き・公開前チェックの4区画にまとめた。公開テストだけが CLI の制約で止まっている。",
  "figure": {
    "kind": "stats",
    "items": [
      { "label": "Claude Code", "value": "2.1.173", "detail": "local CLI check" },
      { "label": "Input files", "value": "92 KB", "detail": "data/2026-06-19" },
      { "label": "Drafts", "value": "5", "detail": "source URL 付き" },
      {
        "label": "Publish test",
        "value": "blocked",
        "status": "ng",
        "detail": "non-interactive CLI"
      }
    ]
  },
  "sections": [
    {
      "heading": "今日の入力",
      "badge": { "tone": "warn", "text": "鮮度メモあり" },
      "blocks": [{ "kind": "table", "...": "..." }]
    },
    {
      "heading": "公式ソースで言えること",
      "badge": { "tone": "ok", "text": "source checked" },
      "blocks": [
        {
          "kind": "list",
          "style": "bullet",
          "items": [{ "label": "Claude Code Artifacts", "text": "..." }]
        }
      ]
    },
    {
      "heading": "下書き候補",
      "badge": { "tone": "info", "text": "5 drafts" },
      "blocks": [{ "kind": "list", "style": "cards", "items": ["..."] }]
    },
    {
      "heading": "公開前チェック",
      "badge": { "tone": "ng", "text": "do not overclaim" },
      "blocks": [{ "kind": "chart", "chartKind": "bar", "...": "..." }]
    }
  ]
}
```

タブ（Claude・Codex・Slack・発信）は書かない。下書き候補の4枚は分類の札を `label` に持つ1つの小格子で全部見せる。

## 5. 塊を増やす以外の道との比較

| 道                                                                                                                                                                  | 書き手の判断負荷                                                                     | スキーマ・実装                                                                                                                    | 既存の決定との関係                                                                                                                               | 見立て                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| A. **塊を増やす**（`kpi`・`card`（中に塊を入れる）・`tabs`）                                                                                                        | 大。塊を選ぶ判断が3つ増え、`card` の中の塊の並びを組む判断が要る                     | `card`・`tabs` は入れ子の塊で、検査と描画が倍。`figure` と `sections` の名前の共有も崩れる                                        | 提案書5章「新しい塊を増やす」を採らなかった理由（判断が増える）と、10-01 の `compare` の入れ子を採らなかった理由にそのまま当たる                 | 採らない                     |
| B. **レイアウトの欄**（候補1〜3）                                                                                                                                   | 小。レポートに二択1つ、節に任意の札1つ                                               | 欄3つ。描画は既存の `@container` の格子（`stats`・`cols` の畳み方）を節に広げる                                                   | 「Z 字に読ませない」に板の型の例外を足す正典の変更                                                                                               | **推す**                     |
| C. **別の口**（`board` のツール。頭・数の札・区画の並びを持つ別の型）                                                                                               | 中。`report` と `board` のどちらを呼ぶかの判断が増えるが、`board` の中は板の文法だけ | ツール1本と描く経路1本。読み物の規約（問いの順・判決の頭）と切り離せる                                                            | `report-schema-alternatives.md` が「ツールを割る案」を採らなかった。最終の `report` との関係（どちらがターンを閉じるか）を新しく決めることになる | B で足りなければ             |
| D. **逃げ道の HTML を教え直す**（`markdown` の塊に `<div class="cols cols-of-2"><div class="card">`・`<span class="badge badge-ok">` を書かせる。描く側は既に持つ） | 中〜大。HTML の入れ子と空行の規則を書き手が守る                                      | コードは0行（規約の文面だけ）。ただし `cols` の中に塊は入らず、表や箇条は Markdown で書く                                         | 10-01「`cols` / `card` はモデルに教えない」を覆す。逃げ道の `cols` は 364回で数回しか書かれなかった（書くのが重い記法は使われない、2026-09-30）  | B を作る前の**試し**に向く   |
| E. **外のファイルにする**（「HTML にして」には書き手が1枚の HTML を書き、`image` の塊で撮った画を見せるか、Orca のタブで開く）                                      | 大。毎回デザインを決める（artifact の方式 [2]）                                      | tsukumo のコードは0行。ただし Orca で開く口はエディタ向けで、HTML をブラウザのタブで開く口は無い【実測: `hostContract.openFile`】 | 「固定の部品で描く」方式の外。会話の載るページに外部を読みに行かない条件とは別の場所になる                                                       | 利用者が頼んだ回だけの別の道 |

### 5.1 推す順

1. **D で試す**（規約の文面だけで、見本の型を数回書かせて画を撮り、板の型が利用者に効くかを目で見る）。`docs/history/mockup/` に置く見本と同じ扱い
2. 効くと分かったら **B の候補1〜3**を入れる。`layout` の使われ方・`badge` の数・`stats` の新しい欄を `report-usage` の版を上げて数える（`block-criteria.md`）
3. 板の型の規約（区画の独立・重要度の順・札の数）が読み物の規約と食い違って書き手が迷うと記録で分かったら **C** を考える

## 確かめていないこと

- Material 3 の card の指針（m3.material.io）・Shopify Polaris の layout・Datadog の dashboard の best practices・Notion は、ページが JavaScript で組まれているか接続が切れて本文が読めなかった
- Stripe Dashboard 本体と Linear Insights の格子の寸法（ログインが要る。`report-page-geometry.md` 2章でも測れていない）
- `board` の2列が 1400×900 の既定（読む面 約 764×458px【`report-page-geometry.md` の実測】）で2列になるか。2列の下限（約 612px）は超えるが、区画1つが約 370px で、表の3列が収まるかは目視していない
- 区画の地（`surface-raised`）と枠を入れたとき、`ai-report-surfaces-2026.md` 6章のテンプレっぽさの手がかり（同じ形のカード・数の札の横並び）がどれだけ増えるか
- 見本を D（逃げ道の HTML）で書かせたときに、書き手が空行と入れ子の規則を守れるか（2026-10-01 以前の記録の書き崩れの数は見ていない）
- 書き上げる演出（筆）が区画の格子のどの順で進むか。左上から Z 字に書くと「Z 字に読ませない」の理由が演出の側で戻ってくる【推測】
