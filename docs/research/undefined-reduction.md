# `undefined` を減らす案（2026-09-22）

**この文書は提案であって正典ではない。** `docs/` の他ファイルにある「節の索引」はここには作らない。
正典は `docs/coding-standards.md`「## 「無いかもしれない」値」と `CLAUDE.md`
「コーディング規約・レビュー方針」の該当4行で、**採用が決まるまで規約もコードも1行も変わらない。**

**きっかけ**: ユーザーの指示（2026-09-22）「`undefined` はできるだけ使いたくない。すべて
`undefined` を使わず表現できると仮定して、基本は使わず表現して。それでも難しいと判断したものは
残していいよ」。

**対象**: `main` の `ef8ad9a`。実測はすべて 2026-09-22 時点。数え方は
`grep -rn '| undefined' src/ test/ --include='*.ts' --include='*.tsx'`（**型の位置に書いた
`| undefined` だけ**。`src/` 297行・303箇所、`test/` 28行）。

**結論（4行）**

1. **型注釈から `undefined` を全部消すことはできない。** `tsconfig.json` の
   `noUncheckedIndexedAccess` と `Map.get` / `Array.at` / `find` / `findLast`、React の型、
   外来APIの3つが**型注釈を書かずに `undefined` を生む**。規約で触れるのは書いてある297行だけで、
   **実際のチェックの数（`=== undefined` / `!== undefined` が 277箇所、`?.` 79、`??` 78）は
   ほとんど減らない**
2. **それでも297行のうち約50行（17%）は減らせる。** 手は2つだけ——「判別可能な合併型にする」と
   「入口で全域なレコードに畳む」。**どちらもいまの規約がすでに命じていて、適用されていないだけ**
   （`docs/coding-standards.md`「### 複数の「無い」が1つの状態」の**「避ける」例がそのままの形で
   `src/shared/session-state.ts` に生き残っている**）
3. **規約を「`| undefined` 禁止」へ書き換えるのは勧めない。** 禁止すると
   「`?:` を使わない」条と「`null` を自前の型に出さない」条が同時に効かなくなり、
   **「無い」の表し方が1つも残らない**。逃げ道は `!` か `as` で、これは「型を迂回するキャストを
   書かない」条を壊す
4. **勧める形**: 条文を「禁止」ではなく**「`| undefined` を書いてよい5つの場所」の列挙**に変える。
   ユーザーの言う「難しいと判断したもの」を、読み手によって結論が変わらない5条件（3節）に置き換える

**`ReadonlyMap<Expression, string>` にする案は採らない。** `Map.get` の戻り値が

### 2.3 P — 検証の戻り値を結果型にする案は採らない（0行）

`parse*` の35行は `{ ok: true; value } | { ok: false; reason }` に置ける。**が、勧めない。**

- 出どころは **zod の `safeParse`**（`src/shared/frame.ts:92` ほか）で、
  `{ success; data } | { success: false; error }` を**境界で意図的に `| undefined` へ畳んでいる**。
  結果型に戻すのは、畳んだものをもう一度開く作業
- 呼び出し側が理由を使っていない。`src/browser/lib/socket.ts:48-51` は
  `if (frame !== undefined)` で**捨てて次を待つ**のが仕様（`docs/design.md` 4.5「未知の `kind` で
  落ちない」）。`src/server/adapter/session-socket.ts:126` も同じ
- 置き換えても**「無い」は消えず、`{ ok: false }` という名前に変わるだけ**。
  分岐の数は同じで、`.ok` と `.value` の2段になるぶん読む手数は増える

**ただし1つだけ例外**: `src/shared/task-summary.ts:41` の `readTaskSummaries` が返す
`undefined` は「**ファイルの形が信用できない**」を表し、`src/shared/session-state.ts:175` の
`tasks: ... | undefined`（「まだ届いていない」）と**画面上で同じ「不明」に合流している**。
ここは「1つの `undefined` に複数の意味が乗っている」（規約が「避ける」と書いている3パターンの2つめ）
なので、`tasks: { kind: "unknown" } \| { kind: "known"; items }` に割る価値がある（S に数えた5行
——`session-state.ts:175` / `session-event.ts:169` / `task-list.tsx:14,25` / `task-board.tsx:45,104`）。

### 2.4 「無いを表さない値」（空配列・空文字列・既定値）に畳む案

**空配列は既に使えている。** `CharacterInfo.expressions` は `readonly ExpressionChoice[]`、
`SessionState.characterPacks` も空配列で「まだ届いていない」を表していて、**`| undefined` が無い**。
これは先例として正しい。

**が、これ以上は広げられない。** `tasks` を空配列にすると「タスク0件」と「読めない」が混ざる
（2.3 のとおり、いまは画面が「不明」と「0件」を区別している）。**空文字列も同じ理由で使わない**
——`accent` を `""` にすると「色の指定が無い」と「空文字が指定された」が型で区別できなくなり、
**`undefined` を消して情報を1つ失う**。規約の「「無い」を型から消すことを目的にしない」に反する。

## 3. 残してよい例外の条件

ユーザーの「難しいと判断したものは残していいよ」を、**読み手によって結論が変わらない形**に
置き換えたもの。**この5つに当たるものだけが例外**で、それ以外に「難しい」と書かない。

| #   | 例外                                     | 判定（コードを見れば決まる）                                                                                                                             |     件数 |
| --- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------: |
| 1   | **外の世界の値を写した直後**             | その `\| undefined` を書いている関数が `src/server/adapter/` にある、または `unknown` / 定義ファイルの中身 / 環境変数 / SDK のイベントを引数に取っている |      62+ |
| 2   | **TypeScript が生む `undefined`**        | 型注釈を書いていない（`noUncheckedIndexedAccess` の添字・`Map.get` ・`Array.at` / `find` / `findLast` の戻り値）                                         | 数えない |
| 3   | **React が型で要求するもの**             | `useState` / `useRef` / `createContext` の型引数、`CSSProperties` の拡張                                                                                 |       13 |
| 4   | **React の外の資源を持つ可変の入れ物**   | `let` 宣言で、初期値が `undefined`、あとから代入がある（タイマー・ソケット・キャッシュ・畳み込みの途中）                                                 |       17 |
| 5   | **丸ごと省略できるオプション引数の中身** | 既存の例外（`docs/coding-standards.md`）。引数オブジェクトごと省略でき、既定値がある                                                                     |     少数 |

**1に当てはまらないのに `| undefined` を書くときの条件**（新しく足すぶん）:

- **「片方だけ `undefined` になる状態が実在するか」を確かめた**こと。しないなら合併型（2.1）
- **その `undefined` が1つの意味しか持たない**こと。「まだ来ていない」と「読めない」が
  同じ `undefined` に乗っているなら割る（2.3）
- **入口より内側へ運ばない**こと。層をまたぐなら入口で畳む（2.2）

上の3つは**いまの規約に既に書いてある**。つまり**条文を足す必要はなく、
「例外の一覧」だけが新しい**。

| 163〜165 | `null` を自前の型・関数の戻り値・`shared` に出さない                                  | **禁止案を採るなら書き換えが要る**（畳み先が無くなる） |

### 規約どうしの衝突（1つ直すと別の条が効かなくなる）

1. **「`?:` を使わない」×「`| undefined` を使わない」** — 両方守ると、
   **「無いかもしれない props」が1つも書けない**。`portrait.tsx:32,42,47` のような
   「省略できるつまみ」は、いまは `| undefined` しか許されていない。片方を緩めるしかない
2. **「`null` を出さない」×「`undefined` を使わない」** — 「無い」の表し方が両方禁止になる。
   残るのは合併型だけで、**`{ kind: "none" }` という3つ目の書き方が生まれる**。
   3つの書き方が並ぶのは、この条が避けたかったことそのもの
3. **「型を迂回するキャストを書かない」×「型から `undefined` を消す」** — `!` と `as` への圧力。
   2.1 の #2 のように、合併型にせず `turnFinishedAt!` で潰す近道が常にある
4. **「「無い」を型から消すことを目的にしない」×指示そのもの** — これが**いちばん大きい衝突**。
   いまの規約は「なぜ「無い」が生まれるのかを先に問え」と言っていて、
   「まず `undefined` を消せ」とは順番が逆。**ユーザーの指示を採るなら、この段落を削るか、
   「消す手は2つ（合併型・入口で畳む）だけで、それで消えないものは本物」と書き換える**のが筋
5. **「案を選ぶときの指標」（開くファイルの数・呼ぶ側が自分の外の事情を知らずに済むか）** —
   2.1 の合併型は**呼ぶ側の把握を楽にする**ので指標に沿う。
   2.3 の結果型は**呼ぶ側の手数を増やす**ので沿わない。**同じ「undefined を消す」でも評価が割れる**
