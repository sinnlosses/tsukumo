## 要点

1. **4本の調査は同じ1点に収斂した。** 読む時間を食うのは「探す・照らし合わせる・同じものを二度処理する」（Sweller 2019）で、
   先例はそれを「読者の問いの順に置く」「図と説明を1か所に」「明るさと余白で段を作る」「数は絶対値を2桁で」で潰している
2. **本文の帯は 10-02 の組み直しで先例の範囲に入った**（15px・1.75・42字は Linear・Observable・日経・note と同じ帯）。残る差は
   **段の作り方**（見出し 12.6:1 が本文 12.8:1 より暗い、見出しの下のあき 20px、表の行罫 2.54:1 は先例の倍、題が中央の1段、字の色が
   実質6つ）と**型の穴**（「なぜ・影響」の置き場が無い、`unverified` が検証の行の 24% なのに確かめ方が無い、図のあるレポート 12%、
   `fold` 0.4%）
3. **戦略の芯は「3秒・30秒・5分の3層で読め、各層で読者の問いに位置だけで答える紙面」。** 問いの順（終わった? → 何が変わった? →
   なぜ・影響 → 証拠 → 限界 → 私がすること → どこを見る → 次）は、Google の CL・Stripe・Smart Brevity・Test Plan・Azure の PIR・
   Codex・Copilot のどの型でも一致する
4. 原則は5つ: **(1) 問いの順に置き、位置で答える (2) 図と説明は1か所、題は主張 (3) 段は明るさと余白で、色は意味だけ
   (4) 数は絶対値・2桁・n件中k件 (5) 縛る前に測る**
5. 最大の3手は **判決の頭の完成**（なぜの1文・検証の総括行・お願いの印・変更の量の札）、**字の段と余白の体系**（拾う字の段、
   見出しの上下 52/13、行罫 1.3:1、題を左揃え2段で図の上）、**余白の柱**（本文の右に出典・覚え書き・押せるパス）
6. 塊は足さず**欄で精度を上げる**: `checks` の `howToVerify`、`stats` の `series` と `better`、`chart` の `arrow` と `slope`、`code` の
   `marks`、`graph` の `group`、`table` の `rest`、題の2段。`pie` は外す候補
7. **演出は見出しを先に全部出して本文だけを書き上げ、全体 10 秒で打ち切る**（見出しを拾う読み手を最後の節まで待たせない）
8. **測る仕組みを先に置く**: 理解にかかる時間＝描画が終わってから最初の依存する操作まで、5分以内の聞き直しの1ビット、抜き取りの
   1タップの労力評価、描き方の変種の A/B、順を入れ替えた LLM の対の判定
9. 6段のタスクに割れ、測る段を先頭に置く。段1〜2で最初の1画面と段の作りが直り、読む時間の大半はここで戻る見込み。利用者が
   決めることは9つ

## 2. 戦略: 読み手の問いに、位置で答える

### 2.1 外在負荷の3つの源と手当て

| 源（Sweller 2019） | レポートで起きる形                                                   | 手当て（根拠）                                                                                                                                              |
| ------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **探す**           | 結論・なぜ・証拠・お願いが決まった位置に無い。図を語る文が後ろの節に | 問いの順に欄を固定し、最初の1画面に判決の全部（NN/g の 57%・BLUF・Copilot）。図を語る文は図の隣（空間近接 d = 0.82）                                        |
| **照らし合わせる** | 凡例と図、題と中身、パスと場所、前後の2枚                            | 直接ラベル（Larkin & Simon・SWD）、題は主張（Borkin・Datawrapper）、`path:line` を押すと行で開く（Codex）、前後は同じ位置で切り替える（Josephs: 約6秒速い） |
| **二度処理する**   | 結論の言い直し、太字の多用、note の多用、相対値だけの数              | 冗長の効果量 d = 0.10（効かない）、合図は控えめなときだけ効く（Lorch 1995）、相対値は理解を変えずに大きく見せる（Cochrane 0.02 / 0.41）                     |

### 2.2 3つの層

| 層   | 読む時間 | 答える問い    | 置くもの                                                                                   | いま                             | 案                                                         |
| ---- | -------- | ------------- | ------------------------------------------------------------------------------------------ | -------------------------------- | ---------------------------------------------------------- |
| 判決 | 3秒      | 1・2・3・6・9 | 目録（ID・状態・変更の量）→ 見出し → 変化の1文＋なぜの1文 → 検証の総括行（お願いの印つき） | 目録・見出し・結論・検証のカード | 変更の量の札・なぜの1文・総括行・お願いの印を足す          |
| 骨   | 30秒     | 4・5・7       | 主張の題を持つ図1 → 節の見出し（演出中も先に全部）→ 確かめていない行と確かめ方 → 数の札    | 図は 12%・見出しは演出で遅れる   | 図の題を2段で上に、見出しを先出し、`unverified` に確かめ方 |
| 肉   | 数分     | 4・5・7・8    | 節の本文・表・コード → 余白の柱の出典と補足 → お願い                                       | 節・表・favor                    | 柱、表の罫と揃え、塊の欄                                   |

### 2.3 原則

1. **問いの順に置き、位置で答える。** 欄の順は読者の問いの順。同じ問いの答えは毎回同じ場所にあり、読み手が探す前に目に入る
2. **図と説明は1か所、題は主張。** 図を語る文は図の隣、題は結論を数と向きで言い、ラベルは要素に直接付ける
3. **段は明るさと余白で、色は意味だけ。** 拾う字（見出し・太字・数）は一段明るく、本文は静か。見出しは上に大きく下に小さく空ける。
   罫は 1.3:1。色は状態とキャラクターの持ち物のまま（13.1 の原則は変えない）
4. **数は絶対値・2桁・n件中k件。** 前→後を先に、割合は添え、変わる桁2つに丸め、数えられるものは件数で言う
5. **縛る前に測る。** 新しい差し戻しは使われ方の数を見てから。理解にかかる時間を定義して記録し、描き方の変種を比べる

### 3.2 報告の種類と節の型

`task` に種類（作業・判断・調べもの）を足し、`stopped` は中断の型として扱う。既定の節の並びを規約に置き、節の数は縛らない。

| 種類     | 既定の節の並び（読者の問いの順）                                                                       | 必ず入る塊                             |
| -------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 作業     | 変化 → 証拠（checks）→ 変更の要所（どこを見るか: files・`path:line`）→ 限界と変えていないもの → お願い | `checks`（直したと言うなら空にしない） |
| 判断     | 決めたこと → 理由と採らなかった案（options）→ 結果（良いも悪いも）→ 未決                               | `options` が1つ                        |
| 調べもの | 分かったこと → 根拠（出典・`path:line`）→ 何を意味するか → 確かめていないこと → 次                     | 出典か `path:line` が1つ               |
| 中断     | どこで止まったか → 原因 → 何を残し何を戻したか → 再開に要るもの（読者の判断・情報）                    | `favor`                                |

### 3.7 書き手の規約（足す条の案文）

1. 結論の2文目は「それで何が良いか」か「変えていないもの」。1文目は読み手から見た変化（今のまま）
2. 各文は既知（依頼の語・ファイル名・直前の目的語）から始め、新しいことを文末に置く。「この変更」の先行詞が直前に無ければ名前で書く
3. 今回の作業で生まれた名前だけ、使う前に1行で役割を言う。用語集にある名前・読み手が作った名前は説明しない
4. 数は絶対値の前→後を先に、割合は添える。数えられるものは「n件中k件」。変わる桁2つに丸める
5. 図表の題は主張を数と向きで言う1文＋測り方の1文。評価語を入れない。図を語る文は図の直下の1段落に限る
6. 列挙は同種の項目だけ。異種なら表の列で分けるか文に戻す。2行以下の表は `stats` か label 付きの箇条に
7. `unverified` の行には確かめ方（繰り返せる手順）を書く。目視の行は「何を見て、何が見えたか」
8. 図の条: 1枚に1つの話を同じ抽象度で／どの辺にも向きと合う動詞のラベル／交差が出たら節点の並びか図の分け方を変える／群は囲みで言う
9. 最終レポートは終わった状態から書き直し、中間レポートを継ぎ足さない
10. 撮った画像は要る所に切り抜く

〔規約〕。条1・2・3・4・6 は**正典の変更**（今の条に無い）。既存の条（段落3文・note は2つ・`**` は1段落に1か所）は研究と整合し、変えない。

## 7. 利用者が決めること

1. **拾う字の段（`--ink-bright`）を足すか。** 字の段を3つから4つにし、見出し・太字・数を本文より一段明るくする（正典の変更）
2. **余白の柱を置くか。** 本文の右に memo・題の補足・出典・パスを出す。やり取りの列を開いた 1400 幅では本文に畳む（正典の変更）
3. **図表の題を上に移すか。** 図は下・表は上の今の形（学術誌の流儀）を、どちらも上（報道・分析ノートの流儀）にする（正典の変更）
4. **`task` に報告の種類を足すか。** 作業・判断・調べものの既定の節の並びを規約に置く（正典の変更）
5. **結論の2文目を「なぜ・影響」に充てる条を足すか**
6. **演出を「見出しは先に全部、本文だけ書き上げ、全体 10 秒」に変えるか**（`requirements.md` 4.3 の変更）
7. **note の地の染めを warn・ng だけに残すか**
8. **`beforeAfter` の画像の既定を同じ位置の切り替えにするか、口を足すだけにするか**
9. **理解にかかる時間の記録を始めるか。** 残すのは秒・真偽・塊の種類だけで、本文と入力の文字列は保存しない

**答え（2026-10-17）**: 1・2・4・5・6・8 は採る。**9 は採らない**——利用者はレポートが出てから読み始めるまでに別の作業を挟むことが
多く、描画の終わりから最初の操作までの秒は理解の時間にならない。3.8 の表のうち時間に依る行（理解にかかる時間・聞き直し・読まれ方）と
6章の段0のその記録は落とし、段0は使われ方の記録に欄（強調の数・辺のラベルの無い割合・節点数・報告の種類・`howToVerify` の有無）を足す
だけにする。描き方の変種を比べる物差しは、利用者自身の選択と、それで較正した LLM の対の判定に絞る。3（題の位置）と 7（note の地）は
根拠を下に足して議論し、3案ずつ並べた見本（`variants.html`）を見て決めた: **3 は A（今のまま。図の題は下・中央の1段）、7 は C
（段差。warn・ng は 13%、info・ask・memo は 6%）**。3.1 の図1の行と 3.3 の図表の題の行のうち「図の題を上に」は採らない。
見本 `after-first.png`・`after-wide.png` は題を上に描いているので、この点だけ答えと違う。表の題の左揃え・2段は判断に含めて
いないので、段2で目視して決める。

**値と塊の意匠の答え（2026-10-17）**: 3場面（短い・長い・調べもの）×2幅（1400・1920）の見本 `values.html` を A/B/C の3案で組み、
利用者は **B** を採った（`--ink-bright` 約 15:1・`##` 21px・格子 13/26・見出し 52/13・`--rule-soft` 約 1.3:1）。あわせて、3.3 に
「数と線の規律」を足すこと、1920 幅でも余白の柱は**左寄せのまま**（中央に寄せない）、塊の意匠は見本どおりに進めることを決めた。
段2〜4のタスクは、本文の値をこの答えに揃えてある。

### 7.1 判断3の根拠: 図の題を上に置くか

「上が下より理解が速い」を直接測った実験は見つかっていない（2026-10-17 に2回探した）。根拠は3種で、どれも間接。

| 種類         | 根拠                                                                                                                                                                                                                                                                                                                                      | 向き                         |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 読む順       | 走り読みで最も効く layer-cake は見出しを先に拾う（NN/g 2019）。図では**題が最も注視され、題と添え文が主旨を運ぶ**（Borkin 2016）。**題の傾きで同じ図から逆の主旨を読む**（Kong 2018）。題を図より先に読む位置に置くと、題が図の読み方を導く（Mayer の signaling・pre-training）。下にあると、図を見てから題で答え合わせをして図を二度見る | 上                           |
| 様式         | **APA は第7版（2019）で図の題を下から上へ移し、表と同じ形にした**（第6版は図の下）。報道とデータ可視化（Datawrapper・SWD・FT・Observable）は上。学術誌（Nature）・Tufte・Distill は下か横                                                                                                                                                 | 様式で割れる。新しい様式は上 |
| tsukumo 固有 | 表は既に上なので、図だけ下だと読み手が2つの規則を持つ（探す負荷）。書き上げる演出では、題が先に出れば図が描かれる前に何を見るかが分かる                                                                                                                                                                                                   | 上                           |
| 反対         | 学術の慣行に慣れた読み手には違和感がある。図が縦に長いと、上の題と図の末尾が離れる                                                                                                                                                                                                                                                        | 下                           |

折衷は Datawrapper の形で、**主張の1文は図の上、測り方・出典は図の下**に置く（上の題を2段にせず、1段目と2段目を上下に分ける）。
題の2段を分けるだけなので塊の形は変わらない。

### 7.2 判断7の根拠: note の地の染めを warn・ng だけに残すか

先例3つはどれも**種類ごとの色を持つ**（GitHub は左罫＋題の字の色で地なし、Docusaurus は左罫＋薄い地、MDN は左罫＋地＋アイコン）。
tsukumo の今の形（左罫 3px＋種類の色 10% の地）は Docusaurus 型で、それ自体が先例の1つ。提案は色分けをやめることではなく、
**頻度の高い穏やかな種類（info・ask・memo）で地だけを外す**こと。

- 合図は控えめなときだけ効く（Lorch 1995: 狙いの文だけの下線は再生を上げ、半分に引くと無印と同じ。Mayer の signaling も控えめで強い）。
  `ask` は note の 45%、note は 25% のレポートに出るので、染めた箱が常態になり、warn・ng の箱の目立ちが相対的に下がる
- NN/g の banner blindness（色の地の小さな箱は広告に見えて飛ばされる）は欧文サイトの広告の文脈の研究で、技術文書での実験は無い
- 中間案: **表の状態セルが既に持つ段差**（NG・要注意は 13%、OK は 6%）を note にも当て、warn・ng は 13%、info・ask・memo は 6% にする。
  罫と題の字の色はそのままなので種類の見分けは残り、強さの差だけが付く

決めるのは目視で、同じ場面で「今のまま／地なし／段差」の3つを並べて見比べる。

## 8. 確かめていないこと

- 見本は静的な HTML で、実物の React の木・書き上げる演出・やり取りの列の幅の実測（232px）と合わせた柱の畳む境目を目視していない
- `text-box-trim`・`text-wrap: balance` が Orca のタブの描画エンジンで和文にどれだけ効くか
- 3.8 の代理指標（最初の依存する操作までの秒・5分の聞き直し）が tsukumo で理解と相関するか。Hassan の5分の規則を対話に移すのは推論
- 認知負荷と図の研究はすべて欧文・初学者・短い授業の条件で、文脈を持つ専門家1人が判断のために読む場面の実験は見つからなかった
- 変更の量（`git diff --numstat`）を tsukumo が数える経路の設計（どの時点の差分を数えるか・委譲先の変更を含めるか）
- 報告の種類ごとの使われ方の数（記録に欄が無いので、段0で足してから見る）
- E2E の期待値（`test/e2e/expected/`）のうち何件が段2で変わるか
