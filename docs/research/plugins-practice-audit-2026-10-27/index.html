赤 1. 導入経路が「plugin の 1 経路」と食い違い、hooks.json の関門が効いていない

今の形
README.md:24 と skills/task-model/tw-reference.md:90 は「入れ方は plugin の 1 つだけ（GH-771）。リンクで置くと hooks/hooks.json が読まれず、ask-guard・lap-hook・主のセッションの bd の書き込みの拒否・受け入れ役の拒否が掛からない」と書く。 ところが手元の環境は ~/.claude/skills/<name> と ~/.claude/agents/*.md がこのリポジトリへのシンボリックリンクで、claude plugin list は「No plugins installed」。スキルの Base directory も ~/.claude/skills/plan-tasks と出る。 その結果、効いている関門は agents/no-delegate.md の frontmatter の hook（commit-guard・handback-guard）だけで、plugin 側で足した --agent-scoped の判定・ask-guard・lap-hook は掛かっていない。 さらに両方の経路を生かすため、skills と agents に「リンクで入れたとき／plugin で入れたとき」の分岐が 18 行あり、スキル名を「一覧の末尾一致」で探す手順（#10）が要っている。
公式の言い分
plugin の hooks は plugin が読み込まれたときから常に走り、plugin 同梱の agent では frontmatter の hooks・mcpServers・permissionMode が無視される [components]。 ローカルパスから足した marketplace の plugin は複製されずその場で読まれ、編集は次のセッションか /reload-plugins で効き、version を上げなくてよい [loading]。 symlink の置き場は Personal・Project で使えるが、plugin とは別の名前空間（plugin:skill）になる [skills]。
筋が悪い理由
関門を hook に置いたのに hook の置き場（hooks.json）が読まれない経路で運用しているので、「守らせたい規則は hook へ」という公式の枠組みが崩れている。二経路を文書で支えるぶん、手順の分岐（18 行）と名前解決（末尾一致）が増え、hook の挙動の説明も「plugin なら／リンクなら」で二重になっている。
提案
README の「リンクで入れていた環境の切り替え」を人がやる（リンクを外し、/plugin marketplace add /絶対パス/tsukumo-plugins → /plugin install tsukumo-workflow@tsukumo-plugins）。切り替えたら、18 行の二経路の記述と末尾一致の手順を plugin の全名（tsukumo-workflow:task-workflow など）に書き換え、tw lap の「リンクだけで入れたときは手で打つ」の段落も消す。 tsukumo が SDK で起こすセッションにも同じ plugin が載るかは、tsukumo 側の settingSources（省くと user/project/local を読む [claude-code-features]）で確かめる。
根拠
ls -l ~/.claude/skills（accept-step ほか 13 件がこのリポジトリへのリンク）、ls -l ~/.claude/agents（acceptor.md・no-delegate.md がリンク）、claude plugin list（0 件）。

黄 3. 実装役の決まり（implementer-brief.md）が 51 本・21.8KB の規則の山になっている

今の形
委譲のたびに実装役が最初に読む parts/implementer/implementer-brief.md は箇条 51 本（grep -c '^- '）・21,786 バイト。これに依頼文の型 implementer-request.md（9,258 バイト）、タスクの本文、プロジェクトの CLAUDE.md が重なる。 中身は「Edit の前に Read する」（63 行）、「/ やホーム全体を find しない」（66 行）、「待つコマンドに上限を付ける」（67 行）、「コメントを足す前の 3 問」（72 行）のような、モデルが既に持つ作法と、hook（commit-guard）が拒むものの言い直し（62 行の git stash）が混ざる。振り返り（retrospect）のドラフトが 1 件ごとに行を足す構造で、GH-1576 が「28 日に 1 度でも効いたか」で行を選別する作業として積まれている。
公式の言い分
足す内容は「Claude が既に知っていること」を除いた最小限にし、選択肢を並べすぎず既定を 1 つ示す [skill best-practices]。 文脈は有限の注意予算で、増えるほど想起が落ちる（context rot）。システムプロンプトは脆い手書きの分岐でも曖昧な一般論でもなく「ちょうど良い高さ」で [effective-context-engineering]。 強調や念押しを足し続けるのは過剰適用を招く。守られない行は、長すぎて埋もれているか、例外のない規則なので hook にすべきかのどちらか [best-practices]。 慣習は段階的に足す: 同じ誤りを 2 度したら CLAUDE.md、毎回やらせたいなら hook [features-overview]。
筋が悪い理由
規則が増えるほど 1 行あたりの遵守率が下がる、と公式が明言している形に、振り返りの仕組みが構造的に向かっている。hook で既に拒んでいるものを文でも言う二重化は、文脈を食うだけで強制力を足さない。
提案
GH-1576 の選別を、公式の梯子で分類し直す: (a) hook・commit-guard・handback-guard が既に拒むもの → 文から消す（拒否文が案内する）。(b) 例外ゼロで毎回守らせたいもの → hook か tw step の検査へ移す。(c) モデルの既知の作法 → 消す。(d) このワークフロー固有（tw step／tw pause の打ち方、返却の書式、phase_result）→ 残す。 残す行は implementer-request.md の場合分けと同じ型で「その段に当たるときだけ」依頼文に入れ、brief 自体は固有の決まりだけにする。目安は、brief と request を合わせて今の半分（約 15KB）以下。

今の形

公式の言い分

黄 5. 無音の見張りが transcript の symlink を stat する 5 秒ループ

今の形
parts/implementer/delegate.md:58-66。委譲を投げた直後に Monitor で、Agent の戻りの output_file（symlink。実体は委譲先の transcript）を stat -L -f %m で 5 秒ごとに読み、更新が T 秒止まったら SILENT を 1 回出し、6 回に 1 回 tw escalate-check を打つ。timeout は上限の 30 分で、失効したら起こし直す。
公式の言い分
hook はサブエージェントの中でも発火し、入力に agent_id・agent_type が付く [hooks・claude-code-features]。SubagentStop は agent_transcript_path を入力に持つ [hooks]。 進捗を返す専用の仕組みは無く、SendMessage が公式の記述 [sub-agents]。transcript のパスや symlink の形は、どの docs も契約として書いていない。
筋が悪い理由
「output_file は symlink で実体が transcript」「macOS の stat -f %m」という、docs に無いハーネスの内部に寄りかかっている。transcript の置き方が変われば見張りが黙って死ぬ（更新が見えず、常に SILENT か常に無音）。既に委譲先に SendMessage で「段の区切りと長いコマンドの前に 1 行」を送らせているので、鼓動の源は 2 つある。
提案
鼓動を hook で取る: hooks/hooks.json の PostToolUse（agent_id があるときだけ）で tw が台帳（.tw/local/）に「agent_id ごとの最終活動時刻」を書く。Monitor のループはその時刻を読む（transcript に触らない）。 tw escalate-check も同じ時刻を読めるので、見張りのシェルは「台帳の時刻を読む → T 秒超なら SILENT」の 1 行になる。hook の起動は Bash 1 回につき子プロセス 1 つの合流（tsukumo の GH-1647）と同じ流れで、新しい子プロセスを増やさず commit-guard の入口に相乗りさせる。

黄 6. hooks.json の書き方: 同じ殻を 7 回、exec 形・onFailure・Subagent 系の matcher が未使用

今の形
hooks/hooks.json は 7 つの hook すべてが "${CLAUDE_PLUGIN_ROOT}/bin/tw" <sub> || { c=$?; case $c in 78|127) …exit 0;; *) …exit 1;; esac; } という同じ 200 字の shell 形で、サブコマンド名だけが違う。SubagentStop・SubagentStart は matcher 無しで、Explore・Plan・acceptor・general-purpose のどれが止まっても tw（python の起動）が走り、絞り込みは lap_hook.py の中で agent_type を見て行う。 tw が落ちたとき（78・127 以外）は exit 1 で「関門が掛かっていない」と stderr に出すだけで、ツールは通る。
公式の言い分
plugin の hook は args を付けた exec 形ならクォート不要、shell 形は二重引用符で包む [manifest-reference]。 Subagent 系の matcher は agent 型（plugin は ^plugin:name$）で書ける [hooks]。 終了コード 2 以外のエラーは非ブロッキングで、onFailure: "block" を付けたときだけ止まる [hooks]。command 型の timeout は既定 600 秒 [hooks]。
筋が悪い理由
殻の重複は直すとき 7 か所を揃える手間になり、shell 形は引用の崩れを validate が拾えない。関門が「落ちたら通す」なのは、python が無い環境（78・127）を通す判断としては正しいが、tw 自体のバグ（1）まで通すのは fail-open で、hook を置いた目的（例外ゼロの強制）と逆向き。Subagent 系の全発火は、1 セッションあたりの python 起動を増やすだけで判定は変わらない。
提案
(a) bin/tw-hook（1 本の殻）を置き、各 hook は exec 形 {"type":"command","command":"${CLAUDE_PLUGIN_ROOT}/bin/tw-hook","args":["commit-guard","--agent-scoped"]} にする。(b) 78・127 は殻の中で exit 0、それ以外は exit 2（止める）にするか、onFailure: "block" を付けて fail-closed にする。どちらにするかは「関門が壊れたとき作業を止めてよいか」の判断で、/loop の無人運転なら止めるほうが安全。(c) SubagentStop・SubagentStart に "matcher": "tsukumo-workflow:no-delegate|tsukumo-workflow:acceptor|general-purpose" を付け、Explore・Plan では起動しない。

description を「受け入れの判定だけを返す。ファイルを書き換えない」程度（60 字以内）にし、hook の掛かり方は本文か tw-reference.md「hook の関門」へ移す。model は受け入れの難易度の対応表（task-model「difficulty とモデルの切り替え」）から渡す形にし、固定値の検査は外す。

8. 公式プラクティスの要点（7 観点）

調べもの役が集めた一覧のうち、この点検に効いた行だけ。全文は会話の記録にあり、数値は原文で確かめてから設計に使う。

観点 推奨 非推奨・注意 上限・既定値
