# 開発ハーネスを「測って育てる閉ループ」にする — 世界水準への戦略（2026-10-17）

状態: 採用

**この文書は提案であって正典ではない。** tsukumo の開発フローを取り巻く仕組み全体（タスク運用・委譲・受け入れ・振り返り・送り出し・関門・
常設の指示文・計測）を「ハーネス」と呼び、2026-10-17 時点の実測と、外の仕組み
（google-research/harness2・QoderAI/better-harness・各社の一次情報）との比較から、次に目指す形を
提案する。対象ユーザーは作者本人のみ（`docs/requirements.md`「2.3 想定利用者」）。

調べ方: 実測は `tw metrics`・`tw metrics --stages`・振り返りの `weekly.py`・`hook-denial-tally.ts`・
`summarize_usage.py --days 30`・`wc`・git で取った。外の仕組みは4体のサブエージェント（harness2 の
本体と論文、better-harness の本体、2025〜2026 の一次情報、このリポジトリの棚卸し）の報告を突き合わせた。
会話の実物・transcript は読んでいない。

## 要点

- いまのハーネスは**速い**（7日で 298 件を main へ、着手から送り出しまで中央値 17 分）が、
  **開いたループ**になっている。振り返りは 28 日で 166 件のドラフトを積み、72%（119 件）が採用されたが、
  採用した規則が狙った摩擦を減らしたかを測る口が無い。結果、`docs/workflow.md` は 14 日で
  20.5KB → 35.1KB（+71%）に伸び、同じ期間に検証の落ちは 61 → 116 回に増えた
- 外の最先端（harness2・better-harness・Anthropic・OpenAI）が揃って置いているのは、**介入を実験として
  扱う**こと: 変更ごとに狙いの数・基準線・比較の窓・やめる条件を持ち、「採用した」ではなく「後の同種の
  タスクで良くなった」ときだけ効いたと言う。常設の指示文には機械の字数上限を掛け、足すなら削る
- 戦略は **「測る → 閉じる → タスクの再試で比べる」の順**で、流れの形（Beads が正・委譲 → 受け入れ → 振り返り →
  送り出し・ff で main）は変えない:
  1. タスク1件あたりのトークン・段の時間・関門の拒否・送った後の直しを、1件単位で結び付けて記録する
     （いまは token-usage にタスク ID が無く、tw の関門の拒否は記録されない）
  2. 振り返りのドラフトに「介入台帳」（狙う兆候・基準線・判定の期日・出し先の種類）を必須にし、
     週ごとの振り返りが helped / hurt / no observed effect / confounded を判定して、効かない規則を外す
  3. 常設の指示文（CLAUDE.md + rules）の字数に上限を掛け、出し先を hook・検査 → スクリプト → スキル →
     サブエージェント → 常設の順で選ばせる
  4. 過去のタスク 20 件を凍結したタスクの再試集を作り、CLAUDE.md・スキル・hook・モデルの割り当てを変えるときは
     タスクの再試の前後（通過率・トークン・時間）で比べる
  5. 検証の判定を pass / fail / unobserved / blocked の4値にし、「0件実行」「飛ばした段」を緑と言わない
- 役とモデルの配分（判断は上位モデル、決まった編集は下位モデル）と文脈の経済（探索の歩 33% を減らす
  索引、長い委譲の分割）は、1. の計測が揃ってから前後で比べて入れる

## 2. 外の仕組みから借りる原則

### 2.1 harness2（Google Research、arXiv:2610.14224、2026-10）

研究用の基盤。実行役（OpenCode / Codex）の設定ファイル群（system prompt・guardrails・memory・
tool guidance・skills・subagents・scripts・hooks の8部品）をタスクごとに自動で書き換えて改善し、
採用した一式と教訓をライブラリに積む。借りるのは次。

- **常時読み込みの文章が一番高くつく**ので、字数に機械の上限を掛ける（OpenCode は常時ファイル4つ計
  24,000 字、Codex は AGENTS.md 8,000 字）。入れ方の優先順は skill → script → subagent → plugin/hook →
  常時テキストで、常時テキストを足すなら「cut something else to pay for it」
- **変更は軌跡の瞬間に結び付ける。** 結び付かない変更は推測（"one you cannot trace to a moment is
  speculation"）。「変更なし」も正当な答え
- **学びは根拠がある分だけ。** 教訓は cue・lesson・evidence の3欄が揃わなければ NO_ENTRY。編集ごとの
  判定は helped / hurt / no observed effect / confounded の4語。「採用された」は「効いた」の根拠に
  ならない（"Adoption alone never establishes that an edit helped"）
- **選択は盲検。** 候補は匿名化して並べ、長さや丁寧さを加点しない
- **完了は印と指紋で記録する。** 出力があるだけでは完了としない
- 数値: 編集役の分担（やり方 / 中身の知識）を外すと −2.9 / −3.7、ライブラリを外すと −3.1 / −1.8、
  参照実行と probe 無しで直接書き換えると悪化（73.4 → 63.2）。ループの中に人の承認・質問・停止の口は無い

### 2.2 better-harness（QoderAI、v0.7.0-alpha2、2026-10）

エージェント本体ではなく、ホスト（Claude Code など）の中で `/better-harness` として動き、その
ハーネスを証拠で評価して改善項目を返す。借りるのは次。

- **設定があることは使われた証拠にならない。** 証拠に Present → Wired → Exercised → Outcome-supported
  の段階を付け、点数の上限を段階で決める（59 / 74 / 84 / 94 / 100）
- **評価の単位は Task Episode**（1つの目標と1つの受け入れ境界）。セッションは証拠の入れ物
- **介入台帳**: 規則や hook を足したら、変えた部品・基準線・比較の窓・止める条件を記録し、「効いた」は
  後の同種の Episode で良くなってから言う
- **再発の閾値**: 既定は「比較できる 2 件で同じ兆候」。1件の事故は再発と呼ばない。hook が正しく拒んだ
  件は摩擦でなく成功した防御
- **検証の判定は 4 値**（pass / fail / unobserved / blocked）で「偽の緑」を拒む。修理ラウンドに上限を
  置き、上限で blocked にして人に渡す
- **hook は段階を踏んで強くする**: log-only → warn → ask → block。各段で記録済みの事例を再生して確かめる
- **常設の指示文の長さの関門**: 80 行以下が健全、121〜180 行は境界、180 行超は過積載。「一度きりの失敗
  から規則を足し、古い規則を剪定しない」をアンチパターンに挙げる
- **新しいスキルを作る前の梯子**: 観測済み → 組み込み → 既存の設定 → 既存の拡張 → 新規作成 → 証拠不足
- **受け入れ役に親の結論も期待する答えも渡さない。** 判定は verified / partial / blocked に限る

### 2.3 2026 年時点の合意と、割れている論点

合意に見える原則（出典は 8 章）:

1. 文脈の窓が最も希少な資源。常設の指示は短い目次にし、詳細は要るときに読ませる（Anthropic の
   context engineering、Claude Code best practices の「200 行未満」、OpenAI harness engineering の
   「約 100 行の目次」）
2. エージェント自身が回せる検証が最大のレバーで、検証器の質が上限になる（Carlini の C コンパイラ、
   Claude Code best practices）
3. 作る役と判定する役を分け、判定は新しい文脈で precision を保つ（Anthropic harness design、OpenAI の
   コード検証）
4. 守らせたい規則は文章より機械に置き、エラー文に直し方を書く（OpenAI、SWE-agent の lint の関門を
   外すと −3pt）
5. 長いタスクの状態は文脈の外（計画・進捗ファイル・git・台帳）に置く
6. ツール・境界（ACI）の設計は同じモデルの成績を大きく動かす（SWE-agent の ablation、LangChain +13.7、
   編集形式だけで 6.7% → 68.3%）
7. ハーネスの部品はモデルの弱点についての仮定で、モデルが変わるたびに外せるかを試す（Managed Agents の
   「死んだコード」、skill-creator の「能力の底上げ」と「好みの符号化」）
8. 劣化は積もる。失敗を規則や検査に昇格させ、定期に掃除する（OpenAI の doc-gardening、Anthropic の
   4/23 事後報告: プロンプト1行で −3%）
9. 隔離を先に置き、承認を増やさない（サンドボックスで確認 −84%、auto mode の記事: 利用者は確認の
   93% を承認）
10. 成否だけでなくトークンと時間を報告する（Scaffold Effect: 差は通過率より 1 問のトークンに出る、
    最大 40 倍）

割れている論点: AGENTS.md がどれだけ効くか（ETH: 生成したものは −0.5〜−2pt でコスト +20%、人が
書いたもので +4pt。Vercel: 索引 100% vs スキルだけ 53%）、マルチエージェントか単一か（Cognition
「作るな」 vs Cursor の数百体。落としどころは「書きは衝突させず、読む・レビューは並列」）、人の関門の
位置（OpenAI は最小、HumanLayer は計画に）、仕様駆動の重さ、厚いハーネスか薄いか（mini-swe-agent
約 100 行で 74% 超）、自己生成した知識は効くか（SkillsBench: 自己生成のスキルは平均で効果なし、
人が整えた小さなスキルは +16.2pt）。

### 2.4 この戦略の原則

1. **常設は目次、詳細は要るときに。予算は機械で守る。** 常設の字数に上限を置き、超える追加は何かを
   削ってから
2. **規則は介入、介入は実験。** 狙う兆候・基準線・窓・やめる条件を持たない規則は積まない。効かなかった
   規則は外す
3. **緑を疑う。** 検証は 4 値で、実行していないものを通ったと言わない
4. **作る・測る・判定するを分け、判定は盲検。** 判定役には差分と基準だけを渡す
5. **1 件単位で測る。** トークン・時間・歩・拒否・送った後の直しを、タスク ID に結び付ける
6. **ハーネスを変えるときはタスクの再試で比べる。** 体感と採用で判断しない
7. **道具が先、文章は後。** 拒まれる形を禁じるより、正しい形が最初に手に入る道具を置く
8. **人は上流と介入の判定に。** 1 件ごとの承認を増やさず、再発した兆候と介入の効き目だけを人に見せる

これらは流れの形（Beads が正・委譲 → 受け入れ → 振り返り → 送り出し・ff で main）を変えない。変えるのは、
流れの周りの計測・学習・予算・判定の仕組み。

## 3. 案

### 3.1 計測の土台（他のすべての前提）

| 案                               | 中身                                                                                                                                                                                                      | いまの穴                                    |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 3.1.1 タスク ID でトークンを結ぶ | tsukumo が token-usage の1行に、そのターンの着手の印のタスク ID（作業ツリーの `.tw/local/task-open-claims/`）と段（台帳の最新の lap）を足す。委譲先のぶんは `agent` の出来事（agent_id ↔ タスク）で結ぶ   | 行に sessionId と mode しか無い             |
| 3.1.2 関門の拒否を全部記録する   | tw の commit-guard・handback-guard・ask-guard・ref-guard も `hook-denials/` と同じ形（時刻・名前・規則のキー・呼び手）に書く。tally は呼び手（main / subagent）と規則のキーの内訳を出す                   | tw の関門は記録されない。tally に内訳が無い |
| 3.1.3 lap を hook で自動に       | 進行中のタスクのとおり、段の頭と尻を人手でなく hook で打つ。OPEN を 0 にする                                                                                                                              | OPEN が受け入れ 3・レビュー 5               |
| 3.1.4 送った後の直しを数える     | 直しのタスクを元の送り出しに結ぶ欄（Beads の metadata `fixes`。`tw new --fixes <ID>` と、本文の ID の自動検出）。週ごとの振り返りが「送り出しから 7 日以内に直しが要った率」と「送った件の revert」を出す | 無い                                        |
| 3.1.5 受け入れ役の較正           | 受け入れの判定（指摘の数・差し戻しの回数・判定の語）を台帳に残し、3.1.4 の後の事実と月に1度突き合わせて、偽陽性（差し戻したが直しは要らなかった）と見逃し（通したが 7 日以内に直し）を出す                | 無い                                        |
| 3.1.6 検証の落ちを分類する       | verify の落ちを「本当の落ち」「打ち直したら通った（揺れ）」「基盤（ポート・E2E の上限）」に分けて台帳に書く。揺れたテストは名前で数える                                                                   | verify_failed 116 の中身が見えない          |

### 3.2 学びのループを閉じる

**3.2.1 介入台帳。** 振り返りのドラフトと、ハーネスを変えるタスク（CLAUDE.md・rules・docs/workflow.md・
スキル・hook・`.tw/config.toml`・モデルの表を触るもの）の本文に `## 介入` の節を必須にする:

```markdown
## 介入

- 狙う兆候: <material.py の SIGNAL の種類 / tw metrics の数 / hook の規則のキー / 直しの率>
- 基準線: <直近 28 日の値（数）>
- 出し先の種類: <hook | 検査 | スクリプト | スキル | サブエージェント | 常設の文章>
- 判定の期日: <送り出しから 14 日、または比較できるタスク 20 件>
- やめる条件: <期日に兆候が減っていなければ戻す>
```

`tw new --draft` と `tw edit` は「出し先の種類」が語彙の外なら拒み、「常設の文章」のときは「削るもの」の
行を要求する。狙う兆候は自由記述にせず、material.py の SIGNAL の種類・`tw metrics` の数・hook の規則の
キー・3.1.4 の直しの率から選ぶ。

**3.2.2 週ごとの振り返りが介入を判定する。** `weekly.py` に「期日を過ぎた介入」の節を足し、介入ごとに
狙う兆候の基準線と直近の値を並べ、helped / hurt / no observed effect / confounded（同じ期間に同じ兆候を
狙う介入が 2 つ以上）を付ける。no observed effect と hurt は「戻すドラフト」を積む。判定は数で機械が出し、
言葉の説明だけをモデルが書く。

**3.2.3 ドラフトに証拠の段階と再発の閾値。** 1 件ごとの振り返りで積むドラフトを、人の承認の列に出す
前に段階で分ける:

| 段階     | 条件                                                                      | 行き先                                                                                  |
| -------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 赤・1 件 | 止まった・人に預けた・壊れたまま進みかけた                                | いまどおり承認の列へ                                                                    |
| 黄・再発 | 比較できる 2 件以上で同じ兆候（material.py の SIGNAL の種類と場所が同じ） | 承認の列へ                                                                              |
| 黄・1 件 | 1 件だけ                                                                  | `候補` として Beads に残し、28 日以内に再発しなければ自動で閉じる（`- 却下: 再発なし`） |

これで人が見るドラフトは、赤と再発だけに絞られる（直近 28 日の 166 件が何件になるかは、3.1 の記録が
揃ってから数える）。hook が正しく拒んだ件は摩擦に数えず、「成功した防御」として tally にだけ残す。

**3.2.4 出し先の梯子と常設の予算。** 出し先は hook・検査 → スクリプト・道具 → スキル → サブエージェント →
常設の文章 の順に当て、上の段で済むものを下の段に置かない。常設の文章（CLAUDE.md + `.claude/rules/`）には
`test/architecture/` に字数の上限の検査を置く（値は 6 章の判断 1）。`docs/workflow.md`「タスクを書くとき・
受け入れるとき」の散文の項目は、1 項目ずつ 3.2.1 の形（狙う兆候・出し先の種類）に写し、hook・検査・
`tw` の判定に置き換えられるものは置き換え、置き換えられないものだけを残す（25 項目の棚卸し）。

**3.2.5 「何の失敗を防ぐ部品か」の 1 行。** CLAUDE.md の各規則・rules の各行・hook・スキルの description に、
防ぐ失敗（兆候の種類）を 1 行持たせる（CLAUDE.md は末尾の索引に列を足す）。モデルの世代が上がったら、
その部品を外して 3.3 のタスクの再試で比べ、差が出なければ外したままにする。

### 3.3 ハーネスのタスクの再試評価

**3.3.1 凍結したタスクの再試集。** 送り出し済みのタスクから 20 件を選び（difficulty と種類を散らす）、1 件ごとに
着手時の main のコミット・タスク本文（`tw show` の写し）・完了条件を確かめる台本（検証コマンドと、完了条件の
各行を機械で見る `node` の台本）を `test/harness-replay/<ID>/` に凍結する。会話の実物は入れない（本文は
Beads の課題の写しで、会話内容ではない）。

**3.3.2 走らせ方。** `node scripts/dev/harness-replay.ts --tasks <ID,…> --k 2` が、1 件ごとに一時の
作業ツリーを着手時のコミットで起こし、いまのハーネス（CLAUDE.md・rules・スキル・hook・モデルの表）で
`claude -p` か SDK の `query` を使って委譲の流れを 1 回走らせ、完了条件の台本・トークン・時間・拒否の
回数を記録する。出力は pass^k（k 回とも通る）・1 件のトークンの中央値・時間の中央値。

**3.3.3 使うとき。** CLAUDE.md・rules・スキルの本文・hook・モデルの表・`.tw/config.toml` を変えるタスクは、
送り出しの前にタスクの再試集の 5 件以上を k=2 で前後比べ、差を介入台帳に書く。差が「3 ポイント未満は疑う」
（Anthropic infrastructure-noise）の線を越えなければ no observed effect とし、常設の文章を増やす変更は
そのまま積まない。

**3.3.4 盲検の対の判定。** 通過率で差が出ない変種（文章の書き方・レポートの描き方）は、同じ依頼から書いた
2 本を順を入れ替えて 2 回判定する LLM の対の判定で比べる（レポートの戦略で保留中の「利用者の選んだ対で
較正した LLM の対の判定」と同じ仕組み）。

費用の見積もり: 1 件のタスクの再試を 1,000 万トークンとすると、5 件 × k=2 で 1 億（30 日の消費量の 0.5%）、
20 件 × k=3 で 6 億（2.8%）。
