## 結論（3行）

1. **「設定しづらい」の主因は環境変数ではない。** 7つの `TSUKUMO_*` のうち**3つは開発専用**
   （`DRIVER` / `FAKE_SCENE` / `WATCH_UI`）、**2つは起動1回きりの逃げ道**（`NEW_SESSION` / `OPEN_VIEW`）で、
   「一度決めたら変えない」のは `VIEW_PORT` と `CHARACTER` の**2つだけ**。設定ファイルを足しても
   移せる行が2行しかない
2. **実際に毎回やり直しているのは「画面で選んだのに覚えてくれないもの」**（モデル・許可モード・
   雑談モードの3つは毎起動で `opus` / `auto` / 仕事に戻る）と、**ポートがずれると消えたように見える
   `localStorage` の2つ**（領域の比率・画面の3色）。**推す案は C**: 人が書く設定ファイルを作らず、
   既にある `~/.tsukumo/state.json` を「最後に選んだものを覚える1ファイル」に育てる
3. **DB（SQLite など）は要らない。** 書き方も読み方も各1つしかなく、実測で `~/.tsukumo` の 12MB のうち
   **11.6MB（96%）は立ち絵の PNG** で、記録のほうは初日で 63KB。`node:sqlite` は Bun 1.4.2 では
   import できるが **1.3.8 では無い**ので、採ると Bun の下限を上げることになる（下の「DB は要るか」）

## 2. 論点に答える

### 2.1 「設定しやすい」が指すもの — 毎回変えるものと、一度決めたら変えないもの

| 環境変数              | 毎回変えるか                       | 移し先の候補                                         |
| --------------------- | ---------------------------------- | ---------------------------------------------------- |
| `TSUKUMO_VIEW_PORT`   | **変えない**（一度決めたら固定）   | 設定ファイル／覚える                                 |
| `TSUKUMO_CHARACTER`   | **変えない**（画面の切り替えが主） | 覚える（#8 が既にやっている）                        |
| `TSUKUMO_OPEN_VIEW`   | 起動1回きり（タブを開き直すとき）  | **環境変数のまま**                                   |
| `TSUKUMO_NEW_SESSION` | 起動1回きり（逃げ道）              | **環境変数のまま**（設定に書いたら逃げ道でなくなる） |
| `TSUKUMO_DRIVER`      | 開発・目視確認のときだけ           | **環境変数のまま**                                   |
| `TSUKUMO_FAKE_SCENE`  | 開発・目視確認のときだけ           | **環境変数のまま**                                   |
| `TSUKUMO_WATCH_UI`    | `bun run dev` が渡す               | **環境変数のまま**（人が打たない）                   |

**移せるのは2つだけ**で、しかも `TSUKUMO_CHARACTER` は**既に画面の切り替え＋ `state.json` に置き換わっている**
（`docs/design.md` 5章が「この口が要るのはパックを3つの探し先の外に置いたときだけ」と書いている）。
**環境変数を設定ファイルに移す作業の利得は、実質 `VIEW_PORT` の1行**。

対して、**毎起動でやり直しているのは #15 の3つ（モデル・許可モード・雑談モード）**と、
**ポートがずれた回の #13・#14** ——「設定しづらい」の体感はここに集まっている、というのがこの棚卸しの
読みどころ。**設定ファイルを足してもこの5つは1つも解けない。**

### 2.2 設定ファイルを足すなら、置き場と優先順位

足すと決めた場合の答えだけ書く（足すかどうかは 3章）。

- **置き場は `~/.tsukumo/config.json` の1つだけ。プロジェクトごとは作らない。**
  `~/.tsukumo/` は「`cwd` に依存させない」を設計が明示的に選んだ置き場で（`docs/design.md` 7章・
  chat-archive と chat-summary の両方に同じ文がある）、プロジェクトごとの設定を足すとその線が割れる。
  プロジェクトで変えたい値は素材だけで、それには **`<cwd>/characters/local/` という `cwd` 相対の口が
  既にある**。置き場が2つあると「いまどっちが効いているか」を毎回考えることになり、**設定しやすさの逆**
- **優先順位は 環境変数 > 設定ファイル > 既定。** 環境変数は「この1回だけ違う値で起こす」ための口なので、
  必ず最後に勝つ側に置く
- **読むのは1箇所（`core/config.ts`）のまま。** ファイルを読むのは外の世界に触る操作なので、
  実際の `readFileSync` は `adapter/` に1ファイル置き、`core/config.ts` は**読み終わった値を
  重ねるだけ**にする（原則3。`cli.ts` が `process.env` を読むのと同じ形）
- **不正な値で落とさない。** いまの `readConfig` と同じく、読めない値は既定へ倒す

### 2.3 対象外（`docs/requirements.md` 2.2）に当たらないか

**当たりうるのは「汎用の設定機構」**。対象ユーザーは作者本人だけで、**手元にソースがある**ので、
`MAX_MAIN_VIEW_TURNS`（5）や `CHAT_COMPACT_THRESHOLD_BYTES`（32 KiB）のような定数は
**その場で書き換えて起こし直せば済む**。これらを設定項目として外に出すのは、利得のない一般化になる。

下の案はどれも **(a) 起動前に決まっていないと動かない値**（ポート）と
**(b) 画面で選べるのに覚えていない値**（#15・#13・#14）だけを対象にし、
**定数を設定項目に昇格させることはしない。**

## 3. 案の比較

### 案A — 何も足さない（現状維持）

環境変数のまま。毎起動でモデル・許可モード・雑談モードを選び直し、ポートがずれた回は比率と色が戻る。

| 何が楽になるか | 増える手数                | 目的に沿うか                              |
| -------------- | ------------------------- | ----------------------------------------- |
| 何も           | ゼロ。読む場所も1つのまま | 沿う（足さないことは常に 2.2 に適合する） |

**採る理由になるとすれば**: 起動のたびの選び直しが実際には苦になっていない場合。
**この文書はそれを測っていない**ので、まずここを確かめるのが安い。

### 案B — `~/.tsukumo/config.json` を足し、人が書く設定にする

`VIEW_PORT` と `CHARACTER`（と、必要なら `OPEN_VIEW`）を書けるようにする。優先順位は 2.2 のとおり。

```json
{ "viewPort": 7327, "character": "characters/local" }
```

| 何が楽になるか                                         | 増える手数                                                                                                                     | 目的に沿うか                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| `tsukumo` を素で打てる（環境変数を毎回書かなくてよい） | 読む口が1つ増える（`adapter/` に1ファイル＋検証）。**値の出どころが2つに増え、「効いていない」を調べるとき両方見ることになる** | 半分。**移せる行が実質1〜2行**で、#15 は1つも解けない |

**弱いところ**: 2.1 の表のとおり利得が薄い。加えて、**人が JSON を手で書く画面を新しく作る**ことになり、
tsukumo が「画面で選ぶ」方向に積み上げてきた口（キャラクターの切り替え・立ち絵の差し替え・色）と
**入口が割れる**。

### 案C（推す）— 設定ファイルを作らず、`~/.tsukumo/state.json` を「覚える1ファイル」に育てる

**人が書く設定ファイルは作らない。** 既にある #8 の `state.json` を、**最後に選んだものを覚える**
ファイルに広げる。スキーマは `zod` で見てあるので、鍵を足すのはその1箇所。

```json
{
  "character": "tsukumo",
  "model": "opus",
  "permissionMode": "auto",
  "chatMode": false,
  "viewPort": 7327,
  "layoutSplit": { "rowTop": 60, "topLeft": 50, "bottomLeft": 50, "collapsedRowTop": null },
  "appearanceColor": { "ground": null, "surface": null, "ink": null }
}
```

- **書くのは画面で切り替えたその場**（#8 が `switch-character` でやっているのと同じ形）。
  `adapter/remembered-character.ts` が既に「書けなくても例外を投げない」を守っているので、
  **境界は1つも増えない**（原則3）
- **`localStorage`（#13・#14）から `state.json` へ移すと、ポートがずれても比率と色が残る**
  ——2.1 で挙げた体感の半分はこれで消える
- **読むのは起動時の1回**で、`SessionState` の初期値として配る。ブラウザ側は今までどおり
  `SessionState` を受け取るだけ（`docs/design.md` 2章の「browser は `SessionState` で受け取るだけ」を保つ）
- **古い鍵・知らない鍵は既定へ倒す**（いまの `safeParse` の振る舞いのまま）

| 何が楽になるか                                                                                                 | 増える手数                                                                                                                            | 目的に沿うか                                                                          |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **起動して即そのまま使える**（モデル・許可モード・雑談モード・比率・色が前回のまま）。ポートがずれても崩れない | `state.json` のスキーマが1つ → 7つに増える。**比率と色の正典がブラウザからサーバへ移る**ので、その2つの読み書きを書き換える必要がある | 沿う。**新しい設定の言語を作らず、いまある「覚える」を広げるだけ**で、利用者は作者1人 |

**弱いところ**

- **許可モードを覚えるのは危ない。** `bypassPermissions` のまま終了すると、**次の起動が黙って緩む**。
  「覚えるが、`bypassPermissions` だけは既定へ戻す」か「許可モードは覚えない」かを決める必要がある（5章の3）
- **ポートを覚えると、ずらした先が焼き付く。** 2つ目の tsukumo が 7328 で起きて、それを覚えると
  次から1つ目も 7328 を狙う。**ポートは「明示的に渡したときだけ覚える」か、覚えない**のが無難
- **雑談モードを覚えると、仕事のつもりで起こしたときに雑談で立ち上がる。** これも決め（5章の3）

### 3.1 3つの並び

| 軸                                     | A        | B                           | C                          |
| -------------------------------------- | -------- | --------------------------- | -------------------------- |
| 毎起動の選び直し（#15）が消えるか      | 消えない | 消えない                    | **消える**                 |
| ポートがずれた回の比率と色（#13・#14） | 戻る     | 戻る                        | **戻らない**               |

## 4. DB は要るか — **要らない**

### 4.1 結論

**いまの tsukumo に SQLite（あるいは他の DB）は要らない。** 候補として挙がった `chat-archive/` と
`chat-summary/` は、どちらも DB が解く問題を持っていない。

### 4.2 根拠

1. **量が足りない。** 実測で `chat-archive` は**初日で 63 KB / 1ファイル**。同じ伸び方なら1年で 23 MB 程度で、
   日付でファイルが割れているので1ファイルは 63 KB のまま。**一方 `~/.tsukumo` の 12 MB のうち
   11.6 MB（96%）は立ち絵の PNG**（#9）で、**DB はこれを1バイトも減らさない**。
   （参考: claude 自身の transcript は 1.2 GB / 803 ファイルあるが、**あれは tsukumo が持つものではない**）
2. **読み方が1つしかない。** `readRecent(pack, 16 KiB)` ——「新しい日のファイルから、末尾の行を遡って
   文面が 16 KiB に届いたら止める」。**日付のファイル名がそのままインデックス**になっていて、
   B-tree が要る問い合わせ（横断検索・期間の集計・結合・並べ替え）が**1つも無い**。
   読む量はファイルが何年ぶん増えても変わらない
3. **書き方も1つしかない。** 1件 = 1行の追記。**複数行が揃って初めて意味を持つ更新が無い**ので、
   トランザクションの出番が無い。むしろ現在のエラー方針（「書けなくても例外を投げない。落ちるのは
   その1行だけ」＝ `docs/coding-standards.md`「常駐プロセスは描画1回の失敗で落ちない」）と、
   DB の「開く・文を用意する・コミットする・閉じる」は**失敗の粒度が合わない**
4. **人が読めて、人が消せることを設計が明示的に選んでいる。** `docs/design.md` 7章が
   「太り方が目で分かり、消す単位も人に分かる」「JSONL は壊れても被害が1行で、`grep` でも読める」を
   採用の理由として書いている。**DB にすると会話が不透明なバイナリ1本になる** ——
   `docs/coding-standards.md`「会話内容の扱い」の観点でも、**中身を目で確かめられず、日ごとに
   手で消せなくなる**のは後退
5. **依存が増える。** SQLite を使うなら道は2つ:
   - **`node:sqlite`（標準API側）**: 実測で **Bun 1.4.2 では import できる**が、
     **`~/.bun/bin/bun` 1.3.8 では `No such built-in module: node:sqlite`**。`CLAUDE.md` の
     セットアップは **Bun 1.3 以上**なので、採用は**下限を 1.4 へ上げる**ことを意味する。
     Node 側でも実験的扱いの API
   - **`better-sqlite3` などの外部ドライバ**: ネイティブビルドが要り、`docs/research/external-dependency.md`
     の「スタンドアロンで動かしたい」方向と逆に働く

   **どちらの道も、入れるのはユーザーの承認後**（`CLAUDE.md`「`orca` 以外の外部コマンド依存を増やす
   ときはユーザーの承認を得る」）。この文書は提案までで、**依存は1つも足していない。**

### 4.3 では何が要るのか（DB の代わりに効くもの）

棚卸しで出た「消えないのに消す口が無い」の2つ（#9・#12）に、**上限か捨てる口**を付けるほうが効く。
どちらも DB を要求しない。

| 対象                           | いま                           | 効く手                                                                                              |
| ------------------------------ | ------------------------------ | --------------------------------------------------------------------------------------------------- |
| `~/.tsukumo/characters/<pack>` | 11.6 MB。捨てる口が無い        | **画面から「このパックを捨てて同梱に戻す」**（#10・#11 が既に上限と上書きを持っているのと同じ発想） |
| `~/.tsukumo/chat-archive/`     | 日ごとに増え続ける。消すのは人 | **保持日数**（古い日付のファイルを落とす）。ファイル名が日付なので判定に中身を読まなくてよい        |

**どちらも決めごとなので、この文書では実装しない**（5章に載せる）。

### 4.4 DB が要るようになる条件（先に書いておく）

次のどれかが来たら、この結論を読み直す。

- **雑談のアーカイブを画面から横断して検索する**と決めたとき（「あの話いつだっけ」）。
  ただしその前に `grep` / `rg` で足りるかを試す ——JSONL を選んだ理由の1つがそれ
- **同じパックへ複数の tsukumo プロセスが同時に追記して行が壊れる**のを実際に観測したとき
  （いまは追記オープンで、1行が小さいうちは混ざらない）
- **日付ファイルが1000を超える**か、`~/.tsukumo` の記録側が数百 MB を超えたとき
  （いまの伸び方だと十数年先で、その前に 4.3 の保持日数が効く）

## 5. 次に決めてほしいこと

1. **「設定しやすい」の的はどれか。** (a) 環境変数を減らす／(b) 起動のたびに選び直すのをやめる／
   (c) 画面から設定を変えられるようにする。この文書の読みは **(b)** だが、**体感の正典はユーザー**
2. **案 A / B / C のどれを採るか**（推すのは C）。B と C は排他ではないが、**同時に採ると値の出どころが
   3つ**（環境変数・設定ファイル・覚えたもの）になるので勧めない
3. **C を採るなら、覚える対象に何を入れるか。** 候補は モデル／許可モード／雑談モード／領域の比率／
   画面の3色 の5つ。**特に次の2つは別に決めてほしい**:
   - **許可モードを覚えてよいか**（`bypassPermissions` を覚えると次の起動が黙って緩む。
     「覚えるが `bypassPermissions` だけ既定へ戻す」案もある）
   - **雑談モードを覚えてよいか**（仕事のつもりで起こして雑談で立ち上がる）
4. **ポートを覚えるか／固定するか。** ずらしを続けるなら覚えないのが無難（3章の「弱いところ」）
5. **人が書く設定ファイル（`config.json`）を作るか。** 作らないなら、環境変数まわりで残る宿題は
   **`README.md` の表に `TSUKUMO_FAKE_SCENE` の行を足す**ことだけ
6. **`~/.tsukumo/characters/<pack>` の写し（実測 11.6 MB）を捨てる口を作るか**、
   **`chat-archive/` に保持日数を設けるか**（4.3）
7. **DB は要らないという結論でよいか。** 要ると判断するなら、`node:sqlite` を使うために
   **Bun の下限を 1.3 → 1.4 へ上げる承認**が要る（4.2 の 5）
