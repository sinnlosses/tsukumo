## 4. 案

3案とも、指した所は同じ印で見せる。指した行・案・主張は左端に差し色の線を引き、地を差し色でわずかに染める。今の形の「欄を開いている行」の地と、「聞いたことのある行」の左端の線を合わせた見え方である。

### 案 A 余白の注釈

- **下敷き**: Google ドキュメントのコメント（選んだ所の横にボタン1つ・余白の欄）と、Hypothesis（選んだ所にだけ出す口）。
- **ボタンの出し方**: 何も押していないときはボタンを出さない。代わりに、本文の右の余白に「字・行・案を選ぶと、ここに「聞く・頼む」が1つ出る（⌘⌥M）」と書いておく。字を選ぶか、行・案・主張を押すと、その横の余白に「聞く・頼む」が1つ出る。
- **欄**: 「聞く・頼む」を押すと、余白に札が開く。札の頭に指した所の1行と、聞く・頼むの切り替えがある。本文は押し下げない。
- **答え**: 札がそのまま問いと答えの札になり、指した所の横に残る。同じ答えは吹き出しにも出る。指した行には「聞 1」の印を付ける。
- **付箋**: 余白の付箋の札と、入力欄の上の頼みごとの列（今の形と同じ）。案・主張に「頼 n」の印を付ける。「この案で進める」「確かめて」のボタンは置かず、案・主張を指して頼むにする。画は付箋になったあとだけを写した。
- **狭い幅・触れる画面**: 幅 700 では余白が無いので、「聞く・頼む」を行の右に出し、欄と答えは下から出すシートにする。触れる画面では、行を押すと指す。
- **弱いところ**: 幅 1400 でも、余白の分だけ本文の幅が狭くなる（試作では余白を 248px にした）。何も押していないときに操作が見えないので、余白の書き添えとキーで補う。⌘⌥M が macOS やブラウザのキーとぶつからないかは確かめていない。

### 案 B 行の印とまとめて頼む

- **下敷き**: GitHub のプルリクエストのレビュー（行の横の「＋」1つ・積んでおく pending のコメント・Submit review でまとめて送る）。
- **ボタンの出し方**: 部品ごとに、題の行の左に薄い「＋」を1つ常に出す。表の行・案・主張は、重ねたとき・フォーカスしたとき・押したときに、その行の左の溝に「＋」を1つ出す。
- **欄**: 「＋」を押すと、行の下に1行の欄が開く。欄の頭に指した所の1行がある。送るボタンは「いま聞く」と「付箋に積む」の2つで、聞くか頼むかを送るときに選ぶ。今の欄より低いので、押し下げは 94.18px に縮む。
- **答え**: 行の下に、答えを1行に畳んで残す（「開く」で広げる）。同じ答えは吹き出しにも出る。行には「聞 1」の印を付ける。
- **付箋**: 指した行の下に「保留」の1行として残す。レポートの上の帯に「頼みごと 2 件は、まだ送っていない（自分にだけ見える）」と「まとめて頼む」を出す。入力欄の上の列は使わない。
- **狭い幅・触れる画面**: 幅 700 でも同じ形。触れる画面では重ねられないので、行を押すと「＋」が出る。
- **弱いところ**: 欄を開くと、まだ本文が押し下がる。答えと付箋の行が本文に残り、表の外枠が伸びる。左の溝の分だけ表が右へずれる。

### 案 C 入力欄へ引用

- **下敷き**: ChatGPT の「Ask ChatGPT」の帯、Claude の Reply、assistant-ui の引用（選んだ所を入力欄へ引用）と、Linear（字に結んだコメント）。

## 5. 解くべき論点への答え

### 論点 1: 案の組み方

ボタンの出し方と、入力欄・答えの置き場を、次の3組にした。「今の形のまま数を減らす」は B の題の行の「＋」に近く、別の案にはしなかった。

| 案  | ボタンの出し方                    | 入力欄・答えの置き場                           | 下敷き                                         |
| --- | --------------------------------- | ---------------------------------------------- | ---------------------------------------------- |
| A   | 選んだ所に1つ出す                 | 右の余白（狭い幅では下から出すシート）         | Google ドキュメントのコメント・Hypothesis      |
| B   | 部品・行の端に印を1つ出す         | 行の下の低い欄、答えは畳んで本文に残す         | GitHub のプルリクエストのレビュー              |
| C   | 選んだ所の近くに小さな帯を1つ出す | 入力欄へ引用、答えは吹き出しとやり取りの列だけ | ChatGPT・Claude の Reply・assistant-ui・Linear |

### 論点 2: 細かい単位で、指した所をどう見せるか

3案とも、行・案・主張ごとにボタンを並べない。指した単位に差し色の線と地を付け、欄の頭（A は余白の札、B は行の下の欄、C は入力欄の引用）に指した所の1行（`検査ごとの所要 › 表 1 › E2E（会話）`）を出す。答えたあとと付箋にしたあとは、単位の横に小さな印を残す。A・B は「聞 1」、C は番号の印、付箋は A・C が「頼 n」、B が「保留」。「この案で進める」「確かめて」のボタンもやめ、案・主張を指して頼むにする。

### 論点 3: 答えを本文に残すか

- A は本文の流れの外（余白の札）に残す。本文を押し下げず、答えは指した所の横にある。
- B は本文の中に、1行に畳んで残す。残る分は幅 1400 で 43.79px に減るが、0 にはならない。
- C は本文に残さず、吹き出しとやり取りの列にだけ出す。見返すには、本文の印からやり取りの列へ移る。

本文を押し下げずに答えを見返す道を、A は余白の札で、C は印からの移動で作る。B は押し下げを小さくする案で、見返す道は畳んだ1行である。

### 論点 4: 「引いて聞く」と部品・行を指す「聞く」をまとめるか

3案ともまとめる。A は字を選んでも行を押しても、同じ余白の「聞く・頼む」が出る（Google ドキュメント・Hypothesis と同じく、選んだものが何でも口は1つ）。B は選んだ字のある行の溝に、同じ「＋」を出す（試作の画は行を指したときだけを写した）。C は今の「引いて聞く」（入力欄の頭へ引用）を、行・案・主張にも広げる形で、もっとも素直にまとまる。

### 論点 5: 狭い幅（700px）と触れる画面

- A は余白が無いので、「聞く・頼む」を行の右に出し、欄と答えは下から出すシートにする（高さ 205.77px、本文は押し下げない）。触れる画面では、行を押して指す。
- B は幅 700 でも同じ形で、押し下げも 94.18px のまま。触れる画面では、行を押すと「＋」が出る。題の行の「＋」は常に見えるので、何も押していないときの 3 個は変わらない。
- C は形が変わらない。引用が入る分だけ入力欄が伸び、本文の見える高さが 61.59px 減る。

今の形は、触れる画面（`hover: none`）では 30 個のボタンが常に見える。3案はどれも、触れる画面でも数が増えない。

## 6. おすすめ

**A（余白の注釈）をすすめる。** 理由は次の3つ。

- 何も押していないときのボタンが 0 個、指したときが 1 個で、今の形（重ねられる画面で 4 個と 8 個、触れる画面で 30 個）からいちばん減る。利用者が挙げた「ボタンが並んでうるさい」に、ボタンの数を減らすことで直接答える。
- 欄を開いても本文を押し下げない（今の形は 208.78px）。答えは指した所の横に残る。ADR 0051 が決めた「答えを聞いた所のそばに残す」形を、本文の流れの外で保てる。
- 付箋の札と頼みごとの列は今の形のままで、変える所が少ない。

B は押し下げを半分以下にするが、0 にはならず、本文に答えと付箋の行が残る。C はいちばん作りやすいが、答えが指した所から離れ、入力欄が依頼と聞く・頼むを兼ねる。A を選ぶなら、次の段で決めることは、余白の幅と本文の幅の配分、何も押していないときの手がかり（余白の書き添えで足りるか）、キーの割り当ての3つである。

## 7. 確かめていないこと

- 試作は画を撮るためのもので、選ぶ・押す・送るは動かない。字を選んだときの帯の出方（A・C）や、選んだ字の行に「＋」を出すこと（B）は画に無い。
- 試作の字は Figtree を読み込んでおらず、端末の字（-apple-system・Hiragino Sans）で描いている。色はテーマのトークンの値（`src/browser/styles/theme.css`）と、tsukumo のパックの差し色 `#6fe3cd` を写した。
- 触れる画面は実機で触っていない。数は CSS の規則と試作の作りから数えた。
- ⌘⌥M（A）が macOS・ブラウザのキーとぶつかるかは確かめていない。
