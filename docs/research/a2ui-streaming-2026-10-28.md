# A2UI の部品を引数の断片から 1 つずつ描けるか（2026-10-28）

ステータス: 一次情報（測定の記録）。採るかの決定は利用者が持つ。

問い: Agent SDK の `includePartialMessages` の断片に `report` の引数の JSON の途中が入るか。入るなら、部品の境目で区切って 1 部品ずつ描き始められるか。そのとき最初の部品が見えるまでの時間は、全部が届くまでの時間とどれだけ違うか。

## 結果

測定は疑似の長い報告 1 本を 1 回（sonnet）。依頼は架空のアプリの架空の事実だけで、実際の会話は使っていない。

## 測り方

- `scripts/runtime/a2ui-fragment-record.ts`: SDK の `query()` を直に呼び、組み込みツールを外して `report` だけを持つ進行内 MCP サーバで 1 ターン走らせる（`permissionMode` は `default`）。断片の種類・時刻・字数を表にし、本文は作業ツリーの外にだけ書く。
- `scripts/runtime/a2ui-streaming-trial.ts`: 録った断片を順に足し、`src/server/session-driver/core/a2ui-component-splitter.ts` の読み手で部品が閉じる時刻を測る。
- 1 回だけの測定で、モデルと依頼の長さを変えた比較はしていない。時刻は 1 回の実行の値で、ばらつきは測っていない。本番の経路は変えていない。

## 判断に効く点

断片に引数の JSON は入り、部品を 1 つずつ切り出すこともできる。採るかの決定は利用者。材料を並べる。

- 採るなら変えるもの:
  - 駆動: `reportDraftingEvents`（`src/server/session-driver/core/sdk-stream-message.ts`）の隣で、メインの `report` の塊の `input_json_delta` を足して読み手に渡す。塊ごとに状態を持つ。
  - イベント: `report-drafting` は引数の断片を運ばない。部品の断片を運ぶイベントを足す（セッションイベントの種類が増え、E2E の期待値も変わる）。
  - ブラウザ: 部品が届くたびに `updateComponents` を流して描く。親が先に描かれ、子が届くたびに埋まる動きは試作で確かめ済み（`docs/research/a2ui-report-prototype-2026-10-28/index.md`）。
- 効果: 長い報告で最初の部品が見えるまでの時間が、この測定では約 15 秒短くなる。節の数が少ない短い報告では差が小さい。
- 採らない理由になりうる点:
  - 差し戻し（`VALIDATION_FAILED`）の判定は呼び出し全体が届いてから `report` ツールが行う。先に描いた部品が後で差し戻されると、描いたものを取り消す必要が出る。
  - 部品の構造の規約（根・節・葉の入れ子）は全部の部品が揃わないと判定できない。途中の描画は、規約に合うか分からないまま出ることになる。
  - 目次・演出・復元は、いまは完成した報告を前提にしている。途中の状態を扱う変更が、それぞれに要る。
  - 現状の駆動は、完成した `report` のイベントを 1 回だけ流す。1 回だけの測定なので、効果の大きさは見込みの域を出ない。
