## 13. 画面のデザイン

### 13.14 トークン消費の見直し区画

トークン消費の画面の「減らし方を見てもらう」区画（`token-usage/components/usage-review-card/usage-review-card.tsx`。
題の帯といまのコンテキストの札のあいだ）の、文言・配置・押せない条件・経過時間の書式。
区画の地・枠・札・ボタンの色とその理由は 13.2 Color。

**題の帯の右の「見直し中」は `<span role="status">`**（見本は `disabled` の `<button>`）——押せない
ことを示すだけの印で、実際に押せるボタンに見せる理由が無いため。地の不透明度は見本の 0.45 では
薄すぎたので 0.6 にした（この画面の地 `--usage-card` に対する実測での見やすさ）。

**段の印は `current-work-pill.tsx`（「いまの作業」の札）と同じ文字**（済 = ✓、進行中は
回る「…」、未着手は ○）にする。見本は SVG のチェック・スピナー・丸だが、新しい絵を増やさず
帯と同じ読み方に揃えた。回る印は `current-work-spin` と同じ仕組み（`animation` を
`prefers-reduced-motion: reduce` で止める `theme.css` の全体規則に乗る）なので、動きを減らす
設定のための分岐は要らない（「解くべき論点」の回答）。**経過の書式も見本の `M:SS` ではなく
`<TurnStatus>` と同じ「N秒」「M分SS秒」** にする（`dispatch/hooks/use-turn-status.ts` から
`browser/domain/elapsed-time.ts` の `formatElapsed` へ出し、2つの機能で共有）——アプリの中で
経過時間の書き方を2通り持たない。

ふだんの区画の決め事（この画面を作ったタスクの本文）への回答:

- **ボタンを押せないとき**: 提案の実行が走っている間だけ押せず、理由「いま提案を頼んでいる。
  終わってからもう一度押す。」を区画の下に文で出す。見直しは会話とは別の問い合わせで走るので、
  仕事のターンの進行中も雑談中も押せる（`docs/architecture/adr/0029-usage-review-own-query.md`）
- **直近のセリフの出どころ**: 見直しの問い合わせの `speak` が流したセリフ（`usageReview.speech`）。
  会話の吹き出し（`SessionState.speeches`）とは混ぜない（まだ無ければ何も出さない）
- **狭い幅での段の並び**: 760px 以下で2列→1列（他の区画と同じ境目。`usage-review-card.module.css`
  末尾の `@media`）
- **段の右の数**: モデル・キャッシュ・ツールの3段だけ、手続き `tokenUsage.summary` に
  `usageReview.days` を渡して引く。**`usageReview.days` が選べる日数（1/7/30）でなければ数を出さない**
  ——手続きの入力は選べる日数だけなので、それ以外の値では引けない（見た目の期間と違う数を出さない）
  （コンテキスト・見直し案の2段は数える元が無いので常に出さない）
- **終わりの知らせ**: 区画の外には出さない。見直しは仕事の会話のターンではないので、ヘッダーの
  「いまの作業」の札も会話の吹き出しも動かない。見直し中の注記は「ほかの画面に移っても続きます。」だけにする
- **「前回の提案」リンク**: 押しても現時点では何も起きない（`use-usage-review.ts` の
  `previousReviewView` にその旨のコメントがある）。結果の札を描く後続タスクが、押すと同じ札の
  形で開く配線に差し替える

いまのパックの顔（`CharacterInfo.face`）をこの区画にも出す。`<CharacterFace>` へ渡す形
（`{ url, alt }`）は帯（`screen-nav`）と同じ導き方なので、`browser/domain/character-face.ts`
（`characterFaceInfo`）へ出して2機能で共有した（AGENTS.md 原則5）。

**結果の場面**（`usage-review-card.tsx` の `ResultReviewCard`。見本
`docs/history/mockup/token-advice-result-2026-09-23.html`）は、**今回の結果
（`usageReview.kind === "result"`）と「前回の提案」を開いたとき（`previousUsageReview`）の
両方で同じ部品を使う**（`use-usage-review.ts` の `resultView`。「解くべき論点」への回答）。
「前回の提案」は画面を移さず、区画がその場で同じ札の形に差し替わり、右上に「閉じる」が出て
「ふだん」へ戻れる（今回の結果には「閉じる」を出さない——戻る先の「ふだん」が無いため）。

結果の場面の決め事（もとのタスク本文）への回答:

- **主ボタンを押したあと画面をどうするか**: **留まる**。主ボタンは会話へ送らず、その提案だけの
  別の問い合わせを起こす（`usageReview.runProposal`）ので、移る先が無い。「機能の側は `useScreen` を
  読まない」（13.9）にも沿う
- **全部見送ったときの区画の一言**: 「いま出せる提案は無い。」（見送りきった・スキルがそもそも
  挙げなかったの両方に使う——`UsageReviewFindings.proposals` にはどちらだったかの区別が無い）
- **押せないあいだの主ボタン・「もう一度見てもらう」の扱い**: 見直しも提案の実行も1度に1つだけ
  走るので、ふだんの「減らし方を見てもらう」と同じ理由（`startAvailability`）を1つだけ出し、
  主ボタンの数だけ繰り返さない。**「見送る」は走りを起こさないので、いつでも押せる**
- **提案の実行の様子**: 実行した提案（`usageProposalRun.key` が一致する札）の本文の下に、区切り線を
  引いて1行で出す。走っている間は「頼んでいる…」（`--accent`）・経過・直近のセリフ・「止める」、
  終わったら「済んだ」「できなかった」「止めた」とセリフ。次の実行を頼むまで残す。狭い幅では折り返し、
  「止める」は右へ寄る。ほかの札には出さない

結果の場面の見た目の決定（色の項目は 13.2 Color）:

- **主ボタンの文言は `delegate` → 「tsukumo に頼む」、`task` → 「タスクにする」の2つに固定**
  （`docs/requirements.md` 4.12「トークン消費の見直し」）。見本にある「設定を開く」は置かない
  （2026-09-23 ユーザー決定。行き先が無いため）
- **頭の吹き出しは三角を描かず、左上の角だけ立てる**（`border-radius: 0.25rem 0.875rem …`。
  見本と同じ手）。新しい部品（`<Balloon>`）は増やさない——`components/page/conversation/components/character-view/` に
  閉じた部品で、2機能目のこの区画から読むには `browser/domain/` へ上げる手間が要り、この
  区画だけの単純な吹き出しにその手間は見合わない
- **日時は見本の `[MM-DD HH:MM]` の角括弧を付けない**（他の画面に角括弧で時刻を囲む言い回しが
  無いため）。期間は「直近 N 日」（1日だけは「今日」——`presentational-token-usage.tsx`
  の期間の切り替えと同じ言い換え）

**会話の画面には見直しの導線を置かない。** 見直しは仕事の会話のやり取りにならないので、結果の札を
開くリンクを添える先が無い（`docs/architecture/adr/0029-usage-review-own-query.md`）。
