# ワークフローの契約

最終更新: 2026-10-10。ステータス: **正典**。

責務: tsukumo がワークフロー（タスクを段に分けて送り出す手順）に対して定める契約 — 受ける口の名前と引数の意味、
委譲の返却の書式と関門、読む Beads の欄、ワークフローがしてよいことと tsukumo が読まないもの — を1か所に持つ。
読む時: 独自のワークフローを tsukumo に当てるとき、`tsukumo-plugins` のワークフローを直すとき、口の引数や Beads の読み口を変えるとき。
直す時: 口の引数・委譲の返却の書式と帯の進め方・関門・Beads の読み取る欄・読まないものを変えたとき。判断の経緯は
`docs/architecture/adr/0024-no-skill-dependency.md`、帯・中間レポートの描き方と差し戻しは `docs/architecture/display.md`「段取り」が持つ。

## 節の索引

| 節              | 中身                                                 |
| --------------- | ---------------------------------------------------- |
| ## 契約とは何か | 契約が受けるもの、型の合うワークフローの立場         |
| ## 口           | 3つの口の名前と引数の意味                            |
| ## 委譲の返却   | 返却の1行目の書式、帯の進め方、関門                  |
| ## Beads の欄   | 読む欄と、読まないもの                               |
| ## してよいこと | ワークフローが呼んでよい口と、tsukumo が読まないもの |
| ## 合わせ方     | 利用者独自のワークフローが合わせる相手、置き場       |

## 契約とは何か

**契約は、タスクに段があり、並列に走る部分があり、それがパイプラインのように流れることを受ける口。** tsukumo が定めるのは
この口と、委譲の返却の1行目と、読む Beads の欄だけで、ワークフローの手順・道具・それ以外の書式は定めない。

契約を満たすワークフローは、`tsukumo-plugins` のものも利用者独自のものも同じ立場で tsukumo に当てられる。
`tsukumo-plugins` のものは契約に型の合う1つの例で、tsukumo の一部ではない。core は契約だけを見る。

## 口

口は MCP ツール `work_plan` と `report` と `clear_and_send`。意味はツールの説明（`src/server/session-driver/core/work-plan-tool.ts`・
`src/server/report/core/report-tool.ts`・`src/server/session-driver/core/clear-and-send.ts`）とシステムプロンプトの「段取り（tsukumo）」の節がモデルに教える。

`work_plan`（段取り。毎回段の並びごと渡す）:

| 引数                         | 意味                                                                                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `phases`                     | 段の並び（1つ以上）。要素は段の名前か、同時に走る段の名前の配列（段のまとまり。2つ以上・重ならない）。段の番号は並びを平らにした読み順                                   |
| `current`                    | 今の要素の位置（0始まり）。全部済んだら要素の数。最後の段を閉じるのは `report` の `workPlanClosing`                                                                      |
| `finishedInGroup`            | `current` が段のまとまりを指すとき、その中で済んだ段の名前。まとまりの最後の段を済ませる呼び出しでは `current` を進めて空にする                                          |
| `phaseSummary`               | 終えた段でしたこと・分かったことを1〜2文で。済んだ段があり全部は済んでいない呼び出しで必須。ただし返却で進んだ位置を同じまま渡す呼び出しでは省ける（下の「委譲の返却」） |
| （足す予定）`delegatedRange` | 委譲先の段の範囲。`first`（委譲先の段1に当たる位置。平らにした並びで0始まり）と `count`（段の数）。委譲しないときは省く。下の「委譲の返却」                              |

段は1つずつ進める（平らにした並びで済んだ段を1回で2つ以上増やす呼び出しは差し戻される）。並列にできるかを決めるのは渡す側で、
tsukumo は推し量らない。

`report`（ターンの結果）のうち契約に当たる欄:

| 引数              | 意味                                                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task`            | タスクの作業のレポートのときだけ。`id`（Beads の ID）・`name`（作業の名前）・`outcome`（`finished` 終えた／`stopped` 止めた／`awaiting-answer` 利用者の答え待ち） |
| `workPlanClosing` | 段の閉じ方。`work_plan` を渡した依頼では必須。`finished`（最後の段にいるときに渡すと tsukumo が帯を全部済みにする）／`stopped`（止まった段が「今」のまま残る）    |

`task.outcome` は目録の1行の終わり方で、帯は閉じない。どこへ送ったかは tsukumo の関心にしない。

`clear_and_send`（文脈を空にして次の依頼を送る。仕事のときだけ載る）:

| 引数   | 意味                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------- |
| `text` | 文脈を空にしたあとに最初の依頼として送る文面。呼んだ時点では何も送らず、tsukumo が文面だけを預かる |

呼んだターンが成功で終わると、tsukumo が `/clear` → `text` の順に続けて積む（`/clear` の完了は待たない）。
2つとも利用者の依頼と同じく列に出る。呼ばれたら送るだけで、いつ呼ぶかはワークフローが決める。
呼んだら `report` を渡してターンを終える。預かりは1つで、2回呼ぶと後のほうに置き換わる。
次のときは何も送らず、預かりを捨てる（画面にも知らせない）: ターンが中断・失敗で終わった・呼んだあとに利用者が
依頼か脇の話を送った・ターンの終わりに答え待ちが残っている・セッションが終わった。

## 委譲の返却

**委譲先が `SubagentHandback` で返す報告の1行目を、tsukumo が読んで帯を進める。** 書式の正典はこの節で、ワークフローの依頼文は
この節を参照し、書式を言い直さない。経緯と採らなかった案は `docs/architecture/adr/0024-no-skill-dependency.md`「2026-10-10 の改訂」。

返却の1行目（2行目より後ろは tsukumo は読まない。組み直しでは、仕掛けが足す前置き・注記の行と空の行を除き、字下げを外した最初の行を1行目とし、
その1行だけが形に合うかを見る）:

| 1行目                  | 意味                                                        | 帯                                    |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------- |
| `計画 0/N \| <要約>`   | 計画だけの回。段に数えず、委譲先の段の数が `N` だと知らせる | 進めない                              |
| `段 n/N \| <要約>`     | 委譲先の段 `n` を済ませた（`1 ≤ n ≤ N`）                    | 段 `n` に当たる帯の段を済ませる       |
| `止めた n/N \| <理由>` | 段 `n` の途中で止めた                                       | 進めない（段 `n` が「今」のまま残る） |

- `<要約>` は読み手から見た変化を1〜2文で書く。tsukumo はこれを済ませた段の段のまとめにする（2文で切り詰める）
- 差し戻しを受けてやり直した段は、同じ `段 n/N` をもう一度返す。並列の段も段の番号だけで表し、どの委譲先が返したかは書かない
- 上の形でない1行目と、`段`・`止めた` の `N` が宣言した範囲の段の数と違う返却は帯を進めない（下の関門は立つ）

帯の進め方:

- **帯の段と委譲先の段は1つずつ対応させる。** メインは `work_plan` の `delegatedRange` で、委譲先の段1〜`N` に当たる帯の段の範囲を宣言する。
  委譲先の段 `n` は範囲の先頭から `n - 1` 個目の帯の段に当たる。範囲の前後にメインの段（計画・受け入れなど）を置いてよい。
  範囲の中に段のまとまりを置いてよいが、範囲の端をまたぐまとまりは差し戻す
- 計画だけの回までは範囲を宣言しなくてよい。同じ依頼で `N` を受けたあと、範囲の段の数が `N` と違う `work_plan` は差し戻す
- **`段 n/N` が届き、段 `n` に当たる帯の段が今の段の集合に入っていれば、tsukumo がその段を返却の届いた時刻で済ませる**
  （1本道なら `current` を1つ進め、まとまりの中なら `finishedInGroup` に足す。まとまりの最後の段なら `current` を進めて空にする）
- 一足飛びの返却（段 `n` が今の段の集合より先）・もう済んだ段の返却・範囲を宣言していない依頼の返却は帯を動かさない
- 返却では帯を全部済みにしない。最後の段を閉じるのは今までどおり `report` の `workPlanClosing`
- 返却で進んだあとにメインが同じ位置を渡す `work_plan` は「同じ段のまま」で、段のまとめが無くても通り、中間レポートを足さない
  （この判定は返却で進んだ位置を覚えている `WorkPlanReview` が行い、状態を持たない `parseWorkPlan` では行わない）

関門:

- **効く範囲**: 仕事のセッション（`work_plan` が載る）で、同じ依頼にメインの受け付けた段取りがあるときだけ。雑談のセッションの委譲と、
  段取りを渡していない依頼（`work_plan` を呼ばない依頼）の返却では立てない。`delegatedRange` の宣言は条件にしない
- **返却が届いたら印を立て、メインの `work_plan` が受け付けられたら下ろす。** 返却の中身は見ず、届いた事実だけで立てる
  （上の形でない返却・やり直し・`止めた` でも立つ）。返却の数は数えず、続けて届いても `work_plan` 1回で下りる。差し戻された `work_plan` では下りない
- **印が立っているあいだ、メインの作業のツールを拒む。** 通すのは読み取りのツール（`Read`・`Grep`・`Glob`・`ToolSearch`）と
  tsukumo の MCP ツール（`speak`・`work_plan`・`report` など）。委譲先のツールは対象にしない
- 差し戻しの返却を受けて同じ段をやり直させるときは、同じ位置のまま `work_plan` を呼べば下りる
- 印は組み直しでは戻さない

## Beads の欄

**タスクは Beads の組み込みの欄だけから作る。** 写すのは Beads の読み口（`server/**/adapter/`）の1か所で、shared・画面・各機能の core は
一般の形（`TaskSummaryItem`・`DoneTask`）だけを扱う。

- ID（そのまま）・題（`title`）・依存（`blocks` の依存先）
- 状態: `open` → todo・`in_progress` → doing・`deferred` → hold・`closed` → done。ほかの値は生のまま出す
- 作った時刻（`created_at`）・閉じた時刻（`closed_at`）・置き場所（`https://` で始まる `external_ref`）
- `labels`: 字のまま並べるだけで、意味は解釈せず、並べ替え・絞り込み・色分けに使わない
- 本文: `description`・`acceptance_criteria`・`notes` を Beads の欄の順に、tsukumo が決めた見出しで並べる

読まないもの: 担当（`assignee`）、スキルが足した独自の状態・ラベルの意味、本文の節の書式（`## やること` の段など）、ID の書き換え。

## してよいこと

- 口を呼ぶ: メインが `work_plan` で段を進め、`report` で結果と段の閉じ方を渡し、文脈を空にして次の依頼を送りたいときは `clear_and_send` を呼ぶ
- 委譲先に、上の「委譲の返却」の1行目を返させる。委譲中の段はその返却で tsukumo が進め、メインの `work_plan` は並びと `delegatedRange` を渡す。
  返させないワークフローでは、段取りを渡した依頼なら返却のたびに関門が立つので、メインが `work_plan` で段を進める
- Beads の組み込みの欄に書く（題・本文・依存・状態など）

tsukumo が読まないもの: 委譲の返却の2行目より後ろ、委譲先の `SendMessage` の合図、スキルの道具（着手の印・検証の見張り）、
課題の本文の書式、委譲の依頼文、ファイルの置き場。ワークフローが段を帯に出したければ、メインにこの口を呼ばせる。

## 合わせ方

独自のワークフローが合わせる相手はこの節で、`tsukumo-plugins` のものも同じ立場。ワークフローの置き場は
`sinnlosses/tsukumo-plugins` で、tsukumo はそれをコミット単位で固定して取り込む（経緯と決めたことは ADR 0024）。
素の Claude Code では利用者の手元のワークフローを使い、tsukumo の中では取り込んだものを使う。
