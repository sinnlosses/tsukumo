# ワークフローの契約

最終更新: 2026-10-15。ステータス: **正典**。

責務: tsukumo がワークフロー（タスクを段に分けて送り出す手順）に対して定める契約 — 受ける口の名前と引数の意味、
委譲の返却の書式と委譲ゲート、読む Beads の欄、ワークフローが持つ設定コマンド、並びに置くスキルの契約、ワークフローがしてよいことと tsukumo が読まないもの — を1か所に持つ。
読む時: 独自のワークフローを tsukumo に当てるとき、`tsukumo-plugins` のワークフローを直すとき、口の引数や Beads アダプタ・設定コマンドを変えるとき、並びに置くスキルを書くとき。
直す時: 口の引数・委譲の返却の書式と帯の進め方・委譲ゲート・Beads の読み取る欄・設定コマンドの形・スキルの契約・読まないものを変えたとき。判断の経緯は
`docs/architecture/adr/0024-no-skill-dependency.md`（並びの話は `docs/architecture/adr/0030-workflow-as-skill-sequence.md`）、帯・中間レポートの描き方と差し戻しは `docs/architecture/display.md`「段取り」が持つ。

## 契約とは何か

**契約は、タスクに段があり、並列に走る部分があり、それがパイプラインのように流れることを受ける口。** tsukumo が定めるのは
この口と、委譲の返却の1行目（移行後は `phase_result`）と、読む Beads の欄と、ワークフローが持つ設定コマンドと、並びに置くスキルの契約だけで、ワークフローの手順・道具・それ以外の書式は定めない。

契約を満たすワークフローは、`tsukumo-plugins` のものも利用者独自のものも同じ立場で tsukumo に当てられる。
`tsukumo-plugins` のものは契約に型の合う1つの例で、tsukumo の一部ではない。core は契約だけを見る。

## 口

口は MCP ツール `work_plan` と `report` と `clear_and_send`、委譲先が呼ぶ `phase_result`（下の「スキルの契約」）。意味はツールの説明（`src/server/session-driver/core/work-plan-tool.ts`・
`src/server/report/core/report-tool.ts`・`src/server/session-driver/core/clear-and-send.ts`・`src/server/session-driver/core/phase-result-tool.ts`）とシステムプロンプトの「段取り（tsukumo）」の節がモデルに教える。

`work_plan`（段取り。毎回段の並びごと渡す）:

| 引数              | 意味                                                                                                                                                                                                                          |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `phases`          | 段の並び（1つ以上）。要素は段の名前か、同時に走る段の名前の配列（段のまとまり。2つ以上・重ならない）。段の番号は並びを平らにした読み順                                                                                        |
| `current`         | 今の要素の位置（0始まり）。全部済んだら要素の数。`current` が要素の数に等しい `work_plan` の呼び出しは差し戻す。全部済みにするのは `report` の `workPlanClosing` だけ                                                         |
| `finishedInGroup` | `current` が段のまとまりを指すとき、その中で済んだ段の名前。まとまりの最後の段を済ませる呼び出しでは `current` を進めて空にする                                                                                               |
| `phaseSummary`    | 終えた段でしたこと・分かったことを1〜2文で。済んだ段があり全部は済んでいない呼び出しで必須。ただし `段 n/N` の返却で進んだ位置を同じまま渡す呼び出しでは省ける（下の「委譲の返却」。`phase_result` で進んだ位置では省けない） |
| `delegatedRange`  | 委譲先の段の範囲。`first`（委譲先の段1に当たる位置。平らにした並びで0始まり）と `count`（段の数）。`count` を省くと `pending`（段の数が未定）。委譲しないときは省く。下の「委譲の返却」                                       |
| `skippedPhases`   | 済んだ段のうち、飛ばした段の名前の配列（下の「スキルの契約」の「飛ばした段の印の決まり」）。`phases` の名前に含まれ、その呼び出しで済んでいる段だけ。毎回の呼び出しで、メインが飛ばした段をすべて渡す。飛ばさなかったら省く   |

段は1つずつ進める（平らにした並びで済んだ段を1回で2つ以上増やす呼び出しは差し戻される。飛ばした段も済んだ段に数える）。並列にできるかを決めるのは渡す側で、
tsukumo は推し量らない。
受け付けた呼び出しの戻り値は `ok` の次の行に、帯の今の段（「3/6 段の名前」。`delegatedRange` があれば「本 2/3 段の名前」「後 1/3 段の名前」のように群の名と群の中の番号）を返す。

`report`（ターンの結果）のうち契約に当たる欄:

| 引数              | 意味                                                                                                                                                                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task`            | タスクの作業のレポートのときだけ。`id`（Beads の ID）・`name`（作業の名前）・`outcome`（`finished` 終えた／`stopped` 止めた／`awaiting-answer` 利用者の答え待ち）                                                                                                                                         |
| `workPlanClosing` | 段の閉じ方。`work_plan` を渡した依頼では必須。`finished`（最後の段にいるときに渡すと tsukumo が帯を全部済みにする）／`stopped`（止まった段が「今」のまま残る）                                                                                                                                            |
| `figure`          | 必須。レポートの図1つ（`image`・`mermaid`・`graph`・`svg`・`beforeAfter`・`chart`・`stats`・`dimension` の塊）か、`{ kind: "none", reason }`（`short-answer`／`no-shape`／`single-value`／`no-material`）。理由が本文と合わないと差し戻す（`docs/architecture/display.md`「出力の分離（セリフと詳細）」） |

`task.outcome` は目録の1行の終わり方で、帯は閉じない。どこへ送ったかは tsukumo の関心にしない。
`checks` に `ng` の行がある `report` の `finished` は差し戻す（`docs/architecture/display.md`「出力の分離（セリフと詳細）」）。

`clear_and_send`（文脈を空にして次の依頼を送る。仕事のときだけ載る）:

| 引数   | 意味                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------- |
| `text` | 文脈を空にしたあとに最初の依頼として送る文面。呼んだ時点では何も送らず、tsukumo が文面だけを預かる |

呼んだターンが成功で終わると、tsukumo が `/clear` → `text` の順に続けて積む（`/clear` の完了は待たない）。
2つとも利用者の依頼と同じく列に出る。呼ばれたら送るだけで、いつ呼ぶかはワークフローが決める。
呼んだら `report` を渡してターンを終える。預かりは1つで、2回呼ぶと後のほうに置き換わる。
次のときは何も送らず、預かりを捨てる（画面にも知らせない）: ターンが中断・失敗で終わった・呼んだあとに利用者が
依頼か脇の話を送った・ターンの終わりに答え待ちが残っている・セッションが終わった。

## 委譲の返却

**委譲先が `SubagentHandback` で返す報告の1行目を、tsukumo が読んで帯を進める。** 書式の正典はこの節で、ワークフローの依頼文は
この節を参照し、書式を言い直さない。経緯と採らなかった案は `docs/architecture/adr/0024-no-skill-dependency.md`「2026-10-10 の改訂」。

**この1行目は移行中の形で、構造化した返却（MCP ツール `phase_result`。下の「スキルの契約」）に置き換える。**
ワークフローが移り終えるまでは両方を読む。委譲先が前の返却のあと `phase_result` を呼んでいれば、
その返却の1行目は読まない（帯は `phase_result` で動いている）。ワークフローが移り終えたら、この表と `計画 0/N` の形を消す。
「呼んでいれば」は委譲先ごとに見る。委譲先のメッセージの `parent_tool_use_id` で `phase_result` の呼び出しと返却を対にし、形の合う呼び出しのあとの最初の返却1件だけを読まない。
ほかの委譲先の返却と、その次の返却は今までどおり読む。読まない返却でも委譲ゲートは立ち、注記は「委譲先は `phase_result` で結果を返したので、返却の1行目は読んでいない。」と言う。
帯の進め方のうち「返却の届いた時刻」「`段 n/N` が届き」は、`phase_result` では受け付けた呼び出しの時刻と引数に読み替える。委譲ゲートはどちらでも `SubagentHandback` の返却で立てる。

返却の1行目（2行目より後ろは tsukumo は読まない。組み直しでは、仕掛けが足す前置き・注記の行と空の行を除き、字下げを外した最初の行を1行目とし、
その1行だけが形に合うかを見る）:

| 1行目                  | 意味                                                        | 帯                                    |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------- |
| `計画 0/N \| <要約>`   | 計画だけの回。段に数えず、委譲先の段の数が `N` だと知らせる | 進めない                              |
| `段 n/N \| <要約>`     | 委譲先の段 `n` を済ませた（`1 ≤ n ≤ N`）                    | 段 `n` に当たる帯の段を済ませる       |
| `止めた n/N \| <理由>` | 段 `n` の途中で止めた                                       | 進めない（段 `n` が「今」のまま残る） |

- `<要約>` は読み手から見た変化を1〜2文で書く。tsukumo はこれを済ませた段の段のまとめにする（2文で切り詰める）
- 差し戻しを受けてやり直した段は、同じ `段 n/N` をもう一度返す。並列の段も段の番号だけで表し、どの委譲先が返したかは書かない
- 上の形でない1行目と、`段`・`止めた` の `N` が宣言した範囲の段の数と違う返却は帯を進めない（下の委譲ゲートは立つ）

帯の進め方:

- **帯の段と委譲先の段は1つずつ対応させる。** メインは `work_plan` の `delegatedRange` で、委譲先の段1〜`N` に当たる帯の段の範囲を宣言する。
  **帯の段は、範囲の前（前）・範囲（本）・範囲の後ろ（後）の3つの群に分かれ、群ごとに1から数える。** 群は `delegatedRange` の位置だけで決まり、
  ほかの引数は持たない。本の段は帯でも委譲先の段と同じ番号（範囲の先頭が 1、段の数は `N`）で、前・後の段（計画・受け入れ・振り返り・送り出しなど）は
  「前 1/1」「後 2/3」のように群の名を付けて数える。範囲の無い依頼は並び全体が1つの群で、群の名を付けずに通し番号で数える。
  範囲の前後にメインの段を置いてよい。範囲の中に段のまとまりを置いてよいが、範囲の端をまたぐまとまりは差し戻す
- 計画を委譲先に頼む最初の呼び出しは `delegatedRange` を `{ first }` だけで渡す（`pending`。`N` が未定のため）。
  そのあいだ前の段だけが番号を持ち、範囲の先頭から後ろの段は番号を持たず（右肩に位置を出さない）、範囲の先頭の丸が「…」になり、委譲先の返却では動かない。
  同じ依頼で形の読める返却（`計画 0/N`・`段 n/N`・`止めた n/N`）を受けたあと、範囲の無い・`pending` の `work_plan` と、範囲の段の数が `N` と違う `work_plan` は差し戻す。
  範囲を宣言しない依頼（返却を受けない委譲）は今までどおり通る
- セリフが委譲先の段を番号で言うときは、その番号を `speak` の任意の引数 `phase` で申告する。範囲があるあいだ、`phase` が 1〜`N` の外なら差し戻す。
  セリフ・レポート・`phaseSummary` の本文の段の番号は読まず、`phase` を省いた `speak` は検査しない。
  セリフで番号を言うのは本の段だけで、前・後の段は名前で言う（帯が「後 1/3」と出しても、セリフの「段1」は本の段1を指す）
- **`段 n/N` が届き、段 `n` に当たる帯の段が今の段の集合に入っていれば、tsukumo がその段を返却の届いた時刻で済ませる**
  （1本道なら `current` を1つ進め、まとまりの中なら `finishedInGroup` に足す。まとまりの最後の段なら `current` を進めて空にする）
- 一足飛びの返却（段 `n` が今の段の集合より先）・もう済んだ段の返却・範囲を宣言していない（`pending` を含む）依頼の返却は帯を動かさない
- 返却では帯を全部済みにしない。最後の段を閉じるのは今までどおり `report` の `workPlanClosing`
- `段 n/N` の返却で進んだあとにメインが同じ位置を渡す `work_plan` は「同じ段のまま」で、段のまとめが無くても通り、中間レポートを足さない（`phase_result` で進んだ位置は下の「スキルの契約」）
  （この判定は返却で進んだ位置を覚えている `WorkPlanReview` が行い、状態を持たない `parseWorkPlan` では行わない）

委譲ゲート:

- **効く範囲**: 仕事のセッション（`work_plan` が載る）で、同じ依頼にメインの受け付けた段取りがあるときだけ。雑談のセッションの委譲と、
  段取りを渡していない依頼（`work_plan` を呼ばない依頼）の返却では立てない。`delegatedRange` の宣言は条件にしない
- **返却が届いたら印を立て、メインの `work_plan` が受け付けられたら下ろす。** 返却の中身は見ず、届いた事実だけで立てる
  （上の形でない返却・やり直し・`止めた` でも立つ）。返却の数は数えず、続けて届いても `work_plan` 1回で下りる。差し戻された `work_plan` では下りない
- **印が立っているあいだ、メインの作業のツールを拒む。** 通すのは読み取りのツール（`Read`・`Grep`・`Glob`・`ToolSearch`）と
  tsukumo の MCP ツール（`speak`・`work_plan`・`report` など）。委譲先のツールは対象にしない。
  拒否文の末尾に、返却で進んだあとの帯の位置（`work_plan` の戻り値と同じ文）を足す
- **返却を運ぶメインの入力に、返却の本文とは別の tsukumo の注記を1回だけ添える。** 注記は返却ごとに済んだ帯の段の位置と名前を言い
  （範囲の無い依頼・`計画`・`止めた`・形の読めない返却・帯を動かさない返却では帯が動いていないことを言う）、末尾に次の帯の段と
  群ごとの数え方と、本の番号が委譲先の段と同じであることと、セリフで番号を言うのは本の段だけなこと（`work_plan` の戻り値と同じ文）を付ける。返却が続けて届けば、まだ添えていない返却の文を重ねる。
  受け付けた `work_plan`・次の依頼で溜めた注記を捨て、組み直しでは足さない。
  口は `UserPromptSubmit` のフックで、返却の入力（`<agent-message` で始まる）はメインが手すきでもターンの途中でもここを1回通る
- 印と注記の元は、委譲先の `SubagentHandback` の呼び出しから読む返却で、委譲先のメッセージのうち返却だけを `WorkPlanReview` に通す。
  委譲先が `SubagentHandback` で返すのは、許可モードが `auto` で auto に対応するモデルのときだけで、それ以外の返却（`<task-notification>`）では印も注記も立たない
- 差し戻しの返却を受けて同じ段をやり直させるときは、同じ位置のまま `work_plan` を呼べば下りる
- 印は組み直しでは戻さない
- 許可の口は `PreToolUse` のフック（許可モードによらず毎回呼ばれ、`agent_id` でサブエージェントの中を見分けられる）。疑似セッションは `work_plan` の判定もしないので、委譲ゲートも効かない

## Beads の欄

**タスクは Beads の組み込みの欄と、metadata の2つの属性（`difficulty`・`loopable`）だけから作る。** 写すのは Beads アダプタ（`server/**/adapter/`）の1か所で、shared・画面・各機能の core は
一般の形（`TaskSummaryItem`・`DoneTask`）だけを扱う。

- ID（そのまま）・題（`title`）・依存（`blocks` の依存先）
- 状態: `open` → todo・`in_progress` → doing・`deferred` → hold・`closed` → done。ほかの値は生のまま出す
- 作った時刻（`created_at`）・閉じた時刻（`closed_at`）・置き場所（`https://` で始まる `external_ref`）
- metadata の `difficulty`（`haiku`・`sonnet`・`opus`）・`loopable`（`Y`・`N`）: 板に出すだけで、おすすめの選びには使わない。
  無い・表に無い値は「無い」として読み、label からは読まない
- `labels`: 字のまま並べるだけで、意味は解釈せず、並べ替え・絞り込み・色分けに使わない。属性とは別の欄
- 本文: `description`・`acceptance_criteria`・`notes` を Beads の欄の順に、tsukumo が決めた見出しで並べる

読まないもの: 担当（`assignee`）、スキルが足した独自の状態・ラベルの意味、本文の節の書式（`## やること` の段など）、ID の書き換え。

## 設定コマンド

**ワークフローは、設定の欄を `tw config --schema` で返し、`tw config set` で書かせる。**
任意の口ではなく契約の義務で、歯車の設定の「ワークフロー」の面はこの2つだけで描いて書く。経緯は
`docs/architecture/adr/0024-no-skill-dependency.md`・`docs/architecture/adr/0025-no-project-settings.md` の「2026-10-14 の改訂」と
`docs/architecture/adr/0030-workflow-as-skill-sequence.md`。

欄の形は2つの版がある。**目指す形は `schema: 2`（並び `steps` の1欄）で、`schema: 1`（流れ `flow` と4つのパーツの枠 `parts.<枠>`）は移行中の形。**
1回の `--schema` が返す JSON の版は1つで、2つの版の並存は版を選ぶ引数 `--version` で表す。
移行のあいだ、引数なしの `tw config --schema` は schema 1 を返し続け、`tw config --schema --version 2` が schema 2 を返す。
tsukumo は先に `--version 2` を打ち、失敗したら（`--version` を知らない古い `tw`）引数なしに落とし、返った版の欄を描く。
ワークフローが schema 2 に移り終えたら、ワークフローは引数なしで schema 2 を返して `--version` と schema 1 を外し、
tsukumo は `--version 2` の打ち分けと schema 1 の描画を外して、この段落と下の schema 1 の表を消す。

ワークフローが持つもの（どちらも作業先の作業ツリーで打つ）:

| コマンド                            | 返すもの                                                                                                                                                                                                             |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tw config --schema`                | 1行の JSON。終了コード0。schema 1 は `{"schema": 1, "default_word": <既定の語>, "none_word": <外す語>, "keys": [...]}`、schema 2 は `{"schema": 2, "keys": [...]}`。`keys` は画面に出す順の欄。移行中は schema 1     |
| `tw config --schema --version <版>` | 移行中だけの形。`<版>` の JSON を返す（`2` で schema 2）。知らない版は終了コード2（stderr に理由）                                                                                                                   |
| `tw config set <キー> <値>`         | 検査してから設定ファイルに書き、`SET\t<キー>\t<値>`（終了コード0）。知らないキー・語彙の外の値は終了コード2（stderr に理由、ファイルは変えない）。設定ファイルが無ければ `MISSING`（6）、読めなければ `INVALID`（3） |
| `tw config`                         | 1行目 `CONFIG\t<設定ファイルの作業ツリーからの相対パス>`、続けて `<キー>\t<解けた値>\t<config\|default>` の行。`flow`・`parts.<枠>`・`steps` の今の値はここから読む。設定ファイルが無ければ `MISSING`（6）           |

`keys` の各欄（`schema: 2`）:

| 欄                     | 意味                                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `key`                  | `set` に渡すキー。並びは `steps`                                                                                                                                             |
| `label`・`description` | 画面に出す名前と説明                                                                                                                                                         |
| `kind`                 | `choice`（schema 1 と同じ）か `steps`（`values` の中から1つ以上を選んで並べる）                                                                                              |
| `default`              | 書いていないときの値。`steps` ではスキルの全名の配列で、既定の並びはワークフローが決める                                                                                     |
| `values`（`steps`）    | 候補の `{ value, label, description }` の配列。`value` はスキルの全名（`<プラグイン>:<名前>` か `<名前>`）で、候補は契約を満たすと宣言したスキルだけ（下の「スキルの契約」） |

`steps` の欄の決まり:

- **空にできない。** 1つ以上が契約の縛りで、欄では表さない。tsukumo は最後の1つを外す操作を出さず、`tw config set` は空の並びを終了コード2で断る
- 同じスキルを2度並べない（`set` が終了コード2で断る）。`values` にも今の値にも無い名前の `set` も断る
- 値の文字の形は1行の JSON の文字列の配列（例: `["task-workflow:implement","task-workflow:ship"]`）。`tw config set steps '<配列>'` に渡し、
  `tw config` の値の列にも同じ形で出す。`.tw/config.toml` では最上位の文字列の配列 `steps = ["…", "…"]` で、並びの順がそのまま実行の順
- tsukumo は `values` に無い名前が今の値にあっても消さずに並べる（スキルを外したあとの並びを失わない）

`keys` の各欄（`schema: 1`。移行中の形）:

| 欄                     | 意味                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| `key`                  | `flow` か `parts.<枠>`。`set` に渡すキー                                                        |
| `label`・`description` | 画面に出す名前と説明                                                                            |
| `kind`                 | `choice`（`values` の `{ value, label, description }` から選ぶ）か `part`（パーツの全名を書く） |
| `default`              | 書いていないときの値                                                                            |
| `candidates`（`part`） | 候補の出どころ。`agent`（エージェントの一覧）か `skill`（スキルの一覧）。候補そのものは返さない |
| `allow_none`（`part`） | `none_word` を選べるか                                                                          |

`schema` は欄を消す・意味を変えるときだけ上がる。tsukumo は先に `--version 2` を打って `schema` が 2 の形（`choice`・`steps`）を描き、
失敗したら引数なしの `--schema` に落として `schema` が 1 の形（`choice`・`part`）を描く。

tsukumo がすること:

- **欄は schema だけから描く。** 欄の名前・語彙・既定・パーツやスキルの名前を tsukumo は持たない。`part` の選択肢は `default_word`、
  `allow_none` なら `none_word`、続けて SDK の `init` の `agents`（`agent`）か `skills`（`skill`）の名前を並べ、今の値が一覧に無ければ足して失わない。
  `steps` の候補は `values` だけから並べ（SDK の一覧も SKILL.md も読まない）、足す・消す・並べ替えた結果の並び全体を1回の `set` で書く
- **書くのは `tw config set` だけ。** 設定ファイル（`.tw/config.toml`）を直に読み書きしない
- **呼ぶ `tw`**: 取り込んだワークフローを載せるとき（`mount`・`partial`）と疑似セッションは取り込みの `bin/tw`、
  利用者がリンクで入れていて載せないとき（`user-installed`）は PATH の `tw`。いま走るワークフローと同じ持ち主の `tw` を呼ぶ
- **どのリポジトリの値かを言う。** 面の見出しの下に作業ツリー名と設定ファイルの絶対パスを出す（歯車のほかの値は利用者の好みで、リポジトリに属さない）
- **使えないときは欄を出さず、何が無いかを言う**（`docs/requirements.md` 2.3）。ナビの項目は残す:

| 状態                                                          | 面に出すこと                       |
| ------------------------------------------------------------- | ---------------------------------- |
| `tw` が起動できない                                           | `tw` が見つからない（探した場所）  |
| `--schema` が失敗する・JSON でない・`schema` が描ける版でない | `tw` が設定コマンドを持たない      |
| `tw config` が `MISSING`                                      | このリポジトリに設定ファイルが無い |
| `tw config` がそのほかで失敗する（`INVALID`・git の外など）   | 読めない（stderr の1行目）         |

## スキルの契約

**ワークフローは、契約を満たすスキルの並び（schema 2 の `steps`）。** 並びの要素はスキルだけで、エージェントはスキルが中で使う道具として並びに出さない。
並びは線形で、近道・`loopable`・メインで行うのような分岐は並びで表さず、各スキルが「飛ばした」と返す。並びの中の並列は持たない（段の中の並列はスキルの中で行う）。
並びを読んで順に呼ぶのはワークフローのオーケストレーターで、tsukumo は並びを読まない。帯は今までどおりメインの `work_plan` で受ける。
tsukumo が並びに課す縛りは「1つ以上」だけで、送り出しのスキルも並びの1つとして外せる。
この節は schema 2 の契約で、`phase_result` と `work_plan` の `skippedPhases` は入っており、飛ばした段の帯での描き方は `docs/architecture/display.md`「段取り」に入っている（schema 2 を描く面はまだ入っていない）。経緯と採らなかった案は `docs/architecture/adr/0030-workflow-as-skill-sequence.md`。

**印（候補になる宣言）**: 並びに置けるスキルは、SKILL.md の frontmatter の `metadata` に `workflow-step: "true"` を持つものだけ。
`metadata` は Agent Skills の書式で、書式に無い属性を文字から文字への対応で置く欄。印を拾うのは `tw config --schema`（移行中は `--version 2`）で、tsukumo は frontmatter を読まない。

- `tw` が拾う範囲: 作業ツリーの `.claude/skills/`・利用者の `~/.claude/skills/`（リンクで入れたものを含む）・`tw` と同じチェックアウトの plugin の `skills/`。ほかの plugin のスキルは拾わない
- 拾ったスキルは `steps` の `values` の1つになる。`value` は Skill ツールで呼ぶ全名（plugin のスキルは `<プラグイン>:<名前>`）、`label` は frontmatter の `name`、`description` は frontmatter の `description`

**受け取るもの**:

- 呼び出しの引数のタスクの ID 1つ。それ以外を会話の文脈から受け取らない
- 前段の結果は Beads の欄から読む。どの欄・節に書くかはワークフローが決め、tsukumo は上の「Beads の欄」のほかは読まない。
  止まった段から再開するための位置も、ワークフローが Beads に残す

**返すもの**: 段の結果を3つの語の1つで返す。結果の中身（何をしたか・何が分かったか）は Beads に書き、返す値には入れない。

| 結果       | 意味                                                    | 並びと帯                                                                                                                                            |
| ---------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `finished` | 段を済ませた                                            | 次のスキルへ進む。帯の段を済ませる                                                                                                                  |
| `skipped`  | 段を飛ばした（近道・`loopable` などでこの段が要らない） | 次のスキルへ進む。帯の段を飛ばした段として済ませる。どちらの口から返しても帯は同じになる（描き方は `docs/architecture/display.md`「段取り」が持つ） |
| `stopped`  | 段の途中で止めた。理由を添える                          | 並び全体を止め、後のスキルを呼ばない。帯は止まった段が「今」のまま残る。同じタスクを呼び直すと止まった段から再開する                                |

返す口は、段がどこで走るかで2つある。どちらも許す:

- **メインで走る段**: `finished`・`skipped` は `work_plan` で次の位置へ進め、`phaseSummary` に段のまとめ（`skipped` なら飛ばしたわけ）を書く。
  `skipped` は、その段の名前を `skippedPhases` に入れる。`stopped` は `report` の `workPlanClosing` に `stopped` を渡す
- **委譲先で走る段**: 委譲先が `SubagentHandback` の前に `phase_result` を呼ぶ。上の「委譲の返却」の1行目を置き換える口

飛ばした段の印の決まり（どちらの口でも、印の付いた段は帯で同じに描く）:

- **メインで走る段の `skipped`**: `work_plan` の `skippedPhases` に入れた段に印が付く。`skippedPhases` の名前は `phases` に含まれ、その呼び出しで済んでいる段
  （`current` より前の要素の段か `finishedInGroup` の段）でなければ差し戻す。毎回の呼び出しで、メインが飛ばした段をすべて渡す。
  前に受け付けた呼び出しで印なしに済んでいた段を新しく入れる呼び出しは差し戻す（済ませた段をあとから飛ばした段に変えない）。
  前に受け付けた呼び出しで `skippedPhases` に入れた段を、その呼び出しでもまだ済んでいるのに外した呼び出しも差し戻す（飛ばした段をあとから済ませた段に変えない。
  黙って印を消すことも残すこともしない）。その段が済んでいなくなった（位置を戻した・並びから消えた）呼び出しでは、印も消える。
  どちらの判定も受け付けた呼び出しを覚えている `WorkPlanReview` が行う。印は段の名前で持つので、同じ名前の段は見分けない
- **委譲先で走る段の `skipped`**: 受け付けた `phase_result` が段を済ませるときに印が付く。メインはその段を `skippedPhases` に入れなくてよく（入れてもよい）、
  入れなくても印は消えない。`phase_result` で付いた印は `WorkPlanReview` が覚え、同じ依頼の段取りのあいだ、その段が済んでいるかぎり残す
  （受け付けた `work_plan` の記録に足す）。組み直しでは戻らない（`phase_result` の呼び出しは委譲先の transcript にあり、組み直しはメインの transcript だけを読む）
- **範囲の外の段・済んだ段の `skipped`**: `phase_result` が帯を動かさない条件（範囲が無い・`pending`・一足飛び・済んだ段・`count` の違い）に当たれば、印も付けない。
  `work_plan` では、済んでいない段の名前と、印なしに済んでいた段の名前は差し戻す（上の項）
- `skippedPhases` も段を1つずつ進める決まりに従う。飛ばした段も済んだ段に数え、`phaseSummary` に飛ばしたわけを書く

`phase_result`（構造化した返却。委譲先が段ごとに1回呼ぶ）:

| 引数      | 意味                                                                                                 |
| --------- | ---------------------------------------------------------------------------------------------------- |
| `phase`   | 結果を返す委譲先の段の番号（1始まり）。`delegatedRange` の範囲の中の番号で、`段 n/N` の `n` に当たる |
| `count`   | 委譲先の段の数。`段 n/N` の `N` に当たる                                                             |
| `outcome` | `finished`・`skipped`・`stopped`（上の表）                                                           |
| `reason`  | 止めた理由を1〜2文で。`outcome` が `stopped` のときだけ渡す                                          |

- 引数は zod で検証し、形が合わなければ差し戻す（`phase` が 1〜`count` の外、`reason` の有無が `outcome` と合わない・空白だけの `reason`）。
  メインの呼び出しは `PreToolUse` のフックが `agent_id` の無い呼び出しとして拒む（メインは `work_plan` で進める。SDK の handler は呼び手を知らないので、handler では見分けない）
- 受け付けた呼び出しは、上の「帯の進め方」の `段 n/N` と同じ条件で帯を動かす。`finished`・`skipped` は段 `phase` に当たる帯の段を済ませ（`skipped` は飛ばした段の印を付ける。上の「飛ばした段の印の決まり」）、`stopped` は動かさない。
  条件に合わない呼び出し（範囲が無い・`pending`・一足飛び・済んだ段・`count` が範囲の段の数と違う）も差し戻さず、帯を動かさない。
  受け付けた呼び出しの `count` は、`段 n/N` の `N` と同じく「返却で知らされた段の数」として、後の `work_plan` の範囲の差し戻しに使う
- 帯を動かす判定は handler が行い、帯を動かしたときだけ、結果を読んだ形の返却のイベントを1件流す（画面の帯はそれで動く）
- 戻り値は `work_plan` と同じく `ok` の次の行に帯の今の段（「帯の今の段は 本 2/2 段の名前。…」）。帯を動かさなかったときは、その行の頭に「帯は動いていない。」を付ける
- `phase_result` は要約を持たない。返却で済んだ段のまとめは、返却のあとメインが同じ位置で呼ぶ `work_plan` の `phaseSummary` に書く（`段 n/N` の返却のときの「省ける」は `phase_result` では使わない）。
  まとめの空のまま返却で済んだ段は**まとめ待ちの段**になり、次に受け付けた `work_plan` が `phaseSummary` を持ち、その段がまだ済んでいれば、そのまとめをその段の中間レポートにする。
  まとめ待ちの段は1つだけ覚えるので、メインの `work_plan` の前に `phase_result` が2件続けて段を済ませると（並列の段）、先の段はまとめ待ちから外れ、中間レポートが出ない
- 計画だけの回は `phase_result` を呼ばない（`計画 0/N` に当たる形は無い）。段の数はメインが Beads から読んで `delegatedRange` の `count` に渡す
- 委譲ゲートは今までどおり `SubagentHandback` の返却で立つ。`phase_result` は許可モードによらず呼べるので、`<task-notification>` で返る委譲でも帯は進む（委譲ゲートは立たない）

## してよいこと

- 口を呼ぶ: メインが `work_plan` で段を進め、`report` で結果と段の閉じ方を渡し、文脈を空にして次の依頼を送りたいときは `clear_and_send` を呼ぶ
- 委譲先に、上の「委譲の返却」の1行目を返させるか、`phase_result` を呼ばせる（上の「スキルの契約」。移り終えたら `phase_result` だけ）。委譲中の段はその返却で tsukumo が進め、メインの `work_plan` は並びと `delegatedRange` を渡す。
  返させないワークフローでは、段取りを渡した依頼なら返却のたびに委譲ゲートが立つので、メインが `work_plan` で段を進める
- Beads の組み込みの欄に書く（題・本文・依存・状態など）

tsukumo が読まないもの: 委譲の返却の2行目より後ろ、委譲先の `SendMessage` の合図、スキルの道具（着手の印・検証の見張り）、
課題の本文の書式、委譲の依頼文、ファイルの置き場、ワークフローの設定ファイル（`.tw/config.toml`。見せて書くのは上の「設定コマンド」だけ）。
ワークフローが段を帯に出したければ、メインにこの口を呼ばせる。

## 合わせ方

独自のワークフローが合わせる相手はこの節で、`tsukumo-plugins` のものも同じ立場。ワークフローの置き場は
`sinnlosses/tsukumo-plugins` で、tsukumo はそれをコミット単位で固定して取り込む（経緯と決めたことは ADR 0024）。
素の Claude Code では利用者の手元のワークフローを使い、tsukumo の中では取り込んだものを使う。
独自のワークフローも、上の「設定コマンド」の2つのコマンドを持てば、歯車の設定から流れとパーツ（schema 2 では並び）を選べる。
並びに置くスキルを書くときは、上の「スキルの契約」の印を付け、受け取るもの・返すものを合わせる。

取り込んだワークフローを載せるとき（`mount`・`partial`）は、plugin の `hooks/hooks.json` が `AskUserQuestion` に `tw ask-guard` を当てる。
利用者がスキルとエージェントをリンクで入れていて載せないとき（`user-installed`）は、Claude Code が `PreToolUse` の `AskUserQuestion` に取り込みの `bin/tw ask-guard` を当てる。
どちらか一方だけが効き、二重に拒まない。子が失敗・無出力・読めない出力のときは質問を通す。`report` の `favor` は扱わない。
