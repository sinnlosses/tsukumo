# ワークプラン: 入力・フェーズの進め方・委譲中のフェーズ

戻り: `docs/architecture/display.md`「ワークプラン」

**作業中に「いまどのフェーズにいて、あと何が残っているか」を画面で追えるように、claude からワークプラン（フェーズの並びと
今の位置）を MCP ツール `work_plan` で受け取る**（用語は `docs/glossary.md`
「ワークプラン」「work_plan ツール」）。依頼の手順はツールの実行を1回ずつ並べるだけで、`report` は渡したときにしか出ないので、
作業中のフェーズはそれらでは見えない。Claude Code の TodoWrite を
拾う案とツールの手順からフェーズを推し量る案は採らない（tsukumo から縛れない・推測になる）。

- **入力は `{ phases, current, finishedInGroup, phaseSummary }` で、毎回フェーズの並びごと渡す**（引数の意味は
  `docs/architecture/workflow-contract/port-and-return.md`「ツール」。`phases` を省く呼び出しは作らない）。
  並列のフェーズは「同時に走るフェーズは、並列のフェーズで受ける」、`phaseSummary`（フェーズのまとめ）は「フェーズが移ったときの
  中間レポート」。空白だけの名前は不可。形の崩れ・`current` が要素の数を超えた呼び出し・フェーズのまとめの足りない
  呼び出しは差し戻す。メインの呼び出しだけを受け、サブエージェントの呼び出しは捨てる。
  戻り値は `"ok"` で、ターンは閉じない。**仕事のときだけ載る**
- **フェーズは1つずつ進める**。同じ依頼の中で同じフェーズの並びのまま、済んだフェーズ（並びを平らにして数える）を
  1回で2つ以上増やした呼び出しは差し戻す（`src/server/work-plan/core/work-plan-review.ts`）。飛ばしたフェーズは
  フェーズのまとめを持たず、中間レポートがそのフェーズだけ抜けるため。覚えるのは同じ依頼で最後に受け付けたワークプランだけで、
  依頼で忘れる。委譲中に返却で進めたフェーズも同じ決まりで数え、一足飛びの判定は返却で進んだ位置を起点にする
  （「委譲中のフェーズは、委譲先の返却で tsukumo が進める」）。差し戻した呼び出しは結果まで預かって捨てる
  （transcript から組み直すときも同じ）
- **同時に走るフェーズは、並列のフェーズで受ける**（用語は `docs/glossary.md`「並列のフェーズ」）。並列にできるかを決めるのは
  ワークプランを渡す側で、tsukumo はフェーズの並列を推し量らず、受けて描くだけ。`work_plan` の入力の形はスキルの書式（`## やること`・`tw`）に依存しない
  （`phase_result` の引数は契約の形で、スキルの書式ではない）
  - **形**: 並列のフェーズは `phases` の1要素で、2つ以上のフェーズの名前を重ならずに並べる。フェーズの番号は並びを平らにした読み順で振る
    （`[A, [B, C], D]` なら B が 2、C が 3）。位置は1つの数で言う
  - **今のフェーズの集合**: `current` の要素がフェーズならその1つ、並列のフェーズならその中で `finishedInGroup` に無いフェーズのすべて。
    `finishedInGroup` は並列のフェーズを指していないときは空で、並列のフェーズの中のフェーズを全部入れることもできない（全部済んだら `current` を進める）
  - **済ませ方**: 並列のフェーズの中のフェーズを1つ済ませるたびに、その名前を `finishedInGroup` に足す。メインは `work_plan` を呼んで足し、
    委譲中は委譲先の `phase_result` を受けた tsukumo が同じ形で足す。並列のフェーズの最後に残ったフェーズを済ませると `current` を1つ進め、
    `finishedInGroup` を空に戻す。委譲先がどの順で返っても、返却のフェーズの番号かメインの呼び出しが済んだフェーズを名指すので、
    後ろの番号から済んでもプログレスバーは戻らず取りこぼさない。どの委譲先が返したかは見ず、済んだ順も推し量らない
  - **一足飛びの判定**は、平らにした並びで済んだフェーズの数で行う（「フェーズは1つずつ進める」）。並列のフェーズに入る呼び出しで、同時に中のフェーズを
    済ませたことにすると2フェーズ増えるので差し戻す
- **フェーズはファイル単位・操作単位で切らず、作業のまとまりで切る**。この粒度は
  ツールと引数の説明で伝える（仕事の append の節「ワークプラン〔tsukumo〕」には重ねない）。委譲中は委譲先のフェーズをプログレスバーのフェーズに
  1つずつ合わせ、その範囲をメインが `work_plan` で渡す（「委譲中のフェーズは、委譲先の返却で tsukumo が進める」）
- **呼ぶ条件は条として書き、差し戻しでは縛らない。** 条は「作業をするターンはフェーズの数にかかわらず呼ぶ。
  作業のまとまりが1つなら1フェーズのワークプランを渡す（カードには `1/1` のように出る）。答えるだけ・1回調べる
  だけの依頼では呼ばない」。機械で縛れるところは機械に寄せた（雑談では
  載らない・0フェーズのワークプランは形の検査が受け付けない）。呼ばなかったことはターンの終わりにしか判定できず、
  そこで差し戻すと着手時に渡すはずのワークプランを後から書かせるだけになる。呼ばなくてもカードと一覧は
  ワークプランの無い表示のままで壊れない
- **委譲中のフェーズは、委譲先の返却で tsukumo が進める**（メインが返却のあとに `work_plan` を呼び忘れても
  プログレスバーのフェーズの時間が実際と離れないように。境界と経緯は `docs/architecture/adr/0024-no-skill-dependency.md`「2026-10-10 の改訂」、
  返却の書式と規則は `docs/architecture/workflow-contract.md`「委譲の返却」、用語は `docs/glossary.md`「委譲の返却」「委譲先のフェーズの範囲」）。
  `phase_result` の引数の形は契約の持ち物で、スキルの依頼文は契約を参照する側なので、受けてもスキルには依存しない
  - **並びと委譲先のフェーズの範囲はメインが `work_plan` で渡す。** 「計画」「受け入れ」をフェーズにするかも渡す側が決め、範囲の前後に置いてよい。
    プログレスバーのフェーズと委譲先のフェーズは1つずつ対応し、**範囲の前（前）・範囲（本）・範囲の後ろ（後）の群ごとに1から数える**（
    受け入れ以降のどこにいるかも数で分かり、委譲先の番号との取り違えが起きないように）。
    本のフェーズは範囲の先頭からの番号と範囲のフェーズの数 `N` で数え、委譲先のフェーズの番号と同じ。前・後のフェーズ〔計画・受け入れ・振り返り・送り出し〕も
    群の中の番号とフェーズの数で数え、「前 1/1」「後 2/3」のように群の名を前に付ける。範囲の無い依頼は群が1つで、群の名を付けない。
    カード・現在の手順・スマホの頭・中間レポートの見出し・時間の表が同じ式を使う。
    群は範囲の位置だけで決め、後の始まりを宣言する欄は持たない（古い記録も同じ規則で読み戻せる）。
  - **プログレスバーは群の先頭の丸の前に群の名を小さく置き、前の群の丸とは線でつながず間を空ける。** 今いる群の名は差し色にする。
    ワークプランの一覧は群ごとの行に群の名を置き、印をプログレスバーと同じ丸の番号（済んだフェーズは ✓）にする。
    並列のフェーズの番号は、先頭と末尾を「–」でつなぐ（「2–3」。名前をつなぐ「・」と見分けるため。並列のフェーズの中のフェーズは平らにした並びで隣り合う）。
  - 計画を頼む最初の呼び出しは `{ first }` だけの範囲（`pending`）で渡し、そのあいだ前のフェーズだけが番号を持つ。
    範囲の先頭の丸が「…」、その後ろの丸が「・」で、`phase_result` はプログレスバーを動かさない。
    `phase_result` を受けたあとの `work_plan` は、範囲のフェーズの数をその `count` で tsukumo が確定する（差し戻さない）。
  - フェーズの数の言い方は2つに分ける。「本 2/3」「後 3/3」のような分数は番号の話で群の中のフェーズだけを数え、
    「5フェーズすべて済み」「5フェーズのうち3フェーズ済み」のような済み具合は全部のフェーズ（範囲の外を含む）で数える（範囲の外が残っていれば「すべて済み」と言わない）。
  - 範囲があるあいだ、`speak` の `phase`（セリフが番号で言う委譲先のフェーズ）が範囲の外なら差し戻す。本文のフェーズの番号は読まない
    （セリフで番号を言うのは本のフェーズだけで、前・後のフェーズは名前で言う。これは案内で、検査は `phase` の値にだけ掛かる）。
    範囲の端をまたぐ並列のフェーズも差し戻す。範囲を宣言していない（`pending` を含む）依頼では返却はプログレスバーを進めない
  - **委譲先の `phase_result` の `finished`・`skipped` が届いたら、tsukumo が `phase` に当たるプログレスバーのフェーズを済ませる**。区切りの時刻は受け付けた呼び出しの時刻。
    フェーズが今のフェーズの集合に入っていなければ（一足飛び・もう済んだフェーズ・差し戻しのやり直し）プログレスバーは動かない。
    `stopped`・範囲の無い依頼・`count` が宣言した範囲のフェーズの数と違う呼び出しもプログレスバーを動かさない。プログレスバーを閉じるのは `report` の `workPlanClosing` だけ
  - **メインの `work_plan` とは二重に進まない。** メインは位置ごと渡すので、`phase_result` で進んだあとに同じ位置を渡す呼び出しは「同じフェーズのまま」。
    メインが並びや位置を組み替えたら、メインの呼び出しがプログレスバーを決める
  - **`phase_result` がプログレスバーのフェーズを済ませたとき、`summary` を渡していれば、その文がフェーズのまとめになる。** 渡していなければフェーズのまとめは空のまま届く。
    そのフェーズはまとめ待ちのフェーズになり、メインが同じ位置で渡す `work_plan` の `phaseSummary`（省けない）がそのフェーズの中間レポートになる。
    `summary` つきで済んだフェーズは、メインの `work_plan` が `phaseSummary` を持たなくても受け付け、持っていても中間レポートに出るのは `summary`（ワークフロースクリプトの走るあいだメインは返却を受けないので、ワークフロースクリプトの中の委譲先が書く）
    （引数とプログレスバーの動かし方は `docs/architecture/workflow-contract.md`「スキルの契約」。飛ばしたフェーズの描き方は次の項）
  - **飛ばしたフェーズは、済んだフェーズと見分けて同じ面で描く**（印の付け方は `docs/architecture/workflow-contract.md`「スキルの契約」の「飛ばしたフェーズの印の決まり」で、
    どちらの経路で付いた印も同じに描く）。飛ばしたフェーズは済んだフェーズの一種で、位置・線・番号・済み具合の数え方は済んだフェーズと同じ。変えるのは印と色だけで、新しい色は足さない
    - **丸**（プログレスバー・スマホの頭の点・一覧の頭のワークプラン）: 「✓」の代わりに「/」を出し、済んだフェーズの差し色の地と字をやめて、地なし・`--rule` の破線の枠・字 `--ink-quiet` にする。丸の寸法と線のつながりは済んだフェーズと同じ。
      読み上げと `title` の接尾は「（済）」の代わりに「（飛ばした）」
    - **狭い画面の「済んだフェーズ · 中間レポート」の一覧**の行と板の頭の印も、飛ばしたフェーズは「✓」の代わりに「/」を `--ink-quiet` で出す
    - **一覧の頭のワークプランの名前**は取り消し線と `--ink-quiet`（プログレスバーの丸は名前を今のフェーズしか出さない）
    - **プログレスバーのフェーズの吹き出し**: 名前の行は「/ フェーズの名前」、状態の行は「飛ばした · 所要 …」、フェーズのまとめ（飛ばしたわけ）は済んだフェーズと同じに出し、「このフェーズの手順へ」は出さない
    - **中間レポートは出す。** `docs/architecture/workflow-contract.md` が飛ばしたフェーズにもフェーズのまとめ（飛ばしたわけ）を必須にしているため、出さないと契約と食い違う。
      タスク見出し行の2行目は「中間レポート　1/3 フェーズの名前　飛ばした　所要 0秒」、畳んだ `<summary>` は「中間レポート: … · 飛ばした · 所要 …」。「中間レポートは所要を必ず出す」は保つ
    - 同じ名前のフェーズは印を見分けない（飛ばしたフェーズを名前で持つため）
  - **委譲ゲート**: 仕事のセッションで、同じ依頼にメインの受け付けたワークプランがあるときだけ効く（雑談の委譲と、`work_plan` を呼ばない依頼の返却では
    立てない。下ろす手段が無い依頼で作業のツールを拒み続けないため。範囲の宣言は条件にしない）。返却かワークフロースクリプト（`Workflow`）の完了の知らせが届いたら印を立て、メインの `work_plan` が受け付けられたら下ろす
    （ワークフロースクリプトの完了は、走り出しの `task_started`（`task_type` が `local_workflow`）の `task_id` と同じ `task_id` の `task_notification` で見分ける。`docs/architecture/workflow-contract/port-and-return.md`「委譲の返却」）。
    印が立っているあいだ、メインの作業のツール（`Bash`・`Edit`・`Write`・`Agent`・`SendMessage`・`TaskStop` など）を拒み、
    読み取りのツール（`Read`・`Grep`・`Glob`・`ToolSearch`）と tsukumo の MCP ツール（`speak`・`work_plan`・`report` など）は通す。
    返却の中身は読まず届いた事実だけで立てるので、`phase_result` を呼ばなかった返却・差し戻しのやり直し・`stopped` の返却でも立ち、
    同じ位置のまま `work_plan` を呼べば下りる。並列のフェーズの返却が続けて届いても `work_plan` 1回で下りる。差し戻された `work_plan` では下りない。
    委譲先のツールは対象にしない。印はセッションを起こし直すと下り、組み直しでは戻さない。
    拒否文の末尾と受け付けた `work_plan` の戻り値は、返却で進んだあとのプログレスバーの位置（今のフェーズ。範囲があれば範囲の中のフェーズだけ番号つき）を返し、
    返却を運ぶメインの入力にも同じ文を土台にした注記を添える（`docs/architecture/workflow-contract.md`「委譲の返却」）。
    プログレスバーを進めるのは `phase_result` で、委譲ゲートは「メインが返却を読み、並びと範囲を確かめてから次のフェーズを送る」ことを保証する保険。
    `phase_result` を呼ばない委譲先でも、ワークプランを渡した依頼なら委譲ゲートがメインに `work_plan` を呼ばせるのでプログレスバーは止まらない
  - **組み直しでは返却で進めたプログレスバーは戻らない。** `phase_result` の呼び出しは委譲先の transcript にあり、組み直しはメインの transcript だけを読むので、
    組み直した会話のプログレスバーはメインの `work_plan` が決める位置になる
  - **委譲先の `SendMessage` の合図はプログレスバーを動かさない**。合図は吹き出しの途中の一言として残し、tsukumo は読まない。
    バックグラウンドタスクの顔ぶれの変化もプログレスバーを動かさない。フェーズの所要の短さで呼び忘れを差し戻す形は、本当に短いフェーズと見分けられないので採らない
  - **防げないこと**: `phase_result` を呼ばない委譲先のフェーズは、メインの `work_plan` でしか進まない（委譲ゲートが呼ばせるが、区切りの時刻はメインが呼んだ時刻になる）。
    `phase_result` の `phase` が実際に済ませたフェーズと違っても、tsukumo は見分けない
