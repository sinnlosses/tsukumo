# 読む時間を減らす物差しと線引き

戻り: `docs/architecture/display.md`「読む時間を減らす物差しと線引き」

**物差しは、レポートを読んで分かるまでの時間が短くなるか。** 短くなるなら、3層（レンダラ /
通す HTML と CSS / 組み立ての規約）のどこに足してもよい。レポートのレイアウトの設計・画像 `img`・
`svg`・`chart`・`compare` もこの物差しで採る。文字を減らすこと自体は
目的ではなく、図・グラフ・画像のほうが速く分かる内容をそれで描く。規約を書く場所は
`src/server/report/core/report-notation.ts` で、グローバルの `~/.claude/output-styles/asuna.md` は
TUI 向けのまま触らない。

- **見せ方と再構成の線引き**: **本文の文字列を変えないものが見せ方**（CSS・要素の付け替え・
  段組み・折りたたみ・列揃え・書き手が渡した数や寸法や画像を図にして描くこと）で、これは足してよい。
  **レンダラが本文から目次・要約を起こす・中身を削る・並べ替える・言い換えるのは再構成**
  （2.2 のスコープ外）なので採らない。**書き手（モデル）が最初からその構造で書くのは
  執筆であって再構成ではない**ので、規約で促してよい。この線引きは同じ議論が再燃したときの基準
- **画像を描く条件**: tsukumo 自身のサーバが配る手元の画像だけを描き、外部の URL は読まない
  （会話の載るページに外部を読みに行く経路を作らない）。会話の中身が写る画像（スクリーンショット）は
  同じマシンのディスクに留める（`docs/coding-standards.md`「会話内容の扱い」）。`image` の塊の画像は次のとおり
  扱う:
  - **tsukumo は画像を書き出さない**。描いた `report` を受けた時点で書き手のファイルを1回読み、プロセスの
    メモリの棚にだけ持つ。読んでメモリ上のビューに出すだけなので、「会話内容の扱い」の複製の例外は増えない
  - **棚から消えるのは**、プロセスの終わり・記録の窓からレポートが落ちたとき・
    合計が 64 MiB を超えたとき（古いレポートから）。起こし直し・続きからの復元のあとは、
    記録の窓に残った `report` で、時刻が分かり24時間以内のもののうち、ファイルの更新時刻がその `report` の時刻以前のものだけ読み直して棚に戻す。
    時刻が分からない・24時間より古い・更新時刻が新しいもの（同じパスを使い回した別の画かもしれない）は「画像を出せない」の札になる
    （記録に残るのはパスだけ。質問の `preview` の画像は復元では戻さない）
  - **書き手が撮ったファイルそのものは tsukumo が作りも消しもしない**（`scripts/capture/capture-view.ts` は既定で `/tmp` に撮る）
  - **読む場所では絞らない**。拡張子と先頭の印が png・jpeg・gif・webp のどれかに合う、5 MiB 以下の普通のファイル
    だけを読む（モデルは元々どのファイルも読めるので、場所で絞っても守れるものが増えない）
  - **経路は起動トークン付きの `/report-image/` だけで、URL にはファイルを読ませない**（経路は棚を引く鍵で、
    要求の時点ではファイルに触らない）
  - **質問の選択肢の `preview` に書いた画像も同じ棚・同じ読む範囲で扱う**（書き方と鍵は「各表示物」の
    「許可と質問」）。積まれた質問を受けた時点で1回読み、**棚から消えるのは**、答えずに答え待ちから抜けた
    とき・答えたあとの記録が記録の窓から落ちたとき・合計が 64 MiB を超えたとき・プロセスの終わり。
    続きからの復元は質問の記録を組み直さないので、画像の扱いも増えない。**質問の添え書きの `image` の塊も
    同じ棚・同じ鍵（質問の tool use id）・同じ契機で扱う**
- **足さないもの**: **レンダラによる目次・先頭の要約の生成**（上の線引きで再構成の側）/
  **`.note` の種類を増やす**（ok / warn / ng の3つで区別がつく。増やすと選ぶ手が止まる）

**`class` の語彙を増やすときは、同じコミットで規約の文面・`sanitize-schema.ts` の許可リスト・
CSS の3つを揃える**（レンダラを直したのに規約が古いまま、が起きない）。**記法の表の行を削ることは
許可リストを同じコミットで削ることを意味する。**

**効くのは書く前だけ。** 規約は `systemPrompt` の append なので、**本文が書かれたあとに tsukumo が
削る経路は無い**（例外は `report` の本文の整形で、落とすのは意味の変わらない行だけ。上の
「出力の分離」）うえ、**規約の変更が効くのは次にプロセスを起こしたときから**（定数なので、
動いているセッションには当たらない）。**量の上限は数で書かない**（行数や項目数で縛ると、長い調査の
報告まで同じ長さに押し込められる。ユーザーの選択）。**ただし段落の単位にだけは縛る**
（地の文は1段落1話題、話題が変わるなら段落を分け、並ぶ事実は表・箇条書き・`<details>` へ移す。
全体の量ではなく段落が続くことを止めるための縛りなので、長い報告を押し込める話にはならない。
差し戻しはしない: 話題の切れ目は機械で測れず、欄に分けると書く量が増えるため。
「3文まで」から言い換えた経緯は `docs/history/decision.md` の同じ節）。

改訂の経緯（6回ぶん）は `docs/history/decision.md`「requirements.md 4.2 表示 / 読む時間を減らす
ために足すのは、規約の側」、短縮の案と実測は `docs/research/report-notation-shortening.md`。

**規則と置き場の対応。** 規則を足すたびに置き場を考え直さないため、毎ターン読ませる価値がある規約と、書く瞬間に読ませる説明と、直す瞬間だけ要る情報とで置き場を分ける。各塊の `describe` は単体の書き方だけを持ち、欄名・enum・型で読めることは持たない。

**変種の対と判定。** 規約や描き方の版を比べるときは、同じ依頼から書いた2本のレポートの対を、利用者の選択と LLM の判定で見比べる。

- 対を作る入口は `scripts/runtime/variant-pair.ts`。コードに固定した架空の依頼 24 本（`variant-request.ts`）を、`REPORT_SCHEMA_VARIANTS` の版2つ（既定 `json-schema` と `body-fence`）で本物の SDK の駆動に1回ずつ書かせる。書き手の既定は `opus`。受け付けた `report` が来なかった回は2回まで書き直させる。揃った対は疑似セッションの場面にして撮り、左右に並べた `index.html`・左右と版の対応の `pairs.json`・選択のひな形の `choices.json` を、リポジトリの外（既定 `/tmp/variant-pair/<日付>`）に書く。実物の会話は使わない（`docs/coding-standards/conversation-content.md`「会話内容の扱い」）
- 選択の JSON（`choices.json`）の形は `{ "choices": { "<対の ID>": "left" | "right" | "undecided" } }`。`left`・`right` は利用者が速く分かると選んだ側、`undecided` は選んでいない対で、ひな形は全部 `undecided`。読むのは `pair-verdict.ts` の `choicesSchema`
- 判定の入口は `scripts/runtime/pair-judge.ts`（既定のモデルは `sonnet`）。対ごとに左右の画と架空の依頼文だけを渡し、左を先にした回と右を先にした回の2回聞いて、両方で同じ側が勝ったときだけその側の勝ちにする（食い違えば `tie`）。判定は `verdicts.json` に書く
- 一致率の分母は利用者が `left`・`right` を選んだ対で、判定がその側と同じ対を一致に数える。判定の `tie` は一致に数えず、件数を別に出す
- 自己贔屓は、対の両側を同じ書き手が書く（書き手への贔屓が両側に等しく掛かる）・判定のモデルの既定を書き手と違うものにする・版の名前を HTML にも判定にも出さず左右を対の ID から散らす・利用者の選択との一致率で較正する、の4つで避ける。判定を使うかは、一致率を測ってから決める

**聞き直しの記録（読んで分かる時間の代理指標）。** 読んで分かる時間は直接測れないので、受け付けた `report` の直後の依頼が聞き直しで始まるかを `~/.tsukumo/report-usage/` に `kind: "followed"` の行で残す（`at`・`sessionId`・`driver`・`restated`）。行は直前の受け付けの行と同じ `sessionId` で、時刻が直前のものと引き当てる。`report` のあと最初の依頼に1行で、`report` が先に無い依頼は書かない。「受け付けた `report` に続く依頼がまだ来ていない」印はプロセスのメモリだけで持つので、再起動の前の `report` に続く依頼と、セッション ID が決まる前（`starting` のあいだ）に届いた依頼は書かない。行が無いことを「次の依頼が無かった」と読まない。`restated` は依頼の書き出しが語句の表（`report-usage.ts` の `RESTATEMENT_OPENINGS`）に当たるかの真偽で、判定は書き出しの語句の一致だけ。依頼の本文・抜粋は記録しない（`docs/coding-standards.md`「会話内容の扱い」）。同じ論点を聞き直したのはレポートで伝わっていない兆候というだけの代理指標で、読みやすさそのものではない。集計スクリプトは `followed` の行を読み飛ばす。
