# テスト: ハーネスのタスクの再試集

ステータス: **正典**。入口は `docs/architecture/testing.md`（テストの全体）。

責務: ハーネス（CLAUDE.md・rules・スキル・hook・モデルの割り当て）を変えたとき前後を比べる、凍結したタスク30件の置き場・形・選び方・会話の実物を入れない規則と、タスクの再試の走らせ方・費用を持つ。
読む時: タスクの再試集を足す・読む・走らせるとき。
直す時: タスクの再試集の件数・形・選び方、走らせ方、費用の見積もりを変えたとき。

## ハーネスのタスクの再試集

戦略の根拠は `docs/research/harness-strategy.md`。送り出し済みのタスク30件を、着手前の木で落ち、送り出し後の木で通る判定コマンドつきで凍結する。走らせ方は末尾の「走らせ方」。

- **置き場**: `test/harness-replay/<タスクID>/`。1件が次の2ファイル
  - `task.txt`: `tw show` の出力から `## 結果`・`## 介入` を除いた本文の写し。Beads の課題の本文だけで、会話の実物は入れない。拡張子を `.md` にしないのは、凍結した写しを整形とタスク番号の検査（`src/`・`test/`・`scripts/`・`docs/` の `.md` を読む）に当てないため
  - `replay.json`: `base`（着手前の木。送り出したコミットの親）・`after`（送り出したコミット）・`checkFiles`（`after` から取り出して `base` の木へ置くテスト）・`command`（判定コマンド。`checkFiles` を `vitest run` する配列）・`difficulty`・`kind`
- **判定コマンドの確かめ**: `base` の木へ `checkFiles` を `after` から置いて `command` を打つと落ち、`after` の木で打つと通る。30件すべてでこれを確かめて凍結した（落ちるテストは1〜8件。実装のファイルを新しく足す件は、テストの import が解けずファイルごと落ちる）
- **一時の木の決まり**: 一時の木へ共有の `node_modules` を張らない。張った木で `pnpm` を打つと古い base のロックファイルで install が走り、`node_modules/playwright-core` が古い版に差し替わって本体の `tsc --noEmit` が落ちる。張るなら `pnpm` を打たず `node node_modules/vitest/vitest.mjs run <checkFiles>` のように実行ファイルを直に呼ぶ。止まったら本体で `pnpm install --frozen-lockfile --force` で戻す
- **着手時のコミット**: 台帳の `claim` の記録はコミットを持たないので、送り出したコミットの親（`git log --first-parent`）で代える。着手から送り出しの間に main が進んだ件でも、親は main の直前の状態なので判定コマンドの結果は変わらない
- **会話の実物を入れない**: SDK のイベント・transcript・画面の会話の抜粋は1件も入れない（`docs/coding-standards.md`「会話内容の扱い」）。入れるのは課題の本文とテストのファイルだけ

### 選び方

直近28日に `main` へ送り出した件のうち、次を満たすものから難しさと種類を散らして30件を選ぶ。

1. 送り出したコミットが `test/` の単体テスト（`*.test.ts`、E2E を除く）を足すか直している（判定のテストにできる）
2. そのテストを `base` の木へ置くと落ち、`after` の木では通る（判定コマンドが変更を見分ける）
3. 課題の本文が、人の手や実機の確かめを要求していない（タスクの再試の走らせ手が claude だけで進められる）

2を満たさなかった件（テストが既存の実装でも通る規約の検査、`after` の木でも環境のために落ちる件）は外した。目視の確かめだけが完了条件の件は、判定コマンドにできないので初めから候補に入れていない。

| 難しさ \ 種類 | feature | bug | refactor | docs | 計  |
| ------------- | ------- | --- | -------- | ---- | --- |
| haiku         | 4       | 1   | 4        | 1    | 10  |
| sonnet        | 8       | 3   | 1        | 0    | 12  |
| opus          | 3       | 3   | 2        | 0    | 8   |
| 計            | 15      | 7   | 7        | 1    | 30  |

難しさの比は、候補の分布より haiku と opus を厚くして、モデルの割り当てを変えたときの差が見えるようにした。最初の10件は候補150件（上の1を満たす件）の分布（sonnet 125・opus 13・haiku 12）から選んだ。20件を足したときは、直近28日の候補841件のうち、テストが2ファイル以下で完了条件が目視・実機を求めない431件から選んだ。このうち難しさ別に数えたのは362件（sonnet 302・opus 39・haiku 21）で、残り69件の難しさは数えていない。種類は課題の件名から数えた（Beads の `kind` の記録は読んでいない）。

## 走らせ方

```bash
pnpm run harness-replay -- --tasks <ID,…> --k <n>
```

`--brief <path>` を足すと、そのファイルの本文（実装役の決まり `implementer-brief.md` など）を依頼文の先頭に「次の決まりを最初に読んで従ってください。」と添えて入れる。brief の行を外した版と元の版を比べるときは、版ごとのファイルを渡して2回ずつ走らせ、`pass^k` を比べる。

```bash
pnpm run harness-replay -- --tasks <ID,…> --k 2 --brief <元の版>
pnpm run harness-replay -- --tasks <ID,…> --k 2 --brief <外した版>
```

`--brief` を省くと依頼文は従来のまま（課題の本文だけ）で、brief を通らない。費用の幅は下の「費用と負荷」の「5件 × k=2 の概算」を見る。

1回ごとに、`base` で一時の作業ツリーと枝を起こし、いまの `AGENTS.md`・`CLAUDE.md`・`.claude/`・`.tw/config.toml` を重ね、`task.txt` を依頼にして `claude -p` を1回起こす（モデルは `claude -p` の既定。判定コマンドは伏せる）。終わったら `checkFiles` を `after` から置いて `command` を打ち、通れば1回の合格。一時の作業ツリーと枝は成否にかかわらず消す。

- **出力**: 1件ごとに4行。`pass^k`（k 回とも通ったか）・トークンの中央値（入力・出力・キャッシュの合計）・時間の中央値・拒否の回数（hook や権限で断られた数の合計）
- **再試しないもの**: `tw claim` からの委譲・受け入れ・振り返りの流れそのもの（課題は Beads で完了済みで、一時の作業ツリーには印を立てられない）。起こすのは `claude -p` 1回で、CLAUDE.md・rules・スキルの本文・モデルの表の差が出る範囲を比べる
- **環境変数**: `CLAUDE_CODE_*`・`CLAUDECODE`・`CLAUDE_AGENT_SDK*`・`ORCA_*` は子へ渡さない（今のセッションや orca のタブの一員として振る舞わせないため）。認証は環境変数に依らず、落としても `claude -p` は動いた
- **判定コマンドの限界**: テストが新しく足された実装のファイルや名前を import する件は、課題の本文にその名前が無いと合格しにくい（`pass^k` が実装の質でなく名前の当て推量で決まる）。結果を読むときは `checkFiles` の import を見る

### 費用と負荷

- **1件の実測**: 小さな整理の課題（haiku）を k=1 で走らせて、トークン 37万・57秒。判定コマンドは名前の当て推量のため通らなかった。戦略の見積もり（1件 1,000万トークン）は大きな課題向けで、整理・小さな追加は桁が小さい
- **5件 × k=2 の概算**: 10回。同じ規模なら 370万トークン・約10分（直列）。戦略の見積もりどおりの規模なら 1億トークン（30日の消費量の0.5%）。実測が揃うまでは上の幅で見る
- **CPU**: 直列で1回ずつ起こすと、走行中の `secd` は 0% のまま、`claude -p` は5%台だった。複数を同時に起こしたときの `secd` の様子は未確認（この道具は直列にしか起こさない）
