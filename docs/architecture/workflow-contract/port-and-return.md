# ワークフローの契約: ツールと委譲の返却

ステータス: **正典**。入口は `docs/architecture/workflow-contract.md`（ワークフローの契約の全体）。

責務: tsukumo がワークフローから受ける2つのツール（`work_plan`・`report`）の名前と引数の意味、委譲先の返却（`phase_result`）でのプログレスバーの進め方を持つ。
読む時: ツールの引数を変える・使う、プログレスバーの進め方を直すとき。
直す時: ツールの引数・委譲の返却の書式とプログレスバーの進め方を変えたとき。メインを縛る振る舞いは `docs/architecture/display/work-plan-host-rule.md`。

## ツール

契約のツールは MCP ツール `work_plan` と `report`、委譲先が呼ぶ `phase_result`（`docs/architecture/workflow-contract/skill-sequence.md`「スキルの契約」）。意味はツールの説明（`src/server/work-plan/core/work-plan-tool.ts`・
`src/server/report/core/prompt/report-tool.ts`・`src/server/work-plan/core/phase-result-tool.ts`）とシステムプロンプトの「ワークプラン（tsukumo）」の節がモデルに教える。

`work_plan`（ワークプラン。毎回フェーズの並びごと渡す）:

| 引数              | 意味                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `phases`          | フェーズの並び（1つ以上）。要素はフェーズの名前か、同時に走るフェーズの名前の配列（並列のフェーズ。2つ以上・重ならない）。フェーズの番号は並びを平らにした読み順。名前の代わりに `{ id, name }`（`id` は段の id。`docs/architecture/screen-design/work-strip.md`）でも渡せ、並列のフェーズの配列の中も同じ。id は全部の段に重ならない値で渡すか、どの段にも渡さない（一部だけ・空白だけ・重なる id は差し戻す） |
| `current`         | 今の要素の位置（0始まり）。全部済んだら要素の数。`current` が要素の数に等しい `work_plan` の呼び出しは差し戻す。全部済みにするのは `report` の `workPlanClosing` だけ                                                                                                                                                                                                                                           |
| `finishedInGroup` | `current` が並列のフェーズを指すとき、その中で済んだフェーズの名前。並列のフェーズの最後のフェーズを済ませる呼び出しでは `current` を進めて空にする                                                                                                                                                                                                                                                             |
| `phaseSummary`    | 終えたフェーズでしたこと・分かったことを1〜2文で。済んだフェーズがあり全部は済んでいない呼び出しで必須。`phase_result` で進んだ位置でも省けない（下の「委譲の返却」）                                                                                                                                                                                                                                           |
| `delegatedRange`  | 委譲先のフェーズの範囲。`first`（委譲先のフェーズ1に当たる位置。平らにした並びで0始まり。省くと `current` の次）と `count`（フェーズの数。省くと `pending`＝フェーズの数が未定で、`phase_result` を受けたあとは `count` で確定する）。委譲しないときは省く。下の「委譲の返却」                                                                                                                                  |
| `skippedPhases`   | 済んだフェーズのうち、飛ばしたフェーズの名前の配列（`docs/architecture/workflow-contract/skill-sequence.md`「スキルの契約」の「飛ばしたフェーズの印の決まり」）。`phases` の名前に含まれ、その呼び出しで済んでいるフェーズだけ。毎回の呼び出しで、メインが飛ばしたフェーズをすべて渡す。飛ばさなかったら省く                                                                                                    |

依頼の最初の `work_plan` は着手の時点でフェーズ1（`current: 0`）で渡す。済んだフェーズのある位置（`current` 1 以上）から始まる呼び出しも差し戻さず、前のフェーズは済みに数え、そのフェーズの所要は「不明」になる。
フェーズは1つずつ進める（平らにした並びで済んだフェーズを1回で2つ以上増やす呼び出しは差し戻される。飛ばしたフェーズも済んだフェーズに数える）。並列にできるかを決めるのは渡す側で、
tsukumo は推し量らない。
受け付けた呼び出しの戻り値は `ok` の次の行に、プログレスバーの今のフェーズ（「3/6 フェーズの名前」。`delegatedRange` があれば「本 2/3 フェーズの名前」「後 1/3 フェーズの名前」のように群の名と群の中の番号）を返す。

`report`（ターンの結果）のうち契約に当たる欄:

| 引数              | 意味                                                                                                                                                                                                                                                                                                                        |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task`            | タスクの作業のレポートのときだけ。`id`（Beads の ID）・`name`（作業の名前）・`outcome`（`finished` 終えた／`stopped` 止めた／`awaiting-answer` 利用者の答え待ち）・`genre`（報告の種類。`work`／`decision`／`research`。省略可、無い・読めないときは `unspecified`）                                                        |
| `workPlanClosing` | フェーズの閉じ方。`work_plan` を渡した依頼では必須。`finished`（最後のフェーズにいるときに渡すと tsukumo がプログレスバーを全部済みにする）／`stopped`（止まったフェーズが「今」のまま残る）                                                                                                                                |
| `figure`          | 任意。レポートの図1つ（`image`・`mermaid`・`graph`・`svg`・`compare`・`chart`・`stats` の部品）。省くと図なしで描く。旧い形の `{ kind: "none", reason }`（`short-answer`／`no-shape`／`single-value`／`no-material`）も読め、理由が本文と合わないと差し戻す（`docs/architecture/display.md`「出力の分離（セリフと詳細）」） |

`retrospective`（任意）は、ワークフローに振り返りのフェーズがあるとき、その結果を本文のセクションに混ぜずに受ける欄。
`summary`（結果の1〜2文）と `drafts`（積んだドラフトのタスクID。積まなければ空）、`blocks`（`sections` と同じ部品。図・表・コードが要るときだけ）を持ち、`sections` の後ろ・`favor` の前に見出し「振り返り」のセクションとして描く（目次に載る）。
tsukumo はプログレスバーのフェーズの名前を見ず、欄があるときだけ描く（フェーズの名前を契約にすると他のワークフローを縛るため）。欄が欠けても差し戻さず、数えない。

`task.outcome` はタスク見出し行の終わり方で、プログレスバーは閉じない。どこへ送ったかは tsukumo の関心にしない。
`task.genre` は種類ごとの既定のセクションの並びを選ぶだけで、描き方も差し戻しも変えない（並びの正典は `REPORT_FIELD_CARD_NOTES` の `task`）。
`checks` に `ng` の行がある `report` の `finished` は差し戻す（`docs/architecture/display.md`「出力の分離（セリフと詳細）」）。

## 委譲の返却

**委譲先は `phase_result`（MCP ツール。`docs/architecture/workflow-contract/skill-sequence.md`「スキルの契約」）でフェーズの結果を返し、tsukumo は `SubagentHandback` の本文を読まない。** 書式の正典はこの節と `docs/architecture/workflow-contract/skill-sequence.md`「スキルの契約」で、ワークフローの依頼文はこれを参照し、書式を言い直さない。経緯と採らなかった案は `docs/architecture/adr/0024-no-skill-dependency.md`「2026-10-10 の改訂」と `docs/architecture/adr/0030-workflow-as-skill-sequence.md`。
`phase_result`（と `work_plan`・`report`・`speak`）は tsukumo の会話画面が `query()` に渡すプロセス内の MCP サーバ `tsukumo` にあり、会話画面の中でだけ、メインにも委譲先にも見える。素の `claude` の CLI では存在せず、委譲先は呼べないので自由文の返却で進む（その返却ではプログレスバーは動かない）。根拠は `docs/research/phase-result-unavailable-2026-11-05.md`。`/loop /next-task` は tsukumo の会話画面で回す前提とする。

返却でプログレスバーを動かすのは `phase_result` の `finished`・`skipped` だけで、受け付けた呼び出しの時刻と引数で動く（ワークフロースクリプトの写しで進む道は下の「プログレスバーの進め方」）。
`phase_result` を呼ばなかった委譲先（古い plugin、計画だけの回）の返却ではプログレスバーは動かない。
返却を受けたメインを縛る振る舞いは `docs/architecture/display/work-plan-host-rule.md` が持つ。

プログレスバーの進め方:

- **プログレスバーのフェーズと委譲先のフェーズは1つずつ対応させる。** メインは `work_plan` の `delegatedRange` で、委譲先のフェーズ1〜`N` に当たるプログレスバーのフェーズの範囲を宣言する。
  **プログレスバーのフェーズは、範囲の前（前）・範囲（本）・範囲の後ろ（後）の3つの群に分かれ、群ごとに1から数える。** 群は `delegatedRange` の位置だけで決まり、
  ほかの引数は持たない。本のフェーズはプログレスバーでも委譲先のフェーズと同じ番号（範囲の先頭が 1、フェーズの数は `N`）で、前・後のフェーズ（計画・受け入れ・振り返り・送り出しなど）は
  「前 1/1」「後 2/3」のように群の名を付けて数える。範囲の無い依頼は並び全体が1つの群で、群の名を付けずに通し番号で数える。
  範囲の前後にメインのフェーズを置いてよい。範囲の中に並列のフェーズを置いてよいが、範囲の端をまたぐ並列のフェーズは差し戻す
- 計画を委譲先に頼む最初の呼び出しは `delegatedRange` を `{ first }`（`first` も省いてよい）だけで渡す（`pending`。`N` が未定のため）。
  そのあいだは範囲を並びの1要素（実装）とみなし、前のフェーズと後ろのフェーズ（受け入れ・振り返り・送り出しなど）は群の中で1から数えて番号を持つ（後の番号は `N` が決まっても変わらない）。
  番号を持たないのは範囲の要素だけで（右肩に位置を出さず、範囲は下線の区間1つ）、委譲先の `phase_result` では動かない。
  同じ依頼で `phase_result` を受けたあとの `work_plan` は、`count` を書いても省いても、範囲のフェーズの数を最後に受けた `phase_result` の `count` で tsukumo が確定する（食い違いも差し戻さない）。
  範囲の `first` は、渡された範囲が決めていればそれ、省かれていれば受け付け済みの範囲の `first`、まだ範囲が無ければ渡した時点の `current` の次。
  確定した範囲が並びをはみ出すか並列のフェーズの端をまたぐときだけ差し戻す。
  `phase_result` の `count` が来ない環境（計画だけの回の返却・古い plugin）は `pending` のまま通り、範囲の要素に番号は付かない。範囲を宣言しない依頼（`phase_result` を受けない委譲）は今までどおり通る。
  組み直しで戻るもの・戻らないものは `docs/architecture/display/work-plan-host-rule.md`「組み直しで戻るもの・戻らないもの」
- セリフが委譲先のフェーズを番号で言うときは、その番号を `speak` の任意の引数 `phase` で申告する（検査は `docs/architecture/display/work-plan-host-rule.md`「speak の phase の検査」）。
  セリフで番号を言うのは本のフェーズだけで、前・後のフェーズは名前で言う（カードや頭の番号が「後 1/3」と出ても、セリフの「フェーズ1」は本のフェーズ1を指す）
- **`phase_result` の `finished`・`skipped` が届き、結果を返す段（`step` の id か呼んだ agent の段。解き方は `docs/architecture/workflow-contract/skill-sequence.md`「スキルの契約」）が今のフェーズの集合に入っていれば、tsukumo がそのフェーズを受け付けた呼び出しの時刻で済ませる**
  （1本道なら `current` を1つ進め、並列のフェーズの中なら `finishedInGroup` に足す。並列のフェーズの最後に残ったフェーズなら `current` を進めて空にする）
- `step` で返した呼び出しは範囲に依らず済ませ、一足飛び・もう済んだフェーズは差し戻す。
  互換の道（`phase`・`count` と範囲で解く）では、一足飛び（フェーズ `n` が今のフェーズの集合より先）・もう済んだフェーズ・`stopped`・範囲を宣言していない（`pending` を含む）依頼・`count` が範囲のフェーズの数と違う呼び出しはプログレスバーを動かさない。
  ただし `phases` に段の id を渡したワークプランでは、範囲があり `count` が範囲のフェーズの数と同じ `finished`・`skipped` の一足飛び（飛ばし）ともう済んだフェーズ（戻り）を差し戻す（`count` は確定に使わない）
- **ワークフロースクリプトの写し（`task_progress` の `workflow_progress`）の `workflow_agent` の `phaseTitle` が `phases` の段の id に一致すると、その agent の段（一致が複数ならいちばん後ろの段）の要素が今の要素より後ろのときだけ、写しの届いた時刻でその要素を今の要素にし、前のフェーズを済ませる。**
  `phase_result` を待たず、後の群（受け入れ・振り返り）も完了の知らせを待たずに今のフェーズになる。写しで飛び越えたフェーズに飛ばした印は付けず、直前に済んだフェーズの扱いはメインを縛る決まりに従う。
  写しでは戻さない。段の id の無いワークプランと、題が `phase N` に伏せられた写しでは動かない（契約の全体は `docs/architecture/screen-design/work-strip.md` の「ワークフロースクリプトの流れでは」の項）
- `phase_result` ではプログレスバーを全部済みにしない。最後のフェーズを閉じるのは今までどおり `report` の `workPlanClosing`
- **`phase_result` の `finished` は、任意の欄 `summary`（フェーズのまとめを1〜2文）を持てる。** `summary` のある `finished` で済んだフェーズは、その文がプログレスバーの中間レポートに出て、メインが同じ位置を渡す `work_plan` は `phaseSummary` を要らない。
  メインが `phaseSummary` を添えても、そのフェーズの中間レポートに出るのは `summary`（フェーズは既に済んでいて、メインの文では出し直さない）。`summary` を持たない `finished` で済んだフェーズは、メインの `work_plan` に `phaseSummary` が要る。
  `summary` は `skipped`・`stopped` には付けられない（`stopped` の理由は `reason`）。ワークフロースクリプトのあいだメインは返却を受けないので、フェーズごとの中間レポートはワークフロースクリプトの中の委譲先が `summary` で書く
