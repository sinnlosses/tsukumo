# 相づちの札: 代ごとに先に書く返事・作業の会話を通らない経路・局面の表と札の決め方（2026-11-13）

ステータス: 採用

**相づち（立ち絵の右上に出る短い返事の札と、押したときのキャラクターの一言）は、反応の行と同じく代（起こした1回）の始めに使い捨ての問い合わせ1本で先に書いておく。押したときは問い合わせを起こさない。押した札はコマンドで受け、セッションの記録に「利用者の札の行」と「反応の行」を積む。SDK の駆動には何も渡さないので、作業は止まらず、作業中の会話（依頼・補足）にも入らない。どの局面に札を何枚まで出すかは共有のコードの局面の表が持ち、札の文と返事はキャラクターの人格から問い合わせが書く。相づちは記憶（会話のアーカイブ・あらすじ）に残さない。作業を走らせたまま雑談する形は作らず、作業中の雑談への切り替えは今のまま拒む。**

この ADR が決めるのは、返事の出どころ・押してから吹き出しに出るまでの経路・札の決め方・記憶との関係・回数と費用の上限まで。札の見た目と置き場は ADR 0057 の舞台と見本が決める。

## 何が困っていたか

- 見本（`docs/history/mockup/report-progress-2026-11-12/index.html` の `.aizuchi`）では、渡したあと・失敗のあと・働いているあいだに札が1〜2枚出て、押すとキャラクターが表情を変えて返す。返事は場面ごとに手で書いた決め打ちの文で、作り方は決めていなかった。
- キャラクターに喋らせる道は2つある。作業中のセッションの `speak` と、会話とは別に起こす使い捨ての問い合わせ（`src/server/core/query/throwaway-query.ts` の `ThrowawayQueryKind`）。前者に札の言葉を入れると、作業中の会話に入ってしまう。
- 作業中に雑談へ切り替えるコマンド（`src/shared/contract/session.ts` の `setChatMode`）は、駆動を起こし直す（`restarts: true`）。そのため、ターンの最中は `chatModeSwitchDuringTurn` で断られる。

## 利用者が決めたこと

- 見本は `docs/history/mockup/report-progress-2026-11-12/index.html`。言葉の説明と見本が食い違ったら見本が勝つ。
- 相づちは作業を止めず、作業中の会話（依頼・補足）とは別のやり取りにする。
- キャラクターの中身（返事の文）はコードに書かない。
- 会話内容の扱いの規約（`docs/coding-standards/conversation-content.md`）を守る。

## 決めたこと

### 論点 1: 返事の出どころ

**採る: 反応の行（`src/server/welcome-greeting/core/written-reaction.ts`）と同じ形で、代の始めに使い捨ての問い合わせ1本で先に書いておく。種類は `ThrowawayQueryKind` に `aizuchi` として足し、反応の行とは別の問い合わせにする。材料は人格（`persona.md`）と表情の選択肢だけで、会話から導いたものを渡さない。**

- 書く単位は局面ごと（論点 3 の表）。局面ごとに、札の文（利用者の言葉）・返事・表情の組を3つずつ書かせる。
- 検査は反応の行と同じく、どれか1組でも空・改行入り・上限超え・知らない表情・欠けに当たれば全部を落とす。落ちたら、その代では札を出さない。
- 反応の行とまとめて1本にはしない。札が落ちたせいで、再試行・失敗・利用上限の反応まで出なくなるのを避ける。
- 局面の中身を推し量った返事は書かせない（反応の行の「作業の中身は知らないので、中身を推し量って書かない」と同じ）。見本の「期待値を直せば」「検査が終わるまで」のような中身に触れる返事は、先に書く形では書けない。見本で見せたいのは、返す・表情が変わる・流れに入るの形なので、返事は局面に合った一般の言葉で足りるとみなす。

| 案                                         | 待ち時間                         | 費用                       | その場の状況に合うか                                                                                                                                              | 判定     |
| ------------------------------------------ | -------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 代の始めに先に書く（反応の行と同じ形）     | 押したらすぐ出る                 | 代ごとに1本                | 局面には合う。作業の中身には触れない                                                                                                                              | 採る     |
| 押したその場で使い捨ての問い合わせを起こす | 数秒〜十数秒。札の軽さに合わない | 押すたびに1本              | 中身に合わせるには会話を渡すことになり、「会話を claude へ渡してよい」2つの例外の外になる（渡す先を増やすにはユーザーの決定が要る）。渡さなければ先に書く形と同じ | 採らない |
| 作業中のセッションに `speak` で返させる    | ターンの切れ目まで待つ           | 作業のセッションのトークン | 合うが、作業中の会話に入る。決まっていることに反する                                                                                                              | 採らない |
| パックの定義ファイルに札と返事を書いておく | すぐ                             | なし                       | 局面には合う                                                                                                                                                      | 採らない |

パックに書く案は今あるパックと画面から作るパックのすべてに書き足しを求める。迎えの挨拶と反応の行が人格から書く形にそろっているので、相づちもそれに合わせる。

### 論点 2: 作業を止めない経路

**採る: 押した札は新しいコマンド（`pressAizuchi`。入力は札の局面と番号だけ）で受ける。`meta` は断らない形（`NO_COMMAND_REFUSAL`）にし、ターンの最中も雑談でも受け付ける。サーバは駆動（SDK の `query()`）に何も送らず、セッションの出来事を1つ出す。畳み込み（`applySessionEvent`）が、記録に利用者の札の行と、反応の行（`kind: "reaction"`。`ReactionKind` に `aizuchi` を足す）を積む。**

- 反応の行の記録は、今もセリフのログ（舞台の流れ）だけが拾い、メインビュー・雑談のログ・会話のアーカイブは拾わない。利用者の札の行も同じ扱いにする。これで、流れには入るが作業中の会話にも紙にも入らない。
- 吹き出しには押した返事を `ShownReaction` の `shown`（`reaction: "aizuchi"`）として出す。本物の `speak` が届けば、ほかの反応と同じく条件が外れて消える。表情も返事の表情に替わり、`speak` が届けばそちらに戻る。
- 入力に文面を持たせない。札の文と返事はサーバが代の始めに書いたものから取り出すので、ブラウザから任意の文字列は受けない。
- transcript には入らないので、続きから起こし直すと札の行と返事は流れから消える。反応の行と同じで、これは受け入れる。

| 案                                               | 物差し                                                                                      | 判定     |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------- | -------- |
| コマンドで受け、記録に積むだけ（駆動に送らない） | 作業のターンに触れない。反応の行の道（記録・`ShownReaction`・セリフのログ）をそのまま使える | 採る     |
| 補足（脇の話）として作業中のセッションへ送る     | 作業中の会話に入り、ターンの指示の流れに混ざる                                              | 採らない |
| ブラウザの中だけで札の行と返事を出す             | タブを開き直すと「押した札」の勘定が消え、同じ札が出直す。タブ同士で食い違う                | 採らない |

### 論点 3: 札の文と出す局面を誰が決めるか・数と繰り返さない決め方

**採る: 札を出す局面と、1つの局面に出す数は、共有のコードの局面の表が持つ。札の文と返事は、論点 1 の問い合わせがキャラクターの人格から書く。局面は `conversationMoment`（`src/shared/session/conversation-moment.ts`）の値を使い、新しい状態を持たない。**

| 局面                       | 出す数 | 見本の場面                                                     |
| -------------------------- | ------ | -------------------------------------------------------------- |
| `deliver`（渡したあと）    | 2      | 「おつかれさま」「ありがとう」                                 |
| `stumble`（失敗のあと）    | 1      | 「大丈夫、続けよう」                                           |
| `work`（働いているあいだ） | 1      | 「がんばって」「あせらなくていいよ」                           |
| `greet`・`ask`             | 0      | 迎えは挨拶と始め方が、尋ねるはお伺いが入力欄を使うので出さない |

- 表に載るのは局面と数だけで、文は持たない。表の局面の名前は問い合わせの出力の形（zod）の鍵にもなる。
- 繰り返さない決め方: 局面ごとの3組から、その代でまだ押していない組を前から順に出す。押した組はその代ではもう出さない。3組とも押した局面には、その代のあいだ札を出さない。押した勘定はサーバのセッションの状態に持ち、代が替われば書き直した新しい3組で数え直す。
- 押すと、その局面にいるあいだは札を全部引っ込める（見本で、返したあと札が消える形）。局面が替わって同じ局面に戻ってきたら、残りの組から出す。
- 過去のやり取りを見ているあいだは札を出さない。札はいちばん新しいやり取りの局面に付く。

| 案                                   | 物差し                                                                                                 | 判定     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------ | -------- |
| 局面と数はコードの表、文は問い合わせ | 局面は画面の都合で、キャラクターの中身ではない。文は人格から書くので、コードにもパックにも文を書かない | 採る     |
| 局面も文もパックが決める             | パックの書き手が画面の局面を知る必要がある。パックの書き足しが要る                                     | 採らない |
| 局面も数もモデルが決める             | 出すかどうかが代ごとに揺れ、画面の配置が安定しない                                                     | 採らない |

### 論点 4: 相づちを記憶に残すか

**採る: 残さない。会話のアーカイブ（`~/.tsukumo/chat-archive/`）にも、定着のあらすじにも書かない。**

- 札の行も返事も代の始めに人格だけから書いたもので、利用者とキャラクターがその場で交わした会話ではない。アーカイブに入れると、次のセッションの `systemPrompt` に「言っていない返事」が記憶として渡る。
- 反応の行の記録がアーカイブに入らないのと同じ線で、書き出しの例外の表（`docs/coding-standards/conversation-content.md`）に行を足さずに済む。
- 押した回数のような数は記憶ではなく成果や日記の材料になりうる。足すなら別に決める。

### 論点 5: 「待つあいだ話そう」

**採る: 作業を走らせたまま雑談する形は作らない。作業中の雑談への切り替えは今のまま `chatModeSwitchDuringTurn` で拒む。見本の「待つあいだ話そう」は、働いているあいだの札の1つ（論点 3 の `work`）として、返事を返すところまでにとどめる。そのためのタスクは足さない。**

- 雑談への切り替えは駆動を起こし直すので、ターンの最中に通すと作業が止まる。走らせたまま話すには、作業のセッションとは別に雑談のセッションをもう1本起こすことになる。費用が倍になり、記憶（アーカイブ・あらすじ）を2本から同時に書く道もできる。
- 長い待ちのあいだに言葉を送る道は、今も補足（脇の話。`PromptRouting` の `aside-when-background`）としてある。相づちはそれとは別に、作業に触れずに返す軽い楽しみ方として出す。
- 問い合わせへの指示に、札の文で「このあと雑談が続く」と約束させないことを入れる。返事のあとに会話は続かないので、続くと読める札は書かせない。

| 案                                               | 物差し                                                                | 判定     |
| ------------------------------------------------ | --------------------------------------------------------------------- | -------- |
| 拒む形のまま、相づちの札で軽く返すだけ           | 作業に触れない。費用は代ごとの1本のまま                               | 採る     |
| 作業を走らせたまま、別の雑談のセッションを起こす | 費用が倍。記憶の書き手が2本になり、あらすじの定着が食い違う道ができる | 採らない |
| 作業中も雑談への切り替えを通す（作業を止める）   | 「作業を止めない」に反する                                            | 採らない |

### 論点 6: 回数と費用の上限

**採る: 問い合わせは代ごとに1本（`runRetriedQuery` の再試行の範囲まで）。押すたびの問い合わせは無い。押せる回数は代ごとに局面ごとの3組まで（局面の表の3局面で、代につき最大9回）。**

- 問い合わせの足跡は、ほかの使い捨ての問い合わせと同じく、種類・時刻・所要・トークン・結果の種類だけを記録する（`ThrowawayQueryFootprint`）。
- モデルと時間切れは、迎えの挨拶と反応の行と同じ値（`WELCOME_GREETING_MODEL`・`WELCOME_GREETING_TIMEOUT_MS`）を使う。誰もこの問い合わせを待たない。
- 書けなかった代では札を出さないだけにし、押したときに書き直しはしない。

## 採らなかった案

- **押したその場で問い合わせる。** 待ち時間と費用が押すたびに掛かり、状況に合わせるには会話を渡す先を増やすことになる（論点 1）。
- **作業中のセッションに返させる。** 作業中の会話に入る（論点 2）。
- **札の文と返事をパックに書く。** パックの書き足しが要り、迎えの挨拶・反応の行の作り方とそろわない（論点 1・3）。
- **作業を走らせたまま雑談のセッションを起こす。** 費用と記憶の書き手が倍になる（論点 5）。

## 残すこと

- 先に書いた返事が局面に合って聞こえるか。札を組む段で、渡したあと・失敗のあと・働いているあいだを撮り、受け入れの目視で確かめる。合わなければ、指示文の局面の説明を直す。
- 押した回数を成果や日記に出すか（論点 4）。出すなら別に決める。
