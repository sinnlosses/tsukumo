# 会話の流れの文法: 届いた順の1組・動詞で言ういまの行・お伺いの頭と2段の確定・空の入力欄の ↑（2026-11-16）

ステータス: 採用

**タスク実行中のメインビューの会話の流れを、作り直した見本（`form=goal` と `states.html`）の文法にそろえる。隣り合う物とセリフは記録の位置の隣で1組にし、並べ替えない（例外は `report` の締めのセリフ1つで、同じ呼び出しの中身なので紙の上に置く）。いまの行は道具の名前ではなく動詞・対象・経過で言い、長く掛かると添え書きを足す。お伺いの頭は種類・題・待ち時間・広げるの4つにし、戻せない選択肢の確定を2段にする。答えた質問は「聞いた1行」と利用者の投稿にし、待っている用件へは入力欄が空のときの ↑ で移る。この ADR は、ADR 0055・0058・0059・0060 の論点の一部を論点ごとに上書きする（本文は書き換えない）。**

この ADR が決めるのは、流れの行の並べ方・組み方・言い方・キー・開閉の形・幅の上限・送る順まで。寸法と色の値は見本（`docs/history/mockup/stream-harmony-2026-11-16/goal.css`）と、器・トークンの ADR が持つ。`report`・`work_plan`・`speak` の入力に欄は足さない。狭い画面（760px 以下）は今のまま残す。

## 決めたこと

見本のファイルは `docs/history/mockup/stream-harmony-2026-11-16/` の下にある（以下、名前だけ書く）。「組」「いまの一言」「初回の説明」「答え直す」「用件へ移る口」は、この ADR で用語集に足した語（`docs/glossary/conversation-phase.md`）。末尾の行は用語集の「いまの行」（`NowLine`）と同じもの。

### 論点 1: 組の規則

**採る: 「隣り合う」は記録の位置の隣で判定する。流れに描く行（投稿・セリフ・済んだフェーズの札・質問の記録・お伺い・失敗の表示・紙）だけを並べた列で、物とセリフが間に何も挟まずに並んでいれば1組にする。物はすぐ後ろのセリフと組み、後ろがセリフでない（か、もう組になっている）ときだけすぐ前のセリフと組む。1つの行は1つの組にしか入らない。組は描く間を詰めるだけで、並びは記録の位置の順のまま変えない。**

- 「同じ応答」では判定できない。記録（`SessionRecord`）は応答の区切りも呼び出しの束も持たない（「実物で確かめたこと」）。
- セリフと `work_plan` の記録の順は、どちらもあり得る。`speech` は `speak` の `tool-finished` で出る（`SpeechReview.pass`）ので、同じ応答に並べた呼び出しは結果の届く順で前後する。疑似セッションにも両方の並びがある。
- 「後ろを先に見る」は書き手の判断。見本の働く場面は「セリフ → 済んだフェーズの札 → セリフ」で、札は後ろのセリフと組んでいる（`flow.js` の `phaseDone`）。お伺いと失敗の表示は流れの末尾に来るので、前のセリフと組む。
- 行の間は3段にする。組の中は狭く（見本の 4px）、同じ話し手の続きは中（16px）、利用者の投稿の前後は広く（16px に 8px を足す）。値は見本の `goal.css` の `.group`・`.flow` の `gap` と `.row-user` の `margin-block`。
- 済んだフェーズの札は、印・「n/N 名前」・所要・まとめの形で、幅をそろえる（見本の `.slip` の `min(100%, 560px)`）。中身の長さで右端が揺れない。
- 該当する見本: `index.html?form=goal&moment=late`、`states.html`「隣り合う物とセリフは、届いた順のまま1組にする」。

### 論点 2: 締めのセリフと紙

> この論点の「いまの行を流れの末尾の決まった位置に置いたままにする」は、ADR 0070 論点 2 が上書きした。広い画面では「レポートを書いています」をプログレスバーの一文が言う（2026-11-18）。

**採る: 締めのセリフは紙の上に置き、紙と1組にする。書いているあいだは、締めのセリフの場所を1行ぶん空けて押さえ、いまの行（「レポートを書いている」）は流れの末尾の決まった位置に置いたままにする。書き終えたら空けた場所に締めのセリフが入り、紙は動かない。**

- 締めのセリフは `report` の `closing` で、記録の上では紙（`report`）のすぐ後ろの `speech` として届く（`closingSpeech` が `report` の直後に出す）。2つの記録だが同じ呼び出しの中身なので、論点 1 の「並べ替えない」の外に置き、紙の上に描く。並べ替えるのはこの1組だけ。
- 書いているあいだ（`ReportDrafting` の `drafting`）は締めのセリフがまだ無い（`closing` は書き終えた引数の中にあり、途中の部品の列には入らない）。
- **見本と違う**: 見本（`states.html`「書きかけのレポート」）は、空けた場所にいまの行を置く。そうすると紙が伸びるにつれていまの行が上へ押され、下端を見ていると画面の外へ出る。ADR 0059 論点 1 が採った理由（いまの行は入力欄の上の決まった位置で動かない）とも合わないので、いまの行は末尾に残し、紙の上は空けて押さえるだけにする。
- 空けて押さえる高さはセリフ1行ぶん。締めのセリフが2行以上なら、そのぶんだけ紙が下がる（書き手の判断。押さえを大きく取ると、1行の締めの下に隙間が残る）。
- 完了したら、紙より前のセリフ・札・質問の記録は「作業の経過」に畳む（ADR 0058 対応表「経過の畳み」を、セリフも畳む形に改める）。締めのセリフと紙の組は畳みの外、畳みのすぐ下に置く。
- 該当する見本: `index.html?form=goal&moment=read`、`states.html`「書きかけのレポート」。
- この論点は ADR 0069 が上書きした（締めのセリフは記録の順のまま紙の下に置き、押さえはやめる）。

### 論点 3: 末尾の行（いまの行）の文

> この論点は ADR 0070 論点 2 が上書きした。表の動詞と対象は使い続け、語順を「対象 を 動詞」の敬体にし、長く掛かっているときの添え書きはやめる（2026-11-18）。同じ日に、道具の手順は動詞を付けず対象だけを出す形に改めた（表の道具の動詞は、対象が引けないときにだけ使う。ADR 0070 論点 2 の注記）。

**採る: いまの行は「していること（動詞）・対象・経過」の3つで言い、長く掛かると添え書きを足す。動詞は道具の名前から下の表で引き、道具でない状態も同じ言い方にそろえる。知らない道具は「道具を使っている」に道具の名前をそのまま対象として添える。ADR 0059 の後回しのうち、「走っている手順を人の言葉に言い換えること」「止まって見えるときの言い方」「委譲先の役ごとの1行」をこの論点で解く。**

| 状態・道具                          | 動詞                   | 対象                                                       |
| ----------------------------------- | ---------------------- | ---------------------------------------------------------- |
| `Read`                              | 読んでいる             | 要約の欄（`file_path`）                                    |
| `Grep`・`Glob`                      | 探している             | 要約の欄                                                   |
| `Edit`・`MultiEdit`・`NotebookEdit` | 書き換えている         | 要約の欄                                                   |
| `Write`                             | 書いている             | 要約の欄                                                   |
| `Bash`                              | コマンドを走らせている | 要約の欄（`command`）                                      |
| `Agent`・`Task`                     | 委譲先に任せている     | 役（`subagent_type`）と、手順の説明（`description`）       |
| ワークフロースクリプトの agent      | 委譲先に任せている     | 段の題（`WorkflowProgress` の `phaseTitle`）               |
| `WebFetch`・`WebSearch`             | 調べている             | 要約の欄                                                   |
| 上に無い道具（MCP の道具を含む）    | 道具を使っている       | 道具の名前（等幅）                                         |
| `report` を書いている途中           | レポートを書いている   | なし                                                       |
| 走っている道具が無い                | 考えている             | なし（依頼が会話の片付けなら「会話を片付けている」のまま） |
| API の再試行中                      | もう一度試している     | 「API の応答待ち · n回目」（`ApiTrouble` の `attempt`）    |

- 対象の字は今の要約（`summarizeToolInput`）をそのまま使い、全文は出さない（会話内容の扱い）。経過は今の秒の数え方（`formatElapsed`）のまま。
- バックグラウンドタスクの手順は、動詞の前に「背景で」を添える（「背景で コマンドを走らせている」）。
- 委譲先の役は1行に収める。役ごとに行を増やさない（同時に走る委譲先が2つ以上でも、今と同じ「いちばん新しく手順が始まったもの」1つ）。
- **長く掛かっているときの添え書き**: 同じ状態が 120 秒を超えたら、回る印を遅くして「長く掛かっている」を添える。委譲先に任せている状態には付けない（委譲は長く掛かるのがふつうで、止まって見える判断は委譲先の中の手順でする）。しきい値は書き手の判断（見本は 12 秒・40 秒に付けず、4 分 12 秒に付けている）。定数は動詞の表と同じ1か所に置く。
- 答え待ちのあいだは、今と同じくいまの行を出さない（お伺いが流れの末尾にある）。
- 後回しのまま残すもの: 見込みの時間・やり直しの周と計画を直した理由・前回との対応・置いた前提・背面のときの通知と音。
- 該当する見本: `states.html`「末尾の行は、していること・対象・経過を言う」「もう一度試しているとき」。

### 論点 4: いまの一言と尾

**採る: いまの一言は、いちばん新しいやり取りが作業中か答え待ちのあいだ、そのやり取りのいちばん新しいセリフ1件にする。その1件だけを明るくして、左下（立ち絵の側）へ向けた尾を付ける。すぐ下に全幅の物（お伺い・紙・失敗の表示）が続くときは尾を出さない。やり取りが完了・失敗・中断で終わったら、いまの一言は無くなる。この規則は仕事の流れだけに当て、雑談の流れには当てない。**

- 立ち絵の表情はいまと同じく最新のセリフに従うので、いまの一言は立ち絵が従っているセリフと一致する。
- 尾は吹き出しの形の一部で、セリフ以外の行（いまの行・札）には付けない（キャラクターが話したものだけを吹き出しの形にする）。
- 雑談に当てないのは書き手の判断。行の部品は雑談と共用だが、雑談の流れは「作業中」を持たず、いつ明るさを外すかの決まりが別に要る。あとで雑談にも広げられる（部品に明るさと尾の有無を渡す形にしておく）。
- 話し手の見分け: セリフは差し色の面と縁、投稿は色味の無い面にし、読み上げ用に話し手の名前（キャラクターの名前・「あなた」）を見えない字で持つ。
- 該当する見本: `index.html?form=goal&moment=work`・`moment=ask`。
- この論点は ADR 0063 論点 1・3 が上書きした（いまの一言に声の定位置を含め、尾は立ち絵が従っているセリフ1件に付けて顔へ向ける）。

### 論点 5: 時刻

**採る: 時刻は、時刻を持つ行のうち、直前に時刻を出した行と分（`HH:MM`）が変わった行だけに出す。省いた行の時刻は、見える字としては行に触れるかフォーカスが行の中にあるときだけ出し、読み上げには常に渡す（見えない字の `<time>`）。省いた行の分は、上にあるいちばん近い出した時刻と同じなので、キーで読む専用の経路は足さない。**

- 時刻を持たない記録（`detail`・`question`）と `restored` は、今と同じく時刻を出さず、分の比べにも数えない。
- この規則は仕事の流れだけに当てる。雑談の流れは日の区切りと今の時刻の出し方のまま（論点 4 と同じ書き手の判断）。
- **見本と違う**: 見本の指摘は「省いた時刻をキーで読む経路が無い」だった。省いた行の時刻は分まで上の行と同じで、読めなくなるのは無い情報（秒）だけなので、新しいキーは足さない（書き手の判断。足すなら論点 8 のキーの表に1行足せばよい）。
- 該当する見本: `index.html?form=goal`（`stampOf`）。

### 論点 6: お伺い

**採る: お伺いの頭は、種類（質問・許可）・題（質問の `header`、許可は道具の名前）・待ち時間・「広げる」の4つにする。「お伺い」のチップは外し、「n / N」は2問以上のときだけ出す。カードの中の印は2系統にする。状態の印（確かめた・戻せない）は塗り、中立の印（写した・おすすめ・確度 高/中/低）は線だけにする。「任せる」は「おすすめに任せる（<選ばれる案の名前>）」と言い、おすすめが無いときは「任せる（戻せる案から選ぶ）」と言う。おすすめが戻せない案のときは「任せる」を出さない。戻せない選択肢を選んだときだけ確定を2段にし、2段目の確定は ⇧⏎ かクリックで行い、⏎ だけでは確定しない。**

- ADR 0058 の「お伺いの中身は変えない」は、頭の項目・印の系統・「任せる」の言い方・戻せない選択肢の確定・答えたあとの形（論点 7）の範囲で改める。本文の並び（問い → 添え書き → 選択肢 → 詳細 → 操作）・2列にする条件・広げた板・狭い画面の答え待ちのカードは変えない。
- 2段目の表示: 操作の行の左に「戻せない操作。⏎ だけでは確定しない」を出し、確定の口を「これで確定する ⇧⏎」に替える。選択を戻せる案に替えたら1段目に戻る。
- 確度の色（高は `ok`・低は `warn`）は外し、字だけにする。確度は書き手の自信の申告で、状態ではない。
- 「任せる」が選ばれる案を言うのは、SDK へ返す文（`pending-answer.ts`）が選ぶ規則と同じ規則で画面が先に名指すため。おすすめの無い問は、どの案が選ばれるかを画面が知らないので名指さない。
- 書いて答えられることの案内は、入力欄の上の1行だけにする（カードの中には置かない）。
- 狭い画面: 答え待ちのカードは変えない。「詳しく」のボトムシートは同じ部品で中身を描くので、頭の項目と印の系統はそこにも及ぶ（書き手の判断。器の形は変えない）。
- 該当する見本: `index.html?form=goal&moment=ask`、`states.html`「質問が2問のとき」「戻せない選択肢は、確定を2段にする」「許可のお伺い」。

### 論点 7: 回答

**採る: 答えた質問は、聞いたセリフと組になる「聞いた1行」（質問の記録。印・題・問い、その下に「聞いたときの詳細」の開閉）と、利用者の投稿にする。投稿は右寄せで、札に「答え」（選んだ・書いた）か「任せた」を出し、本文は選んだ案の名前か書いた字。2問以上なら1問1行で「題: 答え」と並べる。いちばん新しいやり取りの、いちばん新しい答えの投稿にだけ「答え直す」を付ける。押すと、訂正の補足の下書き（「（答え直し）<題>: 」）が入力欄に入り、送らない。入力欄に字があるときは消さずに末尾に改行して足す。**

- 答えの中身は記録の `question`（`answers`）にあるので導ける。`question` は時刻を持たないので、投稿にも時刻を出さない。
- 許可の答えは今と同じく流れに残さない。
- 「答え直す」は作業中のやり取りに補足（`aside`）として届く。完了後に押したときは、ふつうの依頼として届く（送り先の決まりは入力欄のまま）。
- 該当する見本: `index.html?form=goal&moment=late`、`states.html`「答えは、利用者の投稿として残る」。

### 論点 8: キー

**採る: 待っている用件（お伺いの選択肢・お願い）があり、入力欄が空でフォーカスが入力欄にあるとき、↑ でその用件の最初の押せる所（お伺いなら選んでいる選択肢か最初の選択肢、お願いなら次の一手の最初の口）へ移る。用件の中で Esc を押すと入力欄へ戻る（広げた板の中では、Esc はまず板を閉じる）。入力欄の上の1行の口は「選択肢へ」「お願いへ」の字に、キーの印 ↑ を添えるだけにし、条件（入力欄が空のとき）は口の外、口のツールチップと `aria-description` に置く。数字のキーが効かないあいだ（フォーカスが用件の外）は、選択肢の数字のキーの印を破線の枠だけにし、フォーカスが入ると実線の枠にする（字の濃さは下げない）。**

- ↑ の移る先は ADR 0068 論点 7 が置き換えた（お伺い → 入力欄の頭の次の一手の並び → お願いの欄の最初の押せる所）。
- 空の入力欄の ↑ は、今は何にも使っていない（候補の一覧の ↑ は、候補が出ているときだけ効く。`useSuggestion` の `onKeyDown`）。字があるときの ↑ はカーソルの移動のまま。
- **見本と違う**: 見本は口の中に「入力欄が空のとき」の字を置き、クリックにも条件があるように読める。口を押す操作に条件は無いので、条件はキーの説明の側へ移す。見本には入力欄へ戻るキーも無かった。
- キーの手掛かりを見える形で置く所: やり取りの列の頭（`[` `]`）・最終レポートの見出しの並びの頭（`{` `}`）・選択肢（数字）・入力欄の上の口（↑）。
- 上へ送って読んでいるあいだは、流れの下端に「末尾へ」の口を、まだ見ていない新しい行の件数つきで出す（見本の `&up=1`。ADR 0058 の流れの下端の口と同じもの）。
- 該当する見本: `index.html?form=goal&moment=ask`・`moment=read`。

### 論点 9: 開閉の表現

**採る: 流れの中で開いて閉じるもの（作業の経過・聞いたときの詳細）と、進行の帯の「手順」は、右向きの山形の印1種にし、開くと下向きに回す。字は「作業の経過　4フェーズ・6分40秒・セリフ 6件・質問 1件」のように、何がいくつあるかを言う。画面いっぱいの板に開く「広げる」は開閉とは別の操作として、印と字の1つの形（お伺いの頭・紙の右上で同じ部品）にそろえる。レポートの中の部品の畳み（内容部品）は、この ADR では変えない。**

- 下線のリンク（「聞いたときの詳細」）と畳みの印と帯の山形の3種をやめる。
- 失敗の表示の詳細は開かずに読めるようにする（論点 10）ので、開閉を持たない。
- レポートの中を外したのは書き手の判断。部品は減らさない決定（ADR 0039）と、内容部品の見た目は器の ADR が持つため。あとで同じ印にそろえられる。
- 該当する見本: `states.html`「開閉の表現は1種」。

### 論点 10: 失敗と中断

**採る: 失敗の表示は、失敗を言うセリフと組にし（論点 1。セリフが無ければ1つで置く）、理由・詳細・残ったもの・次の操作の4つを開かずに出す。利用者が止めたやり取りには、どこで止めたかと残ったものと次の操作を出す。再試行中は、いまの行が「もう一度試している」と回数を言う（論点 3）。**

| 項目       | 出すもの                                                     | 出どころ                                              |
| ---------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| 理由       | 今の語（`turnFailureLabel`）                                 | `turn-failure` の記録                                 |
| 詳細       | 今 `title` にだけある全文（`turnFailureDetail`）を見える字で | 同じ記録。試した回数は、最新のやり取りの `ApiTrouble` |
| 残ったもの | 済んだフェーズ「n/N」と、書き換えたファイルの数と1件の名前   | 最後の `work-plan` と、成功した `Edit`・`Write` 系    |
| 次の操作   | 今の「同じ依頼を入力欄に戻す」と「失敗した手順を見る」       | 今のまま                                              |

- 止めたやり取りは「止めた」と、止めたフェーズ「n/N 名前」・残ったもの・「続きを頼む文を入力欄に入れる」（送らない）・「手順を見る」を出す。
- 中断は今の記録に残らない（`turn-failure` は `failed` のときだけ積み、`interrupted` は `TurnProgress` の `ended` に畳まれて完了と見分けられない）。止めたやり取りを過去に遡っても見分けられるよう、`turn-failure` と同じ位置に中断の記録を1つ積む。記録の形が変わるので `PROTOCOL_VERSION` を上げる。
- 書き換えたファイルは名前を1件だけ出し、全部は「手順を見る」の一覧で読む。
- 失敗の表示の置き場は、今の「最初の本文の手前」（`withFailure`）をやめ、`turn-failure` の記録の位置（やり取りの末尾）にする。
- 該当する見本: `index.html?form=goal&moment=fail`、`states.html`「失敗で終わったとき」「利用者が止めたとき」「もう一度試しているとき」。

### 論点 11: レポートの中

**採る: 冒頭の検証は、まとめの1行を字で言い（「確かめたこと n件」「通った a・確かめていない b」「単体 …・E2E …」）、状態の印は行ごとの1個だけにする。「記録あり・n回」「申告のみ」は線の印（中立）にする。ADR 0060 論点 5 の「目盛りを並べた帯の1行」は採らず、主張ごとの印と控え・やっていないことの欄・入力の欄（`supports`・`notDone`）はそのまま残す。お願いは、見出し「お願い」のまま題と本文の字を大きくする。「確かめた・違った」は次の一手の行に置き、行の末尾に「押すと、入力欄に下書きが入る（送らない）」を添える。**

- 目盛りの帯を外すのは見本が勝つため（見本の冒頭は字のまとめと行ごとの印で、帯を描いていない）。帯は色と形（背の高さ・中抜き・破線）で状態を言い分ける部品で、行ごとの印と同じことを2か所で言う。
- 「確かめた・違った」を次の一手の行に置くのは ADR 0060 論点 7 と同じ。押しても送らないのは ADR 0051 のまま。
- 狭い画面: 紙の中身は同じ部品なので、この論点の形は狭い画面の紙にも及ぶ（書き手の判断。器の形は変えない）。
- 該当する見本: `index.html?form=goal&moment=read&at=end`。

### 論点 12: 初回だけの説明

**採る: 「確かめた」「確度」（お伺い）と「記録あり」「申告のみ」（レポート）の語の説明と、余白の書き添えの案内は、その語や部品が初めて出たときだけ、面の下端に1行の「初回の説明」として出す。行の右端の「分かった」を押すと、その説明は次から出ない。押したことは端末の好み（`local-preference`）に説明ごとに残す。消したあとも、印そのものにツールチップと `aria-description` で同じ説明を持たせ、歯車の「見た目」に「初回の説明をもう一度出す」を置く。**

- ADR 0055 論点 2 の書き添え（レポートで最初に指せる単位の横の余白に「字・行・案を選ぶと、ここに「聞く・頼む」が1つ出る」）は、この初回の説明に置き換える。書き添えは「そのレポートでまだ一度も指していない」あいだ毎回出ていたが、初回の説明は端末で一度だけ出る。余白のある幅でも無い幅でも同じ1行で、狭い幅でも案内が届く。
- 余白の書き添えの案内も、一度指したら「分かった」を押したのと同じに扱う（使えた人に案内を出し続けない）。
- 歯車に戻す口を置くのは書き手の判断（読み返す手段として、印のツールチップだけでは「余白を選べる」ことの案内が戻らないため）。
- 該当する見本: `states.html`「状態の語の説明は、初回だけ出す」「レポートの中の語と、余白の書き添えの案内も初回だけ」。
- 余白の案内を出す本文は、ADR 0064 論点 2 が、指して聞ける本文だけに絞った（書いている途中の草稿には出さない。2026-11-18）。
- 余白の案内は、ADR 0067 論点 1 が聞く・頼むと一緒に取り下げた。初回の説明は語の説明の2つだけになる（2026-11-18）。

### 論点 13: 幅

> この論点の「✓n」のまとめと帯の右端の「手順 n件」は、ADR 0070 論点 4・8 が上書きした。読む幅の上限と左寄せは変わらない（2026-11-18）。

**採る: 広い画面では、会話の流れ・入力欄・進行の帯の読む幅に上限を置く（見本の 960px。帯と入力欄は縁を含めて 976px）。上限は中央の列の中で左に寄せる。流れは進行の帯の下から始め、送っても行が帯の裏へ潜らない。フェーズが9つ以上で今のフェーズが3つ目より後ろなら、済んだ丸を「✓n」の1つにまとめ、今のフェーズの名前の幅を残す。帯の右端は「手順 n件」と、何の数かを言う。761〜1100px は ADR 0058 論点 6 の形のままで、中央の列が 960px より狭いので上限は効かない。**

- 上限を中央寄せにしないのは見本のとおり（`goal.css` の `inset-inline-end: auto`）。左の列の立ち絵と流れの距離が幅で変わらない。
- 該当する見本: `index.html?form=goal`、`states.html`「フェーズが12あるときの進行の帯」。

### 論点 14: 送る順と、既存の ADR・文書の改め方

**採る: 既存の ADR は論点ごとに上書きし、全体の置き換えはしない。上書きされた論点には、この ADR を指す1行を足す（本文は書き換えない）。画面の設計文書（`docs/architecture/screen-design/`）と表示物の文書（`docs/architecture/display/`）は、実装のそれぞれの段が自分の触った節を同じコミットで書き換える。送る順は下の「送る順」。**

- 置き換えにしないのは、ADR 0058・0059・0060 の大半（器・帯・離席の境目・タブの題・主の図・色・お願いの札）がこの ADR と食い違わず、生きているため。

## 送る順

1件送るごとに画面が使える状態を保つ。見本どおりの段（済んだフェーズのまとめを `work_plan` の記録の位置に出す・完了後はセリフも畳む・流れを入力欄の側へ寄せる・答え待ちの琥珀の枠を外す・依頼の字・紙の面）は、この ADR を待たずに先に送れる。

1. **組と行の間。** 隣り合う物とセリフを記録の位置で1組にし、行の間を3段にし、済んだフェーズの札の幅をそろえる（論点 1）。済んだフェーズのまとめの位置と、完了後の畳みが入ったあとに送る。
2. **いまの行の文。** 動詞の表・知らない道具・委譲先の役・再試行・長く掛かっているときの添え書き（論点 3）。
3. **締めのセリフと紙。** 締めを紙の上に置き、書いているあいだは場所を押さえる（論点 2）。1 と 2 のあとに送る。
4. **お伺いの頭と印。** 頭の4項目・印の2系統（論点 6 の前半）。
5. **「任せる」と2段の確定。** 選ばれる案の名前・戻せない選択肢の2段（論点 6 の後半）。4 のあとに送る。
6. **回答の形。** 聞いた1行と投稿・「答え直す」（論点 7）。1 のあとに送る。
7. **失敗と中断。** 4つの項目・中断の記録・再試行の形（論点 10）。中断の記録は記録の形を変えるので `PROTOCOL_VERSION` を上げ、表示とは分けて先に送る（共有の型とサーバの段）。再試行の形は 2 が持つ。
8. **レポートの中。** 検証のまとめの字・印1個・お願いの重さ・次の一手の案内（論点 11）。
9. **いまの一言と時刻。** 明るさと尾・話し手の名前・分が変わった行だけの時刻（論点 4・5）。1 のあとに送る。
10. **開閉の印。** 山形の1種と「広げる」の形（論点 9）。1 と 6 のあとに送る。
11. **キー。** 空の入力欄の ↑・Esc で戻る・キーの手掛かり（論点 8）。4 と、答え待ちの琥珀の枠を外す段のあとに送る。
12. **初回の説明。** 説明の1行・端末の好み・歯車の戻す口・余白の書き添えの置き換え（論点 12）。4 と 8 のあとに送る。
13. **幅。** 読む幅の上限・帯の下から始める流れ・9つ以上のフェーズの帯（論点 13）。流れを入力欄の側へ寄せる段のあとに送る。
