# レポートと進み具合の契約: 1枚の紙・確かさの台帳・判定・次の手（2026-11-13）

ステータス: 採用

**`work_plan`・中間レポート・`report` を、依頼1つにつき1枚の紙の上の1つの時系列として描く。紙の項目は tsukumo が出来事から組み、書き手には「判定」「次の手」「置いた前提」「出どころ」「前回との対応」「案内の付箋」と、計画を直した理由・やり直しの理由だけを書き足させる。`checks` と `Claims` の未確認の主張は「確かさの台帳」1か所に集め、行ごとに tsukumo が「記録あり（実行）」「記録あり（控え）」「申告のみ」を付ける。欄を足しても差し戻す条は増やさない。**

この ADR は、紙の形と、書き手の道具（`report`・`work_plan`・`phase_result`）の欄と、tsukumo が自分で作るものとの線を決める。見た目の寸法・色・字の大きさは決めない（見本と、器・トークンの ADR が持つ）。

## 何が困っていたか

- 進み具合（プログレスバーと中間レポート）と結果（`report`）は、別々の器に描かれている。働いているあいだに見た計画と、終わってから読む報告とが、画面の上でつながらない。
- `report` は、検証の結果（`checks`）を頭に描き、未確認の主張（`Claims`）を節の中に描き、利用者がすること（`favor`）と次の一手を末尾に描く。確かさが2か所に分かれ、利用者の番であることが末尾まで読まないと分からない。
- 前回のレポートと比べて見る手段が無い。2回目のレポートで、直ったこと・新しく出たこと・残っていることが分からない。
- 検証の行が機械の裏を取ったものか、書き手の申告だけかを、画面で見分けられない（裏取りは `checks[].command` と打った Bash との突き合わせ、ADR 0046 の検証の控えの2つがあるが、印が無い）。
- 委譲先の進みの要約はサーバに届いているが、`src/shared/session/session-event-delegate.ts` の `delegate-progress` の説明のとおりブラウザへ渡していない。委譲中の画面は「背景で · 考えている」のままになる。
- `report` の名前つきの検査は 57 条ある（`src/server/report/core/rules/rejection-mode.ts` の `REPORT_REJECTION_MODES`。表の項目を数えると、値が `"reject"` のもの（`resend` を含む）が 42、`"count"` のものが 15）。欄を足すたびに差し戻しが増えれば、書き手の手戻りが増える。

## 利用者が決めたこと

- 見本は `docs/history/mockup/report-progress-2026-11-12/index.html`（紙の4場面・部品の6族・進み具合の9状態）。言葉の説明と見本が食い違ったら見本が勝つ。
- 2026-11-13 に見直し案を了承した。今のレポートの記法の決まりと画面のデザインの文書に縛られずに作り直してよい。
- 部品の種類は減らさない（表現力は残す）。
- 進み具合を百分率で出さない。経過はいつも出し、見込みは記録があるときだけ出す。
- 会話内容の扱いの規約（`docs/coding-standards/conversation-content.md`）は、ほかのどの決まりよりも優先する。

## 決めたこと

### 論点 1: 1枚の紙のモデル

**採る: 依頼1つにつき紙1枚。紙は「頭（判定の行・結論・あなたの番）」「計画（段の並びと、段ごとの時系列の項目）」「本文（レポートの節）」の3つでできる。働くあいだは頭と計画だけがあり、`report` が届くと本文が入り、計画は紙の末尾の「この結論に至った道筋」になる。**

- 紙はブラウザの画面の状態（`SessionState`）の中で、今と同じ出来事から組む。紙を保存するファイルは作らない。開き直したときは今と同じく transcript から組み直す。
- 時系列の項目は次の7種類。どれも tsukumo が出来事から作り、書き手に項目そのものを書かせない。

| 項目         | 出どころ（tsukumo が見る出来事）                                                  | 段が済んだとき                                            |
| ------------ | --------------------------------------------------------------------------------- | --------------------------------------------------------- |
| いま         | 今の道具の呼び出し（論点 5 の実況の文）                                           | 畳む（段のまとめの1行に置き換わる）                       |
| できた       | `Edit`・`Write` が触ったファイルと、段を閉じたときの変更の量（git の差分）        | 残す                                                      |
| 任せた       | 背景のサブエージェント・ワークフロースクリプトの顔ぶれと、その進みの1行（論点 6） | 畳む（委譲先の `phase_result` の `summary` に置き換わる） |
| あなた       | 作業中に届いた補足メッセージと、それを受けた書き手の返事のセリフ                  | 残す                                                      |
| 計画を直した | `work_plan` の並びが変わった呼び出しと、その理由（論点 4 の `replanReason`）      | 残す                                                      |
| 問い         | お伺い（許可・質問）と、利用者の答え                                              | 残す（答えと対で）                                        |
| 失敗         | 道具の失敗で段が止まったこと・ターンの失敗                                        | 残す                                                      |

- 段が済むと、段の行は「名前・所要・まとめ（`phaseSummary` か `phase_result` の `summary`）・変更の量」の1行になる。残す項目は、段の行を開くと見える。
- 段が多い計画は、済んだ段をまとめて1行に畳み、今の段とこれからの段だけを開く（見本の「長い作業」）。
- 道具の呼び出しの全件（生の記録）は紙に並べない。道筋の段を開くと今の手順の一覧が出る。

| 案                                                             | 種類   | 物差し                                                                                       | 判定     |
| -------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------- | -------- |
| 紙を画面の状態の中で出来事から組み、計画を末尾の道筋に変える   | 仕組み | 新しい保存先が要らず、開き直しも今の組み直しの道に乗る。計画と報告が同じ並びでつながる       | 採る     |
| 中間レポートを今のまま別の器に残し、最終レポートだけを紙にする | 仕組み | 働くあいだと終わったあとで見る場所が変わり、見本の「計画はそのまま末尾の道筋になる」に反する | 採らない |
| 時系列の項目を書き手に `report` の欄で書かせる                 | 手書き | 書き手が書き忘れると項目が黙って欠ける。tsukumo がすでに見ている出来事を二重に書かせる       | 採らない |

### 論点 2: `report` に足す欄と、今の欄との関係

**採る: `Report` の根に、次の6つの欄を足す。どれも省ける。古い欄は読み替えて受け続ける。**

| 欄            | 形                                                                                                                                                             | 描く場所                           |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `verdict`     | `done`（済んだ）・`partial`（一部済んだ）・`yours`（あなたの番）・`stopped`（止めた）・`failed`（失敗で止まった）                                              | 紙の頭の判定の行                   |
| `next`        | `{ owner, action, choices? }`。`owner` は `you`（利用者が動く）・`writer`（書き手が続ける）・`none`。`action` は1文。`choices` は選べる答えの短い語（3つまで） | 判定の行の直後の「あなたの番」     |
| `assumptions` | 置いた前提の文の配列（1要素1文。なぜ置いたかを含める）                                                                                                         | 本文の「置いた前提」               |
| `sources`     | `{ mark, place, note? }` の配列。`mark` は 1 から始まる番号、`place` は `path:line` か一次情報の名前                                                           | 本文の文末の番号と、同じ高さの欄外 |
| `previous`    | `{ resolved, added, remaining }`（それぞれ短い文の配列）                                                                                                       | 結論の直後の「前回から」           |
| `guideNotes`  | `{ target, text }` の配列。`target` は部品の ID か欄の名前（`checks` など）、`text` はキャラクターの口調の1文                                                  | 指した所の横の欄外                 |

- **出どころの番号は、行内の印 `{{src: 1}}` で本文の文末に置く。** 今の行内の印（`src/shared/report/inline-mark.ts` の `{{…}}`）の並びに1種類足す。番号に触れると、今のファイルの覗きで `place` の前後が開く。
- **`guideNotes` は ADR 0051 の「付箋」（利用者が「頼む」で積むもの）と別のもの。** 名前を「案内の付箋」とし、識別子も分ける。欄外は ADR 0055 の札と共有し、同じ高さでは案内の付箋を上に、聞く・頼むの札をその下に積む。
- **前回との対応は書き手が申告する。** tsukumo は前回のレポートの行と今回の行を機械で結ばない（ADR 0051 の「付箋と次のレポートの答えは機械で結ばない」と同じ線）。前のレポートが同じセッションに無いのに `previous` があれば、数えるだけの条に当てる（論点 8）。
- **短い答え・判断を仰ぐ紙でも同じ欄を使う。** 形の選び方は論点 7。

今の欄との関係は次のとおり。

| 今の欄                          | 扱い                     | 新しい形                                                                                                              |
| ------------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `task.outcome`                  | 読み替える               | `finished` → `done`、`stopped` → `stopped`、`awaiting-answer` → `yours`。`verdict` があれば `verdict` が勝つ          |
| `favor`                         | 読み替える               | `next` の `{ owner: "you", action: <favor の字> }`。`next` があれば `next` が勝つ                                     |
| `workPlanClosing`               | 残す（導けるなら省ける） | `verdict` が `done`・`partial` なら `finished`、それ以外なら `stopped` として読む。両方あって食い違えば数えるだけの条 |
| `checks`                        | 残す                     | 形は変えない。確かさの台帳の材料になる（論点 3）                                                                      |
| `Claims`（部品）                | 残す                     | 部品はそのまま置ける。確定でない主張は台帳の「確かめていない」にも並ぶ（論点 3）                                      |
| 次の一手（ADR 0051 論点 6）     | 残す                     | 作り方は変えない。出す場所を、紙の頭の「あなたの番」の下の「続けて頼めること」に移す                                  |
| `task`（`id`・`name`・`genre`） | 残す                     | 判定の行の頭の材料のまま                                                                                              |

- `verdict` も `task.outcome` も無いレポートは `done` として読む。タスクに紐付かない依頼も `verdict` を書ける。
- tsukumo 自身が決まる判定は書き手に書かせない。利用者が止めたとき（中断）とターンが失敗したときは、`report` が届かなくても tsukumo が「あなたが止めた」「失敗で止まった」を出す。書き手の `stopped`・`failed` は、書き手が自分で止めた・検証が落ちて止めたときに使う。
- 読み替えはサーバの1か所（`report` の入力を受けて画面の状態へ写す手前）に封じ、ブラウザは新しい形だけを読む。

| 案                                                              | 種類     | 物差し                                                                                           | 判定     |
| --------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------ | -------- |
| 根に省ける欄を足し、古い欄を1か所で読み替える                   | 仕組み   | 古い呼び出しも transcript の読み戻しもそのまま通る。描く側は1つの形だけを知ればよい              | 採る     |
| `task.outcome` の値を増やして判定にする                         | 仕組み   | タスクに紐付かない依頼で判定を書けない。`task` の有無で紙の頭の形が割れる                        | 採らない |
| 前回との対応を、前のレポートの台帳の行と tsukumo が機械で照らす | 推し量り | 行の文が変わると結べず、結び違えると「解決」と誤って出る                                         | 採らない |
| 案内の付箋を ADR 0051 の付箋と同じ store に入れる               | 仕組み   | 利用者が積んだ頼みごとと、キャラクターが差した案内が混ざり、「まとめて頼む」の下書きに案内が入る | 採らない |

### 論点 3: 確かさの台帳と「記録あり」「申告のみ」

**採る: 紙の「確かさ」は1つの台帳にする。行の材料は `checks` の全行と、`Claims` の確定でない主張。並びは「落ちた（`ng`）」→「確かめていない（`unobserved`・`blocked`・確定でない主張）」→「確かめた（`ok`）」で、確かめた行は1行に畳む。行ごとの裏取りの印は tsukumo が付け、書き手に申告させない。**

| 印               | 付ける条件                                                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 記録あり（実行） | 行の `command` が、同じ依頼のあいだに tsukumo が見た Bash の呼び出し（メインと、委譲先の中で見えたもの）と完全一致し、その呼び出しの終わり方が行の状態と食い違わない |
| 記録あり（控え） | 行が検証の段に当たり、ADR 0046 の検証の控えの段として木の SHA が合った（控えの段の成否と件数を行に添える）                                                           |
| 申告のみ         | 上のどちらにも当たらない行。`command` が空の行（目で見た確かめなど）と、確定でない主張はいつもここ                                                                   |

- 画面では、2つの「記録あり」をどちらも「記録あり」と書き、行を開くと「打った Bash と照らした」か「検証の控えと照らした」かを出す。
- 突き合わせの範囲は、今の「同じターン」から「同じ依頼」に広げる。背景のワークフローは依頼の中でターンをまたぐため。
- `ok` の行の `command` が実行の記録と食い違う（打っていない・失敗で終わった）ときは、今の `unrun-check-command` と同じく数えるだけの条に当てる。差し戻さない。
- `Claims` の部品は節の中にそのまま描く。台帳の「確かめていない」の行は、その主張の置き場所へ跳べるようにする。同じ主張を台帳に全文で二重に描かない（台帳の行は主張の1文目と確かめ方だけ）。
- 紙の頭の数（✕1 ?1 ✓4 の並び）は台帳の3つの群の件数から数える。

| 案                                                           | 種類   | 物差し                                                                                                   | 判定     |
| ------------------------------------------------------------ | ------ | -------------------------------------------------------------------------------------------------------- | -------- |
| tsukumo が実行と控えの記録から印を付け、書き手は申告しない   | 仕組み | 印が書き手の言葉に頼らない。どちらの裏取りかを行ごとに言える                                             | 採る     |
| 書き手に `seal`（記録あり・申告のみ）を書かせる              | 手書き | 書き手が「記録あり」と書けば裏が無くても出る。機械の裏取りという印の意味が崩れる                         | 採らない |
| `checks` と `Claims` を1つの新しい欄 `ledger` に書き直させる | 手書き | 古い呼び出しの読み替えが2本になり、`Claims` を節の中に置く表現が消える（部品を減らさない決まりに反する） | 採らない |

### 論点 4: `work_plan` と `phase_result` に足す欄

**採る: `work_plan` に `replanReason`・`redoReason`・段の `doing`・`assumptions` を足し、`phase_result` の `outcome` に `redo` を足す。周の番号は tsukumo が数え、書き手に番号を書かせない。**

| 道具           | 欄                         | 形と意味                                                                                                           |
| -------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `work_plan`    | `replanReason`             | 並び（`phases`）を前の呼び出しから変えた呼び出しで、変えた理由を1文で。紙の「計画を直した」の項目になる            |
| `work_plan`    | `redoReason`               | `current` を済んだ段へ戻した呼び出しで、やり直す理由を1文で（「差し戻し ― 指摘 3 件」など）。戻した段の周が1つ進む |
| `work_plan`    | 段の `{ id, name, doing }` | 今の `{ id, name }` に、進行形の名前 `doing`（「表示の層を直している」）を足す。省くと今の段も `name` のまま出す   |
| `work_plan`    | `assumptions`              | ここまでに置いた前提の文の配列。`skippedPhases` と同じく、毎回それまでの全部を渡す。離れていたあいだのまとめに出す |
| `phase_result` | `outcome: "redo"`          | 委譲先の段（受け入れなど）が差し戻されて同じ段をもう1周する。`reason` に理由を1文で。段は済まず、周が1つ進む       |

- **周は段の中に積み、段を増やさない。** 紙の段の行に「2周目」と出し、周ごとの所要と理由を段の中に並べる（見本の「流れと周回」）。
- **進行形の名前は書き手が渡す。** tsukumo が辞書形から活用を作ると、五段と一段の見分けを推し量ることになる（「帰る」と「調べる」）。渡されなければ名前のまま出す。
- 委譲の範囲の数え方・並列の段・飛ばした段の決まりは変えない。

| 案                                                                       | 種類     | 物差し                                                                                      | 判定     |
| ------------------------------------------------------------------------ | -------- | ------------------------------------------------------------------------------------------- | -------- |
| 周の番号は tsukumo が戻した回数・`redo` の回数から数え、理由だけ書かせる | 仕組み   | 番号の書き違いが起きない。メインの `work_plan` と委譲先の `phase_result` のどちらからも進む | 採る     |
| 書き手に `round: 2` のような周の番号を書かせる                           | 手書き   | 番号と実際の戻りが食い違ったときに、どちらを信じるかの決まりが要る                          | 採らない |
| 段の進行形を tsukumo が辞書形の語尾から作る                              | 推し量り | 五段と一段の動詞を語尾だけで見分けられない                                                  | 採らない |
| 差し戻しのたびに新しい段を足す                                           | 仕組み   | 段の数が増え続け、見本の「工程は増やさず、差し戻しは周として同じ工程の中に積む」に反する    | 採らない |

### 論点 5: tsukumo が作るもの（書き手に書かせないもの）

**採る: 実況の文・見込みの時間と「いつもは」の幅・離れていたあいだのまとめ・止まって見えるときの言い方は、tsukumo が作る。書き手は書かない。**

- 実況の文は、今の道具の名前と入力の欄1つから、動詞＋対象の文（「`bar-chart.tsx` を直している」）を表で作る。入力の中身を出す範囲は今の1行と同じにし、広げない。表に無い道具は今の出し方のまま。
  - 範囲（「6 個のうち 4 個目」）は、tsukumo が数えられるもの（並列の段の中の何個目・委譲先の段の番号）だけから添える。書き手の頭の中にしか無い数は、段の `doing` に書き手が書く（論点 4）。
- 見込みの時間と「いつもは」の幅は、手元の記録（件数と秒数だけ。`src/shared/usage/experience-metric-record.ts` と同じく、会話の中身を入れない）から出す。似た作業が足りないとき、見込みも幅も出さず経過だけを出す。百分率は出さない。何を「似た作業」とし、何件から出すかは、記録を数えてから見込みの後段で決める。
- 離れていたあいだのまとめは、ページが見えなくなった時点を「前に見た位置」として覚え、戻ったときに、そこから後の項目（済んだ段・できた・計画を直した・問い）と、`work_plan` の `assumptions` を紙の頭に並べる。前に見た位置はタブのメモリだけに持ち、保存しない。
  - 「離れていた」は、ページが見えなかった時間（`visibilitychange` で隠れてから表に戻るまで）が 3 分以上のときだけ（Claude Code の session recap と同じ値）。ページが見えているのに読んでいないときは、入力や視線を測る手が無く推し量りになるので扱わない。
  - 前に見た位置は、隠れた時点で今の依頼の `work-plan` の記録を何件持っていたかで決める。サーバの時刻とブラウザの時計を比べない。開き直したタブには隠れた記録が無いので出さず、依頼が替わった（最初の記録が隠れた時点と違う）ときも出さない。
  - まとめと印は、戻ったあとの最初の操作（クリック・キー）まで出し、その操作で両方とも畳む。時間では畳まない（離れているあいだに消えると意味が無い）。
- 止まって見えるときは、新しい出来事が無い時間を数え、待ち（背景の検査など）・再試・利用の上限・動かない（いつもの幅を大きく超えた）の4つの言い方を tsukumo の固定の文で出す。
- 知らせは、出来事を「気配」「一目」「割り込み」「まとめ」の4段に分ける。割り込み（通知・音・タブの題の「● あなたの番」）に当てるのは、問い（許可・質問）・判定が `yours` か `failed` の `report`・ターンの失敗だけ。済んだ（`done`・`partial`）は「まとめ」の段で、割り込みに出すかは利用者の設定が決める。

| 案                                                    | 種類   | 物差し                                                                | 判定     |
| ----------------------------------------------------- | ------ | --------------------------------------------------------------------- | -------- |
| 実況・見込み・まとめ・止まりの言い方を tsukumo が作る | 仕組み | 書き手の手間と道具の定義の字数が増えない。数の根拠を tsukumo が言える | 採る     |
| 書き手に `speak` や欄で実況と見込みを言わせる         | 手書き | 黙っているあいだは出ない。見込みに根拠が無く、書き手ごとにぶれる      | 採らない |

### 論点 6: 委譲先の進みを、役ごとの1行で画面に出すか

**採る: 出す。委譲先の進みの要約（`delegate-progress` の `summary`）を、紙の「任せた」の項目に役ごとの最新の1行として、ブラウザのメモリにだけ置く。**

会話内容の扱いの規約と照らした結果は次のとおり。

- 規約が禁じるのは、外部に送ること・別の場所に書き出すこと・ログに全文を出すこと・フィクスチャに実物を使うことの4つ。`127.0.0.1` のビューに出すことと、ブラウザ側の画面の状態に持つことは、規約の「会話は tsukumo のプロセスの外へ出さない」の線の内側にある（`docs/coding-standards/conversation-content-read-back-and-boundary.md`）。
- 今「ブラウザには届かない」としているのは `delegate-progress` の設計の決まりで、規約の条ではない。この ADR がその決まりを改める。
- 画面に出すときは、次を守る。
  - 書き出さない。会話のアーカイブ・進行の計測値の記録・診断ログ・ブラウザの永続化（`localStorage` など）に入れない。
  - 保つのは役ごとの最新の1通だけ。委譲先が段を返したら、`phase_result` の `summary` に置き換えて捨てる。
  - 開き直したときは組み直さない（要約は transcript から読み戻す出どころにしない）。
  - 1行は今の道具の1行と同じ長さで切る。
  - 役の名前は、今「背景で 説明」に出している委譲の説明をそのまま使う。
- 差し込み（`ProgressNudge`）でメインへ渡す道は今のまま残す。

| 案                                                              | 種類   | 物差し                                                                             | 判定     |
| --------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------- | -------- |
| メモリにだけ最新の1行を置き、書き出さず、開き直しで組み直さない | 仕組み | 規約の4条に触れない。委譲中の画面が「考えている」だけでなくなる                    | 採る     |
| 今のまま画面に出さない                                          | 仕組み | 委譲中に何をしているかが画面から分からず、見本の「任せた」の行が描けない           | 採らない |
| 要約を画面の状態の記録に畳み、開き直しでも出す                  | 仕組み | 要約を transcript の外から読み戻す道が要り、書き出しの例外の表に行を足すことになる | 採らない |

### 論点 7: 読む深さの3段と、紙の形を誰が決めるか

**採る: 読む深さの3段と紙の形は、tsukumo が欄と出来事から決める。書き手は形を申告しない。**

読む深さは次の3段で、利用者が `d` のキーと紙の頭の切り替えで替える。既定は「本文」で、タブのメモリにだけ覚える。

| 段   | 出すもの                                                                                     |
| ---- | -------------------------------------------------------------------------------------------- |
| 一目 | 判定の行・結論・前回から・あなたの番・続けて頼めること                                       |
| 本文 | 一目に加えて、主要な数・確かさの台帳（確かめた行は畳む）・節・置いた前提・道筋（段の行だけ） |
| 記録 | 本文に加えて、台帳の全行を開いた形・道筋の段を開いた形（残した項目と手順の一覧へのつなぎ）   |

紙の形は次の表を上から順に当てて決める。

| 形           | 当てる条件                                                                    | 出すもの                                                   |
| ------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 失敗・止めた | 判定が `failed`・`stopped`、または tsukumo が中断・失敗を見た                 | 判定の行・あなたの番・残っているもの・台帳・ここまでの道筋 |
| 判断を仰ぐ   | 判定が `yours` で、`next.choices` か `Options` の部品がある                   | 判定の行・勧め・案ごとの「これにする」・比べた点・台帳     |
| 短い答え     | 依頼に `work_plan` が無く、変更が無く、`checks` が無く、節の部品が段落1つ以下 | 判定の行（「答えた」）・答え・出どころ                     |
| 渡す         | 上のどれでもない                                                              | 紙の全部                                                   |

- 2回目のレポートは形を分けない。`previous` があれば、どの形でも結論の直後に「前回から」を出す。
- 「これにする」と「続けて頼めること」は、押すと入力欄に下書きを入れるだけで送らない（ADR 0051 論点 6 と同じ）。

| 案                                                  | 種類   | 物差し                                                                  | 判定     |
| --------------------------------------------------- | ------ | ----------------------------------------------------------------------- | -------- |
| tsukumo が欄と出来事の決まった表で形を選ぶ          | 仕組み | ADR 0038 の「形は決定表が決める」と揃う。書き手が形を書き違える道が無い | 採る     |
| 書き手に `form`（短い答え・判断を仰ぐ）を申告させる | 手書き | 欄が1つ増え、申告と中身の食い違いを見張る条が要る                       | 採らない |

### 論点 8: 検査の扱い

**採る: 差し戻す条は1つも足さない。足す欄の検査は全部「数えるだけ」の段で入れ、形の崩れは描く側で丸める。古い欄は期限を切らずに受ける。**

- 足す条（すべて `count`）は次の5つ。
  - `verdict` と `workPlanClosing` が食い違う
  - 本文の `{{src: n}}` に当たる `sources` が無い、または使われない `sources` がある
  - 前のレポートが同じセッションに無いのに `previous` がある
  - `guideNotes` が4つ以上ある、または `target` が無い部品を指す
  - `work_plan` の並びを変えたのに `replanReason` が無い（`work_plan` の条。下の項）
- **描く側で丸めるもの**: 案内の付箋は先頭の3つだけを描く。台帳の並びと畳みは tsukumo が決めるので、書き手の並べ方を検査しない。出どころの番号が飛んでいても、描く側は書かれた番号のまま出す。
- **今の reject の条で、意味を読み替えるもの**: `finished-with-ng` は、`verdict` が `done` で `checks` に `ng` がある呼び出しにも当てる（条の数は増えない）。`unobserved-without-how` はそのまま。
- **古い欄の受け方**: `task.outcome`・`favor` は、新しい器が既定になったあとも読み替えて受ける。transcript からの組み直しが古い呼び出しを読み続けるため。道具の定義とカードの説明からは、新しい器を既定にする段で古い欄の説明を外す。
- 条を `reject` に上げるのは、今の決まり（`REPORT_REJECTION_MODES` の説明。記録の数と日付を `docs/history/decision.md` に書く）のとおり、記録を見てから。
- `work_plan` の検査には、今は差し戻す条しか無い。`replanReason` の欠けのために、`report` と同じ「数えるだけ」の段を `work_plan` にも設け、差し戻さずに記録だけ残す。

| 案                                                 | 種類   | 物差し                                                          | 判定     |
| -------------------------------------------------- | ------ | --------------------------------------------------------------- | -------- |
| 新しい条は全部 `count`、上限と並びは描く側で丸める | 仕組み | 欄を足しても書き手の手戻りが増えない。記録を見てから上げられる  | 採る     |
| zod の `max` で上限を切り、SDK に差し戻させる      | 仕組み | 数えるだけの段を通らずに差し戻しが増え、記録にも残らない        | 採らない |
| 古い欄を期限を決めて受けなくする                   | 仕組み | transcript の古い呼び出しが読めなくなり、開き直した画面が崩れる | 採らない |

### 論点 9: 続けてタスクを進めるループの一覧の材料

**採る: 材料は tsukumo の側にあるので、ループの一覧を作る。一覧は後段のタスクとして足す。**

| 一覧の欄           | 材料                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| タスクの ID と名前 | 同じセッションの `report` の `task`（`id`・`name`）。着手中の行は Beads のタスク一覧の見回り（`TaskSummaryItem`） |
| 所要               | 依頼を送ってから、その `task` を持つ `report` が届くまでの時刻の差                                                |
| 差し戻し           | その依頼の中で数えた周（論点 4）                                                                                  |
| 結果               | `report` の判定（論点 2）                                                                                         |
| これから           | Beads のタスク一覧で、未着手・待ちが無い・`loopable` の件数                                                       |

- 「これから」は件数だけを出し、どのタスクを次に選ぶかは出さない。次の1件を選ぶのはワークフローの側で、tsukumo は選び方を知らない（ADR 0024）。見本の最後の「これから」のタスクの行は、件数の行に置き換える。
- 分母（「5件のうち4件目」）は、済んだ件数＋今の1件＋これからの件数で出し、タスクが足されれば変わる。
- 一覧の行を押すと、そのタスクの依頼の紙が開く。
- 終えたタスクが成果の暦の今日の狐火になるのは、今の成果の数え方（Beads の閉じた課題）のまま。

## 移行の順

1. **欄を足す。** `report` の6つの欄・`work_plan` と `phase_result` の欄を足し、古い欄の読み替えをサーバの1か所に置く。新しい欄の検査は数えるだけで入れる。識別子は先に用語集の子へ足す。描く側はまだ新しい欄を使わず、画面は変わらない。
2. **tsukumo が作るものを足す。** 実況の文・見込みと幅・止まりの言い方・知らせの4段・委譲先の1行を、今の器の上で出せるところから入れる。互いに独立に進められる。
3. **紙の骨組みを、新旧の切り替えの印の裏に作る。** 判定の行・あなたの番・読む深さ・確かさの台帳・道筋を組み、部品の族ごとに描き直す。ループの一覧もここで組む。
4. **新しい器を既定にする。** 旧い器を消し、上の表の文書を書き直す。道具の定義とカードから古い欄の説明を外す（読み替えは残す）。

## 採らなかった案

- **`report` と `work_plan` を1つの道具にまとめる。** 働くあいだと終わったときに同じ道具を呼ぶ形は紙のモデルに近いが、`work_plan` の関門と委譲の数え方（ADR 0045）を組み直すことになる。紙は画面の状態の側で1枚にまとめれば足りる。
- **紙を書き手が丸ごと書く（計画も時系列も `report` の部品で）。** tsukumo がすでに見ている出来事を書き手に書き写させることになり、書き忘れと書き違いの道が増える。
- **確かさの印を色だけで分ける。** 色に頼る印は読み上げで消える。印は語（記録あり・申告のみ）で持つ。

## 残すこと

- 見込みの「似た作業」の決め方と件数の境、「動かない」と言い始める境は、記録を数えてから見込みの後段で決める。
- 通知の許しを求める時機と、Orca のタブでどこまで届くかは、知らせの後段で実物を見て決める。
- 寸法・色・字の大きさ・器の局面は、器とトークンの ADR が決める。
