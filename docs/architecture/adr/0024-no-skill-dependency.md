# tsukumo はワークフローの契約だけを定め、特定のスキルに依存しない（2026-10-08）

**tsukumo が定めるのは、ワークフローの契約だけ。** 契約は、タスクに段があり、並列に走る部分があり、
それがパイプラインのように流れることを受ける口で、中身は `docs/architecture/workflow-contract.md` が正典。

- **tsukumo は Beads 専用。** ファイル方式（`.tw/` の1件1ファイル）は持たない。Beads には依存してよく、それを制約とする（`docs/requirements.md` 2.3）
- **core は契約だけを見る。** スキルの書式（道具・課題の本文の書式・ラベル・置き場）を直接読まない。
  段取りは `work_plan`、委譲先の段の済み方は契約に定めた委譲の返却の1行目、作業の結果は `report` と `report.task` で受け、
  タスクは Beads の組み込みの欄だけから作る（返却の1行目を契約に入れたのは 2026-10-10 の改訂。下の「2026-10-10 の改訂」）
- **タスクを段に分けて送り出すワークフロー（next-task・plan-tasks・tw・agent・hook）の置き場は専用のリポジトリ
  `sinnlosses/tsukumo-plugins`。** tsukumo はそれをコミット単位で固定して取り込む
- **`tsukumo-plugins` のものも外のスキルと同じ立場。** 契約に型の合う1つの例で、Beads などの依存さえ満たせば単独で動く。
  契約を満たしているから tsukumo で使えるのであり、利用者の独自のワークフローも同じ立場で当ててよい
- **tsukumo の中では取り込んだ next-task を使い、素の Claude Code では利用者の next-task を使う。** 中身は当面同じ

## 2026-10-07 の版との差分

10-07 の版は「特定のスキルに依存しない」までで、同梱のスキルの位置づけも、置き場も言い切れていなかった。
10-08 に、同梱のものを契約に型の合う1つの例と位置づけ、Beads 専用と明記し、ワークフローを `tsukumo-plugins` へ
切り出すと改めた。契約の中身はツールの説明・システムプロンプト・表示の文書・要件に散らばっていたので、
合わせる相手を `docs/architecture/workflow-contract.md` の1か所に集める。以下の経緯と決めたことは 10-07 の版から引き継ぐ。

## 何が困っていたか

tsukumo のゴールは、レポートを分かりやすく表示し、キャラクターが魅力的に話すこと。タスクを段に分けて
測り、描くのは tsukumo の機能で、特定のスキルの持ち物ではない。それなのに次の箇所がスキルの約束事を
読んでいて、スキルの書式が変わると画面が黙って崩れる形になっていた（2026-10-07 の棚卸し）:

- **帯の段**: `work_plan` の `phases` を省くと、tsukumo が着手したタスクの `## やること` の `### n. 名前` から
  「計画」「各段」「受け入れ」の並びを作っていた（作業ツリーの名前と課題の `assignee` の対応も、スキルの着手の印の約束事）
- **委譲中の帯の進み**: 委譲先の `SubagentHandback` の1行目（`段 n/N |`・`計画 0/N |`・`止めた n/N |`）を読み、
  並びが「計画・各段・受け入れ」であることを前提に位置を決めていた。この書式は委譲を回すスキルの依頼文が決めている
- **`report.task` の終わり方**: `shipped` を「完了して main へ送った」と説明していた（送り方はスキルの手順）
- **人格の一言**: 「タスクの難易度でモデルを切り替える運用」を前提にしていた
- **タスク一覧・おすすめ・成果**: スキルが課題に足したラベル（`difficulty:`・`loopable:`・`cancelled`）と独自の状態（`pending`）、
  ID の書き換え（`T-`/`GH-`）、本文の7節の並べ替えを、スキルの写しとして shared に置いて画面と core まで運んでいた。
  成果はスキルの置き場（`develop/` の下など）を「運用の帳面」としてコミットの数から外し、節目は `T-`/`GH-` の番号の順に足していた

## 決めたこと

- **持ち物を分ける。** tsukumo が持つのは、段を受けて測り・残し・描く口（契約）と、タスクの一般の形と、Beads の読み口。
  ワークフロー（スキル）が持つのは、自分の道具（着手の印・検証の見張り）・課題の本文の書式（`## やること` の段）・委譲の依頼文・
  課題のラベル・ファイルの置き場。tsukumo はスキルの持ち物を読まず、スキルも tsukumo の中を読まない。
  委譲の返却の1行目の書式は 2026-10-10 の改訂でスキルの持ち物から契約へ移した（スキルは契約を参照する）
- **口は `work_plan`・`report`・`report.task` の3つ**（引数の意味は `docs/architecture/workflow-contract.md`）。どれも tsukumo の MCP ツールとその引数で、意味はツールの説明と
  システムプロンプトが教える。スキルが段を帯に出したければ、メインにこの口を呼ばせる。
  委譲中の段の済み方だけは、委譲先の返却の1行目でも受ける（2026-10-10 の改訂）
- **委譲中の段は、委譲先の返却の1行目で tsukumo が進める**（2026-10-10 の改訂。10-08 の版の「委譲中も段はメインの `work_plan` で進む」を置き換えた。
  決めたことの中身は下の「2026-10-10 の改訂」）。メインの `work_plan` は並び（`phases`）と委譲先の段の範囲を渡す口として残る
- **並びは `phases` だけで受ける。** `phases` を省く呼び出しは無くし、「計画」「受け入れ」を段にするかは渡す側が決める。
  段は1つずつ進める決まり（一足飛びの差し戻し）は残す。同時に走る段のまとまりは `phases` の配列の要素と `finishedInGroup` で受ける。
  委譲中にどの段が済んだかは、返却の1行目の段の番号かメインの呼び出しが明示し、済んだ順が前後しても tsukumo は推し量らない
- **`report.task` は ID・作業の名前・終わり方。** 終わり方は `finished`（作業を終えた）・`stopped`（止めた）・
  `awaiting-answer`（利用者の答え待ち）。どこへ送ったかは tsukumo の関心にしない。前の記録の `shipped` は `finished` として読む。
  帯の閉じ方（`workPlanClosing`）との照合は「`finished` なのに `stopped` で段が残っている」を差し戻す形で残す
  （語を `workPlanClosing` の `finished` と揃え、照合の意味を字で読めるようにする）
- **タスクの一般の形は Beads の組み込みの欄だけから作る。**
  - ID は Beads の ID そのまま（書き換えない）。題は `title`。依存は `blocks` の依存先
  - 状態は Beads の組み込みの状態を tsukumo の語（`open` → todo・`in_progress` → doing・`deferred` → hold・`closed` → done）に写し、
    ほかの値は生のまま出す
  - 作った時刻（`created_at`）と閉じた時刻（`closed_at`）、置き場所（`https://` で始まる `external_ref`）、
    ラベル（`labels`。字のまま並べて出すだけで、意味は解釈せず、並べ替え・絞り込み・色分けに使わない。2026-10-08 に足した）。
    担当（`assignee`）は読まない（2026-10-08 に外した）
  - 本文は `description`・`acceptance_criteria`・`notes` を Beads の欄の順に、tsukumo が決めた見出しで並べる（節を並べ替えない）
  - 並びは作った時刻の順
  - 写すのは Beads の読み口（`server/**/adapter/`）で、shared・画面・各機能の core は一般の形だけを扱う
- **一般の形にしたことの帰結。** おすすめは依存（待っているものの数）・状態・題から選び、難しさは渡さない。
  卒業は作った時刻のままで変わらない。タスクの節目は閉じた時刻の順に足す。取り下げを見分けないので、閉じた課題は
  すべて終えたタスクとして数える。コミットの数から特定の置き場のファイルを外す規則は無くし、コミットはすべて数える
- **段の所要は tsukumo が記録の時刻で測る。** 別の保存先は作らない。組み直しは transcript の `timestamp` から時刻を戻す。
  スキルが残す時間の記録は読まない。セッションをまたぐ集計は今は作らない
- **このリポジトリを開発するための `scripts/` は境界の外。** 製品ではなく開発の運用なので、スキルの道具を前提にしてよい

## 採らなかった案

- **委譲先に合図を送らせて帯を進める**（`SendMessage` の1行）: 2026-10-03〜10-05 に合図で帯を動かしていたが、合図が
  届かないと帯が止まり、合図の番号で何段も飛んだ。合図は委譲先の transcript（`subagents/`）にしか残らず、組み直しで戻せない
- **返却の1行目の書式を tsukumo の定めとして残す**（10-08 の版では採らず、2026-10-10 の改訂で採った）: 10-08 の時点では、書式を定めたのは
  委譲を回すスキルで、tsukumo の口にするとスキルの依頼文と二重の正典になり、番号の照合のために「計画・各段・受け入れ」の並びも
  前提にし続けることになる、として採らなかった。10-10 に、書式の正典を契約へ移してスキルは参照するだけにし（二重にならない）、
  並びは前提にせず `work_plan` で委譲先の段の範囲を宣言させる形に改めた（下の「2026-10-10 の改訂」）
- **`phases` の省略を残して `## やること` から並びを作る**: 課題の本文の書式とスキルの着手の印（`assignee`）に依存する。
  メインが段を書き写す手間とずれは、口の説明とスキルの側の手順で受ける
- **`shipped` の説明だけを直す**: 語が「送った」を言い続け、`workPlanClosing` の `finished` と同じ意味の別の語が残る
- **ラベル `cancelled` を Beads の読み口で読み続ける**: スキルが足したラベルで、Beads の欄ではない。取り下げを数から外すなら、
  Beads の組み込みの欄で表せるようになってから足す
- **段の所要を `~/.tsukumo/` に別に残す**: transcript が正典で、そこから時刻を戻せる。二重に持つと食い違いの扱いが要る

## 2026-10-10 の改訂

**委譲先の返却の1行目を契約に入れ、tsukumo がそれを読んで帯を進める。** メインの `work_plan` は並びと委譲先の段の範囲を渡す口として残し、
返却が届いたのにメインが `work_plan` を呼んでいないあいだは作業のツールを拒む関門を保険に置く（2026-10-10 利用者決定）。

- **何が困ったか**: 2026-10-10 に `/next-task` でタスクを進めたとき、メインが計画だけの返却のあとに `work_plan` で段を進めるのを忘れ、
  帯の「段ごとの時間」が計画 25 分・実装 0 秒・受け入れ 9 秒に偏った。10-08 の版では段を進めるのがメインの呼び出しだけで、
  呼び忘れを tsukumo は検知できなかった。帯の数字が実際の作業の長さを表さなくなった
- **同梱スキルへの依存を可とした決定との関係**: 2026-10-10 に、tsukumo がコミット単位で固定して取り込む `tsukumo-plugins` への依存は可と決まった。
  ただし返却の書式の正典はスキルではなく契約（`docs/architecture/workflow-contract.md`）に置き、スキルの依頼文は契約を参照するだけにする。
  core が見るのは契約のままで、書式を言い直すスキルが無いので二重の正典にならない。利用者独自のワークフローも、
  委譲先に契約どおりの1行目を返させれば同じく帯が進み、返させなければ 10-08 の版と同じくメインの `work_plan` だけで進む

### 返却が届く経路（実測）

2026-10-10 に、Agent SDK 0.3.288 の型定義と、このリポジトリの作業ツリーの transcript・`~/.tsukumo/token-usage/` の記録で
構造だけを数えて確かめた（本文は読まない）。

- **生きたセッションでは、委譲先の `SubagentHandback` の呼び出しがメインの query に流れる。** 背景に回した委譲先の
  `assistant` メッセージは `parent_tool_use_id` 付きで届き、`SubagentHandback` の `tool_use` の `input.message` に返却の本文が丸ごと入る。
  10-06〜10-07 の実装（`parseDelegateReturn`）はここから1行目を読んでいた。`SendMessage` で再開した段の返却も同じく流れる
  （10-09 は `Agent` 33回・`SendMessage` 60回に対して返却 85回、10-10 は 46回・83回に対して 124回が、使用量の記録の
  `subagent` の持ち場に数えられている）。再開した段の返却の `parent_tool_use_id` が最初の `Agent` の呼び出しの id かは確かめていない。
  下の設計は段を返却の1行目の番号で決め、どの委譲先の返却かを見分けないので、この値に頼らない
- **返却は `task_notification` を起こさない。** 返却を受けたメインの transcript に `<task-notification>` は無く、
  返却の識別に `task_notification` は使えない
- **メインの transcript には、返却が `user` の役のメッセージとして残る。** `origin` は `{ kind: "peer", from: <委譲先の agentId>, handback: true, body }`
  （`handback` は型定義に無い欄）、本文は `<agent-message from="<agentId>">` の塊で、決まった前置きの行のあとに返却の各行が2字下げで入る。
  前置きと返却の間に仕掛けの注記の行が挟まることがあるので、返却の1行目は塊の先頭からの行数では決まらない。
  `agentId` は、メインの `Agent` の呼び出しの結果（`tool_use_result` の `agentId`）と委譲先の transcript の `meta.json` の `toolUseId` で `Agent` の呼び出しの id に結べる。
  組み直し（`session-restore.ts`）はいま `<agent-message>` の塊を依頼の文面から落としているだけで、返却としては読んでいない
- **返却の時刻**: 生きたセッションでは委譲先の `SubagentHandback` の `assistant` メッセージが届いた時刻、組み直しではメインの transcript の
  返却の `user` メッセージの `timestamp`。後者は前者より数秒遅い（実測で6秒）
- **疑似セッションには委譲の返却が無い。** `test/fixture/fake-session.json` の脇の話の場面（`aside`）は `Agent` の呼び出しと背景のタスクの顔ぶれまでで、
  `SubagentHandback` も返却の `user` メッセージも無い。返却で帯を進める実装はここに場面を足す

返却は生きたセッションでも組み直しでも tsukumo に届くので、返却を契約にして tsukumo が読む形は成り立つ。

### 返却の形

**いまの1行目の字の形をそのまま契約にする。** `SubagentHandback` の引数は字の `message` 1つで、組み直しで読めるのも
字下げした本文だけなので、構造化した欄を足す場所が無い。人が読んでも分かる字の形のまま、tsukumo が読む。

| 1行目                  | 意味                                                        | 帯                                    |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------- |
| `計画 0/N \| <要約>`   | 計画だけの回。段に数えず、委譲先の段の数が `N` だと知らせる | 進めない                              |
| `段 n/N \| <要約>`     | 委譲先の段 `n` を済ませた（`1 ≤ n ≤ N`）                    | 段 `n` に当たる帯の段を済ませる       |
| `止めた n/N \| <理由>` | 段 `n` の途中で止めた                                       | 進めない（段 `n` が「今」のまま残る） |

- **差し戻しのやり直し**は同じ `段 n/N` をもう一度返す。帯の段がもう済んでいれば何もしない（同じ返却を何度受けても帯は同じ）
- **並列の段**は段の番号だけで表し、どの委譲先が返したかは見ない。済んだ順が前後しても、段 `n` が今の段の集合に入っていれば済ませる
- 1行目が上のどれでもない返却と、`段`・`止めた` の `N` が宣言した範囲の段の数と違う返却は帯を進めない。読むのは1行目の番号と要約だけで、2行目より後ろは読まない
- 1行目は、生きたセッションでは `SubagentHandback` の `message` の先頭の行、組み直しでは返却の `user` メッセージの `<agent-message>` の塊の中で、
  仕掛けが足す行（前置きと `[harness: …]` の注記）と空の行を除き、字下げを外した最初の行。どちらもその1行だけが形に合うかを見て、
  2行目より後ろに形の合う行があっても読まない（生きたセッションと組み直しで結果を分けない）

### 帯の段と委譲先の段の対応

**帯の段を委譲先の段に1つずつ合わせ、どこからどこまでが委譲先の段かを `work_plan` で宣言させる。**
`work_plan` に、委譲先の段の範囲（平らにした並びで委譲先の段1に当たる位置〔0始まり〕と段の数）を渡す欄を足す（識別子は `docs/glossary.md` に足してから決める）。
委譲先の段 `n` は、範囲の先頭から `n - 1` 個目の帯の段に当たる。範囲の前後には「計画」「受け入れ」などメインの段を置いてよい。

- 範囲の中に段のまとまりを置いてよい（並列の段）。範囲の端をまたぐまとまりは形の誤りとして差し戻す
- **段の数が途中で分かるとき**: 計画だけの回（`計画 0/N`）までは範囲を宣言しなくてよい。`N` を受けたあとの `work_plan` で、範囲の段の数が
  同じ依頼で最後に受けた返却の `N` と違う呼び出しは `WorkPlanReview` が差し戻す。帯の段と委譲先の段の数え方の食い違い（2026-10-10 に起きた、
  委譲先の6段を帯の1段にまとめ、帯は「3/4」なのにセリフが「6段のうち段4」と言った組み方）は、言葉の規則ではなくこの照合で防ぐ
- 範囲を宣言していない依頼では、返却は帯を進めない（下の関門だけが効く）
- **条で頼む案は置き換える。** `WORK_PLAN_PROMPT` に「委譲先の段を帯の段にして `phases` を組む」条を足す案は採らず、この範囲と照合が持つ。
  セリフ・段のまとめで段を帯の段で数える条は残し、返却で帯を進める実装が `WORK_PLAN_PROMPT` と合図の条（`SPEECH_CADENCE_PROMPT`）を書き換えるときに範囲の宣言と合わせて書き直す

### 帯の進め方

- **返却を受けた時刻で段を区切る。** 契約の形の `段 n/N` が届き、段 `n` に当たる帯の段が今の段の集合に入っていれば、tsukumo がその段を済ませる。
  1本道の段なら `current` を1つ進め、まとまりの中の段なら `finishedInGroup` に足す（最後の1段なら `current` を進めて空にする）。記録の時刻は返却の届いた時刻
- 段 `n` が今の段の集合より先にある返却（一足飛び）・もう済んだ段の返却は帯を動かさない。帯を閉じるのは今までどおり `report` の `workPlanClosing` だけで、
  範囲の最後の段が並びの最後の段でも、返却では全部済みにしない
- **段のまとめは返却の要約から作る**（`MAX_PHASE_SUMMARY_SENTENCES` 文で切り詰める）。中間レポートにはこれが出る
- **メインの `work_plan` は位置ごと渡すので、二重に進まない。** 返却で進んだあとにメインが同じ位置を渡す呼び出しは「同じ段のまま」で、段のまとめが無くても通り、
  中間レポートを足さない。メインが位置を組み替えたら、今までどおりメインの呼び出しが帯を決める。
  段のまとめの必須を緩めるこの判定は、返却で進んだ位置を覚えている `WorkPlanReview` が行う（状態を持たない `parseWorkPlan` では、返却で進んだ位置かどうかが分からない）
- 範囲・照合・返却で進んだ位置は `WorkPlanReview` が覚え、一足飛びの判定も返却で進んだ位置を起点にする

### 関門の数え方

**返却が届いたら印を立て、メインの `work_plan` が受け付けられたら下ろす。印が立っているあいだ、メインの作業のツールを拒む。**

- **効く範囲**: 仕事のセッション（`work_plan` が載る）で、同じ依頼にメインの受け付けた段取りがあるときだけ立てる。
  雑談のセッションの委譲と、段取りを渡していない依頼（答えるだけ・1回調べて答えるだけで `work_plan` を呼ばない依頼）の返却では立てない。
  下ろす口（`work_plan`）が無い・呼ぶ条件に当たらない依頼で、作業のツールを拒み続けないため。範囲（`delegatedRange`）の宣言は条件にしない
  （契約の形で返さないワークフローでも、段取りがあればメインに `work_plan` を呼ばせる）
- 印は返却の数を数えない。並列の段の返却が続けて届いても、メインの `work_plan` 1回で下ろす（位置ごと渡すので、1回で全部の返却を写せる）
- 届いた事実だけで立てる。契約の形でない返却・差し戻しのやり直し・`止めた` の返却でも立つ。差し戻しの返却は同じ位置のまま `work_plan` を呼べば下りる
- 差し戻された `work_plan` では下りない
- **通すもの**: 読み取りのツール（`Read`・`Grep`・`Glob`・`ToolSearch`）と tsukumo の MCP ツール（`speak`・`work_plan`・`report` など）。
  それ以外のメインのツール（`Bash`・`Edit`・`Write`・`Agent`・`SendMessage`・`TaskStop` など）を拒み、拒む文は「返却を受けたので `work_plan` で段を進めるか、
  同じ段のまま呼ぶ」と言う。委譲先のツールは対象にしない
- **役割の分け方**: 帯を進めるのは返却で、関門は「メインが返却を読み、並びと範囲を確かめてから次の段を送る」ことを保証する保険。
  契約の形で返さないワークフローでも、関門がメインに `work_plan` を呼ばせるので帯が止まらない
- 印はターンをまたいで残り、セッションを起こし直すと下りる（組み直しでは戻さない。関門は生きているセッションの往復の中だけの決まり）

### 組み直し

10-08 の版の「段の時間の区切りは前後とも同じだけずれる」（メインが返却を読んで呼ぶまでの数秒のずれ）は、返却の実際の時刻で区切る形に変わった。
組み直しでは、メインの transcript の返却の `user` メッセージ（`<agent-message>` の塊）から1行目を読み、その `timestamp` で、生きたセッションと同じ変換を通して帯を進める。
メインの `work_plan` は今までどおりメインの transcript から戻る。生きたセッションの区切り（委譲先の `assistant` の時刻）と組み直しの区切り（メインに届いた時刻）は
数秒ずれるが、どちらも返却を基準にした時刻なので、段の所要の比はほとんど変わらない。

### 採らなかった案（2026-10-10）

- **メインに呼ばせ続ける**（10-08 の版のまま）: 呼び忘れを tsukumo が検知できず、帯の段の時間が実際と離れる（上の「何が困ったか」）
- **所要の短さで差し戻す**（段が数秒で済んだら呼び忘れとみなす）: ヒューリスティックで、本当に短い段と見分けられない。機械で判定できる「返却が届いた事実」を使う
- **委譲先に tsukumo の MCP ツールで段を済ませさせる**: handler はメインと委譲先の呼び出しを見分けられず、委譲先の呼び出しは `subagents/` にしか残らないので組み直しで戻せない
- **返却に構造化した欄（JSON の塊など）を持たせる**: `SubagentHandback` の引数は字1つで、組み直しで読めるのも字下げした本文だけ。字の1行で足りる
- **`parent_tool_use_id`・`agentId` で委譲先ごとに段を割り当てる**: どの担当にどの段を渡したかはワークフローの持ち物で、段の番号だけで帯の段が決まる。再開した段での値も確かめられていない
- **`計画 0/N` から tsukumo が並びを作る**: 段の名前が無く、「計画・各段・受け入れ」の並びを tsukumo が前提にすることになる
- **返却1件ごとに `work_plan` 1回を求める**: 並列の段の返却が続けて届くと、同じ位置を渡す呼び出しを何度も強いる。位置ごと渡すので1回で写せる
- **`task_notification` で返却を数える**: 返却では届かない（上の実測）
