# トークン消費の見直しは、会話とは別の使い捨ての `query()` で走らせる（2026-10-12）

**トークン消費の画面の「減らし方を見てもらう」と、結果の提案の「tsukumo に頼む」「タスクにする」は、
仕事の会話へ依頼を送らず、機能 `usage-review` が押すたびに起こす使い捨ての `query()` で走らせる。**
仕事の会話からは見直しの2つのツール（`usage_review_stage` / `usage_review_result`）を外す。
見直しの状態は `SessionState` の欄に残すが、寿命はターンと起こし直しから切り離し、見直しの走りが流す
イベントだけで動かす。

## 何が困っていたか

「減らし方を見てもらう」は、仕事のページと同じセッションへ依頼文を送っていた（`dispatch.session.prompt`）。
提案の主ボタンも同じだった。そのため次のことが起きていた:

- トークンの画面で押した依頼と返答が、仕事の画面の会話に並ぶ。利用者にとっては見覚えのない依頼で、不意打ちになる
- 仕事のターンが進行中だと押せない（`TURN_RUNNING_BLOCKED_REASON`）。雑談中も押せない（雑談の会話にはツールが載らないため）
- 見直しの状態（`usageReview`）がターンの始まりの時刻を経過に使い、ターンの終わり・起こし直しでふだんへ戻る。
  見直しの寿命が仕事の会話の寿命に混ざっている
- 見直し中の「止める」が仕事のターンを止める

## 決めたこと

- **別のセッションは使い捨ての `query()`** にする（日記の `sdk-diary.ts` と同じ形）。置き場は機能 `usage-review`
  （判断は `core/` の見直しの走り、SDK に触るのは `adapter/` の `sdk-` で始まるファイル）。押すたびに1回起こし、
  終われば消える。
  - `systemPrompt` は `claude_code` の preset に、人格と役目の短い指示を append する（スキルを読み込ませるため、
    日記のように文字列で丸ごと置き換えはしない）
  - スキルは同梱の `plugin/` を `plugins` で載せる。組み込みのツールは `Skill`・`Read`・`Bash(python3:*)` だけを
    `allowedTools` で許し、`permissionMode: "dontAsk"` でほかは聞かずに断る。`settingSources: []`・`strictMcpConfig: true`
  - MCP には `usage_review_stage` / `usage_review_result` と、この問い合わせ専用の `speak` を載せる。見直しの2つの
    handler は受け付けたものを `UsageReviewIntake` 越しにイベントで流すだけで、仕事の会話の駆動に依存しない
    ので、そのまま移せる
  - 1度に走るのは見直しか提案の実行の1つだけ。走っている間は、ほかを始めるコマンドを断る
- **提案の「tsukumo に頼む」「タスクにする」も、同じ見直しの走りで、提案ごとに別の使い捨ての `query()` として
  走らせる。** 仕事の会話には何も送らない。トークンの画面には許可の問い合わせを出す場所が無いので、**利用者が
  その提案の主ボタンを押したことを同意とみなし**、許可は尋ねない（`dontAsk`）。許す道具は押す口ごとに絞る:
  `delegate` は `Read`・`Edit`・`Write`・`Glob`・`Grep`、`task` は取り込んだワークフローのプラグインと
  `Bash(tw new:*)`。実行の様子（頼んでいる・済んだ・できなかった・止めた、経過、直近のセリフ）はその提案の札の
  上に出す（2026-10-12 利用者の決定）
- **仕事の会話から見直しの2つのツールを外す。** 状態を動かす出し手を見直しの走り1つにする。入力欄から見直しを
  頼んだときは、スキルの「ツールが無ければ本文のレポートに書く」の側で返る。会話のやり取りに添えていた
  結果の札を開く導線と、その開き先の hash（`#token-usage?review=last`）は無くなる（2026-10-12 利用者の決定）
- **見直しの状態は `SessionState` の欄に残す**（`usageReview` / `previousUsageReview` と、足す
  `usageProposalRun`）。会話とは別の問い合わせの進みを同じ状態で配る先例（おすすめの札 `recommendation`・
  日記 `diaryWriting`）に揃え、ADR 0021 の「`SessionState` の形は変えない」を保つ。画面が読む口は今のまま
  `useSession` の `state` の欄（2026-10-12 利用者の決定）
- **切り離すのは寿命。** 見直しの欄は、見直しの走りが流す始まり・段・セリフ・結果・終わりのイベントだけで動く。
  `turn-finished`・`session-ended` では動かさず、経過は見直しの始まりのイベントから数え、起こし直し
  （`restart`）をまたいで残す。会話の記録（`records`。今の呼び名は「セッションの記録」で、「会話の記録」は
  `docs/glossary.md` のあらすじ・会話のアーカイブ・エピソード索引を束ねた語）には何も積まない。見直しのイベントは、タスクの見張りと
  同じく、流すたびにその時点の代へ流す
- **雑談中の制限は要らない。** 別の問い合わせは仕事・雑談のモードによらず自分のツールを載せるので、
  雑談中でも見直しが走る。押せない理由は「見直しか提案の実行が1つ走っている」だけにする
- **会話の扱い**（`docs/coding-standards.md`「会話内容の扱い」）:
  - どちらの問い合わせも `persistSession: false` で transcript を作らない
  - 依頼文・セリフ・結果の本文・ツールの引数を、ログ・診断ログ・会話のアーカイブ・ファイルへ書かない。
    セリフは `speak` の handler が専用のイベントで状態へ流すだけで、会話のアーカイブが拾うセリフの経路を通らない
  - ホームに書くのは今までどおり、見直しの結果（`~/.tsukumo/usage-review.json`）と見送った提案の識別子だけ。
    結果を書くのは見直しの走りで、`session-manager` は書かない
  - 使用量はトークン消費の記録に混ぜない（`docs/architecture/core-and-adapter.md`「使い捨ての `query()`」）
- **疑似セッション（`TSUKUMO_DRIVER=fake`）では `query()` を起こさず**、疑似セッションのファイルに書いた
  架空の見直しの手順をそのまま流し直す。画面の往復を claude なしで E2E と目視にかけるため

## 採らなかった案

- **`session-manager` に第2の駆動（`SessionDriver`）を持たせる**: 駆動が抱える `report` の関所・許可の待ち行列・
  復元・会話のアーカイブ・代の起こし直しが、どれも見直しには要らない。キャラクターやモードを切り替えると代ごと
  起こし直すので、見直しがそれに巻き込まれる
- **ページに1本の長く続く別セッション（入力の流れを持つ `query()`）を置き、見直しと提案の実行を順に流す**:
  見直しの文脈を提案の実行で使える利点はあるが、文脈がたまり続けてトークンを食い、許可の問い合わせを出す画面と
  セッションの寿命（いつ閉じるか）を新しく決めることになる。提案の実行に要るのは提案の見出し・やること・根拠
  だけで、それは依頼文で渡せる
- **見直しの状態を別の配信口（`SessionState` の外の購読）で配る**: 配信の口が2本になり、`hello` の作り直し・
  版の上げ方・ブラウザの読み手を2通り持つことになる。会話とは別の問い合わせの状態を `SessionState` に載せる
  先例がすでに2つある
- **仕事の会話にも見直しのツールを残す**: 見直しの状態を動かす出し手が2つになり、ターンの寿命との結び付き
  （ターンの終わりで戻す・始まりの時刻）を残すことになる
- **提案の実行だけ仕事の会話へ送る**: トークンの画面の実行が仕事の会話に現れないという決まりに反する
- **トークンの画面に許可の問い合わせを作る**: 仕事の画面の問い合わせ（答え待ちの列と画面）を、もう1組作る
  ことになる。押す口ごとに道具を絞り、押したことを同意とみなせば要らない
