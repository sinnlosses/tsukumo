# 設定は誰の・何に属する値かで3つの置き場に割る（2026-10-03）

**設定の置き場は3つで、値が何に属するかで決める。** 起動のしかた・マシンに属する値は環境変数、
利用者の好みは歯車の設定、そのリポジトリで作業する誰にとっても同じ値は**プロジェクトの設定**
（起動先の `.tsukumo/project.json`）に置く。**プロジェクトの設定は、tsukumo が動くときに読む
出どころをそのファイル1つに限る。** CLAUDE.md の見出しや git の状態から値を推し量るのは、画面で
書くときの下書きにだけ使う。

## 何が困っていたか

tsukumo は作者の運用（task-workflow スキル・Beads・`main` ブランチ・orca・`/next-task`）が揃った
環境を前提にしていて、無い環境では落ちずに「不明」へ倒れ、機能が黙って欠ける。直すにはいくつかの値を
変えられるようにする必要があり、その置き場が決まっていなかった。

設定の口は2つあった（環境変数は `src/server/core/config.ts` の `readConfig` と `TSUKUMO_HOME`、
歯車は `~/.tsukumo/state.json` と `localStorage`）。それに加えて、タスクの方式を起動先の
AGENTS.md / CLAUDE.md の「## タスク運用」節から読んでいて（`taskStoreOf`）、プロジェクトごとの設定が
暗黙に3つ目としてあった。日本語の見出しを探して読むので、節の書き方が変わると黙って読めなくなる。
主ブランチ名も、`src` は `refs/heads/main` を決め打ちし、`scripts` は
「行 → `origin/HEAD` → main/master/trunk を順に試す」で当てていて、同じリポジトリの中で食い違っていた。

## 決めたこと

| 置き場             | 入る値                                                                                                                | 書く人・書き方                                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 環境変数           | 起動のしかた・マシンに属する値（ポート・ホームの場所・`CLAUDE_CONFIG_DIR`・どのホストで開くか・疑似セッションの駆動） | 起動する人がシェルで渡す                                                                                               |
| 歯車の設定         | 利用者の好み（色・新しいセッションの既定・演出の速さ・訪問）                                                          | 画面の歯車から。持ち先は `state.json` か `localStorage`（`docs/architecture/screen-design.md`「13.6 設定の置き場所」） |
| プロジェクトの設定 | そのリポジトリで誰にとっても同じ値（タスクの方式・主ブランチ名・「tsukumo に頼む」の送る文面）                        | 起動先の `.tsukumo/project.json`。画面から書ける（リポジトリに入れて共有する）                                         |

- **プロジェクトの設定は書かれたファイルだけで決まる。** 起動中に CLAUDE.md を読んだり、git の
  状態から主ブランチを当てたりしない。同じファイルなら、どの環境でも同じ振る舞いになる
- **推し量りは画面の下書きにだけ使う。** 画面でプロジェクトの設定を書くとき、初期値として
  「## タスク運用」節や `origin/HEAD` から推し量った値を出してよい。利用者が確かめて保存した値だけが
  ファイルに入る
- **ファイルが無いときは「タスク運用なし」。** タスクの節・タスクボードの入口・タスク由来の成果を
  出さない。黙って欠けるのではなく、画面にプロジェクトの設定を書く入口を出す
- **ファイルが読めないとき（形が違う）は「読めない」と画面に出す。** 既定へ倒さない。
  常駐プロセスは落とさない
- **値を1つずつ足さない。** 成果から除くパス（`develop/task/` など運用の帳簿のファイル）はタスクの
  方式から決まるので欄にしない。欄を足すのは、方式から決まらず、リポジトリによって違う値だけ
- **応答の言語は設定にしない。** 日本語だけに対応する（`docs/requirements.md`「2.2 対象外とすること」）

## 採らなかった案

- **「## タスク運用」節を読み続ける**: task-workflow の `tw` と同じ出どころで二重にならないが、
  日本語の見出しを探す読み方は書き方の揺れで黙って外れ、無いときは推し量りに頼ることになる。
  動くための値は明示の1か所から読む、を優先した。task-workflow を使うリポジトリでは節と
  ファイルの両方にタスクの方式が書かれることになるが、画面の下書きが節から値を取るので、
  書くときに食い違わない
- **`state.json` にプロジェクトごとの欄を持つ**: 画面から書きやすいが、利用者の手元にしか残らない。
  主ブランチ名やタスクの方式はリポジトリの性質で、同じリポジトリを別の作業ツリーや別のマシンで
  開いても同じであるべきなので、リポジトリの中に置く
