# 草稿は最終レポートと同じ紙に描き、骨組みは次に届く1か所、余白の列は札のある部品だけ、下書きは依頼の文（2026-11-18）

ステータス: 採用

論点 5 と、論点 2 の余白の案内は 0067 が取り下げた（2026-11-18）。

**書いている途中のレポート（草稿）を、最終レポートと同じ紙・同じ幅で描く。罫線の伸びる待ちの欄をやめ、まだ届いていない部品のうち、次に届く見込みの1つの場所にだけ骨組みを置く。返す層の余白の列は、札（開いた欄・聞いた対・付箋）のある部品にだけ空け、札の無い部品は本文の幅いっぱいに描く。押すと入力欄へ入る下書き（次の一手・お願いの選択肢・前回の続き）は、利用者が打つ依頼の文にする。A2UI・AG-UI・Astryx からは、いまの構成に合う規則と部品だけを借り、パッケージは足さない。この ADR は、ADR 0040・0051・0055 の論点の一部を論点ごとに上書きする（本文は書き換えない）。**

この ADR が決めるのは、草稿の器と骨組みの置き方、草稿の画像の札、余白の列を空ける条件、下書きの文の形まで。`report` の入力の欄は足さない。部品の途中の字を先に出すことは、あとで測って出さないと決めた（論点 8）。幅で折り返す配置の部品・書き手が続きの依頼を渡す欄は決めず、下の「残したこと」に置く。

## 何が困っていたか

2026-11-18 に、疑似セッションを 1400×900 で撮って測った。

- 草稿は中間レポートと同じ破線の箱に入り、幅は 560px だった（最終レポートの紙は 747.33px）。箱は中央の列の左に寄り、右に約 199px の空きが出た。書き終えて紙に替わると幅が広がり、表のセルの折り返しが変わった。
- 草稿の末尾の「次の部品を待つ欄」は、本文の幅の半分ほどの罫線2本が左から右へ伸びる動き（1.6 秒・8 段）を繰り返した。割合を言わないのに進み具合の棒に見え、どの部品を待っているかも言わなかった。
- 根の部品が届くまで（書き始め）は草稿の箱が出ず、流れの末尾の「レポートを書いている」の行だけが出た。
- 返す層の余白の列（248px と間 24px）は、札が1枚も無くても、本文の全部の部品の右に空いていた。紙の内側 724.92px のうち、部品が使えたのは 452.92px（列と間の 272px を引いた幅）で、表のセルが折り返し、`Options` は題と理由が2行に割れる狭い形になった。
- 次の一手の「続ける」の下書きは「続けて。」に残りの作業の文をつないだもので、残りの作業の文は状態を言う文（「〜が着手できる。」）なので、入力欄に入ると利用者の指示に読めなかった。始め方の一覧の「前回の続き」が送る依頼は「前回の続き: 」に残りをつないだもので、動詞が無かった。

## 利用者が決めたこと（2026-11-18）

- レポートを全面的に見直す。気になる点は4つ: 書いているときに出る中途半端なプログレスバーのようなもの、書きかけのレポートが左に寄っていること、レポートの右側が空白になることが多いこと、次の一手などで入力欄に入る文言が利用者の指示らしくないこと。
- A2UI・AG-UI・Astryx を使って、良いレポートを作る仕組みにする。

個々の形は利用者が選んでいない。下の決定は書き手の判断で、あとで戻せるほうを選んだ。

## 決めたこと

「草稿」と「骨組み」は、この ADR で用語集に足した語（`docs/glossary/detail-and-report.md`）。調べた仕様の原文の場所は `docs/research/a2ui-agui-astryx-2026-11-18/index.md`。

### 論点 1: A2UI・AG-UI・Astryx から借りるもの

**採る: 借りるのは規則と部品で、パッケージは足さない。**

| 出どころ                                      | 借りるもの                                                                    | tsukumo での形                                                                                 | 採否           |
| --------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------- |
| A2UI の仕様（段階描画）                       | まだ届いていない子は置き場を取って段階的に描き、根が届くまでは面を描かない    | 草稿は根から辿れる部品だけを描き、次に届く見込みの部品の場所に骨組みを置く（論点 3）           | 採る           |
| A2UI の blueprint の `fallbacks` の `pending` | 骨組みを返す口は、届いていない部品の ID と親の種類を受ける                    | 骨組みの形を親の種類で決める（根の子は見出しと本文、節の子は本文）。口が実装されたら載せ替える | 採る（形だけ） |
| A2UI の Agent SDK の `progressiveKeys`        | 部品が閉じる前の字を、頭から先に送る                                          | 段落の途中の字を草稿に出す                                                                     | 見送り         |
| `@a2ui/agent`                                 | 書き手の出力を A2UI のメッセージへ組む                                        | 無し。Claude が `report` の引数を直接書く構成に合わない                                        | 採らない       |
| AG-UI の公式ミドルウェアの型                  | 同じ鍵の表示を、組み立て中から面へ、その場で置き換える。読み込みの印は1つまで | 草稿は `toolUseId` を鍵に、白紙の紙・草稿・確定版を同じ場所で置き換える。骨組みは紙に1か所     | 採る（規則）   |
| `@ag-ui/client`・`@ag-ui/claude-agent-sdk`    | HTTP の run とイベントの流れ                                                  | 無し。SDK を子プロセスで動かす構成（ADR 0008）に合わない                                       | 採らない       |
| Astryx の `Skeleton`                          | 寸法の分かっている場所に置く、明滅する帯                                      | 骨組みの帯（`src/browser/components/ui/skeleton/skeleton.tsx` の包み）                         | 採る           |
| Astryx の `ProgressBar`                       | 割合の棒                                                                      | 無し。部品の総数は節が届くたびに増えるので、割合が後戻りする                                   | 採らない       |
| Astryx の `Grid`・`GridSpan`                  | 器の幅で折り返す格子と、またがる数                                            | 配置の部品に足す                                                                               | 見送り         |

- `progressiveKeys` の行は論点 8 が上書きする（測った結果、途中の字は出さない）。
- Astryx の `Grid`・`GridSpan` の行は ADR 0065 が上書きする（自作の部品 `Grid` を足し、`GridSpan` は写さない）。
- 調べた日の手元の版は `@a2ui/react` 0.14.0 と `@astryxdesign/core` 0.7.10。同じ日に 0.15.0 と 0.7.16 へ上がり、載せ直して測り直した値は下の「実物で確かめたこと」。

### 論点 2: 草稿は最終レポートと同じ紙に描く

**採る: 草稿の器は最終レポートと同じ紙（地・枠・内側の余白・幅）にし、破線の箱をやめる。見出しの行は最終レポートと同じ条件（`task` があるか、中間レポートのあるやり取り）で出し、ラベルは「書きかけのレポート」にする。終わり方の札は出さない。**

- 書き終えても紙の幅と見出しの行の有無が変わらないので、本文の折り返しは草稿と確定版で同じになる。
- 根の `Report` が届く前（書き始め）から紙を出す。白紙の草稿は、結論の骨組み（明滅する）と、節1つぶんの骨組み（止めた薄い帯）を置く。次に届くのは根なので、明滅させるのは結論の側だけ。
- 読み上げ: 紙の名前は「書きかけのレポート」。書いている途中だと言う印（`aria-busy`）は、引数を書いているあいだ（白紙の草稿と、書いている途中の草稿）だけ真にする。差し戻されて書き直しを待つ草稿と、届いて確定を待つ草稿では偽。
- 草稿には、返す層の初回の説明（ADR 0062 論点 12 の余白の案内）を出さない。案内を出すのは、指して聞ける本文（`report` の呼び出しの id を持つ本文）だけにする。
  > 余白の案内は、ADR 0067 論点 1 が聞く・頼むと一緒に取り下げた（2026-11-18）。
- ADR 0040 論点 1 の「草稿と確定版は同じ要素として引き継がない」は変えない。入れ替わる1回の作り直しは残る（確定で検証結果・合図の行・所要時間が足される）。
- 描くのは `src/browser/components/page/conversation/components/main-view/draft-report.tsx` の `DraftReport`。草稿の形は `src/shared/session/main-view-shape.ts` の `MainViewDraft`（白紙の `blank` と、部品のある `parts`）。

| 案                                     | 種類   | 物差し                                                                 | 判定     |
| -------------------------------------- | ------ | ---------------------------------------------------------------------- | -------- |
| 最終レポートと同じ紙に描く             | 仕組み | 書き終えたときに幅と折り返しが変わらない。右の空きが出ない             | 採る     |
| 破線の箱のまま、幅だけ広げる           | 仕組み | 幅はそろうが、確定で枠と地が替わる。中間レポートと見分けが付かないまま | 採らない |
| 草稿を描かず、書き終えてから一度に出す | 仕組み | 長いレポートで最初の部品が約 15 秒遅れる（ADR 0040 の計測）            | 採らない |

### 論点 3: 骨組みは、次に届く見込みの部品の場所に1つ

**採る: 紙に置く骨組みは1か所だけにする。置く場所は、親に名指されたのにまだ届いていない部品のうち、紙の順で先頭のもの（次に届く見込みの部品）の場所。**

- 紙の順は、根の子を上から、子の参照を深さ優先でたどった順（`src/browser/domain/main-view/a2ui-draft-pending.ts` の `draftPendingOf`）。`Report.figure` と `retrospective.blocks` の参照はたどらない（図は届いたらその場で描くが骨組みは置かない、草稿は振り返りを描かない）。
- 形は親の種類で決める。根の子が届いていなければ、見出しの骨組みと本文2行の骨組み。節の中の部品が届いていなければ、本文2行の骨組み。
- 届いた `Section` は、内容部品が届く前でも見出しを先に出す。次に届く見込みでない、届いていない根の子は何も描かない（`src/browser/features/report/a2ui-report-context.ts` の `sectionSlots`）。
- 骨組みは読み上げに出さない（`aria-hidden`）。書いている途中であることは紙の `aria-busy` が言う。
- 明滅は Astryx の `Skeleton` の動きをそのまま使う。動きを減らす設定（`prefers-reduced-motion`）と演出の速さ「切る」では明滅させず、止めた薄い帯にする。見るのは、草稿をマウントした時点の値だけ。
- 帯の色と寸法は `src/browser/features/report/leaf/pending-part.css`、部品は `src/browser/features/report/leaf/pending-part.tsx` の `PendingPart`。

| 案                                     | 種類   | 物差し                                                                                                                   | 判定     |
| -------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------ | -------- |
| 次に届く見込みの1か所にだけ置く        | 仕組み | 紙が先に伸びない。どこが書かれているかが1か所で分かる。読み込みの印は1つまでという AG-UI の規則とも合う                  | 採る     |
| 届いていない部品の全部に置く           | 仕組み | 実装して撮ると、根が届いた直後の紙が 728px になり、流れが末尾に張り付いて、届いた結論が画面の外へ出た（1か所なら 428px） | 採らない |
| 部品の数の棒（届いた数と名指された数） | 仕組み | 分母は節が届くたびに増え、割合が後戻りする。進み具合の棒に見えるものを、別の形で残すことになる                           | 採らない |
| 罫線の伸びる待ちの欄のまま             | 仕組み | どの部品を待っているかを言わない。末尾に固定で、紙の中の位置と結ばれない                                                 | 採らない |

### 論点 4: 草稿の画像の札

**採る: 書いている途中の草稿の画像は、読み込みを試みず、「画像はまだ出ない」と「レポートを書き終えると出る」の2行の札にする。読めなかった画像の札（斜めの縞と、斜線つきの印）と見分けるため、平らな地と斜線なしの印にする。**

- 画像を置き場へ置くのは `report` が受け付けられたあとなので、書いている途中は取り出し元が無い。読めなかった画像の札をそのまま出すと、失敗に見える。
- 取り出し元の種類に「まだ無い」（`pending`）を足し、札の文と形だけを替える（`src/browser/features/report/renderer/report-image.tsx` の `ReportImage`）。

### 論点 5: 余白の列は、札のある部品にだけ空ける

> この論点は、ADR 0067 論点 1 が取り下げた（余白の列と札が無くなり、内容部品はいつも本文の幅いっぱい。2026-11-18）。下に書いた実装の置き場は、取り下げで消えた。表の題を包みの幅で折り返す規則だけは残る。

**採る: 返す層の余白の列（幅 248px・本文との間 24px）を空けるのは、札（開いた欄・聞いた対・付箋）のある部品と、送った問いが記録に載るのを待っている部品だけにする。札の無い部品は本文の幅いっぱいに描く。列を出せる幅の規則（器から列と間を引いても本文が 30em 以上残る）は ADR 0055 論点 1 のまま。**

- 「聞く・頼む」の口: 列を出していない部品では、口を部品の外枠の右端に重ね、指した単位の上端の高さに出す（口の台に地を塗り、本文の字に重なっても読める）。列を出している部品では、列の左端（本体のすぐ右）に出す。
- 札が自分の部品より下へ伸びたとき: 札の横に来たほかの塊だけ、右を空ける。本文の根が札と塊の位置を測って印を付ける。`Row` は右を空けると列の幅が足りないので、縦に積む。
- 札の横の塊の右の空きは `margin` で取る。地や枠を持つ塊を `padding` で縮めると、地が札の下まで伸びる。規約の上限の表（`test/architecture/design-token-margin.test.ts`）は、この1宣言ぶんを上げた。
- `Row` のセル: セルを器（`report-body` の container）にする。セルの中の部品はセルの幅で狭い形に替わり、列を出せるかもセルの幅で決める。出せないセルでは、札をシートに出す。
- 欄の開け閉めで列が出入りすると本文が組み直されるので、指した単位を画面の同じ高さへ戻す（開け閉め1回につき1度）。問いを送ったあとは、記録に載るまで列を空けたままにし、欄を閉じてから札が届くまでのあいだに列を出し入れしない。
- 表の題: 札の無い表は紙の幅いっぱいになるので、題も包みの幅（表の幅）で折り返す。本文の段の幅（42em）で止めると、題だけが表より狭いところで折れる（`src/browser/features/report/renderer/report-notation-figure.css`）。
- 列の幅と条件は余白の列の CSS が持っていた。ADR 0058 論点 4 の境目（本文の器の幅 692px）は変わらない。

| 案                                     | 種類   | 物差し                                                                        | 判定     |
| -------------------------------------- | ------ | ----------------------------------------------------------------------------- | -------- |
| 札のある部品にだけ列を空ける           | 仕組み | 札の無い部品は紙の幅を全部使う。札を開いた部品だけが狭くなる                  | 採る     |
| レポート全体に列を空けたままにする     | 仕組み | 欄の開け閉めで本文が動かない。札が無いあいだも、紙の内側の約 38% が空く       | 採らない |
| 札を本文に重ねて出し、列を空けない     | 仕組み | 本文は動かないが、札が指した行の右側の字を隠す                                | 採らない |
| 札をいつもシート（下から出す板）に出す | 仕組み | 広い画面でも、指した所と札が離れる（ADR 0055 が余白の札を選んだ理由に反する） | 採らない |

### 論点 6: 下書きは、利用者が打つ依頼の文にする

**採る: 押すと入力欄へ入る下書きは、利用者がそのまま送れる依頼の文にする。残りの作業の文（`sessionRemaining`。状態を言う文）は札の字にだけ使い、下書きへ写さない。**

| 口                             | 前の下書き                                 | 後の下書き                                                                     |
| ------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------ |
| 続ける（残りの作業がある）     | 「続けて。」に残りの文                     | 「続きを進めて。」                                                             |
| 続ける（`Options` の採った案） | 「続けて。」に案の題                       | 案の題を鉤括弧で括り「で進めて。」                                             |
| 確かめる                       | 「確かめて。」と主張の行                   | 「次の点を確かめて。」と主張の行                                               |
| 確かめた・違った               | 「確かめた: 」「違った: 」に検証の行の名前 | 名前を鉤括弧で括り「を確かめた。問題なかった。」「を確かめたら、違っていた。」 |
| 別の案で進める                 | 案の題に「 で進めて。」                    | 案の題を鉤括弧で括り「で進めて。」                                             |
| 再開する                       | 「止めたところから再開して。」             | 変えない                                                                       |
| 前回の続き（始め方の一覧）     | 「前回の続き: 」に残り                     | 1行目「前回の続きを進めて。」、2行目「前回の残り: 」に残り                     |

- お願いの選択肢（`favorOptions`）があるレポートには、「続ける」を足さない。書き手が次の依頼を札で並べているので、同じ用件の口が2つになる。
- お願いの選択肢の `draft` の説明を「利用者がそのまま送る依頼の文」に改めた（`src/shared/report/a2ui-report-catalog.ts` の `favorOptionSchema`）。差し戻しの検査は足さない。
- 「前回の続き」は新しいセッションへ送るので、前回の残りを2行目に名前を付けて添える（`src/browser/components/page/conversation/domain/welcome-entry-list.ts` の `resumeRequestOf`）。同じセッションの「続ける」は、残りを書き手が知っているので添えない。
- 名前を鉤括弧で括るのは、名前の中の空白や読点で文の切れ目が分からなくならないようにするため。
- 規則は `src/browser/features/report/domain/next-step-plan.ts` の `buildNextSteps`。
- 「続ける（残りの作業がある）」の下書きは ADR 0066 が上書きする。

### 論点 7: 既存の ADR・文書の改め方

**採る: 既存の ADR は論点ごとに上書きし、全体の置き換えはしない。上書きされた論点には、この ADR を指す1行を足す（本文は書き換えない）。**

### 論点 8: 部品が閉じる前の字は出さない

**採る: 草稿の切り出しは、部品が閉じるたびに1つずつ送るまま（`src/server/report/core/body/draft-component-intake.ts` の `createReportDraftIntake`）にし、部品の途中の字は送らない。論点 1 の `progressiveKeys` の行は見送りから「採らない」に改める。骨組みは次に届く見込みの1か所のまま（論点 3）。**

2026-11-18 に、`report` だけを持たせた SDK を1ターンずつ走らせ、部品ごとに開いてから閉じるまでの秒数と字数を測った。依頼は架空のアプリの架空の事実（長い段落の不具合の報告・30〜50 行のコードを3つ載せる報告・長い段落の設計の提案）で、数えたのは部品の種類・時刻・字数だけ。本番の経路は変えず、計測の道具は測ったあとに消した。sonnet で3本、opus で2本、84 部品。

| 部品        | 数  | sonnet の秒数 | opus の秒数 | 最も長い字の欄の字数 |
| ----------- | --- | ------------- | ----------- | -------------------- |
| `Paragraph` | 42  | 0.9〜2.0      | 0.9〜1.9    | 77〜284              |
| `Code`      | 7   | 1.2〜3.4      | 3.8〜5.3    | 312〜1478            |
| `Report`    | 5   | 1.1〜3.6      | 3.8〜4.6    | 40〜84               |
| `Table`     | 6   | 0.8〜1.7      | 1.4〜3.4    | 13〜25               |
| `Section`   | 24  | 0.2〜0.4      | 0.3〜0.5    | 9〜21                |

- 骨組みのまま待つ時間がいちばん長いのは、opus の `Code`（約 1500 字で 5.3 秒）と、根の `Report`（結論と数のカードを持ち、4.6 秒）。段落は長いもの（約 280 字）でも 2 秒以内に閉じた。
- 部品は、読む速さより速く届く（段落 1 つが 2 秒以内）。利用者は前に届いた部品を読んでいるあいだに次が届くので、途中の字を出しても、読み終えるまでの時間はほとんど縮まない。
- 途中の字を出すと、引数の断片ごとに草稿を描き直す。断片は平均約 7 字（ADR 0040 の計測の 3476 字・516 断片）なので、280 字の段落 1 つで約 40 回、レポート全体で数百回になる。いまは部品 1 つにつき 1 回（このレポートの例で 15〜20 回）。
- 測ったのは 1 種類の依頼につき 1〜2 本で、ばらつきは測っていない。本番の書き手の規約（`report` の説明）は渡しておらず、部品のカタログだけを渡した。

| 案                                                          | 種類   | 物差し                                                                                       | 判定     |
| ----------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------- | -------- |
| 部品が閉じるたびに送るまま                                  | 仕組み | 骨組みのまま待つのは長くて約 5 秒。描き直しは部品 1 つにつき 1 回                            | 採る     |
| 字の欄（`Paragraph.text` など）の途中を断片が届くたびに送る | 仕組み | 段落が 1〜2 秒早く見えるだけで、読み終えるまでの時間は変わらない。描き直しが断片ごとに増える | 採らない |
| `Code.source` と `Report.conclusion` だけ途中を送る         | 仕組み | 待ちの長い 2 種は 1〜4 秒早くなるが、途中で切れたインラインの記法と送る形の変更を抱える      | 採らない |
| 一定の間隔・文の切れ目で途中を送る                          | 仕組み | 描き直しは減るが、早く見える時間がさらに縮む                                                 | 採らない |

### 論点 9: 草稿で主の図をその場で描き、選んでいないタブの見出しに途中の印を付ける

**採る: 主の図（`Report.figure`）は、届いたら草稿でもその場で描く。画像は論点 4 の札を図の場所に置き、高さは実物と違ってよい。図が届く前の骨組みは置かない。次に届く見込みの部品が選んでいない `Tabs` の中にあるときは、そのタブの見出しに「書いている途中」の印を付け、開いているタブは切り替えない。**

2026-11-18 に、主の図のある疑似セッションを 1400×900 で撮り、紙の上端から最初の節の見出しまでを測った。

| 場面             | 草稿    | 確定     | 動く量    |
| ---------------- | ------- | -------- | --------- |
| 主の図が Mermaid | 92.19px | 475.52px | +383.33px |
| 主の図が画像     | 92.19px | 614.16px | +521.97px |

- 図を描かなかった形では、確定のたびに図より下の本文が 380px から 520px 動いた。長いレポートで読んでいる位置が飛ぶ。
- 選んでいない `Tabs` の中が次に届く草稿では、骨組みが紙のどこにも出ず、書いている途中だと分からなかった。

図を草稿でも描くようにしたあとに、同じ場面を同じ幅で撮り直した（紙の上端から最初の節の見出しまで）。

| 場面             | 草稿     | 確定     | 動く量    |
| ---------------- | -------- | -------- | --------- |
| 主の図が Mermaid | 475.52px | 475.52px | 0px       |
| 主の図が画像     | 320.58px | 614.16px | +293.58px |

- 画像の草稿は札の高さで止まるので、実物との差だけ動く。選んでいないタブの見出しの途中の印（「案B …」）も同じ幅で出た。

| 案                                         | 種類   | 物差し                                                                                                             | 判定     |
| ------------------------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------ | -------- |
| 図を、届いたらその場で描く（画像は札）     | 仕組み | 確定での本文の動きが札と実物の高さの差だけになる。骨組みは増えない                                                 | 採る     |
| 図の場所に骨組みを先に置く                 | 仕組み | 図が届く見込みは根の `figure` の参照だけで決まるが、高さは図の種類で 383px から 522px と開き、骨組みでは動きが残る | 採らない |
| 今のまま描かない                           | 仕組み | 確定で 383px 以上動く                                                                                              | 採らない |
| 選んでいないタブの見出しに途中の印を付ける | 仕組み | 骨組みの場所が紙に無い問題を、利用者が開いたタブを動かさずに解く                                                   | 採る     |
| 選んでいないタブを開いて見せる             | 仕組み | 利用者が読んでいるタブを奪う                                                                                       | 採らない |
| `Tabs` の後ろに骨組みを置く                | 仕組み | 次に届く部品の場所と結ばれない（論点 3 の決まりに反する）                                                          | 採らない |

## この ADR が改めるもの

| 元の決定                                                                        | 扱い   | 改めた形                                                                           |
| ------------------------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------- |
| ADR 0040 論点 2「辿れない子は届くまで描かない」                                 | 上書き | 次に届く見込みの部品の場所にだけ骨組みを置く。届いた節は見出しを先に出す（論点 3） |
| ADR 0040 論点 3「草稿の面は中間レポートと同じ破線の箱に入れ、ラベルは付けない」 | 上書き | 最終レポートと同じ紙に入れ、ラベルは「書きかけのレポート」（論点 2）               |
| ADR 0051 論点 6 の下書きの文（「続けて。」「確かめて。」ほか）                  | 上書き | 依頼の文にする。お願いの選択肢があれば「続ける」を足さない（論点 6）               |
| ADR 0055 論点 1 の余白の列を出す範囲（出せる幅ならレポート全体）                | 上書き | 札のある部品にだけ空ける。幅の規則は変えない（論点 5）                             |
| ADR 0062 論点 12 の余白の案内を出す本文                                         | 絞る   | 指して聞ける本文にだけ出す（論点 2）                                               |

ADR 0040・0051・0055・0062 は今のステータスのままで、改めた論点に、この ADR を指す1行を足した。

2026-11-18、疑似セッションを同梱の撮影の道具で撮り、DOM の寸法を測った（依存を `@a2ui/react` 0.15.0・`@astryxdesign/core` 0.7.16 へ載せ直したあとの値）。
