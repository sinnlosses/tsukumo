# SDK の道具の境界と、ブラウザだけが読むように見える shared の描画の語彙の置き場（2026-11-06）

ステータス: 提案

**問い1（SDK の道具の境界をどこに置くか）は、案1C を推す。道具の名前・説明文・判定は持ち主の機能の `core/` に置いたまま、SDK の `tool()` で包む継ぎ目は `mcpServers` に載せる側の session-driver の adapter に残し、規約の文面をこの分け方に合わせて直す。問い2（ブラウザだけが読むように見える描画の語彙を shared から下ろすか）は、案2B を推す。型の辺まで辿ると、ブラウザだけが読むファイルは `src/shared/report/` に1つも無い。直接の読み手がブラウザだけの 13 ファイルも、残る shared のファイルから 12 本の import が入っていて、いまの形のままでは下ろせない。**
このファイルは利用者が決める前の比較の記録で、まだ何も決めていない。決まるまでコードと規約の文は変えない。

## 何が困っていたか

規約の文と、いまのファイルの置き場が食い違って見える箇所が2つある。

- `docs/architecture/server-feature.md` は「Agent SDK を import してよいのは、機能の `adapter/` の直下（または `adapter/sdk/`…）の `sdk-` で始まるファイルだけ」とし、「1つの箱にはまとめず、**その境界が属する機能に置く**」と続ける。ところが `report`・`work_plan`・`phase_result`・`question_brief`・`report_part_card`・`remember`/`forget`・`speak` の道具の境界5本は、すべて `src/server/session-driver/adapter/sdk/` に置いてある
- `docs/architecture/shared-contract.md` は「描画のためにブラウザだけが読むものやサーバだけが読むものは `shared` に置かず、それぞれの層へ置く（版を上げる理由にしない）」とする。ところが `src/shared/report/` には、直接の読み手がブラウザだけのファイルがある

どちらの文も、何を数えるかで読み方が変わる。問い1は「境界が属する機能」が道具の持ち主なのか、SDK に載せる側なのか。問い2は「ブラウザだけが読む」が直接の読み手のことなのか、推移で辿った読み手のことなのか。

- 道具の名前・説明文・答えを返す判定は、`report`・`work_plan`・`phase_result`・`question_brief`・`report_part_card` については、もう持ち主の機能の `core/` にある（`report-tool.ts`・`work-plan-tool.ts`・`phase-result-tool.ts`・`question-brief.ts`・`part-card.ts`）。session-driver の adapter に残っているのは、zod の形に説明文を付けて `tool()` で包み、handler で `CallReview` の判定を呼ぶ継ぎ目だけ

- `CallReview` の型の欄は、`report/core` の判定の型（`ReportVerdict`・`A2uiStructureVerdict` ほか）・`work-plan/core` の判定の型（`WorkPlanVerdict`・`PhaseResultVerdict`・`PhaseMentionVerdict`）・`speech-review.ts` の `SpeechVerdict` で組んである。`call-review.ts` は `report/core` を 8 本、`work-plan/core` を 2 本 import する。`reportEvents`（`sdk-report-message.ts`）は `report/core/body/` を 3 本 import する。共有モジュールは機能を読めないので、どちらもそのままでは `server/core/` へ移せない

### 推奨: 案1C

- 1B は、道具1本を持ち主へ寄せるたびに逆向きの組が要り、`speechShape` の辺で adapter の層に輪ができる。逆向きの組を消す 1B′ は、`CallReview` の型が機能の判定の型でできているので、判定の型を共有モジュールへ移す別の設計が前提になる
- 1A と 1C はどちらも移さずに済む。1A は「載せる側に置く」と書くだけで、道具の定義をどこに置くかを言わない。1C はいまの分け方（定義は持ち主の `core/`、`tool()` の継ぎ目は載せる側）を文面にするので、次に道具を足す人が定義を session-driver に書かずに済む

## 問い2: ブラウザだけが読むように見える描画の語彙の置き場

### 事実

`src/` と `test/` の depcruise の JSON（`pnpm exec depcruise src test --config .dependency-cruiser.cjs --output-type json`）から、`src/shared/report/` の 59 ファイルの読み手を3通りに数えた。テストと scripts は数えない。

| 数え方                                                                           | 「ブラウザだけ」のファイル      | 入る import                                                                            | テストの鏡（`test/shared/report/`） |
| -------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------- |
| 直接: `shared/report/` の中どうしとテストを除いた読み手が、すべて `src/browser/` | 13                              | 72（browser 38・`shared/report` 19〔うち 13 ファイルどうしの 7〕・test 15・scripts 0） | 8                                   |

server も読む: 59（型の辺も含めて推移で辿った読み手にサーバが入る）。

- 直接の 13 は `report-expression-block.ts`・`report-file-markdown.ts`・`report-file-tree.ts`・`report-inline-markdown.ts`・`plot-drawing.ts`・`plot-gauge.ts`・`plot-histogram.ts`・`plot-scatter.ts`・`report-caption.ts`・`report-notation.ts`・`timeline-markdown.ts`・`report-table-markdown.ts`・`report-fence.ts`。移すファイルからは 23 本の import が出ている（移すと相対の書き方が変わる）
- 13 には、13 の外に残る shared のファイルから 12 本の import が入る（`a2ui-report-catalog.ts`・`changed-file-section.ts`・`drawn-entry-markdown.ts`・`report-leaf-value.ts`・`report-phase-time.ts`・`report-tidy.ts`・`report-image-markdown.ts` から）。13 を browser へ移すと、この 12 本が shared → browser の辺になる
- その読み手を辿ると、サーバに行き着く。`report-leaf-value.ts` → `shared/session/report-drawn-markdown.ts` → `main-view-entry.ts` → `conversation-moment.ts` → `server/usage/core/experience/experience-metric.ts`、`report-tidy.ts` → `report-drawn-outline.ts` → `server/usage/core/experience/report-body-length.ts`、`a2ui-report-catalog.ts` → `server/report/core/rules/structure.ts` など
- `main-view-entry.ts` が `drawn-entry-markdown.ts` を読む1本を断っても、数は変わらない（値の辺で 1、型の辺も含めて 0）。`report-drawn-markdown.ts`・`changed-file-section.ts`・`a2ui-report-catalog.ts`・`report-drawn-outline.ts` の経路が残るため
- `shared-contract.md` のこの文は「版が守る範囲は `shared/session/` のイベント・状態・契約に限る」に続く文で、版を上げる理由にしない置き場を言っている

型の辺も含めて数えると、ブラウザだけが読むファイルは無い。下ろせるファイルが無いという意味で、問い2は前提の時点では当たらない。下の案は、「直接の読み手」で数えたときに下ろせるかの比較として並べる。

### 推奨: 案2B

- 型の辺も含めて数えると下ろせるファイルは 0 で、2A も 2C（値の辺）も、読む側を割る設計をしないと層の規則に当たる
- 描画の語彙は `shared/session/` の状態（`main-view-entry.ts` ほか）と、サーバの検査・使われ方の記録（`report/core/rules/`・`usage/core/experience/`）から推移で読まれている。文面を推移の読み手に合わせれば、いまの置き場が規約どおりになる
