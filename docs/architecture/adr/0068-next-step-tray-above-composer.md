# 次の一手を入力欄の頭の札の並びにする（2026-11-18）

ステータス: 採用

**次の一手を紙から外し、入力欄のすぐ上の「次の一手の並び」に置く。並びは見出しの1行・1行の札・下見の3段で、入力欄の上の帯のうちお願いの知らせは並びの見出しの1行へ合わせる。切断・終了・`/clear` の止め・お伺いの帯が出ているあいだは並びを出さない。押した札は畳まずに残し、今の下書きにその文が入っているあいだだけ印を付ける。並びは畳んだ形で出し、開いた状態は最終レポートごとに持つ（2026-11-19 の改訂。論点 4）。入力欄が空のときの ↑ は、お伺いの次に並びの先頭の札へ移る。760px 以下は札を1段の横送りにし、下見を出さない。タッチでも押せばすぐ入れる。**

この ADR は、ADR 0051 論点 6 の出す場所（レポートの末尾）と、ADR 0059 論点 5 の入力欄の上の知らせの出し方、ADR 0062 論点 8 の ↑ の移る先（お願いなら次の一手の最初の口）を置き換える。次の一手の作り方（種類・並び・下書きの文）は ADR 0051 論点 6・ADR 0064 論点 6・ADR 0066 のまま変えない。見本は `docs/history/mockup/next-step-2026-11-18/decided.html` で、言葉と食い違ったら見本が勝つ。

## 何が困っていたか

- 次の一手の行は紙の中、お願いの下に地の文と同じ色で並び、レポートの続きに見えた。広い画面（1400×900）では紙の末尾が入力欄より下にあり、レポートを開いた直後の画面に行が入らない（`reply-next` の場面で行の上端が 887px、ビューポートの高さは 900px で、その位置は入力欄に隠れる）。
- 札の字は押すと入る文ではなかった（別の変更で、入る文の1行目に直した）。
- 入力欄の上には、お願いの知らせの帯（「お願いが1件あります」）が別にあり、次の一手と同じ「利用者が次にすること」を2か所で言っていた。

## 利用者が決めたこと（2026-11-18）

- 置き場は入力欄の頭（見本 `compare.html` の案B）。紙の中からは外し、同じ札を2か所に出さない。
- 札は押すと入力欄に入る文そのものを主の字にし、切らない。押しても送らない。
- 札の形は `chips.html` の案②「1行の札と下見」。札はどれも同じ背の1行で、角の丸みは小さく（8px）、丸い札にしない。複数行の下書きは、札に1行目と点の数だけを出し、全文は札の並びの下の下見に出す。下見は触れた・フォーカスした札の文に替わり、最初は先頭の札の文を出す。
- 出すのは最新のやり取りの最終レポートだけ。利用者が動く用件は入力欄のそばに置く。

下の論点は、物差し「札を見ただけで、押すと次に何が起きるか（何の文が入力欄に入るか・送られないこと）が分かるか」と「見落とさないか」で書き手が決めた。

## 決めたこと

### 論点 1: 帯との並び

**採る: 入力欄の頭は上から「帯（1行）」か「次の一手の並び」のどちらか1つにする。切断・終了・`/clear` の止め・お伺いの帯は今の順で並びより先に出し、出ているあいだ並びは出さない。お願いの知らせは並びの見出しの1行の右端に「お願いが1件あります」「お願いへ」として合わせ、並びが無いときだけ今の帯で出す。**

- お伺いはターンの最中にしか届かず、ターンの最中は最新のやり取りに最終レポートが無いので、ふつうは並びと重ならない。重なるのは、最終レポートのあとにバックグラウンドタスクが聞いてきたときだけで、そのときは答えるのが先なので帯を出す。
- 切断のあいだは送れず、終了のあとは新しいセッションでないと頼めないので、押しても次に進めない札は出さない。`/clear` の止めは下書きの直しを求める帯で、札を押すと下書きが変わって帯の条件が崩れるので並べない。
- お願いの選択肢（`favorOptions`）は紙のお願いの欄に残す（並びに写さない）。並びの見出しの「お願いへ」は、今の帯と同じく見えていないあいだだけ出し、押すとお願いの欄へ送る。

| 案                                                            | 種類   | 物差し                                                                                                                      | 判定     |
| ------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------- | -------- |
| 帯か並びのどちらか1つ。お願いの知らせは並びの見出しへ合わせる | 仕組み | 入力欄の上が「次にすること」の1か所になる。帯の4種のあいだは押しても進めない札を見せない。背は並び1つ分                     | 採る     |
| 帯と並びを縦に積む（帯が上・並びが下）                        | 仕組み | 次にすることが2か所に分かれる。お願いの帯と並びが同時に出ると、同じ用件を2行で言う。入力欄の上が最大で帯1行分さらに高くなる | 採らない |
| お願いの選択肢も並びへ写し、紙のお願いの欄から選択肢を外す    | 仕組み | 札が1か所に集まるが、お願いの本文と選択肢が離れ、何を頼まれているかを読まずに押せてしまう                                   | 採らない |

### 論点 2: 札・見出し・下見の形

**採る: 見出しの1行は「次の一手」と、下書きが空なら「押すと下の入力欄に入る（送らない）」、字があれば「押すと下の入力欄の後ろに足す（送らない）」。札は種類の語（小さく）と主の字（入る文の1行目）を1行で出す。複数行の下書きは主の字の後ろに点の数（「2点」）を添える。下見は「押すと入る文」の語のあとに全文を出す。**

- 入力欄に字があるときは `appendDraft` で空行を挟んで後ろへ足すので、見出しの語でそれを言う（物差しの「何が起きるか」）。足す先の位置は下書きの末尾で、今の振る舞いのまま。
- 「確かめた」「違った」の対は、対ごとに2つの札として並べる（主の字はそれぞれの下書き。項目名の札は立てない）。
  - 改め: 利用者が「問題なければそのまま次へ移るので有用でない」と判断し、この対は外した。代わりに書き手が根の `nextSteps` で、レポートの中身から次に頼むと助けになる依頼を3つまで勧め、種類の語に書き手の `name` を出す（`docs/architecture/display/conclusion.md`「次の一手」）。
- 「別の案で進める」は札1つで、押すと並びの中のその札の後ろに案の札を開く（今の開閉と同じ）。

### 論点 3: 押したあと

**採る: 押しても並びは畳まず残す。押した札には、今の下書きにその札の文が入っているあいだだけ「入れた」の印（✓ と差し色の枠）を付ける。印の付いた札をもう一度押しても足さず、入力欄へフォーカスを送るだけにする。並びは、依頼を送ったときに消える（お願いの知らせを外すのと同じ時点）。**

| 案                                               | 種類               | 物差し                                                                                                                                  | 判定     |
| ------------------------------------------------ | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 残す。印は下書きにその文が入っているかから決める | 仕組み             | 「確かめた」を2行分押す・続けるに確かめるを足す、が並びのまま続けられる。印は下書きから求めるので、消したら印も消え、状態を別に持たない | 採る     |
| 押したら畳む                                     | 仕組み             | 2つ目を入れるのに開き直す手が要る。入れた文は入力欄に見えるので、畳んでも「何が起きたか」は増えない                                     | 採らない |
| 押した札を覚えて印を付ける（下書きを見ない）     | ヒューリスティック | 下書きから文を消しても印が残り、入っていない文を入れたように見える                                                                      | 採らない |

### 論点 4: 畳む口と開き直す時点

**2026-11-19 の改訂: 利用者が「領域を圧迫しないように、既定で畳んだ状態にする」と決めた。並びは最終レポートが届くたびに畳んだ1行（「次の一手 n件」と「開く」）で出し、「開く」で開いた状態をその最終レポートの間だけタブのメモリに持つ。次の最終レポートと再読み込みでは畳んだ形に戻る。畳んだ1行でも件数を出すので、次の一手があることは見落とさない。下の表と本文は改訂前の判断の記録。**

**その後の改め: 利用者の求めで、右端の「開く」「畳む」の口をやめ、見出しの「次の一手」の字（畳んだ形では件数と向きの線画を含む）を開閉の口にした。口は `aria-expanded` を持つボタン1つで、右端にはお願いの知らせだけが残る。**

**採る: 見出しの1行の右端に「畳む」の口を置く。畳むと並びは1行（「次の一手 n件」と「開く」。お願いの知らせがあれば右端に残す）になる。畳んだ状態は最終レポートごとにタブのメモリに持ち、次の最終レポートが届くと開いた形で出す。再読み込みでは開いた形に戻る。**

- 畳んだ1行でも件数を出すので、次の一手があることは見落とさない。
- 端末の好みに残すと、読み終えたレポートに「いつも畳む」が掛かり、新しい次の一手を見落とす。

| 案                                       | 種類   | 物差し                                                                       | 判定     |
| ---------------------------------------- | ------ | ---------------------------------------------------------------------------- | -------- |
| 最終レポートごとにメモリに持ち、次で開く | 仕組み | 新しい最終レポートの次の一手は必ず開いて見える。畳んだ理由は今のレポート限り | 採る     |
| 端末の好みに保つ                         | 仕組み | 一度畳むと、以後の最終レポートの次の一手も畳まれたままで見落とす             | 採らない |
| 畳む口を持たない                         | 仕組み | 札が多いときに入力欄の上が高いまま、流れを読む高さが削られる                 | 採らない |

### 論点 5: 狭い画面と高さの上限

**採る: 761px 以上は、札の並びを2段までの高さにし、超えた分は並びの中で縦に送る（下見は送る範囲の外の下に固定）。760px 以下は札を1段の横送りにし、下見は出さない（押すと入力欄に全文が入るので、入力欄が下見を兼ねる）。760px 以下でも見出しの1行と畳む口は出す。お願いの知らせは 760px 以下では今どおりレポートの冒頭の印が持つ。**

- 札が最も多いのは「再開する」「続ける」「確かめる」「確かめた・違った」の2対「別の案」の8枚（`buildNextSteps` の種類ごとの上限から数えた）。1400×900 の入力欄の幅（`reply-next` の場面で撮った画でおよそ 780px）に、見本 `decided.html` の札の字の大きさで8枚を並べると3段に回る見積もりなので、2段で切って中を送る。
  - **改訂（2026-11-27）: 既定の高さを3段に上げ、並びの上の仕切りで高さを変えられるようにする（761px 以上）。** 下書きが長い札は1枚で1段を占め、2段では3枚目から送りに回って狭かった。仕切りは札1段から札が全部見える高さまで動き、高さは `localStorage` の `tsukumo-next-step-tray-height:v1` に px で保つ。ダブルクリックで既定の3段に戻る。
- 下見を送る範囲の外に置くので、札が何段になっても下見の位置は動かない。
- 390 幅の見本では、見出し1行と札1段で背はおよそ 60px。下見（複数行の下書きは全文で数行）まで出すと背が下書きの行数で伸び、画面の頭と入力欄に挟まれた流れの高さを削る。

| 案                                                         | 種類   | 物差し                                                                         | 判定     |
| ---------------------------------------------------------- | ------ | ------------------------------------------------------------------------------ | -------- |
| 広い画面は2段で切って送る。狭い画面は1段の横送りで下見なし | 仕組み | 背の上限が決まる。どの幅でも押す前に主の字（入る文の1行目）が読める            | 採る     |
| 段数を切らずに全部出す                                     | 仕組み | 札が多いと入力欄の上が 4段を越え、流れが押し上がる                             | 採らない |
| 3段目以降を「ほか n件」の札にまとめる                      | 仕組み | 段の折り返しを測って札を選ぶ仕組みが要り、どの札が隠れるかが幅で変わる         | 採らない |
| 狭い画面は紙の中に残す                                     | 仕組み | 幅ごとに置き場が変わり、狭い画面では紙の末尾まで送らないと見えない（見落とす） | 採らない |

### 論点 6: 下見とタッチ

**採る: どの入力でも、押せばすぐ入れる。下見は最初に先頭の札の文を出し、触れた・フォーカスした・押した札の文に替わる。タッチでは触れる前に替える手が無いので、押した札の文が下見に残る（入れた文は入力欄にも出る）。**

| 案                                                 | 種類   | 物差し                                                                                          | 判定     |
| -------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------- | -------- |
| 押せばすぐ入れる（入力の種類で振る舞いを変えない） | 仕組み | 押すと入力欄に入り送られないことが、どの入力でも同じ。入れた文は入力欄に見え、消せば戻る        | 採る     |
| タッチは1押し目で下見・2押し目で入れる             | 仕組み | 1押し目に何も入らず、押したのに何も起きないように見える。マウスとタッチで同じ札の振る舞いが違う | 採らない |

### 論点 7: キー

**採る: 入力欄が空のときの ↑ は、お伺い → 次の一手の並び（開いているとき）の先頭の札 → お願いの欄の最初の押せる所、の順に、最初にあるものへ移る。並びの中は札1つ分のタブ止まりで、← → で札を移り、Enter・Space で押す。並びの中で ↓ か修飾キーなしの Esc を押すと入力欄へ戻る。並びの見出しの「お願いへ」には ↑ の印を添えない（↑ は並びへ移るので）。**

- 入力欄の中の ↑ ↓ ← → は、字があるときはカーソルの移動のまま（空のときの ↑ だけを使う。今と同じ）。並びの中の ← → はカーソルとぶつからない。
- 狭い画面・切断・終了のあいだは ↑ が効かない（今と同じ）。
- 札を押すと入力欄へフォーカスが移るので、並びの中に留まらない。続けて押すときは ↑ でまた先頭の札へ移る。

| 案                                                   | 種類   | 物差し                                                                                 | 判定     |
| ---------------------------------------------------- | ------ | -------------------------------------------------------------------------------------- | -------- |
| ↑ はお伺い → 並び → お願い。並びの中は ← → と ↓・Esc | 仕組み | 入力欄のすぐ上の物へ移る。並びとお願いのどちらに移るかが「並びが開いているか」で決まる | 採る     |
| ↑ はお願いを先、並びへは Tab だけ                    | 仕組み | すぐ上にある並びを飛ばして紙の中へ移り、画面が動く。並びへは Tab を何度か押す          | 採らない |
| 札ごとにタブ止まりを持たせる                         | 仕組み | 札が8枚のとき、入力欄から前の要素へ Tab で戻るのに8回要る                              | 採らない |

### 論点 8: 出す条件

**採る: 並びを出すのは、最新のやり取りに最終レポートが届いていて、そのやり取りを見ていて、論点 1 の4種の帯が出ていないときだけ。依頼を送ったとき（脇の話の送り方も含む）に消し、次の最終レポートが届くまで出さない。過去のやり取りを見ているあいだは出さない。書いている途中のレポート（草稿）からは作らない。**

- 止めたあと（`task.outcome` が `stopped` の最終レポート）は「再開する」が先頭の札になる。止めて最終レポートが無いときは並びを出さない。
- 過去のやり取りを見ているあいだに出すと、見ているレポートの続きに読める（ADR 0051 論点 6 の「古いレポートの次の一手は、今の作業の続きとして読めない」と同じ理由）。
- 紙の中のお願いの選択肢が押せる条件（最新のやり取りの最終レポートだけ）は変えない。

## 採らなかった案

- 置き場の案A（紙の下の独立した札）と案C（紙の末尾の区画と下見）は、利用者が案B を選んだので扱わない（見本 `compare.html`）。
- 札の形の案1（角丸の札）と案3（縦の行）は、利用者が案② を選んだので扱わない（見本 `chips.html`）。

## 影響

- 紙の中の次の一手の行を消す。`FavorFollowUp` は「お願いの欄」だけを描き、`nextSteps` は紙へ渡さず、最新のやり取りの最終レポートの次の一手を store（お願いの見え方の store と同じ形）で入力欄の側へ運ぶ。
- `ComposerBand` の `favor` は、並びがあるあいだは帯としては出さず、並びの見出しの右端に出す。↑ の移る先に並びを足す。
- 760px 以下の入力欄（`phone` の形）にも並びを置く。
- E2E の `reply-next` の場面と、期待する DOM の写しが変わる。
