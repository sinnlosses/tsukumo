# 質問の設計を Guidelines for Human-AI Interaction の則から決める（2026-11-10）

ステータス: 採用

**質問（`AskUserQuestion`・`question_brief`・お伺いのカードの質問の側）の決まりを、Amershi ほか「Guidelines for Human-AI Interaction」（CHI 2019）の18則だけから組み直す。質問の場面に効く則は G2・G3・G4・G8・G9・G10・G11・G12・G16 の9つ。添え書きは「聞く理由・利用者が見ていない事実・おすすめの理由と確度・選択肢ごとの戻せない印と図」に替え、どの則にも当たらない判断の軸・軸ごとの評価・良い点・悪い点を外す。カードはおすすめの理由と選択肢ごとの結果を触る前から見せ、問ごとに「任せる」で答えられるようにする。許可要求のカードは対象に入れない（文を書くのは書き手ではなく SDK の `canUseTool`）。**

利用者が決めたのは次の2つ（2026-11-10）。質問の設計の背骨は18則だけにし、ほかの手本から則を足さない。則で説明できない今の条・欄・画面の決まりは、この ADR が則に照らして残すか外すかを決める。

## 前提

### 選んだ思想と裏付け

- Amershi ほか「Guidelines for Human-AI Interaction」（CHI 2019、Microsoft）。150件を超える AI 向けの設計の推奨を18則にまとめ、UX・HCI の専門家と評価を重ねて絞った（Microsoft Research の掲載 <https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/>。2026-11-10 に読んだ）。
- 利用者の評価は Li ほか「Assessing Human-AI Interaction Early through Factorial Surveys」（ACM TOCHI。Microsoft Research の掲載では 2022年4月）。則を守った版と破った版を見せ、利用者の受け止め方を factorial survey で比べた。「1,300人に18本を走らせ、操作が成り立った16本が則の適用を支持した」という数は、着手時のタスクの記録が ResearchGate の要旨から写したもの。この ADR を書くときに読んだ Microsoft Research の掲載の要旨には載っておらず、ACM の本文は 403 で読めなかった。則ごとの効き目も確かめていない。
- 会話で比べたほかの候補は、完結幕僚作業・BLUF・GOV.UK の質問ページ・NN/g の確認ダイアログ・Windows のコマンドリンク・lazy consensus。AI と人のやり取りのために作られ、利用者の評価の数で裏付けがあるのは18則だけだった（2026-11-10 の会話）。今の質問の書き方は NN/g の確認ダイアログを参考にしていた（`docs/history/decision.md` に残した質問の書き方の経緯）。この ADR はその参考を18則に置き換える。

### 何が困っていたか

利用者は、質問で何を聞かれているのか、どう答えるのがよいのかが分からないことがあると言った（2026-11-10）。会話で見立てた出どころ4つを実物で確かめ、4つとも成り立った。

1. **背景の欄が書き手の側の事情だけを求めている。** `questionBriefSchema`（`src/shared/session-driver/question-brief.ts`）の `background` の説明は「背景。なぜ今聞くか・何が決まっていないかを2〜3文で」。利用者がまだ見ていない事実（ツールの出力・読んだファイル・数）を書かせる欄も説明も無い。
2. **おすすめの理由が選択肢を押すまで見えない。** 質問の書き方の条3は、理由を `description` の頭に書かせる。ところが広い画面のカードが `description` を出すのは、フォーカスした選択肢の詳細（`InquiryDetail`）だけで、触る前は詳細を出さない（`docs/architecture/screen-design/inquiry.md`「お伺い」）。狭い画面の答え待ちのカードは `description` を出さず、「詳しく」の板の中でしか読めない。
3. **作業中に生まれた語（段・控えなど）を、意味を添えずに問いと背景に書ける。** `QUESTION_NOTATION_PROMPT` の5条にも、添え書きの欄の説明にも、語の意味を添えさせる決まりが無い。
4. **比べる表の位置が場面で変わる。** 触る前は詳細の場所（広い画面では右の列）に開いて出し、触ったあとはカードの下に畳む。カードが狭ければ選択肢の下へ回り、狭い画面では板の中に出る（同じ節）。セリフやレポートが「下の表」のように位置で指すと、場面によって食い違う。2026-11-09 に起きた（タスクの記録による。リポジトリに再現の記録は無い）。

### いまの形

- 質問の書き方の節は `src/server/question/core/question-notation.ts` の `QUESTION_NOTATION_PROMPT`。5条で 659 字（2026-11-10 に字の数を数えた）。仕事モードのときだけ `systemPrompt` の append に載る。
- 添え書きの欄は `header`・`background`・`axes`・`options`（`label`・`pros`・`cons`・`byAxis`・`irreversible`・`figures`）。呼んだ時点の差し戻しと質問との突き合わせは `src/server/question/core/question-brief.ts`。
- カードは `src/browser/components/page/conversation/components/inquiry/` の `inquiry.tsx`・`inquiry-detail.tsx`。答えの組み立ては `conversation/stores/inquiry-answer.ts`、SDK へ返す文に畳むのは `src/server/session-driver/core/pending-answer.ts`。

## 論点 1: 質問の場面に効く則

**採る: 効く則は G2・G3・G4・G8・G9・G10・G11・G12・G16 の9つ。G13 と G15 は後段に入れない。残る7つ（G1・G5・G6・G7・G14・G17・G18）は質問の場面に効かない。** 名前と説明は Microsoft Research の掲載のまま引き、訳はこの表でだけ付ける。以下の節は則を番号で指す。

| 則  | 掲載の名前と説明                                                                                                                             | 訳                                       | 質問で                         | 当てる欄・画面・条                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| G1  | Make clear what the system can do. Help the user understand what the AI system is capable of doing.                                          | できることを分かるようにする             | 効かない                       | なし。質問は書き手のできることを説明する場ではない                                                              |
| G2  | Make clear how well the system can do what it can do. Help the user understand how often the AI system may make mistakes.                    | どれだけうまくできるかを分かるようにする | 効く                           | 欄 `facts` の `basis`（確かめた・写した）と `recommended` の `certainty`。今の条5を欄へ移す                     |
| G3  | Time services based on context. Time when to act or interrupt based on the user's current task and environment.                              | 文脈に合わせて時を選ぶ                   | 効く                           | 条1（聞くことは1回にまとめる）。自走のタスクで質問を拒む `tw ask-guard` はワークフローの側が持つ                |
| G4  | Show contextually relevant information. Display information relevant to the user's current task and environment.                             | 文脈に合う情報を見せる                   | 効く                           | 欄 `facts`・`figures`、条2（材料は添え書きに書き、位置で指さない。作業中の語に意味を添える）                    |

| G8  | Support efficient dismissal. Make it easy to dismiss or ignore undesired AI system services.                                                 | 手早く退けられるようにする               | 効く                           | 画面の「任せる」と、それが返す答えの文（論点 4）                                                                |

| G11 | Make clear why the system did what it did. Enable the user to access an explanation of why the AI system behaved as it did.                  | なぜそうしたかを分かるようにする         | 効く                           | 欄 `recommended` の `reason`、画面（触る前から見せる）                                                          |
| G12 | Remember recent interactions. Maintain short-term memory and allow the user to make efficient references to that memory.                     | 最近のやり取りを覚えておく               | 効く（同じセッションの中だけ） | 条4（聞き直さない）、答えた質問の記録（今のまま）。論点 6                                                       |

| G14 | Update and adapt cautiously. | G18 | Notify users about changes. Inform the user when the AI system adds or updates its capabilities.                                             | 変わったことを知らせる                   | 効かない                       | なし。質問の場面で書き手のできることは変わらない                                                                |

- **G13 を入れない理由**: 利用者がどの種類の問を任せたかを覚えるには、質問と答えをセッションの外へ残すことになる。会話のアーカイブは質問を書かない（`docs/coding-standards/conversation-content-read-back-and-boundary.md`）。会話内容の扱いは、ほかのどの規約よりも優先する。
- **G15 を入れない理由**: 質問ごとに「この問は要らなかった」を受け取る口になる。同じセッションの中では、論点 4 の「任せる」がその合図を兼ねる。セッションをまたいで残さない以上、G13 と同じく生かす先が無い。新しい口は足さない。

採らなかった案:

- 18則を全部当てる: 効かない則のために欄や条を作ると、書き手の手間と毎ターンの字数が増える。
- G13 を入れ、任された問の種類を覚えて聞く数を減らす: 上の会話内容の規約とぶつかる。

## 論点 2: 添え書きの欄

**採る: 添え書きの欄を次の形に替える。どの則にも当たらない `axes`・`byAxis`・`pros`・`cons` は外す。`background` は `whyAsk` と `facts` に分ける。**

| 欄                       | 中身                                                                                                                                                                                    | 則                     |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `header`                 | どの質問の添え書きか（今のまま）                                                                                                                                                        | なし（突き合わせの鍵） |
| `whyAsk`                 | 書き手だけで決められない理由。利用者の目的・好みのどこが分からないかを1〜2文で                                                                                                          | G10                    |
| `facts`                  | 利用者がまだ見ていない事実（ツールの出力・読んだファイル・数）。1件1文の `text` と、出どころの `basis`（`checked`＝このターンで打って確かめた、`copied`＝文書やタスクの本文から写した） | G4・G2                 |
| `recommended`            | おすすめの理由（`reason`。1〜2文）と確度（`certainty`。`high`・`medium`・`low`）。おすすめが無ければ省く                                                                                | G11・G2                |
| `options[].label`        | 質問の選択肢の `label` と同じ字（今のまま）                                                                                                                                             | なし（突き合わせの鍵） |
| `options[].irreversible` | 選ぶとあとで戻せないか（今のまま）                                                                                                                                                      | G9                     |
| `options[].figures`      | 選んだときの形を見せる図（今のまま）。見た目・画面の形・データやコードの構造を選ばせるときは必ず付ける、という今の条4を欄の説明へ移す                                                   | G4                     |

- どの選択肢を勧めるかは、今のままラベル末尾の印（`(推奨)`）だけが持つ。`recommended` は理由と確度だけを持ち、選択肢を名指さない。
- 欄の名前を `recommendation` にしないのは、その識別子をおすすめのカードの機能・状態の欄・イベントが使っているため（`docs/glossary/conversation-phase.md`「おすすめのカード」）。質問の側は印の判定 `isRecommendedLabel` と同じ `recommended` にそろえる。
- 選択肢ごとの結果（G16）は、`AskUserQuestion` の選択肢の `description` に1行で書かせ、添え書きには写さない。
- 今の `background` の「何が決まっていないか」は、問いの文が持つ（今の条1のまま）。

理由:

- 出どころ1は、欄が利用者の側の材料を求めていないことだった。`facts` の欄で求めれば、書き手は欄を埋めるときに、利用者が見ていない事実を探す（G4）。
- `basis` は、今の条5（打って確かめた数と、写した数を分ける）を欄へ移したもの（G2）。条で頼むより欄で縛るほうが守られる。添え書きを足したときも「モデルのお願いに留めると守られなかった」（`docs/history/decision.md` に残した質問の添え書きの経緯）。
- 出どころ2の理由の置き場を `description` から添え書きへ移すと、画面は触る前から理由を出せる（G11。論点 3）。
- 判断の軸・軸ごとの評価・良い点・悪い点は、どの則にも当たらない。G11 が求めるのは、書き手がなぜそれを勧めるかの説明で、選択肢を軸ごとに評価した表ではない。G16 が求めるのは、操作が書き手のこの先の動きにどう効くかで、選択肢の良し悪しの一覧ではない。良い点・悪い点のうち、結果に当たるものは `description` の1行へ、勧める理由に当たるものは `reason` へ入る。戻せないことは `irreversible` が持つ。
- おすすめの印をラベルに残すのは、添え書きの無い質問（選択肢が1つ以下）にも、SDK へ返す答え・今の並べ替え・狭い画面の塗りにも、同じ1か所で効くため。

採らなかった案:

- `background` の説明だけを書き替え、欄はそのまま残す: 出どころ1は直るが、確かめた事実と写した事実の区別（G2）を欄で縛れない。
- 良い点・悪い点を G11 の説明として残す: 選択肢の数だけ書き手の手間が増え、触るまで見えないことも変わらない。勧める理由は `reason` の1〜2文で足りる。
- 判断の軸と比べる表を残す: どの則にも当たらない。出どころ4の、位置が場面で変わる部品でもある。
- `recommended` に `label` を持たせ、勧める選択肢を添え書きで名指す: どれを勧めるかを書く場所が、ラベルの印と合わせて2つになる。
- 選んだあとの書き手の動き（G16）を、添え書きの選択肢ごとの欄にする: `AskUserQuestion` の `description` と中身が重なる。
- 答えたあとの直し方（G9）を、選択肢ごとの欄にする: 戻せる選択肢では「あとで頼めば戻せる」と書くだけになる。戻せない場合は `irreversible` が持つ。

課題の分け方: 欄・呼んだ時点の差し戻し・質問との突き合わせ（論点 7）・道具の説明と欄の説明・画面へ運ぶ型（`PROTOCOL_VERSION` を上げる）・疑似セッションの場面（`question-brief`・`phone-inquiry-pick`）と、ブラウザの添え書きの塊（論点 3 の並びの (2)〜(4)）・答えた質問の記録の畳みを、1つの課題でまとめて替える。`QuestionBrief` の型はブラウザも読むので、欄を外すとブラウザの描画も同じ差分で直さないと型の検査が通らない。

## 論点 3: カードの並びと出し方

**採る: 広い画面のカード・広げた板・狭い画面の板・答えた質問の記録の畳みは、同じ並びで出す。上から順に、(1) 問いの文、(2) 聞く理由（`whyAsk`）、(3) 利用者が見ていない事実（`facts`。出どころの印つき）、(4) おすすめの理由と確度、(5) 選択肢の並び（番号・ラベル・バッジ・`description` の1行）、(6) フォーカスした選択肢の図と `preview`、(7) 操作の行（戻る・任せる・次へ／これで答える）。比べる表は無くす。**

- 選択肢の `description` は、選択肢の並びの行に出す（今はフォーカスした選択肢の詳細にしか出ない）。G16。
- おすすめの理由と確度は、選択肢の並びの直前に、触る前から出す。G11・G2。
- 詳細の欄に残るのは図と `preview` だけ。どの選択肢にも図と `preview` が無ければ詳細の欄を出さず、2列にもしない。触る前は今の案内の1行（「選択肢を押すと詳細が出ます」）だけを出す。
- 狭い画面の答え待ちのカード（入力欄の上）は、問いのすぐ下におすすめの理由を1行で出す（`recommended` のある質問だけ）。聞く理由と事実は「詳しく」の板で読む。答えのボタンの並びに「任せる」を足す。
- 答えた質問の記録の「質問のときの詳細」の畳みは、上の並びから操作の行を除いたもの。任せた問は、答えの行に「任せた」と出す。
- 許可要求のカードは変えない。

理由:

- 出どころ2は、理由が触ったあとにしか見えないことだった。G11 の「説明を見られるようにする」を、触る前から見えるようにすることで満たす。
- おすすめをカードの頭ではなく選択肢の直前に置くのは、勧める理由が事実を指すため。事実を読んでから理由を読む並びにする。問いの文 → 聞く理由 → 事実の順は、何を決めるか、書き手が何を分かっていないか（G10）、判断の材料（G4）の順。
- 4つの面を同じ並びにすれば、どの面でも同じものが同じ順に並ぶ。出どころ4の、位置が場面で変わる部品は比べる表だけで、論点 2 で無くなる。
- 狭い画面の答え待ちのカードは高さ 50dvh までで、答えのボタンをカードの下端に残す。足すのは理由の1行だけにし、事実は板へ回す。

採らなかった案:

- おすすめと理由をカードの頭（問いの文の上）に置く: 理由が指す事実を、まだ読んでいない。
- 触る前の比べる表を残し、おすすめの行を足す: 論点 2 で軸を外したので、表の中身が無い。
- 狭い画面の答え待ちのカードに事実まで出す: 50dvh に収まらず、答えのボタンが押し下げられる。

課題の分け方: (2)〜(4) の添え書きの塊と記録の畳みは、論点 2 の課題が新しい欄と一緒に作る。選択肢の行の `description`・詳細の欄を図と `preview` に絞ること・2列にする条件・狭い画面の答え待ちのカードの理由の1行・論点 4 の「任せる」は、2つ目の課題にまとめる。どちらの課題も描画を変えるので、広い画面のカード・広げた板・狭い画面の答え待ちのカードと板・記録の畳みを撮って目視を受けてから、E2E を撮り直す。

## 論点 4: 「任せる」の答え

**採る: 質問のカードに「任せる」を足す（G8）。押すと、いま見ている1問の答えを「任せた」として確定し、次の問へ進む（最後の問なら送る）。SDK へ返す答えの文は tsukumo が決める。中身は「判断を任せる。おすすめがあればそれを、無ければあとで戻せる選択肢を選んで進め、何を選んだかを伝える」の3つで、字面は課題が決める。**

- 置き場は、広い画面のカードと広げた板の操作の行、狭い画面の答え待ちのカードの答えのボタンの並び、狭い画面の板の下端。許可要求のカードには出さない。
- 入力欄の自由入力は、今のまま「選択肢に無い答え」を書く口で、「任せる」とは別のもの。「任せる」を押したときは入力欄の字を答えに使わず、下書きのまま残す。
- 答えの文を持つのは、SDK へ返す文に畳む `pending-answer.ts` の1か所。ブラウザは「任せた」という種類の答えを送り、文を組まない。答えた質問の記録には「任せた」と出す。
- 問が複数あるときは、問ごとに押す。残りを全部まとめて任せる口は作らない。

理由:

- G8 は、要らない働きを手早く退けられること。質問の場面の「要らない働き」は、利用者が決めたくない問。今は選択肢を選ぶか、入力欄に「任せる」と書くしかない。書くのは手早くなく、書き方によって書き手の受け取り方も揺れる。
- 答えの文に「おすすめが無ければ戻せるもの」を入れるのは G10、「何を選んだかを伝える」を入れるのは G9 と G11 による。この文は「任せる」を押したときだけ書き手に届くので、毎ターンの規約の字数を増やさない。
- 文を組むのを `pending-answer.ts` の1か所にするのは、今の答えの畳み方（複数選択をつなぐ字）と同じ置き場で、字面を変えるときも1か所で済むため。

採らなかった案:

- 足さない（入力欄に書けば足りる）: 上の理由。
- 書き手に「任せる」の選択肢を毎回入れさせる: 選択肢の上限（4つ）を1つ使い、入れ忘れても縛れない。添え書きとの突き合わせにも例外が要る。
- 残りを全部任せる口を足す: 問ごとに重さが違う。戻せない選択肢のある問までまとめて任せることになる（G9）。

## 論点 5: 聞くかどうかの関門

**採る: 関門の本体は、質問の書き方の節の条1に短く置く。添え書きの `whyAsk` の欄で、決められない理由を書かせる。** 条1の中身は「聞くのは、利用者の目的や好みが分からず、書き手が決めると外れやすいか戻せないときだけ。決められることは決めて進め、レポートで伝える。聞くことは1回にまとめる」（G10・G3）。

- 節の字数は、今の 659 字以下にする。条5（事実の出どころ）を `facts` の `basis` へ、条4（図）を `figures` の欄の説明へ、条3の理由の置き場を `recommended` へ移した分で、関門の字をまかなう。
- `whyAsk` の欄の説明は、利用者の目的・好みのどこが分からないかを書かせ、書けないなら聞かずに進める、と添える。

理由:

- 関門は、聞くと決める前に効かないと意味が無い。`question_brief` の道具の説明と欄の説明は、聞くと決めてから読まれる。だから本体は、セッションの始めから載る質問の書き方の節に置く。
- 欄で理由を書かせると、書き手は関門を通ったかを自分で文にして確かめ、その文は利用者にも見える（論点 3 の (2)）。仕組みで縛れるのは、欄が空でないことまで。
- G3 のうち、自走のタスクで質問を拒むのは、ワークフローの側の `tw ask-guard` がすでに持つ。tsukumo の側は「聞くことは1回にまとめる」だけを条に書く。

採らなかった案:

- 道具の説明だけに置く: 上の理由。
- サーバが質問の要否を判定して断る: 要否は文の中身でしか決まらず、判定できない。
- 関門のための節を別に足す: 毎ターンの字数が増える。

## 論点 6: 決めたことを聞き直さない

**採る: 同じセッションの中だけを支える。支えは、SDK の会話に残る質問と答え（`AskUserQuestion` の結果）と、質問の書き方の節の条4「一度答えを得たことは聞き直さない」。答えた質問の記録（画面）は、利用者が前の答えを見返す場所として今のまま残す。あらすじでは支えない。**

理由:

- G12 は、短期の記憶を持ち、利用者がその記憶を手早く参照できること。同じセッションの書き手は、答えを会話の中に持っている。利用者は答えた質問の記録で読める。
- あらすじや会話のアーカイブで支えるには、質問と答えをセッションの外へ書くことになる。会話のアーカイブは質問を書かない（`docs/coding-standards/conversation-content-read-back-and-boundary.md`）。会話内容の扱いは、ほかのどの規約よりも優先する。
- タスクの本文の「決まっていること（蒸し返さない）」は、決めたことをセッションをまたいで運ぶ。ただしこれはワークフローの側の契約で、tsukumo の質問の決まりはそれに頼らない（`docs/architecture/adr/0024-no-skill-dependency.md`）。

採らなかった案:

- 答えた質問をあらすじへ畳む: 上の理由。
- 答えた質問の記録を書き手へ読み戻す: 同じセッションでは会話にすでにあり、二重になる。セッションをまたぐなら、上と同じ理由で書けない。

## 論点 7: 検査で縛るものと、文面で頼むもの

**採る: 形で決まるものは検査で縛り、中身の良し悪しは文面で頼む。**

| 決まり                                                           | 則          | 縛り方                           | 置き場                    |
| ---------------------------------------------------------------- | ----------- | -------------------------------- | ------------------------- |
| 選択肢が2つ以上の質問には添え書きが要る                          | G4・G11     | 質問を断る（今のまま）           | `reviewQuestionBriefing`  |
| 添え書きの選択肢の `label` の集合が質問と合う                    | なし（鍵）  | 質問を断る（今のまま）           | `reviewQuestionBriefing`  |
| おすすめの印と `recommended` の有る無しが合う                    | G11         | 質問を断る（新しく足す）         | `reviewQuestionBriefing`  |
| `whyAsk` が空でない                                              | G10         | 呼んだ時点で差し戻す             | `answerQuestionBriefCall` |
| `facts` が1〜5件で、空の `text` が無い                           | G4          | 呼んだ時点で差し戻す             | `answerQuestionBriefCall` |
| `facts` の `basis` が `checked` か `copied`                      | G2          | 型                               | `questionBriefSchema`     |
| `recommended` の `reason` が空でない                             | G11         | 呼んだ時点で差し戻す             | `answerQuestionBriefCall` |
| `recommended` の `certainty` が `high`・`medium`・`low` のどれか | G2          | 型                               | `questionBriefSchema`     |
| 図は選択肢1つに2つまで                                           | G4          | 呼んだ時点で差し戻す（今のまま） | `answerQuestionBriefCall` |
| 「任せる」の答えの文                                             | G8・G9・G10 | tsukumo が組む                   | `pending-answer.ts`       |
| 事実は利用者がまだ見ていないもの                                 | G4          | 文面                             | `facts` の欄の説明        |
| 作業中に生まれた語に意味を添える                                 | G4          | 文面                             | 条2                       |
| 質問の材料を画面の位置で指さない                                 | G4          | 文面                             | 条2（論点 8）             |
| 聞くのは決められないときだけ、1回にまとめる                      | G10・G3     | 文面                             | 条1・`whyAsk` の欄の説明  |
| ラベルは選んだあと書き手がすること、`description` はその結果     | G16         | 文面                             | 条3                       |
| 一度答えを得たことは聞き直さない                                 | G12         | 文面                             | 条4                       |
| 見た目・画面の形・構造を選ばせるなら図を付ける                   | G4          | 文面                             | `figures` の欄の説明      |

- 質問の時点の断りの文（`reviewQuestionBriefing`）は今のまま、`header` と数だけを言い、質問文・ラベル・添え書きの字を入れない。新しく足す断り（おすすめの印と `recommended` の有る無し）も質問文・ラベル・添え書きの字を入れない。
- 呼んだ時点の差し戻しの文（`answerQuestionBriefCall`）は今のまま、直す箇所を `header` と選択肢の `label` で名指してよい。新しく足す差し戻し（`whyAsk`・`facts`・`recommended` の `reason`）も同じ決まりに従う。

理由:

- 形で決まるものを文面に残すと守られない（論点 2 の理由と同じ経緯）。中身の良し悪し（事実が利用者にとって新しいか、語が作業中に生まれたものか）は、サーバに判定の材料が無い。
- おすすめの印と `recommended` の突き合わせを質問の時点にするのは、印が `AskUserQuestion` のラベルにあり、`question_brief` を呼んだ時点ではまだ届いていないため。

採らなかった案:

- `facts` を0件でも通す: 出どころ1の、書き手の側の事情だけで済ませる形に戻る。質問に至った材料が1つも無いなら、聞く理由（G10）も無い。
- 位置を指す語をセリフから拾って差し戻す: 「上の」「下の」は、位置で指していない文にも出る。

## 論点 8: 質問の材料を位置で指す件

**採る: G4 で扱う。答えるのに要る材料は全部カードに載せ（論点 2・3）、質問の書き方の条2に「質問の材料をセリフやレポートから画面の位置で指さない」を入れる。**

理由:

- G4 は、いまの作業に合う情報をその場で見せること。材料がカードに全部あれば、セリフやレポートが別の場所を指す理由が無くなる。
- 位置が場面で変わる部品だった比べる表は、論点 2・3 で無くなる。それでも「下の選択肢」のように指すと、狭い画面（答え待ちのカードは吹き出しの下）と広い画面（カードはメインビューの本文の末尾、吹き出しはキャラクターの側）で食い違う。条で頼む。
- 利用者がカードへ移る口は、入力欄の上の帯の「お伺いへ」と、メインビューの下端の「お伺い ↓」が今もある。セリフから指す必要は無い。

採らなかった案:

- 扱わない: 2026-11-09 に起きている。条の1句で頼める。
- セリフからカードへ移る印を作る: セリフは字だけを持つ。「お伺いへ」と「お伺い ↓」が同じ役を持つ。
- セリフの字を機械で検査する: 論点 7 の理由。

## 質問の書き方の節の中身

論点 5・6・8 が指す条1〜4の中身。字面は課題が書き、節全体を 659 字以下にする。

1. 聞くのは、利用者の目的や好みが分からず、書き手が決めると外れやすいか戻せないときだけ。決められることは決めて進め、レポートで伝える。聞くことは1回にまとめる（G10・G3）
2. `AskUserQuestion` の直前に `question_brief` で添え書きを渡し、問いの文には何を決めるかだけを書く。答える材料は添え書きに書き、セリフやレポートから画面の位置で指さない。作業中に生まれた語は使わないか、意味を添える（G4）
3. 選択肢のラベルは選んだあと書き手がすることを言う語にし、`description` にはその結果を1行で書く。おすすめはラベル末尾に `(推奨)` を付け、理由は添え書きの `recommended` に書く（G16・G11）
4. 一度答えを得たことは聞き直さない（G12）

今の条1は新しい条2に、今の条2と条3は新しい条3に入る。今の条4（図）は `figures` の欄の説明に、今の条5（事実の出どころ）は `facts` の `basis` に移る。
