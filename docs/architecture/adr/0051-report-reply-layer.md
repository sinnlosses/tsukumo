# 返す層: レポートの部品を指して「聞く」「頼む」、末尾から「続き」を選ぶ（2026-11-08）

ステータス: 採用

**レポートの本文に、読み手が会話へ返すボタンを置く。「聞く」は部品を指した問いを補足メッセージとして送り、作業を始めずに `speak` 1回で答えさせる。補足メッセージは待ちのときにも使えるようにする。「頼む」は送らずに付箋を作り、付箋は入力欄の上の列で順番を決めてから1つの下書きにまとめる。「続き」はレポートの末尾に次の一手のボタンを並べ、押すと下書きが入る。どのボタンも、押した結果が画面に必ず出る。会話へ送る口を持たない描画にはボタンを出さない。**
返す操作を3つにすること、聞く・頼む・続きの形と見え方、待ちのときにも補足メッセージを使うこと、聞くの答えをセリフだけにすること、付箋と次のレポートの答えを機械で結ばないことは、2026-11-08 に利用者が試作の画を見て決めた（下の「利用者が決めたこと」）。それ以外の論点（読むだけの面との両立・指した所の形・送り方の語・付箋の置き場・下書きの文面・次の一手の作り方・機能の境界）はこの ADR が決める。

## 何が困っていたか

- **本文は読むだけの面だった。** `src/browser/features/report/renderer/task-check.ts` は、押せるように見えて何も起きない操作部品を本文に並べないため、チェックリストを印に畳んでいる。ADR 0039 の論点 7 が入れた操作（表の並べ替え・絞り込み）は見え方を変えるだけで、状態はデータモデルの `/view/` に置き、イベントにも記録にも載せない。会話へ何かを送るボタンは本文に無い。
- **補足メッセージは委譲中だけのものだった。** `src/server/session/core/session-command.ts` の `promptOpening` は、仕事のとき・バックグラウンドのタスクが1件以上・送り方が `aside-when-background` のときだけ補足メッセージにする。包みの説明の1行（`src/server/session-driver/core/aside-prompt.ts` の `ASIDE_NOTE`）も「委譲中に利用者が送った補足メッセージ」と言う。待ちのときに作業を始めずに答えさせる手段が無い。
- **部品を指して返す手段は「引いて聞く」だけだった。** 字を選んで入力欄の頭へ引用する（`use-selection-ask.ts`・`composer-draft.ts` の `prependToDraft`）。表の行・案・主張を単位では指せず、1回に1か所しか指せない。答えは指した所に戻らない。

## 利用者が決めたこと

見本は `docs/history/mockup/report-interactive-2026-11-08/` の `reply-ask-open.png`・`reply-ask-request-mode.png`・`reply-ask-waiting.png`・`reply-ask-answered.png`・`reply-notes.png`・`reply-drafted.png`・`reply-sent.png`・`reply-running.png`・`reply-next.png`。言葉の説明と食い違ったら見本が勝つ。

- 返す操作は「聞く」「頼む」「続き」の3つにする。押しても何も送らない「了解」の印は置かない。
- **聞く**: 部品の右上（重ねたときとフォーカスしたときに出る）と、表の行の右端のボタンから、部品の下にその場の入力欄を開く。欄の頭に指した所（節 › 部品の題 › 行の1列目）を出す。送ると、作業を始めずに答える。答えは聞いた部品の下に問いと答えの対で残り、吹き出しにも出る。待つあいだは「作業は始めていない」と出す。部品の題の行に「聞 n・答え待ち」か「聞 n・答えた」のバッジを、やり取りの列の節に「聞 n」を出す。答えの下に「これを頼む」「続けて聞く」を置く。
- **待ちのときの聞く**: 補足メッセージの仕組みを、待ちのとき（バックグラウンドのタスクが無いとき）にも広げる。
- **聞くの答えの形**: セリフ（`speak` 1回）だけ。表やコードで答えてほしい問いは、頼むで新しい依頼にする。
- **頼む**: その場の入力欄を頼むに切り替えると、送るボタンが「付箋にする」になり、会話へは送らずに付箋にする。案の「この案で進める」は「この案で進めて。」、推測・未確認の主張の「確かめて」は「確かめて。確かめ方: …」を中身にして付箋にする。付箋は本文の右の欄外に並び、「まだ送っていない」と出て、× で外せる。付箋にした所のボタンは「付箋にした」に変わる。やり取りの列の節に「頼 n」を出す。
- **頼みごとの列**: 入力欄の上に、まだ送っていない付箋を順に並べる。順番を変えられる。「まとめて頼む」で、指した所と中身を番号順に並べた下書きを入力欄に入れる（送らない）。送るのは利用者の ⌘⏎ で、送ったあとの付箋には「送った」と送ったやり取りの番号を出す。
- **付箋と答え**: まとめて頼んだ付箋と、次のレポートの答えは機械で結ばない。付箋には送ったやり取りの番号だけを出す。
- **作業中**: 聞くはいつでも送れる。頼みごとの列のボタンは「終わったら頼む」になり、作業が終わったときに下書きを入れる（送らない）。
- **続き**: レポートの末尾（お願いの下）に「次の一手」のボタンを並べる。元にするのは `sessionRemaining` と `Options` の採った案（続ける）、`Claims` の推測・未確認（確かめる）、`Options` の検討・見送りの案（別の案で進める）、`task.outcome` が `stopped` のレポート（再開する）。押すと下書きを入れるだけで、送らない。
- 採らない案: 全部を1つの列に溜める・押したらすぐ送る・作業が終わったら溜めた分を自動で送る・聞くを別のセッションで答える。

## 決めたこと

### 論点 1: 読むだけの面の線を引き直す

- **線は「押せる見た目の部品は、押した結果が必ず画面に出る手続きに結ぶ」に引き直す。** `task-check.ts` の理由（押せるように見えて何も起きない部品を並べない）はそのまま守る。チェックリストは今までどおり印に畳み、返す層の対象にしない。返す層のボタンは、どれも押すと画面が変わる（その場の入力欄が開く・付箋が増える・入力欄に下書きが入る）。
- **ボタンを描くのは、会話へ返す口（論点 7 の `ReplyPort`）が渡された描画だけにする。** 口の無い描画（見本帳・会話の画面の外の見せ方）はボタンを出さない。押しても何も起きないボタンが出る道を、型で塞ぐ。
- **ADR 0039 の論点 7 を広げる関係にする。** 論点 7 の操作（並べ替え・絞り込み・つまみ）は見え方だけを変え、`/view/` に置き、記録に載せない。この決めは変えない。返す層は、それとは別の「会話へ返す操作」の種類として足す。
- **ボタンの置き場**は次の5つ。
  - 内容部品の外枠（`report-leaf-frame.tsx`）の右上に「聞く」「頼む」を出す。重ねたときとフォーカスしたときだけ出す。配置の部品・頭の欄（要点の数・確かめたこと・振り返り）・`Report.figure` には出さない。
  - `Table` の各行の右端に「聞く」「頼む」を出す。重ねた行とフォーカスした行にだけ出す。
  - `Options` の各案に「この案で進める」を出す（採った案にも出す）。
  - `Claims` の推測・未確認の主張に「確かめて」を出す。確かめた主張には出さない。
  - お願いの欄の下に「次の一手」の行を出す（論点 6）。
- **ボタンの状態（答え待ち・答えた・付箋にした）は `/view/` に置かず、出どころから導く。** 答え待ち・答えたは画面の状態の補足メッセージ（論点 2 の鍵つき）から、付箋にしたは付箋の置き場（論点 4）から、描くたびに求める。`/view/` は面ごとのデータモデルで、開き直すと初期化され、書き手の部品の木の中に閉じる。状態の出どころが記録と付箋の置き場にあるのに `/view/` へ写すと、出どころが2つになる。

| 案                                                       | 種類         | 物差し                                                                                           | 判定     |
| -------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------ | -------- |
| 口が渡された描画だけボタンを出し、状態は出どころから導く | 仕組み（型） | 開くファイルは部品と口の型だけ。口が無ければ型の上でボタンが作れず、押しても何も起きない道が無い | 採る     |
| ボタンは常に描き、口が無ければ押せない見た目にする       | 仕組み       | 呼ぶ側が「どの描画で押せるか」を知らないと正しく描けない。押せない見た目のボタンが並ぶ           | 採らない |
| ボタンの状態を `/view/<部品の ID>/reply` に置く          | 仕組み       | 開き直すと消え（黙って効かなくなる）、記録・付箋の置き場との二重の出どころになる                 | 採らない |

### 論点 2: 指した所の形

指した所（`ReplyTarget`）は、Claude へ渡す字（`label`）と、ブラウザが答えを戻す鍵（`key`）の2つを持つ。

- **`label`**: `section`（節の見出し。無ければ省く）・`component`（部品の題。無ければ部品の種類の名前）・`row`（表の行の1列目の字。行を指したときだけ）。Claude へは `›` でつないだ1行で渡す（`指した所: 検査ごとの所要 › 表「架空の検査ごとの所要」 › E2E（会話）`）。図表番号は描くときに振るもので Claude の引数に無いため、`label` に入れない。
- **`key`**: `reportToolUseId`（その `report` の呼び出しの id）・`componentId`（書き手が付けた部品の ID）・`rowIndex`（書き手が書いた行の並びでの添字。並べ替え・絞り込みのあとの並びではない）。`report` の呼び出しの id は transcript に残り、組み直しでも同じ値になる。同じやり取りの中間レポートと最終レポートも見分けられる。
- **古いレポートの部品を指したときも答えは戻る。** ブラウザは表示の位置でなく `report` の呼び出しの id で部品を探すので、画面にそのレポートが描かれていれば、どのやり取りのものでも部品の下に戻る。描かれていない（上限で落とした・部品が整形で落ちた）ときは、親のカードの補足メッセージの欄に出す（論点 3）。答えが消える道は無い。
- `Options` の案と `Claims` の主張を指すときも、表の行と同じ形にする。`row` に案の題か主張の字を入れ、`rowIndex` に書き手が書いた案・主張の並びでの添字を入れる。同じ部品の別の案・主張が同じ鍵にならない。
- `key` は Claude へ渡さない。Claude が読むのは `label` の1行と問いの字だけ。

| 案                                                  | 種類               | 物差し                                                                                 | 判定     |
| --------------------------------------------------- | ------------------ | -------------------------------------------------------------------------------------- | -------- |
| `report` の呼び出しの id・部品の ID・書いた行の添字 | 仕組み             | 組み直しで同じ値になり、中間レポートと最終レポートを見分ける。並べ替えても行がずれない | 採る     |
| やり取りの番号・レポートの順番・部品の ID           | 仕組み             | 中間レポートの数や落とした記録の数が変わると黙ってずれる                               | 採らない |
| 指した所の字（`label`）で部品を探して戻す           | ヒューリスティック | 同じ題の部品・同じ1列目の行があると黙って別の所へ戻る                                  | 採らない |
| 表示中の行の添字（並べ替えのあとの並び）            | 仕組み             | 並べ替えを開き直しで初期化すると、別の行を指す                                         | 採らない |

### 論点 3: 待ちのときの補足メッセージ

- **送り方の語に `ask` を足す。** 契約の入力（`src/shared/contract/session.ts`）は送り方で分けた合併にし、`ask` のときだけ `target: ReplyTarget` を必須にする。`promptOpening` は、仕事のときに送り方が `ask` なら、バックグラウンドのタスクの有無によらず補足メッセージにする。雑談のときは今どおり補足メッセージにしない（雑談の画面にレポートのボタンは無い）。`aside-when-background`・`new-request` の扱いは変えない。
- **包みの説明の1行を、委譲中に限らない文にする。** 「tsukumo の差し込み。利用者が送った補足メッセージで、作業の依頼ではない。作業は始めず `speak` を 1 回で答え、`report` は呼ばない」。指した所があれば、説明の次の行に `指した所: …` の1行を置く。`asideTextOf` は今の説明と古い説明の両方を除いて読み戻し、指した所の行も本文から分けて読む（説明の無い古い transcript も読める）。
- **出来事と記録の `aside` に、任意の欄 `target?: ReplyTarget` を足す。** 画面の状態の補足（`main-view-shape.ts` の `aside`）にも写す。
- **入力の控えには `key` だけを足す。** 控えの `input` の行に、任意の欄 `target?: { reportToolUseId, componentId, rowIndex? }` を足す。控えは本文を持たない決まりなので、字（`label`）は控えに書かない。組み直し（`session-restore`）は、鍵を控えから、字を transcript の包みの `指した所:` の行から読む。欄は任意なので、古い控えはそのまま読め、控えの版は上げない。
- **差し戻しと関所は、バックグラウンドのタスクに頼らずに掛かる。** `report-review.ts` は補足メッセージのターンを `aside` の出来事で見分けている（バックグラウンドのタスクの顔ぶれを見ていない）ので、待ちのときの補足のターンにも同じ扱いが掛かる。`Stop` の関所は、本文を書かずに `speak` で答えるターンでは今どおり掛からない。後続のタスクは、待ちのときの補足のターンを疑似の駆動で走らせて、これを確かめる。
- **フォアグラウンドの作業中に送った聞くは、作業のターンが終わってから答えのターンになる**（推測。SDK はストリーミングの入力で、走っているターンのあとに届いた入力を次のターンとして受ける。後続のタスクが疑似の駆動で確かめる）。画面は答えが届くまで「答え待ち」を出す。作業のターンを止める・割り込む手は持たない。
- **指した所つきの補足は、部品の下に出し、親のカードの補足メッセージの欄には出さない。** 鍵の部品が画面に無いときだけ、親のカードの欄に指した所の1行を添えて出す。指した所の無い補足メッセージは今どおり親のカードの欄に出す。

| 案                                                                           | 種類               | 物差し                                                                                                                 | 判定     |
| ---------------------------------------------------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------- | -------- |
| 送り方に `ask` を足し、`ask` だけ `target` を必須にする                      | 仕組み（型）       | 送り方の語を読めば補足になるかが分かる。`target` の無い `ask` は型で作れない                                           | 採る     |
| 指した所を持つ入力を、仕事のとき常に補足にする                               | 仕組み             | 欄の有無で送り方が変わるので、呼ぶ側が欄を付けた意味を知らないと正しく書けない。欄を付け忘れると黙って新しい依頼になる | 採らない |
| 補足メッセージの判定にフォアグラウンドの作業中を足し、聞くは送り方を変えない | ヒューリスティック | 待ちのときに聞いても新しい依頼になり、利用者の決め（待ちのときも補足）を満たさない                                     | 採らない |
| 控えに `label` も書く                                                        | 仕組み             | 控えが会話から書いた字を持ち、「本文を持たない」決まりと「会話内容の扱い」に触れる                                     | 採らない |

### 論点 4: 付箋の置き場

- **付箋は `src/browser/stores/` に置く `reply-notes.ts` の zustand の store に、セッションの id ごとに置く。** 作るのはレポートの部品（`features/report`）、並べて送るのは入力欄（`components/page/conversation`）で、両方が import できる層は `src/browser/stores` だけ。
- 付箋1件は `id`・`target`（論点 2）・`body`（中身の字）・`state`（`unsent` か、`sent` と送ったやり取りの番号）を持つ。同じ `key` の `unsent` の付箋は1件だけにする（「付箋にした」のボタンから二度は作れない）。
- **タブのメモリにだけ置く。** セッションの切り替えでは残し、再読み込み・タブを閉じたときは消える。付箋は利用者の字とレポートの字（指した所）を持つので、`localStorage` などブラウザ側の永続化に置かない（`docs/coding-standards/conversation-content-read-back-and-boundary.md` の「ブラウザ側の永続化には置かない」）。サーバにも送らない。

| 案                                                       | 種類   | 物差し                                                                                       | 判定     |
| -------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------- | -------- |
| `src/browser/stores` の store にタブのメモリだけで持つ   | 仕組み | 両側が同じ store を読む。会話の字をブラウザ側に永続化しない                                  | 採る     |
| 会話ページの `stores/` に置き、部品へは口で渡す          | 仕組み | 付箋の読み書きの手続きを全部口に並べることになり、部品の側が口の形を知らないと書けない       | 採らない |
| `localStorage` に保ち、再読み込みでも残す                | 仕組み | 「会話内容の扱い」のブラウザ側の永続化の禁止に触れる                                         | 採らない |
| サーバの姿（`SessionState`）に置き、手続きで読み書きする | 仕組み | 再読み込みでも残るが、送らない付箋のために契約・畳み込み・E2E の型が増え、読むファイルが散る | 採らない |

### 論点 5: まとめた下書きの文面と、送ったやり取りの番号

- **文面**は見本 `reply-drafted.png` の形にする。1行目は「レポート「<レポートの見出し>」への頼みごと n 件。この順に進めて。」、空行を1つ挟み、番号ごとに `n. <指した所>` の行と、字下げした中身の行を並べる。`<レポートの見出し>` は、やり取りの列がそのレポートに出している見出しと同じ字にする。別のレポートの付箋が混じるときは、1行目を「レポートへの頼みごと n 件。この順に進めて。」にして、指した所の頭にレポートの見出しを足す。
- 文面は付箋の並びとレポートの見出しから組む純粋な関数1つが作る。入力欄に字があれば、空行を挟んで後ろに足す（`composer-draft.ts` に後ろへ空行を挟んで足す手続きを置く）。
- **送ったやり取りの番号**: 「まとめて頼む」で入れた下書きには、まとめた付箋の id の組を添えて持つ。利用者が ⌘⏎ で送り、サーバが受け付けたら、その組の付箋を「送った」にし、送ったあとに画面の状態に現れた新しいやり取りの `MainViewTurn.id` を番号として書く。下書きを消したら組も外す。「まとめて頼む」と「終わったら頼む」は待ちのとき（作業中でない）にだけ下書きを入れるので、⌘⏎ は新しい依頼になり、やり取りが1つ増える。

| 案                                                                 | 種類               | 物差し                                                   | 判定     |
| ------------------------------------------------------------------ | ------------------ | -------------------------------------------------------- | -------- |
| 下書きに付箋の組を添え、受け付けたあとに現れたやり取りの id を書く | 仕組み             | 送ったかどうかを送る口で知る。番号は画面の状態から取る   | 採る     |
| 送った時点のやり取りの数に 1 を足す                                | ヒューリスティック | 補足メッセージになった・落とした記録があると黙ってずれる | 採らない |
| 送った依頼の本文に付箋の字が含まれるかで突き合わせる               | ヒューリスティック | 利用者が下書きを書き換えると黙って外れる                 | 採らない |

### 論点 6: 次の一手の作り方

- **出すのは、いちばん新しいやり取りの最後のレポートの末尾だけ。** 古いレポートの次の一手は、今の作業の続きとして読めない。
- **並びと個数**: 種類ごとに最大1つで、並びは「再開する」（`task.outcome` が `stopped`）→「続ける」→「確かめる」→「別の案で進める」。元の欄が無い種類は出さず、1つも無ければ行ごと出さない。先頭のボタンを差し色にする。
  - 続ける: `sessionRemaining` が `remaining` ならその字、無ければ `Options` の採った案の題。ボタンの字は「続ける: <字>」、下書きは「続けて。<字>」。
  - 確かめる: `Claims` の推測・未確認の数を数える。ボタンの字は「確かめる: 推測 n 件」（未確認だけなら「未確認 n 件」、混じれば「n 件」）、下書きは「確かめて。」の行のあとに、主張ごとに `n. <主張>` と、`howToVerify` があれば字下げした「確かめ方: …」の行を並べる。
  - 別の案で進める: `Options` の検討・見送りの案。押すと案を選ぶ欄を開き、選んだ案で下書き「<案の題> で進めて。」を入れる。
  - 再開する: 下書きは「止めたところから再開して。」。
- ボタンの字は1行に収め、はみ出す分は CSS の `text-overflow` で切る（字数では切らない）。押すと入力欄の後ろに空行を挟んで下書きを足し、入力欄へフォーカスを送る。送らない。
- **`sessionRemaining` は画面の状態のレポートの写しに足す。** `main-view-entry.ts` がレポートの出来事の `sessionRemaining` を写す。レポートの本文には今どおり描かない。`session-event-report.ts` の説明は「本文に描かず、次の一手の元にする」に直す。組み直しも同じ写しを通るので、開き直しても同じボタンが出る。
- 書き手に新しい欄を書かせない。

| 案                                                                      | 種類               | 物差し                                                                                | 判定     |
| ----------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------- | -------- |
| 欄から決まった規則で作る純粋な関数1つ。いちばん新しいレポートにだけ出す | 仕組み             | 1ファイルで規則が読め、元の欄が無ければ出ない                                         | 採る     |
| 書き手に `nextSteps` の欄を書かせる                                     | ヒューリスティック | 利用者の決め（書き手に新しい欄を書かせない）に反し、書き忘れると黙って出ない          | 採らない |
| すべてのレポートの末尾に出す                                            | 仕組み             | 古いレポートから「続ける」を押すと、今の作業と食い違う下書きが入る                    | 採らない |
| `sessionRemaining` を、切り替え画面と同じく transcript から読み戻す     | 仕組み             | 画面の状態の外に2つ目の読み口ができ、会話の画面が transcript の読み方を知る必要が出る | 採らない |

### 論点 7: 機能の境界

- **`features/report` は、会話へ返す口の型 `ReplyPort` と、それを渡す React の context を公開の面から出す。** 口は `ask(target, text)`（聞くを送る）と `appendDraft(text)`（入力欄の後ろに空行を挟んで下書きを足し、フォーカスを送る）の2つ。
- **会話ページ（`main-view` の `turn.tsx`）が口の実装を渡す。** 実装は `dispatch` の送る手続き（送り方 `ask`）と `composer-draft.ts` の下書きを呼ぶ。`features/report` は会話ページのファイルを import しない。`.dependency-cruiser.cjs` の `features` の行（`features`・`components/ui`・`hooks`・`domain`・`lib`・`utils`・`stores`）はそのままで通る。
- 付箋は論点 4 の store を両側が直接読む。口には載せない。
- 口が渡されていない描画は、返す層のボタンを出さない（論点 1）。

| 案                                                                  | 種類                   | 物差し                                                                                                 | 判定     |
| ------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------ | -------- |
| `features/report` が口の型と context を持ち、会話ページが実装を渡す | 仕組み（型と辺の検査） | 部品は口の2つの手続きだけを知ればよい。口が無ければボタンを出さないことを型で書ける                    | 採る     |
| `composer-draft.ts` と送る手続きを `src/browser/stores` へ移す      | 仕組み                 | 下書きの保存・書き始めたときに質問の選択を外す処理など会話ページの事情も一緒に移り、移すファイルが散る | 採らない |
| `features` から `components/page` への辺を許す                      | 仕組み                 | ADR 0037 の辺の宣言を崩し、ほかの機能も会話ページを直接呼べるようになる                                | 採らない |
| DOM の独自イベントで送る                                            | ヒューリスティック     | 受け手が居なくてもエラーが出ず、黙って何も起きない                                                     | 採らない |

## 採らなかった案

論点ごとの表のほかに、利用者が採らなかった案（全部を1つの列に溜める・押したらすぐ送る・作業が終わったら溜めた分を自動で送る・聞くを別のセッションで答える・「了解」の印）がある。利用者が採らないと決めたので、この ADR は蒸し返さない。

## 残すこと

- 字を選んで入力欄の頭へ引用する「引いて聞く」は残す。部品の単位で指せない字の範囲を指す手段として、返す層と並べて使う。
- 付箋は再読み込みで消える。消えて困る使われ方が見えたら、ブラウザ側に永続化せずに残す置き場（サーバの姿）を改めて決める。
