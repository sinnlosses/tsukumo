# ワークフローを、契約を満たすスキルの並びにする（2026-10-15）

**ワークフローは、契約を満たすと宣言したスキルの線形の並びで、利用者が歯車の設定からスキルを足す・消す・並べ替える。**
並びはワークフローの設定コマンドの `schema: 2` の1欄 `steps` で、委譲先の段の結果は文字の1行目ではなく MCP ツール `phase_result` で受ける。
形とツールの引数は `docs/architecture/workflow-contract.md`「設定コマンド」「スキルの契約」が正典。

## 何が困っていたか

- 設定コマンド（`schema: 1`）は、流れ（`flow`）と4つのパーツの枠（`parts.implementer`・`parts.acceptor`・`parts.retrospect`・`parts.ship`）の固定の欄だった。
  利用者は枠の中身を差し替えられても、段を増やす・減らす・並べ替えることはできない。振り返りを外す・確かめの段を足すといった組み替えは、ワークフローのコードを直すしかない
- 委譲先の段の済み方は、返却の1行目（`段 n/N | …`）を文字で読んでいた（`parseDelegateReturn`）。書式の揺れを当て推量で受け、
  形の読めない1行目は黙って帯を進めない。委譲先は自分の返却が読まれたかを知る手段が無い
- 1行目は `SubagentHandback` の返却でしか届かず、許可モードが `auto` でない委譲（`<task-notification>` で返る）では帯が進まない

## 決めたこと

出どころは 2026-10-15 の利用者との設計の聞き取り。

- **並びの要素はスキルだけ。** エージェントはスキルが中で使う道具で、並びに出さない。段の中の並列実装はスキルの中で行う
- **並びは線形。** 近道・`loopable`・メインで行うのような分岐は並びで表さず、各スキルが `skipped`（飛ばした）と返す。並びの中の並列（配列の段）は初版では持たない
- **並びは `.tw/config.toml` に持ち、書くのは `tw config set` だけ。** tsukumo は設定ファイルを直に読み書きしない。
  既定の並びはワークフローが `tw config --schema` の `default` で返す。tsukumo は並びを読まず、帯は今までどおりメインの `work_plan` で受ける
- **tsukumo が縛る構成は「1つ以上」だけ。** 送り出しも並びのスキルの1つで、外せる。「空にできない」は欄では表さず、`steps` の種類の決まりにする
- **結果の受け渡しは Beads の欄。** 並びの各スキルが受け取るのはタスクの ID 1つで、前段の結果は Beads から読む。会話の文脈には置かない
- **構造化した返却は MCP ツール `phase_result`。** 引数は `phase`・`count`・`outcome`（`finished`・`skipped`・`stopped`）・`reason`（`stopped` のときだけ）の最小で、zod で検証して形の合わない呼び出しは差し戻す。
  文字の1行目（`段 n/N`・`止めた n/N`）はこれで置き換えて消す。メインが `work_plan` で段を進める道と、委譲先の `phase_result` で進む道の両方を許す
  - 計画だけの返却（`計画 0/N`）に当たる形は持たない。段の数はメインが Beads から読んで `delegatedRange` の `count` に渡す
  - `phase_result` は要約を持たない。返却で済んだ段のまとめは、そのあとメインが同じ位置で呼ぶ `work_plan` の `phaseSummary` に書く
  - `skipped` はどちらの口から返しても帯で同じ結果（飛ばした段の印つきで済む）にする。メインで走る段のために `work_plan` に `skippedPhases`（飛ばした段の名前の配列。
    `phases` の名前に含まれ、その呼び出しで済んでいる段だけ。毎回の呼び出しでメインが飛ばした段をすべて渡す）を足す。`phase_result` で付いた印は tsukumo が覚えて残す
  - `skipped` の段の帯での描き方は `docs/architecture/display.md`「段取り」に後段で決める
- **`stopped` は並び全体を止める。** 後のスキルは呼ばず、同じタスクを呼び直すと止まった段から再開する。再開の位置はワークフローが Beads に残す
- **設定画面の候補は、契約を満たすと宣言したスキルだけ。** 宣言は SKILL.md の frontmatter の `metadata` の `workflow-step: "true"` で、
  `tw config --schema` がそれを拾って `steps` の `values` に候補そのものを返す。tsukumo は frontmatter も SDK のスキルの一覧も読まない
- **移行**: schema 1 と schema 2 を並存させ、文字の1行目と `phase_result` も両方読む。ワークフローが移り終えたら schema 1 と文字の1行目を消す
  - 1回の `tw config --schema` が返す版は1つのまま、並存は版を選ぶ引数で表す。移行中は引数なしが schema 1、`--version 2` が schema 2 を返し、
    tsukumo は `--version 2` を先に打って失敗したら引数なしに落とす。移り終えたら引数なしが schema 2 を返し、`--version` を外す
  - 2026-10-17: tsukumo は文字の1行目と schema 1 の描画、`--version 2` の打ち分けを外した（plugins の `tw config --schema` が引数なしで schema 2 だけを返し、`--version 2` は終了コード2。委譲先は返却の1行目を書かず、止めたことは `phase_result` の `stopped` と本文の先頭の語で読む）
- **実装は2つのリポジトリにまたがる**（このリポジトリと `tsukumo-plugins`）。別々のタスクで進める
- 同梱のスキルの名前を既定の並びとして tsukumo が知ってもよい（ADR 0024 の 2026-10-10・10-11 の改訂）。ただし既定はワークフローが返すので、tsukumo のコードに並びは書かない

ADR 0024「2026-10-14 の改訂」の採らなかった案「段を自由に並べ替える編集画面を作る」は、この ADR で覆す。
あのとき並べ替えを退けた理由は「流れの組み立てはワークフローの持ち物」で、並びの候補と既定と検査をワークフローが持つこの形はそれと両立する。

## 採らなかった案

- **4つの枠の固定のまま、枠を増やす**: 段を足すたびに schema の欄と tsukumo の描き分けが要り、外す・並べ替えるは表せない。
  利用者の独自のワークフローは枠の数も名前も違うので、固定の枠は `tsukumo-plugins` の形を契約に持ち込むことになる
- **エージェントも並びに出す**: エージェントを呼ぶのはスキルの手順で、並びに出すと委譲の依頼文・受け入れの判定といったスキルの中身を並びが受け持つことになる。
  スキルに閉じれば、段の中の並列や委譲の有無もスキルが決められる
- **分岐（近道・`loopable`・メインで行う）を並びで持つ**: 並びが木や条件を持つと、設定画面が条件の編集画面になり、検査と再開の位置の決め方も複雑になる。
  各スキルが `skipped` を返せば、線形の並びのまま同じことが表せる
- **文字の1行目を残して書式を締める**: 揺れを受ける当て推量は残り、委譲先は読まれたかを知れない。ツールなら形の誤りをその場で差し戻せる
- **メインで走る段の `skipped` を `phaseSummary` の文言だけで表す**: 帯の上で済んだ段と見分けられず、委譲先の `phase_result` の `skipped` と結果が食い違う
- **候補を SDK のスキルの一覧からそのまま出す**: 契約を満たさないスキル（コメント監査など）まで並びに置けてしまう。宣言した印で絞れば、並べてよいかをスキルの書き手が決める
