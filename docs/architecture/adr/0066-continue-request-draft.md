# 「続ける」の下書きに、書き手が渡す続きの依頼の文を使えるようにする（2026-11-18）

ステータス: 採用

**`report` の入力に、任意の字の欄 `continueRequest`（続きの依頼の文。利用者がそのまま送る「〜して」の文）を `Report` の直下に足す。`sessionRemaining` の書き方は変えない。受け取った値は、イベントの側で `SessionRemaining` の `remaining` の枝に任意の `request` として畳み、「続ける」の下書きに使う。書かなければ下書きは今の「続きを進めて。」のまま。この ADR は、ADR 0064 の論点 6 の「続ける（残りの作業がある）」の下書きと「残したこと」の1項目を決める。**

この ADR が決めるのは、依頼の文を書き手がどこで渡すか、下書きの決まり、「前回の続き」に使うかまで。お願いの選択肢（`favorOptions`）があるレポートに「続ける」を足さない決まり、札の字を `sessionRemaining` から作ることは変えない。

## 何が困っていたか

「続ける」の下書きは定型の「続きを進めて。」で、何を進めるかは札の字（`sessionRemaining`）にしか出ない（`src/browser/features/report/domain/next-step-plan.ts` の `continueStepsOf`）。お願いの選択肢の `draft` を書かないレポートでは、書き手が依頼の文を渡す欄が無く、利用者は入力欄で続きの中身を自分で足すことになる。

## 決めたこと

### 論点 1: 欄を足し、`sessionRemaining` は変えない

**採る: `Report` の直下に任意の `continueRequest` を足す。欄は任意で、続きがあり書き手が具体的に書けるときだけ渡す。**

| 案                                                             | 種類   | 物差し                                                                                                                                                                       | 判定     |
| -------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `Report` の直下に任意の `continueRequest` を足す               | 仕組み | 書き手の負担は任意の欄1つ分（カードと schema の字数は測った分だけ上げる。ADR 0048）。書いた・書かなかったが欄の有無で機械的に分かる。下書きが具体になる                      | 採る     |
| `sessionRemaining` を「依頼の文」に改めて下書きにも使う        | 仕組み | 欄は増えないが、今までの transcript に残った状態の文（「〜が着手できる。」）が下書きに入り、依頼に読めない。書いた・書かなかったを機械で分けられない。札の字も依頼の文になる | 採らない |
| `sessionRemaining` を2つの欄（札の字・依頼の文）の入れ子にする | 仕組み | 書き手の契約が壊れ、書き方を間違えた差し戻しが増える。今までの transcript も読み戻せない                                                                                     | 採らない |

### 論点 2: 下書きの決まり

**採る: `continueRequest` があり `sessionRemaining` が `remaining` なら、「続ける」の下書きはその文（前後の空白を落とす）。無ければ今の「続きを進めて。」。**

- 空白だけの文字列は無いものとして扱う。`sessionRemaining` が `none`・`unrecorded` のときは `continueRequest` を捨てる（続きが無いのに依頼の文だけが残らない）。
- イベントの側では、`SessionRemaining` の `remaining` の枝に任意の `request` を足して運ぶ。会話の記録とメインビューの経路は `SessionRemaining` をそのまま運ぶので、経路の型は足さない。
- お願いの選択肢があるレポートには「続ける」を足さない決まりは変えない。
- 依頼の文の形（利用者がそのまま送る「〜して」の文）の説明は、`report` の定義の欄の説明と、部品のカードに書く。差し戻しの検査は足さない。

### 論点 3: 「前回の続き」には使わない

**採る: 始め方の一覧の「前回の続き」（`resumeRequestOf`）は、今の2行の形のまま変えない。**

- 新しいセッションは前回の文脈を持たない。1行目の定型と2行目の「前回の残り: 」に残りを名前つきで添える形が、依頼の文だけを渡すより文脈が伝わる。

| 案                                          | 種類   | 物差し                                                                             | 判定     |
| ------------------------------------------- | ------ | ---------------------------------------------------------------------------------- | -------- |
| 「前回の続き」は今の2行のまま               | 仕組み | 前回の文脈が無い新しいセッションに、残りの名前が届く                               | 採る     |
| 「前回の続き」にも `continueRequest` を使う | 仕組み | 「前回の画面で書いた続き」の指示語や前提が、文脈の無い新しいセッションで空振りする | 採らない |

## 影響

- 同梱のプラグインは `sessionRemaining` を読まない（`tsukumo-plugins` を検索して当たり0件）ので、合わせる先は無い。
- `report` の引数の schema は、欄の定義と説明の分だけ増える。実装で測ると 23,669 字から 23,769 字で、`REPORT_INPUT_SCHEMA_MAX_CHARS`（23,770 字）に収まったので上限は上げていない。
