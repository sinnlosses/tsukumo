# 地図に実行の境界の区画と横断の帯を、任意の欄 `lanes`・`lane` で足す（2026-11-24）

ステータス: 採用

**地図のファイルの頭に任意の欄 `lanes`（区画の並び。要素は `id`・`title`・`kind`）を、大の箱に任意の欄 `lane`（属する区画の `id`）を足す。種類 `kind` は `runtime`（実行の境界）・`crosscut`（横断の帯）・`external`（外部）の3つ。版は `1` のまま上げない。区画を持つ地図の全体の図は、`runtime` と `external` の区画を定義の順に左から列に並べ、`crosscut` の区画を `runtime` の列の下にまたがる帯にする。箱1つの `runtime`・`crosscut` の区画は区画そのものが箱になり、`external` の区画は中に箱を縦に並べる。中・小の段の図は、フォーカスした箱の区画の色の枠「〈箱の名〉の中」で子を囲む。図は自前の SVG のまま描き、箱の名前は2行までの折り返しを純粋な関数で決める。レポートの「変えたファイル」のミニマップにも同じ区画を出す。** 契約の正典は `docs/architecture/architecture-map.md` で、この ADR は判断の理由を持つ。

形（左から ブラウザ｜サーバ｜外部 の3列、共有層はブラウザとサーバの下にまたがる横断の帯、ブラウザ・サーバ・共有層は区画そのものが大の箱、外部は区画の中に箱が並ぶ、広げた地図も同じ組み方、区画の無い地図は今の格子）は、2026-11-23 に利用者が見本の案A で採った。見本は `docs/history/mockup/map-lanes-2026-11-23/compare.html`（`scene.html?form=a&at=top|select|deep`）。この ADR は、そのとき残した論点5つを決める。

## 何が困っていたか

- 利用者は、サイドバーの地図で「ブラウザ（クライアント側）・サーバ・外部システムの境界と、それらを横断する共有層」を読み取りたい。今の地図は境界を外の世界の箱の破線でしか表せない
- 契約の大の箱は `external` と `place`（格子の列・行）しか持たず、箱がどの実行の境界に属すかの欄が無い。tsukumo の地図の定義は外の3箱を列0、`server` を列1、`browser` と `shared` を列2に置いており、共有層がサーバとブラウザの両方に効くことが位置から読めない
- 図は `src/browser/features/architecture-map/architecture-map-diagram.tsx` の自前の SVG で、箱の名前を字数で切るので、サイドバーの幅では「tsukumo-pl…」「キャラクターパ」のように途中で切れる

## 前提の裏取り

- **作り手は知らない欄を捨てる**: `vendor/tsukumo-plugins/plugins/tsukumo-architecture-map/skills/architecture-map/scripts/architecture_map.py` の書き出し（`render`）は `BOX_KEYS` に並べた欄だけを書き、頭の欄も `version`・`source`・`overview`・`boxes`・`edges`・`findings` だけを書く。定義に `lane` を書いても、作り手を直すまで地図のファイルには出ない
- **tsukumo の読み手は知らない欄を読み捨てる**: `src/shared/architecture-map/architecture-map.ts` の `architectureMapSchema` は zod の `z.object` で、知らない欄は落ちる。今の tsukumo は `lanes`・`lane` のある地図のファイルも読め、今の格子で描く
- **大の箱の並び**: `docs/architecture/architecture-map.toml` の大の箱は `claude-code`・`tsukumo-plugins`・`character-pack`（どれも `external = true`）・`server`・`browser`・`shared` の6つで、全部 `place` を持つ。中の箱は `server` が24・`browser` が17・`shared` が18
- **図の座標の持ち方**: 箱の座標は `architecture-map-geometry.ts` の `mapGeometryOf` が純粋に決める。広げた地図（`architecture-map-expanded.tsx`）は図を CSS の `transform`（`translate`・`scale`）で動かし、「この箱について聞く」の置き場を同じ `rects` から求める。縮めた図（サイドバー・レポート）は SVG の `viewBox` で器の幅に合わせ、1.4 倍で頭打ちにする
- **フォーカスした図の外の箱**: `src/server/architecture-map/core/map-view.ts` の `focusView` は、子とエッジでつながる外の箱をフォーカスした箱と同じ段に置き換えて図に入れる。外の箱は `place` を使わないので、外の箱のある図は今いつも自前の配置（エッジの向きで列）になる
- **レポートの書き出し**: `src/browser/features/report/minimap-slot.tsx` の差し込み口は、置く側（会話の画面）が描き方を渡したときだけミニマップを描く。HTML の書き出しは渡さないので、書き出した HTML にミニマップは出ない
- **記録に残った図**: レポートの地図（`src/shared/report/report-map.ts` の `ReportMap`）は縮尺が大の全体の図（`MapView`）をセッションの記録に持つ。区画の欄を図の形に任意で足せば、前に記録した図は区画なしの格子で描ける

## 決めたこと

### 論点 1: 契約の欄 — 頭の任意の欄 `lanes` と、大の箱の任意の欄 `lane`

**採る: 頭に任意の欄 `lanes`（区画の配列）、大の箱に任意の欄 `lane`（区画の `id`）を足す。区画は `id`（必須）・`title`（任意。無ければ `id`）・`kind`（必須。`runtime`・`crosscut`・`external` のどれか）を持つ。`lanes` を書くなら大の箱は全部 `lane` を持ち、書かないなら1つも持たない。外の世界の箱（`external: true`）は `kind` が `external` の区画にだけ属し、`external` の区画には外の世界の箱だけが属する。どの区画にも大の箱が1つ以上属する。版は `1` のまま上げない。**

- 地図の定義（TOML）では、頭の欄のあとに `[[lanes]]` の表で並べ、大の箱の表に `lane = "<区画の id>"` を書く。地図のファイル（JSON）では、頭の `lanes` を `overview` と `boxes` のあいだに、箱の `lane` を `external` と `place` のあいだに置く（作り手の義務 5 の「同じ入力から同じバイト列」を保つ並び）
- 区画の `id` は箱の ID の区切り1つの形（`\.?[A-Za-z0-9_][A-Za-z0-9._-]*`）で、区画どうしで重ならない。箱の ID とは別の名前の空間で、`{{map: …}}` では指せない（区画は押して潜る先ではなく、箱の組み方だから）。tsukumo の定義では区画 `browser` と箱 `browser` のように同じ字にしてよい
- **任意の欄にして版を上げない**: ADR 0082 の「版」は、任意の欄を足すことを版を上げないものに数える。区画の欄を持つ地図を古い tsukumo が読んでも、欄を読み捨てて今の格子で描くだけで、読めなくはならない。区画の欄どうしの整合（全部か無しか・`external` との一致）は、欄を書いた地図にだけ掛かる決まりなので、区画を書かない作り手の地図はどれも今までどおり契約に沿う
- **`external` と区画の種類の重なり**: `external` は「箱の性質」（`paths` が空で子を持たない、リポジトリの外の相手）のまま残し、区画の `kind = "external"` は「その性質の箱を集める区画」とする。両方が一致することを契約の決まりにして、食い違う地図は壊れている扱いにする。`external` を区画の種類へ畳むと、区画を書かない地図が外の世界の箱を表せなくなる
- tsukumo の地図の定義は、区画 `browser`（ブラウザ・`runtime`）・`server`（サーバ・`runtime`）・`external`（外部・`external`）・`shared`（共有層・`crosscut`）をこの順に書く。大の箱は `browser`・`server`・`shared` がそれぞれ同じ名の区画、外の3箱が `external` の区画に属する
- 採らなかった案:
  - **大の箱にだけ `lane = { kind, title }` を書き、区画の並びを持たない**: 区画の左右の順と表示名を箱ごとに繰り返すことになり、同じ区画の箱で表示名が食い違ったときにどれが正か決まらない
  - **区画を大の段の上の新しい段（4段目）にする**: 木の段の数を変えるので版を上げる（ADR 0082「版」）。区画は押して潜る先ではなく、`{{map: …}}` で指す箱でもない
  - **`external` を消して区画の種類に一本化する**: 欄を消すので版を上げ、区画を書かない地図が外の世界の箱を表せなくなる
  - **`lane` を書かない大の箱を許し、どの区画にも属さない箱として隅に置く**: 置き場の規則が1つ増え、書き忘れが黙って隅へ行く。全部か無しかにすれば、作り手の検査で書き忘れが落ちる
  - **区画に色の欄を持たせる**: 色は tsukumo の意匠（`docs/architecture/screen-design/color.md`）が決めるもので、作り手の契約に持たせると利用者独自の作り手ごとに色が散らばる

### 論点 2: 区画の並びと帯の置き方 — 定義の順と種類で決め、`place` は使わない

**採る: 全体の図に区画があるときは、大の箱の `place` を使わず、区画の並びと種類で組む。`runtime` と `external` の区画は、`lanes` の定義の順に左から列に並べる。`crosscut` の区画は列の下に、定義の順に上から帯として重ね、どの帯も「いちばん左の `runtime` の列からいちばん右の `runtime` の列まで」にまたがる。`external` の列は、帯がまたがる範囲の外にあれば列の行と帯の行の全部を縦にぶち抜き、範囲の内にあれば列の行だけを占める。区画の中の箱は、大の箱の定義の順に上から並べる。** `runtime` の区画が1つも無い地図では、帯は全部の列にまたがる。

- 定義の順にしたのは、人が TOML の `[[lanes]]` の並びを入れ替えるだけで左右を直せ、種類から順を決める規則（「外部はいつも右」など）を覚えなくてよいため。tsukumo の並びは「画面 → サーバ → 外」と依頼の流れの向きにそろう（見本の案A）
- 帯のまたがる範囲を種類で決めたのは、「横断の帯は実行の境界のどれもが読む層」という種類の意味そのものだから。範囲を別の欄で書かせる必要が無い
- 外部の区画の2行ぶち抜きは、上の規則の結果として出る（tsukumo では外部の列が帯の範囲の外の右端にあるので、列の行と帯の行の2行を占める）。見本の案A の `grid-area: 1 / 3 / 3 / 4` と同じ
- 列の幅は、`runtime` の列どうしを等しくし、`external` の列は中の箱の名前が収まるよう少し広くする（見本は `1fr 1fr 1.3fr`）。幅の比は描き方の細目で、契約には持たない
- 区画の中に箱が2つ以上ある `runtime`・`crosscut` の区画は、`external` の区画と同じく枠の中に箱を並べる（区画そのものが箱になるのは、箱がちょうど1つのときだけ）。tsukumo の地図ではこの形は出ないが、利用者独自の地図で「サーバ」の区画に `api` と `worker` を置く形を描ける
- 採らなかった案:
  - **区画にも `place`（列・行・またがる数）を持たせる**: 列・行・横と縦のまたがる数の4つを人が書くことになり、帯と外部の列のぶつかりを人が避けなければならない。種類から決まる組み方で足りる
  - **帯に「またがる区画の `id` の並び」の欄を持たせる**: 欄が増えるわりに、tsukumo でも想定する利用者の地図でも「実行の境界の全部の下」以外の形が無い。要る地図が出たら任意の欄として足せる（版は上げない）
  - **種類で左右の順を固定する（`runtime` → `external`）**: 外から呼ばれる側（受け口の外部システム）を左に置きたい地図で組み替えられない
  - **区画があっても `place` を残し、`place` で区画の中の位置を決める**: 区画の中は縦1列で足り、2つの規則が同じ箱の位置を取り合う

### 論点 3: 中・小の段の図 — フォーカスした箱の区画の枠で子を囲み、外の箱は枠の外に置く

**採る: 区画を持つ地図で、フォーカスした図（大の箱の中の中の段、中の箱の中の小の段）は区画を組まない。フォーカスした箱が属する区画の色の枠を1つ描き、見出しを「〈フォーカスした箱の名〉の中」にして、その中に子を今の規則（全部が `place` を持てばその格子、欠ければ自前の配置）で並べる。中の箱にフォーカスしたときの枠の色は、その中の箱の親の大の箱の区画の色。子とつながる外の箱は枠の外の右に1列で置き、それぞれが属する区画の色で縁取る（並びは区画の定義の順、同じ区画の中は定義の順）。** 区画を持たない地図のフォーカスした図は今のまま描く。

- 見本の「サーバの中」（`a-deep.png`）の形に合わせた。中・小の段では、境界は「今どの区画の中にいるか」の1つだけが要り、ほかの区画の並びを描くと子の箱の置き場が狭まる
- 外の箱を枠の外に出したのは、今のフォーカスした図が持つ「子とつながる外の箱」（ADR 0082 の論点 4）を保ちつつ、枠の中が子だけになって「中」の見出しと食い違わないようにするため。外の箱が今のように自前の配置で子と同じ列に混ざると、枠の囲みが外の箱も含んでしまう
- 外の箱の縁取りの色で、その外の箱がどの区画（共有層か、外部か）にあるかを、全体の図へ戻らずに読める
- 採らなかった案:
  - **フォーカスした図にも全体と同じ区画の組み方を描き、フォーカスした箱の区画の中に子を並べる**: サイドバーの幅で24個の子を3列のうちの1列に押し込むことになり、読めない
  - **枠だけを描き、外の箱を描かない（見本の deep の画のまま）**: 見本は外の箱を省いて描いたが、子とつながる外の箱は ADR 0082 で決めた描く範囲で、消すと「レポートの機能が共有層の何を読むか」がフォーカスした図から読めなくなる
  - **中・小の段では枠も描かない**: 潜ったあと、どの境界の中にいるかがパンくずの字でしか分からない

### 論点 4: 箱と区画は自前の SVG のまま描き、名前の折り返しを純粋な関数で決める

**採る: 区画・箱・矢印をどれも今の自前の SVG で描き、座標は `mapGeometryOf` と同じ純粋な関数が区画の組み方まで決める。箱の名前は、箱の幅に収まる字数で2行まで折り返し（全角の字を1、半角の字を約 0.55 と数える）、2行に収まらないときだけ末尾を「…」で切る。区画の見出しの字も同じ SVG の `text` で描く。** 箱を HTML にし、描いたあとに位置を測って矢印の SVG を重ねる形（見本の作り）は採らない。

- 座標が純粋な関数で決まるので、広げた地図の拡大・縮小とドラッグ（`transform` で図ごと動かす）、「この箱について聞く」の置き場（同じ `rects` から求める）、縮めた図の `viewBox` での伸び縮み、配置の単体テストが今のまま効く
- 見本が HTML にした利点（字が箱の幅で折れ、箱の外へはみ出さない）は、2行の折り返しを座標と一緒に決めることで得る。区画の箱は字が少なく（ブラウザ・サーバ・共有層と「中の箱 n」）、外部の箱は2行に収まる（「tsukumo-plugins」「キャラクターパック」）。字幅は字の種類で数えるので、実際の描画と少しずれても、2行の高さと「…」で箱の外へははみ出さない
- 押す・フォーカスの作法は今の `g role="button"`（`tabIndex`・Enter と Space）を区画の箱にもそのまま使う
- 採らなかった案:
  - **箱と区画を HTML の格子とボタンにし、描いたあとに位置を測って矢印の SVG を重ねる（見本の作り）**: 描くたびに `getBoundingClientRect` で測る手間が要り、広げた地図では `transform` の倍率で測った値が変わるので倍率で割り戻すことになる。「この箱について聞く」の置き場も測った値に替わる。測る値は jsdom で取れないので、配置の単体テストが実ブラウザの E2E へ移る。縮めた図は `viewBox` で伸び縮みしなくなり、器の幅を測って倍率を決め直す必要がある
  - **箱を HTML にし、純粋な関数が決めた座標に絶対配置する（測らない）**: 字は実際の幅で折れるが、縮めた図の伸び縮みに器の幅の測りが要るのは同じで、箱の高さは座標で決めるので折れた字が高さを超える心配は残る
  - **SVG の `foreignObject` に HTML の字を入れる**: `viewBox` の伸び縮みのまま字を折り返せるが、`transform` で動かす広げた地図の上で字のにじみと位置のずれが出やすく、得るものが2行の折り返しと変わらない
  - **Astryx の部品で箱を描く**: Astryx に図の部品は無く、`Button` は箱の縁取り・区画の色・変えた件数のバッジを持てない。Astryx で表せる部分（パンくず・ボタン・箱の説明）は、ADR 0080 と今の地図のパンくず（Astryx の `Breadcrumbs` の包み）のとおり Astryx の包みを使う

### 論点 5: レポートの「変えたファイル」のミニマップにも区画を出す

**採る: レポートのミニマップも、地図に区画があれば全体の図と同じ区画の組み方で描く。変えた箱の色と件数、押したときの絞り込みは大の箱の ID ごとのまま（区画の箱はその大の箱の ID を持つ）で、外部の区画の中の箱は今までどおり件数を持たない。HTML の書き出しにはミニマップが出ないので影響しない。**

- レポートの図はサーバが `mapViewOf` の縮尺が大の全体の図から作るので、区画は図の形に乗って運ばれる。同じ地図がサイドバーとレポートで違う組み方になると、同じ箱を探し直すことになる
- セッションの記録に残った前の図は区画の欄を持たないので、今の格子で描かれる（区画の欄を図の形に任意で足すため）
- 採らなかった案:
  - **レポートのミニマップは今の格子のままにする**: サイドバーと組み方が食い違い、図の部品に「区画を描かない」分岐が1つ増える
  - **レポートのミニマップで区画だけを描き、箱を省く**: 変えた件数は大の箱ごとで、外部の箱を省いても区画の箱が残るので省く利点が無い

## 見本と違うこと

- **フォーカスした図の外の箱を描く（論点 3）。** 見本の「サーバの中」は子だけを描いたが、ADR 0082 の描く範囲（子とつながる外の箱）を保ち、枠の外の右に1列で置く
- **箱と区画を SVG のまま描く（論点 4）。** 見本の作りは HTML の箱と測って重ねる矢印だったが、見た目（2行に折れる名前・区画の枠と色・帯）は SVG で同じに描く
- 見た目の形（3列の区画・2列の下の帯・外部の2行ぶち抜き・区画そのものが箱・外部は中に箱）は見本の案A のまま

## 後段の分け方

前は3件（作り手 → tsukumo の読み手と定義 → 描画）だった。難しさはどれも sonnet だった。描画の件は、全体の図の区画の組み方・2行の折り返し・3つの面（サイドバー・広げた地図・レポート）・フォーカスした図の枠と外の箱を1件で持ち、触るファイルが図の部品・配置・座標・3つの面の7つ以上と、撮る場面が5つを超える。次の4件に分け直す。

1. **作り手（sonnet のまま）**: `architecture_map.py` が `[[lanes]]` と `lane` を読み、論点 1 の決まり（全部か無しか・`external` との一致・空の区画が無い・`id` の形と重なり）を確かめ、地図のファイルへ論点 1 の位置に書き出す。段の数は3のまま
2. **tsukumo の読み手と定義（sonnet のまま）**: `architecture-map.ts` の形に区画の欄と論点 1 の決まりを足し、`map-view.ts`（共有層の図の形）とサーバの `src/server/architecture-map/core/map-view.ts` が、全体の図に区画の並びと大の箱の区画を、フォーカスした図にフォーカスした箱の区画と外の箱の区画を渡す。tsukumo の定義に論点 1 の区画を書く。名指すファイルにサーバの `map-view.ts` を足す
3. **全体の図の区画（sonnet から opus へ）**: 論点 2・4・5。全体の図の区画の組み方と帯のまたがり、2行の折り返しを配置と座標と図の部品に足し、サイドバー・広げた地図・レポートのミニマップに通す。帯と外部の列のまたがりと、折り返しの字幅の数え方が判断を要するので opus にする
4. **新しい1件 フォーカスした図の枠と外の箱（sonnet）**: 論点 3。全体の図の区画の件のあとに、フォーカスした図に区画の色の枠「〈名〉の中」を描き、外の箱を枠の外の右に区画の色で並べる。全体の図とは配置の規則が別で、止めても全体の図の区画は役に立つので切り分けられる

## 結果

- 区画を書く地図は、ブラウザ・サーバ・外部の境界と、共有層が両方に効くことを、全体の図の位置で読める。区画を書かない地図と古い作り手の地図は、今の格子で描かれ続ける
- 契約の版は `1` のままで、古い tsukumo も区画の欄を読み捨てて読める
- 図は自前の SVG と純粋な座標のままで、拡大・縮小・ドラッグ・配置のテストの作りは変わらない
