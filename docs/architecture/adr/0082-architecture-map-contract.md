# アーキテクチャの地図を、作り手が書く JSON の地図のファイル1つで tsukumo とつなぐ（2026-11-23）

ステータス: 採用

**リポジトリを大・中・小の3段の箱の木と箱どうしのエッジで表した「地図」を、作り手（`tsukumo-plugins` の新しいプラグイン `tsukumo-architecture-map`）が作業ディレクトリの根の `.architecture-map.json` に書き、tsukumo はこのファイル1つだけを読む。人が直す大・中の箱は作り手の入力の TOML（tsukumo では `docs/architecture/architecture-map.toml`）に置き、作り手が抽出した小の箱・実際のエッジ・ずれと合わせて JSON に書き出す。tsukumo の開発では、地図のファイルは `pnpm run check` の新しい段が毎回書き直し、git の外に置く。箱は `{{map: <ID>}}` で指し、本文・セリフ・入力欄で同じ形にする。右の列の入口は、サイドバーの頭の「タスク｜地図」のタブのうち「地図」のタブにする。広げた地図は拡大・縮小とドラッグで動かせる。初版の作り手が地図を作れるのは JS・TS のリポジトリ。** 契約の正典は `docs/architecture/architecture-map.md` で、この ADR は判断の理由を持つ。

方向（作り手と tsukumo を地図のファイルで疎結合にする・3段の縮尺・矢印は一番細かい段で持つ・抽出は dependency-cruiser・段取り5段・LikeC4 を採らない）は 2026-11-22〜23 の会話で利用者が採った。モックアップは `docs/history/mockup/repo-map-2026-11-22/compare.html`。この ADR は、そのとき残した論点9つを決める。

**会話の合意とモックアップから外れる2点は、2026-11-23 に利用者が認めた。**

1. **書式**: 会話では地図のファイルを YAML で書くと合意したが、この ADR は論点 1 で、人が直す定義を TOML、地図のファイル（契約）を JSON に変える。tsukumo にも作り手の Python の標準にも YAML の読み手が無く、どちらに足しても依存の承認か利用者の環境ごとの導入が要るため
2. **大の段の `server` を箱1つにする**: 会話では「見た目はモックアップで合意し、言葉と食い違ったらモックアップが勝つ」と決めたが、この ADR はモックアップの全体の図の `server/*/adapter`・`server/*/core`・`wiring` の3つの箱を、大の段の `server` の1つに畳む。契約の箱の木は親が1つで、層と機能の2つの軸を同時に持てないため（下の「モックアップと違うこと」）

**決めたあと、同じ日に利用者が見本（`docs/history/mockup/repo-map-adr-2026-11-23/compare.html`）を見て、次の4点を改めた。** 本文の論点 5・7・8・9 は改めたあとの形で書いてある。

1. **入口はタブ**: サイドバーに区画を縦に足すとタスクの区画が狭くなる。サイドバーの頭に「タスク｜地図」の2つのタブを置く（論点 7）。保留中の左右の列のタブの提案のほかのタブには触れない
2. **地図のタブの中身は見本で吟味してから決める**: ミニマップの下に何を出すかは、会話しながら横目で見て、そこから話し始める役に立つかで選ぶ。3案を見本で見比べ、利用者が選んだ箱の役割・目的・概要を出す形を選んだ。目的・概要は契約の任意の欄 `purpose`・`overview` として足した（版は上げない。論点 7）
3. **箱ごとの最近のタスクは取りやめる**: 横目で見ても次の一手につながらない（論点 9）
4. **広げた地図は拡大・縮小とドラッグで動かす**: 小の段は中の箱1つで箱が62個になることがあり、全体を1画面に収めると読めない（論点 8）

## 何が困っていたか

- 人がリポジトリの全体を見渡し、部分を指して会話する手段が無い。エージェントの答えも「どこの話か」をファイルのパスで言うだけで、全体の中の位置が分からない
- 会話で決めた骨格（`version`・`source`・`boxes`・`edges.intended`・`edges.actual`・`findings`）を書くには、書式の読み手・名前・指す語・束ね方・入口・配置・最近のタスクの数え方が決まっていない。後段8件は、どれもこの9つを前提に書かれている

## 決めたこと

### 論点 1: 書式 — 人が直す定義は TOML、地図のファイル（契約）は JSON

**採る: 地図のファイル（tsukumo が読む契約）は JSON にし、作り手が毎回まるごと書き出す。人が直す大・中の箱と意図したエッジは作り手の入力の「地図の定義」に置き、その書式は TOML にする。tsukumo は地図の定義を読まない。**

- 地図のファイルを書くのは作り手（Python）、読むのは tsukumo（Node）。JSON はどちらも標準で読み書きでき、利用者独自の作り手もほぼどの言語でも書ける。人が手で直さないので、注釈が書けないことは困らない
- 地図の定義を読むのは作り手（Python）だけ。TOML は Python 3.11 以降の標準の `tomllib` で読め、注釈を書け、2段の木は `[[boxes]]`・`[[boxes.children]]` の表で書ける。作り手は定義を書き換えない（下書きのスキルがエージェントに書かせ、人が直す）ので、標準に TOML の書き手が無いことは困らない
- 会話で合意した「地図のファイル1つを挟んで疎結合」は保つ。tsukumo が読むのは地図のファイル1つで、地図の定義は人と作り手のあいだのもの。会話の骨格の欄は JSON にそのまま置き、`title`・`aliases`・`external`・`place`・`source.tree`・`origin`・`severity` を足した
- **tsukumo の開発では、地図のファイルをコミットしない。** 実際のエッジの `count` は import を足し引きするたびに変わり、並んで走る作業ツリーがそれぞれ書き直すと、送り出しのたびに同じ生成物がぶつかる。検証の控え（`.check-record.json`）と同じく、`pnpm run check` が書いて git の外に置く。地図の定義はコミットし、人が差分を読む
- 採らなかった案:
  - **YAML のまま、tsukumo に `yaml` パッケージを足す**: 依存を足すには利用者の承認が要る（`docs/architecture/build/dependency.md`）。足しても作り手の Python には読み手が無いまま
  - **YAML のまま、作り手に PyYAML を入れてもらう**: 標準の外の Python パッケージの導入は人がやるグローバルな導入で、`pnpm run check` に作り手を載せると、tsukumo を開発するどの環境にも要る
  - **YAML の読み手を作り手が自前で書く**: YAML の仕様は広く、人が書いた字の解き方が作り手と tsukumo でずれる
  - **定義も JSON にする**: 注釈を書けず、50箱の役割の1行と導線を人が直すには読みにくい
  - **定義と抽出を1つのファイルに入れてコミットする**: 作り手が人の直した部分を残して書き直す手間が増え、`count` の変化でぶつかる上の問題が残る

### 論点 2: 置き場と名前

**採る: 概念の名前は「地図」（紛れるときは「アーキテクチャの地図」）、英語識別子は `architecture-map`・`ArchitectureMap`。`repo-map` は今の export の一覧の名前のまま残す。**

| もの                       | 置き場・名前                                                                                                                     |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 地図のファイル（契約）     | 作業ディレクトリの根の `.architecture-map.json`。tsukumo の開発では `.gitignore` に足す                                          |
| 地図の定義（作り手の入力） | tsukumo では `docs/architecture/architecture-map.toml`（コミットする）。置き場は作り手が引数で受ける                             |
| 契約の正典                 | `docs/architecture/architecture-map.md`                                                                                          |
| 作り手                     | `tsukumo-plugins` の新しいプラグイン `tsukumo-architecture-map`。スキル `architecture-map`、スクリプト `architecture_map.py`     |
| `pnpm run check` の段      | 段名と `package.json` の scripts の名前は `architecture-map`                                                                     |
| tsukumo の型と読み         | 共有層 `src/shared/architecture-map/`、server の機能 `architecture-map`、ブラウザの機能 `src/browser/features/architecture-map/` |
| 箱の定義を引く MCP の道具  | `map_box`                                                                                                                        |

- 採らなかった案:
  - **`repo-map` を使い回すか、今のほうを改名する**: 今の `repo-map` は委譲先が `ls`・`grep` の代わりに引く export の一覧で、箱もエッジも持たない。改名すると、それを読む依頼文と記憶の書き直しが増える
  - **`codebase-map`**: 「コード全体の何かの一覧」という点で `repo-map` と同じ読み方をされる
  - **`atlas` などの短い名前**: 語から中身が読めない

### 論点 3: 箱の ID と指す語

**採る: 箱の ID は `/` でつないだ区切りの並び（区切りは `\.?[A-Za-z0-9_][A-Za-z0-9._-]*`、100字以内）。大・中は人が付ける名前、小はディレクトリのパス。箱は `{{map: <ID>}}` で指し、本文・セリフ・入力欄で同じ形を使う。改名は新しい箱の `aliases` に古い ID を残す。**

- 指す語は行内の印（`parseInlineMarks` の `{{…}}`）の仲間にする。区切りの字が決まっていて ID の終わりが曖昧にならず、インラインコードの中を読まない決まりと、字だけの場所へ畳む `foldInlineMarks` をそのまま使える。`InlineMark` に種類 `map` を1つ足す
- セリフも同じ語を読む。吹き出しは字のまま描いているので、`map` の印だけを箱のバッジにし、ほかの `{{…}}` は今までどおり字のまま残す
- 入力欄で箱のバッジを付けて送ると、依頼の文の頭に `{{map: <ID>}}` と縮尺と役割の1行が入る。利用者の吹き出しでも同じバッジで描く
- 印1つに ID は1つ。知らない ID の印と、地図が読めないときの印は字のまま残す
- 小の箱の ID をディレクトリのパスにするのは、エージェントがパスを既に知っていて、人も ID からディレクトリが分かるため。小の箱は抽出のたびに作り直すので別名を持たない
- 区切りの頭に `.` を1つ許すのは、`.` で始まるディレクトリ（`plugin/.claude-plugin`）の小の箱の ID を、そのパスのまま書くため。`.`・`..` だけの区切りは書けない
- 採らなかった案:
  - **`map:<ID>` の素の書き方**: ID の後ろに続く `.`・`の` との境目が字の並びで決まらず、URL に似た字と紛れ、インラインコードの扱いを別に書くことになる
  - **Markdown のリンク `[名前](map:ID)`**: セリフは Markdown ではなく、`react-markdown` は知らない URL の形を落とす
  - **ID に親の ID を頭に付ける決まり**: 箱を別の親へ移すと ID が変わり、別名が増える。木は `children` で表す
  - **印1つに ID をいくつも書く**: バッジ1つが箱1つを指す形のほうが、触れて光らせる先が1つに決まる

### 論点 4: 縮尺の束ね方

**採る: 実際のエッジは小の段だけに持ち、粗い段では両端を祖先の箱に置き換えて `count` を足す。宣言の要る段は「両端の祖先が分かれるいちばん上の段」で、意図したエッジは子孫の import を覆う。フォーカスした図は、その箱の子と、子とつながる外の箱（フォーカスした箱と同じ段に置き換える）だけを描く。** 規則の全文は契約の「tsukumo が読む意味」。

- 束ねた本数と、箱の中で閉じた本数の和は、いつも `edges.actual` の `count` の和に等しい。後段の自己テストはこの等式を確かめる
- 覆う規則にしたので、人は宣言の細かさを選べる。`browser → shared` を大の段で1本宣言すれば、`browser` の中のどの箱から `shared` の中のどの箱へも覆われる。server の機能どうしは、依存の規則から読んだ中の段のエッジで覆う
- 同じ中の箱の中で閉じる import は宣言を要らない。中の箱の中の層の向き（`core` が `adapter` を読まない）は dependency-cruiser の規則の仕事で、地図は二重に見ない
- 採らなかった案:
  - **作り手が段ごとに束ねたエッジを書く**: 同じ数を3つの段で持ち、和が食い違ったときにどれが正か決まらない。会話でも「粗い段は tsukumo が束ねる」と決めている
  - **意図したエッジを中の段だけに書かせる**: 外の世界の箱や層どうしの1本（`browser → shared`）を、中の箱の組の数だけ書くことになる
  - **フォーカスした図に全部の大の箱を並べる**: 子とつながらない箱が図の大半を占め、潜った意味が薄れる

### 論点 5: 作り手と tsukumo の境

**採る: tsukumo は地図のファイルだけを読み、作り手・dependency-cruiser を起こさず、地図の定義を読まない。読めないときは「無い」「壊れている」「知らない版」を分けて扱う。作り手は `tsukumo-plugins` の新しいプラグインに置き、初版の抽出は dependency-cruiser の JSON だけにする。**

- 無いときは入口を出さない。壊れている・知らない版のときは入口を出し、開くと理由の1行だけを出す（黙って消えると、作り手を走らせ直す・tsukumo を新しくする、の手がかりが無くなる）。どの場合も箱の印は字のまま残す（表は契約の「読めないときの振る舞い」）
- 作り手を `plugins/tsukumo-figure` に足さないのは、`tsukumo-figure` が「レポートに載せる画を撮る」道具で、地図の作り手は図を撮らず、リポジトリを読んで照合する道具だから。入れるかどうかを別々に選べるよう、新しいプラグインにする
- 初版の作り手は、dependency-cruiser の `--output-type json` の出力（`modules[].source`・`modules[].dependencies[].resolved`・`summary.ruleSetUsed.forbidden`）と地図の定義を読む。依存の抽出の道具を作り手は入れず、対象のリポジトリにあるものを使う。ほかの言語の抽出は、後から別の入力として足せる（契約は変わらない）
- 作り手は tsukumo の外のどのリポジトリでも使える（地図の定義の下書きもスキルが持つ）。ただし初版で地図を作れるのは、dependency-cruiser で依存を抽出できる JS・TS のリポジトリだけ。ほかの言語の抽出器は別のタスクで足す（利用者が 2026-11-23 に決めた）
- 意図したエッジは2か所から読む。地図の定義に人が書いたエッジと、定義が名指した接頭辞（tsukumo では `server-feature-edge:`）を持つ dependency-cruiser の規則のうち、`from.path` が `^<ディレクトリ>/`、`to.pathNot` が `^<親>/(?:a|b)/` の形のもの（ディレクトリを箱の `paths` で箱に当てる）。どちらも地図のファイルの `edges.intended` に書き出し、`origin` に出どころを書く。地図のファイルは毎回書き出す生成物なので、`.dependency-cruiser.cjs` の写しを人が持つことにはならない
- 箱の `paths` の glob のワイルドカード（`*`・`**`）は `.` で始まる区切りに当たらない、と契約で決める（Node の `path.matchesGlob` の当たり方）。`.` で始まるファイルやディレクトリを箱に入れるときは、その区切りを字のまま書く（`src/x/.*`・`plugin/.claude-plugin/*`）。同じファイルが作り手でも、tsukumo（レポートの変えた箱）でも同じ箱に属するため
- 作り手は Python 3.13 以降を前提にし、箱に属するかを `re.fullmatch(glob.translate(<glob>, recursive=True, include_hidden=False, seps="/"), <パス>)` で照らす（`glob.translate` が 3.13 で入った）。`PurePosixPath.full_match` はワイルドカードが `.` で始まる区切りにも当たるので使わない（前提の裏取り）
- `.` で始まる区切りに当たらないせいで抽出したファイルが箱から抜けると、作り手の照合が `unmapped-file` で落とすので、黙って地図から消えることはない
- 採らなかった案:
  - **ワイルドカードを `.` で始まる区切りにも当てる（Python の `full_match` と git に合わせる）**: `path.matchesGlob` は引数が2つで `dot` の選びを渡せず、tsukumo が glob を照らす関数を自前で書くことになる
  - **tsukumo が地図を開くときに作り手を起こす**: 製品としての tsukumo が同梱外のスクリプトと Python・dependency-cruiser に依存し、会話の画面から外部コマンドを起こす道が増える
  - **初版から TypeScript の型の依存（import type）や呼び出しの関係も抽出する**: dependency-cruiser の JSON で小の段とエッジの数がそろい、それ以上は照合の物差しが決まっていない

### 論点 6: ずれの種類と `pnpm run check` への入れ方

**採る: ずれは7種類（`undeclared-edge`・`unmapped-file`・`overlapping-file`・`split-directory`・`empty-box`・`missing-link` が `error`、`unused-intended-edge` が `warn`）。`pnpm run check` に新しい段 `architecture-map` を足し、作り手の照合を呼ぶ。`error` が1件でもあれば段が落ちる。** 種類ごとの欄は契約の「ずれ」。

- 段は dependency-cruiser の JSON を出し、取り込みの `vendor/tsukumo-plugins` の作り手に地図の定義と一緒に渡し、`.architecture-map.json` を書かせる。`source.tree` には検証の控えと同じ求め方（`worktreeTree`）の木を渡す。レポートの「確かめたこと」には、検証の控えの段として1行が出て、どのエッジがずれたかは、木が一致したときだけ地図のファイルの `findings` から添える
- 規約のテスト（`test/architecture/`）にしないのは、単体の段が変えたファイルに関連するテストだけに絞られるため（`--related`）。リポジトリ全体を読む照合は絞りに乗らず、検証の控えにも自分の行を持てない。`lint` の段に混ぜないのは、落ちた理由が依存の規則の違反か地図とのずれかを段の名前で分けたいから
- **開発のリポジトリとしての tsukumo と、製品としての tsukumo を分ける。** 作り手を呼ぶのは開発の検証（`scripts/` と `package.json` の scripts）だけで、`src/` は作り手のスクリプト・地図の定義・dependency-cruiser のどれにも触らず、地図のファイルを読むだけ。開発の検証が頼るのはコミット単位で固定して取り込む同梱の作り手で、`docs/architecture/adr/0024-no-skill-dependency.md`「同梱スキルへの依存を可とした決定との関係」の範囲に収まる
- 文書（Markdown）だけの変更の計画ではこの段を打たない。地図の定義（TOML）を変えた計画は文書だけの変更に当たらないので、段が走る
- `unused-intended-edge` を `warn` にするのは、依存の規則が「読んでよい」と書いた組のうち、まだ使っていない組があっても誤りではないため
- 採らなかった案:
  - **ずれを全部 `warn` にして段を落とさない**: 古い地図が黙って残る。モックアップの注「メンテナンスの経路」は、置き場が消えた・地図に無い依存が生えたを `pnpm run check` が落とす形で合意した
  - **地図のファイルの `findings` を tsukumo のサーバが数えて「確かめたこと」の行を作る**: 検証の控えと別の出どころができ、同じ判定が2か所に出る

### 論点 7: 画面の入口

**採る: 右の列（サイドバー）の頭に「タスク｜地図」の2つのタブを置き、「地図」のタブにミニマップと「広げる」を置く。ミニマップの下には選んだ箱の役割・目的・概要を出す。「広げる」かミニマップを押すと、中央の列に地図を広げて会話の流れの上に重ね、⎋ で戻る。** 地図が無いときと雑談のあいだはタブの列を出さず、今のサイドバーのまま。

- 使用量の帯はタブの外の下端に残す。タブを切り替えても、タスクの区画の中身（段・探す欄・開いた段）は保つ
- この形は ADR 0058 の「サイドバーは表示する要素とマークを変えない」に、地図が読めるときだけタブの列を足す例外を1つ加える
- タブの中身は、サイドバーの並びに頼らない部品1つ（ブラウザの機能 `architecture-map` の `ArchitectureMapPanel`）にする。左右の列のタブの提案（`docs/history/mockup/side-tabs-2026-11-22/compare.html`。保留中）のほかのタブは足さない
- ミニマップの下は、選んだ箱の名前と縮尺、役割（`summary`）・目的（`purpose`）・概要（`overview`）の順に出し、その下に置き場（`paths`）・用語・つながり（束ねた本数）を小さく添える。目的・概要は契約の任意の欄で、無い箱では出さない。決定の記録（`links.adr`）と「この箱について話す」のボタンは出さない（2026-11-23 に利用者が見本の案 B を選び、この2つを外した）
- 選ぶ箱は、ミニマップで押した箱か、会話で最後に指された箱。何も選んでいないときは「箱を選ぶと役割と概要が出る」の1行だけ。ずれの件数は出さない（レポートの「確かめたこと」の行と重なる）
- 会話で箱が指されたとき、タスクのタブを開いていたら切り替えず、「地図」のタブ名に狐火の青緑の点と件数を付ける。勝手に替わると、見ていたタスクの区画を見失う
- 広げた地図は中央の列で会話の流れの上に重ねる面で、流れに投稿される札ではない。流れはそのまま残り、⎋ か「流れに戻る」で面を閉じると元の位置に戻る。入力欄と声の帯は隠さないので、地図を見たまま依頼を書ける
- 見本は `docs/history/mockup/repo-map-tab-2026-11-23/compare.html`（案 B。案 A・C は下の採らなかった案。見本の案 B にある決定の記録とボタンは採らない）
- 狭い画面（サイドバーを畳む幅）は、サイドバーの開き方に従い、地図だけの出し方を足さない
- 採らなかった案:
  - **タスクの区画と下端の帯のあいだに区画「地図」を縦に足す**（この ADR の最初の形）: タスクの区画を圧迫する。利用者が見本を見て退けた
  - **保留中のタブの提案ごと右の列を組み直す**: 違和感の中身が分かっていない提案の結論に、地図が縛られる
  - **入口を中央の列の頭のボタンだけにする**: 会話で決めた「右の列に小さく」が無くなり、答えの中の箱を右で光らせる場（モックアップの場面3）が無い
  - **コマンドパレットだけにする**: 見つけにくく、ミニマップの置き場にならない
  - **会話で指された箱とこのセッションで変えた箱を行で並べ、選んだ行に「この箱について話す」を置く**（見本の案 A。書き手が推した形）: 利用者は、行の一覧より選んだ箱の役割・目的・概要が読めるほうを選んだ。話し始めるのは入力欄の箱のバッジで足りる
  - **箱の詳細にずれの件数を積む**（案 B）: レポートの「確かめたこと」の行と重なる
  - **箱が指されたらタスクのタブから地図のタブへ切り替える**（案 B）: 見ていたタスクの区画を見失う
  - **指された箱と変えた箱を1つの列に混ぜ、口を「話す」「タスクにする」の2つにする**（案 C）: 同じ箱が札違いで2行に出る。タスクにするかは文を続ければ足り、口が2つでも入力欄に下書きを入れるまでは同じ
  - **タスクのタブの頭に「箱が指された」の1行を出す**（案 C）: タスクの一覧の区画に地図の情報が混ざる

### 論点 8: 箱の配置

**採る: 地図のファイルは画素の座標を持たず、大・中の箱に任意の格子の位置 `place`（`column`・`row`）を持てる。図の中の箱が全部 `place` を持てばその格子に置き、1つでも欠ければ tsukumo が毎回同じ結果になる自前の配置（エッジの向きで列、定義の順で行）で並べる。レポートの `graphDrawingOf` は使い回さない。**

- 格子の位置にしたのは、人とエージェントが TOML で直せる粗さにするためと、描く幅が変わっても崩れないため。大の段の図はモックアップの場面1の並びに `place` で寄せられる
- 自前の配置にしたのは、箱を足しても既存の箱の位置が大きく動かない（定義の順で行が決まる）ようにするため。小の段は作り手が作る箱なので、いつも自前の配置
- `graphDrawingOf` は、文字で書いたレポートの図をどの描き方に回すかを決める関数で、箱ごとのボタン・数のバッジ・光らせる状態を持てない。mermaid の SVG に後から手を入れる形も、図の版で中の要素の形が変わる
- 中の箱1つの小の段が多いと（`src/browser/components/page` は62）図が読めない。下書きのスキルは、小の段が20前後に収まるよう中の箱を切ることを手順に書く
- 広げた地図は拡大・縮小と移動ができる。「+」「−」のボタンで拡大・縮小し、「全体」のボタンで図全体を枠に収める倍率に戻す。地の部分をドラッグすると図が動く（箱の上で押したときは箱を選ぶ）。開いたときと段を潜ったときは図全体を収める倍率で始める。ミニマップは拡大・縮小しない
- 採らなかった案:
  - **ホイールで拡大・縮小する**: 会話の流れの上に重ねた面で、ページのスクロールと取り合う。ボタンとキー（`+`・`-`）で足りる
  - **モックアップのような画素の座標を契約に持つ**: 人が直す手間が大きく、描く幅に縛られる。小の段には座標が無いので、自前の配置はどのみち要る
  - **いつも自前で並べる**: モックアップで合意した並びを再現できず、箱を足すたびに位置が変わる
  - **elkjs・dagre を足す**: 依存を足す承認が要り、1つの図の箱は多くても数十で、列と行の配置で足りる

### 論点 9: 箱ごとの最近のタスク

**取りやめる: 箱ごとの最近のタスクも、広げた地図の「最近7日に触った箱」の数も出さない。** 横目で見ても次の一手につながらない、と利用者が見本を見て判断した。地図のタブの中身（論点 7）も git の履歴を数えないので、tsukumo は地図のために `git log` を打たない。

- 最初の形と数え方は `git show 1371e19b8:docs/architecture/adr/0082-architecture-map-contract.md` の論点 9 にある

## モックアップと違うこと

- **大の段の `server` は箱1つ（利用者が認めた2点の 2）。** モックアップの全体の図は `server/*/adapter`・`server/*/core`・`wiring` を別の箱にし、どれを押しても同じ server の図へ潜る。契約は木（箱の親は1つ）なので、層（`core`・`adapter`）と機能の2つの軸を同時には持てない。tsukumo の地図は、大を `browser`・`server`・`shared` と外の世界、中を機能、小をディレクトリ（`src/server/report/core` など）にし、層の分かれ目は小の段に出る
- 右の列の入口は、サイドバーの頭の「タスク｜地図」のタブ（論点 7）。モックアップの右の列のほかのタブ（変更・検証）は足さない。ミニマップの下は選んだ箱の役割・目的・概要にし、決定の記録と「この箱について話す」は出さない。モックアップの「最近のタスク」は出さない（論点 9）
- 広げた地図は拡大・縮小とドラッグで動かせる（論点 8）。モックアップの「最近7日に触った箱」は出さない
- 地図の下端の出どころは `docs/map/tsukumo.c4` ではなく、`.architecture-map.json` と `source.commit` の短い SHA
- モックアップの「札」は、用語では「箱のバッジ」と呼ぶ（見た目は変えない）

## 後段の分け方

今の後段8件の分け方を保ち、描く段の前に地図のタブの中身を決める設計のタスクを1件挟む。作り手の初版（`tsukumo-plugins`。JS・TS）→ tsukumo 自身の地図と検証の段、地図を読む口 → 地図のタブの中身の設計 → 描く（タブ・広げた地図の拡大・縮小と移動）→ 入力欄のバッジと `map_box` → 本文とセリフの印、レポートのミニマップとずれの行。ほかの言語の抽出器は、作り手の初版の後ろに別のタスクで足す。どの段でも止められ、止めた所までで役に立つ順は会話で決めた段取りのまま。各件の本文に入れる名前・置き場・書式は、この ADR と契約の正典に合わせる。

## 結果

- tsukumo が読むのは JSON の地図のファイル1つで、YAML の読み手も新しい依存も要らない。作り手の側も Python の標準だけで動く
- 人が直すのは TOML の地図の定義だけで、抽出の数は毎回の検証が書き直す。地図の古さは `pnpm run check` の段が落として知らせる
- 箱を指す道具は `{{map: <ID>}}` の1つで、入力欄・本文・セリフが同じバッジになる
