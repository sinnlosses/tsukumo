# 使用中のセッションは名乗りのファイルとプロセスの生存で知る（2026-10-10）

**別の窓の tsukumo がいま開いているセッションは、その tsukumo が自分で書いた「名乗り」と、
そのプロセスが生きているかだけで知る。** ポートが塞がっているか・印の目印が何かでは決めない。
振る舞い（何が使用中か・いつ聞くか・選んだ瞬間の競り合い）は `docs/requirements.md` 4.8
「別の窓で使用中のセッション」が正典。

## 何が困っていたか

同じ `sessionId` を2つの `query` から `resume` すると、別ファイルへ fork せず同じ transcript へ混線する
（`docs/requirements.md` 4.8。2026-09-22 実測）。切り替え先の一覧は部屋（ポート）で絞っていた
ので別の窓のセッションは並ばなかったが、一覧を部屋の縛りから外した（2026-10-10）ので並ぶ。印は transcript に残るだけで、
その印のセッションがいま動いているかは分からない。ポートは別の tsukumo に使い回されるので、
塞がっているかでは判定できない。

## 決めたこと

- **各 tsukumo が `$TSUKUMO_HOME/session-claim/<pid>.json` に名乗る。** 中身は
  `{ "pid": <自分の pid>, "sessionIds": [<いま持っているセッションID>…] }` だけで、ポート・印・見出し・会話の中身は書かない。
  原子的に書き換え、持つものが無くなれば（新規で起こして最初の依頼の前・セッションが終わった・プロセスを閉じた）消す
- **読む側は自分の pid 以外のファイルを読み、`process.kill(pid, 0)` が通ったものだけを使用中とする。**
  `ESRCH`（もういない）ならファイルを消して捨て、`EPERM`（別の利用者のプロセス）も捨てる
- **ファイルと生存の確かめは `session-driver` の adapter の1ファイルに閉じる**（`docs/architecture.md` 原則3）。
  使うのは `node:fs` と `process.kill` だけで、外部コマンドを増やさない
- **起こす直前は「名乗ってから確かめる」。** 自分の名乗りに選んだIDを足して書いてから他を読むので、
  2つの窓が同時に同じIDを選んでも、少なくとも一方は相手の名乗りを見る（両方が見れば両方が断る）

## 残る害

落ちた tsukumo の pid が、利用者の別のプロセスに使い回されているあいだは、その名乗りが生きて見える。
そのあいだ行が選べないだけで、会話は混ざらない。名乗りの置き場が書けない・読めないときは
使用中が無いものとして扱う（画面が止まらないほうを採る。起こす直前の確かめも効かなくなる）。

## 採らなかった案

- **ビューのサーバに、トークンなしで読める手続きを1つ足す**: 起動トークンの照合（`isConnectionGranted`）に
  例外が増え、どこまで出してよいかの線引きを持ち続けることになる。ほかの tsukumo を探すにはポートを
  総なめするしかなく、`TSUKUMO_VIEW_PORT` で遠い番号を指した tsukumo を取りこぼして2重の `resume` を防げない
- **各 tsukumo が Unix ドメインソケットで待ち受け、繋がったかで生存を知る**: pid の使い回しには強いが、
  `$TSUKUMO_HOME` が深いとソケットのパスの上限（macOS で 104 バイト）に当たる
- **ポートが塞がっているか・印の目印で判定する**: ポートは別の tsukumo に使い回され、印は落ちた tsukumo の
  ものと見分けられない（利用者の決定）
