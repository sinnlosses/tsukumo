# 会話の画面を3列と1本の流れにする: 左の列・会話の流れ・サイドバー（2026-11-15）

ステータス: 採用

**会話の画面を、上部の帯（40px）の下の3列にする。左の列にやり取りの列・立ち絵・席のアイテム、中央の列に進行の帯・会話の流れ・入力欄、右の列にサイドバーを置く。投稿もセリフも段もお伺いもレポートも、選んだやり取りの1本の流れとして中央に時系列で出し、立ち絵は吹き出しを持たない。背景は全面に敷いて今と同じ地の色の覆いで暗くし、パネルは背景の透ける面にする。組み替えは7つの段に分け、1段送るごとに画面が使える状態を保つ。この ADR は ADR 0057 を置き換える。**

この ADR が決めるのは、領域の並び・要素の置き場・幅ごとの形・仕切りと設定の持ち方・送る順まで。要件（`docs/requirements/screen-layout.md` 4.7）と画面の設計文書（`docs/architecture/screen-design/`）・`PRODUCT.md` は、後段のそれぞれの段が実装と同じコミットで書き換える（論点 3）。
やり取りの列は ADR 0086 が改訂した。

## 何が困っていたか

- 今の会話の画面は4領域（メインビュー・サイドバー・キャラビュー・入力欄）を2段に並べ、`src/browser/components/page/conversation/components/conversation-layout/presentational-conversation-layout.tsx` が組んでいる。セリフはキャラビューの吹き出しに、依頼・段・お伺い・レポートはメインビューの札に出るので、1つのやり取りを読むのに視線が上下の2領域を往復する。
- 背景は、キャラビューと雑談中のメインビュー（`.layout-ground`）にだけ敷いている。キャラクターの居る場所が画面の左下の箱に限られる。
- 前回の器の組み替え（ADR 0057。11月13〜15日）は一度に行い、不具合が多く、66件を revert した（e938a45c7）。ADR 0057 は採用のまま残っているが、決めた器（舞台と紙・重ねる紙・部屋の頭と探す）はツリーに無い。

## 利用者が決めたこと（2026-11-15）

- 見本は `docs/history/mockup/conversation-directions-2026-11-15/layouts.html?layout=a2`（案 A の仕上げ。差分は同じディレクトリの `refine.css`、比較ページは `compare.html`）。言葉と見本が食い違ったら見本が勝つ。ただしサイドバーの中身とマークは見本ではなく、今の実物のまま。
- 配置は、上部の帯（40px）の下に、左の列（やり取りの列・立ち絵・席）、中央の列（進行の帯・会話の流れ・入力欄）、右の列（サイドバー。領域の下端まで）。
- 投稿もセリフも、メインビューの1本の流れに出す。立ち絵は吹き出しを持たない。
- 背景は全面に敷き、今と同じ地の色の覆いで暗くする（既定 75%・下限 70%）。パネルは背景の透ける面（既定は濃さ 45%・ぼかし 8px）。
- やり取りの列は、立ち絵と左上の席に被らない高さで止め、中だけをスクロールさせる。
- 席のアイテム3つは左の列の中に置く（左上は立ち絵の後ろの頭上、左下と右下は足元の手前）。
- セッションの選択（短縮IDの札 → 切り替えのダイアログ）と、キャラクターの切り替え（顔）は今のまま。
- ペインの幅は仕切りで変えられる（左の列の幅・サイドバーの幅）。
- サイドバーは表示する要素とマークを変えない。例外は1つで、モデル・effort・許可モードの操作子を入力欄へ移す（使用量の目盛りは残す）。
- 狭い画面（760px 以下）は今のまま残す。
- 雑談モードも同じ3列の形にそろえる（サイドバーの中身は今の雑談の4段のまま）。
- 歯車の「見た目」に、背景の暗さ（70〜100%）・パネルのぼかし（0〜24px）・パネルの濃さ（20〜90%）を足す。背景の暗さの下限 70% は変えない。
- 1件送るごとに画面が使える状態を保つ。一度に組み替えない。

## 設計の要点（Impeccable の shape の brief）

利用者の答えを聞く場が無い流れで書いたので、推定は「推定」と書いた。

- **利用者と場面**: 作者本人が、Orca のタブで複数の部屋を並行に進め、随時のぞいて状態を確かめる（`PRODUCT.md`「Users」）。画面の役は Operate（任せた仕事を見守り、聞かれたら答え、レポートを読んで次を決める）。のぞいた瞬間に「いま何をしているか・何を待っているか」が1か所で読めることが要る。
- **成功の基準**: 1つのやり取りの依頼・セリフ・段・お伺い・レポートを、視線を上下に往復させずに上から下へ1本で読める。キャラクターは左の列に常に立ち、背景が画面の全面に見える（一緒にいる感じ）。サイドバーのタスクと使用量は今と同じ位置で読める。
- **方向**: 見本 A2 が視覚の正典。構造の主張は「流れは1本、キャラクターは脇に立つ、道具は右に寄せる」。目を止める所は流れの下端（いま届いたセリフ・お伺い）。
- **範囲と守るもの**: 広い画面の会話の画面（仕事と雑談）だけを変える。狭い画面・サイドバーと上部の帯の中身・レポートの内容部品・お伺いの中身（ADR 0062 論点 6 が上書き）は変えない。
- **状態と幅**: 迎える（記録なし）・働く（段が進む）・答える（お伺いが流れの末尾）・読む（最終レポートと畳んだ経過）・つまずく（失敗の表示）・過去のやり取りを見る、の6つ。やり取りの数は 0〜`MAX_MAIN_VIEW_TURNS` 件で、やり取りの列は 12 件以上で中が送られる。セリフは1ターンに 0〜十数件（推定）。
- **配置と操作**: 3列の幅は仕切り2本で変える。中央の列だけが会話の流れを縦に送り、進行の帯と入力欄は流れの上下に留まる。下端を見ているあいだは新しい行に追従し、上へ送って読んでいるあいだは動かない。

## 決めたこと

### 論点 1: 流れの並びのデータ

**採る: 会話の流れは、選んだやり取りの記録（`SessionState.records` をやり取りで区切ったもの）を、記録の並びの順のまま出す。並べる鍵は記録の位置で、時刻ではない。時刻は行の脇に出すだけに使い、時刻の無い記録と、時刻が分からない記録（`restored`）は時刻を出さない。雑談のログとは、行の部品（セリフの行・投稿の行・時刻・「...」）を共用し、並べる規則は分けたままにする。**

- 記録は届いた順に末尾へ足すだけで並べ替えない（「実物で確かめたこと」）。届いた順がそのまま流れの順になり、時刻で並べ直す必要が無い。時刻で並べると、時刻を持たない `detail`・`question` の置き場が決まらず、`restored` の記録が並べられない。
- 流れに出す行は、依頼（`request`）・補足（`aside`）を右寄せの投稿、セリフ（`speech`）・反応（`reaction`）を左寄せの行、段（`work-plan` と中間の本文）を段の札、答え終わった質問（`question`）を質問の記録、最終レポート（`report`）を紙にする。ツールの記録（`tool`）は流れに出さず、今と同じく進行の帯が持つ。
- 1つの流れに出すのは、選んだやり取り1つ（見本の働く・読むの場面のとおり）。やり取りの行と `[` `]` で別のやり取りを選ぶと、流れが入れ替わる。今の「1ターン＝1枚の札」の入れ替えと同じ線で、`useTurnSelection` と `useMainViewTurns` をそのまま使う。
- 雑談のログ（`chat-view/`）は、やり取りで区切らず日の区切りで積む規則なので、並べる部品は分けたままにする。行の部品は、仕事の流れを組む段で `chat-view/` から共用の置き場へ移す。

### 論点 2: 今の画面の要素の新しい置き場

**採る: 下の「今の要素から新しい置き場への対応表」のとおり。置き場が無くなる要素は次のように扱う。**

- **キャラビューの吹き出しの並び**: 消す。セリフと反応は会話の流れの行になり、同じセリフが2か所に出ない。
- **キャラビューの「ログ」**: 広い画面では口ごと消す。会話の流れが、選んだやり取りのセリフの履歴を持つ。狭い画面の吹き出しから開くログは、狭い画面を今のまま残すので残す。
- **ミニ立ち絵（`mini-portrait.tsx`）**: 消す。左の列の立ち絵が常に見えていて、レポートの上の立ち絵は2か所目になる。のちに利用者の決定で草稿の骨組みの右へ戻した（要件 4.3）。
- **列の頭の知らせ（`head-notice.tsx`）**: 会話の流れの下端に浮く口にし、「お伺い ↓」（`inquiry-jump-float.tsx`）と1つにまとめる。どちらも「いま見ている所の外で何かが起きた」を知らせて、押すとそこへ移る口で、2つ並べると同じ役が2か所になる。
- **答え待ちのカード（`pending-ask-card/`）**: 狭い画面だけの要素で、狭い画面を今のまま残すので変えない。

### 論点 3: 要件 4.7 と `PRODUCT.md` の書き換え方、ADR 0057 を置き換える範囲

**採る: 要件 4.7 の「biim 風の4領域」と「領域ごとに役割を1つ」を、「3列と1本の流れ」と「同じ情報を2か所に出さない」に書き換える。biim との対応は、左の列＝立ち絵・テロップ、中央の列＝ゲーム画面と実況者の手元、右の列＝タイム表・チャートとする。`PRODUCT.md` の Positioning は「セリフと詳細を分けて、別々の場所に出す」から「セリフと詳細を1本の流れの別々の形で出す（セリフは行、詳細は段の札と紙）」に改める。どちらも、その形が画面に出る段（会話の流れの段と3列の器の段）が、実装と同じコミットで書き換える。ADR 0057 は全体を置き換える。**

- 4.7 の狙い「同じ情報が2箇所に出ないようにする」はそのまま残す。変わるのは、守る単位が「領域ごとに役割を1つ」から「要素ごとに置き場を1つ」になること。対応表がその置き場の一覧になる。
- `PRODUCT.md` の Positioning の核（tsukumo が出力の見せ方を組み替える）は変えない。「別々の場所」を「別々の形」に替える。セリフを別の領域に分けたままにする案 F を採らなかったので、場所で分けるとは言えなくなる。
- ADR 0057 の決定は、どれもツリーに無い器の上の決定で、3列の器と両立しない。予告した文書の書き換えも行われていない。論点 4 の「新しい器ではトークンの向きを逆にする」も効かなくなり、ADR 0053 の向きがそのまま効く（論点 5）。

### 論点 4: ADR 0055（余白の札は本文が 30em 以上残るときだけ）との関係

**採る: ADR 0055 は変えない。境目は本文の容器の幅 692px（`ask-box.css` の `calc(30em + 248px + 24px)`。30em は字 14px で 420px）。見本の3列（仕切りは既定）では紙の中身が 1400px で約 729px あり、余白の札が出て本文は約 457px 残る。約 1345px より狭いと 0055 の狭い幅の形（「聞く・頼む」を行の右に、欄と答えは下から出すシート）になる。**

- 0055 の規則は本文の容器の幅を直接見るので、3列でも仕切りの位置でも同じ規則で追いつき、器の側で幅を測る仕組みは要らない。
- 測り方: 見本の読む場面を headless の Chromium で高さ 900px・幅を替えて開き、紙（`.sheet.paper`。tsukumo の `[data-report-body]` にあたる）の幅から padding と縁を引いた幅と字の大きさを取った（値の表と手順は研究の文書）。設計の前に見込んだ「約 1652px」は、見本の紙が持つお伺いの表の境目（880px）だった。
- 実物の `[data-report-body]` の幅は紙の padding で変わるので、会話の流れの段が 1400px で測り直す。
- 狭い幅でも余白の札を出す案（G・H）は採らなかった。H は状態として後から足せる。

### 論点 5: ADR 0053（Astryx の見た目に寄せる）と、透ける面・カプセルの進行の帯

**採る: 例外は定めず、ADR 0053 の向きのまま両立させる。透ける面・カプセルの進行の帯・段の札は、`ui/` の部品ではなく会話の画面の器と部品が持つ面で、その CSS（`conversation-layout.module.css` と各部品の `*.module.css`）が書く。濃さ・ぼかし・縁は、器の CSS のカスタムプロパティ（`--panel-fill`・`--panel-blur` と縁の色）に置き、Astryx のテーマのトークンには足さない。色は今の tsukumo のトークン（`ground`・`surface`・`ink`）から `color-mix()` で作る。**

- ADR 0053 が Astryx に従わせるのは `ui/` の部品の形と大きさ（字の段・余白・角丸・影）で、領域の面の地と縁は対象の外。透ける面の中に置く `ui/` の部品（ボタン・ダイアログ・入力）は、Astryx の見た目のまま使う。
- 角丸（見本の `--radius-container: 16px`）と影（見本の `--lift`）は、Astryx の `--radius-*`・`--shadow-*` に近い段があればそれを引き、無ければ器の CSS に置く。どちらにするかは面の見た目の段が値を突き合わせて決める（Astryx のトークンの上書きはしない）。
- ぼかしの面は、字のコントラストを 4.5:1 以上に保つ（面の見た目の段の完了条件）。

### 論点 6: 幅ごとの形

**採る: 境目は今の2つ（760px と 1100px）のまま。1101px 以上は3列。761〜1100px は、右の列（サイドバー）を今と同じく柱に畳み、左の列と中央の列は残す。760px 以下は今の縦1列のまま変えない。**

| 幅          | 左の列                                      | 中央の列                  | 右の列                                                         |
| ----------- | ------------------------------------------- | ------------------------- | -------------------------------------------------------------- |
| 1101px 以上 | 仕切りで決めた幅（既定は見本の 238px 相当） | 残り（1400px で約 795px） | 仕切りで決めた幅（既定は見本の 319px 相当）。下端まで          |
| 761〜1100px | 仕切りで決めた幅（下限 200px）              | 残り                      | 柱（開く口と進行中の件数）。開くと今と同じくサイドバーを重ねる |
| 760px 以下  | 無い（今のまま）                            | 縦1列（今のまま）         | 無い（引き出し。今のまま）                                     |

- 中くらいの幅でも左の列を残すのは、立ち絵を消すと「一緒にいる感じ」が狭い画面と同じ形まで落ちるため。柱から操作子（`RunSettingGroup placement="rail"`）を外すのは、操作子が入力欄へ移るため（サイドバーの例外の1つ）。
- 760px の境目は動かさない。狭い画面の規則は各機能の CSS の `@media (max-width: 760px)` に分かれていて（`docs/architecture/browser/bundle-style-component.md`「CSS」）、3列の器はその手前の幅だけを書く。
- 3列のそれぞれに `contain: layout style` を掛け、流れが伸びる（書きかけの本文が伸びる）たびの配置の計算を中央の列の中に閉じ込める（modern-web-guidance の `interactions-in-complex-layouts`）。

### 論点 7: 仕切り2本の比率の持ち方と、今の保存値からの移り方

**採る: 左の列の幅は、やり取りの列の幅（`main-view/domain/outline-panel.ts` の `widthPx`）を左の列の幅として引き継ぎ、px で持つ。可動域は 200〜400px に改める。サイドバーの幅は、`split.ts` の新しい鍵 `tsukumo-layout-split:v2` に、器の幅に対する % で持つ。今の鍵 `tsukumo-layout-split:v1` の3本の値は読まず、v2 は既定から始める。やり取りの列の畳み（`collapse`）は、左の列の上のやり取りの列だけを畳む印として残す。**

- 左の列の幅とやり取りの列の幅は3列では同じ幅で、2つの値を持つと食い違う道ができるので1つにする。px にするのは、左の列の中身（立ち絵と一覧の字）が器の幅ではなく自分の幅で決まるため。下限 200px は立ち絵と席が収まると見込んだ値で、測っていない。3列の器の段が撮って確かめ、重なるなら引き上げる。
- v1 の3本の比率のうち2本の仕切りに当たるのは `topLeft`（メインビューとサイドバー）だけで、それも左の列が増えた器では意味が違う。写しても利用者の決めた見え方にならないので、移さない。v1 の鍵は読まなくなるだけにし、消さない（`localPreference` の決まり）。
- 上段と下段の仕切り（入力欄の高さ）は無くなる。入力欄の高さは中身で決まる。
- 「比率を既定に戻す」は、仕切りのダブルクリックと ⌘K の行で、左の列の幅とサイドバーの幅の両方を既定に戻す（脇に出す札は隣と重なるので外した）。

### 論点 8: 背景の暗さの設定とパックの `veil` の優先

**採る: 利用者が「背景の暗さ」を一度でも動かしたら、利用者の値を使う。動かしていない間は、パックの `veil`（`character.json` の `background.veil`。省略時 0.75）を使う。どちらの値も、`MIN_BACKGROUND_VEIL`（0.7）と、今の地と字の色で決まる下限（`--character-background-veil-floor`）の大きいほうを下回らない。「既定に戻す」は、利用者の値を消してパックの値へ戻す。**

- パックの `veil` は、その背景の絵を書いた人が決めた暗さで、絵ごとに違う。利用者の値を既定で上書きすると、パックを替えたときに絵に合わない暗さになる。
- 利用者の値は端末ごとの好み（`src/browser/utils/local-preference.ts`）に置き、パックごとには持たない。「動かしたか」は、`outline-panel.ts` の `collapse: "unset"` と同じく、値が無い状態で表す。
- 下限の式は今の `conversation-layout.module.css` の `max(var(--character-background-veil), var(--character-background-veil-floor))` を残し、利用者の値はその前の項に入る。

### 論点 9: ぼかしの部品の数と描画の負荷の上限、送る順

**採る: ぼかしを常時持つ面は見本どおり7種類（上部の帯・やり取りの列・サイドバー・進行の帯・段の札・入力欄・入力欄の上の引き出し）にする。負荷の上限は「止まった画面で、ぼかしを外した版と描画プロセス・GPU プロセスの CPU が同じ桁（10秒の測定で 2 倍以内）」とする。守るために、ぼかしの面の中で無限に動くもの（進行の帯の回る印）は `steps()` にするか止まる形にし、ぼかしの値が 0 のときは `backdrop-filter` ごと外す。送る順は下の「送る順」の7段（下書きの5件のうち2段ずつを抱えた2件を割った）。**

- 根拠は「実物で確かめたこと」の測定。止まった画面ではぼかしは負荷を生まず、面の中の無限アニメーション1つで GPU プロセスが約10倍になった。部品の数より面の中の動きを止めるほうが効く。
- 測った GPU は SwiftShader で、実機では値が小さく出るが比は同じ向き（推定）。面の見た目の段が Orca の実タブで同じ測り方で取り直す。
- ぼかし 0 で `backdrop-filter` を外すのは、見本の `--glass-blur` が `blur(0px)` でも `saturate(1.15)` を残すため。

## 送る順

1件送るごとに画面が使える状態を保つ。各段のあとの画面の形を書いた。

1. **流れの並びを作り、メインビューを会話の流れで描く。** 選んだやり取りの記録を流れの行に変える純関数を `src/browser/domain/main-view/conversation-stream.ts` に足し、メインビューの札の中身を流れにする（依頼は右の投稿、セリフは左の行、段の札・お伺い・レポート）。ミニ立ち絵を消す。この段のあいだだけ、セリフが流れとキャラビューの吹き出しの2か所に出る。
2. **キャラビューから吹き出しの並びと広い画面の「ログ」を外す。** → キャラビューは立ち絵と席だけになり、セリフは流れの1か所になる。
3. **3列の器にし、背景を全面に敷き、仕切りを2本にする（仕事のとき）。** 立ち絵と席を左の列へ移し、サイドバーを下端まで伸ばし、入力欄を中央の列の下端に置く。中くらいの幅の柱を残す。やり取りの列の幅の値を左の列の幅へ引き継ぎ（論点 7）、「やり取りと本文の境界」の仕切りを外す。雑談は今の形のまま器に載せる。→ 仕事の画面が3列になる。やり取りの列はまだ中央の流れの左にあり、幅は既定で動かない。
4. **雑談モードを3列にそろえる。** 立ち絵を左の列へ、雑談のログを中央の流れへ移し、行の部品を仕事の流れと共用する。→ 雑談も3列になる。
5. **やり取りの列を左の列へ移す。** 立ち絵と左上の席に被らない高さで止め、中だけを送る。幅は左の列の幅に従い、列の頭の知らせを流れの下端の口へまとめる。→ 見本の配置になる。
6. **面の見た目をそろえる。** 透ける面・カプセルの進行の帯・段の札・紙の縁と影。ぼかしの面の中の無限アニメーションを止め、Orca の実タブで負荷を測る。→ 見本の見た目になる。
7. **見た目の設定を足す。** 歯車の「見た目」に背景の暗さ・パネルのぼかし・パネルの濃さを足し、論点 8 の優先で背景の暗さを決める。

入力欄の操作子の移動とヘッダーの細さは、この設計を待たずに別の段で進める。3列の器の段（3）は、操作子が入力欄へ移ったあとに送る（サイドバーの下端の帯から操作子が消えてから、柱の中身を減らすため）。

## 今の要素から新しい置き場への対応表

今の画面（2026-11-15 の主ブランチ dc71f3368）に出る要素を、部品の名前と今の領域（`data-region` の値。`main`・`sidebar`・`character`・`dispatch`）で1行ずつ挙げ、新しい置き場を決めた。新しい置き場の名前は次のとおり。

- **上部の帯**: 40px の1行（今の `screen-nav`）。
- **左の列**: 上から「やり取りの列」・立ち絵・席のアイテム。
- **中央の列**: 上から「進行の帯」（今のプログレスバーをカプセルにしたもの）・「会話の流れ」・入力欄。
- **右の列**: サイドバー。領域の下端まで伸びる。

「変える」は置き場か見た目が替わるもの、「変えない」は置き場も中身もそのままのもの、「消す」は広い画面から無くなるもの。狭い画面（760px 以下）は今のまま残すので、狭い画面だけの要素は「変えない」になる。見本（`docs/history/mockup/conversation-directions-2026-11-15/layouts.html?layout=a2`）の場面は、迎える（`scene=greet`）・働く（`work`）・答える（`ask`）・読む（`read`）の4つで、列「見本」にどの場面で見えるかを書いた（見本に無い要素は「無し」で、置き場はこの ADR が決めた）。

## 実物で確かめたこと
