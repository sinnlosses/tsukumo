# 図は書き手が構造を記述し、tsukumo が決まった配色と配置規則で描く（2026-10-25）

ステータス: 採用

**図を「構造を記述する段」と「描く段」に分け、描く段は tsukumo が持つ。** 書き手（`report` を呼ぶモデル）は
`graph` の記法で節点・辺・群・強調を記述するだけにし、配色と配置は tsukumo の規則が決める。描く段に別のモデル
（描画役）を起こす案は、`report` の前に描かせる形も、受け付けたあとで裏で描かせる形も採らない。
記述の口は新しい塊を足さず `graph` の記法を広げて使い、時間と量は今の `timeline`・`chart` のまま描く。

## 何が困っていたか

図が選ばれにくく、選ばれても書く量の少ない形に寄っていた。2026-10-19〜25 の受け付けた `report` 638件
（`~/.tsukumo/report-usage`、引き継ぎの無いもの）で、`figure` に図を置いたのは98件（540件が `none`）。
本文の塊は `text` 217・`markdown` 162・`list` 159・`graph` 109・`table` 106 に対し、座標を書く `svg` は25だった。
この数は疑似セッションの行を含む。疑似セッションを除いた実データでは `markdown` は 0 だった。
入れ子・色分け・戻り道のある図は、`graph`（mermaid の flowchart として描く）では一列に伸び、`svg` では
座標を全部書くことになる。

先行例 Multimodal DeepResearcher（[arxiv.org](https://arxiv.org/html/2506.02454)）は、本文の図の場所に
図の構造化記述（FDV。配置・尺度・データ・印の4面）を置き場として書かせ、記述を抜き出して D3.js のコードとして
別に描き、描いた図を画像で読み直して最大3回直す。図の枚数は対照と同じ（1本あたり 9.3 と 9.4）まま、
フロー図が 2→15 に増えた。代わりに1本の所要は 767秒（対照 373秒）で、増えた分の大半は描いて直す往復だった。

## 試しの測定（2026-10-25）

同じ3つの素材（構成・時間・原因。会話の実物は使わず `src/` と `tw metrics` から作った）を、記述
（`spec-m*.md`）にしてから4通りで描いた。画と記述と写しの道具は
`docs/history/mockup/report-figure-spec-2026-10-25/` にある。

| --------------------------------------------------------------------- | ------------------------------------- | ----------------------------- | --------------------------------- | -------------------------------------------- |
| 今の塊（`graph`・`timeline`）                                         | 縦一列に伸びる                        | 目盛りと所要の比が正しい      | 読める・色は1つ                   | 書き手のみ                                   |

- **書き手の字数は、記述と今の `graph` でほぼ同じ**だった（記述 591・358・598字、`graph` と `timeline` 395・537・365字）。
  分けても書き手の手間は減らない。減るのは、座標を全部書く `svg`（3702字）と比べたときだけ
- **リッチさは描く側で決まった。** 同じ記述から、描画役は群の色分け・強調の塗りで読みやすくし（原因の図）、
  機械の写しは配色だけが揃った。ただし**配置はどちらも D2 のレイアウト（ELK）任せ**で、構成の図は1列に伸びた。
  D2 の入れ子の向き（群ごとの `direction`）は ELK では効かず、格子（`grid-columns`）は辺が交差して読めなかった
  （`fig-b-grid-m1.png`）。2次元に折り返して読める形になったのは、座標を決めた SVG だけだった
- **時間の図は今の `timeline` が最も正確**だった。描画役の D2 は目盛りを持てず、字の入らない短い段の幅を広げて比を崩した
- **描画役は着手の印の立った作業ツリーで、返却の関門（`tw handback-guard`）に押されて検証まで走らせた**
  （3人とも。2人は `tw pause` も打った）。描く仕事だけを頼む役は今の関門の想定の外にある

## 決めたこと

### 描く段は tsukumo が持つ

ADR 0032 の「描き方を tsukumo が持つことで質を揃える」をそのまま図に当てる。描画役に描かせると、1枚に
4〜5分と約5万トークンが掛かり、出来は回ごとにばらつく（直しの回数が1〜3回に散った）。測定で描画役が勝ったのは
配色と強調の付け方で、これは規則として tsukumo に持たせられる。配置は描画役も D2 に任せていて勝っていない。

### 記述の口は `graph` の記法を広げる

新しい「記述」の欄や塊は足さない。書き手の字数が同じなので、口を2つにする理由が無い。記述の4面
（先行例の FDV に倣う）は `graph` の欄に次のように当てる。広げる部分は実装のタスクで決める。

| 記述の面           | `graph` の欄                                                             |
| ------------------ | ------------------------------------------------------------------------ |
| 目的（何を示すか） | `title`（数と向きで主張を言う1文。今のまま）                             |
| 要素と関係         | 節点の行（`名前 \| 説明`）・辺の行（`A -> B: 語`、点線 `-.>`）。今のまま |
| 群                 | `[群の名]` 〜 `[]` の囲み。今のまま（1階層）                             |
| 強調・戻り道       | 色の印 ` @a`〜` @e` に加え、主経路と戻り道を区別する印を足す             |

時間と量は記述の形が違う（行と数）ので、今の `timeline`・`chart` をそのまま使う。

### 配置と配色の規則

- **主経路が長い図は、tsukumo が行を折り返して座標を決める**（見本は `fig-svg-m1.png`。主経路を左から右へ
  並べ、器の幅を超えたら次の行へ折り返し、戻り道は行の外側を回す）。座標を決めた図は今の `svg` の塊と同じ
  経路で描く。どの図をこの配置に回すか（主経路の節点の数・分岐の数の境目）は実装のタスクで測って決める。
  決めた境目（2026-10-25）: 主経路（戻り道でない辺で辿る最長の一本道。書き手は印を付けない）が **6 節点以上**の図を回す。
  5 節点の流れは今の経路のまま読め、8 節点の流れは折り返すと 1440x900 で字が読める大きさに戻った。1行の数は 3〜6 個から、
  器に収めたときの字がいちばん大きいものを選ぶ。戻り道の印は `A <- B: 語`（規則の正典は `docs/architecture/display/figure-caption.md`）
- それ以外（分岐が多い・節点が少ない）は今の mermaid の flowchart の経路のまま
- 配色は群・強調・戻り道の印から tsukumo が決める（描画役の原因の図が見本。群ごとの地の色、強調の塗り、戻り道の色と点線）。
  書き手は色を書かない（今の ` @a`〜` @e` の意味の印は残す）

### D2 は採らない

D2 は記述からの写しが0.3秒で済み配色も揃うが、配置が mermaid と同じく一列に伸び、折り返しは解けなかった。
採ると、tsukumo が起こす外部コマンド（`test/architecture/outside-world.test.ts` の `ALLOWED_COMMANDS`）と、サーバで描いた
図をブラウザへ配る経路が増える。今の mermaid と `svg` の経路で同じことができるので、足さない。

### ADR 0028・0032 との関係

- ADR 0032（自由な HTML の口は持たない）は変えない。この判断はその「描き方を tsukumo が持つ」の延長にある
- ADR 0028（塊の梯子）の並びは変えない。`graph` の描き方が強くなり、梯子の上の段（図）を選んだときの出来が上がる

## 採らなかった案

| 案                                                                | 採らなかった理由                                                                                                                                                                                                                          |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `report` の前に描画役に描かせ、画像を `image` で載せる            | ターンが1枚あたり4〜5分延びる。出来がばらつく。描画役が返却の関門に押されて検証まで走る。配置は D2 任せで勝っていない                                                                                                                     |
| 受け付けたあとで tsukumo が描画役を起こし、置き場を図に差し替える | メインは待たないが、描画のためにモデルを起こす口（`docs/architecture.md` 原則3の `sdk-` のファイル）と、記録した引数のあとから図を差し替える表示（ADR 0031 の欄の構造との当たり）が要る。1枚約5万トークンを図のたびに払う。出来がばらつく |
| 「記述」の欄・塊を新しく足す                                      | 書き手の字数が `graph` と同じで、口を2つにするだけになる                                                                                                                                                                                  |
| 記述を D2 に写してサーバで描く                                    | 上の「D2 は採らない」                                                                                                                                                                                                                     |

## 見直す条件

- tsukumo の配置と配色の規則を入れても、構成・原因の図が今より読めない（実装のタスクで同じ3素材を撮り直して比べる）
- 描画役の費用（1枚約5万トークン・4〜5分）が、背景で回して気にならない程度まで下がる

## 結果

- 実装は後段のタスクで、`graph` の記法に主経路と戻り道の印を足し、折り返し配置と配色の規則を tsukumo の描画に足す
- 縦に長い図の表示（高さの上限で縮む）は別のタスクが扱う。折り返し配置は横長にも縦長にも伸ばさない向きに効く
