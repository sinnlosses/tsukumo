# 自動判定の拒否を最下部のお願いに出し、一度だけの許可で同じ呼び出しを通す（2026-11-26）

ステータス: 採用

**auto mode の分類器（自動判定）に拒否されたツールの呼び出しを、`PermissionDenied` フックで拾ってセッションの状態「自動判定の拒否」（`permissionDenials`）に積み、お伺いと同じ最下部のカードに「一度だけ許可」「断る」の2つで出す。許可したら、駆動の側に同じツール・同じ入力の次の1回だけに効く印（一度だけの許可）を立て、差し込みの発言で打ち直しを頼む。打ち直しが来たら PreToolUse フックが `ask` を返して `canUseTool` へ回し、印と一致した呼び出しを利用者に聞き直さず許可して印を消す。**

経路の前提は `docs/research/auto-mode-denial-routing-trial-2026-11-26.md`（Agent SDK 0.3.332 の実機の確認）。

## 何が困っていたか

- 自動判定に拒否された呼び出しは、モデルへ拒否の文が返るだけで画面に出ない。モデルが自力で迂回できなければ、利用者は何が止まったか分からないまま会話が止まる。
- tsukumo 自身の PreToolUse（Bash の `command` を短い出力の版へ差し替える書き換え）は、審査のあとに入力を変えるので、それ自体が「判定なし」の拒否を起こす。

## 決まっていたこと（蒸し返さない）

- お願いは入力欄のそば（会話の最下部）に出す。
- 選べるのは「一度だけ許可」と「断る」の2つ。常設の allow の規則を足す選択肢は置かない（`~/.claude/settings.json` を書き換えないため）。
- 一度だけの許可は、許可した拒否と同じツール・同じ入力の次の1回だけに効き、使ったら消える。
- サブエージェントの中の拒否も `agent_id` で拾い、同じお願いに出す。
- 許可の確認の入力と拒否の文（`message`）は会話の内容なので、ログにもファイルにも書かず、セッションイベントにも載せない。
- `PermissionDenied` フックは `retry` を返さない。

## 決めたこと

### 論点 1: お願いを `PendingAsk` の新しい `kind` にするか、別の状態にするか

**採る: 別の状態にする。セッションの状態に `permissionDenials`（自動判定の拒否の並び。1件は `PermissionDenial`）を持ち、イベント `permission-denied`（積む）と `permission-denial-settled`（下げる）で畳む。画面の答えの口は既存の `answer`（`id` と `allow` / `deny`）をそのまま使い、駆動は `id` が答え待ちの列に無ければ拒否の並びへ回す。**

- `PendingAsk` の列は `canUseTool` の Promise に結び付き、中断・セッションの終わりで拒否として畳む（`settleAll`）。拒否はすでに確定した事実で、待っている Promise が無い。同じ列に入れると、畳み方（中断で消す・答えで Promise を解く）の前提が種類ごとに分かれ、列の契約が読みにくくなる。
- 画面では、答え待ちが無いときだけ拒否の先頭をお伺いのカード（種類「自動判定」）として出す。答え待ちは SDK が応答を待って止まっているので、先に答えてもらう。
- 1件が持つのは、`tool_use_id`・ツール名・理由の要約・`agent_id`（サブエージェントの中のときだけ）だけ。`tool_input` と `message` は載せない。
- セッションが終わったら並びを空にする（印を持つ駆動ごと消えるので、答えても通らない）。`/clear` では消さない（駆動は残っている）。

### 論点 2: 拒否の起点を `PermissionDenied` フックと `permission_denied` メッセージのどちらにするか

**採る: `PermissionDenied` フックだけにする。`system` / `permission_denied` メッセージは拾わない。1件の id はフックの `tool_use_id`。**

- 印の照合に要る入力（`tool_input`）を持つのはフックだけで、メッセージは持たない（記録の (a)）。主の拒否もサブエージェントの中の拒否も、フックは1回ずつ呼ばれた（`agent_id` つき）。
- 両方を拾うと、`tool_use_id` で1つにまとめる手間と、片方だけ届いたときの扱いが要る。メッセージは型の説明どおり best-effort で、フックで足りない欄も無い。
- 理由の要約はフックの `reason`（分類器の `decision_reason` と同じ。書き換えの拒否では `Classifier unavailable`）を 200 字で切ったもの。`message` は書き換え後の入力を含むので使わない。

### 論点 3: 画面で許可したことをモデルへどう知らせるか。許可より先に来た打ち直しの扱い

**採る: 駆動が入力のストリームへ定型の差し込みの発言を送る（進みの差し込みと同じ道。依頼の記録 `request` は流さず、組み直しでは `turn-resumed` に戻す）。文はツール名だけを含み、入力は含めない。ターンが走っていれば次の区切りでモデルに届き、止まっていれば新しいターンを起こす。**

- 次の `tool_result` の文で届ける道は、拒否のあとにモデルが別のツールを呼ぶとは限らないので、届く保証が無い。
- **許可より先に来た打ち直し**: 同じ鍵（論点 5）の呼び出しが、印の無いまま PreToolUse に来たら、前の拒否は下げる（`permission-denial-settled`）。その呼び出しは今までどおり分類器に回り、また拒否されれば新しい拒否として積まれ、通れば札は残らない。札が残ったまま打ち直しが通ると、あとから押した許可が同じ操作をもう一度実行させてしまう。

### 論点 4: 「断る」を選んだとき、モデルへ何を伝えて続きを促すか

**採る: 許可と同じ道で、「利用者は許可しなかった。同じ呼び出しを打ち直さず、ほかの手で進めるか、できないことを伝えてほしい」という定型の差し込みの発言を送る。印は立てない。**

- 何も送らないと、モデルは拒否の文の指示（同じ入力で打ち直せ）に従い続けるか、答えを待って止まったままになる。

### 論点 5: 一度だけの許可の印の置き場・同じ入力かを見る鍵・印を捨てる時機

**採る: 印は駆動の側の短命な状態（`src/server/session-driver/core/denial-grant.ts` の `createDenialGrants`。セッション1つに1つ）に持つ。セッションの状態にもファイルにも置かない。**

- **鍵**: ツール名と、入力をキーの順にそろえて JSON にした文字列の組。Bash は tsukumo の書き換えの前と後の2つの入力のどちらかが印と一致すれば当たりにする（拒否のフックが見る入力が書き換えの前か後か、モデルが打ち直す入力が拒否の文の中の書き換え後の版か元の版か、のどれでも照合がずれない）。書き換えと照合は同じ Bash のフックの中で順に行う（別のフックに分けると並んで走り、書き換え後の入力が見えない）。
- **照らす範囲**: 委譲ゲートと同じく、読み取り（`Read`・`Grep`・`Glob`・`ToolSearch`）と tsukumo のツールには照合のフックを当てない（matcher のあるフックを当てない決まりを崩さない）。
- **流れ**: PreToolUse で印と一致した呼び出しは、印を消して `tool_use_id` に「通す」の控えを付け、`permissionDecision: "ask"` を返す（Bash は書き換えの `updatedInput` と一緒に）。`canUseTool` は `toolUseID` に控えがあれば利用者に聞かずに許可し、控えを消す。2回目の同じ呼び出しは印が無いので、今までどおり分類器（または利用者の確認）に回る。
- **捨てる時機**: 差し込みの発言を受け取ったターン（`result` の `user_message_uuids` に、その発言の uuid が入ったターン）が終わったとき。それまでに打ち直しが来なければ印を捨てる。セッションを閉じたときも捨てる。
- 照合はツール名と入力の一致だけで決める機械的な照合で、ヒューリスティックは使わない。

## 確かめられていないもの

- 分類器が危険と判断した拒否（`decision_reason` が理由文になる場合）を、フックの `ask` が覆せるか。覆せないと分かったら、その種類の拒否は「一度だけ許可」を出さず理由だけを見せる形に狭める。
- Bash・Edit の拒否のあとの打ち直し（記録で確かめたのは Write）。

## 影響

- `src/server/session-driver/adapter/sdk/sdk-query-seed.ts` に `PermissionDenied` フックと、PreToolUse の印の照合を足す。
- `src/server/session-driver/core/session/input-ledger.ts` の入力の種類に差し込みの発言（`denial-notice`）を足す。
- 画面は `src/browser/components/page/conversation/stores/inquiry-answer.ts` のお伺いの形に種類 `denial` を足し、お伺いのカードと狭い画面の答え待ちのカードが同じ形で出す。
