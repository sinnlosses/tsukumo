# HTML はローカルの HTTP サーバから配る（ファイルに書き出さない）

検討した案:

- **案A: HTML をファイルに書き出して `file://` で開く** — **採らない**
- **案B: 127.0.0.1 のローカル HTTP サーバから配る** — **採用**

決め手は**会話内容の扱い**（`docs/coding-standards.md`）。案Aはビューの中身、つまり発話の一部を
**平文でディスクに残す**ことになり、「別の場所に複製しない」と正面から衝突する。案Bなら本文は
プロセスのメモリにしか無く、プロセスが終われば消える。**発話を含む HTML をファイルに書き出す
経路をコードに作らない**のは、この判断がそのまま制約になっているため。

副次的な理由が2つある。後段で**入力を claude に送り込む**ことが決まっており、そのときサーバは
どのみち要る（`docs/history/direction.md` 2026-09-09 Q6）。**2026-09-11 にこれは前提になった**:
入力欄・許可の回答・中断がすべてこのサーバへの POST で届く。また `file://` のページは
Server-Sent Events の接続元として扱いが悪く、更新の押し込みが素直に書けない。

**サーバは `127.0.0.1` にだけバインドする。** 会話の一部を平文で配るので、同じマシンの外からは
届かないことが前提になっている。`0.0.0.0` に変えない。

ポートは既定を固定（7327）にした。ブラウザのタブは URL で開きっぱなしになるので、
tsukumo を起動し直すたびにポートが変わると、開いていたタブが全部死ぬ。空きを探して
番号がずれるより、**塞がっていたら起動時に失敗する**ほうが原因が分かりやすい
（起動時の前提不足なので即時終了してよい。`docs/coding-standards.md`「エラーハンドリング」）。
`TSUKUMO_VIEW_PORT` で変えられるようにしてあり、`0` を渡すと空きポートを使う。
