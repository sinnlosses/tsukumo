- 送る前の検証（`pnpm run check --full`。`tw ship` が付け替えたときに打つ）で、自分の差分（main との差）が文書だけなら E2E と単体テストの全件を流さず、文書の検査だけにしたい。`scripts/check.ts` は「タスク登録だけの変更は --full でも format:check と文書の検査だけ」をもう持つので、その判定を文書だけの差分へ広げる。付け替えで入った他人のコードはその人の送り出しで検証済み。GH-366（文書4本だけ）の受け入れ11分17秒のうち、付け替えのあとの `check --full` の全件 E2E が約2分を占めた（2026-10-07 実測。tw の flow の done 23:28:11 → ship 23:30:34）
- usage-review の「タスクにする」は、`tasks` の設定が無いとタスク運用なしとして扱う（`src/server/usage-review/core/usage-review-tool.ts`）。一覧は設定が無くても Beads を試し読みするので食い違う。設定が無くても `.beads` が読めればタスク運用ありとして扱い、`docs/requirements.md` の使い方の見直しの項（「起動先がタスク運用なし」）も合わせて直す
- （claude-skills）`/next-task` の委譲先が最後の段で `tw verify` を打つ前に、タスクの性質ごとのセルフレビューを通す。性質は `review_needed.py` と同じく変えたファイル・差分から台本が機械で決め、性質ごとに「打つコマンド」と「問い」を3〜4個に固定する（自由記述の「見直す」にしない。依頼文で禁じた言い直しのコメントを GH-467 では2回とも書いていた）。初めの性質と問い: コメントを足した → `diff_added_comment_lines.py` の行ごとに comment-audit の判定の1問／型・定数の形を変えた → 推論された型が前より緩んでいないか（readonly・リテラル）／同じ形の処理を足した → 同じファイルに似たループ・関数が既にあるか／文書と検査を両方変えた → 文書が言う範囲と検査が拾う範囲が合うか。描画は既存の目視の段に任せる。受け入れのレビューは残し、セルフレビューはその前段に置く。機械の検査に落とせた種類は問いから外す。効いたかは振り返りの `--review` の found／clean の比で入れる前後を比べる。根拠: GH-467 の受け入れ13分26秒のうち約9分が2回の差し戻しと再検証で、指摘5件はすべて上の問いで拾える種類だった（2026-10-08 実測。tw の flow の accept 22:16:36 → retro 22:25:51）。`develop/draft/2026-10-08-subagent-self-comment-audit.md` はこの1件目の問いに吸収した
