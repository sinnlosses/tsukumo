## 2026-09-09 「二重表示の何が厳しいか」への回答（本質）

大まかな問題点は2つ。

1. asuna が出力するものは詳細な情報+会話のためのセリフ。実現したいのは、詳細な情報と会話の
   ためのセリフを分離して別々のペインに表示することでノイズを減らしてキャラクターとのやり取りを
   楽しみつつ仕事したいというものだよ。
2. 詳細な情報の部分が結構理解しづらいことも多いよ。ここを人間にとってわかりやすくフォーマット
   したうえで会話と分けて出せると仕事が捗る気がする。

### 補足（メインセッションの読み。タスク化のときに確かめること）

**これは `docs/requirements.md` 1章の目的そのものの書き換えになる。** 現在の要件は
「最新の assistant 発話を吹き出しに出す」だが、本当の目的は**出力を「セリフ」と「詳細」に
分離して別ペインに出し、詳細は人間に読みやすく整形すること**。吹き出しはその手段の一部。

分離の手段が最大の論点。少なくとも3案ある:

- **(a) 出力スタイル側に規約を入れて、モデルが構造的に書き分ける**（例: セリフは決まった位置に置く）。
  決定的で安上がりだが、`~/.claude/output-styles/asuna.md` の変更が要り、TUI の見え方にも影響する
- **(b) tsukumo 側がヒューリスティックで分類する**（コードブロック・表・パスは詳細、地の文はセリフ）。
  変更は tsukumo 内で閉じるが、判定が壊れやすい
- **(c) 小さいモデルに分離・整形させる**。2つ目の「読みやすく整形」にも同時に効くが、
  コストと遅延が乗り、`docs/requirements.md`「会話内容の扱い」（外部に送らない）と衝突しうる

**2つ目の「理解しづらい」の正体を先に切り分けること。** 見た目の問題（Markdown が素のまま出る）なら
レンダラを作れば済み、中身の問題（情報が多い・順序が悪い）なら要約や再構成が要る。前者なら (c) は不要。

## 2026-09-09 前提の訂正と Q1〜Q3 への回答

**前提**: tsukumo とは「キャラクターと一緒に楽しく仕事をするためのターミナル環境」。
この目的に沿うなら要件に入れてよい。詳細な情報とセリフの分離は**その手段の1つ**。

- **Q1（分離をどこでやるか）→ (a) 出力スタイル側に規約を入れて、モデルが構造的に書き分ける**
- **Q2（「理解しづらい」の正体）→ 見た目が主、で合っている。**
  実例として挙がったのは、メインセッションが書いた「目視確認の手順」の応答
  （見出し＋箇条書き＋コードブロック＋注意書き2件が一度に並ぶもの）。
  「いろんな情報があってすぐに頭に入らなかった」「見やすく HTML で描画できたりするといいけどねぇ」
- **Q3（TUI ペインに何を残すか）→ 正直不要まである。**
  入力専用・表示専用・キャラクターとのやり取り専用、と完全分離できると biim っぽくなる

### 補足（メインセッションの観察）

**ユーザーが実例として貼り返した応答は、貼られた時点で表示が途中で欠けていた**
（「衣装は当面「不明」のま の payloadにしか載らなくて」のように、行の途中が飛んでいる）。
これは「読みづらさ」が中身だけでなく**端末上の表示そのもの**にも由来している裏付けになる。

**目的の書き換えが2段階で必要**:

1. `docs/requirements.md` 1章の目的を「キャラクターと一緒に楽しく仕事をするためのターミナル環境」にする。
   現在の「発話を立ち絵と吹き出しで表示するサイドカー」は手段であって目的ではない
2. スコープ（2章）に「詳細とセリフの分離」「詳細の読みやすい整形」「ペインの役割分担」を入れる

**次に決めること（未確定）**: 詳細ペインの実体をどうするか。ターミナル内でリッチに描画するのか、
HTML を別ウィンドウ（ブラウザ）で出すのか。後者は「ターミナル環境」という前提と衝突しうるので、
ユーザーに確認すること。

## 2026-09-09 詳細ペインの実体（Orca の機能調査つき）

**HTML の方向でよい。ただし Chrome に出るのは嫌で、このシステムを使って一体感を出せる
仕組みにしたい。**

### メインセッションが調べた事実（2026-09-09、Orca v1.4.194 / com.stablyai.orca）

`orca --help` で確認した、tsukumo に効く機能:

| コマンド                | できること                                             |
| ----------------------- | ------------------------------------------------------ |
| `orca tab create --url` | **Orca 自身のブラウザタブ**を開く（Chrome に出ない）   |
| `orca terminal split`   | ペインを分割し、`--command` で起動時のコマンドも渡せる |
| `orca terminal create`  | worktree 内にターミナルを作る                          |
| `orca terminal rename`  | タブのタイトルを設定する                               |
| `orca terminal switch`  | タブを前面に出す                                       |
| `orca file open`        | Orca のエディタでファイルを開く                        |
| `orca agent-context`    | エージェント向けの機械可読なコマンドスキーマを出す     |

**これにより「Chrome に飛ばずに HTML を出す」が素直に実現できる**（詳細を HTML として
ローカルに書き出し、`orca tab create --url file://...` で Orca 内に開く）。
さらに `orca terminal split` があるので、**biim レイアウトを tsukumo 自身が組み立てられる**。

想定する構成:

```
┌──────────────┬──────────────────┐
│ claude (入力) │  Orca ブラウザタブ │
│              │   詳細をHTMLで     │
├──────────────┤   きれいに描画      │
│ tsukumo      │                  │
│ 立ち絵＋セリフ │                  │
└──────────────┴──────────────────┘
```

### タスク化のときに確かめること

- **Orca 依存をどこまで許すか。** `docs/requirements.md` は現状 macOS + VS Code 統合ターミナルを
  第一級としているが、この構成は Orca 固有の機能に強く依存する。Orca 前提にするのか、
  Orca が無いときはターミナルだけにフォールバックするのかを決める
- `orca agent-context` の中身をまだ読んでいない。実装前に読むこと
- HTML をどう生成するか（詳細のテキスト → HTML）。整形の主体は Q1 の (a) と整合させる

## 2026-09-09 Orca 依存と画面レイアウトの決定

**まずは Orca 前提でよい。**

レイアウトは biim システムをリスペクトした配置にする:

- **左上**: ブラウザ（詳細を HTML で描画）
- **左下**: 立ち絵＋セリフ
- **右下**: 入力（claude の TUI）
- **右サイドバー**: その他情報

**比率の指定**: サイドバーはもう少し狭く、ブラウザは広く、左下と右下は半分ずつ。
サイドバーは右端に全高で細く取り、その左を上下に割る。

```
┌────────────────────────────────────┬─────────┐
│ ブラウザ                            │ サイド   │
│  詳細をHTMLで描画（広く取る）        │ バー     │
│                                    │ （狭め）  │
│                                    │         │
├─────────────────┬──────────────────┤ 情報     │
│ 立ち絵＋セリフ    │ 入力              │         │
│  （半分）         │  claude TUI（半分）│         │
└─────────────────┴──────────────────┴─────────┘
```

### タスク化のときに確かめること

- **「その他情報」に何を出すか**が未定。候補: 実行中のモデル、経過時間、context 残量、
  `develop/tasks.json` の進捗、直近のツール実行。**ここは biim でいうタイム表・チャートに当たる**
- Orca 前提にしたので、`docs/requirements.md`「5. 実行環境」の「VS Code 統合ターミナルを
  第一級」という記述と、`docs/architecture.md`「tmux ではなく VS Code の split terminal を
  前提にした」の設計判断を**両方書き換える**必要がある
- レイアウトを誰が組み立てるか（tsukumo が `orca terminal split` で自動構築するのか、
  ユーザーが手で配置するのか）
