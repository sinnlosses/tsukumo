## 目的

`bun run check` のテストが、ときどき 100% CPU のまま返らなくなる原因を突き止め、直せるなら直す。これが起きると `/loop /next-task` の受け入れが止まる。

## 完了条件

- 再現の手順（または再現できなかった試行の記録）と、止まったときに `bun test` の子プロセスがどのファイルを走らせていたかを、タスクの結果に書く
- 原因が分かったら直し、直す前に止まっていた条件で止まらなくなったことを示す。直せない（bun 本体の不具合など）なら、回避策と、`docs/coding-standards.md`「テスト」節への注意書きを足す
- 原因が分からなければ、試したことと絞り込めた範囲を書いて `done` にしてよい
- `bun run check` が通る
- 調べて前提が成り立たなければ、理由を書いて `dropped` で閉じてよい

## 背景

- 2026-09-25 に、ほかの `bun test` が並んでいないのに `bun run check` が 8分以上返らず、残った `bun test --isolate` のプロセスを止めて打ち直すと 27秒で通った（T-606 の受け入れ）。T-597 の受け入れでも同じ症状があり、そのときは同じ作業ツリーで `bun test` を2本並べたのが原因と見ていた
- 1ファイルずつ流すと全部通るので、ファイルの組み合わせか、時刻・ポートに依る無限ループが疑われる
- `bun run test` は `bun test --isolate`（素の `bun test` は `mock.module` が漏れるので使わない）

## 解くべき論点

- 再現の確率が低いときに、どのファイルで止まっているかを外から取る方法（子プロセスの引数・`--timeout`・ファイルの二分探索など）
- 原因が tsukumo のテスト（サーバやタイマーの後片付け漏れ）にあるのか、bun 本体にあるのか

## 注意

- `diagnosing-bugs` スキルの手順で進める
- 調べるために起こした背景のプロセスは、報告の前に必ず止める
