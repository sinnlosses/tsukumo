## 目的

`bun run check` のテストが、ときどき 100% CPU のまま返らなくなる原因を突き止め、直せるなら直す。これが起きると `/loop /next-task` の受け入れが止まる。

## 完了条件

- 再現の手順（または再現できなかった試行の記録）と、止まったときに `bun test` の子プロセスがどのファイルを走らせていたかを、タスクの結果に書く
- 原因が分かったら直し、直す前に止まっていた条件で止まらなくなったことを示す。直せない（bun 本体の不具合など）なら、回避策と、`docs/coding-standards.md`「テスト」節への注意書きを足す
- 原因が分からなければ、試したことと絞り込めた範囲を書いて `done` にしてよい
- `bun run check` が通る
- 調べて前提が成り立たなければ、理由を書いて `dropped` で閉じてよい

## 背景

- 2026-09-25 に、ほかの `bun test` が並んでいないのに `bun run check` が 8分以上返らず、残った `bun test --isolate` のプロセスを止めて打ち直すと 27秒で通った（T-606 の受け入れ）。T-597 の受け入れでも同じ症状があり、そのときは同じ作業ツリーで `bun test` を2本並べたのが原因と見ていた
- 1ファイルずつ流すと全部通るので、ファイルの組み合わせか、時刻・ポートに依る無限ループが疑われる
- `bun run test` は `bun test --isolate`（素の `bun test` は `mock.module` が漏れるので使わない）

## 解くべき論点

- 再現の確率が低いときに、どのファイルで止まっているかを外から取る方法（子プロセスの引数・`--timeout`・ファイルの二分探索など）
- 原因が tsukumo のテスト（サーバやタイマーの後片付け漏れ）にあるのか、bun 本体にあるのか

## やること

いまのコードで前提を調べ直した結果（2026-09-26。bun 1.4.2 / macOS arm64）:

- **`--isolate` は子プロセスを起こさない。** 1つのプロセスの中で、ファイルごとに新しいグローバルを作って順に流す（`bun test --help`）。「子プロセスの引数」からは走っているファイルを取れない
- **既定の出力（非 TTY）は最後の要約しか出さない**ので、止まった回のログからもファイルは分からない。代わりに `--preload` で読ませる小さなファイルが使える: preload はファイルごとに評価し直され、`beforeEach` / `afterEach` の中の `Bun.main` がいま走っているテストファイルを指す（実測）。これを時刻つきで追記すれば、止まったファイルと「テストの中か外か」が外から取れる
- **100% CPU で止まるのは、ふつうの待ちではない。** 子の終了を待つ `spawnSync` は CPU を使わない（`sleep 4` を待たせて user/sys とも 0.00s。実測）。非同期の待ち（fetch・タイマー・`execFile`）は、テストごとの時間切れ（既定 5 秒）で落ちて次へ進む。残る候補は (a) テストか本体の同期的な無限ループ、(b) **bun の `spawnSync` の待ちが空回りする不具合**（oven-sh/bun #34069「child exit lost, wait loop busy-spins at 100% CPU（macOS ARM64）」と、その修正 PR #40078。どちらも 2026-09-26 時点で open。PR によれば空回り中は `spawnSync` の `timeout` も効かず、非同期の spawn は当たらない）
- テストの中で同期的に子を起こしているのは5ファイル: `test/cli.test.ts`（`spawnSync` で `bun run src/cli.ts`）、`test/scripts/deny-broad-kill.test.ts`、`test/server/achievement/adapter/main-history.test.ts`、`test/server/repository/adapter/task-summary.test.ts`、`test/server/diary/adapter/diary.test.ts`（どれも `execFileSync`）。全体を1回流すと `git` だけで約 710 回起きる（`PATH` に数える `git` を差して実測）

作業:

1. 上の preload と見張り（一定時間を超えたら最後のファイルを記録して pid で止める）で、全体と、同期 spawn の多いファイルの組を繰り返し流し、止まる回を捕まえる
2. 捕まえたら、そのファイルと待っている場所（`sample` のスタック）から原因を決めて直す
3. 捕まらなければ、(b) に当たっても**時間切れで落ちて次へ進む**形にする: テストの中の同期的な子の起動を非同期に替える（ふつうに待っている `spawnSync` はテストの時間切れで子ごと止まる（実測）が、(b) の空回りの最中は `spawnSync` の `timeout` も効かないと修正 PR が報告している。非同期の待ちはその経路を通らない）。`.oxlintrc.json` で `test/` の同期 spawn を止める。あわせて `docs/coding-standards.md`「テスト」節に注意書きと、止まったときにファイルを取る手順を足す

- 調べるために起こした背景のプロセスは、報告の前に必ず止める
