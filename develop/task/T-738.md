## 目的

`bun run check` の最後の段（`bun run test:e2e`）が全シナリオを直列に流していて時間がかかる。検証のたびに全件を流す運用のまま、段の所要時間を縮める（2026-09-27 ユーザーの指示）。

## 完了条件

- 手を入れる前と後で `bun run test:e2e` の所要時間を同じ機械で測り、タスクファイルの結果の節に前後の秒数を書く
- 並列化などの変更のあと、`bun run test:e2e` を続けて3回通し、落ちないことを確かめる（揺れを増やしていない証拠）
- `docs/design.md` 10章「E2E の走らせ方」の所要時間の目安と `--parallel` の条を、入れた形に合わせて直す
- 検証コマンド `bun run check` を通す
- 調べて速くする手が無い（並列にすると揺れる・Bun に口が無い等）と分かったら、測った数と理由を結果の節に書いて `dropped` で閉じてよい

## 決まっていること（蒸し返さない）

- 改修した範囲に関わる E2E だけを走らせるルールは作らない。関わる分だけ走らせても `task ship` が検証で全件を流すので2回走ることになるため、検証時には全件を流し、その全件を速くする（2026-09-27 ユーザーの判断）
- 件を削って速くしない（`docs/design.md` 10章「E2E の走らせ方」の「件を削らずに `--parallel` を足す」）

## 背景

- `package.json` の `test:e2e` は `bun run build && bun test --isolate --timeout=60000 test/e2e/`。`check` は `typecheck && lint && format:check && test && test:e2e` の順
- シナリオは `test/e2e/<シナリオ>.test.ts` の16ファイルに分かれていて、足場は `test/e2e/scenario-run.ts`
- `docs/design.md` 10章「E2E の走らせ方」: ブラウザは1ファイルに1つ（`beforeAll`）、tsukumo は1件ごとに1つ起こし、ポート（`TSUKUMO_VIEW_PORT=0`）もホームも cwd も1件ごとに分かれている。「所要時間の目安は E2E の段で 60 秒まで。超えたら件を削らずに `--parallel` を足す」とある
- `task ship` は CLAUDE.md「## タスク運用」の検証コマンド（`bun run check`）を自分で走らせてから main へ送る

## 注意

- Bun 1.3 の `bun test` に並列実行の口があるか、`--isolate` と併用できるかは、手元の `bun test --help` とその場の実物で確かめる（記憶の知識を前提にしない）。口が無ければファイル単位で複数の `bun test` を並べる形も比べる
- 並列にすると Chrome を同時に複数起こす。`docs/design.md` 10章の「場面が流れ終わるのを時間で待たない」前提が崩れていないか、負荷で落ちる件が出ないかを見る
- T-672（`input-dispatch.test.ts` が `bun run check` の中でときどき落ちる）と重なる。並列化で落ち方が変わったら T-672 の本文の背景の節に書き足す
- T-725（検証結果に時間を添える）と測り方が重なる。段ごとの時間を測る仕組みを作るならそちらに寄せる
- 2026-09-27: T-785 で単体テストの `maxWorkers` に上限を置く。E2E を並列にするなら、並行する作業ツリーで重なっても1本あたりの負荷がコア数を超えない本数にする
