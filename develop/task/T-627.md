## 目的

`test-audit` スキルのキャンペーンモード（同スキルの `CAMPAIGN.md` の8段）で、`test/scripts/`（5ファイル）と `test/` 直下の `architecture.test.ts` `cli.test.ts` `section-reference.test.ts` `task-id.test.ts`（約2,500行） のテストを刈り込む。価値の低いテスト・実装に結合したテスト・より強い証明と重なるテストと、テストしか呼ばない本番コードを消し、残す契約はより強い境界のテストに寄せる。

## 完了条件

- 対象範囲のテストの宣言ごとに `R` / `F` / `C` / `D` の印と1行の証拠を付けた台帳を作り、印ごとの件数と、`C` / `D` の宣言ごとの残す側（keeper）を タスクの結果 に書く（台帳の全文はリポジトリに置かない）
- `D` / `C` の編集と、それで消せるようになったテスト専用の本番コードの継ぎ目の削除を済ませる
- 移した（`C` / `F`）契約ごとに、本番側の持ち主にわざと1つ変異を入れて keeper が落ちることを確かめ、元に戻す
- 基準線（着手時）と完了時の、対象範囲のテストの `it` の数と行数、本番コードの増減を タスクの結果 に書く
- `bun run check` が通る
- 確信の持てる候補が無ければ、台帳の件数だけ書いて編集なしで `done` にしてよい

## 背景

- 2026-09-25 に `test-audit` スキル（openclaw/openclaw の同名スキルを日本語化して claude-skills に入れたもの）を取り込み、監査モードの試運転で、テストだけが呼んでいた `parseAnswer`（`src/shared/pending-ask.ts`）と `newFormatTaskSummaries`（`src/shared/task-summary.ts`）を消した。固有の検査は `test/shared/command.test.ts` と `test/server/repository/adapter/task-summary.test.ts` に移した（`0b3ef70a`）
- テスト全体は 205 ファイル・約4.7万行で、機能ごとに1タスクに分けた。このタスクはscripts と直下のテストの範囲

## 決まっていること（蒸し返さない）

- 消すかどうかは `docs/coding-standards.md`「テスト」節の「消すかどうか」「埋めないと決めた穴」と突き合わせる。スキルの残す基準とリポジトリの規約が食い違ったら、リポジトリの規約を優先し、食い違いを タスクの結果 に書く
- 残す基準は、スキルの `SKILL.md`「残す基準」のとおり（とくに、出力の書式を固定するテストと過去のバグの退行テストは残す）
- `CAMPAIGN.md` の段7（プロダクトの欠陥）で見つけた欠陥は、このタスクでは直さず、`develop/direction.md` の 「エージェントのドラフト」節 に積む。段8（`main` の merge）はタスクが短いので要らない
- 1タスク＝1コミット。対象範囲の外のテストは、範囲内の契約を吸収する keeper になるときだけ触る

## やること

前提を調べ直した（2026-09-25）。対象範囲は9ファイル・宣言92件（`it`/`test`/`test.each` を1宣言として数える）・
2097行（タスク本文の「約2,500行」は実測とややずれる）:

- `test/scripts/`: `deny-broad-kill.test.ts`(4)・`room-grid.test.ts`(32)・`section-reference.test.ts`(15)・
  `task-id.test.ts`(6)・`task-mention.test.ts`(8)
- `test/` 直下: `architecture.test.ts`(20)・`cli.test.ts`(4)・`section-reference.test.ts`(1)・`task-id.test.ts`(2)

レーンは本番側の持ち主で切る: (1) `scripts/section-reference.ts` + `scripts/lib/repository-reference.ts`
（`test/scripts/section-reference.test.ts` の純粋関数テストと `test/section-reference.test.ts` の
リポジトリ全体0件テスト）、(2) `scripts/task-id.ts` + `scripts/task-mention.ts` +
`scripts/lib/task-id-repository.ts` + `scripts/lib/task-mention-repository.ts`（`test/scripts/task-id.test.ts`・
`test/scripts/task-mention.test.ts` の純粋関数テストと `test/task-id.test.ts` のリポジトリ全体テスト）、
(3) `scripts/deny-broad-kill.ts`（hook を実プロセスで起こす契約テスト）、(4) `scripts/room-grid.ts`
（純粋関数テスト。lsof/orca/git は起こさない）、(5) `src/cli.ts` の起動前提チェック（`test/cli.test.ts`）、
(6) `src/` 全体の層・機能・箱の依存の辺（`test/architecture.test.ts`。1つの `describe`/`it` が広い範囲の
静的解析を1回で行う形で、19個の独立した契約を守る）。

各レーンを読み取り専用でたどり、本番側の持ち主・呼び手・エクスポートの使われ方まで確認した。結果:

- テスト専用の export・グローバル・ラッパーは無い（`section-reference.ts`・`task-id.ts`・
  `task-mention.ts`・`room-grid.ts` の全 export は、対応する `scripts/*.ts` の実エントリポイント
  （`find-stray-reference.ts`・`open-room-grid.ts` など）からも読まれている）
- ソース・grep・フィクスチャの丸写しは無い。`test/scripts/section-reference.test.ts` と
  `test/section-reference.test.ts`（`task-id.test.ts` も同様の対）は、片方が純粋関数の境界ケース
  （行またぎ・入れ子の「」・3行制限など）、もう片方がリポジトリ全体を実データで走査する境界の
  テストで、担っている契約が違う（前者が無くても後者はドキュメントの実際の食い違いしか拾えず、
  後者が無くても前者は「いまのリポジトリで実際に0件か」を保証しない）
- `test/architecture.test.ts` の19個の `it` はそれぞれ CLAUDE.md / docs/design.md /
  docs/coding-standards.md の別々の規約（層の向き・機能どうしの辺・SDK/orca/child_process/
  process.env の境界・経路名リテラル・コメント中の日付・browser の箱と機能・`components/ui/`
  の置き方と className の作法）を、実ソースへの正規表現走査で独立に守っており、"層の判定は…throw
  する" と "循環の検出は…輪を見つける" の2件は検査の道具自体（`layerOf`・`findFeatureCycle`）が
  黙って空振りしないことを守るメタテストで、これも別の契約
- `test/cli.test.ts` の4件は `spawnSync` で本物の CLI を起動時の前提チェックまで走らせる境界テストで、
  重複や空振りの否定対照は無い
- `test/scripts/deny-broad-kill.test.ts` は hook を実プロセスで起こし終了コードで確かめており、
  ゴミの型のどれにも当たらない
- `test/scripts/room-grid.test.ts` の32件は `scanPorts`/`pickRooms`/`buildRoomGridHtml`/
  `previousGridTabs`/`routeRoomGridRequest`/`observeGridTab` という別々の純粋関数を1つずつ守っており、
  重複や名前と検査内容のズレは無い

台帳（92件）はすべて `R`（守っている契約と、上の確認内容がそのまま証拠）で、`C`/`D`/`F` に当たる
確信の持てる候補は見つからなかった。よって完了条件の最後の項目（「確信の持てる候補が無ければ、台帳の
件数だけ書いて編集なしで `done` にしてよい」）に従い、編集はしない。

## 注意

- 変異を入れて確かめるときは、退避したコピーから戻す（`git checkout --` で戻すと、同じファイルへの先行の編集ごと消える）
- `CAMPAIGN.md` の段3・段6は、別のエージェントに読ませることを求めている。サブエージェントの中で別のエージェントを立てられないなら、レーンごとに順に自分で読み、段6の保全のレビューは受け入れのときにメインが行う
- ブラウザに出る絵は自動テストで守らない方針（`docs/architecture.md`）なので、描画のテストを消すときも、足すときも、その方針の範囲で判断する
