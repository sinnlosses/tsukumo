## 目的

検証（テスト・E2E）にかかった時間を、モデルに測らせるのではなく tsukumo が機械で測って見せる。入ったら、モデルに測らせている条を外す（2026-09-27 T-725 のドラフト、ユーザー承認）。

## 完了条件

- `SessionRecord` の `kind: "tool"` と `TurnStep`（`src/shared/turn-step.ts`）が、ツールの開始と終了の時刻を持っている（時刻は `foldSessionEvent` が受け取る `at` から取る）
- 所要時間がどこかに出ている。候補は帯の「依頼の手順」の一歩か `report` の `checks` の帯で、どちらにしたかと理由を結果に書く
- 出した場所に合わせて、`REPORT_NOTATION_PROMPT` の条1 と `REPORT_CHECKS_DESCRIPTION` から「モデルが所要時間を測って `detail` に添える」の部分を外すか縮めている
- 表示を変えたら、何が見えたかを結果に書く
- `pnpm run check` が通る

## 背景

- `tool-started` / `tool-finished`（`src/shared/session-event.ts`）は時刻を持たない。`foldSessionEvent(state, event, at)`（`src/shared/session-state.ts`）は `at` を受け取っていて、`tool-finished` の失敗の時刻（立ち絵の「びくっ」に使う）は既にこの `at` から取っている
- `SessionRecord` の `kind: "tool"` の欄は `toolUseId`・`name`・`input`・`nested`・`status` で、時刻の欄は無い。`TurnStep` はこの記録から `currentTurnSteps` で作る
- T-725 で入れた条は、`report-notation.ts` の「`checks` の `detail` には、測った所要時間が分かれば添える（`time` で包む・コマンドの出力に出た時間を読む）」。`docs/coding-standards.md` では、ヒューリスティックより機械的な仕組みを優先することになっている

## やること

前提を実物で確かめ直した（`## 背景` のパスは実際には `src/shared/session/session-event.ts` /
`src/shared/session/session-state.ts` / `src/shared/session/turn-step.ts`、`REPORT_NOTATION_PROMPT` は
`src/server/report/core/report-notation.ts` にある。中身は `## 背景` の記述どおりで、作業は要る）。

- `src/shared/session/session-state.ts`: `SessionRecord` の `kind: "tool"` に `startedAt: RecordTime`
  を足し、`ToolRunStatus` の `finished` に `finishedAt: RecordTime` を足す。`foldSessionEvent` の
  `tool-started` で `startedAt: { kind: "stamped", at }`、`finishTool`（`tool-finished`）で
  `finishedAt: { kind: "stamped", at }` を積む。`history-restored` の `withRestoredTime` を
  `"tool"` にも広げ、両方の時刻を `{ kind: "restored" }` に畳み直す
- `src/shared/session/turn-step.ts`: `TurnStep` に `startedAt: RecordTime`、`TurnStepStatus` の
  `done` / `failed` に `finishedAt: RecordTime` を足す。新しく `toolDuration(step)` を export し、
  開始・終了の両方が `stamped` なら `{ kind: "known", milliseconds }`、どちらかが `restored` /
  実行中なら `{ kind: "unknown" }` を返す（判別可能な合併型。`docs/coding-standards.md`「無いかも
  しれない値」）
- 所要時間の出し場所は**帯の「依頼の手順」の一歩**に決める（理由は後述）。
  `src/browser/components/domain/screen-nav/hooks/use-current-work.ts` の `stepLabel` で
  `toolDuration` が `known` のときだけ `formatElapsed`（`src/browser/domain/elapsed-time.ts`。
  ターンの経過時間表示と同じ既存の秒フォーマッタ）で付記する
- `src/server/report/core/report-notation.ts` の条1 と `src/server/report/core/report-tool.ts` の
  `REPORT_CHECKS_DESCRIPTION` から、モデルが所要時間を測って `detail` に添える指示を削る
- 型が変わる箇所に合わせてテストを更新する: `test/fixture/session-record.ts`（`toolRecord` の
  既定に `startedAt` を足す）、`test/shared/session/turn-step.test.ts`、
  `test/shared/session/session-state.test.ts`、`test/shared/session/main-view.test.ts`、
  `test/shared/chat/chat-log.test.ts`、
  `test/browser/components/page/conversation/components/main-view/main-view.test.tsx`、
  `test/browser/components/domain/screen-nav/current-work.test.tsx`（所要時間の表示を確かめる
  ケースを足す）、`test/server/report/core/report-notation.test.ts` /
  `test/server/report/core/report-tool.test.ts`（削った指示を検査していたケースを消す）

出し場所を「依頼の手順」にする理由: 所要時間は `tool-started` / `tool-finished` という機械の
イベントの `at` から直接測れ、ツール呼び出し1回と1:1で対応する。`report` の `checks` はモデルが
書く欄で、どの検証がどのツール呼び出しに対応するかを機械的に対応付ける手段が無く、対応付けは
ヒューリスティックになる。`docs/coding-standards.md`「仕組みをヒューリスティックより優先する」に
沿い、機械的に対応が取れる「依頼の手順」を選ぶ。

復元時の時刻の扱い: `startedAt` / `finishedAt` を生の `number` ではなく既存の `RecordTime`
（`stamped` / `restored`）で持たせる。`history-restored` は replay した時刻（`options.now()`）を
`stamped` のまま積んだ直後の記録に対して発行されるので、復元直後の `tool` 記録もいったん
`stamped` になるが、`withRestoredTime` で他の記録（`request` / `speech`）と同じく `restored` に
書き換える。`toolDuration` は両方 `stamped` のときだけ `known` を返すので、復元した手順は
「所要時間なし」（表示しない）になり、replay の速さを本物の所要時間として見せない。

## 注意

- 記録は transcript から読み戻して作り直すことがある（復元）。読み戻したときの時刻をどう扱うか（`RecordTime` の `stamped` とそうでないもの）を決めて書く

## 結果

- 所要時間は帯の「依頼の手順」の一歩に「（N秒）」で出す。`checks` はモデルが書く行とツール呼び出しを機械的に対応付けられないため採らなかった。復元した手順は時刻が `restored` になり所要時間を出さない
- 見えたもの: capture-catalog の `current-work-failed` で「失敗 Bash: dummy-command --check /tmp/dummy/nowhere（0秒）」、実行中の手順には付かない
- 検証コマンド: 単体 2752 pass / E2E 31 pass（受け入れで `docs/display.md`・`docs/screen-design.md` の条を機械測定に合わせて直した）
- 振り返り: 受け入れのときにメインが直したもの・報告に残した気になる点（ドラフト 1件）
