## 目的

`docs/research/server-procedure-proposal.md` の段2。oRPC が Bun・`ws`・zod 4 の組み合わせで動くことを、戻しやすい読み取りの経路だけで確かめ、読み取りの定型（照合・JSON・手書きの `fetch`）を1つの仕組みにする。

## 完了条件

- `@orpc/server` `@orpc/contract` `@orpc/client` `@orpc/tanstack-query` が入り、`docs/research/external-dependency.md` の表1に載っている
- 読み取り5本（`/repository-file` `/token-usage` `/context-usage` `/achievement` `/achievement-calendar`）が `docs/design.md` 2章「コマンドの受け手と手続きの置き方」の形になっている: 契約は `src/shared/contract/<機能>.ts`（`repository` `token-usage` `context-usage` `achievement` の4つ）、手続きは `src/server/<機能>/adapter/<機能>-procedure.ts`（口は `<機能>Procedure(ports)` で受け、`context-usage` の読み取りのように `session-manager` が持つ口も配線が渡す。機能どうしの辺を足さない）、束ねるのは配線の `src/router.ts`
- トークン・`Origin` の照合が `src/server/view-server/adapter/rpc-guard.ts` の1つのミドルウェアで掛かり、`server.ts` には静的な配信と `/prompt-image/<id>` だけが残る
- `src/shared/` から5本の経路名の定数が消え、ブラウザ側の6ファイル（`use-repository-file-paths.ts` `use-token-usage.ts` `use-achievement.ts` `use-achievement-calendar.ts` `use-diary-book.ts` `browser/domain/context-usage.ts`）が型付きの client で読んでいる
- `test/architecture.test.ts` が、`@orpc/server` を機能の `adapter/`（と配線）の外で import したら落とし、`shared` には `zod` と `@orpc/contract` だけを許す（`shared/contract/` のサブディレクトリを置き場として認める）
- `bun run check` が通り、Bun の上で6箇所（`@` 補完・トークン消費・コンテキスト・成果・暦・日記）を目視で開けた（`docs/architecture.md`「手で確かめること」）
- oRPC が Bun・`ws`・zod 4 のどれかと合わず回避策が無いと分かったら、変更を戻し、分かったことを書いて `dropped` で閉じてよい（そのときは T-654 と T-655 も見直す）

## 背景

- 読み取り5本は `src/server/view-server/adapter/server.ts` の `writeRepositoryFileList` などが、照合 → 403 → `writeJson` を手で書いている。画像（`/prompt-image/`）は `<img src>` で読むので HTTP に残す
- ブラウザは既に `@tanstack/react-query` を使っている
- oRPC 1.15.4 の事実（依存・Standard Schema・WebSocket アダプタ）は提案書 3章

## やること

いまのコードで調べ直した前提（2026-09-26）:

- 読み取り5本は `src/server/view-server/adapter/server.ts` の経路の表 `ROUTES`（段1で表にした）の
  `requiresToken: true` の行で、照合は `respond` の `hasStartupToken`（`?t=`）だけ。**HTTP 側には
  `Origin` の照合がまだ無い**（`/ws` の `session-socket.ts` の `isAllowedUpgrade` だけが見ている）
- 読み手の口は `ViewServerOptions` の `listRepositoryFiles` `readTokenUsageSummary`
  `readContextUsage` `readAchievement` `readAchievementCalendar` で、中身は配線の
  `src/view-delivery.ts` が組む（`readContextUsage` は `connect` で `session.readContextUsage` に
  差し替わる）
- `shared` の経路名の定数は `REPOSITORY_FILE_PATH` `TOKEN_USAGE_SUMMARY_PATH` `CONTEXT_USAGE_PATH`
  `ACHIEVEMENT_PATH` `ACHIEVEMENT_CALENDAR_PATH` の5つ。クエリ名 `TOKEN_USAGE_DAYS_QUERY_NAME`
  `ACHIEVEMENT_DATE_QUERY_NAME` と、届いた JSON の読み取り（`readRepositoryFileList` など5つと
  `readTokenUsageDays`）も、手続きの入出力の検証に置き換わるので一緒に消す
  （`ACHIEVEMENT_DATE_QUERY_NAME` は `browser/stores/location-hash.ts` が hash の名前に借りている）
- ブラウザの読み手は6ファイルのほかに `use-usage-review.ts` が `use-token-usage.ts` の
  `fetchTokenUsageSummary` を借りている
- `shared` はすでに `remeda` も読んでいる（`zod` だけではない）
- oRPC 1.15.4 は Bun 1.4.2 の `node:http` の上で `@orpc/server/node` の `RPCHandler` が動き、zod 4 の
  スキーマをそのまま契約に書ける（試して確かめた）。**型の宣言ファイルが2つ壊れている**
  （`@orpc/interop` の compression が CI の絶対パスを指し、`@orpc/shared` が任意の peer の
  `@opentelemetry/api` を読む）ので、`tsconfig.json` に `skipLibCheck` が要る

手順:

1. 依存を足す（`@orpc/server` `@orpc/contract` `@orpc/client` `@orpc/tanstack-query`）。
   `docs/research/external-dependency.md` の表1に載せ、`tsconfig.json` に `skipLibCheck`
2. 契約 `src/shared/contract/{repository,token-usage,context-usage,achievement}.ts` と、束ねた契約・
   `/rpc` の経路名を `src/shared/rpc.ts` に置く。`shared` から5本の経路名の定数と JSON の読み取りを消す
3. 手続き `src/server/<機能>/adapter/<機能>-procedure.ts` を4つ、照合のミドルウェア
   `src/server/view-server/adapter/rpc-guard.ts`（起動トークンと `Origin`）、束ねる `src/router.ts`
4. `server.ts` から読み取り5本を外し、`/rpc` に `RPCHandler` を載せる。`view-delivery.ts` はルータを渡す
5. ブラウザ側を `src/browser/lib/rpc-client.ts` の型付き client（`@orpc/tanstack-query`）で読む
6. `test/architecture.test.ts` に外部パッケージの検査を足し、テストを書き換える。正典
   （`docs/design.md`）の現状の記述を追随させる
7. `bun run check`、疑似セッションで6箇所の画面と `/rpc` の応答を確かめる
