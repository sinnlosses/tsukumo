## 目的

`test/e2e/turn-history.test.ts` の「複数のやり取りが札として積み上がり、長い依頼の1行目は省略される」が、差分と関係なく `bun run check` の中でときどき落ちる。揺れを止め、受け入れの検証を打ち直さずに済むようにする。

## 完了条件

- 落ちる原因を特定し、タスクファイルに書く（待ちの条件・順序の前提など、どこが揺れるのか）
- 原因を直し、`bun run test:e2e` を続けて10回流して落ちないことを確かめる（回数と結果を報告に書く）
- `bun run check` が通る
- 手元で何度流しても再現せず原因も見当たらないときは、試した回数と調べたことを書いて `dropped` で閉じてよい

## 背景

- 2026-09-27、ドキュメントだけの差分の受け入れで `bun run check` を3回流したところ、2回目にこの E2E が1件落ちた（23 pass / 1 fail）。3回目は通った
- テストは `test/e2e/turn-history.test.ts` の18行目。`room.waitForEvent("turn-finished", LAST_TURN_FINISHED_OCCURRENCE)` でターンの終わりを待ってから札を数えている
- E2E の走らせ方は `docs/design.md`「E2E の走らせ方」

## やること

前提を実測し直した（`test/e2e/scenario-run.ts` の `openRoom` から直に呼ぶ確認スクリプトと、`playwright-core` の `Clock` を素で触るプローブの両方）。

- **落ちる原因**: `installFixedClock`（`test/e2e/scenario-run.ts`）は `page.clock.install({ time: FIXED_INSTANT })` だけを呼び、`settleAndMatch` が `pauseAt` を呼ぶまでブラウザの時計は**実時間で進む**（Playwright の `Clock.install` の仕様どおり。プローブで確認: install 後 500ms 実待ちすると `Date.now()` も 534ms 進んでいた）。一方サーバ側は `TSUKUMO_FIXED_CLOCK` で完全に止まった時計（`src/server/adapter/local-time.ts` の `createServerClock`）を使うので、`turn-finished` の `finishedAt` は4つのターンすべて厳密に同じ値（`FIXED_INSTANT` そのもの）になる
  - 立ち絵の「完了の反応」（`data-motion="success"`。`src/shared/portrait-motion.ts` の `resolvePortraitMotion`）は、ターンが終わってから `SUCCESS_MOTION_WINDOW_MS`(700ms) だけ出る。過ぎた瞬間には何のイベントも来ないので、`src/browser/components/page/conversation/components/character-view/hooks/use-character-view.ts` の `usePortraitMotion` がターンが終わるたびに補正の `setTimeout` を立て直し、`now` という state を1回だけ書き換えて読み直させる
  - この補正タイマーの遅延は「スケジュールした瞬間の実時間」から `finishedAt + 700 - now` で計算する。ブラウザの時計は実時間で進んでいるので、4回目の `turn-finished` を処理する頃には（ブラウザの起動・場面の再生ぶんの）実経過時間がすでに 700ms を超えていることがある。超えていると delay が0以下になり `if (delay === undefined) return`（`delay` は正の値だけ残す `filter` で弾かれる）で**補正タイマーが一切立たない**。すると `now` state はマウント時に読んだ小さい値のまま二度と更新されず、`resolvePortraitMotion` は`now - finishedAt`が窓の中に収まったまま `"success"` を返し続ける（永遠に `"reading"` へ戻らない）
  - 実行するたびのブラウザ起動・場面再生の実時間が 700ms の前後をまたぐかどうかで結果が変わるので、`bun run check` の中でだけ・実行のたびに揺れる
  - プローブで再現・確認: `page.clock.install({time})` のみだと 500ms 実待ちで `Date.now()` が実時間ぶん進み、`install` 直後に同じ時刻へ `pauseAt` を呼ぶと以降 `Date.now()` は実時間が経っても動かず、`setTimeout` も `pauseAt(先の時刻)` で明示的に進めるまで発火しないことを確認した
- **直したこと**:
  1. `installFixedClock`（`test/e2e/scenario-run.ts`）で `page.clock.install({ time })` の直後に同じ時刻へ `page.clock.pauseAt(time)` を呼び、ブラウザの時計を最初から（`page.goto` の前から）完全に止める。サーバ側の完全に止まった時計と揃え、場面の実再生にかかる実時間の長さに結果が左右されないようにした（待ち時間を延ばす直し方ではなく、「ブラウザの時計が実時間で進む」という揺れの前提そのものを消す直し方）
  2. `use-character-view.ts` の `usePortraitMotion` も直した。もとの実装は `now` state を補正タイマーの発火時にしか進めず、`turn` / `lastToolFailureAt` が変わった直後の再スケジュール時には読み直さない。実ブラウザでもタブが裏に回っていた・端末が混んでいたなどで効果（`useEffect`）が走るまでの実時間が窓を超えると、同じ「`delay` が負で補正タイマーが立たず `now` も進まないまま固まる」不具合が起こりうるので、`scheduleNext` の中で毎回まず `now` を最新値へ進めてから `delay` を計算するように直した。E2E の時計凍結だけでも揺れ自体は止まるが、実ブラウザ側の潜在的な不具合でもあるためこちらも残した
- **`turn-history` だけの不具合ではなかった**: 時計凍結を先に単独で試したところ、他の8本の E2E（`background-task-*` / `final-report-label-*` / `input-dispatch` / `long-report` / `report-rejected` / `report-tidied` / `speak-bubble-closing-narration` / `turn-flow` / `turn-resumed` の11シナリオ）も同じ「`success`/`failure` のまま `reading` に戻らず固まる」不具合を安定して踏んでおり、それがそのまま `test/e2e/expected/*.dom.json` に「正解」として記録されていた（揺れていないので今まで気づかれなかった）。`E2E_UPDATE=1 pnpm run test:e2e` で以下11ファイルを撮り直した（差分はすべて `data-motion` の1行だけ、`success`/`failure` → `reading`。`git diff` で確認済み）:
  - `test/e2e/expected/background-task-resumed.dom.json`
  - `test/e2e/expected/background-task-running.dom.json`
  - `test/e2e/expected/final-report-label-closed.dom.json`
  - `test/e2e/expected/final-report-label-waiting.dom.json`
  - `test/e2e/expected/input-dispatch.dom.json`
  - `test/e2e/expected/long-report.dom.json`
  - `test/e2e/expected/report-rejected.dom.json`
  - `test/e2e/expected/report-tidied.dom.json`
  - `test/e2e/expected/speak-bubble-closing-narration.dom.json`
  - `test/e2e/expected/turn-flow.dom.json`
  - `test/e2e/expected/turn-resumed.dom.json`
- **確認したこと**: `pnpm run test:e2e`（全15ファイル）を通しで10回、`test/e2e/turn-history.test.ts` 単体で10回、いずれも落ちないことを確認（時計を最初から止めても、他のシナリオの debounce・演出の待ちが進まなくなって壊れていないことも兼ねて確認できた）。`pnpm run check` も通過（typecheck・lint・format:check・test 213 files / 2729 tests・test:e2e 15 files / 24 tests）
- **無関係な揺れとして見えたが本タスクの対象にしていないもの**: `pnpm run check` を続けて流す中で以下の2つを見た。どちらも本直しと無関係（原因の層が違う）で、単独では再現しないか、直した後のコードと同じ確率で未変更のコードでも起こることを確認した
  - `test/cli.test.ts` の2件（別々の実行で「ブラウザ側の成果物を読めない」というエラーになり、期待した文言と食い違う）。**未変更のコードでも同じ内容で再現した**ので本直しとは無関係。おそらく `dist/browser` を読み書きするテスト同士が並列 worker で競合している
  - `test/e2e/background-task.test.ts` の1件（コンテキスト使用量が「取得中…」のまま止まり `61%` に上がらない）。本直しの後の1回だけ、`pnpm run check` の中（ユニットテストの直後で負荷が高いとき）に発生し、単独では3回とも通った。立ち絵の動きとは別の非同期取得（`useContextUsage`）の待ちなので、CLAUDE.md の指示どおり「別の E2E の揺れ」「E2E を速くするタスク」の対象として書き添えておく

## 注意

- 別の E2E の揺れ（「⌘Enter で送ると prompt が流れ…」）を直すタスクと、E2E を速くするタスクがある。原因が共通だと分かったら、そのタスクの `## 注意` に書き添える
- 待ち時間を延ばすだけの直し方はしない（何を待つかを直す）

## 結果

- 検証コマンド: 単体 2729 pass / E2E 24 pass（委譲先が E2E 全件を10回連続で通過。受け入れの1回目は T-739 と無関係な cli・main-history の揺れで2件落ち、2回目で全件通過）
