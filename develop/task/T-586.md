## 目的

`src/server/` の平置き（`core/` 39ファイル・`adapter/` 33ファイル）を、サーバサイドの定石に沿って**機能のまとまりと依存の向きがディレクトリから読める形**に整理するための設計を先に決める。後ろの移動タスクは、ここで書いた対応表と依存の規則に従って機械的に移すだけにする。

## 完了条件

- `src/server/` の新しい形が `docs/design.md` 2章（「全体構成」の図・「層と依存の向き」・「ディレクトリ」・「`lib/` と `utils/` に置く基準」の層ごとの読み方）に書かれている。少なくとも次が決まっている:
  - 機能のまとまりの切り方（どの機能を1つの箱にするか。セッション・駆動・訪問・日記・成果・使用量の見直し・雑談・キャラクター・レポート・配信 など、いまのファイルを実際に読んで決める）
  - `core`（判断）と `adapter`（境界）の割りを、機能の**外側**に置くか（`server/core/<機能>/`）**内側**に置くか（`server/<機能>/{core,adapter}`）、あるいは別の形か
  - 機能どうしの import の規則（どの機能がどの機能を読んでよいか。循環を許さない、など）と、どの機能にも属さない共有のもの（`host.ts` `session-driver.ts` の契約、`config.ts` など）の置き場
- **いまの `src/server/` の全ファイル（`core/` 39・`adapter/` 33・`adapter/lib/`）について、移す先（または動かさない）が1行ずつ引ける対応表**が `docs/design.md` にある。テスト（`test/` 側で src と同じ相対パスにあるもの）の移動先も同じ表から決まる
- いまの import の辺（server 内のファイル間の依存）を数えた結果が、設計の根拠として `docs/research/` か `docs/history/decision.md` に残っている（どの機能の塊が密で、どこが横断しているか）
- `test/architecture.test.ts` に足す・変える検査（機能どうしの辺、`core → adapter` 禁止の書き直し、`sdk-` / `orca-host.ts` / `node:child_process` / `process.env` の許可リストの移り先）が表で書かれている
- `CLAUDE.md` 原則2・原則3 と `docs/architecture.md` のサーバ側の記述が新しい形に揃っている（原則5 の単数形の規則と矛盾しないこと）
- 採った・採らなかった案と理由は `docs/history/decision.md` に書き、`docs/design.md` には結論だけを置く
- **移動のタスクを `task new` で登録してある**（このタスクを `--deps` に取る。1タスク1コミットで説明の付く大きさに割り、各本文の `## 完了条件` は書いた対応表の行を指す）
- このタスクではコードを動かさない（`test/architecture.test.ts` も直さない。直すのは移動のタスク）
- `bun run check` が通る（`test/section-reference.test.ts` が見る節の参照が切れていない）
- 調べた結果、いまの平置きのほうが読みやすいと判断したなら、理由を `docs/history/decision.md` に書いて `dropped` で閉じてよい

## 解くべき論点

- 機能の外に `core/adapter` を置く形（層が先）と、機能の中に置く形（機能が先。vertical slice / modular monolith）のどちらが、このリポジトリの読み手にとって「開くファイルの数」「自分の外の事情を知らずに済むか」「前提が変わったときに黙って効かなくならないか」の3つで勝つか（`CLAUDE.md`「案が2つ以上あるときは」）
- Agent SDK の `sdk-*`（1つの境界が数ファイル）を1つの箱にまとめるか、機能ごとに割るか
- `session-manager.ts` のように多くの機能を束ねるファイルをどこに置くか（配線の `src/` 直下との境目）
- `browser` 側の設計（T-581）が決める箱の語彙と揃えるか（揃えるなら何を揃えるか）
