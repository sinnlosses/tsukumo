## 解くべき論点

- 「タスクの性質」を誰が決めるか（モデルが種類を選ぶ／tsukumo が依頼や道具の使われ方から推す／決めない）と、選び違えたときの壊れ方
- テンプレートの単位を「レポート全体」にするか、いまの塊より大きい「部品の組」（例: 調査の結論＋根拠の表＋未確認）にするか
- 自由形式の出力からテンプレート（や塊）へ昇格させる判断を、記録の集計で機械的に行えるか
- JSON Schema の大きさ（毎ターン載る道具の定義の字数）とモデルの書き違いの増え方

## やること

前提は実物で確かめた（背景のパス・関数はすべて実在。`reportSectionsMarkdown` は `src/shared/report/report-block.ts`。塊は9種、`sections` の JSON Schema は4369字、使われ方の記録は `~/.tsukumo/report-usage/2026-09-27.jsonl` の112件〔1日・7時間ぶん〕だけ）。

- 記録を集計した割合（塊の種類の組み合わせの散らばり・逃げ道に入った記法）と、塊ごとの JSON Schema の字数を根拠に、叩き台の効かないところを挙げる
- 叩き台（レポート全体のテンプレート）・部品の組・いまの塊の延長（T-745〜T-748 のまま）・推す案の4つを比べる
- 推す案の形（schema・組み立て・描き方・昇格の流れ）と移行の段を `docs/research/report-architecture.md` に書く。`docs/display.md` の2つの小節との食い違いと、どちらを変えるかも書く
- T-745〜T-748 の本文を結論に合わせて直し、`difficulty` を見直す
- 推す案で新しく要る実装を `develop/draft/` にドラフトとして積む（記録の語彙の不足・`REPORT_BLOCK_KINDS` の抜けを含む）
