## 目的

同じ手順を3回手書きしている集計を remeda で書き直し、何をどう畳んでいるかを1語ずつで読めるようにする。

## 完了条件

- `src/server/token-usage/core/token-usage.ts` の `foldToolCalls`・`summarizeByModel`・`summarizeByTool` が `groupBy` + `sumBy` + `sortBy` で書かれ、`[...new Set(...)]` → 名前ごとの `filter` → `reduce` の形が残っていない
- 専用の比較関数 `compareName`・`compareModelName` が消えている
- 並びは変えない: `foldToolCalls`・`summarizeByTool` は `resultBytes` の降順、同じなら名前の昇順。`summarizeByModel` は `outputTokens` の降順、同じならモデル名の昇順
- 既存のテスト（`test/` の token-usage まわり）が書き換えずに通る
- `bun run check` が通る

## 背景

- 3関数の現状（2026-09-25 時点）は `foldToolCalls`（395行付近）・`summarizeByModel`（475行付近）・`summarizeByTool`（501行付近）。どれも名前の集合を作ってから名前ごとに全件を `filter` しているので、名前の数×件数だけ走査している
- 名前の比較は `left.name < right.name ? -1 : ... ? 1 : 0` の2関数（408行・487行付近）。remeda の `sortBy` も `<`/`>` で比べるので、`localeCompare` に変わることは無い
- `sumTotals`（複数の項目をまとめて足す）は remeda に対応する関数が無いので、そのまま使う

## やること

- 前提を確かめ直した（2026-09-25 時点でも `foldToolCalls`（394行付近）・`summarizeByModel`
  （470行付近）・`summarizeByTool`（485行付近）が `[...new Set(...)]` → 名前ごとの `filter` →
  `reduce` の形のままで、`compareName`・`compareModelName` も残っていた。前提は崩れていない
- `groupBy(calls, prop("name"))`（`groupBy(allUsages, prop("model"))`）で名前・モデルごとに
  `Record` へ分け、`Object.entries` で並べ直してから `sumBy` で `resultBytes` / `calls` /
  `outputTokens` などを畳み、`sortBy` に `[プロジェクション, "desc"]` と2つ目のキーの
  プロジェクションを渡して「主キー降順・同点は名前昇順」の並びに書き直す
- `compareName`・`compareModelName` を削る
- 既存テスト（`test/server/token-usage/core/token-usage.test.ts` の「結果の長さの大きい順に
  並べる（同じなら名前順）」「出力が同じ数なら、モデル名の昇順で並べる」
  「メインとサブエージェントの内訳を足し合わせる（長さの降順、同じなら名前順）」）が既に
  同点の並びを見ているので、新規テストは足さない

## 注意

- `groupBy` は `Record` を返す。`Object.entries` で並べ直すときに、キーの型が `string` に広がっても問題ないことを確かめる

## 結果

- `token-usage.ts` の `foldToolCalls`・`summarizeByModel`・`summarizeByTool` を `groupBy` + `sumBy` + `sortBy`（主キーの降順、同点は名前の昇順を2つ目の規則で明示）で書き直し、`compareName`・`compareModelName` を消した。同点の並びは既存テストが見ていて、書き換えずに通った
- 検証コマンド: 2674 pass / 0 fail
- 振り返り: 兆候なし
