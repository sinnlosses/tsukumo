## 目的

会話画面の複雑な機能を、T-657 の土台に乗った E2E で確かめる。後段の監査で、ここが守る振る舞いの単体テストを消せるようにする。

## 完了条件

- `docs/design.md` 10章「E2E のシナリオの一覧」で担当が「会話」の行ごとに E2E が1本ずつある: 入力欄から送る、speak → キャラビューの吹き出し、report → メインビュー（記法・差し戻し・整え）、途中の発話と流れる本文、許可のモーダル、質問（単数・複数・プレビュー）、続きのターン
- 見たい状態が `class` にしか出ていなければ `data-*` か `aria-*` に出している（`docs/coding-standards.md`「DOM の構造と画面の流れは E2E、見た目は目視」）
- 各 E2E が、どの振る舞いを守っているかをテストの名前で言っている（後段の監査が「どのシナリオが守るか」を書くときに引く）
- 台本に場面が足りなければ `test/fixture/fake-session.json` に足している（手書きの架空の会話だけ）
- `bun run check` が通る

## 背景

- 使える場面: `fake-session.json` の `report`・`long-report`・`permission`・`question-multi`・`question-pair`・`question-long`・`question-preview`・`notation`・`narration` など
- シナリオと場面の対応は `docs/design.md` 10章「E2E のシナリオの一覧」に従う（食い違ったらそちらを直す）
- `docs/architecture.md`「手で確かめること」に、質問の場面を Playwright で自動操作すると `turnInProgress` が解けないまま残ることがある、という既知の症状がある。踏んだら条件を書き足し、E2E の側の待ち方（押す前に何のイベントを待つか）を先に疑う

## やること

**前提を調べ直した結果、`fake-session.json` に場面を足す作業は不要だった。** T-634 が先に
`turns` を埋めていて、「会話」担当の7行が要る場面（`opening`・`closing-narration`・
`notation`・`narration`・`long-report`・`permission`・`question-pair`・`question-multi`・
`question-long`・`question-preview`・`report-rejected`・`report-tidied`・`resumed-report`、
入力欄から送る用の `report`）は全部そろっていた。足したのはシナリオのテストファイルだけ。

- `test/e2e/scenario-run.ts` の `ScenarioRoom.waitForEvent` に `occurrence`（既定1）を足した。
  同じ `kind` が場面の中で複数回流れるもの（`resumed-report` の `turn-finished` が4回、
  `permission` で押したあとにもう一度届く `pending-changed`）を、狙った回目まで待つ口が要る
  ため（既存の呼び先とは後方互換）
- 「会話」担当の7行に1つずつ、`test/e2e/<シナリオ>.test.ts` を足した（scene は
  `fake-session.json` の場面名、テスト名は守る振る舞いを言う）:
  - `input-dispatch.test.ts`: 入力欄から送る（`scene: "none"`、textarea に書いて ⌘Enter →
    `prompt` が流れ `request` が戻り、`turns` の先頭 `report` が続く）
  - `speak-bubble.test.ts`: speak → 吹き出し（`closing-narration`・`question-multi`。
    `data-latest` を持つ `<Balloon>` が積み上がることを確かめる。既存の実装で足りたので
    `data-*` は追加していない）
  - `report-main-view.test.ts`: report → メインビュー（`notation`・`report-rejected`・
    `report-tidied`）
  - `narration-flow.test.ts`: 途中の発話と流れる本文（`narration`・`long-report`）
  - `permission-answer.test.ts`: 許可のモーダル（`permission`。「許可」を押して `answer` が
    流れ、`pending-changed` の2回目で箱が消えるところまで自動操作で確かめた——クリックしても
    `turnInProgress` は解けており、既知の症状は踏まなかった）
  - `question-ask.test.ts`: 質問（`question-pair`・`question-multi`・`question-long`・
    `question-preview`）。**選ぶ・答えるところまでは自動操作しない**——
    `docs/architecture.md`「手で確かめること」にある「質問の場面を Playwright で自動操作すると
    `turnInProgress` が解けないまま残ることがある」を避けるための判断（design.md の行の文言も
    許可のモーダルだけ「押すと」と書き、質問の行にはその言葉が無い）。答え待ちの札が出た時点の
    DOM だけを見る
  - `turn-resumed.test.ts`: 続きのターン（`resumed-report`。`turn-finished` の4回目まで待ち、
    合図をまたいでも中間レポートが残り最後に最終レポートへ差し替わることを見る）
- `class` にしか出ていない状態は見当たらなかった（吹き出しの `data-latest`、質問の
  `<input type="radio"/"checkbox">`、速記録の `data-current`/`data-age` など、既存の実装で
  DOM の構造とメッセージの列だけで判定できた）ので、`data-*` / `aria-*` は足していない
- 期待値は `bun run test:e2e:update` で作り、`git diff` で読んだ（一時ディレクトリ・ポート・
  トークンは置き換え済みで、本文は疑似セッションの手書きの会話と、テスト側で入力した架空の
  文面〔「入力欄から送る場面を見たい（架空の依頼）」〕だけ）。同じ入力で2回走らせ、成果物が
  一致することを確かめた
- E2E の段（`bun run build` を含む）は8ファイル15件で約56秒（60秒の目安に収まる）
