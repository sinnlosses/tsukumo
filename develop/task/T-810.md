## 目的

E2E が差分と無関係に、サイドバーの利用枠の行が「取得中…」のまま撮られて落ちる。`docs/design.md` 10章「E2E の揺れを生まない書き方」の「撮る前に、非同期の取得が済んだことを DOM の印で待つ」条が、利用枠の行にだけ効いていない。取り直しを E2E が待てるようにし、`pnpm run check` が負荷の下でも落ちないようにする（振り返り: T-795）。

## 完了条件

- 利用枠の取り直しのあいだ、E2E の `settledDom`（`test/e2e/scenario-run.ts`）が待てる印（`aria-busy="true"` など）が DOM に出て、取り直しが済むと消える
- `turn-finished` が続けて届いて取り直しが重なっても、印が外れずに残り続けない（`settledDom` が時間切れにならない）。印を付けない以外の形で解く（取り直しを畳む・最新の1回だけを印にする、など）。選んだ形と理由を `## 結果` に書く
- `settledDom` が「DOM が落ち着かない」で投げるとき、`settle-diff.txt` に、そのとき `aria-busy="true"` だった要素（`aria-label` や役割など、どれか分かる手がかり）も残る
- `background-task.test.ts` と `final-report-label.test.ts` を続けて10回ずつ回して、利用枠の食い違いで1度も落ちないことを `## 結果` に書く
- `plan-usage-row.tsx` の「`aria-busy` は付けない」の理由のコメントを、入れた形に合わせて直すか消す
- `pnpm run check` が通る
- 調べて前提が崩れていたら（別の直しで利用枠の揺れが消えている等）、回数と結果を添えて `dropped` で閉じてよい

## 背景

- 2026-09-27、T-795 の委譲先と受け入れの `pnpm run check` で、E2E が差分と無関係に3回落ちた（load average 22 前後）
  - `background-task-running` と `final-report-label-waiting`: 利用枠の行が「10:00 時点」ではなく「取得中…」、取り直しボタンが `aria-disabled="true"` のまま撮られた（期待値との食い違い。`/tmp/tsukumo-e2e/failures/` に控えが残った）
  - `report-tidied`: 「DOM が落ち着かない（15000ms）」で落ち、`settle-diff.txt` は「差分なし。最後の2回のあいだで落ち着いた」だった。何かの `aria-busy` が15秒残ったとみられるが、どの要素かは記録に無く確かめていない
- `src/browser/components/domain/sidebar/plan-usage-row.tsx` は冒頭のコメントで「`aria-busy` は付けない。ターンが終わるたびに取り直すので、`turn-finished` が続けて届くと取り直しが重なり、E2E の『DOM が落ち着くまで待つ』判定が時間切れになる」としている。取得中に前の値があれば行を薄く残して `FETCHING_TEXT = "取得中…"` を出す
- 取り直しは `src/browser/components/domain/sidebar/plan-usage.ts` の `usePlanUsage(refetchKey)`（TanStack Query の `useQuery`、`keepPreviousData`、`staleTime: 0`）。`refetchKey` は `planUsageRefetchKey(lastTurnFinishedAt)`。ボタンからは `retry()`（`query.refetch()`）
- コンテキスト使用量の行（`context-usage-row.tsx`）は `usage.kind === "pending"` のとき `aria-busy="true"` を出す先例
- `settledDom` は `aria-busy="true"` の要素が残るあいだ落ち着いたとみなさず、上限は `SETTLE_ATTEMPTS` × `SETTLE_INTERVAL_MS`。投げるときは最後の2回の DOM の差分を `<scenario>.settle-diff.txt` に書く

## やること

いま HEAD（`e650714e` 「E2E の撮影が利用枠の取り直しの途中を捉えて揺れるのを直す」）で、`## 背景` の前提のうち大半はすでに直っている。

- `plan-usage-row.tsx` は既に `aria-busy={fetching ? "true" : undefined}` を出しており、冒頭コメントも「付けない」ではなく「立てる」に直っている（完了条件1・5は済み）
- `test/e2e/scenario-run.ts` の `settledDom` は `aria-busy="true"` が残るあいだ時計を1ms ずつ進めて起こし、`settleAndMatch` は撮る時刻へ進める前にも1回落ち着くまで待つ（完了条件2に対応する形。印を付けたまま、時計側の眠りを解いて解決している）

残っていたのは完了条件3だけ: `settledDom` が「DOM が落ち着かない」で投げるとき、`settle-diff.txt` に投げた時点で `aria-busy="true"` だった要素の手がかりが残っていなかった（差分が空だと「差分なし。最後の2回のあいだで落ち着いた」だけで、どの要素かが分からない）。これを次で埋める。

- `test/e2e/scenario-run.ts` に `BUSY_ELEMENT_HINTS_SCRIPT`（`aria-busy="true"` の要素を `aria-label`・`role`・タグ名・`class` の手がかりで表す）を追加し、投げる直前に評価して `settle-diff.txt` へ差分と並べて書く（`settleDiffText` に切り出し）
- `background-task.test.ts` と `final-report-label.test.ts` を10回ずつ流し、利用枠の食い違いで落ちないことを確かめる
- `pnpm run check` を通す

## 注意

- 期待値を「取得中…」に書き換えて揺れを隠さない
- 待ちの上限を延ばすだけにしない（何を待つかを直す）
- 利用枠の見本（`QUOTA-Sidebar.dc.html`「3a 取得中（前の値あり）」）の見た目は変えない

## 結果

- 利用枠の `aria-busy` と、重なった取り直しで印が残り続けない形（印は付けたまま、`aria-busy` が残るあいだ凍らせた時計を1msずつ進めて起こす）は `e650714e` で入っていた。このタスクでは `settledDom` が投げるときに `aria-busy="true"` の要素の手がかり（`aria-label`・`role`・タグ名・class）を `settle-diff.txt` に残すのを足した
- `background-task.test.ts` と `final-report-label.test.ts` を続けて10回ずつ: 10/10 成功、利用枠の食い違いで落ちたのは0回
- 検証コマンド: 単体 2763 pass / 0 fail・E2E 31 pass / 0 fail（受け入れで単体を別に回したら1件落ち、打ち直すと通った。落ちたテストは控えていない）
- 振り返り: 運良く助かった（ドラフト 0件。単体の揺れは T-797・T-807 が扱っており、どれかを特定できなかった）
