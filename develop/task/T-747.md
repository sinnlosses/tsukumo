## 目的

候補の比較と触ったファイルの一覧を、判定のバッジ付きのカードと変更の種別付きの行で描けるようにする（`docs/research/report-block-richness.md` 3章・7章の3）。

## 完了条件

- 塊 `options`（`title` と、`name` / `verdict`（`adopt` / `consider` / `reject`）/ `reason` の並び）を足す。候補を1枚ずつのカードにし、頭に判定のバッジを文字（採る / 検討 / 採らない）で置く。並びは書き手の順のまま。「採る」カードの縁にキャラクターの色は入れない（`docs/screen-design.md` 13.2 の3本のまま）
- 塊 `files`（`path` / `change`（`added` / `modified` / `deleted` / `read`）/ `note` の並び）を足す。1行に1ファイルで、種別を頭の文字（追加 / 変更 / 削除 / 読んだ）で、パスは等幅で、押すとファイルを開く（既存の `repository-link`）
- 塊の形と説明・組み立て・CSS・記法の文面を合わせ、`docs/display.md` 4.2 と `docs/glossary.md` を合わせる
- 2つの塊を使ったレポートを目視で確かめ、何が見えたかを結果に書く
- `pnpm run check` が通る
- 前段の形で成り立たないと分かったら、理由を書いて `dropped` で閉じてよい

## 背景

- 実測（本文の有るレポートに対する割合）: 推奨の語 6.3%・パスだけの箇条書き 10.1%。1種類あたり JSON Schema は +500〜580字（`docs/research/report-block-richness.md` 1章・3章・5章）
- 欄の追加（T-746）と分けたのは、T-706 の使われ方の記録を前後で見比べるため
- T-804 の提案（`docs/research/report-architecture.md`）で、タスクの性質に固有の部品（比較の判定・実装の触ったファイル）はテンプレートでなく塊として足すとした。この2つがその例で、塊を足す条件は同じ文書の4.1

## 解くべき論点

- `options` の塊を表で書いたときとの取り違えを、塊の説明でどこまで防ぐか（提案は差し戻しの検査を足さない）
- 塊の種類が逃げ道を含めて11を超えないか（超えるなら外す候補を挙げる）

## 注意

- `options` を tsukumo が並べ替えない・採る候補を先頭へ動かさない（`docs/display.md` の「見せ方と再構成の線引き」）
