## 目的

コード修正・ファイル名の変更・ファイルの移動だけで、関係の薄いコメントを直して回る手間を最小にする。
そのためのコメントの書き方（何を指してよいか・どう指すか）を決め、`docs/coding-standards.md`「コメント」節に書き、できる範囲で機械の検査に載せる。

## 完了条件

- `docs/coding-standards.md`「コメント」節に、名前・置き場所が変わっても書き直さずに済む指し方の規則が書かれている（避ける例と書く例つき）
- 規則のうち機械で判定できるものは `test/architecture.test.ts` などの検査に載っていて、既存の違反は許可リストか段階的な扱いで `bun run check` を通している（載せない規則は、載せない理由を1行で残す）
- `CLAUDE.md`「コーディング規約・レビュー方針」の1行と `comment-audit` スキルの判定（`~/.claude/skills/comment-audit/`）が、新しい規則と食い違っていない。スキルを直す場合は共通スキルなので、このリポジトリ固有の事情を書き込まない
- 後段（このタスクの後ろに依存で繋がった書き換えのタスク）の本文を設計の結論に合わせて直す。書き換えの広がりを見て、後段の `difficulty` と分け方も見直す
- `bun run check` が通る

## 背景

- コメント中のファイルパスの記載が多い。`src` `test` `scripts` のコメント行で `*.ts` / `*.tsx` を含むものが約1600行、`src` の389ファイル中350ファイルにある（例: `src/cli.ts:63` の「解釈は src/server/core/config.ts」、`src/server/session-driver/core/session-title.ts:3`）。ファイル名の変更や移動（T-591・T-592・T-636〜T-639 のような移設）のたびに、これらのコメントが追随の対象になる
- コメント中の `docs/*.md` への参照も約1570行ある。節を「ファイル名＋番号＋「句」」で引く形は `scripts/section-reference.ts` と `test/section-reference.test.ts` が迷子を0件に保っているため、docs の節の改名・移動のたびにコードのコメントも直すことになる
- `{@link}` はすでに約580箇所で使われている。`{@link}` はシンボルを指すので、エディタの改名で追随し、ファイルの移動では変わらない
- 現行の「コメント」節（`docs/coding-standards.md` の `\n## コメント`）は、残す/消すを種類別に決める表と、経路上の複数の関数に書き写さない規則、Markdown の記法を使わない・意味の切れ目で改行する書き方を持つ。指し方（パス・節・シンボル・呼び出し元への言及）の規則は無い

## 解くべき論点

- コメントから別の場所を指すとき、何で指すか（`{@link シンボル}` / ファイルパス / docs の節の句 / 指さない）。ファイルパスを書いてよい場面は残るか（例: 外部コマンドや設定ファイルなど、シンボルで指せないもの）
- 「このファイルの外」についての記述（呼び出し元・使い手の一覧・「〜が呼ぶ」）をコメントに書くことを許すか。書かないならその情報はどこで得るか（エディタの参照検索・`docs/design.md`）
- docs の節への参照をコードに残す基準。節の句で引く形を続けるか、参照そのものを減らすか。`test/section-reference.test.ts` の対象から `src` を外すかどうかとの関係
- 機械の検査に載せる範囲と、既存の約1600行の違反の扱い（一括で直すか、触ったファイルから直すか）

## 注意

- 規則に数字の目安は置かない（「コメント」節の冒頭にある、数字が基準の代わりに使われる理由と同じ判断を踏襲するかを確かめる）
- 調べた結果、規約の変更で解けない（例: 追随の手間の大半が別の原因）と分かったら、根拠を残して `dropped` で閉じてよい
