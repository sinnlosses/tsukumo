## 目的

`src/server` のコメントを、`docs/coding-standards.md`「コメント」の「別の場所を指すとき」に揃え、以後のコード修正・改名・移設でコメントを直す箇所を減らす。

## 完了条件

- `test/comment-reference-backlog.ts` から、`src/server/` で始まるファイルがすべて消えている
- コメントの意味（今の挙動の制約・前提）を落としていない。指し方を変えるだけで消えてしまう情報は、規則に沿った形で残す
- `bun run check` が通る

## やること

- `bun run test` で `test/comment-reference.test.ts` を落とし（一覧から外したファイルの違反が行番号つきで出る）、ファイルごとに直して一覧から外す。外し忘れは同じテストの2つめが落とす
- ソースファイル名: シンボルの名前に替える（JSDoc の中でそのファイルから見えるものは `{@link}`、それ以外はバッククォートの名前）。自分のファイルは「ここ」。呼ぶ側・使う側を並べているだけのもの（「〜が呼ぶ」「〜が使う」）は消し、呼ぶ側に求める条件だけを残す。実在しないファイル名（すでに古くなった名指し）は、今そのことを持つシンボルを探して指すか、要らなければ消す
- 節番号つきの参照: `docs/x.md 4.2「句」` は番号を消すだけ。番号だけで句が無いもの（`docs/design.md 7章`）は、その番号の見出しの句を足す。ファイル名の無い番号だけの参照（`（13.9）`）も同じく `docs/…md「句」` に直す（検査には載っていないので目で拾う）
- `//` の中の `{@link X}`: バッククォートの `X` に替えるか、宣言に付いた説明なら JSDoc（`/** */`）に替える
- 節の句を変えたら `bun run scripts/find-stray-reference.ts` で迷子が0件かを見る
- 着手前に前提を確かめ直した結果、想定どおり100ファイル・877行が対象で、作業は不要にならなかった。実行して分かった追加の判断:
  - `原則N`（`docs/architecture.md` の番号付き原則）も「節番号つきの参照」と同じ扱いで、`docs/architecture.md「句」`（句は原則の本文の太字部分。例: 原則3→「1ファイル = 1つの境界」、原則4→「キャラクターの中身をコードに書かない」、原則2→「core → adapter は禁止」）に直す。ファイル名を外して `（原則3）` のような裸の番号にして検査だけ通すのは規則違反
  - `test/architecture.test.ts` のような検査ファイル名を指す箇所は「呼ぶ側」と同じ扱いで消すが、「その制約を検査が守っている」という事実自体が要るときは、ファイル名を出さずに「検査が落とす」「検査が見張る」のように中身で残す
  - `docs/design.md` の章番号は見出しの句がやや広め（例: 7章の見出しは「キャラクターパック」だが雑談の記憶やエピソード索引の話も同じ章に入っている）なので、句が話題とずれて見えても、その番号の見出しの句をそのまま使う

## 背景

- 着手時点の違反は 100 ファイル・877 行（ソースファイル名・節番号・行コメントの `{@link}` の合計）
- 規則・検査・一覧は T-708 で入った。範囲は後段のタスクと重ならないように、パスの先頭で分けてある

## 注意

- コメント以外のコードの振る舞いを変えない
- `test/comment-reference-backlog.ts` は後段の複数のタスクが同じファイルの別の行を消す。並行して進めたときは merge の衝突に気をつける

- 途中で番号だけの形（`（原則3）`）へ縮める直し方が出たため、メインが2回差し戻して `docs/…md「句」` に揃えさせた
