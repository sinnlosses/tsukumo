## 目的

委譲先のサブエージェントが、`bun link`・brew・`~/.zshrc`・mise のグローバル設定・ホームのディレクトリの削除のような、作業ツリーの外に効く操作を打つと、全部のプロジェクトの環境が書きかけのコードに付け替わったり、自動モードの安全判定で委譲がまるごと止まったりする。こうした手順は登録のときに「人がやること」に分けて、委譲先には渡さないようにする。

## 完了条件

- claude-skills の `skills/plan-tasks/SKILL.md` の手順4（書く）に、次の旨が書いてある: ホームや共有の環境を変える手順は、本文の `## 人がやること` の節に分けて書く。それが残るタスクは、`loopable` を決めるときの判断材料に入れる
- claude-skills の `skills/next-task/SKILL.md` 手順5の、委譲先に渡す禁止事項の並びに、次の旨の1行がある:「`bun link`・ホームのファイル・グローバル設定を触らない。必要なら報告に書く」
- claude-skills の `./check.sh` が通り、claude-skills の `main` に入っている。結果の節に、claude-skills のコミットハッシュを書く
- tsukumo の `docs/requirements.md`「4.6 起動と設定」の `bun link` の項に、「打つのは本体の作業ツリーの直下で、`tsukumo-N` の作業ツリーでは打たない（打つとグローバルの `tsukumo` がその作業ツリーのコードに付け替わる）」旨の1句がある
- tsukumo の `bun run check` が通る

## 背景

T-682 の振り返りで、次の3つが起きた。

- (1) サブエージェントが作業ツリーで `bun link` を打ち直した。その結果、グローバルの `tsukumo` コマンドが、本体ではなく tsukumo-3 の未コミットのコードを指すようになった。メインが受け入れで気づくまで、どこから起こしてもそのコードが走る状態だった
- (2) 本文に「ユーザー承認済み」と書いた `~/.nodebrew`・`~/.bun` の削除を委譲に含めたところ、自動モードの安全判定で委譲がまるごと止まった。範囲を削って委譲し直した
- (3) サブエージェントは、自分が打った `mise use -g` が「承認済みの操作の範囲」の外かどうかを判断できず、人に預け直した

補足:

- `task new` は、必須の節（目的・完了条件・背景）と禁止の節（やること・結果）だけを見ている（claude-skills の `taskfile.py` の `REQUIRED_NEW_SECTIONS` / `FORBIDDEN_NEW_SECTIONS`）。そのため `## 人がやること` の節を足しても拒まれない
- `next-task` の手順5は T-675 も直す。同じ箇条で衝突しないよう、このタスクは T-675 のあとに置いた
