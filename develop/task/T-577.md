## 目的

帯（`docs/screen-design.md` 13.9）から、いまのセッションの effort を切り替えられるようにする。表示するのは送った値ではなく、T-576 で確かめた口から読み取った値。

- 読み取った effort が状態に入り、帯のモデルのドロップダウンの隣（モデル → effort → 許可モードの並び）に出ている。選択肢はいまのモデルが選べる段だけで、effort に対応しないモデルでは選べない（理由を `title` で出す）
- 疑似セッション（`src/server/adapter/fake-driver.ts`）も切り替えに応じる
- ターン進行中の扱いがモデルの切り替えと揃っている
- テスト: コマンドの検証・状態の畳み込み・帯の部品の振る舞い
- `bun run check` が通る。帯の見た目は目視で確かめ、どの端末で何が見えたかを結果に書く
- T-576 が「成り立たない」で終わっていたら、着手せず `dropped` で閉じてよい

## やること

前提の調べ直し:

- モデルの切り替えの経路（背景に書いたとおり）は現行のまま: `src/shared/command.ts` の `set-model` → `src/server/core/driver-command.ts` の `dispatchToDriver` → `src/server/adapter/sdk-driver.ts` の `setModel`。`session-manager.ts` の `dispatch` は `set-model` / `set-permission-mode` を特別扱いしておらず（ターン中でも断らない）、`set-effort` も同じ形にすれば揃う
- `Stop` フックはいま `reportGateHooks`（`sdk-driver.ts`）が**仕事のときだけ**登録している（`mode.kind !== "work"` なら `hooks` そのものを渡さない）。雑談のときは `chatSummaryHooks` の `PostCompact` だけが載る
- `supportedModels()` の実機確認: スクラッチで `query()` を1つ起こし（`tools: []`・`persistSession` 相当・cwd はスクラッチ）、`await session.supportedModels()` を呼んで返り値を見た（中身はモデルのカタログで会話の内容ではない）。結果:
  - `opus` / `sonnet` / `haiku` は `value` がそのままエイリアスと一致する
  - `fable` は一致しない（`value: "claude-fable-5-1"`）——`resolveModelAlias` と同じ部分一致で当てないと選べない
  - `haiku` は `supportsEffort` フィールド自体が無い（`undefined` → `false` に畳む）。`supportedEffortLevels` も無い
  - 対応する行では `supportedEffortLevels` は `["low","medium","high","xhigh","max"]`（5段）だったが、`sdk.d.ts` の型は4段（`xhigh` 無し）のモデルもあると言っている（Opus 4.6 / Sonnet 4.6 相当）ので、選べる段は表示側で「対応表の値だけ」にする（決め打ちの5段にしない）

2つの判断:

- **雑談でも `Stop` フックを常に登録する**（`chatSummaryHooks` の `PostCompact` と共存）。effort を読む理由づけ（`input.effort?.level` を見て `effort-changed` を流す）は「report の関所」とは無関係な独立した仕事なので、`mode.kind` で分岐するのは関所の判定（`gate.shouldBlock` と、それにかかる macrotask 待ち）だけにする。**理由**: 雑談のときだけ effort が帯から見えなくなるのは、帯が「どの画面からも動き方を変えたい」という資格の規則（`docs/screen-design.md` 13.9「帯に何を置くか」）に反する。関数名を `reportGateHooks` から `stopHooks` に変え、常に `{ Stop: [...] }` を返す形にした（`undefined` を返さない）
- **起動直後（1ターンも読めていない）は「対応する・しないに関わらず選べない」を、読めない理由の文言で出す**。`model`/`permissionMode` が「まだ届いていない値は見た目上の既定へ倒す」のと違い、effort は「対応表の行があり、対応しないと分かっている」ときだけ `unsupported`（「このモデルは effort に対応していない」）を出し、対応表そのものがまだ届いていない・対応する値がまだ1件も読めていないときは `unknown`（「まだ effort を読み取れていない（ターンが終わると分かる）」）にする。どちらも選べない（`disabled`）点は同じだが、**分かってもいないことを「対応しない」と言い切らない**ため状態を分けた（`src/browser/features/screen-nav/domain/effort-label.ts` の `EffortSelect`）

## 注意

- 新しいセッションの既定（歯車・`~/.tsukumo/state.json`）に effort を覚えさせるのは後ろの別タスク。ここではセッション限りの切り替えまで

## 結果

- 検証コマンド: 2642 pass / 0 fail（+16）。macOS の headless Chromium で疑似セッションを見た: 起動直後は effort が選べず「まだ読み取れていない」、1ターン後に medium で選べる、`set-effort(high)` の直後は medium のまま、次のターンの後に high。haiku では選べず「対応していない」。帯は Opus → High → 自動判定 の並び、1400/400px で横スクロールなし
- 雑談でも effort を読むため `Stop` フックを常に登録し（関所の判定だけ仕事に絞る。`reportGateHooks` → `stopHooks`）、起動直後の「未読」と「非対応」を型で分けた。`docs/screen-design.md` 13.9 に残っていた「effort も既定 medium に倒す」を「読めない値は出さない」に合わせて直した（前のタスクの受け入れで見落とした行）
