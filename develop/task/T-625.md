## 目的

`test-audit` スキルのキャンペーンモード（同スキルの `CAMPAIGN.md` の8段）で、`test/browser/components/page/` の `achievement/` `character/` `token-usage/`（約5,500行） のテストを刈り込む。価値の低いテスト・実装に結合したテスト・より強い証明と重なるテストと、テストしか呼ばない本番コードを消し、残す契約はより強い境界のテストに寄せる。

## 完了条件

- 対象範囲のテストの宣言ごとに `R` / `F` / `C` / `D` の印と1行の証拠を付けた台帳を作り、印ごとの件数と、`C` / `D` の宣言ごとの残す側（keeper）を タスクの結果 に書く（台帳の全文はリポジトリに置かない）
- `D` / `C` の編集と、それで消せるようになったテスト専用の本番コードの継ぎ目の削除を済ませる
- 移した（`C` / `F`）契約ごとに、本番側の持ち主にわざと1つ変異を入れて keeper が落ちることを確かめ、元に戻す
- 基準線（着手時）と完了時の、対象範囲のテストの `it` の数と行数、本番コードの増減を タスクの結果 に書く
- `bun run check` が通る
- 確信の持てる候補が無ければ、台帳の件数だけ書いて編集なしで `done` にしてよい

## 背景

- 2026-09-25 に `test-audit` スキル（openclaw/openclaw の同名スキルを日本語化して claude-skills に入れたもの）を取り込み、監査モードの試運転で、テストだけが呼んでいた `parseAnswer`（`src/shared/pending-ask.ts`）と `newFormatTaskSummaries`（`src/shared/task-summary.ts`）を消した。固有の検査は `test/shared/command.test.ts` と `test/server/repository/adapter/task-summary.test.ts` に移した（`0b3ef70a`）
- テスト全体は 205 ファイル・約4.7万行で、機能ごとに1タスクに分けた。このタスクはbrowser の achievement・character・token-usage 画面の範囲

## 決まっていること（蒸し返さない）

- 消すかどうかは `docs/coding-standards.md`「テスト」節の「消すかどうか」「埋めないと決めた穴」と突き合わせる。スキルの残す基準とリポジトリの規約が食い違ったら、リポジトリの規約を優先し、食い違いを タスクの結果 に書く
- 残す基準は、スキルの `SKILL.md`「残す基準」のとおり（とくに、出力の書式を固定するテストと過去のバグの退行テストは残す）
- `CAMPAIGN.md` の段7（プロダクトの欠陥）で見つけた欠陥は、このタスクでは直さず、`develop/direction.md` の 「エージェントのドラフト」節 に積む。段8（`main` の merge）はタスクが短いので要らない
- 1タスク＝1コミット。対象範囲の外のテストは、範囲内の契約を吸収する keeper になるときだけ触る

## やること

前提を調べ直した（2026-09-25 着手時点）。

- 対象範囲は `test/browser/components/page/achievement/` `character/` `token-usage/` の23ファイル・
  5,519行・262件の `it`（`it.each` は無し）。対応する本番コードは `src/browser/components/page/`
  の同名3ディレクトリで6,890行（`.module.css` を除く）。基準線は `bun test --isolate` で
  262 pass・0 fail（落ちているテストは無い）
- レーンは本番側の持ち主の境界で4つに切った: (1) achievement/日記帳
  （`diary-book-request` / `diary-book` / `diary-section` / `diary-notice` / `use-diary-book`）、
  (2) achievement/暦と画面（`day-switch` / `lantern-calendar` / `use-achievement-calendar` /
  `bookmark-section` / `surprise-section` / `presentational-achievement-screen` / `use-achievement` /
  `domain/kanji-date`）、(3) character（`character-create` / `character-edit` / `character-screen` /
  `use-character-create` / `use-character-edit`）、(4) token-usage
  （`context-usage-card` / `presentational-token-usage-screen` / `usage-review-card` /
  `use-token-usage` / `use-usage-review`）
- 全262件を読み、production側の持ち主・呼び手・兄弟テストと突き合わせた。achievement・token-usage の
  2レーンは全件 `R`（container/presentational の分割どおりに、hook がロジックを、component が
  DOM描画・DOM固有の配線（ダイアログの確かめ・ドラッグ&ドロップ・フォーカス）を、それぞれ独立して
  検査しており、重複や死んだ本番コードは無かった）
- character レーンで2件の候補を見つけた。いずれも「component 側のテストが、hook 側で既に検査済みの
  契約を DOM 経由でもう一度、同じ強さで検査している」形（`test-audit` の「本物の境界で重複して
  検査されている」）。詳細は タスクの結果 に書く（台帳の全文はリポジトリに置かない）
- テストだけが呼ぶ本番の継ぎ目（getter・reset export・注入フック）は `diary-book-request.ts` /
  `use-selected-pack.ts` を含め見当たらず、`D` に伴う本番コードの削除は無い
- 前提は崩れておらず、作業（`C` 1件・`F` 1件の編集と変異での確認）を実施した

## 注意

- 変異を入れて確かめるときは、退避したコピーから戻す（`git checkout --` で戻すと、同じファイルへの先行の編集ごと消える）
- `CAMPAIGN.md` の段3・段6は、別のエージェントに読ませることを求めている。サブエージェントの中で別のエージェントを立てられないなら、レーンごとに順に自分で読み、段6の保全のレビューは受け入れのときにメインが行う
- ブラウザに出る絵は自動テストで守らない方針（`docs/architecture.md`）なので、描画のテストを消すときも、足すときも、その方針の範囲で判断する
