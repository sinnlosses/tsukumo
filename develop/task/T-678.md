## 目的

「5段のうち4段目」のように段（フェーズ）の位置が分かっているものを、文字列でなくプログレスバーや段の図で見せ、ひと目で読めるようにする。書き手（claude）の心がけに頼らず、`report` の塊の種類として型で渡させる。

## 完了条件

- `report` の塊の種類に `progress` がある（各段の名前と、いまの段の位置）。tsukumo がそれを段の図として描き、いまの段・済んだ段・残りの段が色だけでなく文字か形でも見分けられる
- 塊の説明（`src/shared/report-block.ts` の `describe`）に使いどころを書く（段の位置が分かっているときはこれで見せ、文字で「N のうち M」と書かない）
- `docs/display.md` のレポートの仕様と `docs/glossary.md` を合わせる
- 手で確かめる: 段の図が出ること、段の名前が長いときや段が多いとき（10段前後）に崩れないこと。何が見えたかを結果の節に書く
- `bun run check` が通る

## 決まっていること

- **渡す手段は `report` の塊の種類 `progress`**（`docs/research/report-block.md` 11章の4段目）。塊なので型で縛れて、節の中のどこにでも置ける（「型付きの欄か、本文の記法か」は塊で両方が取れるので論点から外した）
- **塊の仕組み（`report` の引数を `sections` に切り替えるタスク）が done になってから着手する。** 仕組みのタスクは T-705（`dependencies` に入れてある）
- **本文に段の位置を文字で書いたときの差し戻しは足さない。** 過去の `report` 522件のうち、段の位置を文字で書いたものは10件（1.9%）で、日付・版番号・分数との誤検出を抑える手間に見合わない（`docs/research/report-block.md` 2章）

## 背景

- 塊の形と「塊 → Markdown」の組み立ては `src/shared/report-block.ts`、描いた塊は `src/shared/main-view.ts` の組み立てを通って `src/browser/components/page/conversation/components/main-view/markdown/` で描かれる（塊の仕組みのタスクで入る。組み立てが出す class 名の語彙は `src/shared/report-notation.ts`、見た目は `report-notation.module.css`）
- 検証結果の帯（`checks`。`src/shared/report-check.ts`）が「型で受けて、色と文字の両方で描く」の前例
- 素の HTML の `progress` / `meter` は許可リストに載せていない（バーの長さは色と同じく「文字でも読める」を満たさない。`src/server/report/core/report-notation.ts` の JSDoc）。段の図は長さでなく、段ごとの印と文字で描く
- サブエージェントの合図はすでに `状況 | n/N | …` の形で段の位置を持っている（`src/server/system-prompt/core/speech-cadence.ts` の規約）が、画面には出ていない

## 解くべき論点

- 塊の形。案は `{ kind: "progress", steps: string[], current: number }`（`current` は0始まりの位置。全部済んだら `steps.length`）。名前の無い段を許すか（許すなら番号を tsukumo が振る）
- 段の途中でレポートを出すのは中間レポートが多い。中間レポートが畳まれる（`superseded`）とき、進み具合の塊をどう見せるか（畳んだ見出しに出すか、出さないか）

## やること

前提の確かめ（2026-09-27）: 依存タスク T-676（`checks`）・T-679（提案書）・T-705（`sections` への切り替え）は
いずれも done（`develop/task/` から消えており、振り返り済み）。`src/shared/report-block.ts` の
`reportBlockSchema` は現在 `text` / `list` / `table` / `note` / `stats` / `code` / `mermaid` / `markdown` の
8種で、`progress` は無い。前提は崩れていない。

論点の決定:

- **塊の形は案のまま採用**: `{ kind: "progress", steps: readonly string[], current: number, fold }`。
  `steps` は1個以上、空文字を許し（`steps.trim() === ""` の段は tsukumo が1始まりの番号を振る）、
  `current` は0始まりの整数（全部済んだら `steps.length`）。`current` と `steps.length` の突き合わせは
  スキルでは縛らない（`ragged-table` と同じく、型を跨ぐ整合は検査の層に置く発想もあるが、崩れても
  「全部済んだ表示になる／全部残りの表示になる」だけで実害が薄いため、このタスクでは追加しない）
- **見せ方は `checks` と同じ「型で受けて、色と文字の両方で描く」**: 各段を `<div class="progress-step ...">`
  で並べ、済んだ段は `<b>済</b>`、いまの段は `<b>今</b>`、残りの段は `<b>N</b>`（番号）を前置きし、
  色（クラス）だけでなく文字でも判別できるようにする。`stats` と同じ HTML の塊なので、段の名前は
  `htmlInlineWithCode` で HTML として逃がす
- **畳まれた中間レポートでの見せ方**: 何もしない（既存の仕組みのまま）。折りたたみの `<summary>` は
  `extractFirstLine`（`src/shared/main-view.ts`）が本文の先頭行から作るが、本文の先頭は常に
  `report.conclusion`（`reportMarkdown` の組み立て順）で、`progress` の塊は `sections` の中、つまり
  先頭行より後ろに来る。したがって `progress` の塊は畳んだ見出しには出ず、本文を開けば見える
  ——`checks` の帯と同じ扱いで、新たに手を入れる必要はない
- 塊の種類がある記法（`note` / `stats` と同列）として、逃げ道の外側に手書きの `class="progress"` を
  書いたら差し戻す（`src/server/report/core/report-notation.ts` の表と対応する `report-violation.ts` の
  `MARKDOWN_NOTATION_NAMES` / `hasNotation` に `progress` を足す）

実装:

- `src/shared/report-block.ts`: `progressBlockSchema` を追加し `reportBlockSchema` の union に足す。
  `blockMarkdown` に `case "progress"` を足し、`progressMarkdown` で HTML を組む
- `src/shared/report-notation.ts`: `REPORT_BLOCK_MARK_NAMES` に `progress` / `progress-step` /
  `progress-step-done` / `progress-step-current` を足す（モデルには教えない、塊から組む印）
- `src/browser/components/page/conversation/components/main-view/markdown/report-notation.module.css`:
  上記の class に見た目を足す（済み・今・残りが枠・地・文字で見分けられるようにする）
- `src/server/report/core/report-notation.ts`: 本文の塊の並びに `progress` を足す（8種→9種）
- `src/server/report/core/report-violation.ts`: `MARKDOWN_NOTATION_NAMES` に `progress` を足し、
  `hasNotation` の `note` / `stats` の分岐に `progress` を合流させる
- `docs/display.md` 4.2・`docs/glossary.md`「塊」: 塊の種類の列に `progress` を足す
- テスト: `test/shared/report-block.test.ts`（`progress` の Markdown の組み方。名前の無い段・済み/今/残りの出し分け）、
  `test/server/report/core/report-violation.test.ts`（逃げ道に `class="progress"` を書いたら差し戻す）、
  `test/server/report/core/report-notation.test.ts`（`REPORT_NOTATION_NAMES.length` の期待値を更新）
- 手で確かめる: E2E か capture 系スクリプトで、段の名前が長いとき・段が10個前後のときに崩れないことを見る

## 注意

- 調べて、既存の塊（`stats` やチェックリストの `list`）で十分に表せる（新しい塊が要らない）と分かったら、塊の説明に使い方を足すだけにして完了条件を縮めてよい。その判断は結果の節に書く
