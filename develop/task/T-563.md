## 目的

成果の画面の「灯りの暦」（直近5週の日ごとの灯りと日記ありの鈴）に要る数を、開くたびに重くならない形でブラウザへ渡す。

## 完了条件

- 直近5週ぶん（範囲は `docs/design.md`「成果の集め方と配り方」の暦の範囲）の日ごとの**コミットの数**を、`git log` 1回で集める関数（`readCommitCalendar`）がある。**終えたタスクの数は日ごとに数えない**（灯りはコミットの数だけで決める。`docs/requirements.md` 4.11「灯りの段階」）
- 今日以外の日の数はプロセスの中で覚え、2回目からは取り直さない（今日の分だけ取り直す）ことをテストで確かめてある。覚えの入れ物は配線（`src/view-delivery.ts`）で作って渡す
- `GET /achievement-calendar`（型は `AchievementCalendar`。`docs/design.md`「成果の集め方と配り方」）でブラウザが受け取れ、読めない形は「取れなかった」に倒れる
- 灯りの段階（灯りなし／ほのか／ともる／明るい）の判定は shared の純粋関数 `lampLevel` で、区切りは `docs/requirements.md` 4.11「灯りの段階」の表
- `bun run check` が通る

## 背景

- いまの1日ぶんの集計は `src/server/adapter/main-history.ts` の `readAchievement`（`git log --since` に7日の余裕、タスクの中身は `git ls-tree` と `git cat-file --batch`）。git の呼び出しは `src/server/adapter/git.ts` の `runGit`
- 経路の先例は `ACHIEVEMENT_PATH`（`src/shared/achievement.ts`、`src/server/adapter/server.ts`）
- 「日記あり」は型の `diaryDates` で運ぶ。日記の保存（T-564）がまだ無ければ空の配列を返してよい（T-564 が日記の置き場の一覧で埋める）

## やること

前提を調べ直した結果、`ACHIEVEMENT_PATH`・`readAchievement`・`AchievementMilestone` などの先例は
本文どおりに存在し、`readCommitCalendar`・`AchievementCalendar`・`lampLevel`・`/achievement-calendar`
はまだ無い（T-561 が正典を先に書いただけ）ので、素直に着手できる。

1. `src/shared/achievement-calendar.ts` を新規作成: `ACHIEVEMENT_CALENDAR_PATH`
   （`/achievement-calendar`）、型 `AchievementCalendar`（`achievement.ts` の `DailyAchievement` と
   同じ形——`unknown` / `known`。`known` は `today`・`days`（`date`・`commitCount`）・`diaryDates`）、
   `readAchievementCalendar`（zod、読めない形は `UNKNOWN_ACHIEVEMENT_CALENDAR`）、暦の範囲を出す
   `achievementCalendarDateKeys(today)`（今週の月曜の4週前の月曜〜今日、`Temporal.PlainDate`）、
   `LampLevel` と `lampLevel`（区切りの表は `satisfies` で持つ）
2. `src/server/core/achievement.ts` に `achievementCommitCountsByDate`（committer date をローカル
   日付に直した `AchievementCommitWithDate` の並びを、運用の帳面を除いて日付キーごとの数に畳む
   純関数）を足す
3. `src/server/adapter/main-history.ts`: `AchievementCommitCache`（`dailyCounts`・`totalsBeforeDay`
   の2つの `Map` を持つ1つの入れ物。`createAchievementCommitCache` で作る）と
   `readCommitCalendar(cwd, today, cache)` を足す。**手順2の `readCommitsSince` をそのまま使い回せる**
   （`--since` だけの1回の `git log` で足りるので、新しい `git` コマンドは要らない）。合わせて
   `readAchievement` に `cache` 引数を足し、いまの `readAllCommitsUntil`（節目の通算のコミットの数）
   の呼び出しを `cache.totalsBeforeDay` を先に見るラッパーで包む（同じ入れ物を使い回す。既存の
   `git log --until` の形は変えない——注意の「1回にまとめられない事情」はここで、暦は窓（直近5週+
   7日の余裕）だけを見る `--since` の1回で足り、節目は履歴の頭からの `--until` が要るので、2つは
   別の `git log` のまま）
4. `src/server/adapter/server.ts` に `ReadAchievementCalendar` 型と `GET /achievement-calendar`
   の配信（`writeAchievement` と同じ形: 起動トークン確認→403、`unavailable`→503、それ以外は JSON）
   を足す
5. `src/view-delivery.ts` で `createAchievementCommitCache()` を1つ作り、`readAchievement` と
   新しい `readAchievementCalendar` の両方に配線する（`diaryDates` は T-564 が無いのでいまは
   常に空配列）
6. `docs/design.md`「成果の集め方と配り方」の手順7の文言（「入れ物は暦と一緒に足すので、それまでは
   …数え直す」）を、実装後の形（`AchievementCommitCache` に2つの `Map` がある・持ち主は
   `view-delivery.ts`）に直す
7. テスト: `test/shared/achievement-calendar.test.ts`（`lampLevel` の区切り・`achievementCalendarDateKeys`
   の範囲・`readAchievementCalendar` の読み取り）、`test/server/adapter/main-history.test.ts` に
   `readCommitCalendar`（範囲・日ごとの数・帳面除外・キャッシュの使い回し）を追加。`server.test.ts`
   に `/achievement-calendar` の403/503/200を追加

## 注意

- 覚えの入れ物は、1日ぶんの応答の通算のコミットの数（節目。`main-history.ts` の `readAllCommitsUntil`）にも使う（`docs/design.md`「成果の集め方と配り方」手順7。今日以外の日の数を覚える）。この入れ物が無かったので、節目のほうはまだ応答ごとに数え直している
- 会話の中身・コミットの件名は運ばない（`docs/coding-standards.md`「会話内容の扱い」）
- 調べて、いまの `readAchievement` の形では1回にまとめられない事情が見つかったら、その理由を結果の節に書いて最小の呼び出しの数で済ませてよい

## 結果

- 検証コマンド: 2352 pass / 0 fail（+20）
- 暦（日ごとの数）と節目（通算のコミットの数）は、`view-delivery.ts` で1つ作る `AchievementCommitCache` を共有して、今日以外の日を覚える。受け入れのときに、中の `Map` をそのまま渡していた形から、覚える・引く口だけを持つ形に包み直した（渡した入れ物を呼び出し先が書き換えないようにするため）。`git log` は暦で1回、節目で1回の、目的の違う2本のまま
- 覚えたかどうかのテストは、覚えた値を口から書き換え、2回目がその値を返すことで確かめる（過去の日付のコミットを足す方法は `--since` の打ち切りに当たるので使わなかった）。`diaryDates` は日記の保存が入るまで空
- 振り返り: 受け入れのときにメインが直したもの（ドラフト 1件）
