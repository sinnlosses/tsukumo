## 目的

`docs/research/server-procedure-proposal.md` の段1のうち HTTP の側。ビューサーバがどの経路をどう受けるかを、`if` の連なりを読まずに1枚の表から辿れるようにする。

## 完了条件

- `src/server/view-server/adapter/server.ts` の `respond` にあった経路の分岐が、経路（完全一致か接頭辞か）・メソッド・トークン照合の要否・受け手を1行ずつ持つ表になっている
- トークン照合（`hasStartupToken` → 403）が表の列から1箇所で掛かり、各 `write*` 関数から照合の手書きが消えている
- 応答（状態コード・`content-type`・`cache-control`・404 の本文）は変わらない。既存の `test/` の配信のテストが書き換えなしか、表の形に合わせた最小の書き換えで通る
- `bun run check` が通る

## 背景

- `respond`（`server.ts` の 242行目あたり）は `if (path === ...)` / `path.startsWith(...)` を11本並べ、最後に 404 を返す。経路名の定数は `src/shared/*.ts`（`REPOSITORY_FILE_PATH` など）と `server.ts`（`LAYOUT_PATH` など）にある
- トークン照合は `writeRepositoryFileList` `writeTokenUsageSummary` `writeContextUsage` `writePromptImage` `writeAchievement` `writeAchievementCalendar` の6関数がそれぞれ冒頭で書いている
- `docs/research/hono-server.md`「入れずに済ませる中間案」がこの形（経路の表）を挙げている

## やること

前提を確かめ直した（2026-09-26）。`src/server/view-server/adapter/server.ts` の `respond`
（242行目〜319行目）はいまも `if` 11本の連なりのままで、`docs/research/hono-server.md`
「入れずに済ませる中間案」が挙げた形（経路の表）はまだ未着手。`docs/design.md` の
「コマンドの受け手と手続きの置き方」は WebSocket 側（`session-manager.ts` の `switch`）の話で、
このタスクが対象にする HTTP の `respond` はまだ表になっていないので、前提は崩れていない。作業は要る。

- `respond` の直前に、経路の表 `ROUTES`（`satisfies readonly ViewRoute[]`）を足す。1行1経路で、列は
  - `match`: `{ kind: "exact", path }` か `{ kind: "prefix", prefix }`（判別可能な合併型）
  - `method`: `"GET"` か、いまの `respond` で未検査（`LAYOUT_PATH` だけ）の経路を表すための `"ANY"`
    （`| undefined` は使わない。既存の11行のうち `LAYOUT_PATH` だけが `request.method` を見ていない
    ので、その1行だけ `"ANY"` にして挙動を変えない）
  - `requiresToken`: `boolean`（`hasStartupToken` を掛ける6経路だけ `true`）
  - `handle`: `(request, response, path, options) => void`（実処理は既存の `write*` 関数へそのまま委譲。
    経路の接頭辞を剥がす `path.slice(...)` は `handle` の中——今までその剥がし方をしていた
    呼び出し側と同じ場所）
- `respond` 本体を「`ROUTES` から最初に一致する行を探す → 無ければ404 → `requiresToken` かつ
  `!hasStartupToken` なら403 → `handle` を呼ぶ」に置き換える。**トークン照合はここ1箇所**にし、
  `writeRepositoryFileList` `writeTokenUsageSummary` `writeContextUsage` `writePromptImage`
  `writeAchievement` `writeAchievementCalendar` の6関数それぞれの冒頭にある
  `if (!hasStartupToken(...)) { 403; return }` を削る（403の応答はいまと同じ本文・ヘッダのまま
  `respond` 側に1つ残す）。6関数のシグネチャは、403判定に使っていた `request` が要らなくなる分だけ
  削る（`writeTokenUsageSummary` と `writeAchievement` は `request` からクエリ値も読むのでそのまま
  残す）
- 応答（状態コード・`content-type`・`cache-control`・404/403の本文）は変えない。`test/server/view-server/adapter/server.test.ts`
  はふるまいだけを見ているので書き換えは不要な見込み（実装後に `bun run test` で確認する）

## 注意

- 依存は足さない（Hono は提案で却下済み）
- 読み取りの5本はのちの段（oRPC への移行）で表から抜けるので、表の形に凝りすぎない
