## 目的

`docs/research/server-procedure-proposal.md` の段1のうち HTTP の側。ビューサーバがどの経路をどう受けるかを、`if` の連なりを読まずに1枚の表から辿れるようにする。

## 完了条件

- `src/server/view-server/adapter/server.ts` の `respond` にあった経路の分岐が、経路（完全一致か接頭辞か）・メソッド・トークン照合の要否・受け手を1行ずつ持つ表になっている
- トークン照合（`hasStartupToken` → 403）が表の列から1箇所で掛かり、各 `write*` 関数から照合の手書きが消えている
- 応答（状態コード・`content-type`・`cache-control`・404 の本文）は変わらない。既存の `test/` の配信のテストが書き換えなしか、表の形に合わせた最小の書き換えで通る
- `bun run check` が通る

## 背景

- `respond`（`server.ts` の 242行目あたり）は `if (path === ...)` / `path.startsWith(...)` を11本並べ、最後に 404 を返す。経路名の定数は `src/shared/*.ts`（`REPOSITORY_FILE_PATH` など）と `server.ts`（`LAYOUT_PATH` など）にある
- トークン照合は `writeRepositoryFileList` `writeTokenUsageSummary` `writeContextUsage` `writePromptImage` `writeAchievement` `writeAchievementCalendar` の6関数がそれぞれ冒頭で書いている
- `docs/research/hono-server.md`「入れずに済ませる中間案」がこの形（経路の表）を挙げている

## 注意

- 依存は足さない（Hono は提案で却下済み）
- 読み取りの5本はのちの段（oRPC への移行）で表から抜けるので、表の形に凝りすぎない
