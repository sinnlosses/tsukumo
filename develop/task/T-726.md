## 目的

5時間枠と週の利用枠の使用状況（使用率・戻る時刻）を、サイドバーに常に出すための出どころと出し方を決める（2026-09-27 ユーザーの指示。表示は後段のタスク）。

## 完了条件

- `docs/research/` に調べた結果と設計を書く。少なくとも「解くべき論点」の各項に結論と理由がある
- 採る案を `docs/display.md`（サイドバー・入力欄の節）と `docs/requirements.md` の該当の機能に反映している
- 後段のタスク（T-727）の背景と注意を設計の結論に合わせて直す。実装の広がり（足す口・プロトコルの変更・触る機能の数）を見て後段の `difficulty` も見直す

- `bun run check` が通る

## 背景

- いまの利用上限は SDK の `rate_limit_event` だけが源（`src/server/session-driver/core/sdk-message.ts` の `rateLimitEvents` → `SessionState.rateLimit`、型は `src/shared/rate-limit.ts` の `RateLimit`）。知らせが来たときの状態（`clear` / `warning` / `rejected`）・枠・戻る時刻だけを運び、使用率（`utilization`）は単位が型定義に書かれていないので運んでいない。claude.ai の契約のときだけ届く
- 入力欄の経過時間の行が `useTurnStatus` の `turnStatusNotice` で「利用上限が近い」「利用上限 HH:MMまで」を出している
- サイドバーのコンテキストの行は `src/browser/components/domain/sidebar/context-usage-row.tsx`

## 解くべき論点

- 5時間枠と週の枠の使用状況を、知らせが来ていないときにも取れる出どころがあるか（SDK の API・Claude Code が `/usage` で読むもの・`rate_limit_event` の `utilization` の単位）。一次情報で確かめる
- 「再読み込み」ボタンが何を呼び直すか（出どころへ取りに行けるのか、最後に届いた知らせを出し直すだけか）
- 「利用上限に達した」（`rejected`）は入力欄に残すか。ユーザーの指示が消すと言ったのは「利用上限が近い」

## やること

背景の主張（`rateLimitEvents` → `SessionState.rateLimit`、`RateLimit` の型、`turnStatusNotice`、`context-usage-row.tsx`）は 2026-09-27 に実物と一致することを確かめた。

1. 同梱の SDK（`@anthropic-ai/claude-agent-sdk` 0.3.283 / Claude Code 2.1.283）の型定義と同梱の CLI の中身から、5時間枠・週の枠の使用状況を知らせ無しでも取れる口（`Query` の `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET`、制御要求 `get_usage`）の返す形・単位・取りに行く先・スナップショットの寿命を確かめる。`rate_limit_event` の `utilization` の単位も確かめる
2. 調べた結果と設計（出どころ・再読み込みが呼ぶもの・`rejected` の置き場所・採らなかった案）を `docs/research/plan-usage.md` に書く。認証情報を読んで外部 API を呼ぶ案は提案書に書くところまでで止める
3. 採る案を `docs/display.md` 4.2「各表示物」のサイドバー・入力欄、`docs/requirements.md` 4.1、`docs/glossary.md`「利用上限」に反映する（見出しの数を前後で比べ、`node scripts/find-stray-reference.ts` を通す）
4. T-727 の背景と注意を結論に合わせて直し、`difficulty` を見直す
5. `pnpm run format` のあと `pnpm run check` を通す
