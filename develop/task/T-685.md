## 目的

Bun から Node + Vite + Vitest へ移す5段の4段目。保存したときにページごと取り直すのをやめ、開いている
画面・選んでいるターン・組み立て中の答えを保ったまま部品を差し替える。

## 完了条件

- 下の論点の結論が `docs/design.md` 11章（作り直しを押す仕組み）に書かれている
- HMR を採ったなら、`bun run dev` で `src/browser/` の部品を保存すると、画面の状態を保ったまま差し替わる
  ことを目で見て確かめている。採らなかったなら、理由と今の見張りがどう動くかを結果の節に書く
- 使わなくなった `src/server/view-server/adapter/ui-rebuild.ts` の口と環境変数（`TSUKUMO_WATCH_UI`）が消えている
- `bun run check` が通る

## 背景

- `src/server/view-server/adapter/ui-rebuild.ts`（154行）が `node:fs` の `watch` で `src/browser/` を再帰に
  見張り、保存が静まったら組み立て直してタブに「取り直せ」を送る（`docs/design.md` 11章
  「作り直しを押す仕組み」）
- サーバは `node:http`（`src/server/view-server/adapter/server.ts`）で、`/rpc` と `/ws`（`ws`）を同じ口で持つ

## 解くべき論点

- Vite を middleware mode で `node:http` のサーバに差し込むか、`vite build --watch` に留めるか
- 差し込むなら `/ws`（`ws`）と Vite の HMR の WebSocket が同じサーバで衝突しないか
- 本番（`tsukumo` の起動）で Vite を読み込まない形にできるか

## やること

調べ直した前提（2026-09-27 のコード）:

- `/ws` は `ws` の `noServer` で、`session-socket.ts` の `upgrade` の受け口が経路・トークン・`Origin` を見る。
  合わない upgrade には 403 を書いて閉じるので、そのままでは同じサーバに載せた Vite の HMR の接続も壊す
- Vite 8 の開発サーバは `server.ws.server` に渡したサーバの `upgrade` を聞き、サブプロトコル
  `vite-hmr` と経路（`server.ws.path`）が合うものだけを受ける。`ws.server` を渡すと HMR の client は
  ページと同じオリジンへ繋ぐので、ポートを別に取らなくてよい
- Vite の JS API（`createServer`）は同じプロセスの `process.env.NODE_ENV` を `development` に書き換える。
  `src/cli.ts` は `process.env` そのものを `readConfig` に渡していて、claude の子プロセスの環境
  （`inheritedEnv`）にも混ざる
- 依存の事前の束ね（`optimizeDeps`）の走査は `vite.config.ts` の `oxc` を読まず、`import { type Element } from "hast"`
  を依存として探して走査ごと諦める

論点の結論:

- **middleware mode で `node:http` のサーバに差し込む。** `vite build --watch` に留めると、保存のたびに
  ページを読み込み直す今の形から変わらず、目的（画面の状態を保ったまま差し替える）に届かない。
  差し込む量はアダプタ1つ（`ui-dev-server.ts`）と、サーバの配り方を合併型（`ViewUi` の `bundle` / `dev`）
  にすることで収まる。経路の表に無い要求だけを開発サーバへ回すので、既存の経路は変わらない
- **`/ws` との衝突は、HMR の経路を分けて `/ws` の受け口に譲らせて解く。** HMR は `/vite-hmr`
  （サブプロトコル `vite-hmr`）で、開発サーバが `ownsUpgrade` で自分の upgrade かを答え、
  `attachSessionSocket` の `yieldsUpgrade` がそれを見て触らずに返す。譲る条件は Vite が受ける条件と同じ
  （経路とサブプロトコル）なので、どちらも受けない upgrade は残らない
- **本番では Vite を読み込まない。** `vite` は `startUiDevServer` の中の動的 import だけで読み、
  呼ぶのは `--dev` のときだけ。`NODE_ENV` の書き換えは、`src/cli.ts` が `process.env` の写しを
  `readConfig` に渡すことで子プロセスへ漏らさない
- **サーバ側のソースが起動時から変わったら HMR を止める**（前の見張りの `sourceFingerprint` の決まりを保つ）。
  開発サーバのプラグインが保存のたびに指紋を比べ、変わっていたら何も当てず、配り方を起動のときに
  読んだ対（`bun run dev` が起こす前に組み立てたもの）へ戻してタブに `refresh` の `page` を押す

手順:

1. `src/server/view-server/adapter/ui-rebuild.ts` を消し、`ui-dev-server.ts` を置く（`vite` の動的 import・
   middleware mode・HMR の経路・指紋の比べ）
2. `server.ts` の `ViewAssets` を `ViewUi`（`bundle` / `dev`）にし、`dev` のときはページを開発サーバに通し、
   経路の表に無い要求を開発サーバへ回す
3. `session-socket.ts` に `yieldsUpgrade` を足す
4. `TSUKUMO_WATCH_UI` を消し、`--dev` 引数にする（`package.json` の `dev`・`src/cli.ts`・`src/main.ts`）。
   `src/cli.ts` は `process.env` の写しを `readConfig` に渡す
5. `vite.config.ts` の `optimizeDeps` に型だけの import を消す指定を足す
6. テスト（`server.test.ts` の `dev` の配り方・`session-socket.test.ts` の譲る upgrade）と、
   `docs/design.md` 11章・`docs/architecture.md`・`README.md` などの記述を追随させる

## 注意

- 調べて HMR が割に合わないと分かったら、`vite build --watch` に留めた形で閉じてよい

## 結果

- 検証コマンド: 単体 2718 pass / 0 fail（+2）、E2E 24 pass / 0 fail
