## 目的

並行する作業ツリーで `pnpm run check` が重なったときに、機械の負荷がコア数の数倍に膨らんでテストが揺れで落ち、打ち直しで検証の回数がさらに増えるのを防ぐ（2026-09-27 ユーザーの指示）。

## 完了条件

- `vitest.config.ts`（単体テスト）に `maxWorkers` の上限を置く。値は `3` と `"30%"` を同じ機械で測って決め、1本で流したときの単体テストの秒数と、3本同時に流したときの負荷（`uptime` の1分平均）を、候補ごとに結果の節に書く
- `pnpm run check` を `nice` で走らせる（`package.json` の `check` か、それを呼ぶ口のどちらに置くかは、`task ship` の検証と手で打つ場合の両方に効くほうを選ぶ）
- 検証コマンド `pnpm run check` を通す

## 決まっていること（蒸し返さない）

- 作業ツリー間で `check` を順番待ちにするロックは入れない。上限でコア数に収まれば要らない（2026-09-27 ユーザー決定）

## 背景

- `vitest.config.ts` には `maxWorkers` も `pool` の指定も無く、Vitest の既定（コア数に応じた本数。この機械は10コアで9本）で走る。`vitest.e2e.config.ts` は `fileParallelism: false` で直列
- 2026-09-27 に測った値（負荷 15〜22）: typecheck 10s・lint 1s・format:check 2s・test 25s・test:e2e 105s
- 同じ日、tsukumo-2・tsukumo-5・tsukumo-6 の check と beads のセルフテストが重なり、1分平均の負荷が 35〜133 に達した。className の検査（`test/architecture.test.ts`）のタイムアウト、`cli.test.ts` と `character-edit.test.tsx` の失敗が、回ごとに違う組み合わせで出た（単独ではどれも通る）
- tsukumo-2 は手で `--maxWorkers=2` を付けて走っていた

## やること

- 前提の確認（2026-09-27 時点）: `vitest.config.ts` に `maxWorkers`・`pool` の指定は無い（背景の記述どおり）。T-776 は `status: todo` のままで `vitest.config.ts` に未着手（`git log` に触った跡なし）なので、同じファイルへの衝突は無い
- `task ship` の検証コマンドの呼び方（`~/.claude/skills/task-workflow/scripts/ship.py` の `read_verify_command`・`attempt`）を確認: CLAUDE.md「## タスク運用」の検証コマンドの行から、バッククォートで囲んだ中身をそのまま取り出し、`subprocess.run(["sh", "-c", verify_command], ...)` で実行する。つまり `task ship` も手で打つときも、実行されるのは同じ `pnpm run check`（package.json の `"check"` スクリプト）。よって `nice` は package.json の `"check"` スクリプト側に置けば両方に効く（CLAUDE.md の検証コマンドの行は変えない）
- `vitest.config.ts` に `test.maxWorkers` を候補値（`3` と `"30%"`）で入れ替えながら、同じ機械で次を測る
  - 1本で `npx vitest run` を流した所要時間（単体テスト全体）
  - 3本同時に `npx vitest run --maxWorkers=<値>` をこの作業ツリーの中だけで起こしたときの `uptime` の1分平均（前後で `uptime` を取り、測った時刻と周りの負荷も記録する）
- 候補を比べて上限の値を決め、`vitest.config.ts` に `maxWorkers` を書く
- package.json の `"check"` スクリプトを `nice` で包む（`typecheck`〜`test:e2e` の一連を1つの `nice` に収める形にする。個別のコマンドごとに `nice` を付けない）
- `pnpm run check` を通す

## 注意

- T-738（E2E を速くする）は E2E を並列にする方向の案を持つ。並列にするなら、この上限と合わせて1本あたりの負荷がコア数を超えないようにする
- T-776（Vitest の並列化で増えた揺れをまとめて扱う）は重い検査のタイムアウトや直列化で揺れを抑える。こちらは負荷の総量を抑える側で、同じ設定ファイルに触るので、先に入ったほうに合わせる
- 上限を入れても揺れが残るなら、それは負荷ではなくテスト側の問題。T-739・T-671 など既存の揺れのタスクに回し、ここで直さない

## 結果

- `maxWorkers: "30%"`（10コアで3本）を採った。15:15〜15:21 の計測（周りの負荷 10〜21）では、1本の単体テストが既定 20.9s → 26.4s。3本同時に流したときの1分平均は、上限なしで 37.1（毎回1〜3ファイルが揺れで落ちる）だったのが 21.5（3本とも全件通る）になった。`3` は同じ本数なので結果も同じで、機械のコア数に比例する `"30%"` にした
- `nice` は `package.json` の `check` を `nice sh -c '…'` で包んで置いた（`task ship` も CLAUDE.md の `pnpm run check` を `sh -c` で打つので、手打ちと ship の両方に効く）
- 検証コマンド: 単体 2729 pass・E2E 24 pass（受け入れの1回で exit 0、125s）
- 振り返り: 兆候なし
