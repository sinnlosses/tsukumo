## 目的

`/next-task` の1件で検証コマンドが委譲先と受け入れの2回、同じ中身に対して走るのを1回に減らす。同じ機械の負荷と待ち時間を下げる（2026-09-27 ユーザーの指示）。

## 完了条件

- 検証コマンドが通ったときに、作業ツリーの中身から作った鍵を控える口を `task` コマンドに足す。受け入れのときにその鍵と同じなら検証を省いてよいと判定する口も足す
- 鍵には、追跡中のファイルの変更・未追跡のファイル（`.gitignore` の対象を除く）・lock ファイルを含める。1ファイル変えると鍵が変わることを、スキルのセルフテストで確かめる
- `next-task` の手順5（委譲先に控えさせる）と手順6（受け入れで照合し、違えば検証コマンドを打つ）を書き換え、正典 `WORKFLOW.md` の該当の節を合わせる
- `task ship` の付け替え後の検証は、この控えで省かない（付け替えで中身が変わるため）
- スキルのセルフテストを通す。このリポジトリの検証コマンド `pnpm run check` も通す

## 解くべき論点

- 鍵の作り方。`git write-tree` は index しか見ないので、`git add -A` を使わずに未追跡のファイルまで含める方法（一時的な index（`GIT_INDEX_FILE`）に足して write-tree する、など）
- 控えの置き場所。作業ツリーの外で、委譲先とメインが同じ場所を読めること（`.git` の中の作業ツリーごとの場所など）。並行する作業ツリーとぶつからないこと
- 検証が揺れで1回落ちたあとに通った場合も「通った」として控えてよいか
- 受け入れで整形コマンドが差分を出したら鍵が変わる。そのときは検証を打ち直すのが正しい、で足りるか

## 背景

- 2026-09-27 の T-724 では、1件で検証コマンドが約12回走った（委譲先2人で約5回、受け入れで6回、衝突を解いたあとに1回）。多くは負荷による揺れの打ち直し
- 揺れが無ければ最低は委譲先1回と受け入れ1回で、`task ship` が付け替えたときはさらに1回。1回あたり約2分20秒（負荷 15〜22 のとき）
- 手順6はいま「報告をそのまま信用しない。`git diff` を読み…整形コマンド → 検証コマンドを打つ」。差分を読むことはそのまま残し、検証を打つかどうかだけを機械の照合で決める

## 注意

- `~/.claude/skills` は claude-skills の本体の作業ツリーへの symlink。本体で枝を切り替えると、全プロジェクトのスキルが即座に変わる。スキルの変更は別の作業ツリーで行う
- 調べて、照合が鍵の作り方のせいで偽の一致を起こしうると分かったら、その理由を結果の節に書いて `dropped` で閉じてよい
