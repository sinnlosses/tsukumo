## 目的

`develop/task/` が際限なく増えないように、振り返りが済んだ `done` / `dropped` のタスクファイルを `git rm` で消す仕組みを入れる。本文は git の履歴から読む。

## 完了条件

- `task` にサブコマンド `prune` があり、消してよいタスクファイルだけを `git rm` して stage する（コミットはしない。ほかのサブコマンドと同じく出力の1語で結果が分かる）。`--dry-run` で消す対象の一覧だけを出せる
- 消してよいかの判定が、T-558 のあとの振り返りの記録の持ち方に合っている（下の論点1）
- `WORKFLOW.md`「ファイル配置と CLAUDE.md」の「アーカイブの段は無い」が、振り返り済みの `done` / `dropped` は `task prune` で消す、に書き換わっていて、サブコマンドの参照の表に `prune` が載っている
- `prune` を誰がいつ呼ぶかが、該当するスキル（`next-task` か `retrospect` の手順、など）に書いてある（論点2）
- tsukumo で1回走らせ、消したファイルを1コミットにして `main` へ送っている。そのあと `task status` の `invalid` が0で、依存の解決が変わっていない
- 下の「解くべき論点」の1つ1つに結論があり、完了時の結果に論点 → 結論を1行ずつ書く
- claude-skills の `./check.sh` が通り、変更が claude-skills の `main` に入っている。tsukumo 側は `bun run check` が通る

## 背景

2026-09-24 に利用者が決めた（`docs/history/direction.md` の 2026-09-24 の項）。直近の振り返りでは1日に71件・76件のタスクを見ていて、いまの「`done`・`dropped` も同じ場所に残す。アーカイブの段は無い」（`WORKFLOW.md`「ファイル配置と CLAUDE.md」）のままだと `develop/task/` が際限なく増える。

- 依存の解決は既に「`done`・`dropped` と、タスクファイルに無い ID は解決済み」（`WORKFLOW.md`「状態」の節）なので、消しても依存は壊れない
- 採番は台帳の `last-id` なので、消した番号が再利用されることはない
- `task.py` のサブコマンドは `status` / `new` / `claim` / `release` / `done` / `ship` / `migrate`（`cmd_*` 関数と `add_parser`）
- いまの `retrospect` は `develop/retrospective.md` の「最後に振り返ったコミット」1行を基準点にしている。T-558 がこの基準点の持ち方を変えうる（T-558 の論点1・2）ので、このタスクは T-558 のあとに置いた
- 振り返りが消えたファイルを読めるようにするのは前段のタスク（依存に置いた）

## 決まっていること（蒸し返さない）

- 移すのではなく消す（`develop/task/done/` のような置き場は作らない）
- 消すのは `/retrospect` ではない。`retrospect` の SKILL.md の「`develop/task/` を直接書き換えない」を守る
- 消す手段は `task` のサブコマンド（`task prune`）にする
- `/retrospect` が読み終える前のタスクは消さない

## 解くべき論点

1. **消してよいかの判定**: T-558 のあとの形で「振り返りが済んだ」をどう判定するか。基準点のコミットの祖先に `done` / `dropped` にしたコミットがある、で足りるか。タスクごとに振り返る形になっていれば、結果の節の記録で判定するほうが確かか
2. **呼ぶ契機**: 人が手で呼ぶのか、`/next-task` や `/retrospect` の手順の最後で呼ぶのか。`/loop` で回っているときに消してよいか
3. **コミットの単位**: 消したファイルを単独の1コミットにするか、振り返りの記録のコミットと一緒にするか。並行する作業ツリーが同じファイルを触っていて `task ship` の rebase でぶつかる場合の扱い
