## 目的

`input-dispatch` と `permission-answer` の揺れはどちらも、場面のタイマー（`afterMs`）で届く `opening` の一言と、テストの操作で流れるイベントの競り合いだった。いまは各シナリオが `waitForEvent("speech", n)` を書き忘れないことに頼っている。書き方ではなく足場の仕組みで、操作が場面のタイマーと競わないようにする（2026-09-27 ユーザーの指示「E2E の失敗を振り返ってタスク化」）。

## 完了条件

- 下の論点を決め、決めた形と理由を `## 結果` に書く
- 決めた形を `test/e2e/scenario-run.ts` に入れ、今ある4ファイル（`input-dispatch`・`permission-answer`・`question-ask`・`task-list`）の手書きの `waitForEvent("speech", …)` のうち、足場が肩代わりするものを消す
- 待ちを書き忘れたシナリオでも競り合いが起きないことを、足した仕組みの側で確かめる（例: 開幕の待ちを外した版を一時的に作って続けて回す）
- 触ったシナリオのファイルを続けて10回回して落ちないこと、`pnpm run test:e2e` を3回通すことを `## 結果` に書く
- `docs/design.md` 10章「E2E の走らせ方」と、前段で足した「E2E の揺れを生まない書き方」の「操作の前に場面のタイマーで届くイベントを待つ」条を、仕組みに合わせて直す
- `pnpm run check` が通る
- 調べて足場で塞ぐ形が立たない（場面ごとの事情が違いすぎる等）と分かったら、理由と比べた案を書いて `dropped` で閉じてよい

## 解くべき論点

- 何を「流し終えた」とみなすか: 疑似セッション（`test/fixture/fake-session.json`）の `opening` と名指しの場面の予定されたイベントの数を足場が数えるのか、fake driver が「予定を流し終えた」印をメッセージの列に出すのか（出すなら成果物のメッセージの列が変わる）
- 待つのは `open` の中か、操作の口（送る・押すの手伝い）を足場に足してそこで待つのか。今の各シナリオは `room.page` を直に操作している
- 場面の途中で操作するシナリオ（許可・質問）では「流し終える」前に操作が要る。その場合の待ち方を仕組みに入れるか、書き方の条に残すか
- 本番のコードに試験用の口を作らない（`docs/design.md` 10章「E2E の成果物と再現」の時計の条と同じ線）。fake driver は `src/` 側にあるので、そこに印を足すのが「試験用の口」に当たるかを判断する

## 背景

- 競り合いの2件: `input-dispatch`（`opening` の speech `afterMs` 200 と依頼後の `partial-utterance`）・`permission-answer`（押して流れる `pending-changed` と場面の `speech` `afterMs` 200）。どちらも待ちを足して直した
- `waitForEvent(kind, occurrence)` は `openRoom` が返す `ScenarioRoom` の口で、届いたメッセージの列を見て待つ
- fake driver は最初のビューが繋がってから場面を流す（`docs/design.md` 10章「E2E の走らせ方」）

## やること

調べ直した前提（いまのコード）:

- 操作するシナリオは4ファイルのうち `input-dispatch`・`permission-answer`・`task-list` の3つだけ（`question-ask` は操作せず、`question-preview` が撮る時点を決めるために `speech` の2回目を手で数えている）。どれも `opening`（最後の手が `afterMs` 200）か名指しの場面の予定を `waitForEvent` の回数で手で数えている
- fake driver（`src/server/session-driver/adapter/fake-driver.ts`）は `opening` を最初のビューが繋がってから0ms起点で、名指しの場面を `opening` の最後の手の時刻から流す。この「いつ何を流すか」の計算は driver の中に閉じていて、足場は知らない
- 疑似セッションの予定は `test/fixture/fake-session.json` の手書きで、場面の中の手は100ms刻みで続き、区切りでは500ms以上空く（`permission`: 100 `pending-changed`・200 `speech`・1200 `utterance`）

採る形:

1. fake driver に「`opening` と名指しの場面を、流し始めからの時刻つきの1本の予定に並べる」関数を置き、driver 自身もそれで流す（試験用の口ではなく、driver の流し方そのものを1箇所にする）。メッセージの列は変わらない
2. 足場は `open` の中でその予定を読み、最初の「静かな区切り」（次の手まで一定の間が空く時点、予定が尽きた時点を含む）までの手が、種別ごとの回数ですべて届くのを待ってから部屋を渡す。区切りは疑似セッションの時刻だけから決まるので、走らせる速さに依らない
3. 場面の途中で操作する `permission-answer` もこの区切り（200 `speech` のあと）で塞がるので、書き方の条には残さない。区切りより先の手を待つのはこれまでどおり `waitForEvent`
4. 4ファイルから、足場が肩代わりする `waitForEvent("speech", …)` と、区切りまでの手を数えている待ちを消す
5. 待ちを消した版で `input-dispatch`・`permission-answer`・`question-ask`・`task-list` を続けて10回ずつ回し、`pnpm run test:e2e` を3回通す
6. `docs/design.md` 10章「E2E の走らせ方」と「E2E の揺れを生まない書き方」の条1を仕組みに合わせて直す

## 注意

- 待ち時間を延ばす・決まった時間を眠らせる形にしない（届いたものを待つ）
- 期待値のメッセージの列が変わるなら `pnpm run test:e2e:update` で撮り直し、`git diff test/e2e/expected/` が意図した変化だけであることを確かめる

## 結果

- 決めた形: fake driver の `startupSteps` で `opening` と名指しの場面を1本の予定に並べ（driver 自身もそれで流す。メッセージの列は不変）、足場の `open` が予定の最初の静かな区切り（次の手まで 500ms 以上空く時点）までの手を種別ごとの回数で待ってから渡す。区切りは予定の時刻だけで決まる。場面の途中の操作（`permission-answer`）もこの区切りで塞がるので書き方の条には残さない
- 検証コマンド: 2729 pass / 0 fail、E2E 28 pass。待ちを消した4ファイルを続けて10回 10/10、`pnpm run test:e2e` 3/3。対照として `open` の待ちを外すと `input-dispatch` が 5/5 で落ちた
- 振り返り: 兆候なし
