## 目的

レポートを3秒で読めるようにする。検証の結果が結論の文の途中や末尾に混ざらないよう、型で縛った欄として受け取り、tsukumo が決まった場所に視覚情報（状態の印）で描く。あわせて、結論の書き方と「文字より視覚情報を優先する」をレポートの記法に入れる。

## 完了条件

- `report` ツールに検証結果の欄 `checks` を足す。1項目は `{ status, label, detail }` の形で型を縛る（`status` は `ok` / `ng` / `unverified` のような決まった値。`label` は何で確かめたか、`detail` は件数・差分など）
- `checks` は**渡さなくてよい**（検証をしていないターン — 雑談・調べものだけ — では欄も帯も出ない）
- tsukumo が `checks` を**結論とは段落を分けて**、結論のすぐ下に1本の帯として描く。状態は色だけでなく文字か形でも見分けられる
- レポートの記法（`src/server/report/core/report-notation.ts`）に次を足す:
  1. 検証の結果は `checks` に入れ、`conclusion` と `body` に書かない
  2. 結論は、したことではなく**読み手から見た変化**で書く（「書き換えた」でなく「次から〜になる」）
  3. **文字列で言えることでも、視覚情報（表・図・バッジ・数の帯など）で見せられるならそちらを優先する**（いまの「内容ごとの印」の節や「文のままでよいのは次のときだけ」とぶつからない言い方にする）
- `docs/display.md` のレポートの仕様と `docs/glossary.md`「report ツール」を合わせる
- 手で確かめる: 帯が結論の直下に出ること、3つの状態が見分けられること、`checks` を渡さないレポートに帯が出ないこと。何が見えたかを結果の節に書く
- `bun run check` が通る

## 背景

- `report` ツールの定義は `src/server/report/core/report-tool.ts`（説明文は「conclusion → body → favor の順に描かれる」）。受け取った値は `src/shared/session-event.ts`（:157〜 の `report` のイベント。`body` と `favor` は無ければ空文字に畳む）を通り、`src/shared/main-view.ts` の組み立て（:265〜。`favor` を `note-favor` の塊で包む）で1つの本文になる。`checks` も同じ道を通る見込み
- 記法の規約の本文は `src/server/report/core/report-notation.ts`。記法への違反を差し戻す検査は `src/server/report/core/report-violation.ts` / `report-review.ts`
- 2026-09-26 の会話で、完了報告の結論に「（`./check.sh` は終了0。push はしていません）」を括弧で入れたら読みにくいと指摘があり、ユーザーと A 案（型付きの欄を tsukumo が固定の位置に描く）で合意した

## 決まっていること（蒸し返さない）

- 2026-09-26 ユーザー決定: 検証の結果は記法の条で書き手に任せる案（B）ではなく、`report` の型付きの欄として受け取り tsukumo が描く案（A）にする
- 2026-09-26 ユーザー決定: `checks` は省略できる（要らないレポートがある）
- 2026-09-26 ユーザー決定: 「結論は読み手から見た変化で書く」と「文字列より視覚情報を優先する」は、このタスクで一緒にレポートの記法に入れる（「視覚情報を優先」は CLAUDE.md でなくレポートの記法に置く。CLAUDE.md は手の動きの規則だけを置く方針のため）

## 解くべき論点

- `status` の値の名前と数（`ok` / `ng` / `unverified` で足りるか。`skipped` を分けるか）。いまのバッジ（`badge-ok` / `badge-warn` / `badge-ng`）との対応
- 帯を `main-view.ts` の組み立てで HTML の塊として本文に入れるか、本文とは別の部品として描くか（中間レポートでも同じに出るか、セッション一覧・履歴にどう残るか）
- 内部の型で「無い」をどう表すか（`?:` を使わない規約。`favor` と同じく入口で空の配列に畳むのが素直に見える）
- プロトコルの型が変わるなら `PROTOCOL_VERSION` を上げるか
- 記法の3条を、いまの10か条・内容ごとの印の表のどこに入れるか（条を増やすか、既存の条1・「内容ごとの印」の前文に足すか）。プロンプトが長くなりすぎないように

## やること

前提の調べ直し（2026-09-26）: `report` の引数は `sdk-tool.ts` の zod（handler の検査）と `sdk-message.ts` の `reportEvents`（イベントへの変換。transcript からの復元も同じ道）の2か所で読まれ、`session-event.ts` → `session-state.ts` の記録 → `main-view.ts` の `reportMarkdown` で1つの Markdown に組まれる。`favor` は HTML の塊（`note-favor`）として本文に入り、中間レポート・最終レポート・復元のどれでも同じ経路で描かれている。前提は崩れていない。

1. `src/shared/report-check.ts` を足す: 状態の値（`ok` / `ng` / `unverified`）・1項目の型 `ReportCheck`・zod の形（`sdk-tool.ts` の検査と `sdk-message.ts` の取り出しの両方が引く）
2. `report` のイベント・記録・差し戻しの比較（`ReportDraft`）に `checks: readonly ReportCheck[]` を足す。「無い」は `sdk-message.ts` の入口で空の配列に畳む。形が変わるので `PROTOCOL_VERSION` を 23 に上げる
3. `main-view.ts` の組み立てで `conclusion` → 帯 → `body` → `favor` の順にする。帯は tsukumo が組む HTML の1行（`<div class="checks">` の中に状態のバッジ `badge-ok` / `badge-ng` / `badge-warn` と文字「OK」「NG」「未確認」）。モデルの文字列は HTML として逃がし、改行は空白に畳む。空の配列なら帯を置かない
4. 帯の class を語彙（`src/shared/report-notation.ts`）に「tsukumo が描く印」として足し、部品（`notation.tsx`）と CSS（`report-notation.module.css`）に通す
5. `report` の説明文・zod の説明と、記法の条（条1 に `checks` と「読み手から見た変化」、条8 に「文字より視覚情報」）を直す
6. `docs/display.md` のレポートの仕様・`docs/glossary.md`「report ツール」を合わせる。単体テストを足す
7. `bun run build` のうえで、E2E の fake か実画面で帯を目視する

## 注意

- 規約の本文はプロンプトとして毎ターン入るので、足す文は短く保つ
- 判断が想定より重いと分かったら、設計を書く前段と実装に分けてよい（分けるなら登録はメインが受け入れで行う）
