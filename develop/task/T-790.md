## 目的

E2E `test/e2e/background-task.test.ts` で、サイドバーのコンテキスト使用量（期待値 `61%`）が「取得中…」のまま止まって落ちる揺れを無くし、差分と無関係に `pnpm run check` が落ちないようにする（振り返り: T-739）。

## 完了条件

- 揺れの原因（取得が走らない・取得が返らない・返る前に DOM を取っている、のどれか）を特定し、`## 結果` に書く
- コンテキスト使用量の取得が済んだことを E2E が待てる形にする（決まった時間を眠らせて待たない）
- `pnpm run check` を続けて10回流し、`background-task` が1度も落ちない（回数と結果を `## 結果` に書く）。別の揺れが出たら、既存の揺れのタスク（T-776・T-738）に当たるかを見て、当たらなければ `## 結果` に書く
- `pnpm run check` が通る
- 調べて再現せず原因も立たなければ、10回の結果を添えて `dropped` で閉じてよい

## 背景

- T-739 の委譲先の `pnpm run check` で1回出た。単独では3回とも通過した。T-739 の差分とは無関係
- 表示は `src/browser/components/domain/sidebar/context-usage-row.tsx`（`PENDING_TEXT = "取得中…"`）で、取得は `src/browser/domain/context-usage.ts` の `useContextUsage(refetchKey)`（TanStack Query。`queryKey` に `refetchKey` を含め、`staleTime: 0`・`retry: false`）
- 期待値は `test/e2e/expected/background-task-*.dom.json`
- T-739 で E2E のブラウザの時計を最初から凍らせた。時計を使う待ちが取得を止めていないかも疑う
- ほかの揺れのタスク: T-776（単体テストの時間切れ）・T-738（E2E の並列化）

## やること

- 前提の確認: `useContextUsage`（`src/browser/domain/context-usage.ts`）は `refetchKey`
  （`state.lastTurnFinishedAt`）が変わるたびに `staleTime: 0` で引き直す。`background-task-short`
  場面の2回の `turn-finished`（開始・再開）はどちらも `lastTurnFinishedAtOf`
  （`src/shared/session-state.ts`）が値を更新する種類なので、どちらの後も取り直しが起きる。
  `test/e2e/scenario-run.ts` の `settledDom` は DOM の中身を見ず「100ms 間隔で2回連続同じ」
  だけで安定を判定するため、`waitForEvent("turn-finished")` の直後に `settleAndMatch` を呼ぶ
  現状の作りだと、取り直しの応答がまだ返っていない「取得中…」の DOM のまま2回連続で捉えて
  安定と誤判定しうる。これが原因の1つ目（取得は走るが、返る前に DOM を取っている）に当たる。
  前提は崩れておらず、直しが要る
- 2つの形を比べた: (a) `/rpc/contextUsage/report` の応答回数を数えるシナリオ専用の待ち
  （`waitForContextUsageRefetch`）と、(b) 取得中の要素が `aria-busy="true"` を出し、
  `settledDom` が2回連続で同じでもそれが残っていれば撮らずに待つ汎用の形。(a) は機能・経路を
  名指しする書く側の注意に頼り、似た非同期表示を足すたびに専用の待ちが要る。(b) は
  `context-usage-card.tsx`・`usage-review-card.tsx` に先例があり、表示する側が印を1つ出すだけで
  機械的に効き、将来似た表示が増えても書き足しが要らない。**(b) を採った**（`## 注意`）
- `src/browser/components/domain/sidebar/context-usage-row.tsx` の外側の `div` に、取得中
  （`usage.kind === "pending"`）だけ `aria-busy="true"` を足した
- `test/e2e/scenario-run.ts` の `settledDom` に、DOM が2回連続で同じでも
  `document.querySelector('[aria-busy="true"]')` が残っていれば待ち続ける判定を足し、
  シナリオ専用だった `recordContextUsageReports`・`waitForContextUsageRefetch` は消した
  （`background-task.test.ts` の2つの `it` は素の `waitForEvent("turn-finished", …)` に戻した）

## 注意

- 期待値の JSON を「取得中…」に書き換えて揺れを隠さない
- 待てる形は、このシナリオ専用の待ちより先に、取得中の要素が `aria-busy="true"` を出し、`settledDom`（`test/e2e/scenario-run.ts`）が `aria-busy="true"` の無くなるまで待つ汎用の形を比べる（`settledDom` は DOM が2回続けて同じなら通すので、取得中の表示が続いていても落ち着いたとみなす。`aria-busy` は `token-usage` の2つのカードに先例がある）。決めた形を `docs/design.md` 10章「E2E の揺れを生まない書き方」の「撮る前に非同期の取得を待つ」条に反映する（節がまだ無ければ T-792 の本文の背景に書き足す。2026-09-27 E2E の失敗の振り返り）

## 結果

- 原因: 返る前に DOM を取っている。`settledDom` は DOM が2回同じなら通すので、`turn-finished` 直後の「取得中…」を撮りうる。取得中の行が `aria-busy="true"` を出し、`settledDom` がそれの消えるまで待つ汎用の形にした（応答の回数を数える専用の待ちと比べて採用。design.md 10章の条2に反映）
- 検証コマンド: 2729 pass / 0 fail、E2E 28 pass。`background-task` 単独 10/10、`pnpm run test:e2e` 4/4。専用の待ちの版では `pnpm run check` 10/10。別の揺れは出なかった
- 振り返り: 受け入れのときにメインが直したもの・委譲先が入れ子のエージェントを立てた（ドラフト 1件）
