## 目的

`report` の `body`（いまは Markdown の文字列）を、型の付いた塊（表・流れ・進み具合・数の塊など）の配列として受け取り、tsukumo が塊の種類ごとに決まった部品（HTML のテンプレート）へ当てはめて描く形にできるかを詰める。記法の条をモデルへの心がけではなく型で守らせ、見た目を tsukumo 側で揃えるのがねらい。ユーザーは方向性に同意しているが「もっと考えないといけない」としているので、このタスクでは実装せず、判断の材料と案を提案書にまとめる。

## 完了条件

- `docs/research/` に提案書を書く（既存の `report-tool-trial.md`・`report-notation-shortening.md` と同じ置き場）。少なくとも次を含む:
  - 最初に作る塊の種類の一式と、それぞれの schema の案（`checks` と同じく zod で境界検証する前提）
  - 当てはまる部品が無いときの逃げ道（`{ kind: "markdown" }` のような塊）と、逃げ道の使われ方を数えて部品を足す判断の回し方
  - 塊の中の文字にインラインの Markdown（強調・inline code・リンク）をどこまで許すか
  - 過去の記録（文字列の `body`）との互換。記録は引数のまま残り、表示のときに導出している（`src/shared/main-view.ts`）
  - 今ある記法の条・検査（`report-review.ts`）・整形（`report-tidy.ts`）・HTML の許可リスト（`src/shared/report-notation.ts`）のうち、型に置き換わって要らなくなるものと残るもの
  - ツールの定義が毎ターンの文脈に載る重さ（schema の大きさの見積もり。MCP ツールの説明文は既定で 2048 字まで）
  - 段階的に移す順番
- 提案を実装に分けたタスクの案を `develop/direction.md` の `## エージェントのドラフト` に書く（登録はユーザーの承認のあと）
- T-678（進み具合の印）の本文を提案の結論に合わせて直す（塊の種類として作るなら、その旨を `## 決まっていること` に移し、論点「型付きの欄か、本文の記法か」を外す）。直すときは実装の広がりを見て `difficulty` も見直す
- `bun run check` が通る

## 背景

- `report` ツールの定義は `src/server/report/core/report-tool.ts`。T-676 で型付きの欄 `checks` が入り、結論の下に帯で描かれるようになった。これが「型で受けて部品で描く」の最初の例
- いまの流れは「検査（`report-review.ts`）→ 記録（引数のまま）→ 整形（`src/shared/report-tidy.ts`）→ 組み立て（`src/shared/main-view.ts`）→ Markdown の描画（`src/browser/components/page/conversation/components/main-view/markdown/`）」（`docs/display.md` 4.2 付近）
- 記法の条の本文は `src/server/report/core/report-notation.ts`。表の見出し・4文以上の段落など、機械で判定できる条は検査が差し戻している
- 前例（2026-09-26 に会話で挙げたもの。提案書で読み比べる）: Vercel Labs の json-render（https://github.com/vercel-labs/json-render 。zod で部品の catalog を定義し、モデルの出力をその中に縛って React などで描く。いちばん近い）・Google の A2UI（https://a2ui.org/ 。信頼した部品の catalog と、流しながら更新できる平らな部品の表現）・Adaptive Cards（https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/implement-a-renderer 。要素ごとの `fallback` と「知らない要素は飛ばして描き続ける」規則。逃げ道の設計の手本）。MCP Apps（SEP-1865）はサーバが HTML ごと渡す方式で、この設計とは向きが逆

## 解くべき論点

- 塊の種類をどこまで細かく分けるか（少なすぎると逃げ道ばかり使われ、多すぎるとツールの定義が重くなりモデルが選び損ねる）
- mermaid や chart を「塊の種類」にするか、構造（ノードと辺・系列）から tsukumo が組み立てるか
- 見出しと節の構造を塊として持つか（`{ kind: "section", heading, blocks }` のような入れ子にするか、平らな並びに見出しの塊を混ぜるか）

## 注意

- 調べて、構造化しても今の記法より読み手にとって良くならない（逃げ道がほとんどを占めるなど）と分かったら、その根拠を提案書に書いて、実装のタスク案は出さずに閉じてよい
