## 目的

`docs/research/server-procedure-proposal.md` の段3。画面からのコマンドを機能ごとの契約と手続きにし、どのコマンドも「ルータ → 契約 → 手続き → 機能の `core`」の同じ4段で辿れるようにする。

## 完了条件

- T-652 の機能ごとの受け手の表が、`docs/design.md` 2章「コマンドの受け手と手続きの置き方」の形に写っている: 契約は `src/shared/contract/<機能>.ts`（`session` `character-pack` `chat` `visit` `usage-review` `host` の6機能）、手続きは `<機能>/adapter/<機能>-procedure.ts`、束ねは `src/router.ts`（`src/command-route.ts` はここへ吸われて消える）
- 断る条件は契約の `meta`（`{ chatOnly, idleTurn }`。値は段1の列と同じ `false` か `FRAME_ERROR_REASON` の定型文）へ移り、段1の行からは列が消えている（二重に持たない）。`meta` を見るのは `rpc-guard.ts` の1箇所で、順は「雑談の外か」→「ターン中か」のまま
- 手続きの中身は段1の受け手（`<機能>/core/<機能>-command.ts` の行）へ委ねる数行で、`session` の手続きは `CommandSession` を oRPC の context で受ける。機能どうしの辺の表は増えていない
- `/ws` のメッセージを oRPC の `RPCHandler` が受け、`src/shared/command.ts` の `ClientCommand` の和と `parseClientCommand`、`session-socket.ts` の `receive` が消えている
- 受け取る1メッセージの上限（`MAX_MESSAGE_BYTES`、16 MiB）と、起動トークン・`Origin` の照合が保たれている
- ブラウザの `src/browser/stores/session.tsx` の `dispatch` が型付きの client で呼んでいる
- 押し出し（`hello` と `events` のフレーム、`subscribe`）は変えていない
- `bun run check` が通り、fake driver で依頼・答え・キャラの切り替え・雑談の切り替え・画像2枚つきの依頼が目視で通った

## 背景

- コマンドは `src/shared/command.ts`（約590行、28種）で定義され、`src/server/view-server/adapter/session-socket.ts` の `receive` が `parseClientCommand` で検証して `session-manager` の `dispatch` へ渡す
- 読み取り5本は T-653 で先に手続きになっている
