## 目的

タスクの管理（`develop/task/` の1件1ファイルと git の外の台帳）を GitHub Projects へ移すかを検討する。特に、コミットを積まずに着手の排他制御ができるかを見る（2026-09-27 ユーザーの指示）。

## 完了条件

- `docs/research/` に検討の結果を書く。少なくとも「解くべき論点」の各項に結論と理由がある
- 移す・移さないの推奨と、移すなら段取り（スキルの何を変えるか・移行の順番）を書く
- 後段のタスク（T-734 の状態名の改名、T-735 の履歴の置き場の検討）の本文を結論に合わせて直す（移すなら改名は GitHub Projects の状態の設計に畳む、など）
- `bun run check` が通る

## 背景

- 運用の正典は `~/.claude/skills/task-workflow/WORKFLOW.md`（claude-skills のリポジトリ。全プロジェクト共通）と、このリポジトリの上乗せの `docs/workflow.md`
- 今の排他制御: `task claim` が git の外の台帳に着手の印を立て、タスクファイルの状態はコミットで `main` へ送る（`task ship`）。採番の錠もある
- 登録時、`develop/task/` を使っているのはこのリポジトリだけ

## 解くべき論点

- GitHub Projects（と Issues）の API で、着手の印を原子的に取れるか（競合したときに片方だけが勝つ仕組みがあるか）
- `/loop /next-task` の無人運転・オフライン・`gh` の認証・API の回数制限への影響
- タスクの本文（背景・完了条件・結果）をどこに置くか。git の履歴に残らなくなることの損得
- 外部サービスへの公開になる範囲（非公開の Project でも、会話内容の扱いの規約（`docs/coding-standards.md`「会話内容の扱い」）に触れないか）

## 注意

- 検討と提案だけ。GitHub に Project や Issue を作るのは外部への公開に当たるので、試すならユーザーの承認を得る
